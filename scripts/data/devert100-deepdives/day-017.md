=== intro ===
Day 16 used opposite-ends two pointers on a **pair**. Day 15 used sortedness to make **duplicates adjacent**. Today needs both at once, plus one more move: turning a three-element problem into a two-element one.

> When a problem asks for triplets, fix one element and the rest is a pair problem you already know. Sorting first buys you two things at once: a two-pointer search for the pair, and duplicates that sit next to each other so you can skip them.

=== problem ===
Given an integer array `nums`, return **all unique triplets** `[a, b, c]` taken from three **different indices** with `a + b + c == 0`.

```text
nums   = [-1, 0, 1, 2, -1, -4]
answer = [[-1, -1, 2], [-1, 0, 1]]
```

### What "unique" means

Uniqueness is about the **values**, not the indices. In the example, `-1` appears at index 0 and index 4:

| indices | values | sum |
| :------ | :----- | --: |
| (0, 1, 2) | -1, 0, 1 | 0 |
| (1, 2, 4) | 0, 1, -1 | 0 |
| (0, 3, 4) | -1, 2, -1 | 0 |

The first two rows are the **same triplet** `{-1, 0, 1}` built from different indices. It must appear in the output once. The third row uses two different `-1`s, which is allowed - they are different indices - so `[-1, -1, 2]` is a valid triplet.

The order of the triplets in the output, and the order inside each triplet, do not matter.

### More examples

```text
[0, 1, 1]      ->  []             no triplet sums to 0
[0, 0, 0]      ->  [[0, 0, 0]]    three different indices, all 0
```

### Constraints

`3 <= n <= 3000`, values between `-10^5` and `10^5`. At `n = 3000`, `O(n^3)` is about `4.5 * 10^9` triplets - too slow. `O(n^2)` is about `4.5 * 10^6` - fine. Sums fit in an `int` (at most `3 * 10^5` in size).

=== pattern ===
**Sorting + Two Pointers**: fix the first element, then run opposite-ends two pointers on the rest.

### The reduction

If `nums[i]` is the first element of a triplet, the other two must sum to `-nums[i]`. That is Two Sum - and on a **sorted** array, Two Sum is the opposite-ends two pointer from Day 16:

```text
sorted:   [-4, -1, -1, 0, 1, 2]
            i   l              r       need nums[l] + nums[r] == -nums[i]

sum too small  ->  l++    (nums[l] is finished: every partner left of r is smaller)
sum too big    ->  r--    (nums[r] is finished: every partner right of l is bigger)
sum == 0       ->  record, then move both
```

`n` choices of `i`, each with an `O(n)` two-pointer scan: `O(n^2)`.

### Why sorting is worth it twice

1. **It makes the pair search a two pointer.** On sorted values, "too small" has exactly one fix (make the small end bigger), so each step discards one element for good - the same elimination argument as Day 16.
2. **It makes duplicates adjacent** - Day 15's observation. Two equal values for `i` would produce exactly the same set of pairs, so the second one can be skipped with one comparison: `nums[i] == nums[i - 1]`. Same for `l` and `r` after a match.

Sorting costs `O(n log n)`, which disappears under the `O(n^2)` that follows.

### Recognising it

Reach for sort + two pointers when:

- you need **pairs, triplets or quadruplets** that hit a target sum
- you must return **unique** combinations by value (not indices)
- the output does not need the original positions - so sorting loses nothing

The mental question:

> If I fix one element, is what remains a sorted pair search I already know how to do?

That generalises: 4Sum (LC 18) fixes two elements and runs the same two pointer inside, `O(n^3)`.

=== bruteForce ===
The definition says "three different indices that sum to zero". So try every set of three indices, and use a set to throw away repeated value-triplets.

### Step logic

1. For every `i < j < k`:
2. If `nums[i] + nums[j] + nums[k] == 0`, sort those three values (so `{0, 1, -1}` and `{-1, 0, 1}` look identical) and add the sorted list to a set.
3. Return the set's contents as a list.

### Java

```java
class Solution {
    public List<List<Integer>> threeSum(int[] nums) {

        int n = nums.length;
        Set<List<Integer>> found = new LinkedHashSet<>();

        for (int i = 0; i < n; i++) {
            for (int j = i + 1; j < n; j++) {
                for (int k = j + 1; k < n; k++) {
                    if (nums[i] + nums[j] + nums[k] == 0) {
                        List<Integer> t = Arrays.asList(nums[i], nums[j], nums[k]);
                        Collections.sort(t);    // canonical order, so the set can dedupe
                        found.add(t);
                    }
                }
            }
        }

        return new ArrayList<>(found);
    }
}
```

### Why it works

Every choice of three different indices is tried, so no triplet is missed. Sorting each hit gives equal value-triplets the same representation, and `List.equals` / `hashCode` compare contents, so the set keeps one of each.

### Complexity

**Time:** `O(n^3)` - **Space:** `O(t)` for the set of `t` distinct triplets found

### Where it hurts

Two separate kinds of waste:

1. **The third loop is a search the sum already answers.** Once `i` and `j` are chosen, the third value is forced: it must be `-(nums[i] + nums[j])`. The inner loop walks the whole array to find a value we already know. Even fixing only `i`, the remaining question - "which two values sum to `-nums[i]`?" - is a pair problem with a known `O(n)` answer on sorted input.
2. **Duplicates are generated, then thrown away.** Row 12 did the full work of finding `{-1, 0, 1}` a second time, only for the set to discard it. With many repeated values (say forty `0`s), the brute force produces the triplet `[0, 0, 0]` thousands of times. The set fixes the output, but the work has already been done.

> Fix one element and the rest is Two Sum. Sort first, and Two Sum becomes two pointers - and duplicates become neighbours you can skip instead of results you have to filter.

=== optimization ===
Sort the array. For each `i`, two-pointer search `i+1 .. n-1` for pairs summing to `-nums[i]`, skipping duplicate values as you go.

### The algorithm

1. Sort `nums`.
2. For `i` from `0` to `n - 3`:
   - If `nums[i] > 0`, **stop**: everything after it is `>= nums[i] > 0`, so no three of them can sum to zero.
   - If `i > 0` and `nums[i] == nums[i - 1]`, **skip**: this value already produced every triplet it can.
   - `l = i + 1`, `r = n - 1`. While `l < r`:
     - `sum = nums[i] + nums[l] + nums[r]`
     - `sum < 0` -> `l++` (need bigger)
     - `sum > 0` -> `r--` (need smaller)
     - `sum == 0` -> record `[nums[i], nums[l], nums[r]]`, then `l++`, `r--`, and keep moving `l` past values equal to the one just used, and `r` likewise.

### Why the two-pointer moves are safe

This is Day 16's argument with sums instead of areas. On sorted values, if `nums[i] + nums[l] + nums[r] < 0`, then pairing `nums[l]` with any `r' < r` gives an even smaller sum. So `nums[l]` has no partner left that works - discard it with `l++`. Symmetrically, a sum that is too big means `nums[r]` is finished.

### Why the duplicate skips are safe

- **For `i`:** if `nums[i] == nums[i - 1]`, the run for `i - 1` searched a range that contains this run's range (`i .. n-1` versus `i+1 .. n-1`), with the same target. Every triplet this run could find, the previous run already found.
- **For `l` and `r` after a match:** once `[nums[i], x, y]` is recorded, any other pair starting with value `x` must end with `y` to hit the same target - the same triplet. So skip every `l` still equal to `x`, and every `r` still equal to `y`.

The skips are not an optimisation on top of a correct algorithm. They **are** the uniqueness guarantee - without them the output contains repeats.

`i` stops at `n - 3 = 3`. Result: `[[-1, -1, 2], [-1, 0, 1]]` - the same two triplets as the brute force, found **once each**, with no set.

Count the work: 7 sums computed, against the brute force's 20. And row `i = 2` is the duplicate skip doing exactly what the brute force's set had to do after the fact: `-1` already had its turn at `i = 1`.

### Dry run where the inner skip matters

```text
sorted = [-2, 0, 0, 2, 2]
```

| i | l | r | values | sum | action |
| -: | -: | -: | :----- | --: | :----- |
| 0 | 1 | 4 | -2, 0, 2 | 0 | record `[-2, 0, 2]`; `l=2`, `r=3`; `nums[2]==nums[1]` so `l=3`; now `l == r`, stop skipping |
| 0 | 3 | 3 | - | - | run ends |
| 1 | 2 | 4 | 0, 0, 2 | 2 | too big, `r--` |
| 1 | 2 | 3 | 0, 0, 2 | 2 | too big, `r--` |
| 1 | 2 | 2 | - | - | run ends |
| 2 | - | - | - | - | `nums[2] == nums[1]`, skip |

`i` stops at `n - 3 = 2`. Result `[[-2, 0, 2]]`. Without the inner skip, `l = 2, r = 3` would have produced `-2 + 0 + 2 = 0` again - a duplicate `[-2, 0, 2]`.

=== complexity ===
### Time

Sorting is `O(n log n)`. Then up to `n` values of `i`, each with a two-pointer run in which `l` and `r` only move toward each other: `O(n)` per run.

```text
O(n log n) + O(n^2)  =  O(n^2)
```

The duplicate-skip `while` loops do not add a factor: they move the same `l` and `r` that the outer `while` moves, so the run is still at most `n` steps total.

### Space

A few integers, plus whatever the sort uses (Java's `Arrays.sort` on `int[]` is a dual-pivot quicksort, `O(log n)` stack). The output list is not counted.

```text
O(1) extra   (ignoring the sort's stack and the output)
```

### Comparison

| Approach | Time | Extra space | Duplicates handled by |
| :------- | ---: | ----------: | :-------------------- |
| Three loops + set | `O(n^3)` | `O(t)` set | filtering after the fact |
| Fix `i` + HashSet Two Sum | `O(n^2)` | `O(n)` per `i` | a set of triplets, messy |
| Sort + two pointers | **`O(n^2)`** | **`O(1)`** | skipping adjacent equals |

Can it beat `O(n^2)`? Not in general - 3Sum is the classic problem believed to need roughly quadratic time, which is why "3SUM-hard" is a named complexity class. If an interviewer asks for better, the honest answer is that `O(n^2)` is the expected bound.

=== implementation ===
```java
class Solution {
    public List<List<Integer>> threeSum(int[] nums) {

        Arrays.sort(nums);
        int n = nums.length;
        List<List<Integer>> result = new ArrayList<>();

        for (int i = 0; i < n - 2; i++) {
            if (nums[i] > 0) break;                          // smallest is positive: no more zeros
            if (i > 0 && nums[i] == nums[i - 1]) continue;   // same first value, same triplets

            int l = i + 1, r = n - 1;
            while (l < r) {
                int sum = nums[i] + nums[l] + nums[r];
                if (sum < 0) {
                    l++;
                } else if (sum > 0) {
                    r--;
                } else {
                    result.add(Arrays.asList(nums[i], nums[l], nums[r]));
                    l++;
                    r--;
                    while (l < r && nums[l] == nums[l - 1]) l++;   // skip repeated second values
                    while (l < r && nums[r] == nums[r + 1]) r--;   // skip repeated third values
                }
            }
        }

        return result;
    }
}
```

### The lines that matter

**1.**

```java
if (i > 0 && nums[i] == nums[i - 1]) continue;   // same first value, same triplets
```

Compare with the **previous** element, not the next one. `nums[i] == nums[i + 1]` would skip the **first** `-1` in `[-1, -1, 2]` and lose the triplet that uses both. Comparing backwards means the first copy runs (and may use later copies as `l`), and only the later copies are skipped.

**2.**

```java
result.add(Arrays.asList(nums[i], nums[l], nums[r]));
l++;
r--;
while (l < r && nums[l] == nums[l - 1]) l++;   // skip repeated second values
```

Move **both** pointers after a match: moving only one cannot keep the sum at zero unless the value repeats - which is exactly the case we are skipping. Then step past every copy of the value just used. `l - 1` is the value just recorded, so this compares against what was used, not against an unvisited neighbour.

**3.**

```java
if (nums[i] > 0) break;                          // smallest is positive: no more zeros
```

After sorting, `nums[i]` is the smallest of the three. If it is positive, the sum is positive - for this `i` and every later one. `break`, not `continue`.

### Java notes

- `Arrays.sort(nums)` sorts the caller's array in place. LeetCode does not care; in production code, sort a copy if the caller needs the original order.
- `Arrays.asList(a, b, c)` returns a fixed-size list backed by an array - fine for output. It boxes the three `int`s into `Integer`s.
- `nums[r + 1]` in the skip loop is safe: `r` was just decremented from a valid index, so `r + 1 <= n - 1`.
- The sum of three values in `[-10^5, 10^5]` is at most `3 * 10^5` in size - no overflow. 4Sum on LeetCode does overflow `int` with its larger target, so use `long` there.

=== edgeCases ===
### No triplet

```text
[0, 1, 1]  ->  []
```

Sorted `[0, 1, 1]`: `i = 0`, `l = 1`, `r = 2`, the only sum is `0 + 1 + 1 = 2` - too big, `r--`, the run ends. Empty result.

### Three zeros

```text
[0, 0, 0]  ->  [[0, 0, 0]]
```

Three different indices, all holding `0`. The `nums[i] > 0` check does not fire (`0` is not positive).

### Many zeros

```text
[0, 0, 0, 0]  ->  [[0, 0, 0]]
```

The triplet appears once. `i = 1` is skipped as a duplicate of `i = 0`, and inside `i = 0` the inner skip stops a second match.

### All positive

```text
[1, 2, 3]  ->  []
```

`nums[0] = 1 > 0`, the loop breaks immediately.

### All negative

```text
[-3, -2, -1]  ->  []
```

Every sum is negative; `l` walks right until it meets `r`.

### Duplicates in the second and third positions

```text
[-2, 0, 0, 2, 2]  ->  [[-2, 0, 2]]
```

The second dry run. Without the inner skip loops this returns `[-2, 0, 2]` twice.

### A repeated value used twice in one triplet

```text
[-1, -1, 2]  ->  [[-1, -1, 2]]
```

The case that breaks a "compare with the next element" skip: `nums[0] == nums[1]` would skip `i = 0`, and `i = 1` alone cannot find a second `-1`.

### Several triplets sharing a first value

```text
[3, 0, -2, -1, 1, 2]  ->  [[-2, -1, 3], [-2, 0, 2], [-1, 0, 1]]
```

Sorted `[-2, -1, 0, 1, 2, 3]`. `i = 0` (`-2`) finds two different pairs in one run - the reason the loop continues after a match instead of stopping.

=== takeaway ===
> When you see **"all unique triplets / quadruplets summing to a target"**, think **sort, fix the first element, two pointers on the rest, skip adjacent duplicates**.

### The core observation

Fixing `nums[i]` turns 3Sum into Two Sum with target `-nums[i]`. Sorting makes that Two Sum an `O(n)` opposite-ends scan (Day 16's elimination: a sum that is too small means the left value is finished), and puts equal values side by side so duplicates are skipped by comparing with a neighbour (Day 15) instead of being filtered through a set.

### The pattern trigger

```text
                     sort
                       |
                       v
     for i:  nums[i] > 0 ?  -> break
             same as nums[i-1] ? -> continue
                       |
                       v
          l = i + 1          r = n - 1
                       |
                       v
           sum < 0 -> l++    sum > 0 -> r--
           sum == 0 -> record, l++, r--,
                       skip equal l, skip equal r
```

### The common mistakes

**Skipping duplicates with `nums[i] == nums[i + 1]`.** Loses `[-1, -1, 2]` - the first copy is the one that must run.

**Forgetting the inner skips.** Correct triplets, repeated. On `[-2, 0, 0, 2, 2]` the output has `[-2, 0, 2]` twice.

**Stopping the inner loop after the first match.** One `i` can be part of several triplets.

**Using a `HashSet<List<Integer>>` to dedupe the two-pointer output.** It works, but it hides a missing skip instead of fixing it, and costs extra space.

**`continue` instead of `break` on `nums[i] > 0`.** Still correct, just wasted work - every later `i` is also positive.

### What to remember in six months

> k-Sum = sort + fix (k - 2) elements + one two-pointer scan. Duplicates are skipped at every level by comparing with the previous value at that level.

3Sum Closest (LC 16) is the same loop tracking `|sum - target|` instead of recording matches. 4Sum (LC 18) adds one more fixed loop with its own duplicate skip.
