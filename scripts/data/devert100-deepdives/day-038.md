=== intro ===
Yesterday we made one stack smarter by storing extra information in it. Today we take two plain stacks and make them behave like a completely different structure - a queue - and meet the idea that decides whether that is cheap or expensive: **amortized cost**.

> A stack reverses order. Reverse twice and you are back to the original order. The whole problem is deciding **when** to do the second reversal - and the answer is "as late as possible, and never undo it".

=== problem ===
Implement a first-in-first-out queue, `MyQueue`, using **only two stacks** and only standard stack operations (push to top, pop/peek from top, size, is-empty).

| method | does |
| :----- | :--- |
| `push(x)` | add `x` to the back of the queue |
| `pop()` | remove and return the element at the front |
| `peek()` | return the front element without removing it |
| `empty()` | `true` if the queue holds nothing |

### The example

```text
MyQueue q = new MyQueue();
q.push(1);
q.push(2);
q.peek();    // 1
q.pop();     // 1
q.empty();   // false
```

LeetCode's expected output: `[null, null, null, 1, 1, false]`.

### Why this is not trivial

A stack and a queue disagree about which element comes out next:

```text
pushed in order:   1, 2, 3

stack pops:        3, 2, 1      (last in, first out)
queue pops:        1, 2, 3      (first in, first out)
```

The element a queue wants - the **oldest** - is at the **bottom** of a stack, the one place a stack cannot reach. Getting to it means removing everything on top of it first, and those elements have to go somewhere. That somewhere is the second stack.

### What the constraints tell you

- `1 <= x <= 9`, at most `100` calls, and `pop`/`peek` are never called on an empty queue.
- The follow-up: make every operation **amortized `O(1)`** - `n` operations in `O(n)` total, even if one particular call is slower.

=== pattern ===
**Two Stacks** - one for input, one for output.

The key fact: pouring one stack into another **reverses** it.

```text
in (bottom -> top):   1  2  3          3 is on top - newest first
pour into out:        pop 3, push 3
                      pop 2, push 2
                      pop 1, push 1
out (bottom -> top):  3  2  1          1 is on top - oldest first
```

After one pour, `out` pops in queue order. So:

- `push` always goes onto `in`. New elements are the newest; they belong at the back.
- `pop` / `peek` read from `out`. Its top is the oldest element.
- When `out` runs dry, pour **all** of `in` into it - and only then.

### Why "only when empty"

Everything in `out` is older than everything in `in` - they arrived first. So as long as `out` has anything, its top is the true front of the queue, and nothing in `in` can jump ahead of it. Pouring `in` onto a non-empty `out` would put newer elements **on top** of older ones, and the next pop would return the wrong one.

### Recognising it

Reach for the two-stack queue when:

- you need FIFO behaviour but only have LIFO tools (or vice versa - the bonus problem)
- a problem asks for "amortized" complexity: some operations may be slow if they are rare enough that the total stays linear
- you need a queue that also reports its min or max in `O(1)` - build it from two of yesterday's min-stacks

The mental question:

> Is work I do now going to be **reused** by later operations - or am I going to undo it and redo it? If it is reused, it can be paid for once.

=== bruteForce ===
Before thinking about cost, write the version that obviously works.

Keep every element in `in`, newest on top. To reach the front, pour everything into `out` (which reverses it, putting the oldest on top), take the top, then pour everything **back** so the next `push` finds things the way it expects.

### Step logic

- `push(x)`: push onto `in`.
- `pop()`: pour `in` into `out`; pop `out`'s top; pour `out` back into `in`.
- `peek()`: the same, but peek instead of pop.
- `empty()`: `in` is empty (everything always lives there between calls).

### Dry run

A longer sequence than LeetCode's, so that pushes and pops interleave:

```text
push 1, push 2, push 3, pop, push 4, pop, pop, pop, empty
```

A **move** is one element popped from one stack and pushed onto the other. Stacks are shown bottom -> top.

| # | call | in before | work | in after | returns | moves |
| -: | :--- | :-------- | :--- | :------- | :------ | ----: |
| 1 | `push(1)` | `[]` | push | `[1]` | - | 0 |
| 2 | `push(2)` | `[1]` | push | `[1, 2]` | - | 0 |
| 3 | `push(3)` | `[1, 2]` | push | `[1, 2, 3]` | - | 0 |
| 4 | `pop()` | `[1, 2, 3]` | pour 3 into out (`out = [3, 2, 1]`), pop `1`, pour 2 back | `[2, 3]` | **1** | 5 |
| 5 | `push(4)` | `[2, 3]` | push | `[2, 3, 4]` | - | 0 |
| 6 | `pop()` | `[2, 3, 4]` | pour 3 (`out = [4, 3, 2]`), pop `2`, pour 2 back | `[3, 4]` | **2** | 5 |
| 7 | `pop()` | `[3, 4]` | pour 2 (`out = [4, 3]`), pop `3`, pour 1 back | `[4]` | **3** | 3 |
| 8 | `pop()` | `[4]` | pour 1 (`out = [4]`), pop `4`, pour 0 back | `[]` | **4** | 1 |
| 9 | `empty()` | `[]` | check | `[]` | **true** | 0 |

Output `1, 2, 3, 4, true` - correct FIFO order. Total moves: **14**, for four elements.

### Java

```java
class MyQueue {

    private final Deque<Integer> in = new ArrayDeque<>();
    private final Deque<Integer> out = new ArrayDeque<>();

    public MyQueue() {
    }

    public void push(int x) {
        in.push(x);
    }

    public int pop() {
        while (!in.isEmpty()) out.push(in.pop());     // reverse: oldest on top
        int front = out.pop();
        while (!out.isEmpty()) in.push(out.pop());    // reverse back
        return front;
    }

    public int peek() {
        while (!in.isEmpty()) out.push(in.pop());
        int front = out.peek();
        while (!out.isEmpty()) in.push(out.pop());
        return front;
    }

    public boolean empty() {
        return in.isEmpty();
    }
}
```

### Complexity

**Time:** `push` `O(1)`; `pop` and `peek` `O(n)` each - **Space:** `O(n)`

### Where it hurts

Look at row 4. After pouring, `out` was `[3, 2, 1]` - the remaining elements **in perfect queue order**, `2` next, then `3`. Then we poured them back into `in`, reversing them again. In row 6 we poured them into `out` again to get... the same order, plus `4` underneath.

Every `pop` reverses the stack, uses one element, and then **undoes the reversal**. The next `pop` redoes it. The pour-back exists only so that `push` can keep using `in` - but `push` never needed `out` to be empty. New elements go to the back of the queue; they can wait in `in` until the old ones are gone.

With `n` elements and `n` pops, the moves add up to about `n^2`: 14 here for just 4 elements.

> The reversal into `out` is useful work. Undoing it is pure waste. Keep `out` as it is, and only refill it when it is empty.

=== optimization ===
Stop pouring back.

### The key observation

Once elements are in `out`, they are in queue order, and **every element in `out` is older than every element in `in`**. So:

1. `out`'s top is always the true front, whenever `out` is non-empty.
2. Elements in `in` cannot be needed until `out` is empty.
3. When `out` is empty, pouring `in` into it puts the oldest remaining element on top - correct again.

Each element is therefore moved **at most once** in its whole life: pushed to `in`, moved to `out` once, popped from `out`.

### Step by step

- `push(x)`: push onto `in`.
- `pop()` / `peek()`: if `out` is empty, pour all of `in` into `out`. Then pop / peek `out`.
- `empty()`: both stacks are empty.

### Dry run - same sequence

| # | call | out empty? | work | in after | out after | returns | moves |
| -: | :--- | :--------- | :--- | :------- | :-------- | :------ | ----: |
| 1 | `push(1)` | - | push to in | `[1]` | `[]` | - | 0 |
| 2 | `push(2)` | - | push to in | `[1, 2]` | `[]` | - | 0 |
| 3 | `push(3)` | - | push to in | `[1, 2, 3]` | `[]` | - | 0 |
| 4 | `pop()` | yes | pour 3, then pop `1` | `[]` | `[3, 2]` | **1** | 3 |
| 5 | `push(4)` | - | push to in | `[4]` | `[3, 2]` | - | 0 |
| 6 | `pop()` | no | pop `2` | `[4]` | `[3]` | **2** | 0 |
| 7 | `pop()` | no | pop `3` | `[4]` | `[]` | **3** | 0 |
| 8 | `pop()` | yes | pour 1, then pop `4` | `[]` | `[]` | **4** | 1 |
| 9 | `empty()` | - | both empty | `[]` | `[]` | **true** | 0 |

Same output, `1, 2, 3, 4, true`. Total moves: **4** - one per element - instead of 14.

Row 5 is the important one: `4` arrives while `out` still holds `2` and `3`. It waits in `in`. Rows 6 and 7 serve `2` and `3` straight from `out`. Only at row 8, with `out` empty, does `4` get moved.

### What goes wrong if you pour when `out` is not empty

Suppose row 6 poured `in` into `out` anyway:

```text
before:  in = [4]    out = [3, 2]      (2 on top - the true front)
pour:    out = [3, 2, 4]               (4 now on top)
pop  ->  4                             wrong - 2 was pushed first
```

The "only when empty" condition is not an optimisation. It is what keeps the answer correct.

### Amortized `O(1)` - what it means

Row 4 did 3 moves; row 8 did 1; every other call did 0. One call can cost `O(n)` - that is unavoidable, since the first `pop` after `n` pushes has to dig out the bottom element. But count the work **per element** instead of per call:

```text
each element, over its whole life:
   1 push onto in
   1 pop from in  + 1 push onto out      (the single move)
   1 pop from out
 = 4 stack operations, no matter what order the calls come in
```

So any sequence of `m` calls does at most about `4m` stack operations. Spread over the `m` calls, that is a constant per call: **amortized `O(1)`**. The expensive pour is pre-paid by the cheap pushes that put those elements there.

This is the sentence to say out loud in an interview: *"Each element is moved from `in` to `out` at most once, so the total work over `n` operations is `O(n)`, which is amortized `O(1)` per operation - even though a single pop can be `O(n)`."*

=== complexity ===
### Time

```text
push:          O(1)
pop / peek:    amortized O(1), worst case O(n) for a single call
empty:         O(1)
```

### Space

Every element lives in exactly one of the two stacks.

```text
O(n)
```

### Comparison

| Approach | push | pop / peek | moves for the 9-call example | Total for `n` pushes + `n` pops |
| :------- | ---: | ---------: | ---------------------------: | ------------------------------: |
| Pour there and back on each pop | `O(1)` | `O(n)` | 14 | `O(n^2)` |
| Keep front on top of one stack (pour on push) | `O(n)` | `O(1)` | - | `O(n^2)` |
| Lazy transfer, only when `out` is empty | `O(1)` | **amortized `O(1)`** | **4** | **`O(n)`** |

The middle row is the other common first attempt: on every `push`, pour everything into the spare stack, push `x`, and pour back, so the oldest element is always on top. It just moves the `O(n)` from `pop` to `push`.

### Amortized is not average

"Average" depends on the input being random. "Amortized" is a guarantee about the **worst-case sequence**: no matter how an adversary orders the calls, `m` calls cost `O(m)` total. A single call can still be slow - if you need a hard per-call bound (real-time systems), this structure does not give one.

=== implementation ===
```java
class MyQueue {

    private final Deque<Integer> in = new ArrayDeque<>();    // newest on top
    private final Deque<Integer> out = new ArrayDeque<>();   // oldest on top

    public MyQueue() {
    }

    public void push(int x) {
        in.push(x);
    }

    public int pop() {
        moveIfNeeded();
        return out.pop();
    }

    public int peek() {
        moveIfNeeded();
        return out.peek();
    }

    public boolean empty() {
        return in.isEmpty() && out.isEmpty();
    }

    // Refill `out` only when it is empty - otherwise newer elements would
    // land on top of older ones and break FIFO order.
    private void moveIfNeeded() {
        if (out.isEmpty()) {
            while (!in.isEmpty()) {
                out.push(in.pop());
            }
        }
    }
}
```

### The lines that matter

**1.**

```java
if (out.isEmpty()) {
```

The correctness condition and the complexity argument in one line. Without it the order breaks (newer on top of older); with it, every element is moved at most once.

**2.**

```java
out.push(in.pop());
```

The reversal. `in` gives up its newest element first, so the oldest ends up on top of `out`.

**3.**

```java
return in.isEmpty() && out.isEmpty();
```

Both stacks. After `push(1), push(2), pop()`, `in` is empty and `out` still holds `2`. Checking only `in` would report an empty queue that is not empty.

### The bonus: Stack using Queues (LC 225)

The mirror problem. With one queue, make the newest element the front by rotating the older ones behind it on every push:

```java
class MyStack {

    private final Queue<Integer> q = new ArrayDeque<>();

    public MyStack() {
    }

    public void push(int x) {
        q.offer(x);
        // Rotate the older elements behind x, so x is at the front.
        for (int i = 0; i < q.size() - 1; i++) {
            q.offer(q.poll());
        }
    }

    public int pop() {
        return q.poll();
    }

    public int top() {
        return q.peek();
    }

    public boolean empty() {
        return q.isEmpty();
    }
}
```

Here `push` is `O(n)` and `pop`/`top` are `O(1)`. There is **no** amortized trick this time: rotating does not leave the queue in a state that helps later pushes, so the work cannot be pre-paid. You pick which operation to make expensive.

### Java notes

- `ArrayDeque` used through `push`/`pop`/`peek`/`isEmpty` is a stack - those methods all work on the head. That stays inside the "standard stack operations" rule. Avoid `java.util.Stack`, a legacy synchronized class.
- `out.peek()` returns an `Integer`; returning it from an `int` method unboxes it. On an empty deque it would return `null` and the unboxing would throw `NullPointerException` - LeetCode promises `pop`/`peek` are only called on a non-empty queue.
- `moveIfNeeded` is shared by `pop` and `peek` so the transfer rule lives in exactly one place. Duplicating the loop into both methods is how the two drift apart.
- In `MyStack`, `q.size() - 1` is evaluated on every loop check, but `offer` and `poll` cancel out, so the size is constant during the rotation.

=== edgeCases ===
### The LeetCode example

```text
push(1), push(2), peek(), pop(), empty()  ->  1, 1, false
```

### Interleaved pushes and pops

```text
push 1, push 2, push 3, pop, push 4, pop, pop, pop, empty  ->  1, 2, 3, 4, true
```

The dry run. `4` waits in `in` while `2` and `3` are served from `out`.

### `peek` does not remove

```text
push(1), push(2), peek(), peek(), pop(), pop()  ->  1, 1, 1, 2
```

The first `peek` performs the transfer; the second finds `out` non-empty and moves nothing.

### Push after a peek

```text
push(1), peek(), push(2), pop(), pop()  ->  1, 1, 2
```

After the `peek`, `out = [1]` and `2` goes into `in`. The first `pop` returns `1` from `out`; the second finds `out` empty, transfers `2`, and returns it.

### `empty()` must check both stacks

```text
push(1), push(2), pop(), empty()  ->  1, false
```

At this point `in` is empty and `out` holds `2`. A version that only checks `in` returns `true`.

### One element

```text
push(7), pop(), empty()  ->  7, true
```

### Reuse after emptying

```text
push(1), pop(), push(2), peek()  ->  1, 2
```

Nothing is left behind after the queue drains, so it starts cleanly.

### Many pushes, then many pops

```text
push 1 .. 100000, then 100000 pops  ->  1, 2, ..., 100000  with exactly 100000 moves
```

The first `pop` moves all `10^5` elements; the other `99,999` pops move nothing. The brute force would make about `10^10` moves on the same input.

=== takeaway ===
> When you need a **queue from stacks**, think **in-stack and out-stack**: push to `in`, read from `out`, and pour `in` into `out` **only when `out` is empty**.

### The core observation

Pouring one stack into another reverses it, which turns newest-on-top into oldest-on-top. Everything in `out` is older than everything in `in`, so `out` can serve pops until it runs dry without ever being undone - each element is moved once, which makes every operation amortized `O(1)`.

### The pattern trigger

```text
     push(x)  ------------------->  in.push(x)

     pop() / peek()
            |
            v
     out empty?  -- yes -->  pour ALL of in into out (reverses order)
            |
            no
            |
            v
     out.pop() / out.peek()        <- always the oldest element

     empty()  -->  in empty AND out empty
```

### The common mistakes

**Pouring back after every pop.** Correct but `O(n)` per pop - it undoes the one piece of useful work.

**Pouring when `out` is not empty.** Puts newer elements above older ones. Wrong answers, not just slow ones.

**`empty()` checking only one stack.** Elements can sit in either.

**Calling it `O(1)` without saying "amortized".** A single `pop` can move `n` elements. Interviewers listen for the word and for the "each element moves once" justification.

### What to remember in six months

> Amortized `O(1)` means: expensive operations are paid for by the cheap ones that set them up. The proof is always "count how many times each element can be touched".

That counting argument comes back for monotonic stacks (each element pushed and popped at most once - later this week), dynamic arrays doubling their capacity, and union-find. And the two-stack queue itself reappears whenever you need a queue with an `O(1)` min or max: build it from two of yesterday's min-stacks.

A queue wants the oldest element. In a stack, the oldest element is at the bottom - the one place a stack cannot reach. Pour the stack into a second stack and the order reverses: oldest on top.
