=== intro ===
The last day of the linked-list week, and a revision day in disguise. Yesterday was about two pointers meeting; today puts two tools you already own - **find the middle** (day 30) and **reverse a list** (day 29) - into one function.

> A singly linked list can only be read forwards. When a problem needs you to read it backwards, you do not need a copy - you can **reverse the half you need** and then put it back.

=== problem ===
Given the head of a singly linked list, return `true` if its values read the same forwards and backwards.

```text
head = 1 -> 2 -> 2 -> 1        ->  true
head = 1 -> 2                  ->  false
head = 1 -> 2 -> 3 -> 2 -> 1   ->  true
```

### What "palindrome" means here, position by position

A palindrome mirrors around its centre: position `0` matches the last position, position `1` matches the second-last, and so on, until the two meet in the middle.

| pair | from the front | from the back | equal? |
| ---: | :------------- | :------------ | :----- |
| 1 | `1` (index 0) | `1` (index 3) | yes |
| 2 | `2` (index 1) | `2` (index 2) | yes |

For `1 -> 2 -> 2 -> 1`, two comparisons settle it. For an odd length like `1 -> 2 -> 3 -> 2 -> 1`, the centre element `3` has no partner and does not need to match anything.

### Why this is harder on a list than on an array

On an array you put one index at each end and walk them inwards. That needs to step **backwards** from the end. A singly linked list only has `next` pointers - there is no `prev`, and no index. Getting to "the second-last node" means walking from the head again.

### What the constraints tell you

- Up to `10^5` nodes, values `0` to `9`.
- The follow-up: `O(n)` time **and `O(1)` extra space**. That rules out copying the values out, and it rules out recursion (which uses a call stack as deep as the list). That follow-up is the whole problem.

=== pattern ===
**Fast/Slow pointers + in-place reversal.** Two linked-list primitives, composed.

The array approach compares the front half with the back half *read backwards*. On a list, we cannot read backwards - but we can make the back half **point** backwards:

```text
before:  1 -> 2 -> 2 -> 1 -> null

find the middle, reverse from there:

         1 -> 2 -> 2 -> null          (first half, still wired to the middle)
                   ^
         1 -> 2 ---+                  (second half, reversed: 1 -> 2 -> null)
```

Now both halves can be read **forwards**, from their own starts, in lockstep. Comparing them is the array two-pointer check, done with `next` instead of `i++` and `j--`.

Each step is something you have done before:

| step | tool | from |
| ---: | :--- | :--- |
| 1 | slow moves 1, fast moves 2; slow ends at the middle | day 30 |
| 2 | reverse from the middle with `prev`, `curr`, `next` | day 29 |
| 3 | walk both halves together, compare values | two pointers |
| 4 | reverse the second half again to restore the list | day 29 |

### Recognising it

Reach for "middle + reverse" when:

- a list problem needs the **end** paired with the **start** (palindrome, Reorder List LC 143, Maximum Twin Sum LC 2130)
- you are told `O(1)` extra space, so copying to an array is out
- modifying the list temporarily is allowed (and you can undo it)

The mental question:

> If this were an array, would I use two pointers from opposite ends? Then on a list: find the middle, reverse one half, and walk both halves forwards.

=== bruteForce ===
Forget the space limit. The array version of this problem is easy, so turn the list into an array.

### Step logic

1. Walk the list, appending each value to an `ArrayList<Integer>`.
2. Put `i` at index `0` and `j` at the last index.
3. While `i < j`: if `vals[i] != vals[j]`, return `false`; otherwise `i++`, `j--`.
4. If the pointers meet without a mismatch, return `true`.

### Dry run

```text
head = n0(1) -> n1(2) -> n2(2) -> n3(1) -> null
```

**Phase 1 - copy the values.**

| step | node | value | vals afterwards |
| ---: | :--- | ----: | :-------------- |
| 1 | n0 | 1 | `[1]` |
| 2 | n1 | 2 | `[1, 2]` |
| 3 | n2 | 2 | `[1, 2, 2]` |
| 4 | n3 | 1 | `[1, 2, 2, 1]` |
| 5 | null | - | stop |

**Phase 2 - two pointers from both ends.**

| step | i | j | vals[i] | vals[j] | equal? | action |
| ---: | -: | -: | ------: | ------: | :----- | :----- |
| 1 | 0 | 3 | 1 | 1 | yes | `i = 1`, `j = 2` |
| 2 | 1 | 2 | 2 | 2 | yes | `i = 2`, `j = 1` |
| 3 | 2 | 1 | - | - | - | `i >= j`, stop: return `true` |

And the failing example, `1 -> 2`:

| step | i | j | vals[i] | vals[j] | equal? | action |
| ---: | -: | -: | ------: | ------: | :----- | :----- |
| 1 | 0 | 1 | 1 | 2 | **no** | return `false` |

Correct in both cases.

### Java

```java
class Solution {
    public boolean isPalindrome(ListNode head) {

        List<Integer> vals = new ArrayList<>();
        for (ListNode node = head; node != null; node = node.next) {
            vals.add(node.val);
        }

        int i = 0;
        int j = vals.size() - 1;

        while (i < j) {
            // equals(), not != : these are Integer objects, not ints
            if (!vals.get(i).equals(vals.get(j))) {
                return false;
            }
            i++;
            j--;
        }

        return true;
    }
}
```

### Complexity

**Time:** `O(n)` - **Space:** `O(n)`

### Where it hurts

Time is already optimal: every value has to be looked at.

The cost is the copy. The array holds all `n` values - `10^5` boxed `Integer`s - and it exists for one reason: **so that `j` can walk backwards**. That is the only thing the list could not do on its own.

But look at what phase 2 actually reads. `j` only ever visits the **back half** (indices `2` and `3` above). The front half is read by `i` in the same order the list already provides. So the array is doing two jobs, and we only need one of them:

- giving `i` the front half in forward order - the list already does this
- giving `j` the back half in **reverse** order - this is the only real requirement

> We do not need a reversed copy of the whole list. We need the back half to be readable in reverse - and a list's own back half can be reversed in place.

=== optimization ===
Replace "copy everything so `j` can go backwards" with "reverse the back half so a pointer can go forwards through it".

### The key observation

Reversing a linked list costs `O(n)` time and `O(1)` space (day 29). If we reverse only the back half, then a pointer starting at its new head visits the back half in exactly the order `j` did: last node first. Pair it with a pointer from `head`, and the comparisons are identical to the brute force's phase 2 - with no array.

To reverse the back half we need to know where it starts. That is day 30's fast/slow pointers.

### Step by step

1. **Middle.** `slow = fast = head`. While `fast != null && fast.next != null`: `slow` one step, `fast` two. `slow` ends at the start of the back half.
2. **Reverse** the list starting at `slow`. Call the new head `secondHead`.
3. **Compare.** `p1 = head`, `p2 = secondHead`. While `p2 != null`: if values differ, the answer is `false`; else advance both.
4. **Restore.** Reverse `secondHead` again so the caller's list is unchanged. Return the answer.

### Dry run - same list

```text
n0(1) -> n1(2) -> n2(2) -> n3(1) -> null
```

**Step 1 - find the middle.**

| iteration | slow | fast | loop check before moving |
| --------: | :--- | :--- | :----------------------- |
| start | n0 | n0 | - |
| 1 | n1 | n2 | `fast = n0`, `fast.next = n1`: keep going |
| 2 | n2 | null | `fast = n2`, `fast.next = n3`: keep going |
| - | n2 | null | `fast == null`: stop |

`slow = n2`. For an even length, `slow` lands on the **second** of the two middle nodes - the first node of the back half.

**Step 2 - reverse from n2.**

| iteration | curr | `next = curr.next` | `curr.next = prev` | prev afterwards | curr afterwards |
| --------: | :--- | :----------------- | :----------------- | :-------------- | :-------------- |
| start | n2 | - | - | null | n2 |
| 1 | n2 | n3 | `n2.next = null` | n2 | n3 |
| 2 | n3 | null | `n3.next = n2` | n3 | null |

`secondHead = n3`. The list now looks like this:

```text
first:   n0(1) -> n1(2) -> n2(2) -> null
second:  n3(1) -> n2(2) -> null
```

`n1.next` still points at `n2` - we never touched it. So `n2` sits at the end of **both** chains. That is fine: it is how the restore works later.

**Step 3 - compare.**

| step | p1 | p1.val | p2 | p2.val | equal? | action |
| ---: | :--- | -----: | :--- | -----: | :----- | :----- |
| 1 | n0 | 1 | n3 | 1 | yes | advance both |
| 2 | n1 | 2 | n2 | 2 | yes | advance both |
| 3 | n2 | 2 | null | - | - | `p2 == null`: stop, `result = true` |

Two comparisons - the same two the brute force made, the same pairs (index 0 with 3, index 1 with 2).

**Step 4 - restore.** Reverse from `n3`: `n3.next = null`, `n2.next = n3`, returns `n2`. Since `n1.next` is still `n2`, the original chain `n0 -> n1 -> n2 -> n3 -> null` is back. Return `true`.

### Odd length - where the centre goes

```text
n0(1) -> n1(2) -> n2(3) -> n3(2) -> n4(1) -> null
```

| iteration | slow | fast | note |
| --------: | :--- | :--- | :--- |
| start | n0 | n0 | |
| 1 | n1 | n2 | |
| 2 | n2 | n4 | `fast.next == null`: stop |

`slow = n2`, the centre. Reversing from `n2` gives `second: n4(1) -> n3(2) -> n2(3) -> null`.

| step | p1 | p2 | values | equal? |
| ---: | :--- | :--- | :----- | :----- |
| 1 | n0 | n4 | 1 vs 1 | yes |
| 2 | n1 | n3 | 2 vs 2 | yes |
| 3 | n2 | n2 | 3 vs 3 | yes - the centre is compared with itself |
| 4 | n3 | null | - | stop, `true` |

The centre ends up in both halves and matches itself, which is harmless. No special case for odd lengths.

### A failing case

```text
1 -> 2 -> 3 -> 1
```

Middle is the node `3` (index 2). Reversed back half: `1 -> 3`. Compare `1` vs `1` (equal), then `2` vs `3` - **mismatch**, `result = false`. The loop breaks, the restore still runs, and the method returns `false`.

=== complexity ===
### Time

Finding the middle walks `n/2` steps. Each reversal touches `n/2` nodes. The comparison makes at most `n/2` steps. Four passes over half the list each is still linear.

```text
O(n)
```

### Space

A handful of references: `slow`, `fast`, `prev`, `curr`, `next`, `p1`, `p2`. No array, no recursion.

```text
O(1)
```

### Comparison

| Approach | Time | Extra space | Modifies the list? |
| :------- | ---: | ----------: | :----------------- |
| Copy to array + two pointers | `O(n)` | `O(n)` | no |
| Push all values on a stack, pop and compare | `O(n)` | `O(n)` | no |
| Recursion (compare on the way back up) | `O(n)` | `O(n)` call stack | no |
| Middle + reverse half + restore | **`O(n)`** | **`O(1)`** | temporarily, then restored |

The recursive solution looks like `O(1)` space because it allocates no collection, but every frame sits on the call stack. With `10^5` nodes that is `10^5` frames - enough to throw `StackOverflowError` on a default JVM stack. Say so if an interviewer suggests it.

=== implementation ===
```java
// ListNode is provided by LeetCode: int val; ListNode next;

class Solution {
    public boolean isPalindrome(ListNode head) {

        // 1. Find the start of the back half.
        ListNode slow = head;
        ListNode fast = head;
        while (fast != null && fast.next != null) {
            slow = slow.next;
            fast = fast.next.next;
        }

        // 2. Reverse the back half so it can be read last-to-first.
        ListNode secondHead = reverse(slow);

        // 3. Walk both halves forwards and compare.
        boolean result = true;
        ListNode p1 = head;
        ListNode p2 = secondHead;
        while (p2 != null) {
            if (p1.val != p2.val) {
                result = false;
                break;
            }
            p1 = p1.next;
            p2 = p2.next;
        }

        // 4. Put the list back the way the caller gave it to us.
        reverse(secondHead);

        return result;
    }

    private ListNode reverse(ListNode head) {
        ListNode prev = null;
        ListNode curr = head;
        while (curr != null) {
            ListNode next = curr.next;
            curr.next = prev;
            prev = curr;
            curr = next;
        }
        return prev;
    }
}
```

### The lines that matter

**1.**

```java
while (fast != null && fast.next != null) {
```

Both checks are needed. `fast != null` stops an even-length list (fast steps off the end); `fast.next != null` stops an odd-length list (fast sits on the last node). The order matters too: `&&` short-circuits, so `fast.next` is never read when `fast` is `null`.

**2.**

```java
while (p2 != null) {
```

Loop on the **back half**, not the front. The back half is never longer than the front (for odd lengths they share the centre), so `p1` can never run out first. Looping on `p1 != null` instead fails on even lengths: the front chain still ends with the middle node (`n0 -> n1 -> n2` above, three nodes against the back half's two), so the third iteration reads `p2.val` with `p2 == null` and throws `NullPointerException`.

**3.**

```java
reverse(secondHead);
```

The restore. The node before the middle still points at the middle, so reversing the back half a second time reconnects everything with no extra bookkeeping. That is why the comparison uses `break` and a `result` flag rather than an early `return false` - an early return would skip this line and hand the caller a broken list.

### Java notes

- `p1.val != p2.val` is safe here: `val` is a primitive `int`. In the brute force the values are `Integer` objects in a list, where `!=` compares **references**. It happens to work for `0`-`9` because Java caches `Integer` values from `-128` to `127` - and silently breaks above that. Use `.equals()` with boxed values, always.
- `reverse` is a `private` helper, which LeetCode allows inside `Solution`. It is day 29's code unchanged.
- If an interviewer says modifying the input is fine, step 4 can go - but mention it. Leaving a caller's data structure half-reversed is the kind of side effect that causes bugs far away from this function.

=== edgeCases ===
### Single node

```text
[7]  ->  true
```

The middle loop does not run, `slow = head`. Reversing one node gives the same node; comparing it with itself is equal. One element always reads the same both ways.

### Two equal nodes

```text
[1, 1]  ->  true
```

`slow` ends at the second node. Back half is `[1]`, compared against the first `1`.

### Two different nodes

```text
[1, 2]  ->  false
```

Back half is `[2]`, compared against `1`. Mismatch on the first comparison.

### Odd length palindrome

```text
[1, 2, 3, 2, 1]  ->  true
```

The centre `3` lands in both halves and is compared with itself. No special case.

### Mismatch next to the middle

```text
[1, 2, 3, 1]  ->  false
```

The outer pair matches; the inner pair (`2` vs `3`) does not. Shows that the check cannot stop after the first comparison.

### All the same value

```text
[5, 5, 5, 5, 5]  ->  true
```

### Not a palindrome, but the halves contain the same values

```text
[1, 2, 1, 2]  ->  false
```

Front half `1, 2`; back half reversed `2, 1`. The **order** differs, so the first comparison (`1` vs `2`) fails. A solution that only compared counts or sums of the halves would wrongly say `true`.

### The list is unchanged afterwards

```text
[1, 2, 3, 1]  ->  false, and the list still reads 1 -> 2 -> 3 -> 1
```

Even on the `false` path, the restore runs because the loop uses `break`, not `return`.

### Long list

`10^5` nodes: the iterative version uses constant extra memory. A recursive version would need `10^5` stack frames and is likely to overflow.

=== takeaway ===
> When a **singly linked list** needs to be read **from both ends**, find the middle with fast/slow, **reverse the back half**, and walk both halves forwards. Restore it before returning.

### The core observation

The array solution only needs its extra memory so that one pointer can move backwards - and that pointer only ever visits the back half. Reversing the back half in place gives the same backwards traversal for `O(1)` space. Finding where the back half starts is exactly what fast/slow pointers do.

### The pattern trigger

```text
     list problem pairs node i with node n-1-i
                       |
                       v
     slow +1, fast +2   ->  slow = start of back half
                       |
                       v
     reverse(slow)      ->  back half now reads last-to-first
                       |
                       v
     p1 from head, p2 from reversed head, compare while p2 != null
                       |
                       v
     reverse again      ->  caller's list is untouched
```

### The common mistakes

**Returning early and skipping the restore.** `return false` inside the comparison loop leaves the list half-reversed. Use a flag and `break`.

**Looping on the wrong half.** Loop while the back half (`p2`) has nodes. It is never the longer one.

**Comparing boxed `Integer`s with `!=`.** Passes every LeetCode test because values are `0`-`9`, and breaks on any value above `127` in real code.

**Calling recursion `O(1)` space.** The call stack is `O(n)`.

### What to remember in six months

> Linked lists cannot go backwards, but they can be **made** to - in place, for `O(1)` space, and undone afterwards.

The same three moves (middle, reverse, walk two halves) solve Reorder List (LC 143, which interleaves instead of comparing) and Maximum Twin Sum of a Linked List (LC 2130, which adds instead of comparing). Only step 3 changes.
