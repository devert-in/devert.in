=== intro ===
Yesterday the array was sorted except for one break, and binary search survived by finding the half that was still sorted. Today **nothing is sorted** - and binary search still works.

> Binary search never needed sorted data. It needs one comparison at `mid` that proves the answer exists on a particular side. Here that comparison is the **slope**: if the array is going uphill at `mid`, keep walking uphill and you are guaranteed to reach a peak.

=== problem ===
A **peak** is an element strictly greater than its neighbours. Given an array `nums` where no two **adjacent** elements are equal, return the index of **any** peak. Treat the positions just outside the array as negative infinity: `nums[-1] = nums[n] = -infinity`. The required time is `O(log n)`.

```text
nums = [1, 2, 3, 1]          ->  2        (3 > 2 and 3 > 1)
nums = [1, 2, 1, 3, 5, 6, 4] ->  1 or 5   (2 > 1, 1;  6 > 5, 4)
```

| index | 0 | 1 | 2 | 3 | 4 | 5 | 6 |
| :---- | -: | -: | -: | -: | -: | -: | -: |
| value | 1 | **2** | 1 | 3 | 5 | **6** | 4 |
| peak? | no | yes | no | no | no | yes | no |

Either `1` or `5` is accepted. The problem asks for **a** peak, not the highest one - that word "any" is what makes `O(log n)` possible.

### The constraints that matter

- `1 <= nums.length <= 1000`.
- `-2^31 <= nums[i] <= 2^31 - 1` - the full `int` range. You **cannot** fake the `-infinity` boundary with `Integer.MIN_VALUE`, because a real element can be `Integer.MIN_VALUE`.
- `nums[i] != nums[i + 1]` - no flat stretches. Every step between neighbours is strictly up or strictly down. The whole argument depends on this.
- `nums[-1] = nums[n] = -infinity` - so the first element is a peak if it beats `nums[1]`, the last if it beats `nums[n - 2]`, and a one-element array is its own peak.

### Why a peak always exists

Start at index `0`. Its left neighbour is `-infinity`, so the array begins by going **up** into `nums[0]`. It ends by going **down** into `nums[n] = -infinity`. Somewhere between a start that rises and an end that falls, the direction must switch from up to down - and the element where it switches is a peak. No sorting needed; the boundaries guarantee it.

=== pattern ===
**Binary Search on the slope.**

Look at `mid` and its right neighbour:

```text
nums[mid] < nums[mid + 1]   ->  going UP at mid
nums[mid] > nums[mid + 1]   ->  going DOWN at mid
```

- **Going up**: keep walking right. Either the values keep rising until the end - and then the last element is a peak, because `nums[n] = -infinity` - or they turn down somewhere, and the turning point is a peak. Either way, there is a peak **strictly to the right of `mid`**. Discard the left half including `mid`.
- **Going down**: by the mirror argument walking left, there is a peak **at `mid` or to its left**. `mid` itself might be it (if `nums[mid - 1] < nums[mid]`). Discard the right half, keep `mid`.

```text
           going up at mid                       going down at mid
                    .                              .
                 .                                    .
   mid  ->  .            peak is right    peak is here or left   <- mid .
```

This is still binary search: one comparison, half the window gone, guaranteed not to lose the answer. The guarantee comes from the `-infinity` boundaries plus "no equal neighbours", not from order.

### Recognising it

Reach for slope binary search when:

- the problem asks for **any** local maximum / minimum, not the global one
- the boundaries are defined to fall off (here `-infinity`), so a climb must end
- the problem demands `O(log n)` on an array that is **not** sorted - a strong hint that some local property decides direction

The mental question, the same one as the last four days:

> If I compare `mid` with one neighbour, can I prove that an answer exists on one particular side?

For a peak: "uphill to the right" proves there is a peak on the right. Discarding the other side cannot lose every answer - it might lose some peaks, but we only need one.

=== bruteForce ===
Walk left to right looking for the first place the array goes **down**.

### Step logic

1. For `i` from `0` to `n - 2`: if `nums[i] > nums[i + 1]`, return `i`.
2. If the loop finishes, the array never went down: return `n - 1`.

Why the first "goes down" is a peak: we reach `i` only if every earlier step went up, so `nums[i - 1] < nums[i]` (or `i = 0`, whose left neighbour is `-infinity`). Then `nums[i] > nums[i + 1]` makes it greater than both neighbours. We never need to look at `nums[i - 1]` explicitly.

### Dry run - example 1

```text
nums = [1, 2, 3, 1]
```

| step | i | nums[i] | nums[i+1] | nums[i] > nums[i+1]? | action |
| ---: | -: | ------: | --------: | :------------------- | :----- |
| 1 | 0 | 1 | 2 | no (up) | next |
| 2 | 1 | 2 | 3 | no (up) | next |
| 3 | 2 | 3 | 1 | **yes** (down) | return `2` |

### Dry run - example 2

```text
nums = [1, 2, 1, 3, 5, 6, 4]
```

| step | i | nums[i] | nums[i+1] | nums[i] > nums[i+1]? | action |
| ---: | -: | ------: | --------: | :------------------- | :----- |
| 1 | 0 | 1 | 2 | no (up) | next |
| 2 | 1 | 2 | 1 | **yes** (down) | return `1` |

Both answers are valid peaks.

### Java

```java
class Solution {
    public int findPeakElement(int[] nums) {

        for (int i = 0; i < nums.length - 1; i++) {
            if (nums[i] > nums[i + 1]) {
                return i;               // first step down: nums[i] is a peak
            }
        }

        return nums.length - 1;         // never went down: last element is the peak
    }
}
```

### Complexity

**Time:** `O(n)` - **Space:** `O(1)`

### Where it hurts

Give it a strictly increasing array:

```text
nums = [1, 2, 3, 4, 5, 6, 7]
```

| step | i | nums[i] | nums[i+1] | down? |
| ---: | -: | ------: | --------: | :---- |
| 1 | 0 | 1 | 2 | no |
| 2 | 1 | 2 | 3 | no |
| 3 | 2 | 3 | 4 | no |
| 4 | 3 | 4 | 5 | no |
| 5 | 4 | 5 | 6 | no |
| 6 | 5 | 6 | 7 | no |
| - | - | - | - | return `6` |

Six comparisons, each saying the same thing: "still going up". Look at what step 4 alone already proves. `nums[3] < nums[4]` means we are climbing at index `3` - and a climb that cannot go on forever (it hits `-infinity` at `n`) must end at a peak **somewhere to the right of 3**. Steps 1 to 3 checked the left side, which that one comparison has made irrelevant.

The scan uses each slope comparison to learn about **one position**. But a single slope comparison is a fact about a **whole side**: "there is a peak over there". That is exactly the property binary search needs. Check the slope at the middle, not at the left edge.

=== optimization ===
### The key observation

The comparison `nums[mid]` vs `nums[mid + 1]` proves a peak exists on one specific side of `mid`:

- `nums[mid] < nums[mid + 1]` -> a peak exists in `[mid + 1, hi]`.
- `nums[mid] > nums[mid + 1]` -> a peak exists in `[lo, mid]`.

So keep a window `[lo, hi]` that always contains a peak, and halve it.

### The invariant

> The window `[lo, hi]` contains at least one peak of the whole array.

More precisely: the element just left of `lo` is lower than `nums[lo]` (or `lo = 0`), and the element just right of `hi` is lower than `nums[hi]` (or `hi = n - 1`). The window "rises in" at its left edge and "falls out" at its right edge, so by the argument in the problem section, it contains a peak. Both updates preserve that:

- `lo = mid + 1` happens only when `nums[mid] < nums[mid + 1]`, so the new left edge rises in.
- `hi = mid` happens only when `nums[mid] > nums[mid + 1]`, so the new right edge falls out.

When the window shrinks to one element, that element rises in from the left and falls out to the right: it **is** a peak.

### Deriving it step by step

1. `lo = 0`, `hi = n - 1`.
2. While `lo < hi` (more than one candidate): `mid = lo + (hi - lo) / 2`.
3. If `nums[mid] < nums[mid + 1]`: `lo = mid + 1`.
4. Else: `hi = mid` (not `mid - 1` - `mid` may be the peak).
5. Return `lo`.

`mid + 1` is always in range: `lo < hi` and rounding down give `mid < hi`, so `mid + 1 <= hi <= n - 1`.

### Dry run - example 1

```text
nums = [1, 2, 3, 1]
```

| step | lo | hi | mid | nums[mid] | nums[mid+1] | slope | action |
| ---: | -: | -: | --: | --------: | ----------: | :---- | :----- |
| 1 | 0 | 3 | 1 | 2 | 3 | up | `lo = 2` |
| 2 | 2 | 3 | 2 | 3 | 1 | down | `hi = 2` |
| - | 2 | 2 | - | - | - | `lo == hi` | return **2** |

### Dry run - example 2

```text
nums = [1, 2, 1, 3, 5, 6, 4]
```

| step | lo | hi | mid | nums[mid] | nums[mid+1] | slope | action |
| ---: | -: | -: | --: | --------: | ----------: | :---- | :----- |
| 1 | 0 | 6 | 3 | 3 | 5 | up | `lo = 4` |
| 2 | 4 | 6 | 5 | 6 | 4 | down | `hi = 5` |
| 3 | 4 | 5 | 4 | 5 | 6 | up | `lo = 5` |
| - | 5 | 5 | - | - | - | `lo == hi` | return **5** |

The scan returned `1`; this returns `5`. Both are correct - and this is where "any peak" matters. Step 1 discarded `[0..3]`, which contained the peak at index `1`. That is fine: the comparison proved a peak exists on the right, and one is all we need.

### Dry run - the scan's worst case

```text
nums = [1, 2, 3, 4, 5, 6, 7]
```

| step | lo | hi | mid | nums[mid] | nums[mid+1] | slope | action |
| ---: | -: | -: | --: | --------: | ----------: | :---- | :----- |
| 1 | 0 | 6 | 3 | 4 | 5 | up | `lo = 4` |
| 2 | 4 | 6 | 5 | 6 | 7 | up | `lo = 6` |
| - | 6 | 6 | - | - | - | `lo == hi` | return **6** |

Two comparisons instead of six. Step 1 is the observation from "Where it hurts", applied at the middle instead of after walking there.

### Why `lo < hi` and `hi = mid` here

This is day 44's half-open style of update, used for a different reason. `hi = mid` keeps `mid` because it might be the peak, so the loop must stop at `lo == hi` - with `lo <= hi` it would compute `mid = lo`, find "down" (or read `nums[mid + 1]` out of bounds), set `hi = mid` and never shrink again. The pair "`lo < hi`, `hi = mid`, `lo = mid + 1`" always shrinks the window and always leaves one survivor.

=== complexity ===
### Time

Each iteration halves `[lo, hi]` and does one comparison.

```text
O(log n)
```

For `n = 1000`, at most 10 iterations.

### Space

`lo`, `hi`, `mid`.

```text
O(1)
```

### Comparison

| Approach | Time | Space | Which peak it returns |
| :------- | ---: | ----: | :-------------------- |
| Check every element against both neighbours | `O(n)` | `O(1)` | any (first found) |
| Scan for first step down | `O(n)` | `O(1)` | the first peak |
| Global maximum | `O(n)` | `O(1)` | the highest peak |
| Slope binary search | **`O(log n)`** | **`O(1)`** | some peak |

The global maximum is always a peak and is a common first instinct - but finding it requires looking at every element. Asking for **any** peak is what lets us look at only `log n` of them.

=== implementation ===
```java
class Solution {
    public int findPeakElement(int[] nums) {

        // Invariant: [lo, hi] always contains a peak.
        int lo = 0;
        int hi = nums.length - 1;

        while (lo < hi) {                        // more than one candidate
            int mid = lo + (hi - lo) / 2;        // mid < hi, so mid + 1 is in range

            if (nums[mid] < nums[mid + 1]) {
                lo = mid + 1;                    // uphill: a peak is to the right
            } else {
                hi = mid;                        // downhill: mid or left has a peak
            }
        }

        return lo;                               // one candidate left - it is a peak
    }
}
```

### The lines that matter

**1.**

```java
if (nums[mid] < nums[mid + 1]) {
```

The whole algorithm. It compares with the right neighbour only - never `nums[mid - 1]` - because one direction is enough to know which side has a peak.

**2.**

```java
hi = mid;                        // downhill: mid or left has a peak
```

Not `mid - 1`. Going down from `mid` means `mid` itself might be the peak; throwing it away could empty the window of peaks (`[1, 3, 2]` with `mid = 1`).

**3.**

```java
while (lo < hi) {                        // more than one candidate
```

Paired with `hi = mid`. It stops at a single element - which the invariant says is a peak - and it guarantees `mid + 1` never runs past `hi`.

### Why no `-infinity` sentinel

The code never reads `nums[-1]` or `nums[n]`. The boundaries enter only through the argument: when `lo` reaches `n - 1` or `hi` stays at `n - 1`, it is because every comparison said "up", which is the case where the last element beats its only neighbour. Good thing, too - with values reaching `Integer.MIN_VALUE`, there is no `int` you could use as a sentinel.

### Follow-up - Peak Index in a Mountain Array (LC 852)

A mountain strictly rises then strictly falls, so it has exactly one peak - and the same code finds it:

```java
class Solution {
    public int peakIndexInMountainArray(int[] arr) {

        int lo = 0, hi = arr.length - 1;
        while (lo < hi) {
            int mid = lo + (hi - lo) / 2;
            if (arr[mid] < arr[mid + 1]) lo = mid + 1;
            else hi = mid;
        }

        return lo;
    }
}
```

### Follow-up - Find a Peak Element II (LC 1901)

In a grid where adjacent cells differ, binary search the **rows**. In row `mid`, take the column `c` of the row's maximum - it beats its left and right neighbours. Then compare with the cell below, exactly like the 1D slope:

```java
class Solution {
    public int[] findPeakGrid(int[][] mat) {

        int lo = 0, hi = mat.length - 1;
        while (lo < hi) {
            int mid = lo + (hi - lo) / 2;
            int c = maxCol(mat[mid]);
            if (mat[mid][c] < mat[mid + 1][c]) lo = mid + 1;   // uphill downward
            else hi = mid;
        }

        return new int[] { lo, maxCol(mat[lo]) };
    }

    private int maxCol(int[] row) {
        int best = 0;
        for (int j = 1; j < row.length; j++) {
            if (row[j] > row[best]) best = j;
        }
        return best;
    }
}
```

`O(n log m)` for an `m x n` grid: `log m` rows visited, `O(n)` to find each row's maximum.

### Java notes

- `nums.length - 1` for a one-element array is `0`, so `lo == hi` immediately and the loop never runs - `[x]` returns `0` without reading a neighbour.
- Comparisons only; no arithmetic on values, so no overflow concerns even at `Integer.MIN_VALUE` / `Integer.MAX_VALUE`.

=== edgeCases ===
### Single element

```text
[1]  ->  0
```

Both neighbours are `-infinity`, so it is a peak. The loop does not run.

### Two elements

```text
[1, 2]  ->  1
[2, 1]  ->  0
```

`mid = 0`; up means the answer is `1`, down means it is `0`.

### Strictly increasing

```text
[1, 2, 3, 4, 5]  ->  4
```

The last element is the peak, because `nums[n] = -infinity`. Every comparison says "up".

### Strictly decreasing

```text
[5, 4, 3, 2, 1]  ->  0
```

The first element is the peak. Every comparison says "down" and `hi` walks to `0`.

### Valley in the middle - peaks at both ends

```text
[3, 1, 2]  ->  2
```

Peaks at `0` and `2`. `mid = 1`, `1 < 2`, so `lo = 2`. Returning `0` would also be correct; this code happens to go right.

### Keeping `mid` matters

```text
[1, 3, 2]  ->  1
```

`mid = 1`, `3 > 2`, so `hi = 1` - keeping index `1`. Next `mid = 0`, `1 < 3`, `lo = 1`. With `hi = mid - 1` the first step would have discarded the only peak.

### Extreme values

```text
[-2147483648]               ->  0
[-2147483648, 2147483647]   ->  1
```

No sentinel is ever used, so `Integer.MIN_VALUE` as a real element is harmless.

### Multiple peaks

```text
[1, 2, 1, 3, 5, 6, 4]  ->  5   (1 is equally valid)
```

### Mountain array (LC 852)

```text
[0, 1, 0]        ->  1
[0, 10, 5, 2]    ->  1
```

=== takeaway ===
> When you see **"find any local peak / valley"** with falling boundaries and an **`O(log n)`** requirement, think **binary search on the slope**: compare `nums[mid]` with `nums[mid + 1]` and walk uphill.

### The core observation

Going uphill at `mid` proves a peak exists to the right - a climb must end somewhere, and the boundary at `-infinity` guarantees it ends inside the array. Going downhill proves one exists at `mid` or to the left. One comparison, one guaranteed side. That is all binary search ever needed; sortedness was only one way of providing it.

### The pattern trigger

```text
             need ANY local max, O(log n), unsorted
                             |
                             v
                window [lo, hi] always holds a peak
                             |
                             v
               nums[mid] < nums[mid + 1] ?
                 /                       \
           yes (uphill)               no (downhill)
           lo = mid + 1               hi = mid   (keep mid)
                 \                       /
                             v
              lo == hi  ->  that index is a peak
```

### The common mistakes

**Thinking binary search needs sorted input** and reaching for an `O(n)` scan. The `O(log n)` requirement on an unsorted array is the hint that some local comparison decides direction.

**`hi = mid - 1` on the downhill branch.** `mid` may be the peak; discarding it can discard the only one in the window.

**`while (lo <= hi)` with `hi = mid`.** When `lo == hi`, `mid + 1` can run off the end, and otherwise the window stops shrinking.

**Using `Integer.MIN_VALUE` as the `-infinity` sentinel.** A real element may equal it. The slope version never needs a sentinel.

**Searching for the global maximum.** Always a peak, never `O(log n)`.

### What to remember in six months

> Binary search works whenever one comparison at `mid` proves which side still contains an answer. Sorted order, a sorted half, a monotonic condition, a slope - they are all just different proofs.

Days 44 to 48 used five different proofs for the same loop. Peak Index in a Mountain Array (LC 852) is this exact code; Find a Peak Element II (LC 1901) runs it on rows of a grid.
