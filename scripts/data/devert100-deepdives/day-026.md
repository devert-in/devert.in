=== intro ===
Day 23 counted every subarray that sums to `k`. Today asks for the **longest** one instead - and that single word changes what the hash map has to remember.

> Counting needs to know *how many* times a running total appeared. Maximising length needs to know *where it appeared first*. Same map, different value - decide what the question needs before deciding what to store.

=== problem ===
Given an array `arr` (which may contain negatives and zeros) and an integer `k`, return the **length** of the longest contiguous subarray whose sum is exactly `k`. If no such subarray exists, return `0`.

LeetCode 325 (Maximum Size Subarray Sum Equals k) is Premium; GeeksforGeeks hosts the same problem for free as "Longest Sub-Array with Sum K". The code below uses the GFG signature.

```text
arr = [1, -1, 5, -2, 3]
k   = 3
```

| Subarray | Indices | Sum | Length |
| :------- | :------ | --: | -----: |
| `[1, -1, 5, -2]` | 0..3 | 3 | **4** |
| `[5, -2]` | 2..3 | 3 | 2 |
| `[3]` | 4..4 | 3 | 1 |

```text
answer = 4
```

### What changed from Day 23

On Day 23 the answer was *how many* of these rows exist (3 here). Today it is *the longest row's length* (4). The prefix sum identity is the same:

```text
sum(arr[i..j]) = prefix[j + 1] - prefix[i]
```

What changes is which earlier prefix we want. For a count, every matching earlier prefix contributes. For the longest subarray ending at `j`, we want the matching prefix that is **furthest back** - the earliest index where that running total occurred.

### The condition that makes it non-trivial

Negatives. With only positive values a sliding window solves this in `O(1)` space (shown in the implementation section). With negatives, the running sum is not monotonic, so a window cannot know when to shrink - the same reason Day 23 needed a map.

=== pattern ===
**Prefix Sum + HashMap (first index).**

Map each running total to the **first index** at which it occurred. At index `j`, with running total `prefix`:

```text
need = prefix - k
if need was seen first at index i:   subarray (i+1 .. j) sums to k, length j - i
```

The earlier `i` is, the longer the subarray. So the map must keep the **earliest** index for each total and never overwrite it.

### The picture

```text
index:          -1    0    1    2    3    4
arr:                  1   -1    5   -2    3
prefix:          0    1    0    5    3    6
                 ^         ^         ^
          first 0 here     0 again   at j = 3 prefix = 3, need 3 - 3 = 0
                           (ignore)  first 0 is at -1 -> length 3 - (-1) = 4
```

If the map had been overwritten at index 1 (the second time the total is `0`), the lookup at `j = 3` would find index 1 and report length 2. Keeping the first occurrence is the whole difference between right and wrong.

### Why the seed is `{0: -1}`

The empty prefix has total `0` and sits just before index 0 - at index `-1`. Seeding it means a subarray starting at index 0 has length `j - (-1) = j + 1`. Many solutions write this as a separate check, `if (prefix == k) best = j + 1`; the seed is the same rule without the special case.

### Recognising it

Reach for prefix + first-index map when:

- the question asks for the **longest** (or **maximum size**) subarray
- the condition is an **exact sum** (or reduces to one - Day 28)
- values can be **negative or zero**

The mental question:

> To make the subarray ending here as long as possible, which earlier position do I want - and how do I make sure I can find it in one lookup?

=== bruteForce ===
Try every subarray, keep a running sum per start index, and record the length whenever the sum hits `k`.

### Step logic

1. `best = 0`.
2. For every `start`: `sum = 0`.
3. For every `end >= start`: `sum += arr[end]`; if `sum == k`, `best = max(best, end - start + 1)`.

### Dry run

```text
arr = [1, -1, 5, -2, 3], k = 3
```

| start | end | arr[end] | sum | sum == 3? | length | best |
| ----: | --: | -------: | --: | :-------- | -----: | ---: |
| 0 | 0 | 1 | 1 | no | - | 0 |
| 0 | 1 | -1 | 0 | no | - | 0 |
| 0 | 2 | 5 | 5 | no | - | 0 |
| 0 | 3 | -2 | 3 | **yes** | 4 | **4** |
| 0 | 4 | 3 | 6 | no | - | 4 |
| 1 | 1 | -1 | -1 | no | - | 4 |
| 1 | 2 | 5 | 4 | no | - | 4 |
| 1 | 3 | -2 | 2 | no | - | 4 |
| 1 | 4 | 3 | 5 | no | - | 4 |
| 2 | 2 | 5 | 5 | no | - | 4 |
| 2 | 3 | -2 | 3 | **yes** | 2 | 4 |
| 2 | 4 | 3 | 6 | no | - | 4 |
| 3 | 3 | -2 | -2 | no | - | 4 |
| 3 | 4 | 3 | 1 | no | - | 4 |
| 4 | 4 | 3 | 3 | **yes** | 1 | 4 |

`best = 4`. Correct.

Notice the sum in the `start = 0` rows: `1, 0, 5, 3, 6`. It drops, rises, drops and rises again. A sliding window would have shrunk at `5` and never seen the `3` that followed.

### Java

```java
class Solution {
    public int longestSubarray(int[] arr, int k) {

        int best = 0;

        for (int start = 0; start < arr.length; start++) {

            long sum = 0;

            for (int end = start; end < arr.length; end++) {
                sum += arr[end];
                if (sum == k) {
                    best = Math.max(best, end - start + 1);
                }
            }
        }

        return best;
    }
}
```

### Complexity

**Time:** `O(n^2)` - **Space:** `O(1)`

### Where it hurts

Fifteen rows for five elements, and `n(n + 1) / 2` in general. At `n = 10^5` that is five billion additions.

The waste is the same as on Day 23. Row `(2, 3)` computes `5 + (-2) = 3`, but rows `(0, 3)` and `(0, 1)` already know the totals up to index 3 (`3`) and up to index 1 (`0`). Their difference is `3`. Every row with `start > 0` re-adds elements that the `start = 0` rows already added.

There is a second, quieter waste specific to "longest": for a fixed `end`, the brute force checks every `start` from `0` upward, even after it has found the earliest matching one. Only the **leftmost** matching start can win. If we could jump straight to it, we would need exactly one check per `end`.

A map from running total to its **first** index is that jump.

=== optimization ===
### The key observation

For the subarray ending at `j` to sum to `k`, the running total just before its start must be `prefix - k`. Among all positions where that total occurred, the **earliest** gives the longest subarray. So store each running total's first index, and look it up once per `j`.

### Step logic

1. `firstIndex = {0: -1}`, `prefix = 0`, `best = 0`.
2. For each index `j`: `prefix += arr[j]`.
3. If `prefix - k` is in the map at index `i`: `best = max(best, j - i)`.
4. If `prefix` is **not** already in the map, store `prefix -> j`. If it is, leave it alone.

### Dry run - same example

```text
arr = [1, -1, 5, -2, 3], k = 3
```

| j | arr[j] | prefix | need `prefix - 3` | first index of need | length | best | map after |
| -: | -----: | -----: | ----------------: | :------------------ | -----: | ---: | :-------- |
| - | - | 0 | - | - | - | 0 | `{0:-1}` |
| 0 | 1 | 1 | -2 | absent | - | 0 | `{0:-1, 1:0}` |
| 1 | -1 | 0 | -3 | absent | - | 0 | `{0:-1, 1:0}` (0 kept at -1) |
| 2 | 5 | 5 | 2 | absent | - | 0 | `{0:-1, 1:0, 5:2}` |
| 3 | -2 | 3 | 0 | -1 | 3 - (-1) = 4 | **4** | `{0:-1, 1:0, 5:2, 3:3}` |
| 4 | 3 | 6 | 3 | 3 | 4 - 3 = 1 | 4 | `{0:-1, 1:0, 5:2, 3:3, 6:4}` |

`best = 4`. Five rows instead of fifteen.

### The row that decides it

At `j = 1` the running total returns to `0`, which is already in the map at index `-1`. The rule says leave it. Compare what happens at `j = 3` under each choice:

| map entry for total `0` | lookup at j = 3 finds | length | answer |
| :---------------------- | :-------------------- | -----: | -----: |
| first index, `-1` (kept) | `-1` | 4 | **4** - correct |
| last index, `1` (overwritten) | `1` | 2 | 2 - wrong |

That is the difference between Day 23 and today in one table. Day 23 needed *every* occurrence counted. Today needs only the *first* one, because a later occurrence can only produce a shorter subarray.

### Why lookup comes before insert

Same reason as Day 23, in a different disguise. With `k = 0`, inserting first would let the lookup find the index we just stored and report length `j - j = 0`. That is harmless here (it never beats `best`), but the order lookup-then-insert is the habit worth keeping, because on Day 23 the other order was a real bug.

=== complexity ===
### Time

One pass, with one `get` and at most one `putIfAbsent` per element - `O(1)` average each.

```text
O(n)
```

### Space

At most `n + 1` distinct running totals in the map.

```text
O(n)
```

### Why

The brute force re-derives sums and scans every start for each end. The map derives each running total once and answers "where is the earliest start that works?" in one lookup.

### Comparison

| Approach | Time | Space | Works with negatives? |
| :------- | ---: | ----: | :-------------------- |
| All subarrays, running sum | `O(n^2)` | `O(1)` | yes |
| Sliding window | `O(n)` | `O(1)` | **no** - non-negative values only |
| Prefix sum + first-index map | **`O(n)`** | `O(n)` | yes |

If an interviewer says "all values are positive", the window is the better answer - same time, constant space. If they say nothing, ask. The constraint decides the tool.

=== implementation ===
```java
class Solution {
    public int longestSubarray(int[] arr, int k) {

        // running total -> the FIRST index at which it occurred
        Map<Long, Integer> firstIndex = new HashMap<>();
        firstIndex.put(0L, -1);     // empty prefix, just before index 0

        long prefix = 0;
        int best = 0;

        for (int j = 0; j < arr.length; j++) {
            prefix += arr[j];

            // the earliest start that makes arr[start..j] sum to k
            Integer i = firstIndex.get(prefix - k);
            if (i != null) {
                best = Math.max(best, j - i);
            }

            // keep the first occurrence only - a later one is always shorter
            firstIndex.putIfAbsent(prefix, j);
        }

        return best;
    }
}
```

### The lines that matter

**1.**

```java
firstIndex.putIfAbsent(prefix, j);
```

`putIfAbsent`, not `put`. `put` overwrites with the latest index, which is right for nothing on this problem and turns the example's answer from 4 into 2.

**2.**

```java
firstIndex.put(0L, -1);     // empty prefix, just before index 0
```

`-1`, so that a subarray starting at index 0 has length `j - (-1) = j + 1`. Seeding with `0` would make every such length one short.

**3.**

```java
best = Math.max(best, j - i);
```

`j - i`, not `j - i + 1`. The stored index `i` is the position of the last element **before** the subarray, so the subarray is `i + 1 .. j`, which has `j - i` elements.

### The sliding window version, for non-negative inputs

When every value is `>= 0`, the window sum only grows as the right edge extends and only shrinks as the left edge advances. That monotonicity is what a window needs.

```java
class Solution {
    public int longestSubarray(int[] arr, int k) {

        int left = 0;
        long sum = 0;
        int best = 0;

        for (int right = 0; right < arr.length; right++) {
            sum += arr[right];

            while (sum > k && left <= right) {   // too big: shrink from the left
                sum -= arr[left];
                left++;
            }

            if (sum == k) {
                best = Math.max(best, right - left + 1);
            }
        }

        return best;
    }
}
```

Run it on the example with negatives and it returns `0`: at index 2 the sum is `5 > 3`, so the window shrinks all the way past the `1, -1` it needed, and never recovers.

### Java notes

- `long prefix` and `Map<Long, Integer>`. With `n = 10^5` values of up to `10^4` in magnitude, the running total reaches `10^9`, and `prefix - k` with `|k|` up to `10^9` can pass `Integer.MAX_VALUE`. A `long` costs nothing and removes the question.
- `0L`, not `0`, as the seed key. `firstIndex.put(0, -1)` would autobox `0` to an `Integer`, which does not compile against a `Map<Long, Integer>`. (In a looser setting the danger is worse: `Integer.valueOf(0).equals(Long.valueOf(0))` is `false`, so a mixed-type key silently never matches.)
- `firstIndex.get(...)` returns `Integer`, which may be `null`. Comparing it to `null` before unboxing avoids a `NullPointerException`.

=== edgeCases ===
### No subarray sums to k

```text
arr = [1, 2, 3], k = 7  ->  0
```

`best` is never updated.

### Single element equal to k

```text
arr = [5], k = 5  ->  1
```

At `j = 0`, need `0`, found at `-1`, length `1`. Only works because of the seed.

### The whole array

```text
arr = [10, 5, 2, 7, 1, -10], k = 15  ->  6
```

The GFG example. The total is `15` at both index 1 and index 5; the seed matches at index 5 and gives length 6.

### First occurrence matters

```text
arr = [1, -1, 5, -2, 3], k = 3  ->  4
```

The worked example. Overwriting the map would give 2.

### All zeros, k = 0

```text
arr = [0, 0, 0], k = 0  ->  3
```

The total is `0` everywhere. The seed at `-1` stays put, so the last index gives `2 - (-1) = 3`.

### Negatives cancelling to zero

```text
arr = [1, -1], k = 0  ->  2
```

### Negative k

```text
arr = [-1, 2, -3], k = -2  ->  3
```

Only the whole array sums to `-2`.

### Sliding window on a negative input

```text
arr = [1, -1, 5, -2, 3], k = 3  ->  window version returns 0 (wrong), map version 4
```

The window is only valid for non-negative values.

### Non-negative with zeros - window and map agree

```text
arr = [0, 0, 1, 0], k = 1  ->  4
```

The window version handles zeros correctly because it only shrinks when the sum is strictly greater than `k`, so leading and trailing zeros stay inside it.

=== takeaway ===
> When you see **"longest subarray with sum k"** and negatives are allowed, think **prefix sum + map of each running total's FIRST index**, seeded with `{0: -1}`.

### The core observation

The longest subarray ending at `j` with sum `k` starts right after the **earliest** position where the running total was `prefix - k`. Store first indices, never overwrite them, and each `j` needs one lookup.

### The pattern trigger

```text
        contiguous subarray + exact sum
                      |
          count it?   |    longest?
             /                \
   map: total -> COUNT      map: total -> FIRST index
   seed {0: 1}              seed {0: -1}
   ans += map[p - k]        best = max(best, j - map[p - k])
   map[p]++                 putIfAbsent(p, j)
          (Day 23)                (Day 26)
```

### The common mistakes

**`put` instead of `putIfAbsent`.** Stores the last index and shrinks every answer that depended on an earlier one.

**Seeding with `{0: 0}`.** Every subarray starting at index 0 comes out one too short.

**`j - i + 1`.** The stored index is the element *before* the subarray. Off by one.

**Sliding window with negatives.** Correct on positive inputs, silently wrong otherwise.

### What to remember in six months

> For subarray sums, the map's value is decided by the question: a **count** to count them, the **first index** to find the longest, the **last index** would find the shortest.
