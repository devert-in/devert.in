=== intro ===
Day 83 swept a sorted list of intervals and kept one running group. Today there is no sort and no list of intervals - but if you look at it the right way, there is a sweep over **ranges** again, and it is the same move: keep one running boundary, and only act when you cross it.

> When a DP table turns out to be made of flat runs of equal values, you are not looking at a DP problem. You are looking at BFS levels in disguise - and BFS over a line needs two integers, not an array.

=== problem ===
You start at index `0` of an array. `nums[i]` is the **maximum** jump length from index `i` - from `i` you may land on any of `i+1 .. i+nums[i]`. Return the **minimum number of jumps** to reach the last index. The last index is always reachable.

```text
nums = [2, 3, 1, 1, 4]
output = 2
```

One optimal route:

```text
index:   0     1     2     3     4
nums:   [2]   [3]   [1]   [1]   [4]
         |-----^                 ^
               |-----------------|
jump 1: 0 -> 1        jump 2: 1 -> 4
```

### Every option from each index

| i | nums[i] | can land on | note |
| -: | ------: | :---------- | :--- |
| 0 | 2 | 1, 2 | |
| 1 | 3 | 2, 3, 4 | reaches the end |
| 2 | 1 | 3 | |
| 3 | 1 | 4 | reaches the end |
| 4 | 4 | - | already at the end |

### What makes it non-trivial

**"Maximum" jump, not exact jump.** From index `1` you may jump 1, 2 or 3. That makes it tempting to always take the longest jump - but the longest jump from `0` lands on index `2`, where `nums[2] = 1` and you crawl: `0 -> 2 -> 3 -> 4` is **3** jumps. The best first jump is the *shorter* one to index `1`, because of where it lets you go *next*.

So the greedy choice is not "jump as far as possible". It is something subtler, and finding it is the point of the problem.

Constraints: `1 <= n <= 10^4`, `0 <= nums[i] <= 1000`, the last index is guaranteed reachable.

=== pattern ===
**Greedy over BFS levels** (sometimes called the "window" or "ladder" greedy).

### The reframe

Think of each index as a node, and each possible jump as an edge. "Minimum number of jumps" is then "shortest path in an unweighted graph" - which is BFS. BFS processes the graph in **levels**: level 0 is the start, level 1 is everything reachable in one jump, level 2 everything reachable in two, and so on.

On this graph the levels have a special shape. Every level is a **contiguous range of indices**:

```text
nums  =  [ 2 | 3   1 | 1   4 ]
index      0 | 1   2 | 3   4
level      0 |   1   |   2
```

Why contiguous? If you can reach index `k` in `d` jumps, you can reach any index between the start and `k` in at most `d` jumps - the last jump could simply have been shorter. So the frontier of level `d` is never a scattered set; it is "everything up to some boundary".

That means BFS needs no queue. A level is fully described by its **right end**, and the next level's right end is the farthest anyone in the current level can jump.

### The two numbers

- `currentEnd` - the right edge of the level you are currently walking through.
- `farthest` - the farthest index reachable from any index seen so far.

Walk left to right. When `i` hits `currentEnd`, you have seen every index of this level, so `farthest` is exactly where the next level ends. Take a jump, move the boundary.

### Recognising it

- "minimum number of steps/jumps/moves" on an array, where each position gives a **range** of next positions
- a DP whose table comes out as runs of equal values (`0 | 1 1 | 2 2`)
- the problem looks like BFS but the graph is a line and the edges go to contiguous ranges

The mental question:

> Do the positions reachable in exactly `k` moves form one contiguous block? If so, I only need the block's right edge.

=== bruteForce ===
Think as if the greedy is unknown. The obvious correct approach is DP.

Let `dp[i]` = the minimum number of jumps to land on index `i`. `dp[0] = 0`, everything else starts at infinity. Then go left to right: from each index `i`, try every jump length `j = 1..nums[i]`, and offer `dp[i] + 1` to the landing index.

### Step logic

1. `dp = [0, INF, INF, ...]`.
2. For each `i` from left to right, for each `j` from `1` to `nums[i]` (stopping at the end of the array):
   - `dp[i + j] = min(dp[i + j], dp[i] + 1)`
3. Return `dp[n - 1]`.

Processing `i` in increasing order is safe because every jump goes forward: by the time we reach `i`, every index that could jump *to* `i` has already been processed.

### Dry run

```text
nums = [2, 3, 1, 1, 4]
dp   = [0, INF, INF, INF, INF]
```

| i | nums[i] | dp[i] | j | target `i+j` | offer `dp[i]+1` | dp[target] before | dp[target] after | dp after |
| -: | ------: | ----: | -: | -----------: | --------------: | ----------------: | ---------------: | :------- |
| 0 | 2 | 0 | 1 | 1 | 1 | INF | **1** | `[0,1,INF,INF,INF]` |
| 0 | 2 | 0 | 2 | 2 | 1 | INF | **1** | `[0,1,1,INF,INF]` |
| 1 | 3 | 1 | 1 | 2 | 2 | 1 | 1 | `[0,1,1,INF,INF]` |
| 1 | 3 | 1 | 2 | 3 | 2 | INF | **2** | `[0,1,1,2,INF]` |
| 1 | 3 | 1 | 3 | 4 | 2 | INF | **2** | `[0,1,1,2,2]` |
| 2 | 1 | 1 | 1 | 3 | 2 | 2 | 2 | `[0,1,1,2,2]` |
| 3 | 1 | 2 | 1 | 4 | 3 | 2 | 2 | `[0,1,1,2,2]` |
| 4 | 4 | 2 | - | past the end | - | - | - | `[0,1,1,2,2]` |

```text
dp[4] = 2
```

Correct. Seven relaxations; three of them changed nothing.

### Java

```java
class Solution {
    public int jump(int[] nums) {

        int n = nums.length;
        int[] dp = new int[n];
        Arrays.fill(dp, Integer.MAX_VALUE);
        dp[0] = 0;

        for (int i = 0; i < n; i++) {
            if (dp[i] == Integer.MAX_VALUE) continue;     // unreachable, nothing to offer

            for (int j = 1; j <= nums[i] && i + j < n; j++) {
                dp[i + j] = Math.min(dp[i + j], dp[i] + 1);
            }
        }

        return dp[n - 1];
    }
}
```

### Complexity

**Time:** `O(n * maxJump)`, which is `O(n^2)` when jumps are as long as the array. **Space:** `O(n)` for `dp`.

With `n = 10^4` and `nums[i]` up to `1000`, that is up to `10^7` relaxations - it passes, but only just, and only because jump lengths are capped.

### Where it hurts

Look at the final table:

```text
index:  0 | 1  2 | 3  4
dp:     0 | 1  1 | 2  2
```

It is **sorted**, and it is made of **flat runs**. That is not a coincidence of this example - it is always true (the pattern section explains why: anything before a reachable index is reachable in no more jumps).

Now look at what the inner loop spends its time on. From `i = 1`, it writes `dp[2] = min(1, 2)` - but `dp[2]` was already in an earlier run, so nothing from a later run could ever improve it. From `i = 3` it offers `3` to `dp[4]`, which already holds `2`. Every offer that lands inside a run that is already filled is wasted.

The only information that actually matters from each run is: **how far right does this run push the next run?** That is one number per level, not one write per (index, jump length) pair.

=== optimization ===
### The observation

The `dp` array is a staircase: `0 | 1 1 | 2 2 | ...`. Each step of the staircase is one BFS level, and each level is a contiguous range. So instead of filling `dp`, track only:

- `currentEnd` - the last index of the level we are walking through now
- `farthest` - the farthest index any index seen so far can reach (that will become the next level's end)
- `jumps` - how many levels we have closed

Walk `i` from left to right. At every index, update `farthest = max(farthest, i + nums[i])`. When `i == currentEnd`, the current level is exhausted, so we must jump: `jumps++`, and the next level ends at `currentEnd = farthest`.

### Why stop the loop at `n - 2`

We only need to *reach* the last index, not jump *from* it. If the loop ran to `n - 1` and `n - 1` happened to be a level boundary, it would count one more jump out of the last index - a jump that does not exist.

### Dry run

```text
nums = [2, 3, 1, 1, 4]       loop i = 0 .. 3
jumps = 0, currentEnd = 0, farthest = 0
```

| i | nums[i] | `i + nums[i]` | farthest after `max` | `i == currentEnd`? | jumps | currentEnd |
| -: | ------: | ------------: | -------------------: | :----------------- | ----: | ---------: |
| - | - | - | 0 | - | 0 | 0 |
| 0 | 2 | 2 | 2 | 0 == 0 yes - jump | 1 | 2 |
| 1 | 3 | 4 | 4 | 1 == 2 no | 1 | 2 |
| 2 | 1 | 3 | 4 | 2 == 2 yes - jump | 2 | 4 |
| 3 | 1 | 4 | 4 | 3 == 4 no | 2 | 4 |

```text
jumps = 2
```

Read it against the BFS levels:

```text
index      0 | 1   2 | 3   4
level      0 |   1   |   2
                 ^       ^
       closed at i=0   closed at i=2, new end = 4 = last index
```

- At `i = 0`: level 0 is just index `0`. It reaches up to `2`, so level 1 is indices `1..2`.
- At `i = 1, 2`: walking level 1. Index `1` reaches `4`, index `2` reaches `3`. Best is `4`.
- At `i = 2`: level 1 is exhausted, so level 2 ends at `4` - the last index. Two jumps.

### Where the greedy choice actually is

Notice the algorithm never decides *which* index to jump to. It only decides *when* a jump is forced (the level ran out) and *how far the next level extends* (the best reach seen inside this level). That is why the trap from the problem section - always jumping as far as possible from where you stand - does not apply. The greedy is "extend the frontier as far as any member of this level can", not "take the longest jump from here".

### What the DP's waste turned into

The brute force did one write per (index, jump length) pair. Here each index does one `max` and one comparison. The staircase is never stored - only its current step edge (`currentEnd`) and the next one (`farthest`).

=== complexity ===
### Time

One pass over `n - 1` indices, constant work each.

```text
O(n)
```

### Space

Three integers.

```text
O(1)
```

### Comparison

| Approach | Time | Space | Work per index |
| :------- | ---: | ----: | :------------- |
| Plain recursion (try every jump) | exponential | `O(n)` stack | branches `nums[i]` ways |
| DP relaxation | `O(n * maxJump)` up to `O(n^2)` | `O(n)` | `nums[i]` writes |
| Explicit BFS with a queue | `O(n * maxJump)` naive, `O(n)` with care | `O(n)` | enqueue new indices |
| Greedy levels | **`O(n)`** | **`O(1)`** | one `max`, one compare |

The BFS row is worth saying out loud in an interview: "this is BFS, and because levels are contiguous I can drop the queue and keep only the level boundary." It shows where the greedy came from.

=== implementation ===
```java
class Solution {
    public int jump(int[] nums) {

        int jumps = 0;
        int currentEnd = 0;     // last index of the level we are walking through
        int farthest = 0;       // farthest index reachable from anything seen so far

        // Stop at n - 2: we need to REACH the last index, not jump out of it.
        for (int i = 0; i < nums.length - 1; i++) {
            farthest = Math.max(farthest, i + nums[i]);

            if (i == currentEnd) {      // this level is used up - a jump is forced
                jumps++;
                currentEnd = farthest;  // the next level ends where the best reach lands
            }
        }

        return jumps;
    }
}
```

### The lines that matter

**1.**

```java
for (int i = 0; i < nums.length - 1; i++) {
```

`nums.length - 1` as the bound, so `i` stops at `n - 2`. With `i < nums.length`, the input `[2,3,1,1,4]` returns `3`: at `i = 4`, `i == currentEnd` is true and a phantom jump out of the last index is counted.

**2.**

```java
farthest = Math.max(farthest, i + nums[i]);
```

Update `farthest` **before** checking the boundary. Index `currentEnd` itself belongs to the current level, so its reach must count towards the next level's end.

**3.**

```java
if (i == currentEnd) {      // this level is used up - a jump is forced
```

The jump is counted when a level runs out, not when you "choose" a destination. `jumps` counts closed levels, which is exactly the BFS distance to the last index.

### The bonus: Jump Game (LC 55)

The same `farthest` idea answers the yes/no version - can you reach the end at all? If `i` ever exceeds the farthest reachable index, you are stuck.

```java
class Solution {
    public boolean canJump(int[] nums) {

        int farthest = 0;

        for (int i = 0; i < nums.length; i++) {
            if (i > farthest) return false;           // i is past everything reachable
            farthest = Math.max(farthest, i + nums[i]);
        }

        return true;
    }
}
```

### Java notes

- `i + nums[i]` can exceed `n - 1`. That is fine - `farthest` is allowed to point past the end; we never index into the array with it.
- No overflow risk: `i < 10^4` and `nums[i] <= 1000`.
- The problem guarantees reachability. Without it, `currentEnd = farthest` could leave `currentEnd` unchanged at a zero (`farthest == i`), and the method would return a meaningless count. Add `if (farthest <= i) return -1;` inside the boundary check if the guarantee is removed.

=== edgeCases ===
### Single element

```text
[0]  ->  0
```

The loop bound is `0`, so it never runs. You start on the last index.

### Two elements

```text
[1, 2]  ->  1
```

`i = 0`: `farthest = 1`, `0 == 0`, `jumps = 1`. Loop ends.

### First jump reaches the end

```text
[4, 1, 1, 1, 1]  ->  1
```

At `i = 0`, `currentEnd` becomes `4`. No later `i` in `1..3` equals `4`, so no more jumps are counted.

### All ones

```text
[1, 1, 1, 1]  ->  3
```

Every level is a single index, so every `i` from `0` to `2` is a boundary. This is the worst case for the number of jumps, `n - 1`.

### Zeros that must be jumped over

```text
[2, 3, 0, 1, 4]  ->  2
```

LeetCode's second example. Index `2` is a dead end (`nums[2] = 0`), but it is inside level 1, so its tiny reach is simply outvoted by index `1`'s reach of `4`.

### Longest jump first is the wrong move

```text
[2, 3, 1, 1, 4]  ->  2   (not 3)
```

Always jumping as far as possible from where you stand goes `0 -> 2 -> 3 -> 4`, three jumps. The level greedy never commits to a landing index, so it does not fall into this.

### Running the loop one step too far

```text
[2, 3, 1, 1, 4]  with  i < nums.length  ->  3   (wrong)
[1, 2]           with  i < nums.length  ->  2   (wrong)
```

Both fail because the last index happens to be exactly a level boundary.

### Large jumps near the end

```text
[1, 1, 1, 1000]  ->  3
```

`nums[n-1]` is never read in a way that matters - the loop stops before it. Only the values you jump *from* count.

=== takeaway ===
> When you see **"minimum jumps/steps"** where each position gives a **contiguous range** of next positions, think **BFS levels tracked by two boundaries: `currentEnd` and `farthest`**.

### The core observation

The set of indices reachable in exactly `k` jumps is one contiguous block. So BFS does not need a queue - a level is described by its right edge. Walk the array; collect the best reach inside the current level; when you hit the level's edge, count a jump and move the edge to the best reach.

### The pattern trigger

```text
      each position i reaches the range [i+1, i+nums[i]]
                          |
                          v
           "minimum jumps"  =  BFS distance
                          |
                          v
         levels are contiguous  ->  no queue needed
                          |
                          v
   for i in 0 .. n-2:
       farthest = max(farthest, i + nums[i])
       if i == currentEnd:  jumps++, currentEnd = farthest
```

### The common mistakes

**Jumping as far as possible from the current index.** Plausible, wrong on the very first example.

**Looping to `n - 1`.** Counts a phantom jump out of the last index whenever it is a level boundary.

**Checking the boundary before updating `farthest`.** The boundary index belongs to the current level; skipping its reach can make the next level too short.

### What to remember in six months

> Minimum jumps is BFS. Contiguous levels mean BFS collapses to two integers.
