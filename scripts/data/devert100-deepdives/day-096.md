=== intro ===
Yesterday's LIS was DP over **one** sequence: `dp[i]` = best chain ending at `i`. Today there are **two** sequences, so the state needs two indices - one into each string - and the table becomes a grid.

> The habit for today: when two strings are compared character by character, the state is "how much of each string have I used?". Look at the last character of each prefix. Either they match and both get consumed together, or they don't and one of them has to go. That three-way choice is the skeleton of every two-string DP - including tomorrow's Edit Distance.

=== problem ===
Given two strings `text1` and `text2`, return the length of their **longest common subsequence** - the longest string that is a subsequence of both. If there is none, return `0`.

A *subsequence* keeps the original order but may skip characters.

```text
text1 = "abcde"
text2 = "ace"        ->  3
```

| LCS | in text1 | in text2 |
| :-- | :------- | :------- |
| "ace" | **a** b **c** d **e** | **a** **c** **e** |

### What makes it non-trivial

**Order must be kept in both strings at once.** `"abc"` and `"cba"` share all three letters, but the LCS is only `1` - any two of them appear in opposite orders in the two strings.

**Greedy matching fails.** The obvious approach - walk `text1`, and for each character grab its next occurrence in `text2` - commits too early:

```text
text1 = "cab", text2 = "abc"

'c' -> found at text2[2]; nothing in text2 after index 2
'a' -> no 'a' after index 2
'b' -> no 'b' after index 2
greedy = 1
```

The true answer is `2` (`"ab"`). Matching the `c` used up the end of `text2` and blocked two later matches. Whether to match a character depends on what comes **after** it, in both strings - which is why this needs a table, not a scan.

### Constraints that matter

`1 <= text1.length, text2.length <= 1000`, lowercase English letters. An `m x n` table is at most `10^6` cells - fine. Trying all `2^1000` subsequences of one string is not.

=== pattern ===
**2D DP on two strings (prefix x prefix).**

### The state

```text
dp[i][j] = LCS length of text1's first i characters and text2's first j characters
```

The table is `(m + 1) x (n + 1)`. Row `0` and column `0` stand for the **empty prefix**, and the LCS of anything with an empty string is `0`. That extra row and column means the recurrence never needs an "is this index valid?" check.

### The recurrence - look at the last characters

Compare `text1[i-1]` and `text2[j-1]` (the last character of each prefix):

```text
if they match:     dp[i][j] = 1 + dp[i-1][j-1]              use both, shrink both
otherwise:         dp[i][j] = max( dp[i-1][j],              drop text1's last char
                                   dp[i][j-1] )             drop text2's last char
```

Why is this complete?

- **Match.** If the last characters are equal, some LCS ends with that character paired with itself. Taking it can never hurt: whatever LCS the two shorter prefixes have, adding the matched pair extends it by one.
- **No match.** The last characters cannot both be in the LCS paired with each other (they differ). So at least one of them is unused - and we do not know which, so try both and keep the better.

### Recognising it

Reach for prefix-by-prefix 2D DP when:

- the input is **two strings or two arrays**
- the answer is built by **aligning** them in order: common subsequence, edit distance, interleaving, wildcard / regex matching, distinct subsequences
- a decision at the end of each prefix is "consume from one, the other, or both"

The mental question:

> Looking only at the last element of each prefix, what are my options - and does each option leave me with two shorter prefixes?

=== bruteForce ===
Write the recurrence as plain recursion, with no table yet.

### Step logic

`lcs(i, j)` = LCS of `text1[0..i-1]` and `text2[0..j-1]`.

1. If `i == 0` or `j == 0`: return `0` (an empty prefix).
2. If `text1[i-1] == text2[j-1]`: return `1 + lcs(i-1, j-1)`.
3. Otherwise return `max(lcs(i-1, j), lcs(i, j-1))`.

The answer is `lcs(m, n)`.

### Dry run

```text
text1 = "abcde", text2 = "ace"
```

Calls in the order they **finish**. Base-case calls (`i == 0` or `j == 0`) return `0` and are shown inside their parent's row.

| call | text1 prefix | text2 prefix | compare and recurse | returns |
| :--- | :----------- | :----------- | :------------------ | ------: |
| `lcs(1,1)` | a | a | match 'a': 1 + `lcs(0,0)` = 1 + 0 | 1 |
| `lcs(2,1)` | ab | a | 'b' vs 'a': max(`lcs(1,1)` = 1, `lcs(2,0)` = 0) | 1 |
| `lcs(3,2)` | abc | ac | match 'c': 1 + `lcs(2,1)` = 1 + 1 | 2 |
| `lcs(1,1)` | a | a | match 'a': 1 + `lcs(0,0)` = 1 + 0 | 1 |
| `lcs(2,1)` | ab | a | 'b' vs 'a': max(`lcs(1,1)` = 1, `lcs(2,0)` = 0) | 1 |
| `lcs(3,1)` | abc | a | 'c' vs 'a': max(`lcs(2,1)` = 1, `lcs(3,0)` = 0) | 1 |
| `lcs(4,1)` | abcd | a | 'd' vs 'a': max(`lcs(3,1)` = 1, `lcs(4,0)` = 0) | 1 |
| `lcs(4,2)` | abcd | ac | 'd' vs 'c': max(`lcs(3,2)` = 2, `lcs(4,1)` = 1) | 2 |
| `lcs(5,3)` | abcde | ace | match 'e': 1 + `lcs(4,2)` = 1 + 2 | **3** |

Answer `3`. Read the top-level chain backwards: `e` matched, then `lcs(4,2)` dropped `d`, then `c` matched, then `lcs(2,1)` dropped `b`, then `a` matched - the LCS `"ace"`.

Rows 4 and 5 are rows 1 and 2 again: `lcs(2,1)` and `lcs(1,1)` were each computed **twice**. In total the recursion made **15** calls (9 shown, plus 6 base cases) for a problem with only `6 * 4 = 24` possible `(i, j)` states, most of which it never needed.

### Java

```java
class Solution {
    public int longestCommonSubsequence(String text1, String text2) {
        return lcs(text1, text2, text1.length(), text2.length());
    }

    // LCS of text1's first i chars and text2's first j chars.
    private int lcs(String a, String b, int i, int j) {
        if (i == 0 || j == 0) {
            return 0;
        }
        if (a.charAt(i - 1) == b.charAt(j - 1)) {
            return 1 + lcs(a, b, i - 1, j - 1);
        }
        return Math.max(lcs(a, b, i - 1, j), lcs(a, b, i, j - 1));
    }
}
```

### Complexity

**Time:** `O(2^(m+n))` worst case - **Space:** `O(m + n)` recursion stack

### Where it hurts

The example matched often, and every match is a single recursive call. The worst case is **no matches at all**, where every call branches twice:

```text
text1 = "abc", text2 = "xyz"   ->  0, after 39 calls
```

There, the two paths

```text
drop text1's 'c', then drop text2's 'z'   ->  lcs(2, 2)
drop text2's 'z', then drop text1's 'c'   ->  lcs(2, 2)
```

reach the same subproblem, and the same is true at every level below. In general the no-match call count is `2 * C(m+n, m) - 1`; for two 1000-character strings that is a number with about 600 digits.

But `lcs(i, j)` depends only on `i` and `j`. There are only `(m + 1) * (n + 1)` of them - about `10^6` at the limits. Compute each once and the recursion becomes a table.

=== optimization ===
### The observation

Every call `lcs(i, j)` reads only three neighbours: `(i-1, j-1)`, `(i-1, j)` and `(i, j-1)` - up, left, and up-left. All three have a smaller `i` or a smaller `j`. So if we fill a table **row by row, left to right**, every value a cell needs is already there when we reach it.

### Building the table

1. Allocate `dp[m + 1][n + 1]`. Row `0` and column `0` stay `0` (empty prefixes).
2. For `i = 1..m`, `j = 1..n`:
   - match: `dp[i][j] = 1 + dp[i-1][j-1]` (diagonal)
   - no match: `dp[i][j] = max(dp[i-1][j], dp[i][j-1])` (up or left)
3. Return `dp[m][n]`.

### Dry run - every cell

```text
text1 = "abcde" (rows), text2 = "ace" (columns)
```

| i, j | text1[i-1] | text2[j-1] | match? | computation | `dp[i][j]` |
| :--- | :--------- | :--------- | :----- | :---------- | ---------: |
| 1, 1 | a | a | yes | 1 + dp[0][0] = 1 + 0 | 1 |
| 1, 2 | a | c | no | max(dp[0][2] = 0, dp[1][1] = 1) | 1 |
| 1, 3 | a | e | no | max(dp[0][3] = 0, dp[1][2] = 1) | 1 |
| 2, 1 | b | a | no | max(dp[1][1] = 1, dp[2][0] = 0) | 1 |
| 2, 2 | b | c | no | max(dp[1][2] = 1, dp[2][1] = 1) | 1 |
| 2, 3 | b | e | no | max(dp[1][3] = 1, dp[2][2] = 1) | 1 |
| 3, 1 | c | a | no | max(dp[2][1] = 1, dp[3][0] = 0) | 1 |
| 3, 2 | c | c | yes | 1 + dp[2][1] = 1 + 1 | 2 |
| 3, 3 | c | e | no | max(dp[2][3] = 1, dp[3][2] = 2) | 2 |
| 4, 1 | d | a | no | max(dp[3][1] = 1, dp[4][0] = 0) | 1 |
| 4, 2 | d | c | no | max(dp[3][2] = 2, dp[4][1] = 1) | 2 |
| 4, 3 | d | e | no | max(dp[3][3] = 2, dp[4][2] = 2) | 2 |
| 5, 1 | e | a | no | max(dp[4][1] = 1, dp[5][0] = 0) | 1 |
| 5, 2 | e | c | no | max(dp[4][2] = 2, dp[5][1] = 1) | 2 |
| 5, 3 | e | e | yes | 1 + dp[4][2] = 1 + 2 | **3** |

The finished grid:

```text
              ""   a   c   e
        ""     0   0   0   0
        a      0   1   1   1
        b      0   1   1   1
        c      0   1   2   2
        d      0   1   2   2
        e      0   1   2   3   <- dp[5][3]
```

Fifteen cells, each computed once with `O(1)` work. The values the recursion computed twice (`dp[1][1]`, `dp[2][1]`) are now read, not recomputed.

### Recovering the subsequence itself

Start at `(m, n)` and walk back:

```text
(5,3) e == e  -> take 'e', go to (4,2)
(4,2) d != c  -> dp[3][2] = 2 >= dp[4][1] = 1, go up to (3,2)
(3,2) c == c  -> take 'c', go to (2,1)
(2,1) b != a  -> dp[1][1] = 1 >= dp[2][0] = 0, go up to (1,1)
(1,1) a == a  -> take 'a', go to (0,0)
collected backwards: "ace"
```

This is the classic follow-up ("print the LCS"), and the reason to keep the full 2D table when it is asked for.

### Step further - two rows are enough

Row `i` reads only row `i - 1` and itself. Keep two arrays, `prev` and `curr`, swap after each row, and the space drops to `O(n)`:

```java
class Solution {
    public int longestCommonSubsequence(String text1, String text2) {

        int m = text1.length(), n = text2.length();
        int[] prev = new int[n + 1];    // row i - 1
        int[] curr = new int[n + 1];    // row i

        for (int i = 1; i <= m; i++) {
            for (int j = 1; j <= n; j++) {
                if (text1.charAt(i - 1) == text2.charAt(j - 1)) {
                    curr[j] = 1 + prev[j - 1];
                } else {
                    curr[j] = Math.max(prev[j], curr[j - 1]);
                }
            }
            int[] tmp = prev;
            prev = curr;
            curr = tmp;
        }

        return prev[n];
    }
}
```

After the last swap, `prev` holds row `m`, so the answer is `prev[n]`. `curr[0]` is never written and stays `0`, which is the empty-prefix column.

=== complexity ===
### Time

Every one of the `m * n` cells is filled once with a comparison and a `max`.

```text
O(m * n)
```

### Space

The full table:

```text
O(m * n)
```

With two rolling rows, `O(n)` - or `O(min(m, n))` if you make the shorter string the column string.

### Comparison

| Approach | Time | Space | Notes |
| :------- | ---: | ----: | :---- |
| Recursion | `O(2^(m+n))` | `O(m + n)` stack | 39 calls on two 3-letter strings with no overlap |
| Recursion + memo | `O(m * n)` | `O(m * n)` + stack | deep recursion at 1000 x 1000 is a stack risk |
| 2D table | **`O(m * n)`** | `O(m * n)` | can reconstruct the LCS string |
| Two rolling rows | **`O(m * n)`** | **`O(n)`** | length only |
| Greedy first-match | `O(m * n)` | `O(1)` | **wrong** - "cab" / "abc" gives 1, answer 2 |

=== implementation ===
```java
class Solution {
    public int longestCommonSubsequence(String text1, String text2) {

        int m = text1.length(), n = text2.length();

        // dp[i][j] = LCS of text1's first i chars and text2's first j chars.
        // Row 0 and column 0 are the empty prefix: LCS = 0.
        int[][] dp = new int[m + 1][n + 1];

        for (int i = 1; i <= m; i++) {
            for (int j = 1; j <= n; j++) {
                if (text1.charAt(i - 1) == text2.charAt(j - 1)) {
                    dp[i][j] = 1 + dp[i - 1][j - 1];                 // use both
                } else {
                    dp[i][j] = Math.max(dp[i - 1][j], dp[i][j - 1]); // drop one
                }
            }
        }

        return dp[m][n];
    }
}
```

### The lines that matter

**1.**

```java
int[][] dp = new int[m + 1][n + 1];
```

The `+ 1` is the design decision of the whole solution. Index `0` means "empty prefix", so the base case is already sitting in the zero-filled array and the loops start at `1` with no bounds checks. Size it `m x n` and every `i - 1` at the edge needs special-casing.

**2.**

```java
if (text1.charAt(i - 1) == text2.charAt(j - 1)) {
```

`i - 1`, not `i`. Table index `i` means "the first `i` characters", whose last character lives at string index `i - 1`. Mixing these two indexings is the most common bug in this problem.

**3.**

```java
dp[i][j] = Math.max(dp[i - 1][j], dp[i][j - 1]); // drop one
```

On a mismatch there is no `dp[i - 1][j - 1]` term. It is never larger than either of the other two (each of them contains it as a sub-case), so including it changes nothing - but adding `1` to it would be the classic wrong answer.

### Java notes

- `charAt` on a `String` is `O(1)`. Converting to `char[]` first with `toCharArray()` is a small constant-factor speed-up some people prefer.
- A `1001 x 1001` `int` table is about 4 MB - fine on LeetCode. If memory is tight, use the two-row version above.
- A top-down memo version recurses up to `m + n = 2000` deep, which is usually fine but is the reason bottom-up is the safer default.

=== edgeCases ===
### Identical strings

```text
"abc", "abc"  ->  3
```

Every diagonal cell matches; `dp[i][i] = i`.

### Nothing in common

```text
"abc", "def"  ->  0
```

No cell ever takes the match branch, so every `max` is over zeros.

### Single characters

```text
"a", "a"  ->  1
"a", "b"  ->  0
```

A `2 x 2` table with one real cell.

### One string is a subsequence of the other

```text
"abcde", "ace"  ->  3
```

The main example. The answer equals the shorter string's length exactly when the shorter one is a subsequence of the longer.

### Same letters, opposite order

```text
"abc", "cba"  ->  1
```

Any two letters appear in opposite orders, so no pair survives. Shows that LCS is about order, not just shared characters.

### Repeated characters

```text
"aaaa", "aa"  ->  2
```

Each `a` in `text2` can be paired with only one `a` in `text1`. The table caps it naturally at the shorter count.

### Different lengths, partial overlap

```text
"bl", "yby"  ->  1
```

Only `b` is shared.

### The greedy trap

```text
"cab", "abc"  ->  2       (greedy first-match gives 1)
```

Matching `c` first consumes the end of `text2` and blocks `a` and `b`. The DP considers dropping `c` instead.

=== takeaway ===
> When you see **two strings compared in order**, think **`dp[i][j]` over prefixes, `(m+1) x (n+1)`**, and decide each cell by **the last character of each prefix**: match -> diagonal, mismatch -> best of up and left.

### The core observation

The last characters of two prefixes either match - and then pairing them is always safe - or they don't, and at least one of them is unused. That turns one hard global question into three smaller ones, each about shorter prefixes. There are only `m * n` prefix pairs, so the exponential recursion becomes a grid filled once.

### The pattern trigger

```text
        two sequences, order matters in both
                        |
                        v
        state = (prefix length of A, prefix length of B)
        table (m+1) x (n+1), row/col 0 = empty prefix
                        |
                        v
        last chars equal?   yes -> 1 + dp[i-1][j-1]       (diagonal)
                            no  -> max(dp[i-1][j], dp[i][j-1])  (up, left)
                        |
                        v
        fill row by row; answer dp[m][n]
```

### The common mistakes

**Off-by-one between table and string indices.** `dp[i][j]` compares `charAt(i - 1)` and `charAt(j - 1)`.

**Sizing the table `m x n`.** Loses the empty-prefix row and column, forcing edge checks everywhere.

**Greedy matching.** Grabbing the first available match fails on `"cab"` / `"abc"`.

**Confusing subsequence with substring.** Longest common **substring** needs contiguity: on a mismatch the cell resets to `0` instead of taking a `max`, and the answer is the maximum cell, not `dp[m][n]`.

### What to remember in six months

> Match -> diagonal plus one. Mismatch -> max of up and left. Row 0 and column 0 are the empty string.

This grid is the template for a whole family. Tomorrow's Edit Distance (LC 72) uses the same three neighbours with `min` and costs instead of `max`. Delete Operation for Two Strings (LC 583) is `m + n - 2 * LCS`. Shortest Common Supersequence (LC 1092) is `m + n - LCS` in length, built by walking the LCS table back. Longest Palindromic Subsequence (LC 516) is the LCS of a string and its reverse.
