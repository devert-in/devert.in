=== intro ===
Three days of graph theory end here. Today starts **Greedy**: algorithms that make one locally best choice, commit to it, and never look back.

> A greedy algorithm is only as good as its proof. "Pick the best-looking option" is not an algorithm until you can say **why** the choice you made can never be the one that costs you the optimum. Today's problem has three plausible greedy rules; only one survives that question.

=== problem ===
There is one room and `n` meetings. Meeting `i` runs from `start[i]` to `end[i]`. The room can host one meeting at a time. Return the **maximum number** of meetings that can be held.

On GeeksforGeeks ("N meetings in one room" and "Activity Selection") the start of a chosen meeting must be **strictly greater** than the end of the previous one - a meeting ending at `4` and one starting at `4` cannot both be held.

```text
start = [0, 5, 1, 3]
end   = [6, 7, 2, 4]
answer = 3
```

Lay the meetings out on a timeline:

| meeting | start | end | timeline (0 to 7, two characters per unit) |
| -: | ----: | --: | :---------------- |
| 0 | 0 | 6 | `[===========]  ` |
| 1 | 5 | 7 | `          [===]` |
| 2 | 1 | 2 | `  [=]          ` |
| 3 | 3 | 4 | `      [=]      ` |

```text
best schedule:  meeting 2 (1-2), meeting 3 (3-4), meeting 1 (5-7)   ->  3 meetings
```

Meeting `0` is the trap: it starts first, but it occupies the room through `6` and blocks all three of the others.

### The larger GFG example

```text
start = [1, 3, 0, 5, 8, 5]
end   = [2, 4, 6, 7, 9, 9]
answer = 4      (1-2, 3-4, 5-7, 8-9)
```

The four-meeting version above is the same problem with fewer rows, so the brute force can be traced completely.

### What the constraints tell you

- `n` up to `10^5`. Trying every subset is `2^n` - hopeless beyond about 20. The expected solution is `O(n log n)`, which is the cost of **one sort**.
- The question asks for a **count**, not which meetings. That is a hint that some simple rule picks them.

=== pattern ===
**Greedy - sort by end time.**

The reframe: instead of asking "which set of meetings is best?", ask "**which meeting should go first?**" - then repeat the same question for whatever time is left.

The answer is: the meeting that **ends earliest**. It frees the room as soon as possible, which leaves the most time for everything after it.

### Why the three obvious rules are not equal

| greedy rule | idea | counterexample | greedy gets | optimum |
| :---------- | :--- | :------------- | ----------: | ------: |
| earliest **start** | get going early | `(0,6) (1,2) (3,4) (5,7)` | 1 | 3 |
| shortest **duration** | use little time | `(1,5) (4,7) (6,10)` | 1 | 2 |
| earliest **end** | free the room soonest | none exists | - | - |

Earliest start picks `(0,6)` and is stuck. Shortest duration picks `(4,7)`, which is short but sits across the boundary of both others. Earliest end never makes a choice it regrets - the proof is in the optimisation section.

### Recognising it

Reach for "sort by end, take what fits" when:

- you choose a **maximum number** of intervals that do not overlap
- the words are "meetings", "activities", "jobs with start and end", "non-overlapping", "arrows to burst balloons", "minimum removals to make intervals disjoint"
- every item is worth the same (each meeting counts as 1)

The mental question:

> If I must commit to one interval now, which choice leaves the **most room** for the rest?

When intervals carry different **weights** (profit per meeting), this greedy breaks and the problem becomes DP (Weighted Job Scheduling). The "every item counts 1" condition is what makes greedy safe.

=== bruteForce ===
No cleverness: try every subset of meetings, keep the ones where no two overlap, and remember the largest.

Represent a subset as a bitmask: bit `i` set means meeting `i` is chosen. For each mask, check every pair of chosen meetings. Two meetings are compatible when one ends strictly before the other starts:

```text
end[i] < start[j]   or   end[j] < start[i]
```

### Which pairs are compatible?

| pair | meetings | compatible? |
| :--- | :------- | :---------- |
| 0, 1 | `(0,6)`, `(5,7)` | no |
| 0, 2 | `(0,6)`, `(1,2)` | no |
| 0, 3 | `(0,6)`, `(3,4)` | no |
| 1, 2 | `(5,7)`, `(1,2)` | yes, `2 < 5` |
| 1, 3 | `(5,7)`, `(3,4)` | yes, `4 < 5` |
| 2, 3 | `(1,2)`, `(3,4)` | yes, `2 < 3` |

| ---: | :----- | :------- | :----- | ---: | ---------: |

| 1 | `0001` | 0 | yes | 1 | 1 |
| 2 | `0010` | 1 | yes | 1 | 1 |
| 3 | `0011` | 0, 1 | no - 0,1 clash | - | 1 |
| 4 | `0100` | 2 | yes | 1 | 1 |
| 5 | `0101` | 0, 2 | no - 0,2 clash | - | 1 |
| 6 | `0110` | 1, 2 | yes | 2 | 2 |
| 7 | `0111` | 0, 1, 2 | no - 0,1 clash | - | 2 |

| 10 | `1010` | 1, 3 | yes | 2 | 2 |

### Java

```java
class Solution {
    public int maxMeetings(int[] start, int[] end) {

        int n = start.length;
        int best = 0;

        // Every subset of meetings, as a bitmask.
        for (int mask = 0; mask < (1 << n); mask++) {

            boolean valid = true;

            for (int i = 0; i < n && valid; i++) {
                if ((mask & (1 << i)) == 0) continue;
                for (int j = i + 1; j < n; j++) {
                    if ((mask & (1 << j)) == 0) continue;
                    boolean apart = end[i] < start[j] || end[j] < start[i];
                    if (!apart) {
                        valid = false;
                        break;
                    }
                }
            }

            if (valid) {
                best = Math.max(best, Integer.bitCount(mask));
            }
        }

        return best;
    }
}
```

### Complexity

**Time:** `O(2^n * n^2)` - **Space:** `O(1)`

### Where it hurts

Ten of the sixteen rows are invalid, and **every one of them contains meeting 0**. The brute force discovers "meeting 0 clashes with everything" eight separate times and never learns from it.

More fundamentally, the brute force treats each subset as an unrelated question. But schedules have **structure**: time moves forward. Once you have decided which meeting goes first, the rest of the problem is the same problem on the time that remains. If there is a way to know the right first meeting **without trying the alternatives**, the search collapses into a single left-to-right pass.

=== optimization ===
### The key observation

Look at the meeting that **ends earliest** - call it `g`. In our example that is meeting 2, `(1,2)`.

> There is always an optimal schedule that starts with `g`.

**Proof by exchange.** Take any optimal schedule. Its first meeting is some `f`. Since `g` ends earliest of all, `end[g] <= end[f]`. Now swap `f` out and `g` in:

```text
optimal:   f ------]    second ---]   third ---]  ...
swapped:   g ---]       second ---]   third ---]  ...
                ^ ends no later than f did
```

Every other meeting in the schedule started after `f` ended, so it also starts after `g` ends. Nothing new clashes, and the count is unchanged. So the swapped schedule is also optimal - and it starts with `g`.

Once `g` is chosen, throw away every meeting that starts at or before `end[g]`, and the remaining problem is the same problem again. Apply the same argument: pick the earliest-ending meeting that still fits. And again.

That is the whole algorithm:

1. Sort meetings by end time.
2. Walk them in that order, remembering `lastEnd` - when the most recently chosen meeting finishes.
3. If a meeting starts after `lastEnd`, take it and update `lastEnd`. Otherwise skip it.

### Dry run

Sorted by end time:

| position | meeting | start | end |
| -------: | ------: | ----: | --: |
| 0 | 2 | 1 | 2 |
| 1 | 3 | 3 | 4 |
| 2 | 0 | 0 | 6 |
| 3 | 1 | 5 | 7 |

Walk them with `lastEnd = -infinity` and `count = 0`:

| meeting | start | end | `start > lastEnd`? | action | count | lastEnd |
| ------: | ----: | --: | :----------------- | :----- | ----: | ------: |
| - | - | - | - | start | 0 | -inf |
| 2 | 1 | 2 | `1 > -inf` yes | take | 1 | 2 |
| 3 | 3 | 4 | `3 > 2` yes | take | 2 | 4 |
| 0 | 0 | 6 | `0 > 4` no | skip | 2 | 4 |
| 1 | 5 | 7 | `5 > 4` yes | take | 3 | 7 |

Answer `3` - the same schedule (meetings 2, 3, 1) the brute force found at mask 14, after four comparisons instead of sixteen subsets.

### Why skipping is always safe

When meeting `0` is skipped, it is because it starts at `0`, before `lastEnd = 4`. It overlaps something already chosen. And because we process meetings in end order, everything already chosen ends **no later** than meeting `0` would - so swapping meeting `0` in for any of them could never help. The skip loses nothing.

### The same walk on the trap orderings

```text
sorted by START:  (0,6) (1,2) (3,4) (5,7)
                  take (0,6) -> lastEnd 6 -> every other start is <= 6 -> count 1

sorted by END:    (1,2) (3,4) (0,6) (5,7)
                  take, take, skip, take                          -> count 3
```

Same loop, same `lastEnd` logic. Only the sort key differs, and it decides everything.

=== complexity ===
### Time

Sorting `n` meetings is `O(n log n)`. The walk is one `O(n)` pass.

```text
O(n log n)
```

### Space

The meetings are paired into an `int[n][2]` array so they can be sorted together.

```text
O(n) for the paired copy, O(1) beyond it
```

The "`O(1)`" sometimes quoted for this problem assumes the input already arrives as pairs that may be sorted in place. With two parallel arrays, as GFG gives them, a paired copy (or an index array) is needed so that `start[i]` and `end[i]` stay together when sorting.

### Comparison

| Approach | Time | Space | Works for `n = 10^5`? |
| :------- | ---: | ----: | :-------------------- |
| All subsets | `O(2^n * n^2)` | `O(1)` | no - only up to about 20 |
| Greedy by start or duration | `O(n log n)` | `O(n)` | fast, but **wrong** |
| **Greedy by end** | **`O(n log n)`** | **`O(n)`** | yes |

The middle row is the important one. A wrong greedy is exactly as fast as the right one. Speed proves nothing; the exchange argument is what makes the third row correct.

=== implementation ===
```java
class Solution {
    public int maxMeetings(int[] start, int[] end) {

        int n = start.length;

        // Pair them so sorting keeps start[i] and end[i] together.
        int[][] meetings = new int[n][2];
        for (int i = 0; i < n; i++) {
            meetings[i][0] = start[i];
            meetings[i][1] = end[i];
        }

        // Earliest END first - the choice that leaves the most room.
        Arrays.sort(meetings, (a, b) -> Integer.compare(a[1], b[1]));

        int count = 0;
        int lastEnd = Integer.MIN_VALUE;   // nothing chosen yet

        for (int[] m : meetings) {
            if (m[0] > lastEnd) {          // strictly after: GFG forbids touching
                count++;
                lastEnd = m[1];
            }
        }

        return count;
    }
}
```

### The lines that matter

**1.**

```java
Arrays.sort(meetings, (a, b) -> Integer.compare(a[1], b[1]));
```

`a[1]` is the **end** time. Sorting by `a[0]` instead compiles, runs, and returns `1` on our example. This one index is the difference between the correct greedy and the plausible wrong one.

**2.**

```java
if (m[0] > lastEnd) {          // strictly after: GFG forbids touching
```

`>` because GFG says a meeting cannot start at the instant the previous one ends. If the problem allows touching (LeetCode 435 does), this becomes `>=`. Read the statement for this; it changes answers.

**3.**

```java
int lastEnd = Integer.MIN_VALUE;   // nothing chosen yet
```

A sentinel that every real start time beats, so the first meeting in sorted order is always taken without a special case.

### The follow-up - Non-overlapping Intervals (LC 435)

"Remove the minimum number of intervals so the rest do not overlap" is the same problem viewed from the other side: **keep** as many as possible, and remove the rest. Touching intervals like `[1,2]` and `[2,3]` count as non-overlapping there, so the comparison becomes `>=`.

```java
class Solution {
    public int eraseOverlapIntervals(int[][] intervals) {

        Arrays.sort(intervals, (a, b) -> Integer.compare(a[1], b[1]));

        int kept = 0;
        int lastEnd = Integer.MIN_VALUE;

        for (int[] in : intervals) {
            if (in[0] >= lastEnd) {        // touching is allowed here
                kept++;
                lastEnd = in[1];
            }
        }

        return intervals.length - kept;    // remove everything we did not keep
    }
}
```

### Java notes

- `Integer.compare(a[1], b[1])` rather than `a[1] - b[1]`. Subtraction overflows when values are far apart (for example `Integer.MIN_VALUE` and a positive number) and silently produces a wrong order.
- `Arrays.sort` on an `int[][]` with a comparator is a stable merge sort (TimSort), `O(n log n)`. Ties in end time keep their input order, which does not affect the count.
- GFG's older signature is `maxMeetings(int start[], int end[], int n)`; newer ones drop `n`. The body is identical - use `start.length` if `n` is not passed.

=== edgeCases ===
### One meeting

```text
start = [5], end = [9]  ->  1
```

### Touching meetings

```text
start = [1, 2], end = [2, 3]  ->  1     (GFG: strict, 2 > 2 is false)
```

The same intervals give `2` under LeetCode 435's rules, where touching is allowed. Same algorithm, one character different.

### Identical meetings

```text
start = [1, 1, 1], end = [2, 2, 2]  ->  1
```

The first is taken, `lastEnd = 2`, and the other two start at `1`, which is not `> 2`.

### One long meeting containing many short ones

```text
start = [1, 2, 4, 6], end = [10, 3, 5, 7]  ->  3
```

Sorted by end: `(2,3) (4,5) (6,7) (1,10)`. The three short ones are taken; the long one is skipped. Earliest-start would have taken `(1,10)` and stopped at `1`.

### Already disjoint

```text
start = [1, 4, 7], end = [2, 5, 8]  ->  3
```

Every meeting is taken. The answer can never exceed `n`.

### All overlapping, same end time

```text
start = [1, 2, 3], end = [4, 4, 4]  ->  1
```

Ties in end time do not matter: whichever is first is taken, and the others start before `4`.

### Zero-length meetings

```text
start = [2, 3], end = [2, 3]  ->  2
```

A meeting that starts and ends at the same moment is legal. `(2,2)` is taken, then `3 > 2`, so `(3,3)` is too.

### The shortest-duration trap

```text
start = [1, 4, 6], end = [5, 7, 10]  ->  2
```

Shortest-first takes `(4,7)` and blocks both others for an answer of `1`. Earliest-end takes `(1,5)`, skips `(4,7)`, takes `(6,10)`: `2`.

### LC 435 follow-up

```text
intervals = [[1,2], [2,3], [3,4], [1,3]]  ->  1
```

Kept: `[1,2]`, `[2,3]`, `[3,4]` (touching allowed). Removed: `[1,3]`. Answer `4 - 3 = 1`.

=== takeaway ===
> When you see **"choose the maximum number of non-overlapping intervals"**, think **sort by END time, take each interval that starts after the last one you took**.

### The core observation

The earliest-ending interval can always be the first in some optimal schedule, because swapping it in for whatever an optimal schedule starts with never creates a clash. After taking it, what remains is the same problem on less time, so the same choice repeats.

### The pattern trigger

```text
     intervals, each worth 1, no two may overlap
                       |
                       v
              sort by END time
                       |
                       v
      for each interval in that order:
           start > lastEnd ?   (>= if touching is allowed)
            /            \
          yes             no
      take it,           skip it
      lastEnd = end
```

### The common mistakes

**Sorting by start time.** It is the right key for **merging** intervals (Day 83), which is why it is the first one people reach for. For **selecting** intervals it fails as soon as an early interval is long.

**Sorting by duration.** Looks reasonable and fails on three intervals.

**Getting `>` versus `>=` wrong.** GFG forbids touching; LeetCode 435 allows it. The algorithm is identical; the boundary decides the answer.

**Trusting a greedy because it passed the examples.** Without an exchange argument, a greedy is a guess. Check it against small counterexamples before committing.

### What to remember in six months

> Selecting intervals: sort by **end**. Merging intervals: sort by **start**. Earliest finish leaves the most room for everything after it.

The same loop answers Non-overlapping Intervals (LC 435, as `n - kept`), Minimum Number of Arrows to Burst Balloons (LC 452), and Maximum Length of Pair Chain (LC 646). When intervals carry different weights, switch to DP with binary search - greedy no longer holds.
