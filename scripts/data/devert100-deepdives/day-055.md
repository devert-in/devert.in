=== intro ===
Yesterday's level order went *across* the tree with a queue. Today goes back *down* into recursion, but with a twist that will carry the rest of the trees block: the recursive function returns one thing to its parent while quietly recording something else on the side.

> When the answer at a node is built from facts about its children, compute those facts **once, on the way back up**. A post-order function can return what the parent needs and update a global answer in the same call.

=== problem ===
Given the `root` of a binary tree, return the length of its **diameter** - the longest path between any two nodes, measured in **edges**.

```text
        1
       / \
      2   3
     / \
    4   5

root   = [1, 2, 3, 4, 5]
output = 3
```

The longest path is `4 -> 2 -> 1 -> 3` (or `5 -> 2 -> 1 -> 3`, same length):

```text
4 --- 2 --- 1 --- 3
   1     2     3      edges
```

Four nodes, **three** edges. The answer is the edge count.

### What a "path" is here

A path is a sequence of nodes where each adjacent pair is connected by an edge, and no node repeats. It may go **up** and then **down** - it is not limited to root-to-leaf. Every path in a tree has exactly one highest node, where it bends:

```text
          bend
          /  \
   left arm    right arm
```

One arm (or both) can be empty. In the example the bend is at `1`, the left arm is `1 -> 2 -> 4` (2 edges), the right arm `1 -> 3` (1 edge). Total 3.

### Reading the constraints

| fact | consequence |
| :--- | :---------- |
| `1 <= n <= 10^4` | `O(n^2)` is 10^8 operations in the worst case - too slow to be comfortable |
| answer counted in **edges** | a single node has diameter `0`, not `1` |
| the path **need not pass through the root** | checking only the root is wrong |

### The condition that makes it non-trivial

The obvious guess is "left height plus right height at the root". It works on the example and fails here:

```text
        1
       /
      2
     / \
    3   4
   /     \
  5       6

through root 1:   left arm 1-2-3-5 = 3 edges, right arm empty    -> 3
bending at 2:     5-3-2-4-6                                       -> 4   (the real answer)
```

The best bend can be at **any** node. So the true question is: over every node, what is the longest path that bends there - and what is the maximum of those?

=== pattern ===
**DFS, post-order, "return height, update a global answer".**

### Why post-order

The longest path bending at a node `x` is:

```text
path(x) = height(x.left) + height(x.right)
```

where `height` counts **nodes** on the longest downward chain (`height(null) = 0`, `height(leaf) = 1`). A left subtree of height 2 contributes 2 edges: one from `x` to its child, one more inside.

To evaluate `path(x)` you need both children's heights first. Children before parent is precisely **post-order** (left, right, root).

### Why "return one thing, record another"

The parent of `x` does not care about `path(x)`. It only needs `height(x)` to compute its own path:

```text
height(x) = 1 + max(height(x.left), height(x.right))
```

So each call has two outputs that go in two directions:

```text
             returns height(x)  ------>  parent
                 |
     at x:  best = max(best, L + R)  -->  global answer
```

`L` and `R` are already in hand when you compute the height, so recording `L + R` costs nothing extra.

### Recognising it

Reach for "return height, update global" when:

- the answer is a **path** that can bend at any node (diameter, maximum path sum, longest univalue path)
- the value at a node combines **both** children, but the parent only needs **one** of them (the longer arm)
- the brute force calls a height/depth helper from inside another traversal

The mental question:

> What does my parent need from me, and is that different from what I need to compute the answer here? If yes, return the first and record the second.

=== bruteForce ===
Take the definition literally. For every node, compute the left height and the right height with a separate helper, add them, and keep the maximum.

### Step logic

1. `diameter(node)`: if `node` is `null`, return `0`.
2. `through = height(node.left) + height(node.right)` - the best path bending here.
3. Recurse: `left = diameter(node.left)`, `right = diameter(node.right)` - the best path bending anywhere below.
4. Return `max(through, left, right)`.

`height` is a full traversal of its subtree every time it is called.

### Dry run

```text
        1
       / \
      2   3
     / \
    4   5
```

`diameter` visits nodes in preorder: `1, 2, 4, 5, 3`. At each one it calls `height` twice. "Height visits" counts how many nodes those two calls touch.

| step | node | `height(left)` | `height(right)` | through | height visits | best so far |
| ---: | ---: | -------------: | --------------: | ------: | ------------: | ----------: |
| 1 | 1 | `height(2)` = 2 | `height(3)` = 1 | 3 | 3 + 1 = 4 | 3 |
| 2 | 2 | `height(4)` = 1 | `height(5)` = 1 | 2 | 1 + 1 = 2 | 3 |
| 3 | 4 | `height(null)` = 0 | `height(null)` = 0 | 0 | 0 | 3 |
| 4 | 5 | `height(null)` = 0 | `height(null)` = 0 | 0 | 0 | 3 |
| 5 | 3 | `height(null)` = 0 | `height(null)` = 0 | 0 | 0 | 3 |

```text
answer = 3
```

Correct. Look at steps 1 and 2: `height(2)` in step 1 already walked nodes `2, 4, 5` and computed `height(4) = 1` and `height(5) = 1` along the way. Step 2 computes them again from scratch.

### Java

```java
class Solution {
    public int diameterOfBinaryTree(TreeNode root) {

        if (root == null) return 0;

        // Longest path that bends at root.
        int through = height(root.left) + height(root.right);

        // Longest path that bends somewhere strictly below.
        int left = diameterOfBinaryTree(root.left);
        int right = diameterOfBinaryTree(root.right);

        return Math.max(through, Math.max(left, right));
    }

    // Number of nodes on the longest downward path from `node`.
    private int height(TreeNode node) {
        if (node == null) return 0;
        return 1 + Math.max(height(node.left), height(node.right));
    }
}
```

### Complexity

**Time:** `O(n^2)` worst case (skewed), `O(n log n)` balanced - **Space:** `O(h)` recursion stack

### Where it hurts

Every node's height is recomputed **once for each of its ancestors**, because each ancestor's `height` call re-walks the whole subtree below it.

On a skewed tree that is quadratic:

```text
1
 \
  2
   \
    3
     \
      4

diameter at 1: height walks 2, 3, 4         3 visits
diameter at 2: height walks 3, 4            2 visits
diameter at 3: height walks 4               1 visit
diameter at 4: nothing                      0 visits
                                           ----------
                                            6 = n(n-1)/2
```

With `n = 10^4` that is about 5 x 10^7 visits.

The waste is specific: `height(x)` is a fixed number. It does not depend on who asks. Yet we compute it repeatedly, and worse, we compute it in a **separate pass** from the one that needs it. The `diameter` walk and the `height` walk visit the same nodes; they just never share their work.

What if a single walk computed each height **once**, and at the same moment checked the path bending there?

=== optimization ===
### The observation

Inside `height(x)` we already have `height(x.left)` and `height(x.right)` in local variables - that is how `height(x)` is computed. Those two numbers are **exactly** what the diameter check at `x` needs.

So fold the diameter check into the height function:

```text
height(x):
    L = height(x.left)
    R = height(x.right)
    best = max(best, L + R)        <- the only new line
    return 1 + max(L, R)
```

One post-order walk. Each node's height computed once. The answer accumulates in `best` as the recursion unwinds.

### Why it is still correct

The brute force took `max` of `through` over every node. The new version also evaluates `L + R` at every node - just during the same traversal instead of a separate one. Same set of candidates, same maximum. The only thing removed is the repetition.

### Dry run - same tree

```text
        1
       / \
      2   3
     / \
    4   5
```

Post-order finishes nodes in the order `4, 5, 2, 3, 1`. Each row is the moment a call is about to return:

| step | node | L = height(left) | R = height(right) | L + R | best after | returns `1 + max(L, R)` |
| ---: | ---: | ---------------: | ----------------: | ----: | ---------: | ----------------------: |
| 1 | 4 | 0 | 0 | 0 | 0 | 1 |
| 2 | 5 | 0 | 0 | 0 | 0 | 1 |
| 3 | 2 | 1 | 1 | 2 | 2 | 2 |
| 4 | 3 | 0 | 0 | 0 | 2 | 1 |
| 5 | 1 | 2 | 1 | **3** | **3** | 3 |

```text
best = 3
```

Five rows for five nodes. Compare the brute force: five `diameter` calls *plus* six height visits, and the gap grows quadratically.

### Dry run - the tree where the root is not the answer

```text
        1
       /
      2
     / \
    3   4
   /     \
  5       6
```

Post-order: `5, 3, 6, 4, 2, 1`.

| step | node | L | R | L + R | best after | returns |
| ---: | ---: | -: | -: | ----: | ---------: | ------: |
| 1 | 5 | 0 | 0 | 0 | 0 | 1 |
| 2 | 3 | 1 | 0 | 1 | 1 | 2 |
| 3 | 6 | 0 | 0 | 0 | 1 | 1 |
| 4 | 4 | 0 | 1 | 1 | 1 | 2 |
| 5 | 2 | 2 | 2 | **4** | **4** | 3 |
| 6 | 1 | 3 | 0 | 3 | 4 | 4 |

The maximum was recorded at node `2`, three levels before the root. When the root checked its own path (3), `best` already held 4 and kept it. This is why the answer lives in a **global** rather than in the return value: the return value only ever carries one arm upward.

=== complexity ===
### Time

Each node is entered once and does `O(1)` work besides its two recursive calls.

```text
O(n)
```

### Space

No data structures - only the call stack, which is as deep as the tree is tall.

```text
O(h)
```

`h` is `log n` for a balanced tree and `n` for a skewed one. With `n = 10^4` a skewed tree recurses 10^4 deep, which Java's default stack handles on LeetCode.

### Comparison

| Approach | Time (balanced) | Time (skewed) | Space |
| :------- | --------------: | ------------: | ----: |
| Height helper at every node | `O(n log n)` | `O(n^2)` | `O(h)` |
| Post-order, return height + update best | **`O(n)`** | **`O(n)`** | `O(h)` |

The fix did not change the space at all. It removed repeated work by reusing a value the recursion was already computing.

=== implementation ===
```java
class Solution {

    private int best;

    public int diameterOfBinaryTree(TreeNode root) {
        best = 0;
        height(root);
        return best;
    }

    // Returns the height of `node` in nodes (null = 0, leaf = 1),
    // and records the longest path that bends at `node` on the way up.
    private int height(TreeNode node) {
        if (node == null) return 0;

        int left = height(node.left);
        int right = height(node.right);

        best = Math.max(best, left + right);   // path bending here, in edges

        return 1 + Math.max(left, right);       // what the parent needs
    }
}
```

### The lines that matter

**1.**

```java
best = Math.max(best, left + right);   // path bending here, in edges
```

`left + right`, not `left + right + 1`. Heights count nodes, and a left subtree of height `L` contributes exactly `L` edges to the path (one to the child, `L - 1` inside). Adding 1 would count nodes on the path, which is the classic off-by-one on this problem.

**2.**

```java
return 1 + Math.max(left, right);       // what the parent needs
```

The return value is **not** the diameter. A path coming up from the parent can only continue down **one** side of this node, so the parent gets the longer arm, plus one for this node.

**3.**

```java
best = 0;
```

Reset at the start of the public method. The field lives on the `Solution` object, and code that reuses an instance across calls would otherwise carry the previous tree's answer into the next one.

### Java notes

- A field (`private int best`) is the simplest way to give a recursive helper a shared, mutable answer. Java has no pass-by-reference for `int`, so a local in `diameterOfBinaryTree` could not be updated from inside `height`.
- Alternatives that avoid a field: pass an `int[] best = new int[1]` down the recursion and write `best[0]`, or return a small record `(height, diameter)` from each call. Both are fine; the field is the most readable in an interview.
- `height(null) = 0` is what makes leaves correct automatically: a leaf sees `left = right = 0`, records `0`, returns `1`.

=== edgeCases ===
### Single node

```text
root = [1]  ->  0
```

No edges exist. `height(1)` sees `0 + 0 = 0`. Answering `1` means you counted nodes.

### Two nodes

```text
root = [1, 2]  ->  1
```

One edge. At node `1`: `L = 1`, `R = 0`, `L + R = 1`.

### Skewed tree (a chain)

```text
root = [1, 2, null, 3, null, 4]  ->  3

      1
     /
    2
   /
  3
 /
4
```

The whole chain is the diameter, bending at the top with an empty right arm. This is also the brute force's `O(n^2)` shape.

### Longest path does not pass through the root

```text
root = [1, 2, null, 3, 4, 5, null, null, 6]  ->  4
```

The tree from the problem section. The bend is at `2` (`5-3-2-4-6`); the root alone would give 3. The global `best` catches it.

### Perfect tree

```text
root = [1, 2, 3, 4, 5, 6, 7]  ->  4
```

Leaf to leaf across the root: `4-2-1-3-6`. At the root `L = R = 2`.

### Empty tree

```text
root = []  ->  0
```

LeetCode guarantees at least one node, but `height(null)` returns `0` without touching `best`, so the method still answers `0` safely.

=== takeaway ===
> When you see **"longest path between any two nodes"** in a tree, think **post-order height with a global answer**: return `1 + max(L, R)` to the parent, record `L + R` at the node.

### The core observation

Every path has one highest node where it bends, and its length there is `height(left) + height(right)`. Those two heights are exactly what you compute anyway to get `height(node)`. So one post-order pass computes every height once and checks every bend for free.

### The pattern trigger

```text
       answer is a path that can bend at any node
                         |
                         v
        f(node):  L = f(left)   R = f(right)
                         |
             +-----------+------------+
             |                        |
     record at node:           return to parent:
     best = max(best, L + R)   1 + max(L, R)
     (both arms)               (one arm only)
```

### The common mistakes

**Answering at the root only.** `height(root.left) + height(root.right)` passes the sample and fails any tree whose longest path bends lower down.

**Counting nodes instead of edges.** `L + R + 1` returns 4 on the example. Heights in nodes plus `L + R` gives edges; keep the units straight.

**Returning the diameter instead of the height.** If `f` returns `L + R`, the parent adds two arms of its child to its own arm and builds a "path" that forks - which is not a path.

**Calling a height helper inside the traversal.** Correct, and quadratic on a chain. If the helper's work is a subset of the outer walk, merge them.

### What to remember in six months

> The return value is what the parent needs. The global is what the problem asks. They are allowed to be different.
