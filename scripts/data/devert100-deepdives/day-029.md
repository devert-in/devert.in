=== intro ===
Week 4 was about arrays you could index into: prefix sums, hash maps, "have I seen this before?". Week 5 takes the index away. A linked list gives you one node and one arrow, and nothing else.

> On a linked list, the danger is never "too slow". It is **losing your grip**. The moment you overwrite the only reference to the rest of the list, that rest is gone. Save what you are about to break, then break it.

=== problem ===
Given the `head` of a singly linked list, reverse it and return the **new head**.

```text
head   = 1 -> 2 -> 3 -> 4 -> 5 -> null
answer = 5 -> 4 -> 3 -> 2 -> 1 -> null
```

LeetCode gives you this node type - you never declare it yourself:

```text
ListNode { int val; ListNode next; }
```

### What "reverse" actually means here

Every arrow flips direction. Nothing else changes - the node holding `3` is still the same object in memory, it just points somewhere new.

```text
before:  1 -> 2 -> 3 -> 4 -> 5 -> null
after:   null <- 1 <- 2 <- 3 <- 4 <- 5
```

Read the "after" line from the right and you get the answer `5 -> 4 -> 3 -> 2 -> 1 -> null`. Two consequences fall out of that picture:

1. The old head (`1`) becomes the new **tail**, so its `next` must become `null`. Forget that and you have a cycle.
2. The old tail (`5`) becomes the new **head**, and it is what you return. Returning the original `head` hands back a one-node list.

### Why this is not trivial

With an array you would swap `a[i]` and `a[n-1-i]`. A singly linked list cannot do that: you cannot jump to the last node, and you cannot walk backwards. Each node knows only what comes **after** it. You have to reverse the arrows while walking forwards, using the very arrows you are reversing.

### Constraints that matter

- `0` to `5000` nodes. **Zero** is allowed - `head` can be `null`.
- Values are irrelevant to the algorithm. Only links move.

=== pattern ===
**Linked list pointer manipulation - the three-pointer reversal (`prev`, `curr`, `next`).**

On an array the unit of work is "read a value, write a value". On a linked list it is "**re-point one arrow**". Almost every linked list problem is a sequence of arrow changes, and the whole difficulty is ordering them so that you never cut off part of the list you still need.

Reversal is the cleanest example. At any moment the list is split in two:

```text
  reversed part              not yet touched
null <- 1 <- 2      3 -> 4 -> 5 -> null
             ^      ^
           prev    curr
```

- `prev` is the head of the part that is already reversed.
- `curr` is the head of the part that is not.

One step moves `curr` from the right part to the left part by flipping its single arrow. Repeat until the right part is empty, and `prev` is the head of the whole reversed list.

The catch: flipping `curr.next` to point at `prev` destroys `curr`'s only link to `4`. So before flipping, you save it in a third pointer - `next`.

### Recognising it

Reach for prev/curr/next whenever:

- a list (or part of one) must be reversed - whole list, between positions, in groups of `k`
- a problem needs to read a list "backwards" with `O(1)` space (palindrome list, reorder list, add two numbers stored forwards)
- you catch yourself wanting to copy a list into an array just to walk it in reverse

The mental question:

> Which reference am I about to overwrite, and is it the only path to something I still need?

If yes, save it first.

=== bruteForce ===
Forget about re-pointing arrows. What would you do if linked lists felt unfamiliar?

Copy the values into an array, where reversal is easy. Then walk the list a second time and write the values back, last one first.

### Step logic

1. Walk the list; append each `val` to `values`.
2. Walk the list again with an index `i` starting at `values.size() - 1`; set `node.val = values.get(i)`, then `i--`.
3. Return `head` - same nodes, same arrows, values reversed.

### Dry run

```text
head = 1 -> 2 -> 3 -> 4 -> 5 -> null
```

**Pass 1 - collect.**

| step | node.val | action | values |
| ---: | -------: | :----- | :----- |
| - | - | start | `[]` |
| 1 | 1 | append 1 | `[1]` |
| 2 | 2 | append 2 | `[1, 2]` |
| 3 | 3 | append 3 | `[1, 2, 3]` |
| 4 | 4 | append 4 | `[1, 2, 3, 4]` |
| 5 | 5 | append 5 | `[1, 2, 3, 4, 5]` |
| 6 | - | node is `null`, stop | `[1, 2, 3, 4, 5]` |

**Pass 2 - write back in reverse.** `i` starts at `4`.

| step | node (old val) | i | values.get(i) | list after write |
| ---: | -------------: | -: | ------------: | :--------------- |
| 1 | 1 | 4 | 5 | `5 -> 2 -> 3 -> 4 -> 5` |
| 2 | 2 | 3 | 4 | `5 -> 4 -> 3 -> 4 -> 5` |
| 3 | 3 | 2 | 3 | `5 -> 4 -> 3 -> 4 -> 5` |
| 4 | 4 | 1 | 2 | `5 -> 4 -> 3 -> 2 -> 5` |
| 5 | 5 | 0 | 1 | `5 -> 4 -> 3 -> 2 -> 1` |

Return `head`, which now reads `5 -> 4 -> 3 -> 2 -> 1 -> null`. Correct.

Notice the middle row: step 3 writes `3` over `3`. In an odd-length list the centre value is copied onto itself - harmless, just wasted.

### Java

```java
class Solution {
    public ListNode reverseList(ListNode head) {

        // Pass 1: copy every value out, in order.
        List<Integer> values = new ArrayList<>();
        for (ListNode node = head; node != null; node = node.next) {
            values.add(node.val);
        }

        // Pass 2: walk again, writing the values back last-first.
        int i = values.size() - 1;
        for (ListNode node = head; node != null; node = node.next) {
            node.val = values.get(i);
            i--;
        }

        return head;
    }
}
```

### Complexity

**Time:** `O(n)` - **Space:** `O(n)`

### Where it hurts

The time is already optimal: you cannot reverse a list without visiting every node. The waste is elsewhere.

**It stores the whole list a second time.** `values` holds `n` boxed `Integer`s just so we can read them backwards. That is `O(n)` extra memory for information the list already has.

**It does not actually reverse the list.** It reverses the *values*. The arrows never move. On LeetCode that passes, but in real code a node usually carries more than an `int` - a record, a payload, references held elsewhere. Anyone holding a reference to "the node with 1 in it" now finds `5` there. Interviewers ask for this problem precisely to see you move links, and "I swapped the values" is the answer they push back on.

Look at what pass 1 is really for. We copy into an array because we cannot walk backwards. But a walk backwards is exactly what reversing the arrows *gives* us. If we flip each arrow as we pass it, the list itself becomes the "backwards" structure, and the array has nothing left to do.

> Can I flip each arrow the moment I reach it, without losing my way to the next node?

=== optimization ===
The array existed to remember "where I came from". One variable can remember that instead.

### The key observation

When you stand on `curr`, the only arrow that needs to change is `curr.next`. It should point at the node you just came from - call it `prev`. Every node needs exactly one such change, and each change only needs two things: `curr` and `prev`.

The one problem: `curr.next` is also your only way forward. Overwrite it and `3 -> 4 -> 5` is unreachable. So each step is four moves, in this exact order:

```text
next      = curr.next;   // 1. save the way forward
curr.next = prev;        // 2. flip the arrow
prev      = curr;        // 3. the reversed part now starts at curr
curr      = next;        // 4. step forward using the saved link
```

Start with `prev = null` (the new tail must point at `null`) and `curr = head`. Stop when `curr` is `null`; `prev` is then the new head.

### Dry run

```text
head = 1 -> 2 -> 3 -> 4 -> 5 -> null
```

Every variable after each step. `next` is the value saved in move 1.

| step | curr (start) | next saved | flip | prev (end) | curr (end) | reversed part | untouched part |
| ---: | -----------: | ---------: | :--- | ---------: | ---------: | :------------ | :------------- |
| - | 1 | - | - | null | 1 | `null` | `1 -> 2 -> 3 -> 4 -> 5` |
| 1 | 1 | 2 | `1.next = null` | 1 | 2 | `1 -> null` | `2 -> 3 -> 4 -> 5` |
| 2 | 2 | 3 | `2.next = 1` | 2 | 3 | `2 -> 1 -> null` | `3 -> 4 -> 5` |
| 3 | 3 | 4 | `3.next = 2` | 3 | 4 | `3 -> 2 -> 1 -> null` | `4 -> 5` |
| 4 | 4 | 5 | `4.next = 3` | 4 | 5 | `4 -> 3 -> 2 -> 1 -> null` | `5` |
| 5 | 5 | null | `5.next = 4` | 5 | null | `5 -> 4 -> 3 -> 2 -> 1 -> null` | (empty) |

`curr` is `null`, so the loop stops. Return `prev`, which is node `5`.

```text
5 -> 4 -> 3 -> 2 -> 1 -> null
```

Five steps, five flips, two pointers plus one saved link. No array.

### Read the table by columns

- **`prev (end)` always equals `curr (start)`.** That is move 3. The node we just flipped becomes the head of the reversed part.
- **`curr (end)` always equals `next saved`.** That is move 4. We never use `curr.next` to advance - by then it points backwards.
- **Step 1 writes `1.next = null`.** That is why `prev` starts as `null`. It is the line that turns the old head into a proper tail.

### What goes wrong if you skip the save

```text
curr.next = prev;     // 1.next = null
curr = curr.next;     // curr = null  ->  loop ends after one step
```

You return a one-node list `1 -> null`, and `2 -> 3 -> 4 -> 5` is garbage-collected. This is the bug the whole pattern is designed around.

### The recursive view

There is a second way to see the same flip. Reverse everything *after* `head` first, then fix one arrow:

```text
head = 1,  rest reversed:  5 -> 4 -> 3 -> 2 -> null,  and 1 still points at 2

head.next.next = head    ->   2.next = 1
head.next      = null    ->   1.next = null
```

It is elegant, but every node waits on the call stack until the recursion bottoms out, so it uses `O(n)` space. The implementation section includes it for the follow-up.

=== complexity ===
### Time

One pass. Each node is visited once and gets exactly four pointer assignments.

```text
O(n)
```

### Space

Three references - `prev`, `curr`, `next` - no matter how long the list is.

```text
O(1)
```

The recursive version is also `O(n)` time, but each of the `n` calls holds a stack frame until the deepest one returns:

```text
O(n) call stack
```

### Comparison

| Approach | Time | Extra space | Moves links? |
| :------- | ---: | ----------: | :----------- |
| Copy values to array, write back | `O(n)` | `O(n)` | no - values only |
| Recursive | `O(n)` | `O(n)` stack | yes |
| Iterative prev/curr/next | **`O(n)`** | **`O(1)`** | yes |

With `5000` nodes the recursive version is safe in Java, but it is the habit that matters: on a list of a million nodes, recursion depth equals list length and a `StackOverflowError` is a real risk. The iterative version has no such ceiling.

=== implementation ===
```java
class Solution {
    public ListNode reverseList(ListNode head) {

        ListNode prev = null;   // head of the reversed part (starts empty)
        ListNode curr = head;   // head of the part still to reverse

        while (curr != null) {
            ListNode next = curr.next;  // 1. save the way forward
            curr.next = prev;           // 2. flip this node's arrow
            prev = curr;                // 3. reversed part grows by one
            curr = next;                // 4. advance via the saved link
        }

        return prev;   // curr is null; prev is the old tail = new head
    }
}
```

### The lines that matter

**1.**

```java
ListNode next = curr.next;  // 1. save the way forward
curr.next = prev;           // 2. flip this node's arrow
```

The order is the correctness condition. Swap these two lines and `next` is read *after* the flip, so it holds `prev` - the loop walks backwards into the reversed part and stops after one node.

**2.**

```java
ListNode prev = null;   // head of the reversed part (starts empty)
```

`null`, because the first node we flip is the old head, and the old head becomes the new tail. Its `next` must be `null`. Starting `prev` anywhere else either loses that terminator or creates a cycle.

**3.**

```java
return prev;   // curr is null; prev is the old tail = new head
```

Not `head`. After the loop, `head` still refers to node `1`, which is now the *last* node. Returning it gives `1 -> null`.

### The recursive version, for the follow-up

```java
class Solution {
    public ListNode reverseList(ListNode head) {

        // Empty list or last node: already reversed.
        if (head == null || head.next == null) {
            return head;
        }

        ListNode newHead = reverseList(head.next);  // reverse the rest

        head.next.next = head;   // the node after head now points back to it
        head.next = null;        // head becomes the tail of what is built so far

        return newHead;          // the old tail, passed all the way up
    }
}
```

`head.next.next = head` is the line people stare at. Read it as: "the node that used to come after me should now point at me". `newHead` never changes on the way up - it is node `5` at every level.

### Java notes

- `ListNode next` is declared inside the loop. It is a fresh local each iteration, which makes it obvious it only lives for one step. Declaring it outside works too.
- `next` is not a reserved word in Java, so it is a legal and readable variable name. Some people write `nxt` or `temp`; the name should say *why* it exists.
- Java passes object references by value. Reassigning `head` inside the method would not affect the caller, which is why the method *returns* the new head rather than mutating a parameter.

=== edgeCases ===
### Empty list

```text
null  ->  null
```

`curr` starts as `null`, the loop never runs, and `prev` (still `null`) is returned. No special case needed.

### Single node

```text
7 -> null  ->  7 -> null
```

One iteration: `next = null`, `7.next = null` (already was), `prev = 7`, `curr = null`. Return `7`.

### Two nodes

```text
1 -> 2 -> null  ->  2 -> 1 -> null
```

The smallest case where an arrow actually changes direction. Step 1 sets `1.next = null`, step 2 sets `2.next = 1`. If the output here is `2 -> 1 -> 2 -> 1 ...`, you forgot that `prev` starts as `null`.

### Duplicate values

```text
1 -> 1 -> 2 -> null  ->  2 -> 1 -> 1 -> null
```

The algorithm never looks at `val`, so duplicates cannot confuse it. This is the case that would trip up any approach that tries to find nodes by value.

### Negative and zero values

```text
-1 -> 0 -> 3 -> null  ->  3 -> 0 -> -1 -> null
```

### Already "reversed-looking" input

```text
5 -> 4 -> 3 -> 2 -> 1 -> null  ->  1 -> 2 -> 3 -> 4 -> 5 -> null
```

Reversal does not sort. It flips whatever order is there.

### Reversing twice

```text
reverse(reverse(1 -> 2 -> 3))  ->  1 -> 2 -> 3 -> null
```

A useful self-test: applying the function twice must return the original order, with the original node objects.

### The maximum length

`5000` nodes runs in one loop of `5000` iterations with the iterative version. The recursive version uses `5000` stack frames - fine at this size, but it is the version that does not scale.

=== takeaway ===
> When you see **"reverse"** on a linked list - all of it, part of it, or as a step inside a bigger problem - think **`prev`, `curr`, `next`**: save, flip, advance, advance.

### The core observation

Reversing a list is `n` independent arrow flips, and each flip needs only the current node and the one before it. The single trap is that the flip overwrites your only path forward, so the path forward must be saved first. Once it is, the list itself remembers the way back, and no array is needed.

### The pattern trigger

```text
        need the list (or a piece of it) backwards
                         |
                         v
           prev = null, curr = head
                         |
                         v
     +---- while curr != null ---------------+
     |   next      = curr.next    (save)     |
     |   curr.next = prev         (flip)     |
     |   prev      = curr         (grow)     |
     |   curr      = next         (advance)  |
     +---------------------------------------+
                         |
                         v
               return prev  (new head)
```

### The common mistakes

**Flipping before saving.** `curr.next = prev` first loses the rest of the list. The output is a single node and no error is thrown - it just looks like a short list.

**Returning `head`.** After the loop `head` is the tail. Return `prev`.

**Initialising `prev` to `head`.** The old head then points at itself, and any traversal of the result loops forever.

**Swapping values instead of links.** It passes LeetCode and fails the interview. The question is about pointers.

### What to remember in six months

> Before you overwrite a `next`, ask: is this the only way to reach the rest of the list? If yes, save it first.

That sentence covers far more than this problem. Reverse Linked List II (LC 92) is the same loop run over a window with the two ends reconnected. Reverse Nodes in k-Group (LC 25) is that window, repeated. Palindrome Linked List (Day 35) and Reorder List (LC 143) reverse the second half and then compare or weave. All of them are these four lines with different start and stop conditions.

Space: `O(1)`
