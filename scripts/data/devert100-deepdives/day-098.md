=== intro ===
Ninety-seven days of algorithms. Today is the first capstone, and it is a different kind of problem: there is no input array to process. You are designing a **data structure**, and the requirement is a complexity budget for every operation.

> When a design problem demands `O(1)` for several operations at once, no single structure will do it. Ask what each operation needs, pick the structure that gives each one, and link them together so they share the same nodes.

=== problem ===
Design a class `LRUCache` with:

- `LRUCache(int capacity)` - a cache that holds at most `capacity` key-value pairs.
- `int get(int key)` - return the value if `key` is present, otherwise `-1`.
- `void put(int key, int value)` - insert or update the pair. If inserting would exceed `capacity`, first **evict the least recently used** key.

Both `get` and `put` must run in **`O(1)`** average time.

### What "used" means

A key is *used* whenever it is read by `get` **or** written by `put`. The least recently used key is the one whose last touch is oldest. A `get` that misses touches nothing.

### LeetCode's example, with capacity 2

| # | call | returns | why |
| -: | :--- | ------: | :-- |
| 1 | `put(1, 1)` | - | cache: `{1}` |
| 2 | `put(2, 2)` | - | cache: `{1, 2}`, now full |
| 3 | `get(1)` | 1 | hit - and `1` is now the most recent |
| 4 | `put(3, 3)` | - | full, evict LRU = `2` (key `1` was just touched) |
| 5 | `get(2)` | -1 | `2` was evicted |
| 6 | `put(4, 4)` | - | full, evict LRU = `1` |
| 7 | `get(1)` | -1 | `1` was evicted |
| 8 | `get(3)` | 3 | hit |
| 9 | `get(4)` | 4 | hit |

Call 4 is the one that matters. Without call 3, key `1` would be oldest and would be evicted. Reading a key **changes who gets evicted next** - so `get` is not a read-only operation.

### The constraints that matter

- `1 <= capacity <= 3000`
- `0 <= key <= 10^4`, `0 <= value <= 10^5`
- Up to `2 * 10^5` calls to `get` and `put`.

`2 * 10^5` calls against a 3,000-entry cache is `6 * 10^8` steps if every call scans the cache. That is what the `O(1)` requirement is protecting against.

=== pattern ===
**HashMap + Doubly Linked List.**

### Why one structure is not enough

Break the work into the four things the cache must do, and see which structure does each in `O(1)`:

| need | HashMap | Array / ArrayList | Doubly linked list |
| :--- | :------ | :---------------- | :----------------- |
| find a key | **yes** | no, scan | no, scan |
| know recency order | no | yes | **yes** |
| move a found entry to "most recent" | - | no, shifting | **yes, if you hold the node** |
| remove the oldest | - | no, shifting | **yes, at the tail** |

The HashMap is good at exactly the one thing the list is bad at, and vice versa. The list can unlink any node in `O(1)` - but only if someone hands it the node. The map can hand it the node in `O(1)`.

So the map does not store the value directly. It stores a **pointer into the list**:

```text
   HashMap                    Doubly linked list (most recent -> least recent)
  +-----+                     
  |  3  | -------------+      head <-> [3:3] <-> [4:4] <-> tail
  |  4  | ----------+  |                 ^         ^
  +-----+           |  +-----------------+         |
                    +------------------------------+
```

Lookup goes through the map, ordering lives in the list, and both refer to the same node objects.

### Recognising it

Reach for "map + linked list" when a design problem asks for:

- `O(1)` lookup by key **and**
- `O(1)` maintenance of some **order** (recency, insertion, frequency bucket) **and**
- removal from the middle or from one end

LRU Cache, LFU Cache (LC 460, a map of lists), All O'one Data Structure (LC 432), and "design a browser history / playlist" variants all use this shape.

The mental question:

> Which operation needs lookup, and which needs order? Can a map point *into* an ordered structure so neither has to search?

=== bruteForce ===
Without the `O(1)` requirement, the obvious design is a single list of `[key, value]` pairs kept in recency order: **oldest at index 0, newest at the end**.

1. `get(key)`: scan for the key. If found, pull it out and re-append it at the end (it is now the most recent). Return its value, or `-1`.
2. `put(key, value)`: scan for the key. If found, pull it out. If the list is still full, remove index 0 (the oldest). Append `[key, value]` at the end.

| 5 | `get(2)` | `[1:1, 3:3]` | 2 checks, miss | nothing | `[1:1, 3:3]` | -1 |

Returns: `1, -1, -1, 3, 4`. Matches LeetCode. The design is correct - the position in the list *is* the recency.

### Java

```java
class LRUCache {

    private final int capacity;
    // Oldest entry at index 0, most recently used at the end.
    private final List<int[]> entries = new ArrayList<>();

    public LRUCache(int capacity) {
        this.capacity = capacity;
    }

    public int get(int key) {
        for (int i = 0; i < entries.size(); i++) {
            if (entries.get(i)[0] == key) {
                int[] entry = entries.remove(i);   // shifts everything after i
                entries.add(entry);                // now the most recent
                return entry[1];
            }
        }
        return -1;
    }

    public void put(int key, int value) {
        for (int i = 0; i < entries.size(); i++) {
            if (entries.get(i)[0] == key) {
                entries.remove(i);
                break;
            }
        }
        if (entries.size() == capacity) {
            entries.remove(0);                     // evict the oldest
        }
        entries.add(new int[] { key, value });
    }
}
```

### Complexity

**Time:** `O(capacity)` per call - **Space:** `O(capacity)`

### Where it hurts

Every row of that table pays twice:

1. **The scan.** "Is this key here, and where?" costs up to `capacity` comparisons. Rows 4-7 scanned the whole list.
2. **The shift.** `ArrayList.remove(i)` moves every later element one slot left. Removing index 0 - which eviction *always* does - moves all of them.

Neither cost is about the recency logic, which is correct. They are about the **storage**. The two questions being asked are:

```text
"where is key k?"                 -> needs a lookup structure
"unlink this entry, re-add it"    -> needs a structure with O(1) removal
```

An array answers neither in `O(1)`. With 3,000 entries and 200,000 calls the scans alone approach `6 * 10^8` comparisons. Fix the storage and the same logic becomes `O(1)`.

=== optimization ===
Take the two costs one at a time.

### Kill the scan - a HashMap

`map.get(key)` answers "is it here, and where" in `O(1)` average. But a map on its own forgets order, so it cannot tell you which key is oldest.

### Kill the shift - a doubly linked list

Linked list nodes are not stored contiguously, so removing one never moves the others. To unlink node `x` you rewire two pointers:

```text
before:   A <-> x <-> B
after:    A <-------> B          x.prev.next = x.next;  x.next.prev = x.prev;
```

That needs `x.prev`, so the list has to be **doubly** linked. A singly linked list would need a scan to find the node before `x`.

### Join them - the map stores nodes

Map key -> node. Now `get` finds the node in `O(1)` via the map and moves it in `O(1)` via its pointers. No step searches anything.

### Two sentinels remove every special case

Keep a dummy `head` and a dummy `tail` that are never removed:

```text
head <-> [most recent] <-> ... <-> [least recent] <-> tail
```

- most recent is always `head.next`
- least recent is always `tail.prev`
- a real node always has a non-null `prev` and `next`, so unlinking never checks for `null` - even when the list holds one node.

### And one detail: the node stores its key

On eviction you find the victim as `tail.prev` - via the list, not the map. To also remove it from the map you need its key. So each node carries `key` as well as `value`.

### Dry run - same example

```text

list shown head -> tail, i.e. most recent -> least recent
```

| # | call | map lookup | action | list after | map keys | returns |
| -: | :--- | :--------- | :----- | :--------- | :------- | ------: |

| 2 | `put(2,2)` | miss | size 1 < 2; new node, `addFirst` | `[2:2, 1:1]` | `{1, 2}` | - |
| 3 | `get(1)` | hit | `remove(1)`, `addFirst(1)` | `[1:1, 2:2]` | `{1, 2}` | 1 |
| 4 | `put(3,3)` | miss | full: `lru = tail.prev = 2`, unlink, `map.remove(2)`; add `3` | `[3:3, 1:1]` | `{1, 3}` | - |
| 5 | `get(2)` | miss | nothing | `[3:3, 1:1]` | `{1, 3}` | -1 |
| 6 | `put(4,4)` | miss | full: `lru = tail.prev = 1`, unlink, `map.remove(1)`; add `4` | `[4:4, 3:3]` | `{3, 4}` | - |
| 7 | `get(1)` | miss | nothing | `[4:4, 3:3]` | `{3, 4}` | -1 |

Same returns as the brute force: `1, -1, -1, 3, 4`. Every row is a fixed number of pointer writes and one or two hash operations - no row's cost depends on how full the cache is.

### Pointer-level view of row 3

`get(1)` with list `head <-> 2 <-> 1 <-> tail`:

| step | code | list |
| :--- | :--- | :--- |
| start | - | `head <-> 2 <-> 1 <-> tail` |
| unlink | `node.prev.next = node.next` (2.next = tail) | `head <-> 2 <-> tail`, `1` detached |
| | `node.next.prev = node.prev` (tail.prev = 2) | |
| relink | `node.next = head.next` (1.next = 2) | |
| | `node.prev = head` (1.prev = head) | |
| | `head.next.prev = node` (2.prev = 1) | |
| | `head.next = node` (head.next = 1) | `head <-> 1 <-> 2 <-> tail` |

Six pointer writes. The same six whether the cache holds 2 entries or 3,000.

=== complexity ===
### Time

`get` and `put` each do at most one `map.get`, one `map.put` or `map.remove`, one `remove` and one `addFirst`. All constant.

```text
O(1) average per call
```

"Average" because `HashMap` is `O(1)` on average; the list operations are worst-case `O(1)`.

### Space

At most `capacity` nodes in the list and `capacity` entries in the map, plus two sentinels.

```text
O(capacity)
```

### Comparison

| Approach | `get` | `put` | Space |
| :------- | ----: | ----: | ----: |
| ArrayList of pairs | `O(capacity)` | `O(capacity)` | `O(capacity)` |
| HashMap only | `O(1)` | `O(capacity)` to find the LRU | `O(capacity)` |
| HashMap + timestamps + scan for min | `O(1)` | `O(capacity)` | `O(capacity)` |
| `java.util.LinkedList` + HashMap of values | `O(capacity)` to find the node | `O(capacity)` | `O(capacity)` |
| **HashMap of nodes + own doubly linked list** | **`O(1)`** | **`O(1)`** | `O(capacity)` |

The `java.util.LinkedList` row is the trap: it *is* a doubly linked list, but it does not expose its nodes, so `list.remove(object)` scans. You have to own the nodes to get `O(1)`.

=== implementation ===
```java
class LRUCache {

    private static class DNode {
        int key, value;
        DNode prev, next;

        DNode(int key, int value) {
            this.key = key;
            this.value = value;
        }
    }

    private final int capacity;
    private final Map<Integer, DNode> map = new HashMap<>();
    private final DNode head = new DNode(0, 0);   // sentinel: head.next = most recent
    private final DNode tail = new DNode(0, 0);   // sentinel: tail.prev = least recent

    public LRUCache(int capacity) {
        this.capacity = capacity;
        head.next = tail;
        tail.prev = head;
    }

    public int get(int key) {
        DNode node = map.get(key);
        if (node == null) return -1;
        remove(node);
        addFirst(node);              // touched -> most recent
        return node.value;
    }

    public void put(int key, int value) {
        DNode node = map.get(key);
        if (node != null) {          // update: new value, and it counts as a use
            node.value = value;
            remove(node);
            addFirst(node);
            return;
        }
        if (map.size() == capacity) {
            DNode lru = tail.prev;
            remove(lru);
            map.remove(lru.key);     // the reason each node stores its key
        }
        DNode fresh = new DNode(key, value);
        map.put(key, fresh);
        addFirst(fresh);
    }

    private void remove(DNode node) {
        node.prev.next = node.next;
        node.next.prev = node.prev;
    }

    private void addFirst(DNode node) {
        node.next = head.next;
        node.prev = head;
        head.next.prev = node;
        head.next = node;
    }
}
```

### The lines that matter

**1.**

```java
map.remove(lru.key);     // the reason each node stores its key
```

The victim is found through the list (`tail.prev`), but it has to leave the map too. Forget this line and the map keeps a stale pointer: a later `get` on that key "finds" a node that is no longer in the list, and `map.size()` never drops, so every later `put` evicts.

**2.**

```java
if (node != null) {          // update: new value, and it counts as a use
```

Updating an existing key must **not** evict anything - the key count does not grow. Check for an existing key *before* the capacity check, or a full cache will evict an innocent key just to overwrite a value.

**3.**

```java
head.next.prev = node;
head.next = node;
```

Order matters inside `addFirst`. Assign `head.next = node` first and `head.next.prev` would then point at `node` itself, losing the old first node's back pointer.

### Java notes

- `DNode` is a `private static class` nested inside `LRUCache`. `static` because it needs no reference to the outer cache; nested so it cannot collide with any other `Node` type on the classpath (LeetCode's own included).
- `Map<Integer, DNode>` autoboxes the key. For keys up to `10^4` a `DNode[10001]` array would work too and avoid hashing, but the map is the general answer and what interviewers expect.
- Sentinels use `(0, 0)` and are never put in the map, so a real key `0` causes no confusion.

### The library answer, for the follow-up

Java ships this exact structure. `LinkedHashMap` with `accessOrder = true` keeps entries in recency order, and `removeEldestEntry` is the eviction hook:

```java
class LRUCache {

    private final int capacity;
    private final LinkedHashMap<Integer, Integer> cache;

    public LRUCache(int capacity) {
        this.capacity = capacity;
        // true = order by access, not by insertion
        this.cache = new LinkedHashMap<>(16, 0.75f, true) {
            @Override
            protected boolean removeEldestEntry(Map.Entry<Integer, Integer> eldest) {
                return size() > LRUCache.this.capacity;
            }
        };
    }

    public int get(int key) {
        return cache.getOrDefault(key, -1);
    }

    public void put(int key, int value) {
        cache.put(key, value);
    }
}
```

Worth mentioning to show you know it exists - but most interviewers will then ask you to build it by hand, which is the version above. `LinkedHashMap` is internally the same hash table plus doubly linked list.

=== edgeCases ===
### Capacity 1

```text
LRUCache(1); put(1,1); put(2,2); get(1); get(2)
->  -1, 2
```

Every new key evicts the only one. With sentinels, `tail.prev` is that single node and unlinking it needs no special case.

### Updating an existing key does not evict

```text
LRUCache(2); put(1,1); put(2,2); put(1,10); get(1); get(2)
->  10, 2
```

The cache was full, but `put(1,10)` is an update, so nothing is evicted. It also makes `1` the most recent.

### An update counts as a use

```text
LRUCache(2); put(1,1); put(2,2); put(1,10); put(3,3); get(1); get(2); get(3)
->  10, -1, 3
```

After the update, `2` is the oldest, so `put(3,3)` evicts `2`, not `1`.

### A get counts as a use

```text
LRUCache(2); put(1,1); put(2,2); get(1); put(3,3); get(2)
->  1, -1
```

This is LeetCode's own trap, from call 4 of the example.

### A missed get changes nothing

```text
LRUCache(2); put(1,1); put(2,2); get(9); put(3,3); get(1)
->  -1, -1
```

`get(9)` misses and touches no node, so `1` is still oldest and gets evicted.

### get on an empty cache

```text
LRUCache(2); get(1)
->  -1
```

### Key and value 0

```text
LRUCache(2); put(0,0); get(0)
->  0
```

`0` is a valid key and a valid value. Returning `0` here is correct; only a miss returns `-1`.

### Repeated puts of the same key at full capacity

```text
LRUCache(2); put(1,1); put(2,2); put(2,5); put(2,6); get(1); get(2)
->  1, 6
```

Three writes, two distinct keys, zero evictions.

=== takeaway ===
> When a design problem wants **`O(1)` lookup** and **`O(1)` reordering or removal by recency**, think **HashMap of key -> node, plus a doubly linked list with sentinels**.

### The core observation

The map is fast at "where is it?" and blind to order; the linked list keeps order and can unlink any node in `O(1)` - but only if you already hold the node. Store the list nodes *as the map's values*, and each structure covers the other's weakness. Sentinels make every unlink and insert the same four lines, with no null checks.

### The pattern trigger

```text
       design: get/put in O(1) + evict by some order
                        |
                        v
       lookup by key?        -> HashMap<key, Node>
       order + O(1) unlink?  -> doubly linked list
                        |
                        v
       every access:   remove(node); addFirst(node)
       eviction:       lru = tail.prev; remove(lru); map.remove(lru.key)
                        |
                        v
       dummy head + dummy tail = no edge cases
```

### The common mistakes

**Forgetting `map.remove` on eviction.** The node leaves the list but stays in the map. Lookups return evicted values and the size check breaks.

**Not storing the key in the node.** Then eviction cannot find which map entry to delete without a scan.

**Treating `get` as read-only.** A hit must move the node to the front. This is exactly the mistake call 4 of the example punishes.

**Evicting before checking for an update.** `put` on an existing key in a full cache must not evict.

**Using `java.util.LinkedList`.** Its `remove(Object)` scans. Owning the nodes is the whole point.

### What to remember in six months

> LRU = HashMap pointing into a doubly linked list. Map for "where", list for "when". Sentinels at both ends, key stored in the node.

LFU Cache (LC 460) is the next step: a map from key to node, plus a map from frequency to its own doubly linked list, with a `minFreq` pointer. Same building blocks, one more layer. Real caches - CPU caches, database buffer pools, CDN edges, `LinkedHashMap` itself - all run some form of this.
