=== intro ===
Day 19's window was valid when it held no repeated character - a yes/no question a set could answer. Today the rule is a **budget**: the window may contain at most `k` characters that disagree with its majority. The window moves the same way; what changes is how you measure it.

> Before asking "how do I make this window valid?", ask "what number tells me how invalid it is?". Once you have that number, the window runs itself.

=== problem ===
Given a string `s` of uppercase English letters and an integer `k`, you may change **at most `k`** characters to any other uppercase letter. Return the length of the longest substring that can be made of **one repeated letter**.

```text
s = "AABABBA",  k = 1   ->  4
```

One way to get 4: take `"AABA"` (indices 0 to 3) and replace the `B` with `A`.

```text
index:  0 1 2 3 4 5 6
        A A B A B B A
        [     ]            "AABA"  -> change the B  -> "AAAA"   length 4
```

Another: `"BABB"` (indices 2 to 5), change the `A` to `B`. No window of length 5 works with only one change - every length-5 window needs at least two.

### Reframe: which characters do you change?

If you are going to turn a window into one repeated letter, the cheapest letter to keep is the **most frequent** one in that window. Everything else must be replaced.

```text
replacements needed  =  window length  -  count of the most frequent letter
```

So a window is achievable exactly when:

```text
length - maxFreq  <=  k
```

That one inequality is the whole problem. You never decide *which* letter to keep or *which* positions to change - the inequality already assumes the best choice.

### Constraints that matter

- `1 <= s.length <= 10^5` - an `O(n^2)` scan is 10^10 steps, too slow.
- Only uppercase letters - counts fit in an `int[26]`.
- `0 <= k <= s.length`. With `k = 0` the problem becomes "longest run of one letter". With `k` large, the answer is capped by `n`.

=== pattern ===
**Variable-size Sliding Window** with a **frequency array**.

The window `[left, right]` is the current candidate substring. Its "health" is one number:

```text
cost = (right - left + 1) - maxFreq
```

- `right` moves forward every step and adds one character.
- If `cost > k`, the window costs more than the budget, so `left` moves forward and releases a character.
- After that, the window length is a candidate answer.

### Why the window is allowed to slide

The rule is monotonic in the right direction:

- **Growing** a window can only keep `cost` the same or raise it. Adding a character raises the length by 1 and `maxFreq` by at most 1.
- **Shrinking** a window can only keep `cost` the same or lower it.

So if `[left, right]` is over budget, every window `[left, right']` with `right' > right` is also over budget. That start is finished - move `left`. Neither pointer ever needs to go back.

### Recognising it

Reach for this shape when:

- "longest substring / subarray where you may **change / flip / delete at most `k`** elements"
- the cost of a window can be expressed as **length minus something you can count**
- the elements come from a small alphabet (letters, 0/1), so the counting is cheap

The mental question:

> What does it cost to make this window valid, and can I keep that cost updated as one element enters and one leaves?

=== bruteForce ===
Without the window, try every start and extend to the right, keeping counts as you go so each extension is cheap.

1. For each start `i`, reset `count[26]` and `maxFreq`.
2. For `j = i, i+1, ...`: add `s[j]` to the counts, update `maxFreq`.
3. If `(j - i + 1) - maxFreq <= k`, record the length. Otherwise **break** - by the monotonic argument above, no longer window from this `i` can come back under budget.

### Java

```java
class Solution {
    public int characterReplacement(String s, int k) {

        int n = s.length();
        int best = 0;

        for (int i = 0; i < n; i++) {

            int[] count = new int[26];
            int maxFreq = 0;

            for (int j = i; j < n; j++) {
                int c = s.charAt(j) - 'A';
                count[c]++;
                maxFreq = Math.max(maxFreq, count[c]);

                if ((j - i + 1) - maxFreq > k) {
                    break;              // over budget: no longer window from i can recover
                }
                best = Math.max(best, j - i + 1);
            }
        }

        return best;
    }
}
```

### Complexity

**Time:** `O(n^2)` in the worst case (e.g. `k = n`, nothing ever breaks) - **Space:** `O(26)` for the counts.

### Where it hurts

Compare rows `i = 0` and `i = 1`:

```text
i = 0:   A A B A | B      broke at j = 4
i = 1:     A B A | B      broke at j = 4 again
```

`i = 0` already counted `A, B, A` at indices 1 to 3. `i = 1` resets the counts and counts them again - and then breaks at the same `j`. The same happens for `i = 2` and `i = 3` at `j = 6`.

When start `i` breaks at `j`, the counts for `[i + 1, j]` are just the counts for `[i, j]` with `s[i]` removed. One decrement, not a recount. And there is no reason to move `j` back: windows `[i + 1, j']` with `j' < j` are **shorter** than windows we already accepted, so they cannot improve `best`.

> Don't reset the counts when the start moves. Subtract the one character that left.

=== optimization ===
### The key observation

When the window `[left, right]` goes over budget, slide the left edge forward by removing `s[left]` from the counts. Keep `right` where it is and keep going. The counts are maintained incrementally - one `++` when a character enters, one `--` when one leaves.

### Version 1 - exact `maxFreq`

The only awkward part: when a character leaves, `maxFreq` might drop, and an `int[26]` does not tell you the new maximum for free. The honest fix is to rescan the 26 counts after each removal - still `O(26)` per step, so `O(26n)` overall.

### Version 2 - never decrease `maxFreq`

Now the observation that makes this problem famous. Look at what `best` is: the longest valid window **ever seen**. For a new window to beat it, its length must be at least `best + 1`, which needs:

```text
(best + 1) - maxFreq <= k     ->     maxFreq >= best + 1 - k
```

The window that set `best` already had `maxFreq >= best - k`. So to improve on it, a window needs a **higher** `maxFreq` than anything seen so far. A `maxFreq` that dropped below the old peak can never produce a new record.

So we can let `maxFreq` go stale: never decrement it, never rescan. Two consequences:

- The window **never shrinks** - each step it either grows by one, or (when over budget) slides by one, removing exactly one character. One removal always restores `length - maxFreq <= k`, because `maxFreq` did not drop. So the `while` runs at most once.
- The window's length is always equal to `best`. It may at times be a window that is **not actually valid** - but it only ever **grows** when `maxFreq` reaches a new high, and a letter that has appeared `maxFreq` times in some real window can always be stretched to `maxFreq + k` by repainting neighbours. So no length it reports is fake.

If the problem asked you to **return the substring**, this version would be unsafe at the end - use version 1. For the **length**, version 2 is exact.

=== complexity ===
### Time

`right` moves `n` times. `left` moves at most `n` times in total. Each move is `O(1)` in version 2; version 1 adds a 26-slot rescan per removal.

```text
version 2:  O(n)
version 1:  O(26 * n) = O(n)
```

### Space

One `int[26]` and a handful of integers, independent of `n`.

```text
O(26) = O(1)
```

### Comparison

| Approach | Time | Space | Window can be invalid? |
| :------- | ---: | ----: | :--------------------- |
| Every substring, count from scratch | `O(n^3)` | `O(26)` | - |
| Every start, incremental counts, break | `O(n^2)` | `O(26)` | - |
| Window, exact `maxFreq` (rescan) | `O(26n)` | `O(26)` | no |
| Window, stale `maxFreq` | **`O(n)`** | **`O(26)`** | yes, harmlessly |

In an interview, present version 1 first - it is obviously correct. Then point out that `best` can only improve if `maxFreq` improves, and drop the rescan.

=== implementation ===
```java
class Solution {
    public int characterReplacement(String s, int k) {

        int[] count = new int[26];
        int left = 0;
        int maxFreq = 0;    // highest count of one letter seen in any window so far
        int best = 0;

        for (int right = 0; right < s.length(); right++) {

            // Grow: s[right] enters the window.
            int c = s.charAt(right) - 'A';
            count[c]++;
            maxFreq = Math.max(maxFreq, count[c]);

            // Over budget: replacements needed exceed k. Slide left by one.
            // maxFreq is never decreased, so this runs at most once per step.
            while ((right - left + 1) - maxFreq > k) {
                count[s.charAt(left) - 'A']--;
                left++;
            }

            best = Math.max(best, right - left + 1);
        }

        return best;
    }
}
```

### The lines that matter

**1.**

```java
maxFreq = Math.max(maxFreq, count[c]);
```

Only the letter that just entered can have increased, so it is the only one compared. And there is no matching line on removal - `maxFreq` only ever goes up.

**2.**

```java
while ((right - left + 1) - maxFreq > k) {
```

Window length minus the count of the letter you keep is the number of letters you must change. Over `k`, the window is over budget.

**3.**

```java
count[s.charAt(left) - 'A']--;
```

The character leaving is subtracted, not recounted. This is what turns the brute force's reset into one decrement.

### Version 1, the exact window

If you need the window itself to be valid at every step (for instance to return the substring), rescan `maxFreq` after each removal:

```java
class Solution {
    public int characterReplacement(String s, int k) {

        int[] count = new int[26];
        int left = 0, maxFreq = 0, best = 0;

        for (int right = 0; right < s.length(); right++) {
            int c = s.charAt(right) - 'A';
            count[c]++;
            maxFreq = Math.max(maxFreq, count[c]);

            while ((right - left + 1) - maxFreq > k) {
                count[s.charAt(left) - 'A']--;
                left++;
                maxFreq = 0;                       // exact: rescan 26 counts
                for (int f : count) maxFreq = Math.max(maxFreq, f);
            }

            best = Math.max(best, right - left + 1);
        }

        return best;
    }
}
```

### Java notes

- `s.charAt(i) - 'A'` turns `'A'..'Z'` into `0..25`. The subtraction promotes `char` to `int`, so the result can index an array directly.
- `int[26]` beats a `HashMap<Character, Integer>` here: no boxing, no hashing, and the "rescan" in version 1 is a fixed 26-step loop.
- Writing `if` instead of `while` in version 2 is also correct, because with a never-decreasing `maxFreq` one removal always suffices. `while` keeps it in the shape of the general template.

=== edgeCases ===
### LeetCode's first example

```text
s = "ABAB",  k = 2  ->  4
```

Change both `A`s (or both `B`s). The whole string.

### No changes allowed

```text
s = "AABBBA",  k = 0  ->  3
```

With `k = 0`, the cost must be `0`, so the window must already be one letter. This is the longest run: `"BBB"`.

### All one letter

```text
s = "AAAA",  k = 0  ->  4
```

Cost is always `0`. `left` never moves.

### All different, no budget

```text
s = "ABCD",  k = 0  ->  1
```

Every window of length 2 costs 1. The best you can do is a single letter.

### Budget as large as the string

```text
s = "ABC",  k = 3  ->  3
```

The largest `k` the constraints allow. The answer is capped by `n` - you cannot create characters, only change them. The window simply never goes over budget.

### Single character

```text
s = "A",  k = 0  ->  1
```

### The best window needs changes at both ends

```text
s = "BAAAB",  k = 2  ->  5
```

Change both `B`s. `maxFreq = 3`, length 5, cost 2.

### The stale-window moment

```text
s = "AABABBA",  k = 1  ->  4
```

In version 2 the final window is `"ABBA"`, which actually needs two changes. The reported **length** is still right, because the window length tracks `best`, not the current window's validity.

=== takeaway ===
> When you see **"longest substring where you may change at most `k` characters"**, think **variable window with cost = length - maxFreq**, and keep the window while `cost <= k`.

### The core observation

The cheapest way to make a window one letter is to keep its most frequent letter and change the rest, so the cost of any window is `length - maxFreq`. That turns a search over replacement choices into one inequality. And because the answer can only improve when `maxFreq` reaches a new high, `maxFreq` never needs to be decreased.

### The pattern trigger

```text
     "longest window where at most k elements may be changed / flipped"
                              |
                              v
        cost(window) = length - (count of what you keep)
                              |
                              v
     for right in 0..n-1:
         count[s[right]]++,  maxFreq = max(maxFreq, count[s[right]])
         while length - maxFreq > k:  count[s[left]]--, left++
         best = max(best, length)
                              |
                              v
     binary alphabet (0/1)?  "count of what you keep" = count of 1s
```

### The common mistakes

**Trying to decide which letter to keep.** Looping over all 26 target letters works (`O(26n)`), but it misses that `maxFreq` already makes the best choice.

**Recounting the window after every move.** That brings back the brute force's `O(n^2)`. Adjust counts by one on each edge move.

**"Fixing" the stale `maxFreq` and assuming the result changes.** It does not - version 1 and version 2 return the same length. Rescanning is only needed if you want the window itself.

**Forgetting `k = 0`.** The formula still works - it becomes "longest run of one letter" - but it is the case most worth checking by hand.

### What to remember in six months

> Variable window problems differ only in their **validity number**. Day 19's was "is there a duplicate?". Today's is `length - maxFreq <= k`. Find the number, and the loop is the same.

The same shape solves Max Consecutive Ones III (LC 1004), where the cost of a window is its count of zeros, and Longest Subarray of 1s After Deleting One Element (LC 1493), which is LC 1004 with `k = 1`.
