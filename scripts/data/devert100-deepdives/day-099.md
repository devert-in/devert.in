=== intro ===
Yesterday was about building a structure that answers fast. Today flips it: the output itself is exponential, so no trick will make it small. The skill is generating every answer **exactly once**, without producing duplicates and throwing them away.

> When a problem says "return all", the question is not "how do I make it fast" but "how do I make sure I never build the same thing twice". Fix an order, and only ever move forward in it.

=== problem ===
Given an array `nums` of **distinct** integers, return **all possible subsets** (the power set). The result must not contain duplicate subsets, and may be returned in any order.

```text
nums   = [1, 2, 3]
answer = [[], [1], [2], [1,2], [3], [1,3], [2,3], [1,2,3]]
```

### Why there are exactly 8

Each element is independently either **in** or **out** of a subset. Three elements, two choices each:

```text
2 * 2 * 2 = 2^3 = 8
```

| 1 in? | 2 in? | 3 in? | subset |
| :---: | :---: | :---: | :----- |
| no | no | no | `[]` |
| yes | no | no | `[1]` |
| no | yes | no | `[2]` |
| yes | yes | no | `[1,2]` |
| no | no | yes | `[3]` |
| yes | no | yes | `[1,3]` |
| no | yes | yes | `[2,3]` |
| yes | yes | yes | `[1,2,3]` |

The empty set and the whole array are both subsets. Forgetting `[]` is a common wrong answer.

### What "no duplicates" means

A subset is a **set** - order inside it does not matter. `[1,2]` and `[2,1]` are the same subset, so only one may appear.

### The constraints that matter

- `1 <= nums.length <= 10`
- `-10 <= nums[i] <= 10`
- All elements are **distinct**.

`2^10 = 1024` subsets. The output is small enough to list, but it grows exponentially - you cannot do better than `O(2^n)` because that is how many answers there are.

=== pattern ===
**Backtracking** - build a candidate one choice at a time, record it, extend it, then undo the last choice and try the next one.

### Why it belongs here

Every subset is reached by a sequence of choices ("take 1, then take 3"). Backtracking walks the tree of those choice sequences depth-first, using **one shared `path`** that grows on the way down and shrinks on the way back up.

The catch is that a set can be reached by many choice sequences: "take 1 then 3" and "take 3 then 1" both give `{1, 3}`. The pattern's real content is a rule that leaves exactly **one** sequence per subset:

> Choose elements only in increasing index order. After choosing index `i`, the next choice must come from index `i + 1` or later.

That rule is the `start` parameter.

### The tree

```text
                         []                      start = 0
            /             |            \
         [1]             [2]           [3]       start = i + 1
        /    \            |
    [1,2]   [1,3]       [2,3]
      |
   [1,2,3]
```

8 nodes, 8 subsets. Every node is an answer - not just the leaves. That is what separates Subsets from Permutations, where only full-length paths count.

### Recognising it

Reach for backtracking when the problem says:

- "return **all**" subsets / combinations / permutations / partitions / paths
- the answer count is exponential and the constraints are tiny (`n <= 10` to `20`)
- each answer is built from a sequence of small choices

The mental question:

> What is one choice, what does undoing it look like, and what rule stops me from building the same answer twice?

For subsets the rule is `start`. For permutations it is a `used[]` array. For combination sums it is `start` plus a running total.

=== bruteForce ===
Ignore the duplicate problem at first. The most direct idea: start from an empty path, and at each step try adding **any element not already in it**. Every path you reach is some subset - so record it. Since `{1,2}` will show up as both `[1,2]` and `[2,1]`, sort each one and keep a `HashSet` to throw away repeats.

1. Sort a copy of `path`. If the set has not seen it, record it.
2. For every index `i` not yet used: mark it used, append `nums[i]`, recurse, then remove it and unmark.

### Dry run

```text
nums = [1, 2, 3]
```

### Java

```java
class Solution {
    public List<List<Integer>> subsets(int[] nums) {
        Set<List<Integer>> seen = new HashSet<>();
        List<List<Integer>> result = new ArrayList<>();
        explore(nums, new boolean[nums.length], new ArrayList<>(), seen, result);
        return result;
    }

    private void explore(int[] nums, boolean[] used, List<Integer> path,
                         Set<List<Integer>> seen, List<List<Integer>> result) {
        List<Integer> key = new ArrayList<>(path);
        Collections.sort(key);                     // [2,1] and [1,2] are one subset
        if (seen.add(key)) result.add(key);

        for (int i = 0; i < nums.length; i++) {
            if (used[i]) continue;
            used[i] = true;
            path.add(nums[i]);
            explore(nums, used, path, seen, result);
            path.remove(path.size() - 1);
            used[i] = false;
        }
    }
}
```

### Complexity

**Time:** `O(e * n! * n log n)` - **Space:** `O(2^n * n)` for the set, plus `O(n)` stack

### Where it hurts

The tree explores every **ordered** selection, but only **unordered** ones are wanted. Each `k`-element subset is visited once per ordering of its elements - `k!` times:

| subset size | subsets | orderings visited | wasted |
| -: | -: | -: | -: |
| 0 | 1 | 1 | 0 |
| 1 | 3 | 3 | 0 |
| 2 | 3 | 6 | 3 |
| 3 | 1 | 6 | 5 |
| **total** | **8** | **16** | **8** |

At `n = 10`, the maximum the problem allows:

```text
subsets wanted:       2^10   =       1,024
paths explored:  sum of 10!/(10-k)!  =  9,864,101
```

Almost ten million paths, each sorted and hashed, to produce a thousand answers. The `HashSet` is not solving the problem - it is cleaning up after a generator that does not know what it is generating.

The waste has a precise source: the loop always starts from index `0`, so after choosing `3` it happily goes back and chooses `1`. If the generator never went **backwards**, no ordering but the sorted one could ever be built, and there would be nothing to deduplicate.

=== optimization ===
### The key observation

Every subset has exactly one **increasing-index** ordering. `{1, 3}` can be written `[1,3]` or `[3,1]`, but only `[1,3]` lists its indices in increasing order.

So: generate only increasing-index paths. After choosing index `i`, the next choice comes from `i + 1` onwards. Carry that lower bound as `start`.

That one parameter replaces the `used[]` array, the sort, and the `HashSet`. A duplicate is no longer filtered out - it is never built.

### The algorithm

`backtrack(start, path)`:

1. Record a **copy** of `path` - every node is a subset.
2. For `i` from `start` to `n - 1`: append `nums[i]`, call `backtrack(i + 1, path)`, remove the last element.

### Dry run - same example

```text
nums = [1, 2, 3]
```

| # | call | path on entry | record | loop runs over | then |
| -: | :--- | :------------ | :----- | :------------- | :--- |
| 1 | `backtrack(0)` | `[]` | `[]` | i = 0, 1, 2 | i=0: add `1`, call 2 |
| 2 | `. backtrack(1)` | `[1]` | `[1]` | i = 1, 2 | i=1: add `2`, call 3 |
| 3 | `. . backtrack(2)` | `[1,2]` | `[1,2]` | i = 2 | i=2: add `3`, call 4 |
| 4 | `. . . backtrack(3)` | `[1,2,3]` | `[1,2,3]` | (empty) | return; remove `3` -> `[1,2]` |
| - | back in call 3 | `[1,2]` | - | done | return; remove `2` -> `[1]` |
| - | back in call 2 | `[1]` | - | i=2 | add `3`, call 5 |
| 5 | `. . backtrack(3)` | `[1,3]` | `[1,3]` | (empty) | return; remove `3` -> `[1]` |
| - | back in call 2 | `[1]` | - | done | return; remove `1` -> `[]` |
| - | back in call 1 | `[]` | - | i=1 | add `2`, call 6 |
| 6 | `. backtrack(2)` | `[2]` | `[2]` | i = 2 | i=2: add `3`, call 7 |
| 7 | `. . backtrack(3)` | `[2,3]` | `[2,3]` | (empty) | return; remove `3` -> `[2]` |
| - | back in call 6 | `[2]` | - | done | return; remove `2` -> `[]` |
| - | back in call 1 | `[]` | - | i=2 | add `3`, call 8 |
| 8 | `. backtrack(3)` | `[3]` | `[3]` | (empty) | return; remove `3` -> `[]` |
| - | back in call 1 | `[]` | - | done | return |

8 calls, 8 records, 0 discards. The result, in the order produced:

```text
[[], [1], [1,2], [1,2,3], [1,3], [2], [2,3], [3]]
```

Compare the brute-force rows that got discarded: `[1,3,2]`, `[2,1]`, `[3,1]`, `[3,2]` and the rest. Each needs a step from a larger index back to a smaller one - exactly what `start` forbids.

Notice `path` returns to `[]` at the very end. Every `add` was paired with a `remove`. That symmetry is what lets one list serve the whole search.

### The other way to see it - bitmasks

The "in or out" table from the problem section is a binary count. Mask `0b101` means "index 0 in, index 1 out, index 2 in" -> `[1,3]`.

| mask | binary | indices in | subset |
| ---: | :----: | :--------- | :----- |
| 0 | `000` | - | `[]` |
| 1 | `001` | 0 | `[1]` |
| 2 | `010` | 1 | `[2]` |
| 3 | `011` | 0, 1 | `[1,2]` |
| 4 | `100` | 2 | `[3]` |
| 5 | `101` | 0, 2 | `[1,3]` |
| 6 | `110` | 1, 2 | `[2,3]` |
| 7 | `111` | 0, 1, 2 | `[1,2,3]` |

Counting from `0` to `2^n - 1` visits every subset exactly once, with no recursion. It is the iterative answer, and the one to mention when an interviewer asks for "another approach". The code is in the implementation section.

=== complexity ===
### Time

`2^n` subsets are recorded, and copying each costs up to `n`.

```text
O(n * 2^n)
```

That is optimal: the output itself contains `n * 2^(n-1)` integers in total, so just writing it down takes this long.

### Space

The recursion is at most `n + 1` deep and `path` holds at most `n` elements.

```text
O(n) extra, not counting the output
```

### Comparison

| Approach | Paths built for `n = 10` | Time | Extra space |
| :------- | -----------------------: | ---: | ----------: |
| Any order + sort + `HashSet` | 9,864,101 | `O(e * n! * n log n)` | `O(n * 2^n)` set |
| Backtracking with `start` | **1,024** | **`O(n * 2^n)`** | **`O(n)`** |
| Bitmask counting | **1,024** | **`O(n * 2^n)`** | **`O(1)`** |

Backtracking and bitmasks are equally fast here. Backtracking wins once the problem adds **pruning** (Combination Sum: stop when the total is too big; Subsets II: skip equal neighbours), because a bitmask cannot skip a branch it never models as a branch.

=== implementation ===
```java
class Solution {
    public List<List<Integer>> subsets(int[] nums) {
        List<List<Integer>> result = new ArrayList<>();
        backtrack(nums, 0, new ArrayList<>(), result);
        return result;
    }

    private void backtrack(int[] nums, int start, List<Integer> path,
                           List<List<Integer>> result) {

        result.add(new ArrayList<>(path));      // every node is a subset - record a COPY

        for (int i = start; i < nums.length; i++) {
            path.add(nums[i]);                  // choose
            backtrack(nums, i + 1, path, result);   // explore: only later indices
            path.remove(path.size() - 1);       // un-choose
        }
    }
}
```

### The lines that matter

**1.**

```java
result.add(new ArrayList<>(path));      // every node is a subset - record a COPY
```

`path` is one list, mutated for the entire search. Adding `path` itself adds a **reference** to that list - and by the end it has been emptied, so every entry in `result` is the same empty list. `new ArrayList<>(path)` freezes the current contents.

**2.**

```java
backtrack(nums, i + 1, path, result);   // explore: only later indices
```

`i + 1`, not `start + 1`. The next choice must come after the element **just chosen**, not after where this loop began. With `start + 1`, choosing index 2 from `start = 0` would let the child choose index 1 next, building `[3,2]`.

**3.**

```java
path.remove(path.size() - 1);       // un-choose
```

The undo step. It restores `path` to what it was before `path.add(nums[i])`, so the next loop iteration starts clean.

### The bitmask version

```java
class Solution {
    public List<List<Integer>> subsets(int[] nums) {
        int n = nums.length;
        List<List<Integer>> result = new ArrayList<>();

        for (int mask = 0; mask < (1 << n); mask++) {
            List<Integer> subset = new ArrayList<>();
            for (int i = 0; i < n; i++) {
                if ((mask & (1 << i)) != 0) {    // bit i set -> nums[i] is in
                    subset.add(nums[i]);
                }
            }
            result.add(subset);
        }

        return result;
    }
}
```

`1 << n` is `2^n`. Fine for `n <= 30` with `int`; LeetCode caps `n` at 10.

### Java notes

- `path.remove(path.size() - 1)` calls `remove(int index)`, because the argument is an `int`. On a `List<Integer>`, `path.remove(nums[i])` would *also* call `remove(int index)` - removing by position, not by value - which is a classic Java bug. Removing the last index sidesteps it entirely.
- `new ArrayList<>(path)` is an `O(k)` copy. It is where the `n` in `O(n * 2^n)` comes from.
- Return type `List<List<Integer>>` - LeetCode accepts any order of subsets and any order of elements inside each.

=== edgeCases ===
### Single element

```text
[0]  ->  [[], [0]]
```

Two subsets. Call 1 records `[]`, adds `0`, call 2 records `[0]`.

### Negative numbers

```text
[-1, 2]  ->  [[], [-1], [-1,2], [2]]
```

Values never matter - only indices do. Nothing is compared.

### Input not sorted

```text
[3, 1]  ->  [[], [3], [3,1], [1]]
```

Order inside each subset follows **index** order, not value order. `[3,1]` is correct; LeetCode accepts any order.

### Maximum size

```text
n = 10  ->  1024 subsets
```

The backtracking tree has exactly 1,024 nodes.

### Empty input (not allowed by LeetCode, still handled)

```text
[]  ->  [[]]
```

The power set of the empty set is a set containing the empty set. Call 1 records `[]` and the loop never runs.

### The copy bug

```text
result.add(path)          with nums = [1, 2]
->  [[], [], [], []]
```

Four references to the same list, which is empty once the search finishes. The count is right, which is what makes this bug easy to miss.

### Duplicates in the input (Subsets II, LC 90)

```text
[1, 2, 2]  ->  this code returns 8 lists, including [1,2] twice
```

This problem guarantees distinct elements. With duplicates, sort first and skip `nums[i] == nums[i-1]` when `i > start`, which leaves 6 subsets.

=== takeaway ===
> When you see **"return all subsets / combinations"**, think **backtracking with a `start` index**: record, then for each later index choose, recurse at `i + 1`, un-choose.

### The core observation

Duplicates come from reaching the same set in different orders. Every set has exactly one increasing-index order, so generating only that order - by never choosing an index smaller than the last one - produces each subset exactly once. No sorting, no `HashSet`, no wasted path.

### The pattern trigger

```text
       "return all ..." + tiny n
                    |
                    v
       backtrack(start, path):
           record COPY of path          <- subsets: every node
                    |
           for i = start .. n-1:
               choose      path.add(nums[i])
               explore     backtrack(i + 1, path)
               un-choose   path.remove(last)
                    |
                    v
       order doesn't matter?  -> start index
       order matters?         -> used[] array (permutations)
```

### The common mistakes

**Adding `path` instead of a copy.** Every result entry aliases one list; you get `2^n` empty lists.

**Recursing on `start + 1` instead of `i + 1`.** Lets the search step backwards and reintroduces reordered duplicates.

**Starting the loop at `0`.** That is the brute force: permutation-style search that needs a `HashSet` to clean up.

**Recording only at the leaves.** That gives only the full-length path. For subsets, every node counts.

### What to remember in six months

> Choose, explore, un-choose. The `start` index is what turns "every ordering" into "every set".

The same template with one line changed solves Combinations (LC 77: record only at size `k`), Combination Sum (LC 39: recurse at `i`, not `i + 1`, to allow reuse), Subsets II (LC 90: sort and skip equal neighbours), and Permutations (LC 46: swap `start` for a `used[]` array and record only at full length).
