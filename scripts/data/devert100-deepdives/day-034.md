=== intro ===
Yesterday's two pointers kept a **fixed gap** of `n` nodes so one of them would land exactly `n` from the end. Today the gap is the problem: two lists of different lengths, and you need two pointers to arrive at the same node at the same moment.

> When two walkers start at different distances from a meeting point, do not measure the difference - make each of them walk the other's route too. Equal total distance means they arrive together.

=== problem ===
You get the heads of two singly linked lists, `headA` and `headB`. At some node they may **merge**: from that node onward they share every node. Return the first shared node, or `null` if they never meet.

```text
A:        a1(4) -> a2(1) \
                          c1(8) -> c2(4) -> c3(5) -> null
B: b1(5) -> b2(6) -> b3(1) /
```

```text
answer = c1   (the node with value 8)
```

The two lists are not two copies with the same values. After `c1` there is exactly **one** chain of nodes, and both lists point into it.

### The trap in the example

Look at `a2` and `b3`. Both hold the value `1`. They are **different nodes** - two separate objects in memory that happen to store the same number. The lists do not meet at `1`; they meet at `8`, because `c1` is the first node that both `a2.next` and `b3.next` point to.

| node | value | reached from A? | reached from B? |
| :--- | ----: | :-------------- | :-------------- |
| a1 | 4 | yes | no |
| a2 | 1 | yes | no |
| b1 | 5 | no | yes |
| b2 | 6 | no | yes |
| b3 | 1 | no | yes |
| c1 | 8 | yes | yes |
| c2 | 4 | yes | yes |
| c3 | 5 | yes | yes |

The question is about **identity**, not value. Every comparison in this problem is `==` on references, never `.val == .val`.

### What the constraints tell you

- Lengths `m` and `n` are each between `1` and `3 * 10^4`.
- Neither list has a cycle.
- You must **not modify** either list - which rules out tricks like marking visited nodes by rewiring them.
- The follow-up asks for `O(m + n)` time and `O(1)` extra memory. That last part is the real problem.

### Why the shape is always a "Y"

Once two lists share a node, they share **everything after it**, because each node has exactly one `next`. So two lists can never cross and separate again - an "X" shape is impossible. The picture is always a "Y": two separate tails that join into one shared stem.

```text
  unique part of A  (length a)  \
                                  shared part (length c) -> null
  unique part of B  (length b)  /
```

In the example: `a = 2`, `b = 3`, `c = 3`. Everything below uses those three numbers.

=== pattern ===
**Two Pointers, switching heads** - sometimes called "the two runners swap tracks".

The difficulty is that the two heads are at **different distances** from the join point. In the example, A's pointer is 2 steps from `c1` and B's pointer is 3 steps away. Walk them in lockstep and A's arrives one step early, passes the join, and they never line up.

There are two ways to fix an unequal start:

1. **Measure** the difference and give the longer list a head start. That is the length-difference method.
2. **Cancel** the difference without measuring it: when a pointer runs off the end of its own list, send it to the head of the *other* list.

The second works because of a simple sum:

```text
pointer from A walks:  a + c   then jumps to B   then  b      ->  a + c + b
pointer from B walks:  b + c   then jumps to A   then  a      ->  b + c + a
```

Both totals are `a + b + c`. After that many steps, both pointers are standing at the start of the shared part - at the same moment. If there is no shared part (`c = 0`), both reach `null` at the same moment instead, and `null == null` ends the loop with the right answer.

### Recognising it

Reach for this shape when:

- two sequences **merge** into a common tail and you want the merge point
- two walkers start at **unknown, different distances** from a target
- you are told `O(1)` extra space, so you cannot remember what you have seen

The mental question:

> Can I make both pointers travel the same total distance, so the difference I cannot measure cancels out by itself?

The same idea - equalise path lengths instead of computing them - reappears in Lowest Common Ancestor with parent pointers (LC 1650), which is literally this problem drawn as a tree.

=== bruteForce ===
Forget the space limit. What is the obvious thing to do?

Remember every node of A. Then walk B; the first B node you have already seen is the join point. Because a `HashSet<ListNode>` stores **references**, "seen" means "this exact object", which is precisely the question.

(An even more naive version compares every node of B against every node of A with two nested loops: `O(m * n)` time, `O(1)` space. The set is the natural first improvement, and it is the version most people write first.)

### Step logic

1. Walk A from `headA` to `null`, adding each node to `seen`.
2. Walk B from `headB`. For each node, if `seen` contains it, return it.
3. If B ends without a hit, the lists never meet - return `null`.

### Dry run

```text
A: a1(4) -> a2(1) -> c1(8) -> c2(4) -> c3(5)
B: b1(5) -> b2(6) -> b3(1) -> c1(8) -> c2(4) -> c3(5)
```

**Phase 1 - record A.**

| step | node | value | action | seen afterwards |
| ---: | :--- | ----: | :----- | :-------------- |
| 1 | a1 | 4 | add | `{a1}` |
| 2 | a2 | 1 | add | `{a1, a2}` |
| 3 | c1 | 8 | add | `{a1, a2, c1}` |
| 4 | c2 | 4 | add | `{a1, a2, c1, c2}` |
| 5 | c3 | 5 | add | `{a1, a2, c1, c2, c3}` |
| 6 | null | - | stop | `{a1, a2, c1, c2, c3}` |

**Phase 2 - probe with B.**

| step | node | value | `seen.contains(node)`? | action |
| ---: | :--- | ----: | :--------------------- | :----- |
| 1 | b1 | 5 | no (`c3` also holds 5, but it is a different node) | continue |
| 2 | b2 | 6 | no | continue |
| 3 | b3 | 1 | no (`a2` also holds 1, but it is a different node) | continue |
| 4 | c1 | 8 | **yes** | return `c1` |

Correct. Rows 1 and 3 are the whole point of using references: a value-based set would have returned `b1` (value 5) immediately, which is wrong.

### Java

```java
class Solution {
    public ListNode getIntersectionNode(ListNode headA, ListNode headB) {

        // ListNode does not override equals/hashCode, so the set compares
        // references - exactly "is this the same node?"
        Set<ListNode> seen = new HashSet<>();

        for (ListNode a = headA; a != null; a = a.next) {
            seen.add(a);
        }

        for (ListNode b = headB; b != null; b = b.next) {
            if (seen.contains(b)) {
                return b;
            }
        }

        return null;
    }
}
```

### Complexity

**Time:** `O(m + n)` - **Space:** `O(m)`

### Where it hurts

The time is already optimal: you cannot find a join point without potentially looking at every node, so `O(m + n)` is the floor.

The cost is the set. It holds **every node of A** - including the shared tail `c1, c2, c3`, which B is going to walk through anyway. With `3 * 10^4` nodes that is `3 * 10^4` hashed references, and the follow-up explicitly asks for `O(1)`.

Now ask what the set is really doing. It answers one question: "has the other pointer already been here?" And the only reason we need memory to answer that is that **the two pointers do not reach `c1` at the same time** - A's walker gets there after 2 steps, B's after 3. If they arrived together, a single `a == b` check would detect the join with no memory at all.

> The set exists to bridge a timing difference. Remove the timing difference and the set is unnecessary.

=== optimization ===
The set compensates for the two pointers being out of step. Let us put them in step.

### The key observation

Split each list at the join point, as in the "Y" picture:

```text
A = (a unique nodes) + (c shared nodes)      length a + c
B = (b unique nodes) + (c shared nodes)      length b + c
```

If pointer `pA` walks all of A and then continues into B, it reaches the shared part after `a + c + b` steps. If pointer `pB` walks all of B and then continues into A, it reaches the shared part after `b + c + a` steps. **Same number.** So they arrive at `c1` on the same step, and the first step where `pA == pB` is the answer.

### Step by step

1. `pA = headA`, `pB = headB`.
2. While `pA != pB`:
   - advance `pA`; if it was `null` (fell off its list), restart it at `headB` instead
   - advance `pB`; if it was `null`, restart it at `headA` instead
3. Return `pA`. It is either the join node or `null`.

The `null` is deliberately treated as a real position for one step. That is what makes the no-intersection case fall out naturally (see below).

### Dry run

Same lists, `a = 2`, `b = 3`, `c = 3`, so both pointers should meet after `2 + 3 + 3 + 1 = 9` steps (the `+1` is the step each spends standing on `null`).

| step | pA | pA.val | pB | pB.val | `pA == pB`? | what happened |
| ---: | :--- | -----: | :--- | -----: | :---------- | :------------ |
| 0 | a1 | 4 | b1 | 5 | no | start |
| 1 | a2 | 1 | b2 | 6 | no | both advance |
| 2 | c1 | 8 | b3 | 1 | no | pA already in the shared part, pB is not - out of step |
| 3 | c2 | 4 | c1 | 8 | no | pB enters the shared part one step late |
| 4 | c3 | 5 | c2 | 4 | no | |
| 5 | null | - | c3 | 5 | no | pA falls off A |
| 6 | b1 | 5 | null | - | no | pA switches to `headB`; pB falls off B |
| 7 | b2 | 6 | a1 | 4 | no | pB switches to `headA` |
| 8 | b3 | 1 | a2 | 1 | no | **same value, different nodes** - the loop correctly continues |
| 9 | c1 | 8 | c1 | 8 | **yes** | both arrive together - return `c1` |

Step 2 is the brute force's problem in one row: pA reaches `c1` while pB is still on `b3`. Steps 5-7 are the fix: by walking each other's unique part, pA picks up `b = 3` extra steps and pB picks up `a = 2`. Step 9 is where the totals match.

Step 8 is worth staring at. If the loop compared values (`pA.val != pB.val`) it would stop here and return `b3`, which is not in list A at all.

### When there is no intersection

```text
A: x1(2) -> x2(6) -> x3(4)
B: y1(1) -> y2(5)
```

Here `c = 0`, so both pointers walk `3 + 2 = 5` real nodes plus one `null`, and land on the **final** `null` together.

| step | pA | pB | `pA == pB`? | note |
| ---: | :--- | :--- | :---------- | :--- |
| 0 | x1 | y1 | no | |
| 1 | x2 | y2 | no | |
| 2 | x3 | null | no | pB falls off B |
| 3 | null | x1 | no | pA falls off A; pB switches to `headA` |
| 4 | y1 | x2 | no | pA switches to `headB` |
| 5 | y2 | x3 | no | |
| 6 | null | null | **yes** | both fall off their second list - return `null` |

The loop ends because `null == null`. No separate "did we switch twice?" counter is needed - and the loop cannot spin forever, because after one switch each both pointers are on the same schedule.

### The alternative: measure the difference

The follow-up the sheet mentions does the same equalisation explicitly:

1. Count `lenA` and `lenB`.
2. Advance the longer list's pointer by `|lenA - lenB|`.
3. Walk both together until they are equal.

In the example `lenA = 5`, `lenB = 6`, so `pB` moves one step first (to `b2`), and then both are exactly 2 steps from `c1`. It is equally `O(m + n)` and `O(1)` - just more code. The switching version is the same idea with the measuring done for free.

=== complexity ===
### Time

Each pointer walks at most its own list, one `null`, and the other list: at most `m + n + 1` steps before the loop ends.

```text
O(m + n)
```

### Space

Two references, `pA` and `pB`. Nothing scales with the input.

```text
O(1)
```

### Comparison

| Approach | Time | Extra space | Modifies lists? |
| :------- | ---: | ----------: | :-------------- |
| Nested loops | `O(m * n)` | `O(1)` | no |
| HashSet of A's nodes | `O(m + n)` | `O(m)` | no |
| Length difference | `O(m + n)` | `O(1)` | no |
| Switching heads | **`O(m + n)`** | **`O(1)`** | no |

The length-difference method and the switching method have the same complexity. In an interview, describe the length-difference version as the reasoning step ("the problem is the unequal distance, so remove it") and the switching version as the tidy implementation of that same reasoning.

=== implementation ===
```java
// ListNode is provided by LeetCode: int val; ListNode next; ListNode(int x)

class Solution {
    public ListNode getIntersectionNode(ListNode headA, ListNode headB) {

        ListNode pA = headA;
        ListNode pB = headB;

        // Compare REFERENCES. Both pointers walk a + b + c steps in total,
        // so they reach the join node (or null) on the same step.
        while (pA != pB) {
            pA = (pA == null) ? headB : pA.next;
            pB = (pB == null) ? headA : pB.next;
        }

        return pA;
    }
}
```

### The lines that matter

**1.**

```java
while (pA != pB) {
```

`!=` on two `ListNode` variables compares **references** - "are these the same object?" That is exactly the question. Writing `pA.val != pB.val` instead would stop at step 8 of the dry run (two different nodes holding `1`) and would also throw `NullPointerException` when a pointer is `null`.

**2.**

```java
pA = (pA == null) ? headB : pA.next;
```

The switch happens **when `pA` is already `null`**, not when `pA.next` is `null`. So each pointer spends one step standing on `null`. That one step is what makes the no-intersection case end at `null == null`. If you switch on `pA.next == null` instead, the pointers skip the `null` and, with no intersection, loop forever.

**3.**

```java
return pA;
```

When the loop ends, `pA == pB`. Either both are the join node, or both are `null`. Returning `pA` covers both outcomes - no separate "not found" branch.

### The length-difference version, for the follow-up

```java
class Solution {
    public ListNode getIntersectionNode(ListNode headA, ListNode headB) {

        int lenA = length(headA);
        int lenB = length(headB);

        ListNode pA = headA;
        ListNode pB = headB;

        // Give the longer list a head start so both are equally far from the end.
        while (lenA > lenB) { pA = pA.next; lenA--; }
        while (lenB > lenA) { pB = pB.next; lenB--; }

        while (pA != pB) {
            pA = pA.next;
            pB = pB.next;
        }

        return pA;
    }

    private int length(ListNode node) {
        int len = 0;
        while (node != null) {
            len++;
            node = node.next;
        }
        return len;
    }
}
```

### Java notes

- Do **not** declare `ListNode` yourself on LeetCode - it is provided, and a second declaration is a compile error. The comment at the top only shows its shape.
- `ListNode` does not override `equals` or `hashCode`, so both `==` and `HashSet<ListNode>` use object identity. That is why the brute-force set works. If a class *did* override `equals` by value, a `HashSet` would silently compare values - use `IdentityHashMap`-based sets in that situation.
- The ternary `(pA == null) ? headB : pA.next` evaluates the `null` check first, so `pA.next` is never read on a `null` reference.
- Neither version modifies a single `next` pointer, which satisfies "the lists must retain their original structure".

=== edgeCases ===
### No intersection, different lengths

```text
A = [2, 6, 4],  B = [1, 5]   (no shared node)  ->  null
```

Shown in the dry run: both pointers land on `null` together after `3 + 2 + 1 = 6` steps.

### Same values, but no shared node

```text
A = [1, 2, 3],  B = [1, 2, 3]   (two separate lists)  ->  null
```

The lengths are equal, so the pointers move in step from the start and both reach `null` after 3 steps, without ever switching. Every pair of nodes they compare holds equal values and is still not the same node. A value comparison would wrongly return the first node.

### The lists are the same list

```text
headA == headB  (e.g. both point at [1, 2, 3])  ->  the head node (value 1)
```

The loop condition is false before the first iteration. Returns `headA` in zero steps.

### One list is entirely inside the other

```text
A:        c1(3) -> c2(4)
B: b1(2) -> c1(3) -> c2(4)          ->  c1 (value 3)
```

`a = 0`, `b = 1`, `c = 2`. The join point is A's head. pA walks `c1, c2, null, b1, c1`; pB walks `b1, c1, c2, null, c1` - both reach `c1` on step 4.

### Shared part is only the last node

```text
A: 1 -> 2 -> c1(7)
B: 5 -> c1(7)                        ->  c1 (value 7)
```

`c = 1` is the smallest possible shared part. The arithmetic does not care how long the stem is.

### Equal-length lists that do intersect

```text
A: 1 -> c1(9) -> c2(8)
B: 4 -> c1(9) -> c2(8)               ->  c1 (value 9)
```

`a = b = 1`, so the pointers are already in step and meet at step 1 without ever switching. The switching logic is only needed when `a != b`.

### Single-node lists

```text
A = [1],  B = [1]  (different nodes)  ->  null
A = [1],  B = A    (same node)        ->  that node
```

### An empty list

```text
headA = null,  B = [1, 2]  ->  null
```

LeetCode guarantees both lists are non-empty, but the code handles it anyway: pA starts on `null`, switches to `headB` on the next step, and both pointers reach `null` together after 3 steps.

=== takeaway ===
> When two pointers start at **different, unknown distances** from a meeting point, make each walk **the other's path too**. Equal totals mean they arrive together.

### The core observation

Two merging lists always form a "Y": unique part `a`, unique part `b`, shared stem `c`. Walking `A` then `B` takes `a + c + b` steps to reach the stem; walking `B` then `A` takes `b + c + a`. The sums are equal, so the first moment the pointers coincide is the join point - or `null` if there is none.

### The pattern trigger

```text
   two chains that may merge into one tail
                     |
                     v
     unequal distance to the merge point?
          /                       \
     measure it                 cancel it
   (count lengths,           (on null, jump to the
    head-start the            OTHER head; both walk
    longer one)                  a + b + c)
          \                       /
                     v
     walk in lockstep until  pA == pB   (references!)
```

### The common mistakes

**Comparing values.** `pA.val == pB.val` stops at the first pair of nodes that merely hold the same number. The example is built to catch exactly this: `a2` and `b3` both hold `1`.

**Switching on `next == null`.** It skips the step on `null`, so with no intersection the pointers keep cycling through both lists forever.

**Switching to your own head.** `pA` must jump to `headB`, not back to `headA`. Re-walking your own list adds `a + c` again and the totals never match.

**Rewiring nodes to mark them visited.** It finds the answer, and it breaks the "do not modify the lists" constraint that the grader checks.

### What to remember in six months

> You do not need to know the difference between two distances to cancel it. Add the other distance to both.

The same trick finds the Lowest Common Ancestor when nodes have parent pointers (LC 1650) - each node's path to the root is a linked list, and the LCA is where they merge. And it is the cousin of yesterday's fixed-gap pointers: day 33 *created* a known gap on purpose; today *erases* an unknown one.
