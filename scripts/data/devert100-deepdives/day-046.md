=== intro ===
Days 44 and 45 binary searched **positions in an array**. Today there is no array at all. You are given one integer and asked for its square root, and the thing being searched is the **answer itself** - the numbers `0, 1, 2, ..., x`.

> Binary search never needed an array. It needs a range of candidates and a yes/no question that flips exactly once across that range. "Is `m * m <= x`?" is such a question, so the answer is wherever it flips.

=== problem ===
Given a non-negative integer `x`, return the square root of `x` **rounded down** to the nearest integer. You may not use any built-in exponent function or operator (`Math.sqrt`, `Math.pow`, `x ** 0.5`).

```text
x = 4   ->  2      (2 * 2 = 4 exactly)
x = 8   ->  2      (real root is 2.828..., rounded down)
x = 30  ->  5      (real root is 5.477..., rounded down)
```

In other words, return the **largest integer `m` with `m * m <= x`**. That restatement is the whole problem - it removes the decimals and leaves a question about integers.

| m | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
| :--- | -: | -: | -: | -: | -: | -: | -: | -: |
| m * m | 0 | 1 | 4 | 9 | 16 | **25** | 36 | 49 |
| m * m <= 30 ? | yes | yes | yes | yes | yes | **yes** | no | no |

The last `yes` is at `m = 5`, so `mySqrt(30) = 5`.

### The constraints that matter

- `0 <= x <= 2^31 - 1`, i.e. up to `2,147,483,647`. So `x` fits in an `int`, but **`m * m` does not always**: `46,341 * 46,341 = 2,147,488,281`, which is larger than `Integer.MAX_VALUE`.
- `x = 0` and `x = 1` are allowed and are their own square roots.
- No built-in power or root. Multiplication and division are fine.

### What "rounded down" rules out

Rounding to nearest would make `mySqrt(8) = 3`. The problem truncates: `2.828...` becomes `2`. That is why the condition is `m * m <= x` (the largest `m` that does not overshoot), not "closest to `x`".

=== pattern ===
**Binary Search on the Answer.**

Write the question as a row of yes/no answers over every candidate:

```text
m         :  0    1    2    3    4    5    6    7   ...   30
m*m <= 30 :  T    T    T    T    T    T    F    F   ...   F
                                      ^
                               last T = answer
```

Because `m * m` grows as `m` grows, once the answer is `F` it stays `F`. The row is **monotonic**: a block of `T`s, then a block of `F`s. Day 45 searched for where such a row flips in an array of values; here the "array" is the integers `0..x` and each cell is computed on demand as `m * m <= x`. Nothing needs to be stored.

### The template

```text
lo = smallest possible answer, hi = largest possible answer
while lo <= hi:
    mid = lo + (hi - lo) / 2
    if condition(mid):  ans = mid;  lo = mid + 1     # mid works, try bigger
    else:               hi = mid - 1                  # mid fails, go smaller
return ans
```

That is day 45's "record and keep searching" with the equality test replaced by a condition. It is the same shape that later solves Koko Eating Bananas, Capacity to Ship Packages and Split Array Largest Sum: the answer is a number in a range, and you can **check** a guess faster than you can compute the answer directly.

### Recognising it

Reach for binary search on the answer when:

- the answer is an **integer in a known range** (here `0..x`)
- you can **test** a candidate (`m * m <= x`) more easily than you can find the answer
- the test is **monotonic** - if `m` passes, every smaller value passes too (or every larger one does)
- the problem says "largest value such that..." or "minimum value that still..."

The mental question:

> If someone handed me a guess, could I quickly say "too big" or "small enough"? And does "too big" for `m` mean "too big" for everything above `m`?

If both are yes, you are binary searching an answer range, not an array.

=== bruteForce ===
Try candidates from the bottom. Keep going while the square still fits; the last one that fit is the answer.

### Step logic

1. Start at `i = 0`.
2. While `(i + 1) * (i + 1) <= x`, increment `i`.
3. Return `i` - the largest value whose square did not overshoot.

Written the more common way: start at `i = 1`, loop while `i * i <= x`, return `i - 1`.

### Dry run

```text
x = 30
```

| step | i | i * i | i * i <= 30? | action |
| ---: | -: | ----: | :----------- | :----- |
| 1 | 1 | 1 | yes | `i = 2` |
| 2 | 2 | 4 | yes | `i = 3` |
| 3 | 3 | 9 | yes | `i = 4` |
| 4 | 4 | 16 | yes | `i = 5` |
| 5 | 5 | 25 | yes | `i = 6` |
| 6 | 6 | 36 | **no** | stop, return `i - 1 = 5` |

Correct: `5`.

### Java

```java
class Solution {
    public int mySqrt(int x) {

        long i = 1;                    // long: i * i must not overflow
        while (i * i <= x) {
            i++;
        }

        return (int) (i - 1);          // last i whose square fit
    }
}
```

`i` is a `long` on purpose. With an `int`, the input `x = 2,147,483,647` reaches `i = 46,341`, whose square overflows to `-2,147,479,015` - which **is** `<= x`, so the loop sails past the answer. For that input it never stops at all: every `int` is `<= Integer.MAX_VALUE`, so `i * i <= x` can never be false.

### Complexity

**Time:** `O(sqrt(x))` - **Space:** `O(1)`

### Where it hurts

`sqrt(x)` sounds small, but it is not `log`:

| x | iterations of the scan |
| -: | ---------------------: |
| 30 | 6 |
| 10,000 | 101 |
| 1,000,000 | 1,001 |
| 2,147,483,647 | 46,341 |

And look at what each row of the dry run actually learned. Step 2 found `2 * 2 = 4 <= 30`. Because squares only grow, that also proves `0` and `1` fit - but we already knew that. Step 5 found `25 <= 30`, which proves every `m <= 5` fits; then step 6 found `36 > 30`, which proves every `m >= 6` fails.

The scan learns one boundary at a time, walking toward it from one side. But each check is a fact about a **whole side** of the candidate range - exactly the property day 44 used to stop scanning arrays. The candidates `0..x` are sorted for free. Check the middle one, and half of them are settled.

=== optimization ===
### The key observation

The candidates `0, 1, ..., x` are in order, and the test `m * m <= x` is monotonic over them. A single test at `mid` settles half the range:

- `mid * mid <= x` -> `mid` is a valid answer, and so is everything below it. The **largest** valid answer is `mid` or above. Record `mid`, search right.
- `mid * mid > x` -> `mid` and everything above it fail. Search left.

This is day 45's "record a candidate, keep searching toward the side you care about", with "the side you care about" being *bigger*.

### Deriving it step by step

1. Candidate range `[lo, hi] = [0, x]`. (`sqrt(x) <= x` for every `x >= 0`, so the answer is inside.)
2. `ans = 0`.
3. While `lo <= hi`: `mid = lo + (hi - lo) / 2`.
4. If `(long) mid * mid <= x`: `ans = mid`, `lo = mid + 1`.
5. Else: `hi = mid - 1`.
6. Return `ans`.

### Dry run - same example

```text
x = 30, search range [0, 30]
```

| step | lo | hi | mid | mid * mid | <= 30? | ans after | action |
| ---: | -: | -: | --: | --------: | :----- | --------: | :----- |
| 1 | 0 | 30 | 15 | 225 | no | 0 | `hi = 14` |
| 2 | 0 | 14 | 7 | 49 | no | 0 | `hi = 6` |
| 3 | 0 | 6 | 3 | 9 | yes | 3 | `lo = 4` |
| 4 | 4 | 6 | 5 | 25 | yes | 5 | `lo = 6` |
| 5 | 6 | 6 | 6 | 36 | no | 5 | `hi = 5` |
| - | 6 | 5 | - | - | `lo > hi` | **5** | stop |

Five steps against the scan's six - barely different at `x = 30`, because the scan stops early on a small input anyway. Step 1 alone, `15 * 15 = 225 > 30`, settles sixteen candidates (`15..30`) at once; at `x = 2^31 - 1` that same halving is the difference between 46,341 steps and 31.

Step 3 is the record-and-continue move: `3` works, so it is written into `ans`, and the search goes right to look for something bigger that also works. Step 4 finds `5`; step 5 tries `6` and fails, so `5` stands.

### Dry run - the largest input

```text
x = 2,147,483,647, search range [0, 2,147,483,647]
```

The scan needs 46,341 iterations. The binary search needs **31**, because each step halves a range of about `2^31` values. The first few steps:

| step | lo | hi | mid | mid * mid (as long) | <= x? |
| ---: | -: | -: | --: | ------------------: | :---- |
| 1 | 0 | 2,147,483,647 | 1,073,741,823 | 1,152,921,502,459,363,329 | no |
| 2 | 0 | 1,073,741,822 | 536,870,911 | 288,230,375,077,969,921 | no |
| 3 | 0 | 536,870,910 | 268,435,455 | 72,057,593,501,057,025 | no |

Step 1's `mid * mid` is about `1.15 * 10^18`. In `int` arithmetic that product would overflow to a meaningless value (possibly small, possibly negative) and the comparison would be wrong. `(long) mid * mid` casts **before** multiplying, so the product is computed in 64 bits, where it fits comfortably.

### The alternative to `long` - divide instead of multiply

`mid * mid <= x` is the same test as `mid <= x / mid` for `mid >= 1` (integer division rounds down, and the two inequalities agree on integers). Division cannot overflow. The catch is `mid = 0`, which divides by zero - so that version searches `[1, x]` and handles `x < 2` up front. Both are shown in the implementation.

=== complexity ===
### Time

The candidate range `[0, x]` halves every iteration.

```text
O(log x)
```

At most 31 iterations for any `x` that fits in an `int`.

### Space

`lo`, `hi`, `mid`, `ans`.

```text
O(1)
```

### Comparison

| Approach | Time | Space | Iterations at `x = 2^31 - 1` |
| :------- | ---: | ----: | ---------------------------: |
| Scan `1, 2, 3, ...` | `O(sqrt x)` | `O(1)` | 46,341 |
| Binary search on `[0, x]` | **`O(log x)`** | **`O(1)`** | 31 |
| Newton's method | `O(log x)`, very fast in practice | `O(1)` | 19 |

Newton's method is the numerical-analysis answer and worth knowing exists (shown below), but binary search on the answer is the one the problem is teaching: it is the template that transfers to problems where there is no formula to differentiate.

=== implementation ===
```java
class Solution {
    public int mySqrt(int x) {

        // Answer is the largest m in [0, x] with m * m <= x.
        int lo = 0;
        int hi = x;
        int ans = 0;

        while (lo <= hi) {
            int mid = lo + (hi - lo) / 2;

            if ((long) mid * mid <= x) {
                ans = mid;          // mid fits - remember it, try bigger
                lo = mid + 1;
            } else {
                hi = mid - 1;       // mid overshoots - go smaller
            }
        }

        return ans;
    }
}
```

### The lines that matter

**1.**

```java
if ((long) mid * mid <= x) {
```

The cast applies to `mid` before the multiplication, so Java multiplies a `long` by an `int` and the result is a `long`. `(long) (mid * mid)` would be wrong: the parentheses make the `int` multiplication happen first, overflow, and *then* widen the garbage.

**2.**

```java
ans = mid;          // mid fits - remember it, try bigger
lo = mid + 1;
```

We want the **largest** `m` that fits, so a fitting `mid` is a candidate, not the answer. Same move as day 45's "record and keep searching".

**3.**

```java
int hi = x;
```

The answer can never exceed `x` (for `x >= 1`, `sqrt(x) <= x`; for `x = 0` the answer is `0`). You could tighten this to `Math.min(x, 46340)` - the largest `int` whose square fits in an `int` - but it saves only a couple of iterations.

### The division version - no `long` needed

```java
class Solution {
    public int mySqrt(int x) {

        if (x < 2) {
            return x;                    // 0 -> 0, 1 -> 1; also keeps mid >= 1 below
        }

        int lo = 1;
        int hi = x / 2;                  // floor(sqrt(x)) <= x / 2 for every x >= 2
        int ans = 1;

        while (lo <= hi) {
            int mid = lo + (hi - lo) / 2;
            if (mid <= x / mid) {        // same test as mid * mid <= x, without overflow
                ans = mid;
                lo = mid + 1;
            } else {
                hi = mid - 1;
            }
        }

        return ans;
    }
}
```

### Newton's method, for the curious

Repeatedly replace a guess `r` with the average of `r` and `x / r`. Starting above the root, it decreases monotonically to `floor(sqrt(x))` in integer arithmetic:

```java
class Solution {
    public int mySqrt(int x) {

        long r = x;
        while (r * r > x) {
            r = (r + x / r) / 2;
        }

        return (int) r;
    }
}
```

### Follow-up - Valid Perfect Square (LC 367)

Same search, but stop on exact equality:

```java
class Solution {
    public boolean isPerfectSquare(int num) {

        long lo = 1, hi = num;
        while (lo <= hi) {
            long mid = lo + (hi - lo) / 2;
            long sq = mid * mid;
            if (sq == num) return true;
            if (sq < num) lo = mid + 1;
            else hi = mid - 1;
        }

        return false;
    }
}
```

### Java notes

- Java evaluates `(long) mid * mid` as `((long) mid) * mid`: the cast binds tighter than `*`. That precedence is what makes the one-liner correct.
- `Math.sqrt` is banned by the problem, and even where allowed, `(int) Math.sqrt(x)` relies on floating-point rounding. For `int` inputs it happens to be exact, but for `long` inputs near `2^63` it is not - the integer binary search is exact everywhere.
- Returning `int` is safe: the answer is at most `46,340`.

=== edgeCases ===
### Zero

```text
x = 0  ->  0
```

Range `[0, 0]`, `mid = 0`, `0 <= 0` so `ans = 0`. The division version returns early because `0 / 0` would throw.

### One

```text
x = 1  ->  1
```

### Two and three

```text
x = 2  ->  1
x = 3  ->  1
```

The real roots are `1.41...` and `1.73...`; both round down to `1`. A rounding-to-nearest bug would give `2` for `3`.

### Perfect squares

```text
x = 4   ->  2
x = 16  ->  4
```

`m * m == x` counts as fitting (`<=`), so the exact root is recorded. Using `<` instead would return `1` and `3`.

### One below a perfect square

```text
x = 8   ->  2
x = 15  ->  3
```

`15` is the classic check for an off-by-one: the real root is `3.87`, the answer is `3`, and `4 * 4 = 16` must be rejected.

### The overflow boundary

```text
x = 2,147,395,599  ->  46,339     (46,340^2 = 2,147,395,600 is one too many)
x = 2,147,395,600  ->  46,340     (exact square)
x = 2,147,483,647  ->  46,340     (Integer.MAX_VALUE)
```

Here the answer itself sits right next to the overflow line. An `int`-only `mid * mid` breaks far earlier than this, though: the first wrong answer is at `x = 92,682`, which returns `65,536` instead of `304`, because it is the first input whose opening `mid` (46,341) has a square that does not fit in an `int`.

### Valid Perfect Square, the follow-up

```text
num = 16  ->  true
num = 14  ->  false
num = 1   ->  true
```

=== takeaway ===
> When you see **"find the largest / smallest integer such that..."** and checking a guess is easy, think **binary search on the answer**: search the range of possible answers, not an array.

### The core observation

`m * m <= x` is true for every `m` up to the answer and false for every `m` after it. That makes the integers `0..x` a sorted, monotonic yes/no row - and day 45 already taught how to find where such a row flips. No array is needed; each cell is computed when `mid` lands on it.

### The pattern trigger

```text
            answer is an integer in [lo, hi]
                           |
                           v
        can I TEST a guess m quickly?  (m * m <= x)
                           |
                           v
        is the test monotonic?  T T T T F F F
                           |
                           v
          mid passes  ->  ans = mid, lo = mid + 1   (want largest)
          mid fails   ->  hi = mid - 1
                           |
                           v
               ans = last value that passed
```

### The common mistakes

**`int` overflow in `mid * mid`.** It passes every small test and first fails at `x = 92,682`, the first input whose opening `mid` squares past `Integer.MAX_VALUE`. Cast before multiplying: `(long) mid * mid`.

**`(long) (mid * mid)`.** Looks like the fix, is the bug - the multiplication already overflowed inside the parentheses.

**Returning the last `mid` instead of the recorded `ans`.** When the loop ends, `mid` was the last thing tried, which may have been one that **failed** (step 5 of the dry run tried `6`).

**`mid <= x / mid` with `mid = 0`.** Division by zero. Start the range at `1` and handle `x < 2` separately.

### What to remember in six months

> If you can check an answer faster than you can compute it, and checks are monotonic, binary search the answer.

Sqrt(x) is the smallest instance of the most reused binary-search idea in interviews.
