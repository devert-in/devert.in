=== intro ===
Yesterday's Coin Change II let every coin be used as many times as you liked, and its inner loop ran **forwards** over the amounts. Today every item can be used **at most once** - and the entire difference between the two problems turns out to be the direction of that one loop.

> 0/1 Knapsack is the parent of half the DP problems you will meet this week. Learn to see every "take it or leave it, under a budget" question as this table, and Partition Equal Subset Sum, Target Sum and Last Stone Weight II stop being separate problems.

=== problem ===
You have `n` items. Item `i` weighs `wt[i]` and is worth `val[i]`. Your bag holds a total weight of at most `W`. Choose a subset of the items - **each item either goes in whole or stays out, at most once** - to maximise the total value.

```text
val = [10, 15, 40]
wt  = [ 1,  2,  3]
W   = 5
```

Answer: `55`.

| item | weight | value | value per unit weight |
| ---: | -----: | ----: | --------------------: |
| 0 | 1 | 10 | 10.0 |
| 1 | 2 | 15 | 7.5 |
| 2 | 3 | 40 | 13.3 |

The best bag is items `1` and `2`: weight `2 + 3 = 5` (exactly full), value `15 + 40 = 55`. Taking all three would weigh `6`, which does not fit.

### What "0/1" means

The `0/1` is the decision per item: `0` copies or `1` copy. Nothing in between (that would be *fractional* knapsack, which greedy solves) and nothing more (that would be *unbounded* knapsack, which is Coin Change II's shape).

### Why the obvious greedy is wrong

The natural instinct is "take the best value-per-weight item first". Run it:

```text
best ratio: item 2 (13.3)  -> take, weight 3, value 40, room left 2
next:       item 0 (10.0)  -> take, weight 4, value 50, room left 1
next:       item 1 (7.5)   -> weight 2 does not fit in 1
greedy total = 50
```

Greedy says `50`; the real answer is `55`. Taking item 0 looked efficient but left exactly the wrong amount of room. Because items cannot be cut, a locally good choice can waste capacity that a later item needed. That is the condition that makes this a DP problem rather than a sorting problem.

### Constraints that matter

On GeeksforGeeks: `n` up to `1000`, `W` up to `1000`, weights and values up to `1000`. So `n * W` is about `10^6` - a table of that size is cheap. `2^n` with `n = 1000` is not something any computer will ever finish.

The GFG signature is `static int knapsack(int W, int val[], int wt[])`. Older versions of the problem used `knapSack(int W, int wt[], int val[], int n)` - same problem, arguments reordered. Read the signature you are given before you start.

=== pattern ===
**0/1 Knapsack DP** - a 2D table that collapses to 1D, with the capacity loop running **backwards**.

### Why it is a DP problem

Ask the two DP questions:

1. **Is there a choice at each step whose consequence is just a smaller version of the same problem?** Yes. For the last item, either you leave it out (now solve the same problem with one fewer item and the same capacity) or you put it in (one fewer item, capacity reduced by its weight, plus its value).
2. **Do those smaller problems repeat?** Yes. A subproblem is fully described by two numbers - *which items are still available* (a prefix, so just a count `i`) and *how much room is left* (`w`). There are only `(n + 1) * (W + 1)` such pairs, but there are `2^n` ways to arrive at them.

That gives the state and the recurrence directly:

```text
dp[i][w] = best value using only the first i items, with capacity w

dp[i][w] = max( dp[i-1][w],                          skip item i-1
                 val[i-1] + dp[i-1][w - wt[i-1]] )   take item i-1   (only if wt[i-1] <= w)

dp[0][w] = 0       no items, no value
dp[i][0] = 0       no room, no value
```

### Recognising it

Reach for 0/1 knapsack when:

- there is a set of items, each used **at most once**
- there is a **budget** (weight, cost, sum, time) that the chosen items consume
- you are asked for the **max / min** of something, **whether** a target is reachable, or **how many** subsets hit it

The mental question:

> For each item, is the choice simply "in or out", and does that choice only change how much budget is left?

If yes, the state is `(items considered, budget left)` and the table is `n x W`.

=== bruteForce ===
Before any table, the honest approach: try every subset. Recursion makes that natural - at each item, branch into "skip it" and "take it".

### Step logic

Define `best(i, cap)` = the most value obtainable from items `i, i+1, ..., n-1` with `cap` room left.

1. If `i == n`, there are no items left: return `0`.
2. **Skip** item `i`: `best(i + 1, cap)`.
3. **Take** item `i`, only if `wt[i] <= cap`: `val[i] + best(i + 1, cap - wt[i])`.
4. Return the larger of the two.

The answer is `best(0, W)`.

### Dry run

```text
val = [10, 15, 40], wt = [1, 2, 3], W = 5
```

Calls listed in the order they **finish** (a call finishes only once both of its children have returned). Calls at `i = 3` return `0` immediately and are folded into their parent's row.

| call | item i (wt, val) | skip result | take result | returns |
| :--- | :--------------- | ----------: | :---------- | ------: |
| `best(2, 5)` | 2 (3, 40) | `best(3,5)` = 0 | 40 + `best(3,2)` = 40 + 0 = 40 | 40 |
| `best(2, 3)` | 2 (3, 40) | `best(3,3)` = 0 | 40 + `best(3,0)` = 40 + 0 = 40 | 40 |
| `best(1, 5)` | 1 (2, 15) | `best(2,5)` = 40 | 15 + `best(2,3)` = 15 + 40 = 55 | 55 |
| `best(2, 4)` | 2 (3, 40) | `best(3,4)` = 0 | 40 + `best(3,1)` = 40 + 0 = 40 | 40 |
| `best(2, 2)` | 2 (3, 40) | `best(3,2)` = 0 | not allowed, 3 > 2 | 0 |
| `best(1, 4)` | 1 (2, 15) | `best(2,4)` = 40 | 15 + `best(2,2)` = 15 + 0 = 15 | 40 |
| `best(0, 5)` | 0 (1, 10) | `best(1,5)` = 55 | 10 + `best(1,4)` = 10 + 40 = 50 | **55** |

Read the top row of the answer: skipping item 0 gives `55`, taking it gives `50`. The recursion found exactly the trap greedy fell into, and declined it.

### The subsets this explored

Every leaf of the recursion is one subset. For completeness:

| subset | weight | fits? | value |
| :----- | -----: | :---- | ----: |
| {} | 0 | yes | 0 |
| {2} | 3 | yes | 40 |
| {1} | 2 | yes | 15 |
| {1, 2} | 5 | yes | **55** |
| {0} | 1 | yes | 10 |
| {0, 2} | 4 | yes | 50 |
| {0, 1} | 3 | yes | 25 |
| {0, 1, 2} | 6 | no | - |

### Java

```java
class Solution {
    static int knapsack(int W, int val[], int wt[]) {
        return best(0, W, val, wt);
    }

    // Most value from items i..n-1 with `cap` room left.
    private static int best(int i, int cap, int[] val, int[] wt) {
        if (i == val.length) {
            return 0;
        }

        int skip = best(i + 1, cap, val, wt);

        int take = 0;
        if (wt[i] <= cap) {
            take = val[i] + best(i + 1, cap - wt[i], val, wt);
        }

        return Math.max(skip, take);
    }
}
```

### Complexity

**Time:** `O(2^n)` - **Space:** `O(n)` recursion stack

### Where it hurts

On three items nothing repeated. Change the weights slightly and watch:

```text
wt = [2, 2, 3], W = 5

take item 0, skip item 1   ->  best(2, 3)
skip item 0, take item 1   ->  best(2, 3)
```

Two different paths arrive at the **identical** question: "with item 2 left and 3 units of room, what is the best you can do?" The recursion answers it twice, from scratch, and each of those answers spawns its own subtree.

That is not bad luck; it is arithmetic. The answer to `best(i, cap)` depends **only** on `i` and `cap` - not on which earlier items were chosen to get there. There are at most `(n + 1) * (W + 1)` distinct `(i, cap)` pairs. With `n = 100` and `W = 1000` that is about `10^5` questions, asked roughly `2^100` times. Almost every call is a repeat.

So the waste has a precise shape: **a two-number subproblem, recomputed once per path that reaches it.** Store each answer the first time and the exponential collapses to the number of distinct pairs.

=== optimization ===
### Step 1 - cache the recursion (top-down)

Since `best(i, cap)` depends only on `(i, cap)`, keep an `Integer[n][W + 1]` memo. Check it before recursing, fill it before returning. Each pair is computed once and each computation does `O(1)` work, so the time drops to `O(n * W)`.

That is already a correct answer. But the recursion stack and the boxed `Integer` cache are overhead, and building the table in order is what unlocks the 1D trick. So flip it around.

### Step 2 - build the table bottom-up

Let `dp[i][w]` be the best value using only the **first `i` items** with capacity `w`. Row `0` (no items) is all zeros. Each later row depends only on the row directly above it:

```text
dp[i][w] = dp[i-1][w]                                       if wt[i-1] > w
dp[i][w] = max(dp[i-1][w], val[i-1] + dp[i-1][w - wt[i-1]]) otherwise
```

The two candidates read straight down (skip) and up-and-to-the-left by the item's weight (take).

### Dry run - the 2D table

```text
val = [10, 15, 40], wt = [1, 2, 3], W = 5
```

Row by row. Each entry in the "how" column shows `skip` vs `take`.

**Row 1 - item 0 (wt 1, val 10)**

| w | skip `dp[0][w]` | take `10 + dp[0][w-1]` | `dp[1][w]` |
| -: | --------------: | :--------------------- | ---------: |
| 0 | 0 | does not fit | 0 |
| 1 | 0 | 10 + 0 = 10 | 10 |
| 2 | 0 | 10 + 0 = 10 | 10 |
| 3 | 0 | 10 + 0 = 10 | 10 |
| 4 | 0 | 10 + 0 = 10 | 10 |
| 5 | 0 | 10 + 0 = 10 | 10 |

**Row 2 - item 1 (wt 2, val 15)**

| w | skip `dp[1][w]` | take `15 + dp[1][w-2]` | `dp[2][w]` |
| -: | --------------: | :--------------------- | ---------: |
| 0 | 0 | does not fit | 0 |
| 1 | 10 | does not fit | 10 |
| 2 | 10 | 15 + 0 = 15 | 15 |
| 3 | 10 | 15 + 10 = 25 | 25 |
| 4 | 10 | 15 + 10 = 25 | 25 |
| 5 | 10 | 15 + 10 = 25 | 25 |

**Row 3 - item 2 (wt 3, val 40)**

| w | skip `dp[2][w]` | take `40 + dp[2][w-3]` | `dp[3][w]` |
| -: | --------------: | :--------------------- | ---------: |
| 0 | 0 | does not fit | 0 |
| 1 | 10 | does not fit | 10 |
| 2 | 15 | does not fit | 15 |
| 3 | 25 | 40 + 0 = 40 | 40 |

The full table:

```text
            w=0  w=1  w=2  w=3  w=4  w=5
i=0 (none)    0    0    0    0    0    0
i=1 (+it0)    0   10   10   10   10   10
i=2 (+it1)    0   10   15   25   25   25
i=3 (+it2)    0   10   15   40   50   55   <- answer dp[3][5]
```

`dp[3][5] = 40 + dp[2][2]` says: take item 2, and fill the remaining 2 units the best way items 0-1 can - which is item 1 alone (`15`). That is the `{1, 2}` subset the brute force found.

### Step 3 - one row is enough

Row `i` reads **only** row `i - 1`. So keep a single array `dp[0..W]` and overwrite it in place, item by item. Before processing item `i`, `dp` holds row `i`; after, it holds row `i + 1`.

The catch is in the take term, `dp[w - wt]`. It must be the **old** value (row above, item not yet used). Its index is *smaller* than `w`.

- Loop `w` **upwards** and `dp[w - wt]` has already been overwritten this round - it may already contain the current item. Reading it lets the item be taken twice.
- Loop `w` **downwards** and every smaller index is still untouched this round - still the old row.

So the capacity loop must run from `W` down to `wt[i]`.

### Dry run - the 1D array, backwards

| item (wt, val) | w | `dp[w]` old | `val + dp[w - wt]` | `dp[w]` new | dp after the item |
| :------------- | -: | ----------: | :----------------- | ----------: | :---------------- |
| start | - | - | - | - | `[0, 0, 0, 0, 0, 0]` |
| 0 (1, 10) | 5 | 0 | 10 + dp[4] = 10 + 0 | 10 | |
| | 4 | 0 | 10 + dp[3] = 10 + 0 | 10 | |
| | 3 | 0 | 10 + dp[2] = 10 + 0 | 10 | |
| | 2 | 0 | 10 + dp[1] = 10 + 0 | 10 | |
| | 1 | 0 | 10 + dp[0] = 10 + 0 | 10 | `[0, 10, 10, 10, 10, 10]` |
| 1 (2, 15) | 5 | 10 | 15 + dp[3] = 15 + 10 | 25 | |
| | 4 | 10 | 15 + dp[2] = 15 + 10 | 25 | |
| | 3 | 10 | 15 + dp[1] = 15 + 10 | 25 | |
| | 2 | 10 | 15 + dp[0] = 15 + 0 | 15 | `[0, 10, 15, 25, 25, 25]` |
| 2 (3, 40) | 5 | 25 | 40 + dp[2] = 40 + 15 | 55 | |
| | 4 | 25 | 40 + dp[1] = 40 + 10 | 50 | |
| | 3 | 25 | 40 + dp[0] = 40 + 0 | 40 | `[0, 10, 15, 40, 50, 55]` |

`dp[5] = 55`. Each "dp after" column matches a row of the 2D table exactly - the 1D array **is** the 2D table, one row at a time.

### What happens if you loop forwards

Same input, same code, `w` running from `wt[i]` up to `W`:

| item (wt, val) | dp after the item | what went wrong |
| :------------- | :---------------- | :-------------- |
| 0 (1, 10) | `[0, 10, 20, 30, 40, 50]` | `dp[2] = 10 + dp[1]`, and `dp[1]` already used item 0 - so item 0 is in twice |
| 1 (2, 15) | `[0, 10, 20, 30, 40, 50]` | no change |
| 2 (3, 40) | `[0, 10, 20, 40, 50, 60]` | `dp[5] = 40 + dp[2] = 40 + 20` - item 2 plus item 0 twice |

Forwards returns `60`: item 2 once and item 0 **twice**. That is the correct answer to *unbounded* knapsack - and exactly what yesterday's Coin Change II wanted. For 0/1 it is wrong. The direction of one loop is the difference between the two problems.

=== complexity ===
### Time

`n` items, each sweeping at most `W + 1` capacities, `O(1)` per cell.

```text
O(n * W)
```

### Space

One array of `W + 1` integers.

```text
O(W)
```

### Why this is "pseudo-polynomial"

`O(n * W)` looks polynomial, but `W` is a **value**, not a count of inputs. Doubling the number of digits in `W` squares it. With `W = 10^9` the table is impossible even for three items. 0/1 knapsack is NP-hard in general; the DP is fast only because the problem caps `W` at a small number. Worth saying out loud in an interview when asked "is this polynomial?".

### Comparison

| Approach | Time | Space | Notes |
| :------- | ---: | ----: | :---- |
| Recursion, all subsets | `O(2^n)` | `O(n)` stack | correct, hopeless past `n` around 30 |
| Recursion + memo | `O(n * W)` | `O(n * W)` + stack | easiest to derive from the brute force |
| 2D table | `O(n * W)` | `O(n * W)` | easiest to reconstruct which items were chosen |
| 1D table, backwards | **`O(n * W)`** | **`O(W)`** | the interview answer |
| Greedy by value/weight | `O(n log n)` | `O(1)` | **wrong** for 0/1 (gives `50` on the example) |

Keep the 2D version in mind for the classic follow-up "which items did you pick?" - you walk back up the table from `dp[n][W]`, and a single row cannot do that.

=== implementation ===
```java
class Solution {
    static int knapsack(int W, int val[], int wt[]) {

        int n = val.length;

        // dp[w] = best value with capacity w, using the items processed so far.
        int[] dp = new int[W + 1];

        for (int i = 0; i < n; i++) {
            // BACKWARDS, so dp[w - wt[i]] is still the value from before item i.
            for (int w = W; w >= wt[i]; w--) {
                dp[w] = Math.max(dp[w], val[i] + dp[w - wt[i]]);
            }
        }

        return dp[W];
    }
}
```

### The lines that matter

**1.**

```java
for (int w = W; w >= wt[i]; w--) {
```

Backwards is the whole correctness argument. The take term reads a smaller index; walking down means that smaller index has not been touched yet in this round, so it still describes a world without item `i`. The lower bound `w >= wt[i]` also does the "does it fit?" check for free - capacities below the item's weight are simply not visited, so they keep the skip value.

**2.**

```java
dp[w] = Math.max(dp[w], val[i] + dp[w - wt[i]]);
```

The recurrence, with the row index erased. Before the assignment `dp[w]` is the row above (skip); `val[i] + dp[w - wt[i]]` is take.

**3.**

```java
int[] dp = new int[W + 1];
```

`W + 1` because capacity `0` is a real state. Java zero-fills it, and zero is exactly the base case: no items yet means no value at any capacity.

### The 2D version, for "which items did you pick?"

```java
class Solution {
    static int knapsack(int W, int val[], int wt[]) {

        int n = val.length;
        int[][] dp = new int[n + 1][W + 1];   // row 0 = no items = all zeros

        for (int i = 1; i <= n; i++) {
            for (int w = 0; w <= W; w++) {
                dp[i][w] = dp[i - 1][w];                       // skip item i-1
                if (wt[i - 1] <= w) {
                    dp[i][w] = Math.max(dp[i][w],
                                        val[i - 1] + dp[i - 1][w - wt[i - 1]]);  // take it
                }
            }
        }

        return dp[n][W];
    }
}
```

In 2D the inner loop can run either direction, because reads come from row `i - 1` and writes go to row `i` - they never collide. The backwards rule exists only because 1D makes them share storage. To recover the chosen items, start at `(n, W)`: if `dp[i][w] != dp[i-1][w]`, item `i-1` was taken, so subtract its weight; either way move to row `i - 1`.

### Java notes

- `int val[]` is C-style array syntax; it is identical to `int[] val`. GFG's stub uses it, so leave it alone.
- The method is `static` on GFG. Helper methods it calls must be `static` too - which is why the brute force's `best` is declared `private static`.
- Maximum value is `1000 * 1000 = 10^6`, well inside `int`.

=== edgeCases ===
### Capacity zero

```text
W = 0, val = [10, 20], wt = [1, 2]  ->  0
```

`dp` has a single slot; the inner loop's condition `0 >= wt[i]` is false for every item, so nothing is ever taken.

### No item fits

```text
W = 4, val = [10, 20], wt = [5, 6]  ->  0
```

Same mechanism - every item's weight exceeds `W`, so the inner loop never runs.

### Everything fits

```text
W = 10, val = [10, 15, 40], wt = [1, 2, 3]  ->  65
```

Total weight `6 <= 10`, so the answer is the sum of all values. The DP does not special-case it; each item's take branch simply always wins.

### Single item, exactly the capacity

```text
W = 3, val = [7], wt = [3]  ->  7
```

The boundary `w >= wt[i]` is inclusive, so `w = 3` is visited and `dp[3] = 7 + dp[0]`. An off-by-one `w > wt[i]` here returns `0`.

### Identical items

```text
W = 4, val = [5, 5], wt = [2, 2]  ->  10
W = 3, val = [5, 5], wt = [2, 2]  ->  5
```

Two copies listed separately are two distinct items, so both can go in when there is room. "At most once" is per index, not per value.

### The greedy trap

```text
W = 5, val = [10, 15, 40], wt = [1, 2, 3]  ->  55   (greedy by ratio gives 50)
```

The main example. Any solution that sorts by value/weight and grabs the best ratio first is wrong for 0/1 - it is only correct for fractional knapsack.

### The forward-loop trap

```text
W = 5, val = [10, 15, 40], wt = [1, 2, 3]  ->  forwards gives 60
```

Looping `w` upwards in the 1D version reuses items and returns `60` (item 2 plus item 0 twice). That is the unbounded answer. If your 1D knapsack ever beats the 2D one on the same input, check the loop direction first.

=== takeaway ===
> When you see **items used at most once** under a **budget**, think **`dp[i][w]` = best with the first `i` items and budget `w`** - then collapse to one row and loop the budget **backwards**.

### The core observation

The best you can do with the remaining items depends only on *which items remain* and *how much room is left* - not on how you got there. That makes the subproblem a pair `(i, w)`, of which there are only `n * W`, so `2^n` paths collapse into a table. Each cell is one choice: skip (straight down) or take (down and back by the item's weight).

### The pattern trigger

```text
     each item: in or out, at most once
                     |
                     v
       state = (items considered, budget left)
                     |
                     v
   dp[i][w] = max( dp[i-1][w],  val + dp[i-1][w - wt] )
                     |
                     v
       one row only? loop w from W DOWN to wt
                     |
          forwards = item reusable = unbounded knapsack
```

### The common mistakes

**Looping capacity forwards in the 1D version.** It silently turns 0/1 into unbounded knapsack. Small tests often still pass (on many inputs the unbounded optimum happens to coincide), which is what makes it dangerous.

**Reaching for greedy.** Sorting by value/weight is right for *fractional* knapsack and wrong here. The example above is a three-item counterexample - memorise that one.

**Forgetting capacity `0` is a state.** `new int[W]` instead of `new int[W + 1]` throws on `dp[W]`.

### What to remember in six months

> Forwards = unlimited copies. Backwards = one copy. The loop direction *is* the problem statement.
