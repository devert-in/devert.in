=== intro ===
Yesterday (Kth Smallest in a BST) the tree's **ordering** did the work: inorder of a BST is sorted, so you just counted. Today the ordering is gone. This is a plain binary tree, values in no particular arrangement, and the only thing you can lean on is the **shape**.

> When the answer at a node depends on what its subtrees found, let the recursion *report upward*. Do the children's work first, then decide at the parent. That is postorder, and it turns "search twice and compare" into a single walk.

=== problem ===
Given the `root` of a binary tree and two nodes `p` and `q` that are both in it, return their **lowest common ancestor** (LCA): the deepest node that has both `p` and `q` in its subtree.

One definition detail matters more than any other: **a node counts as an ancestor of itself.** So if `p` sits above `q`, the answer is `p`.

### The tree used all day

```text
               3
             /   \
            5     1
           / \   / \
          6   2 0   8
             / \
            7   4

level order: [3, 5, 1, 6, 2, 0, 8, null, null, 7, 4]
```

### Worked examples

| p | q | LCA | why |
| -: | -: | --: | :-- |
| 5 | 1 | 3 | they sit in different subtrees of the root |
| 5 | 4 | 5 | `5` is above `4`, and a node is its own ancestor |
| 6 | 4 | 5 | `6` is left of `5`, `4` is deep on the right of `5` |
| 7 | 8 | 3 | the only node above both is the root |

The example we dry-run in every section below is **`p = 6`, `q = 4`, answer `5`**. It is the interesting one: the two nodes are at different depths, and the split happens one level below the root, not at it.

### What the constraints give you

- `2 <= n <= 10^5`, all values unique.
- `p != q`, and **both are guaranteed to exist** in the tree.

That last guarantee is load-bearing. The optimal solution stops searching the moment it hits `p` or `q`, and it is only correct because the problem promises the other one is somewhere. Remember this - it comes back in the edge cases.

### Why it is not trivial

There is no ordering to steer by. In a BST you could compare values and know to go left or right (that is LC 235). Here, `p` could be anywhere, so you cannot know which subtree to enter without looking into it. Any solution has to discover where `p` and `q` are, and the question is how much it has to remember while doing so.

=== pattern ===
**DFS, postorder - information flows up.**

Ask what a node needs to know to decide "am I the LCA?":

- Is `p` or `q` somewhere in my **left** subtree?
- Is `p` or `q` somewhere in my **right** subtree?
- Am **I** `p` or `q`?

None of that is visible from the node itself. It is all facts about the subtrees, so the subtrees must be solved **first** and report back. That is exactly postorder (left, right, then the node).

### The return-value contract

The whole solution rests on one sentence describing what the recursive call returns:

> `lca(node)` returns `p` or `q` if it found one of them in this subtree, the LCA if it found both, and `null` if it found neither.

With that contract, the decision at a node is three cases:

```text
left result    right result    this node returns
-----------    ------------    -----------------------------------------
  non-null       non-null      itself   (p and q split here - this is the LCA)
  non-null       null          left     (pass the finding upward)
  null           non-null      right    (pass the finding upward)
  null           null          null     (nothing down here)
```

The first row is the moment of truth. If one target came up from the left and the other from the right, no deeper node can have both - so this node is the lowest one that does.

### Recognising it

Reach for "postorder with a meaningful return value" when:

- the answer at a node depends on facts about **both** subtrees
- you are tempted to search the tree several times from the top
- the question is about a relationship between nodes (ancestor, distance, path through a node)

The mental question:

> If each child could hand me one value summarising its whole subtree, what value would let me decide here?

Height (1 + max of children), diameter, balanced-check and LCA all answer that question with a different value.

=== bruteForce ===
Pretend we do not know any recursion trick yet. What is the most direct definition?

The ancestors of a node are exactly the nodes on the path from the root down to it. So:

1. Find the root-to-`p` path.
2. Find the root-to-`q` path.
3. Both start at the root. Walk them together; the **last node they share** is the LCA.

Finding a path is a DFS with backtracking: push the node, search below it, and pop it again if the target was not found down there.

### Dry run - path to `p = 6`

| step | node | action | path after | found? |
| -: | -: | :----- | :--------- | :----- |
| 1 | 3 | push, not target | `[3]` | no |
| 2 | 5 | push, not target | `[3, 5]` | no |
| 3 | 6 | push, **is target** | `[3, 5, 6]` | yes |

Three visits. Found on the first branch tried.

### Dry run - path to `q = 4`

| step | node | action | path after | found? |
| -: | ---: | :----- | :--------- | :----- |
| 1 | 3 | push, not target | `[3]` | no |
| 2 | 5 | push, not target | `[3, 5]` | no |
| 3 | 6 | push, not target | `[3, 5, 6]` | no |
| 4 | 6 | both children null, pop | `[3, 5]` | no |
| 5 | 2 | push, not target | `[3, 5, 2]` | no |
| 6 | 7 | push, not target | `[3, 5, 2, 7]` | no |
| 7 | 7 | both children null, pop | `[3, 5, 2]` | no |
| 8 | 4 | push, **is target** | `[3, 5, 2, 4]` | yes |

Notice steps 1-3: this second search walks `3 -> 5 -> 6` **again**, the exact nodes the first search already visited.

### Dry run - compare the two paths

```text
pathP = [3, 5, 6]
pathQ = [3, 5, 2, 4]
```

| i | pathP[i] | pathQ[i] | same? | lca after |
| -: | -------: | -------: | :---- | --------: |
| - | - | - | start | null |
| 0 | 3 | 3 | yes | 3 |
| 1 | 5 | 5 | yes | 5 |
| 2 | 6 | 2 | **no** - stop | 5 |

Answer `5`. Correct.

### Java

```java
class Solution {
    public TreeNode lowestCommonAncestor(TreeNode root, TreeNode p, TreeNode q) {

        List<TreeNode> pathP = new ArrayList<>();
        List<TreeNode> pathQ = new ArrayList<>();
        findPath(root, p, pathP);
        findPath(root, q, pathQ);

        // Walk both paths together; the last shared node is the LCA.
        TreeNode lca = null;
        for (int i = 0; i < pathP.size() && i < pathQ.size(); i++) {
            if (pathP.get(i) != pathQ.get(i)) {
                break;
            }
            lca = pathP.get(i);
        }
        return lca;
    }

    // Fills `path` with root..target and returns true, or leaves it unchanged and returns false.
    private boolean findPath(TreeNode node, TreeNode target, List<TreeNode> path) {
        if (node == null) {
            return false;
        }
        path.add(node);
        if (node == target) {
            return true;
        }
        if (findPath(node.left, target, path) || findPath(node.right, target, path)) {
            return true;
        }
        path.remove(path.size() - 1);   // dead end: backtrack
        return false;
    }
}
```

### Complexity

**Time:** `O(n)` - **Space:** `O(h)` for each stored path plus `O(h)` recursion, which is `O(n)` on a skewed tree.

### Where it hurts

Be honest about this one: the brute force is **already linear**. Two DFS walks of at most `n` nodes each is `2n`, which is `O(n)`. There is no quadratic blow-up to remove.

The waste is elsewhere, and the dry run shows it:

- **The second search repeats the first.** Steps 1-3 of the `q` search re-walk `3 -> 5 -> 6`. In the worst case (both targets deep on the same side) the two walks overlap almost completely.
- **Two explicit lists of nodes** are built only to be compared once and thrown away.
- **The comparison is a third pass** over information the DFS already had at the time it was standing on each node.

Look at step 3 of the comparison: the paths diverge at depth 2, below node `5`. Node `5` was the place where "the `p` side" and "the `q` side" split. The DFS stood on node `5` during both searches. If, while standing there, it had known "`p` is below me on the left, `q` is below me on the right", it could have answered on the spot.

So the question is:

> Can a single DFS find out, at each node, whether `p` and `q` are below it - and answer the moment they turn out to be on different sides?

=== optimization ===
### The key observation

A node is the LCA exactly when **one target is reachable through one child and the other target through the other child** - or when the node **is** one target and the other is below it.

Both conditions are about what the subtrees contain. So instead of returning a path, let each call return a single node summarising its subtree (the contract from the pattern section):

- `null` - neither target is down here
- `p` or `q` - exactly that one is down here
- some node `x` - both are down here, and `x` is their LCA

### The early return, and why it is safe

When the DFS lands on `p` (or `q`), it returns immediately **without searching below it**. That looks like a bug: what if the other target is underneath?

It is fine, because of the guarantee. If `q` is below `p`, then `p` is the LCA (a node is its own ancestor). The other subtree of every ancestor of `p` will report `null` - `q` is not there, it is under `p` - so `p` gets passed all the way to the top unchanged. And if `q` is *not* below `p`, it is somewhere else and will be found by another branch. Either way, looking under `p` is wasted effort.

### Deriving the rules

1. `node == null` - return `null`.
2. `node == p` or `node == q` - return `node`.
3. Recurse left, recurse right.
4. Both non-null - return `node` (the split happens here).
5. Otherwise return whichever is non-null (or `null`).

### Dry run on the same example

`p = 6`, `q = 4`. Rows are in the order calls **finish** (postorder), since that is when each one decides what to return.

| step | node | base case? | left returned | right returned | rule | returns |
| -: | -: | :--------- | :------------ | :------------- | :--- | :------ |
| 1 | 6 | **is p** | - | - | stop, do not look below | `6` |
| 2 | 7 | no | null | null | neither side | `null` |
| 3 | 4 | **is q** | - | - | stop | `4` |
| 4 | 2 | no | `null` (from 7) | `4` | one side | `4` |
| 5 | 5 | no | `6` | `4` | **both sides** | **`5`** |
| 6 | 0 | no | null | null | neither side | `null` |
| 7 | 8 | no | null | null | neither side | `null` |
| 8 | 1 | no | `null` (from 0) | `null` (from 8) | neither side | `null` |
| 9 | 3 | no | `5` | `null` (from 1) | one side | `5` |

The root returns `5`. Correct.

### Reading the table

- **Step 5 is the answer being born.** `6` arrived from the left, `4` from the right. Node `5` returns itself.
- **Step 9 is the answer being carried.** The root sees `5` from the left and `null` from the right. It does not know or care that `5` is an LCA rather than a raw target - it just passes up the one non-null result. That is why the same rule serves both purposes.
- **Step 4 is a target being carried.** Node `2` is not the answer; it just forwards `4` toward the node that will pair it with `6`.

Compare with the brute force: one walk instead of two, no lists, no comparison pass. Every node is visited at most once and the decision is made while the DFS is already standing there.

=== complexity ===
### Time

Each node is visited at most once, and each visit does constant work (two comparisons plus combining two results).

```text
O(n)
```

### Space

No auxiliary data structures. The only memory is the recursion stack, as deep as the tree is tall.

```text
O(h)   -  O(log n) for a balanced tree, O(n) for a skewed (linked-list-shaped) one
```

### Comparison

| Approach | Time | Extra space | Passes |
| :------- | ---: | ----------: | -----: |
| Two root-to-node paths, then compare | `O(n)` | `O(h)` paths + `O(h)` stack | 3 |
| Parent map + ancestor set (iterative) | `O(n)` | `O(n)` | 2 |
| Postorder with return value | **`O(n)`** | **`O(h)` stack only** | **1** |

The asymptotic time is the same for all three. What the recursive version wins is **one pass and no stored structures**. In an interview, say that plainly: "the path approach is already linear; this removes the second traversal and the lists." Claiming a big-O improvement that does not exist costs more credibility than it earns.

=== implementation ===
```java
// TreeNode (val, left, right) is provided by LeetCode.
class Solution {
    public TreeNode lowestCommonAncestor(TreeNode root, TreeNode p, TreeNode q) {

        // Empty subtree, or we are standing on one of the targets.
        if (root == null || root == p || root == q) {
            return root;
        }

        TreeNode left = lowestCommonAncestor(root.left, p, q);
        TreeNode right = lowestCommonAncestor(root.right, p, q);

        // One target came up each side: they split here.
        if (left != null && right != null) {
            return root;
        }

        // Pass up whatever was found (or null if nothing was).
        return left != null ? left : right;
    }
}
```

### The lines that matter

**1.**

```java
if (root == null || root == p || root == q) {
    return root;
}
```

Two base cases folded into one line. Returning `root` covers both: when `root` is `null` it returns `null`, and when it is a target it returns that target. This is also the line that makes "a node is its own ancestor" work without any special code.

**2.**

```java
if (left != null && right != null) {
    return root;
}
```

The only place a node returns **itself** without being a target. Both sides found something, so this is the lowest point where the two meet. This can be true at exactly one node in the tree.

**3.**

```java
return left != null ? left : right;
```

Forwarding. If only the left found something, pass it up; otherwise pass up the right (which may itself be `null`). The parent cannot tell whether it received a raw target or an already-computed LCA, and it does not need to.

### Comparing nodes, not values

`root == p` compares **references**. That is correct here: `p` and `q` are node objects from this tree. Comparing `root.val == p.val` also works on LeetCode because values are unique, but reference comparison states what you actually mean and keeps working if a variant allows duplicate values.

### The iterative version, for very deep trees

`n` can be `10^5`, and a tree that is one long chain makes the recursion `10^5` frames deep. LeetCode's judge handles this, but a default JVM thread stack in your own code may throw `StackOverflowError` at that depth. The fallback records every node's parent with an explicit stack, then walks up from `p` and `q`:

```java
class Solution {
    public TreeNode lowestCommonAncestor(TreeNode root, TreeNode p, TreeNode q) {

        // Record each node's parent until both targets have been seen.
        Map<TreeNode, TreeNode> parent = new HashMap<>();
        Deque<TreeNode> stack = new ArrayDeque<>();
        parent.put(root, null);
        stack.push(root);
        while (!parent.containsKey(p) || !parent.containsKey(q)) {
            TreeNode node = stack.pop();
            if (node.left != null) {
                parent.put(node.left, node);
                stack.push(node.left);
            }
            if (node.right != null) {
                parent.put(node.right, node);
                stack.push(node.right);
            }
        }

        // Every ancestor of p, including p itself.
        Set<TreeNode> ancestors = new HashSet<>();
        for (TreeNode a = p; a != null; a = parent.get(a)) {
            ancestors.add(a);
        }

        // The first ancestor of q that is also an ancestor of p.
        TreeNode b = q;
        while (!ancestors.contains(b)) {
            b = parent.get(b);
        }
        return b;
    }
}
```

`O(n)` time, `O(n)` space, no recursion. The `while` stops as soon as both targets have parents recorded, so it often does not walk the whole tree.

### Java notes

- `TreeNode` is supplied by LeetCode. Do not declare it in your submission - a second `class TreeNode` is a compile error.
- `HashMap<TreeNode, TreeNode>` works with object identity because `TreeNode` does not override `equals`/`hashCode`. That is exactly what we want: two different nodes are different keys even if their values matched.
- `ArrayDeque` is the right stack in Java; the legacy `Stack` class is synchronized and slower.

=== edgeCases ===
All on the tree from the problem section unless stated.

### One target is the ancestor of the other

```text
p = 5, q = 4  ->  5
```

The DFS reaches `5` first and returns it without looking below. The root's right side returns `null`, so `5` travels to the top. The early return is exactly right here.

### One target is the root

```text
p = 3, q = 8  ->  3
```

The very first call hits the base case and returns the root. Zero further work.

### Siblings

```text
p = 7, q = 4  ->  2
```

Both are children of `2`. Node `2` receives `7` from the left and `4` from the right and returns itself.

### Opposite sides of the root

```text
p = 5, q = 1  ->  3
```

The split happens at the very top. The root receives `5` and `1`.

### Deep leaves far apart

```text
p = 7, q = 8  ->  3
```

`7` is four levels down on the left, `8` is three levels down on the right. Their only common ancestor is the root. Different depths do not matter - the algorithm never compares depths.

### Two-node tree

```text
root = [1, 2],  p = 1, q = 2  ->  1
root = [1, 2],  p = 2, q = 1  ->  1
```

The smallest input the constraints allow. The order of `p` and `q` never matters.

### Skewed tree (a chain)

```text
1 -> 2 -> 3 -> 4 -> 5   (each node is the right child of the previous)
p = 3, q = 5  ->  3
```

The recursion goes `1, 2, 3` and stops at `3`. Height equals `n` here, so the stack space is `O(n)`; at `n = 10^5` prefer the iterative version outside LeetCode.

### The guarantee you must not lose

If a variant does **not** promise both nodes exist (LC 1644), the early return becomes a bug: with `p = 5` and a `q` that is not in the tree, the function still returns `5`, which is wrong - the answer should be `null`. The fix is to search the whole tree and count how many targets were actually seen. On LC 236 the guarantee holds, so the short version is correct.

=== takeaway ===
> When you see **"lowest common ancestor"**, or any question whose answer at a node depends on **what both subtrees contain**, think **postorder DFS with a return value**: let the children report, decide at the parent.

### The core observation

The LCA is the first node, walking up, where the two targets arrive from **different directions** (or the node that is itself a target). Each subtree can summarise itself in one returned node - `null`, a target, or a finished answer - and the parent combines the two summaries with three rules.

### The pattern trigger

```text
             lca(node)
                 |
     null or p or q?  --yes-->  return node
                 |
                 no
                 v
     L = lca(left)      R = lca(right)
                 |
      L and R both non-null?  --yes-->  return node   (split here)
                 |
                 no
                 v
         return L if non-null, else R    (forward the finding)
```

### The common mistakes

**Thinking the early return skips something.** Returning at `p` without exploring below is correct *because* both nodes are guaranteed to exist. Drop that guarantee and it is wrong.

**Comparing values in a tree that allows duplicates.** Use `root == p`. It says what you mean.

**Using the BST shortcut on a plain binary tree.** "If both are smaller go left" only works when values are ordered (LC 235). On LC 236 it returns nonsense.

**Claiming the recursion beats the path approach in big-O.** Both are `O(n)`. The recursion wins on passes and memory, not on order of growth.

### What to remember in six months

> Decide what one value each subtree should hand back. Once the return contract is right, the code is five lines.

The same move solves Maximum Depth (return height), Diameter (return height, track the best `L + R`), Balanced Binary Tree (return height or `-1`), Binary Tree Maximum Path Sum (return best downward path, track the best bend), and LCA of a BST (LC 235), where the values let you skip the search entirely.

The direct approach: find the root-to-p path, find the root-to-q path, and take the last node they share. It works, and it is already O(n) - but it walks the top of the tree twice and builds two lists only to compare them once.

```

one side non-null    ->  pass it up
```

One postorder walk, no lists, no comparison pass.

Pattern: DFS (postorder, return value)
Time: `O(n)`
Space: `O(h)`

The line that looks like a bug and is not: returning as soon as you hit p, without searching below it. If q is underneath, p is the answer anyway - a node is its own ancestor. That shortcut is only valid because both nodes are guaranteed to exist.
