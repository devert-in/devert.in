=== intro ===
Yesterday's stack held **values**, and a map turned each value into its answer. Today the answer is not a value but a **distance** - and that one change forces the stack to hold something else.

> If the answer needs to know *where* something was, store the index, not the value. An index gives you the value back for free (`arr[i]`); a value can never give you its index back.

=== problem ===
Given daily temperatures, return an array where `answer[i]` is **how many days you have to wait after day `i`** for a warmer temperature. If no warmer day ever comes, `answer[i] = 0`.

```text
temperatures = [73, 74, 75, 71, 69, 72, 76, 73]
answer       = [ 1,  1,  4,  2,  1,  1,  0,  0]
```

Check two entries:

```text
day 2 (75): days 3, 4, 5 are 71, 69, 72 - all colder. Day 6 is 76. Wait = 6 - 2 = 4.
day 6 (76): only day 7 (73) follows, and it is colder. Never warmer: 0.
```

This is yesterday's "next greater element" with two twists:

1. The output is the **gap in days** (`j - i`), not the warmer temperature itself.
2. Temperatures **repeat**. A day of `70` followed by another `70` is not "warmer" - you keep waiting.

### The constraints that matter

| Constraint | Why it matters |
| :--------- | :------------- |
| `1 <= n <= 10^5` | `O(n^2)` is up to `5 * 10^9` comparisons in the worst case - too slow. Needs `O(n)`. |
| `30 <= temperature <= 100` | Only 71 distinct values. That enables a different trick (see Complexity), but the stack does not need it. |
| Duplicates allowed | A `value -> answer` map, like yesterday's, is now ambiguous. Two days of `73` have different answers. |
| "Warmer" means strictly greater | Equal temperatures do not end the wait. `>` not `>=`. |

The example is LeetCode's own, and it is a good one: day 5's `72` settles two waiting days at once, and day 6's `76` settles two more, including one that has waited four days.

=== pattern ===
**Monotonic stack - of indices.**

Same waiting-room idea as yesterday. Walk the days in order; every day joins a stack of days **still waiting** for something warmer. When a warmer day arrives, it settles every waiting day colder than itself.

The waiting days always have **non-increasing temperatures** from bottom to top. If a warmer day sat above a colder one, the warmer day would have settled the colder one when it arrived, so the colder one would not still be waiting. So a newcomer settles a run at the top, and stops at the first waiting day that is at least as warm.

What changes is **what the stack stores**. To write `answer[prev] = i - prev`, you need `prev` - the waiting day's **position**. So push indices, and read the temperature through them:

```text
stack holds:   [2, 3, 4]               <- days still waiting
meaning:       [75, 71, 69]            <- temperatures[2], [3], [4]
```

The index is strictly more information than the value. Yesterday we got away with values only because they were distinct and a map could stand in for positions.

### Recognising it

- "how many steps until the next bigger / smaller" - next greater, measured as a distance
- "for each element, the nearest element to the right with property P"
- anything where the answer is a **width** or **gap** between two positions

The mental question:

> Does the answer depend on where the settling element is, not just what it is?

If yes, the stack holds indices.

=== bruteForce ===
For each day, walk forward until you find a warmer one.

### Step logic

1. For each day `i`, start `j` at `i + 1`.
2. Advance `j` while `temperatures[j] <= temperatures[i]`.
3. If `j` found a warmer day, `answer[i] = j - i`; otherwise leave `0`.

### Dry run

```text
temperatures = [73, 74, 75, 71, 69, 72, 76, 73]
index           0   1   2   3   4   5   6   7
```

| i | temp[i] | `j` checked (temp) | warmer found at | answer[i] | comparisons |
| -: | ------: | :----------------- | --------------: | --------: | ----------: |
| 0 | 73 | 1 (74) | 1 | 1 - 0 = **1** | 1 |
| 1 | 74 | 2 (75) | 2 | 2 - 1 = **1** | 1 |
| 2 | 75 | 3 (71), 4 (69), 5 (72), 6 (76) | 6 | 6 - 2 = **4** | 4 |
| 3 | 71 | 4 (69), 5 (72) | 5 | 5 - 3 = **2** | 2 |
| 4 | 69 | 5 (72) | 5 | 5 - 4 = **1** | 1 |
| 5 | 72 | 6 (76) | 6 | 6 - 5 = **1** | 1 |
| 6 | 76 | 7 (73) | none | **0** | 1 |
| 7 | 73 | (nothing to the right) | none | **0** | 0 |

```text
answer = [1, 1, 4, 2, 1, 1, 0, 0]
```

Correct, in 11 comparisons.

### Java

```java
class Solution {
    public int[] dailyTemperatures(int[] temperatures) {

        int n = temperatures.length;
        int[] answer = new int[n];

        for (int i = 0; i < n; i++) {
            for (int j = i + 1; j < n; j++) {
                if (temperatures[j] > temperatures[i]) {
                    answer[i] = j - i;
                    break;
                }
            }
            // no warmer day found: answer[i] stays 0
        }

        return answer;
    }
}
```

### Complexity

**Time:** `O(n^2)` - **Space:** `O(1)` extra

### Where it hurts

Row 2's scan walked over days 3, 4 and 5 and learned only "colder than 75". Then rows 3 and 4 walked over days 4 and 5 **again**. The answers for days 3 and 4 - "day 5 is warmer" - were sitting right there during row 2's scan and got thrown away.

The worst case is a long cooling streak:

```text
[100, 99, 98, 97, ..., 31, 30]

day 0 scans n-1 days, day 1 scans n-2, ...    total n(n-1)/2
```

At `n = 10^5` that is about `5 * 10^9` comparisons, every one finding nothing. A warm day at the very end is no better: every day scans all the way to it.

The waste is the same as yesterday's. A day that arrives late is the answer to a whole run of earlier days, but each of those days discovers it separately.

=== optimization ===
### The key observation

Turn it around. Day `i` does not need to search forward for its warmer day - when day `i` **arrives**, it can look back at every day still waiting and settle the ones it is warmer than. It knows both positions at that moment, so the distance is just `i - prev`.

Because the waiting days are in non-increasing temperature order, the ones day `i` settles are a run at the top of the stack.

### The algorithm

1. `answer` starts all zeros - which is already correct for any day that never gets settled.
2. For each day `i`:
   - while the stack is non-empty and `temperatures[i] > temperatures[top]`: pop `prev`, set `answer[prev] = i - prev`.
   - push `i`.
3. Days left on the stack never found a warmer day; their `0` stays.

=== complexity ===
### Time

Every index is pushed exactly once and popped at most once, so the `while` loop runs at most `n` times **in total** across all iterations.

```text
O(n)
```

### Space

The stack holds at most `n` indices - a strictly cooling streak keeps them all. The `answer` array is the required output.

```text
O(n) extra
```

### Comparison

| Approach | Time | Extra space | Worst input |
| :------- | ---: | ----------: | :---------- |
| Scan forward per day | `O(n^2)` | `O(1)` | long cooling streak |
| Backwards with "next index of each temperature" (`30..100`) | `O(n * 71)` | `O(71)` | none, but relies on the value range |
| Monotonic stack of indices | **`O(n)`** | `O(n)` | none |
| Backwards, jumping along `answer[]` | **`O(n)`** amortised | **`O(1)`** | none |

The second row uses the small temperature range: walk right to left, remember the latest index where each temperature from `30` to `100` appeared, and for each day take the minimum over warmer temperatures. It is fine here and useless if the range were `10^9`. The stack does not care about the range at all.

=== implementation ===
```java
class Solution {
    public int[] dailyTemperatures(int[] temperatures) {

        int n = temperatures.length;
        int[] answer = new int[n];                    // 0 already means "no warmer day"
        Deque<Integer> stack = new ArrayDeque<>();    // INDICES of days still waiting

        for (int i = 0; i < n; i++) {
            // Day i settles every waiting day that is strictly colder.
            while (!stack.isEmpty() && temperatures[i] > temperatures[stack.peek()]) {
                int prev = stack.pop();
                answer[prev] = i - prev;
            }
            stack.push(i);
        }

        return answer;
    }
}
```

### The lines that matter

**1.**

```java
Deque<Integer> stack = new ArrayDeque<>();    // INDICES of days still waiting
```

Indices, because the answer is a distance. The temperature is always one lookup away as `temperatures[stack.peek()]`; a stored temperature could never tell you which day it came from - especially with duplicates.

**2.**

```java
while (!stack.isEmpty() && temperatures[i] > temperatures[stack.peek()]) {
```

Strictly greater. With `>=`, a day of `70` would be "settled" by the next `70`, which is not warmer. `[70, 70, 71]` would wrongly give `[1, 1, 0]` instead of `[2, 1, 0]`.

**3.**

```java
answer[prev] = i - prev;
```

The settling day's index minus the waiting day's index. This line is why indices are on the stack.

### The O(1)-space variant, for the follow-up

Walk right to left. For day `i`, start at `j = i + 1`; if day `j` is not warmer, **jump** to `j`'s own warmer day using the already-computed `answer[j]`, instead of stepping one day at a time.

```java
class Solution {
    public int[] dailyTemperatures(int[] temperatures) {

        int n = temperatures.length;
        int[] answer = new int[n];
        int hottest = 0;

        for (int i = n - 1; i >= 0; i--) {
            if (temperatures[i] >= hottest) {
                hottest = temperatures[i];   // nothing to the right is warmer: answer stays 0
                continue;
            }
            int j = i + 1;
            while (temperatures[j] <= temperatures[i]) {
                j += answer[j];              // skip straight to j's next warmer day
            }
            answer[i] = j - i;
        }

        return answer;
    }
}
```

The `hottest` check guarantees a warmer day exists, so every jump lands somewhere (a day colder than `hottest` always has `answer[j] > 0`). The `answer` array plays the role the stack played.

### Java notes

- `new int[n]` is zero-filled, and `0` is exactly the "never warmer" answer. No cleanup pass over leftover stack entries is needed.
- `temperatures[stack.peek()]` unboxes the `Integer` index; that is fine. Never compare two `Integer` objects with `==`.
- On LeetCode, a plain `int[] stack` with a `top` counter beats `ArrayDeque<Integer>` by avoiding boxing. Same algorithm; mention it if asked about constant factors.

=== edgeCases ===
### Single day

```text
[50]  ->  [0]
```

Pushed, never popped, stays `0`.

### Strictly increasing

```text
[30, 40, 50, 60]  ->  [1, 1, 1, 0]
```

Every day is settled by the very next one. The stack never holds more than one index. (LeetCode's example 2.)

### Strictly decreasing

```text
[60, 50, 40, 30]  ->  [0, 0, 0, 0]
```

Nothing is ever popped. The stack grows to all four indices, and every answer is the default `0`.

### All equal

```text
[70, 70, 70]  ->  [0, 0, 0]
```

Equal is not warmer. Strict `>` keeps every day waiting.

### Equal, then warmer

```text
[70, 70, 71]  ->  [2, 1, 0]
```

Both `70`s wait together on the stack and are settled by the same `71` at different distances. The `>=` bug gives `[1, 1, 0]`.

### One warm day settles a long streak

```text
[50, 40, 30, 60]  ->  [3, 2, 1, 0]
```

`60` pops three indices in one step, each with its own distance.

### Warmer day far away

```text
[30, 60, 90]  ->  [1, 1, 0]
```

LeetCode's example 3. Also check `[71, 70, 70, 70, 72]  ->  [4, 3, 2, 1, 0]`: day 0 waits four days, and the three equal days between are all settled together by `72`.

=== takeaway ===
> When you see **"how many days / steps until the next bigger (or smaller)"**, think **monotonic stack of indices**. The newcomer settles everyone it beats, and the distance is `i - prev`.

### The core observation

A late, warm day is the answer to a whole run of earlier days. Let it settle them all when it arrives, rather than have each of them find it separately. Storing indices on the stack is what lets the settling day compute each distance on the spot.

### The pattern trigger

```text
      for i = 0 .. n-1
               |
               v
  while stack not empty AND a[i] > a[stack.top]:
         prev = pop()
         answer[prev] = i - prev      <- distance needs the INDEX
               |
               v
          push(i)
               |
               v
  indices left on the stack keep the default answer
```

### The common mistakes

**Pushing values.** You can find out a value was settled but not how far away it was - and with duplicates you cannot even tell which day it was.

**`>=` instead of `>`.** Equal temperatures end the wait early. Read "warmer" as strictly greater.

**Computing `i - prev` the wrong way round.** The later day is `i`; the answer is positive.

### What to remember in six months

> Values answer "what is the next greater?"; indices answer "how far is it?" and "what lies between?". When in doubt, push the index - it carries both.
