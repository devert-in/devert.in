=== intro ===
Yesterday one min-heap held the frontier of `k` lists. Today needs **two** heaps, facing each other, because the question is no longer "what is the smallest?" but "what is in the middle?" - and the middle is the meeting point of two halves.

> When a value is defined by a **split** of the data - the middle, the top half, the bottom quarter - keep each side in its own heap and keep the sizes balanced. The answer then sits on the tops, where a heap can hand it to you in `O(1)`.

=== problem ===
Design a class that receives numbers one at a time and can report the **median** of everything seen so far at any moment.

- `addNum(int num)` - add a number from the stream.
- `findMedian()` - return the median of all numbers added so far.

The median is the middle value of the sorted data. With an even count there is no single middle, so it is the **average of the two middle values**.

```text
addNum(1)      data = [1]
addNum(2)      data = [1, 2]
findMedian()   -> (1 + 2) / 2 = 1.5
addNum(3)      data = [1, 2, 3]
findMedian()   -> 2.0
```

### A longer stream we will use for both dry runs

| after adding | sorted data so far | count | median |
| -----------: | :----------------- | ----: | -----: |
| 5 | `[5]` | 1 | 5.0 |
| 15 | `[5, 15]` | 2 | 10.0 |
| 1 | `[1, 5, 15]` | 3 | 5.0 |
| 3 | `[1, 3, 5, 15]` | 4 | 4.0 |
| 8 | `[1, 3, 5, 8, 15]` | 5 | 5.0 |

### Constraints that matter

- Values are in `[-10^5, 10^5]`.
- Up to `5 * 10^4` calls in total, and `findMedian` is only called after at least one `addNum`.
- `findMedian` returns a `double` - the answer can be a `.5`.

### What makes it non-trivial

The data arrives **unsorted** and **never stops**. Sorting once at the end is not an option - a median can be asked for after every single add. So the cost has to be split sensibly between `addNum` and `findMedian`, and neither should touch all `n` elements.

=== pattern ===
**Two Heaps.**

Sort the data in your head and cut it in the middle:

```text
           lower half          |        upper half
   1      3                    |     5      8      15
               largest = 3  <--+-->  smallest = 5
```

The median only ever depends on **two** values: the largest of the lower half and the smallest of the upper half. Everything else can sit in any order, as long as it stays on the correct side of the cut.

That is exactly what two heaps give us:

- `low` - a **max-heap** holding the lower half. Its top is the largest small number.
- `high` - a **min-heap** holding the upper half. Its top is the smallest large number.

Two invariants keep the tops meaningful:

1. **Order:** every value in `low` is `<=` every value in `high`.
2. **Balance:** `low.size() == high.size()` or `low.size() == high.size() + 1`.

With those in place, the median is `low.peek()` when the count is odd, and the average of the two tops when it is even.

### Recognising it

Reach for two heaps when:

- the answer is a **median** or a percentile of a changing collection
- you need "the boundary between the smaller half and the larger half"
- elements arrive over time and you must answer after each one

Later relatives: Sliding Window Median (LC 480), IPO (LC 502), and scheduling problems that balance two pools.

The mental question:

> Is the answer defined by where the data **splits**, rather than by its minimum or maximum?

=== bruteForce ===
Keep every number in a list that is always sorted. On `addNum`, walk to the first element greater than the new one and insert it there. On `findMedian`, read the middle.

### Step logic

1. `addNum(num)`: scan `i` forward while `sorted[i] <= num`, then `sorted.add(i, num)`. Every element after `i` shifts one slot right.
2. `findMedian()`: with `n` elements, return `sorted[n/2]` when `n` is odd, otherwise the average of `sorted[n/2 - 1]` and `sorted[n/2]`.

### Dry run

```text
stream = 5, 15, 1, 3, 8      (findMedian after every add)
```

| add | list before | insert index `i` | elements shifted | list after | `n` | median read from | median |
| --: | :---------- | ---------------: | ---------------: | :--------- | --: | :--------------- | -----: |
| 5 | `[]` | 0 | 0 | `[5]` | 1 | index 0 | 5.0 |
| 15 | `[5]` | 1 | 0 | `[5, 15]` | 2 | indices 0, 1 | (5 + 15) / 2 = 10.0 |
| 1 | `[5, 15]` | 0 | 2 | `[1, 5, 15]` | 3 | index 1 | 5.0 |
| 3 | `[1, 5, 15]` | 1 | 2 | `[1, 3, 5, 15]` | 4 | indices 1, 2 | (3 + 5) / 2 = 4.0 |
| 8 | `[1, 3, 5, 15]` | 3 | 1 | `[1, 3, 5, 8, 15]` | 5 | index 2 | 5.0 |

Every median matches the table in the problem section. `findMedian` is instant; all the cost is in `addNum`.

### Java

```java
class MedianFinder {

    private final List<Integer> sorted;

    public MedianFinder() {
        sorted = new ArrayList<>();
    }

    public void addNum(int num) {
        int i = 0;
        while (i < sorted.size() && sorted.get(i) <= num) {
            i++;
        }
        sorted.add(i, num);     // shifts everything after i one slot right
    }

    public double findMedian() {
        int n = sorted.size();
        if (n % 2 == 1) {
            return sorted.get(n / 2);
        }
        return ((double) sorted.get(n / 2 - 1) + sorted.get(n / 2)) / 2.0;
    }
}
```

### Complexity

**Time:** `O(n)` per `addNum`, `O(1)` per `findMedian` - **Space:** `O(n)`

### Where it hurts

Look at the "elements shifted" column and the scan that precedes it. To place one number, the list does up to `n` comparisons to find the slot and up to `n` moves to open it. Replacing the scan with binary search fixes the comparisons (`O(log n)`) but not the moves - `ArrayList.add(i, x)` still shifts every later element.

Over `5 * 10^4` adds that is around `10^9` element moves in the worst case.

And what is all that work buying? A **fully sorted** list. But the median never reads more than two positions of it. We are paying to keep `[1, 3]` in order and `[8, 15]` in order, when all we ever need is "`3` is the biggest of the small ones" and "`5` is the smallest of the big ones". The waste is total order where only a split is needed.

=== optimization ===
### Name the repeated work

The sorted list maintains the exact position of every element. The median needs only the two values on either side of the middle.

### The key observation

If the data is split into a lower half and an upper half, the median depends only on **the max of the lower half** and **the min of the upper half**. A max-heap and a min-heap each give you that one value in `O(1)`, and accept a new element in `O(log n)` - without ever sorting the rest.

### How `addNum` keeps both invariants

A new number could belong on either side, and we do not want a special case for each. So route **every** number through both heaps:

1. `low.offer(num)` - put it in the lower half.
2. `high.offer(low.poll())` - send the lower half's largest value up. This guarantees the order invariant: whatever crosses over is `>=` everything left in `low`.
3. If `high` is now bigger than `low`, move `high`'s smallest back down: `low.offer(high.poll())`. This restores the balance invariant.

Three heap operations per add, each `O(log n)`.

### Dry run on the same stream

Heaps are shown as their contents with the **top first**. `low` is a max-heap, `high` is a min-heap.

| add | after `low.offer(num)` | moved up | after `high.offer(...)` | rebalance? | final `low` | final `high` | median |
| --: | :--------------------- | -------: | :---------------------- | :--------- | :---------- | :----------- | -----: |
| 5 | low `[5]` | 5 | low `[]`, high `[5]` | high 1 > low 0: move 5 down | `[5]` | `[]` | 5.0 (odd: low top) |
| 15 | low `[15, 5]` | 15 | low `[5]`, high `[15]` | 1 vs 1: no | `[5]` | `[15]` | (5 + 15) / 2 = 10.0 |
| 1 | low `[5, 1]` | 5 | low `[1]`, high `[5, 15]` | high 2 > low 1: move 5 down | `[5, 1]` | `[15]` | 5.0 (odd: low top) |
| 3 | low `[5, 3, 1]` | 5 | low `[3, 1]`, high `[5, 15]` | 2 vs 2: no | `[3, 1]` | `[5, 15]` | (3 + 5) / 2 = 4.0 |
| 8 | low `[8, 3, 1]` | 8 | low `[3, 1]`, high `[5, 8, 15]` | high 3 > low 2: move 5 down | `[5, 3, 1]` | `[8, 15]` | 5.0 (odd: low top) |

Same five medians as the brute force. Look at the last row: `8` went into `low`, was immediately recognised as the largest small number and sent up, and the push into `high` exposed `5` as the new smallest large number, which came back down to keep the halves balanced. Nobody sorted anything; each heap only knows its own top.

### Why route through `low` first

Without the "push then pass up" step you would need to compare `num` against both tops and decide which heap it belongs in - three branches, each with its own rebalance. Sending it through `low` and then forwarding `low`'s max is a branch-free way of asking "which side does this belong on?". It costs one extra heap operation and removes a whole class of bugs.

### Why `low` gets the extra element

With an odd count, one side must hold one more. Choosing `low` means the odd-count median is always `low.peek()`, so `findMedian` has exactly two cases. Either side works; picking one and sticking to it is what matters.

=== complexity ===
### Time

`addNum` does at most three heap operations on heaps of size about `n/2`. `findMedian` only peeks.

```text
addNum:     O(log n)
findMedian: O(1)
```

### Space

Every number lives in exactly one of the two heaps.

```text
O(n)
```

### Comparison

| Approach | `addNum` | `findMedian` | Space |
| :------- | -------: | -----------: | ----: |
| Unsorted list, sort on every query | `O(1)` | `O(n log n)` | `O(n)` |
| Sorted list, linear insert | `O(n)` | `O(1)` | `O(n)` |
| Sorted list, binary search + insert | `O(n)` (shift) | `O(1)` | `O(n)` |
| Two heaps | **`O(log n)`** | **`O(1)`** | `O(n)` |

A balanced BST (Java's `TreeMap` with counts) can also reach `O(log n)`, but tracking the middle element through it is fiddly. Two heaps is the standard answer because the invariants are simple to state and simple to check.

### The classic follow-ups

- **"All numbers are in `[0, 100]`."** Keep a `count[101]` array and a total. `addNum` is `O(1)`; `findMedian` walks at most 101 buckets - `O(1)` for a fixed range.
- **"99% of numbers are in `[0, 100]`."** Same buckets, plus a counter for values below `0` and above `100`. The median almost always falls inside the buckets; fall back to the outlier lists only when it does not.

=== implementation ===
```java
class MedianFinder {

    // Lower half: a MAX-heap, so its top is the largest small number.
    private final PriorityQueue<Integer> low;
    // Upper half: a MIN-heap, so its top is the smallest large number.
    private final PriorityQueue<Integer> high;

    public MedianFinder() {
        low = new PriorityQueue<>(Collections.reverseOrder());
        high = new PriorityQueue<>();
    }

    public void addNum(int num) {
        low.offer(num);                 // 1. enter through the lower half
        high.offer(low.poll());         // 2. its largest crosses to the upper half
        if (high.size() > low.size()) { // 3. keep low the same size or one bigger
            low.offer(high.poll());
        }
    }

    public double findMedian() {
        if (low.size() > high.size()) {
            return low.peek();          // odd count: the extra one is in low
        }
        return ((double) low.peek() + high.peek()) / 2.0;
    }
}
```

### The lines that matter

**1.**

```java
low = new PriorityQueue<>(Collections.reverseOrder());
```

Java's `PriorityQueue` is a **min-heap** by default. `Collections.reverseOrder()` flips it into a max-heap. Forgetting this gives you two min-heaps and a median that is silently wrong on most inputs.

**2.**

```java
low.offer(num);                 // 1. enter through the lower half
high.offer(low.poll());         // 2. its largest crosses to the upper half
```

The order invariant in two lines. After them, `num` has been compared against the lower half's maximum, and whatever is larger ended up on the upper side.

**3.**

```java
return ((double) low.peek() + high.peek()) / 2.0;
```

The cast happens **before** the addition. `low.peek() + high.peek()` on two `Integer`s is an `int` sum, which overflows if both values are near `Integer.MAX_VALUE`; casting one side to `double` first makes the whole sum a `double`. Dividing by `2.0` rather than `2` also avoids integer division, which would turn `1.5` into `1`.

### Java notes

- `PriorityQueue<Integer>` stores boxed `Integer`s. `low.peek()` auto-unboxes when it is returned as a `double` or added to one.
- Never compare two boxed `Integer`s with `==` - it compares references. Nothing here needs it, but it is the trap waiting in any variant that checks whether the tops are equal.
- `poll()` on an empty heap returns `null`. Step 2 is safe because step 1 just put something in `low`; step 3 is safe because it only runs when `high` is strictly larger, so it is non-empty.
- `findMedian` assumes at least one number has been added, as LeetCode guarantees. On an empty finder `low.peek()` is `null` and unboxing it throws.

=== edgeCases ===
### A single number

```text
addNum(7), findMedian()  ->  7.0
```

After the first add, `low = [7]`, `high = []`. The odd branch returns `low.peek()`.

### Two numbers - the first average

```text
addNum(1), addNum(2), findMedian()  ->  1.5
```

`low = [1]`, `high = [2]`. A result of `1.0` here means integer division somewhere.

### Duplicates

```text
2, 2, 2, findMedian()  ->  2.0
2, 2, 2, 2, findMedian()  ->  2.0
```

Equal values can sit on both sides of the cut without breaking the order invariant, because it is `<=`, not `<`.

### Negative numbers

```text
-1, -2, findMedian()  ->  -1.5
```

### Strictly increasing stream

```text
1, 2, 3, 4, 5  ->  medians 1.0, 1.5, 2.0, 2.5, 3.0
```

Every new number belongs in the upper half. It passes through `low`, is immediately forwarded up, and the rebalance pulls `high`'s smallest back down whenever `high` gets ahead.

### Strictly decreasing stream

```text
5, 4, 3, 2, 1  ->  medians 5.0, 4.5, 4.0, 3.5, 3.0
```

### Extremes of `int`

```text
2147483647, 2147483647, findMedian()  ->  2147483647.0
-2147483648, 2147483647, findMedian() ->  -0.5
```

Outside LeetCode's `10^5` bound, but this is what the `(double)` cast is for. Without it, the first case overflows to `-1.0`.

### Median asked between every add

The heaps are never rebuilt or sorted for a query, so interleaving `findMedian` after every `addNum` costs nothing extra - which is exactly the usage the problem is designed around.

=== takeaway ===
> When you see **"median" or "middle" of a growing collection**, think **two heaps**: a max-heap for the lower half, a min-heap for the upper half, sizes within one.

### The core observation

The median depends on only two values - the largest of the small half and the smallest of the large half. Keeping each half in a heap exposes exactly those two values in `O(1)`, and accepting a new number costs `O(log n)` instead of the `O(n)` it takes to keep everything sorted.

### The pattern trigger

```text
                 new number
                     |
                     v
          low.offer(num)          (max-heap, lower half)
                     |
                     v
          high.offer(low.poll())  (largest small number moves up)
                     |
                     v
          high bigger than low?
             /             \
           yes              no
            |                |
  low.offer(high.poll())    done
                     |
                     v
  median = low.peek()                      if odd
         = (low.peek() + high.peek()) / 2  if even
```

### The common mistakes

**Two min-heaps.** `new PriorityQueue<>()` twice. The code runs and returns plausible numbers that are wrong.

**Balancing by size alone.** "Push into whichever heap is smaller" keeps the sizes right and breaks the order invariant: stream `1, 2, 3` puts `1` low, `2` high, `3` low, and `low`'s top is now `3`, which is bigger than `high`'s `2`. Every number has to be checked against the cut before it lands. Routing through `low` and forwarding its max does that check for you; comparing against `low.peek()` and then rebalancing by moving tops also works, with more branches.

**Integer division.** `(a + b) / 2` returns `1` for `1` and `2`. Use `/ 2.0` and cast before adding.

**Letting the sizes drift by more than one.** Then neither top is the middle any more.

### What to remember in six months

> A median is a **cut**, not a sort. Two heaps hold the two sides of the cut, and the answer always lives on their tops.

The same idea - keep a boundary between two pools and expose only the edge of each - comes back in Sliding Window Median, where elements also have to leave, and in any problem that asks for a percentile on the fly.
