=== intro ===
Yesterday's Kth Largest kept the **k largest** values in a **min** heap. Today you keep the **k smallest** distances - so by the same reasoning the heap flips to a **max** heap. If yesterday's rule ("the heap points at the member who gets replaced") clicked, today is mostly about applying it to something that is not a plain integer.

> When the elements are objects (points, intervals, words) and the ranking comes from a computed key, the heap logic does not change at all. Only the comparator does.

=== problem ===
Given an array of points `points[i] = [x, y]` on the plane and an integer `k`, return the `k` points **closest to the origin** `(0, 0)`. Distance is Euclidean, `sqrt(x^2 + y^2)`. The answer may be returned in **any order**, and it is guaranteed to be unique apart from order.

### LeetCode's examples

```text
points = [[1, 3], [-2, 2]],           k = 1   ->  [[-2, 2]]
points = [[3, 3], [5, -1], [-2, 4]],  k = 2   ->  [[3, 3], [-2, 4]]
```

In the first, `[1, 3]` is `sqrt(10)` away and `[-2, 2]` is `sqrt(8)` away, so `[-2, 2]` wins.

### The example used all day

LeetCode's examples are too short to show the heap evicting anything interesting, so the dry runs use six points and `k = 3`:

| point | x | y | `x^2 + y^2` |
| :---- | -: | -: | ----------: |
| A | 1 | 3 | 10 |
| B | -2 | 2 | 8 |
| C | 5 | -1 | 26 |
| D | 3 | 3 | 18 |
| E | 0 | 1 | 1 |
| F | -2 | 4 | 20 |

The three smallest squared distances are `1, 8, 10`, so the answer is **E, B, A** = `[[0, 1], [-2, 2], [1, 3]]` in any order.

### No square roots needed

`sqrt` is increasing: if `a < b` then `sqrt(a) < sqrt(b)`. So comparing `x^2 + y^2` gives exactly the same order as comparing true distances. Skipping the square root keeps everything in exact integer arithmetic - no floating point, no rounding questions.

### Constraints

- `1 <= k <= points.length <= 10^4`
- `-10^4 <= x, y <= 10^4`

The largest squared distance is `10^8 + 10^8 = 2 * 10^8`, which fits in an `int` (max about `2.1 * 10^9`). No `long` needed.

=== pattern ===
**Max heap of size k**, keyed on squared distance.

This is yesterday's pattern mirrored. "k closest" means "k **smallest** distances". Keep the k closest seen so far; when a new point arrives, the member it might replace is the **farthest** of the kept ones. Peek farthest, remove farthest, insert: that is a **max** heap.

```text
kept so far (k = 3):   { D:18, A:10, B:8 }     max heap, top = D (18)
                          ^
                     the farthest - first to go

new point E (1):       1 < 18  -> E joins, D is thrown out
kept now:              { A:10, B:8, E:1 }      top = A (10)
```

### The two-line rule, now complete

| You need the k ... | Keep a heap of size k that is a ... | Its top is ... |
| :----------------- | :---------------------------------- | :------------- |
| largest | min heap | the smallest of them (next to be replaced) |
| smallest / closest | **max heap** | the largest / farthest of them |

### Heaps of objects

The heap holds `int[]` points, not numbers. Java's `PriorityQueue` does not know how to order `int[]`, so you hand it a comparator that computes the key:

```text
compare(a, b) = compare( dist(b), dist(a) )     b first -> MAX heap on distance
```

Everything else - offer, poll if over size, peek - is unchanged from Kth Largest.

### Recognising it

- "k closest", "k nearest", "k most frequent", "k cheapest", "top k by score"
- the ranking key is **computed** from each element (distance, frequency, cost)
- you need the k best, not their full order

The mental question:

> What is the key, and which end of my k-best set gets replaced? Order the heap so that end is on top.

=== bruteForce ===
Compute each point's squared distance, sort all points by it, and return the first `k`.

### Dry run

**Step 1 - compute the key for every point.**

| i | point | `x^2` | `y^2` | `d = x^2 + y^2` |
| -: | :---- | ----: | ----: | --------------: |
| 0 | A `[1, 3]` | 1 | 9 | 10 |
| 1 | B `[-2, 2]` | 4 | 4 | 8 |
| 2 | C `[5, -1]` | 25 | 1 | 26 |
| 3 | D `[3, 3]` | 9 | 9 | 18 |
| 4 | E `[0, 1]` | 0 | 1 | 1 |
| 5 | F `[-2, 4]` | 4 | 16 | 20 |

**Step 2 - sort by `d` ascending, then take the first `k = 3`.**

| sorted position | point | d | taken? |
| --------------: | :---- | -: | :----- |
| 0 | E `[0, 1]` | 1 | yes |
| 1 | B `[-2, 2]` | 8 | yes |
| 2 | A `[1, 3]` | 10 | yes |
| 3 | D `[3, 3]` | 18 | no |
| 4 | F `[-2, 4]` | 20 | no |
| 5 | C `[5, -1]` | 26 | no |

Result `[[0, 1], [-2, 2], [1, 3]]`. Correct.

### Java

```java
class Solution {
    public int[][] kClosest(int[][] points, int k) {

        // Sort every point by squared distance, closest first.
        Arrays.sort(points, (a, b) -> Integer.compare(
                a[0] * a[0] + a[1] * a[1],
                b[0] * b[0] + b[1] * b[1]));

        return Arrays.copyOfRange(points, 0, k);
    }
}
```

### Complexity

**Time:** `O(n log n)` - **Space:** `O(n)` (Java sorts object arrays with TimSort, which uses up to `n / 2` extra slots), plus `O(k)` for the copied result.

### Where it hurts

Look at the bottom half of the sorted table. Rows 3-5 were put in exact order - D before F before C - and then **not taken**. We needed to know only that each of them is farther than the third-closest point, not how they rank among themselves.

The same is true at the top: E, B, A came out in order, but the problem accepts any order.

So the sort did `O(n log n)` work to produce a full ranking, of which the answer uses one fact: "which k are in the closest group". When `n = 10^4` and `k = 5`, almost all of that ranking is waste.

> Can I keep only the k closest points as I scan, and throw the rest away as soon as I know they cannot make it?

=== optimization ===
### The key observation

A point belongs in the final answer only if fewer than `k` points are closer. While scanning, keep the `k` closest seen so far. A newcomer only matters if it beats the **farthest** of those - and if it does, that farthest one is evicted. Keep the farthest on top: a max heap on distance.

### The algorithm

1. For each point: `offer` it into a max heap ordered by squared distance.
2. If the heap now holds `k + 1` points, `poll` the farthest.
3. At the end the heap holds exactly the `k` closest. Drain it into the result array.

### Dry run on the same example

`k = 3`. The heap column lists its contents **sorted farthest first for readability**; internally only the top is guaranteed to be the farthest.

| step | point | d | heap after offer | size > k? | polled | heap after | top (farthest) |
| ---: | :---- | -: | :--------------- | :-------- | :----- | :--------- | :------------- |
| 1 | A | 10 | `{A:10}` | no | - | `{A:10}` | A:10 |
| 2 | B | 8 | `{A:10, B:8}` | no | - | `{A:10, B:8}` | A:10 |
| 3 | C | 26 | `{C:26, A:10, B:8}` | no | - | `{C:26, A:10, B:8}` | C:26 |
| 4 | D | 18 | `{C:26, D:18, A:10, B:8}` | **yes** | C:26 | `{D:18, A:10, B:8}` | D:18 |
| 5 | E | 1 | `{D:18, A:10, B:8, E:1}` | **yes** | D:18 | `{A:10, B:8, E:1}` | A:10 |
| 6 | F | 20 | `{F:20, A:10, B:8, E:1}` | **yes** | F:20 | `{A:10, B:8, E:1}` | A:10 |

**Drain:** `poll` three times returns A (10), then B (8), then E (1), so the method returns `[[1, 3], [-2, 2], [0, 1]]` - the right three points, farthest first. Any order is accepted.

### Reading the table

- **Step 3:** C is the farthest point overall, but it still gets in - the heap is not full yet, so nothing can be ruled out.
- **Step 4:** the first eviction. Four candidates, room for three, and C (26) is the farthest. It can never be among the 3 closest because three points (D, A, B) are already closer.
- **Step 6:** F is pushed and immediately polled straight back out. It was farther than everything kept, so it became the top and left. Offering first and polling second handles "not good enough to join" without any extra comparison.
- **The top's distance never increases once the heap is full:** `26 -> 18 -> 10 -> 10`. The bar to get in only gets stricter.

### The follow-up: Quickselect

Exactly as on day 61: partition the points around a random pivot distance, and recurse into only the side containing position `k`. When it stops, the first `k` slots hold the `k` closest (in no particular order). Average `O(n)`, worst `O(n^2)`, and it rearranges the input. The heap is the safer default, and the only option when the points arrive as a stream.

=== complexity ===
### Time

`n` offers and up to `n - k` polls on a heap of at most `k + 1` points, then `k` polls to drain. Each operation is `O(log k)`.

```text
O(n log k)
```

### Space

The heap holds at most `k + 1` references, and the result holds `k`.

```text
O(k)
```

### Comparison

| Approach | Time | Extra space | Notes |
| :------- | ---: | ----------: | :---- |
| Sort all points by distance | `O(n log n)` | `O(n)` | reorders the input |
| **Max heap of size k** | **`O(n log k)`** | **`O(k)`** | works on a stream |
| Quickselect on distance | `O(n)` avg, `O(n^2)` worst | `O(1)` | reorders the input |

For `n = 10^4` all three are fast. The heap is the one that keeps working when the points never stop arriving - "the 10 nearest drivers, updated as positions stream in".

=== implementation ===
```java
class Solution {
    public int[][] kClosest(int[][] points, int k) {

        // MAX heap on squared distance: the top is the farthest of the k kept.
        PriorityQueue<int[]> heap = new PriorityQueue<>(
                (a, b) -> Integer.compare(dist(b), dist(a)));

        for (int[] p : points) {
            heap.offer(p);
            if (heap.size() > k) {
                heap.poll();        // the farthest cannot be among the k closest
            }
        }

        int[][] result = new int[k][];
        for (int i = 0; i < k; i++) {
            result[i] = heap.poll();
        }
        return result;
    }

    private int dist(int[] p) {
        return p[0] * p[0] + p[1] * p[1];   // squared: same order, no sqrt
    }
}
```

### The lines that matter

**1.**

```java
(a, b) -> Integer.compare(dist(b), dist(a)));
```

`b` before `a` is what makes it a **max** heap: a point with a larger distance compares as "smaller", so it rises to the top. Write `dist(a), dist(b)` and you get a min heap of size k, which evicts the closest points and returns the `k` **farthest**.

**2.**

```java
heap.offer(p);
if (heap.size() > k) {
    heap.poll();        // the farthest cannot be among the k closest
}
```

The same two lines as Kth Largest. Offer unconditionally, trim to `k`. A point too far to qualify becomes the top and is polled straight back out (step 6 of the dry run).

**3.**

```java
return p[0] * p[0] + p[1] * p[1];   // squared: same order, no sqrt
```

Integer arithmetic only. With coordinates up to `10^4` this peaks at `2 * 10^8`, safely inside `int`.

### Java notes

- `PriorityQueue<int[]>` stores **references** to the original point arrays. The result contains those same arrays, not copies - which is fine, since we never modify them.
- `new int[k][]` allocates an array of `k` row references; each row is then pointed at a polled point. Writing `new int[k][2]` would allocate `k` throwaway rows first.
- The comparator recomputes `dist` on every comparison. That is `O(1)` each and keeps the code simple. If the key were expensive, you would store `{dist, index}` pairs in the heap instead.
- `Integer.compare` is safer than `dist(b) - dist(a)`. Here subtraction happens to be safe (both values are in `[0, 2 * 10^8]`), but the habit avoids overflow bugs when keys can be large or negative.

=== edgeCases ===
### k = 1

```text
[[1, 3], [-2, 2]],  k = 1  ->  [[-2, 2]]
```

LeetCode's first example. The heap holds one point and keeps whichever is closer.

### k equals n

```text
[[1, 1], [2, 2]],  k = 2  ->  both points
```

The heap never exceeds `k`, so nothing is polled during the scan. Every point is returned.

### The origin itself

```text
[[0, 0], [1, 0]],  k = 1  ->  [[0, 0]]
```

Distance `0` is the smallest possible. Nothing special in the code.

### Duplicate points

```text
[[1, 1], [1, 1], [3, 3]],  k = 2  ->  [[1, 1], [1, 1]]
```

Two separate array entries that happen to be equal. Both are kept; the heap does not deduplicate.

### Equal distances in different directions

```text
[[1, 0], [0, 1], [-1, 0], [3, 3]],  k = 3  ->  [[1, 0], [0, 1], [-1, 0]]  (any order)
```

Three points at distance `1`, one at `18`. Signs disappear when squared, so quadrant never matters. LeetCode guarantees the answer is unique, so a tie never straddles the k-th position.

### Largest coordinates

```text
[[10000, 10000], [-10000, -10000], [1, 1]],  k = 1  ->  [[1, 1]]
```

`10000^2 + 10000^2 = 200,000,000`, under `Integer.MAX_VALUE = 2,147,483,647`. No overflow.

### The `sqrt` trap

Using real distances is not wrong, but a common way of comparing them is:

```text
(a, b) -> (int) (Math.sqrt(dist(b)) - Math.sqrt(dist(a)))
```

For points at `sqrt(1) = 1.0` and `sqrt(2) = 1.414...`, the difference `0.414` is cast to `0`, so the comparator says they are **equal** and the heap may keep the wrong one. Squared integer distances with `Integer.compare` avoid the whole class of bug.

=== takeaway ===
> When you see **"k closest"**, **"k nearest"** or **"k smallest by some score"**, think **max heap of size k on that score**. The farthest kept element sits on top, because it is the one a better arrival replaces.

### The core observation

Only membership in the closest-k group matters, not the order inside or outside it. Keep `k` candidates, always evict the worst of them, and the work per point drops from `log n` (sorting) to `log k`.

### The pattern trigger

```text
       "k closest / k smallest by key"
                    |
                    v
        key = something computed per element
        (distance -> x*x + y*y, no sqrt)
                    |
                    v
     who gets replaced?  the FARTHEST of the k
                    |
                    v
   MAX heap, comparator (a, b) -> compare(key(b), key(a))
                    |
                    v
      offer, poll if size > k, drain at the end
```

### The common mistakes

**Min heap for "closest".** Same mirror-image bug as day 61: it evicts the closest points and returns the farthest `k`.

**Comparator written `a, b` instead of `b, a`.** That is the same bug in disguise - the direction of the comparator *is* the choice of min versus max heap.

**Using `sqrt` and casting the difference to `int`.** Distances less than 1 apart compare as equal.

**Sorting `points` when the problem says "any order".** Not wrong, just `O(n log n)` for order nobody asked for.

### What to remember in six months

> The heap logic is identical for numbers and for objects. Pick the key, pick which end gets evicted, write the comparator to put that end on top.
