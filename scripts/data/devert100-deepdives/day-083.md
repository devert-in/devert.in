=== intro ===
Day 81 sorted meetings by **end** time to fit in as many as possible. Day 82 sorted items by **value per kilo**. Today sorts intervals by **start** time - and the reason it is start, not end, is the whole lesson.

> The sort key is not a detail you pick at random. It is the order in which a single left-to-right sweep can make every decision without looking back. Ask "what do I need to know about everything I have already seen?" - and sort so the answer is "only the last thing".

=== problem ===
You are given a list of intervals `[start, end]`. Merge every group of overlapping intervals into one, and return the intervals that remain.

```text
intervals = [[1,3], [2,6], [8,10], [15,18]]
output    = [[1,6], [8,10], [15,18]]
```

On a number line:

```text
     1   3
     |---|
       |-------|
       2       6
                     |----|          |------|
                     8    10         15     18

merged:
     |---------|     |----|          |------|
     1         6     8    10         15     18
```

`[1,3]` and `[2,6]` share the stretch `2..3`, so they become one interval `[1,6]`. Nothing else touches anything.

### What "overlap" means here

Two intervals `a` and `b` overlap when neither one ends before the other starts:

```text
a[0] <= b[1]  AND  b[0] <= a[1]
```

The intervals are **closed**, so touching counts. `[1,4]` and `[4,5]` share the point `4` and merge into `[1,5]`. This is LeetCode's convention, and it is the single most common reason a correct-looking solution fails a hidden test - write `<=`, not `<`.

### The worked example as a table

| interval | start | end | overlaps with | ends up in |
| :------- | ----: | --: | :------------ | :--------- |
| `[1,3]` | 1 | 3 | `[2,6]` | `[1,6]` |
| `[2,6]` | 2 | 6 | `[1,3]` | `[1,6]` |
| `[8,10]` | 8 | 10 | nothing | `[8,10]` |
| `[15,18]` | 15 | 18 | nothing | `[15,18]` |

### What makes it non-trivial

Two things the example hides:

1. **The input is not sorted.** `[[8,10],[1,3],[15,18],[2,6]]` is an equally valid input with the same answer. Overlapping intervals can sit at opposite ends of the array.
2. **Merges chain.** `[1,3]`, `[3,5]`, `[5,7]` must collapse into one `[1,7]`, even though `[1,3]` and `[5,7]` do not overlap each other directly. Merging two intervals produces a bigger interval, which can then reach a third.

Constraints: `1 <= n <= 10^4`, `0 <= start <= end <= 10^4`. Any order of the output is accepted.

=== pattern ===
**Greedy - sort by start, then sweep and merge.**

### Why sorting by start is the right order

Picture the intervals sorted by start, and you sweeping left to right holding the interval you are currently building (`last`). A new interval `current` arrives. Because of the sort, `current.start >= last.start`. Only two things can be true:

```text
case 1: current starts inside (or touching) last
    last     |----------|
    current        |--------|        current[0] <= last[1]  ->  extend last

case 2: current starts after last ends
    last     |----------|
    current                 |----|   current[0] >  last[1]  ->  last is FINISHED
```

Case 2 is the key. If `current` starts after `last` ends, then **every interval still to come starts at or after `current`** - the sort guarantees it - so none of them can ever reach back to `last` either. `last` is final. You never revisit it.

That is the greedy-choice property here: a decision ("this group is closed") made with only local information is never wrong later.

### Why not sort by end?

Day 81's activity selection sorted by end because it wanted to *finish early* and leave room for more. Here you need to know, the moment an interval arrives, whether it can still join the current group. Sorting by end breaks that:

```text
sorted by end:  [2,3]  [1,10]
```

After `[2,3]` you would think the group is `[2,3]`; then `[1,10]` arrives starting *before* it, and you would need to look back. Sorting by start is what makes "compare only with the last" safe.

### Recognising it

Reach for sort-by-start and merge when:

- the input is a set of ranges, time slots, bookings, or segments on a line
- the question is about their **union**, coverage, or how many groups they form
- you are asked to "merge", "combine", "insert an interval", or "find free time"

The mental question:

> If I process these left to right by start, does anything I have already closed ever need reopening?

If the answer is no, one sweep after the sort does the job.

=== bruteForce ===
Forget sorting. What is the most direct thing that is obviously correct?

Keep a working list. Look for **any** pair that overlaps. If you find one, replace the pair with their union and start looking again from scratch, because the new bigger interval might now overlap something it did not before. When a full scan finds no overlapping pair, you are done.

### Step logic

1. Copy the input into a list.
2. For every pair `(i, j)` with `i < j`, test `a[0] <= b[1] && b[0] <= a[1]`.
3. On the first overlap: set `list[i] = [min(starts), max(ends)]`, remove `list[j]`, mark `changed`, and restart the scan.
4. Repeat until a full scan changes nothing.

### Dry run

```text
intervals = [[1,3], [2,6], [8,10], [15,18]]
```

| scan | i | j | a | b | `a[0]<=b[1]` | `b[0]<=a[1]` | overlap? | action | list after |
| ---: | -: | -: | :- | :- | :---------- | :---------- | :------- | :----- | :--------- |
| 1 | 0 | 1 | `[1,3]` | `[2,6]` | 1 <= 6 yes | 2 <= 3 yes | yes | `list[0] = [1,6]`, remove index 1, restart | `[1,6] [8,10] [15,18]` |
| 2 | 0 | 1 | `[1,6]` | `[8,10]` | 1 <= 10 yes | 8 <= 6 no | no | - | `[1,6] [8,10] [15,18]` |
| 2 | 0 | 2 | `[1,6]` | `[15,18]` | 1 <= 18 yes | 15 <= 6 no | no | - | `[1,6] [8,10] [15,18]` |
| 2 | 1 | 2 | `[8,10]` | `[15,18]` | 8 <= 18 yes | 15 <= 10 no | no | - | `[1,6] [8,10] [15,18]` |

Scan 2 finds nothing, so `changed` stays `false` and the loop ends:

```text
[[1,6], [8,10], [15,18]]
```

Correct. It also handles chains: a merge restarts the scan, so a grown interval gets compared against everything again.

### Java

```java
class Solution {
    public int[][] merge(int[][] intervals) {

        List<int[]> list = new ArrayList<>();
        for (int[] in : intervals) {
            list.add(new int[] { in[0], in[1] });
        }

        boolean changed = true;

        while (changed) {
            changed = false;

            search:
            for (int i = 0; i < list.size(); i++) {
                for (int j = i + 1; j < list.size(); j++) {
                    int[] a = list.get(i);
                    int[] b = list.get(j);

                    if (a[0] <= b[1] && b[0] <= a[1]) {      // the pair overlaps
                        a[0] = Math.min(a[0], b[0]);
                        a[1] = Math.max(a[1], b[1]);
                        list.remove(j);
                        changed = true;
                        break search;                        // list changed - start over
                    }
                }
            }
        }

        return list.toArray(new int[list.size()][]);
    }
}
```

`break search;` is a labelled break - it exits **both** loops at once, which a plain `break` would not.

### Complexity

**Time:** `O(n^3)` worst case - one scan is `O(n^2)` pairs, and there can be up to `n - 1` merges, each followed by a fresh scan. **Space:** `O(n)` for the working list.

### Where it hurts

The example finished in two scans, which hides the cost. Make the merge sit at the end:

```text
[[1,1], [3,3], [5,5], [7,7], [9,10], [10,11], [11,12]]
```

Scan 1 compares `[1,1]` against six intervals, `[3,3]` against five, and so on - **every one of those comparisons says "no overlap"** - before it finally reaches `[9,10]` vs `[10,11]` and merges. Then it restarts and re-asks every one of those same questions about `[1,1]`, `[3,3]`, `[5,5]`, `[7,7]`. The answers cannot have changed: those four intervals were not touched.

```text
scan 1:  1,1 vs ...  (6 nos)   3,3 vs ... (5 nos)   ... then merge
scan 2:  1,1 vs ...  (5 nos)   3,3 vs ... (4 nos)   ... then merge
scan 3:  the same "no" answers, asked a third time
```

Two separate wastes:

1. **Comparing intervals that are far apart.** `[1,1]` and `[11,12]` could never overlap - they are nowhere near each other on the line - yet we test them.
2. **Re-confirming settled facts.** Once we know `[1,1]` overlaps nothing, every later scan asks again.

Both come from the same root: the list has no order, so we cannot tell which intervals are *neighbours*. Put them in order and each interval only ever needs to be compared with the one before it.

=== optimization ===
### The observation

Overlap is a question about **neighbours on the number line**. If the intervals are sorted by start, then the only interval that can possibly overlap the current one is the group you are building right now - everything earlier has already been closed off for good (the pattern section proves why: a later interval starts even further right, so it cannot reach back past a gap).

So:

1. Sort by start.
2. Keep a result list. The last element of the result is the group currently being built.
3. For each interval:
   - if it starts **after** the last group ends, the last group is final - push the current interval as a new group
   - otherwise it overlaps, so stretch the last group: `last[1] = max(last[1], current[1])`

The `max` is not optional. The current interval might be entirely inside the last group (`[1,10]` then `[2,3]`), and setting `last[1] = current[1]` would *shrink* the group from `10` to `3`.

### Dry run

```text
intervals = [[1,3], [2,6], [8,10], [15,18]]
sorted    = [[1,3], [2,6], [8,10], [15,18]]   (already in start order)
```

| step | current | last group | `current[0] <= last[1]`? | action | merged after |
| ---: | :------ | :--------- | :----------------------- | :----- | :----------- |
| 1 | `[1,3]` | (none) | - | result empty, push | `[1,3]` |
| 2 | `[2,6]` | `[1,3]` | 2 <= 3 yes | `last[1] = max(3, 6) = 6` | `[1,6]` |
| 3 | `[8,10]` | `[1,6]` | 8 <= 6 no | `[1,6]` is final, push | `[1,6] [8,10]` |
| 4 | `[15,18]` | `[8,10]` | 15 <= 10 no | `[8,10]` is final, push | `[1,6] [8,10] [15,18]` |

```text
[[1,6], [8,10], [15,18]]
```

Four steps, one comparison each. Compare with the brute force's four comparisons on this tiny input - and its `O(n^2)` comparisons per scan in general.

### A dry run where sorting and `max` both matter

```text
intervals = [[8,10], [1,10], [2,3], [9,12]]
sorted    = [[1,10], [2,3], [8,10], [9,12]]
```

| step | current | last group | `current[0] <= last[1]`? | action | merged after |
| ---: | :------ | :--------- | :----------------------- | :----- | :----------- |
| 1 | `[1,10]` | (none) | - | push | `[1,10]` |
| 2 | `[2,3]` | `[1,10]` | 2 <= 10 yes | `last[1] = max(10, 3) = 10` | `[1,10]` |
| 3 | `[8,10]` | `[1,10]` | 8 <= 10 yes | `last[1] = max(10, 10) = 10` | `[1,10]` |
| 4 | `[9,12]` | `[1,10]` | 9 <= 10 yes | `last[1] = max(10, 12) = 12` | `[1,12]` |

```text
[[1,12]]
```

Step 2 is where `last[1] = current[1]` would go wrong: the group would shrink to `[1,3]`, step 3 would then see `8 <= 3` fail and start a new group, and the answer would come out as `[[1,3], [8,12]]` - which leaves the points `4..7` uncovered even though `[1,10]` covered them.

### Why one pass is enough after the sort

The brute force had to restart because a merge could make an interval reach something it previously missed. Here that cannot happen backwards: a group only ever grows to the **right**, and everything to its left is already closed. Growing to the right is exactly the direction the sweep is moving, so the next comparison naturally sees the bigger group.

=== complexity ===
### Time

Sorting `n` intervals is `O(n log n)`. The sweep is `O(n)` - one comparison and at most one `max` per interval.

```text
O(n log n)   (the sort dominates)
```

### Space

The result list holds up to `n` intervals (when nothing overlaps). Java's object sort (`Arrays.sort` on `int[][]` is TimSort) can use up to `O(n)` auxiliary space too.

```text
O(n)
```

### Comparison

| Approach | Time | Space | Restarts after a merge? |
| :------- | ---: | ----: | :---------------------- |
| Repeated pairwise scan | `O(n^3)` worst | `O(n)` | yes |
| Sort by start + one sweep | **`O(n log n)`** | `O(n)` | no |

### Can it be faster?

Not in general. If the input were already sorted, the sweep alone is `O(n)`. When coordinates are small (here `<= 10^4`), a counting approach over the coordinate range is possible, but it costs `O(range)` space and has to be careful with touching versus gapped intervals. The sort is the honest answer in an interview.

=== implementation ===
```java
class Solution {
    public int[][] merge(int[][] intervals) {

        // Sort by start so overlapping intervals become neighbours.
        Arrays.sort(intervals, (a, b) -> Integer.compare(a[0], b[0]));

        List<int[]> merged = new ArrayList<>();

        for (int[] current : intervals) {
            if (merged.isEmpty() || merged.get(merged.size() - 1)[1] < current[0]) {
                // Gap before current: the last group is final, start a new one.
                merged.add(new int[] { current[0], current[1] });
            } else {
                // Overlaps or touches: stretch the last group to the right.
                int[] last = merged.get(merged.size() - 1);
                last[1] = Math.max(last[1], current[1]);
            }
        }

        return merged.toArray(new int[merged.size()][]);
    }
}
```

### The lines that matter

**1.**

```java
Arrays.sort(intervals, (a, b) -> Integer.compare(a[0], b[0]));
```

Sort by `a[0]`, the start. This one line is what turns an all-pairs problem into a neighbours problem. `Integer.compare` instead of `a[0] - b[0]` avoids overflow in general; with this problem's `0..10^4` range subtraction would be safe, but there is no reason to build the habit.

**2.**

```java
if (merged.isEmpty() || merged.get(merged.size() - 1)[1] < current[0]) {
```

Strict `<`. A new group starts only when there is a real gap. `last[1] == current[0]` means the intervals touch, and touching intervals merge. Write `<=` here and `[1,4],[4,5]` comes out unmerged.

**3.**

```java
last[1] = Math.max(last[1], current[1]);
```

`max`, because the current interval can be fully contained in the group. The start never needs updating - the sort guarantees `last[0] <= current[0]`.

### Java notes

- `merged.toArray(new int[merged.size()][])` converts `List<int[]>` back to `int[][]`. The second dimension is left empty because each row is an existing `int[]` that just gets referenced.
- The code pushes a **copy** (`new int[] { current[0], current[1] }`) rather than `current` itself. Pushing `current` also works on LeetCode, but then `last[1] = ...` writes into the caller's input array. Copying costs nothing in big-O and avoids a surprise.
- `Arrays.sort` sorts the input in place. If the caller must keep its original order, clone first.

=== edgeCases ===
### Single interval

```text
[[1,4]]  ->  [[1,4]]
```

The loop runs once, pushes it, and returns it.

### Touching intervals

```text
[[1,4], [4,5]]  ->  [[1,5]]
```

`4 < 4` is false, so they merge. Closed intervals share the endpoint.

### One interval contains another

```text
[[1,10], [2,3]]  ->  [[1,10]]
```

`max(10, 3) = 10`. Without `max`, the group would shrink to `[1,3]`.

### Containment followed by a later overlap

```text
[[1,10], [2,3], [4,12]]  ->  [[1,12]]
```

The bug from a missing `max` shows up one step later: the group shrinks to `[1,3]`, then `[4,12]` looks like a separate group, and you return `[[1,3], [4,12]]`.

### Unsorted input

```text
[[1,4], [0,4]]  ->  [[0,4]]
[[1,4], [0,0]]  ->  [[0,0], [1,4]]
```

Skip the sort and both come out as `[[1,4]]`. The sweep sees `[1,4]` first, then tests `4 < 0` - false, so it "merges" an interval that lies to the *left* of the group, and `max` only ever stretches the right end. The `0` is silently lost.

### A chain that only merges through the middle

```text
[[1,3], [3,5], [5,7]]  ->  [[1,7]]
```

`[1,3]` and `[5,7]` do not overlap, but each step stretches the group far enough to reach the next one.

### Nothing overlaps

```text
[[1,2], [3,4], [5,6]]  ->  [[1,2], [3,4], [5,6]]
```

Every step finds a gap and pushes. The result is the same size as the input - this is the `O(n)` space worst case.

### Exact duplicates

```text
[[1,3], [1,3]]  ->  [[1,3]]
```

### Zero-length intervals

```text
[[5,5], [5,5]]  ->  [[5,5]]
[[0,0], [1,1]]  ->  [[0,0], [1,1]]
```

A point interval is a valid interval. Two equal points touch and merge; `0` and `1` have a gap between them and do not.

=== takeaway ===
> When you see **ranges that may overlap** and a question about their **union**, think **sort by start, then compare each one only with the last group**.

### The core observation

After sorting by start, an interval can only overlap the group you are currently building. The moment a gap appears, that group is final, because every later interval starts even further to the right. That single fact turns `O(n^2)` pair checks into one pass.

### The pattern trigger

```text
       list of [start, end] ranges
                    |
                    v
          sort by START (not end)
                    |
                    v
     for each current:
        current[0] >  last[1]  ->  gap: close last, push current
        current[0] <= last[1]  ->  overlap: last[1] = max(last[1], current[1])
                    |
                    v
        result = the closed groups, already sorted
```

### The common mistakes

**`last[1] = current[1]` instead of `max`.** Shrinks the group when the current interval is contained in it. Passes the sample, fails `[[1,10],[2,3]]`.

**`<=` instead of `<` in the gap test.** Treats touching intervals as separate. Fails `[[1,4],[4,5]]`.

**Forgetting to sort.** Works on every example that happens to be sorted, which is most of the ones people test by hand.

**Sorting by end.** That is activity selection (Day 81). It answers "how many can I keep without overlap", not "what is their union".

### What to remember in six months

> Sort by start, keep the last group, extend with `max` or close on a gap.

The same sweep solves Insert Interval (LC 57 - the input is already sorted, so it is `O(n)`), Meeting Rooms (LC 252 - any overlap at all means `false`), Employee Free Time (the gaps between merged groups), and Meeting Rooms II (LC 253) once you split each interval into a start event and an end event.
