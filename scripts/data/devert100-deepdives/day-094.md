=== intro ===
Yesterday you built the 0/1 knapsack table: items used at most once, a capacity, maximise value, capacity loop backwards. Today's problem never mentions a knapsack, a weight or a value - and it is the same table with `int` swapped for `boolean`.

> The habit for today: when a problem asks about splitting into two groups, stop thinking about two groups. Pick one group, and ask what its sum has to be. Most "partition" problems are a subset-sum problem wearing a costume.

=== problem ===
Given an array of positive integers `nums`, return `true` if it can be split into **two subsets with equal sums**. Every element goes into exactly one of the two subsets.

```text
nums = [1, 5, 11, 5]   ->  true
```

| subset A | sum | subset B | sum |
| :------- | --: | :------- | --: |
| [1, 5, 5] | 11 | [11] | 11 |

```text
nums = [1, 2, 3, 5]    ->  false
```

The total is `11`. No split of `11` into two equal integers exists, so no partition can work - whatever the elements are.

### The reframe that makes it solvable

"Two subsets with equal sums" sounds like you have to build both at once. You do not. If the total is `S` and the two halves are equal, each half is exactly `S / 2`. And once you have chosen a subset A summing to `S / 2`, subset B is simply **everything else** - its sum is `S - S/2 = S/2` automatically.

So the question becomes:

> Is there a subset of `nums` that sums to exactly `total / 2`?

One subset, one target. That is subset-sum.

### Constraints that matter

`1 <= nums.length <= 200`, `1 <= nums[i] <= 100`. So the total is at most `200 * 100 = 20000` and the target at most `10000`. A boolean array of `10001` entries, swept `200` times, is `2 * 10^6` steps - trivial. Trying all `2^200` subsets is not.

The small value bound is not decoration. It is the reason a table indexed by **sum** is allowed to exist.

=== pattern ===
**Subset-sum DP** - 0/1 knapsack with booleans.

Map it onto yesterday's problem:

| 0/1 Knapsack | Partition Equal Subset Sum |
| :----------- | :------------------------- |
| item | number |
| weight `wt[i]` | the number itself |
| capacity `W` | `target = total / 2` |
| value | none - we only care about reachability |
| `dp[w]` = best value | `dp[s]` = can some subset sum to exactly `s`? |
| `max(skip, take)` | `skip OR take` |
| capacity loop backwards | sum loop backwards |

The recurrence, in its 2D form:

```text
dp[i][s] = true if some subset of the first i numbers sums to exactly s

dp[i][s] = dp[i-1][s]                       skip nums[i-1]
        OR dp[i-1][s - nums[i-1]]           take nums[i-1]   (only if nums[i-1] <= s)

dp[0][0] = true      the empty subset sums to 0
dp[0][s] = false     for s > 0 - no numbers, no positive sum
```

### Why it belongs to this family

Every number is used **at most once** (it goes in subset A or it does not). Choosing it consumes part of a **budget** (the target sum). And the answer to "can the remaining numbers hit the remaining sum?" depends only on *which numbers remain* and *what sum remains* - not on which earlier numbers were chosen. That is the 0/1 knapsack fingerprint, exactly.

### Recognising it

Reach for boolean subset-sum when:

- you must **split into two groups** with equal sum, or with a given difference
- you are asked whether some subset **hits a target** exactly
- the values are **small** enough that a table indexed by sum fits

The mental question:

> If I fix one group, is there a single number its sum must equal?

If yes, it is subset-sum against that number.

=== bruteForce ===
Pretend the DP does not exist. The direct approach is to try subsets until one hits the target.

### Step logic

1. Sum the array. If odd, return `false`.
2. `target = total / 2`.
3. Define `canReach(i, remaining)` = can some subset of `nums[i..n-1]` sum to exactly `remaining`?
   - If `remaining == 0`: `true` (choose nothing more).
   - If `i == n`: `false` (out of numbers, still owe something).
   - **Take** `nums[i]` if it fits: `canReach(i + 1, remaining - nums[i])`.
   - **Skip** it: `canReach(i + 1, remaining)`.
   - Return take OR skip.

Java's `||` short-circuits, so as soon as one branch finds a subset, the rest are never explored.

### Dry run

```text
nums = [1, 5, 11, 5], total = 22, target = 11
```

Calls in the order they are **made**. Take is tried before skip.

| step | call | nums[i] | fits? | branch tried | result |
| ---: | :--- | ------: | :---- | :----------- | :----- |
| 1 | `canReach(0, 11)` | 1 | yes | take -> `canReach(1, 10)` | pending |
| 2 | `canReach(1, 10)` | 5 | yes | take -> `canReach(2, 5)` | pending |
| 3 | `canReach(2, 5)` | 11 | no, 11 > 5 | skip -> `canReach(3, 5)` | pending |
| 4 | `canReach(3, 5)` | 5 | yes | take -> `canReach(4, 0)` | pending |
| 5 | `canReach(4, 0)` | - | - | `remaining == 0` | **true** |
| 6 | `canReach(3, 5)` | | | take returned true | true |
| 7 | `canReach(2, 5)` | | | skip returned true | true |
| 8 | `canReach(1, 10)` | | | take returned true | true |
| 9 | `canReach(0, 11)` | | | take returned true | **true** |

The path that succeeded: take `1`, take `5`, skip `11`, take `5`. Subset A = `[1, 5, 5]`, sum `11`. Subset B = `[11]`.

### Java

```java
class Solution {
    public boolean canPartition(int[] nums) {

        int total = 0;
        for (int num : nums) {
            total += num;
        }
        if (total % 2 != 0) {
            return false;
        }

        return canReach(nums, 0, total / 2);
    }

    // Can some subset of nums[i..] sum to exactly `remaining`?
    private boolean canReach(int[] nums, int i, int remaining) {
        if (remaining == 0) {
            return true;
        }
        if (i == nums.length) {
            return false;
        }

        boolean take = nums[i] <= remaining
                && canReach(nums, i + 1, remaining - nums[i]);

        return take || canReach(nums, i + 1, remaining);
    }
}
```

### Complexity

**Time:** `O(2^n)` - **Space:** `O(n)` recursion stack

### Where it hurts

The example was lucky: the first path tried was nearly the right one. The brute force is at its worst when the answer is `false`, because then **every** subset must be ruled out before it can say so.

```text
nums = [2, 2, 3, 5], total = 12, target = 6
```

No subset sums to `6` (the reachable sums are `0, 2, 3, 4, 5, 7, 8, 9, 10, 12`), so all 16 subsets get explored. And look at two of the paths:

```text
take nums[0]=2, skip nums[1]   ->  canReach(2, 4)
skip nums[0],   take nums[1]=2 ->  canReach(2, 4)
```

Identical question - "can `[3, 5]` make `4`?" - answered twice from scratch. With 200 numbers there are at most `201 * 10001` distinct `(i, remaining)` pairs, but up to `2^200` paths into them.

The answer to `canReach(i, remaining)` depends only on those two numbers. Compute each pair once, and the exponential disappears.

=== optimization ===
### The observation

Stop asking "which subset?" and ask a smaller question for every sum at once: **"is sum `s` reachable using the numbers seen so far?"** Keep one boolean per `s` from `0` to `target`.

Adding a new number `num` makes a sum `s` reachable if it was already reachable (skip `num`), or if `s - num` was reachable before (take `num`):

```text
dp[s] = dp[s] OR dp[s - num]
```

That is the 2D recurrence with the row index dropped - exactly the 1D knapsack trick from yesterday. And for exactly the same reason, `s` must run **backwards** from `target` down to `num`, so that `dp[s - num]` is still the value from *before* this number was added.

### Dry run

```text
nums = [1, 5, 11, 5], target = 11
```

Only the `true` entries are interesting, so the right column lists the set of reachable sums.

| num | s | `dp[s]` old | `dp[s - num]` | `dp[s]` new | reachable after this number |
| --: | -: | :---------- | :------------ | :---------- | :-------------------------- |
| start | - | - | - | - | `{0}` |
| 1 | 11 .. 2 | false | `dp[10..1]` all false | false | |
| | 1 | false | `dp[0]` = true | **true** | `{0, 1}` |
| 5 | 11 .. 7 | false | `dp[6..2]` all false | false | |
| | 6 | false | `dp[1]` = true | **true** | |
| | 5 | false | `dp[0]` = true | **true** | `{0, 1, 5, 6}` |
| 11 | 11 | false | `dp[0]` = true | **true** | `{0, 1, 5, 6, 11}` |
| 5 | 11 | true | `dp[6]` = true | true | |
| | 10 | false | `dp[5]` = true | **true** | |
| | 9 .. 7 | false | `dp[4..2]` all false | false | |
| | 6 | true | `dp[1]` = true | true | |
| | 5 | true | `dp[0]` = true | true | `{0, 1, 5, 6, 10, 11}` |

`dp[11]` is `true`. It first became true when `11` arrived (subset `[11]`), and became true a second way when the last `5` arrived (`dp[6]`, which was `1 + 5`, plus `5`). Either witness proves a partition exists.

Notice the row for `num = 5` the second time: at `s = 10`, it read `dp[5]` - which was made true by the **first** `5`, a different element. That is allowed. What backwards prevents is reading a cell this same `5` already wrote.

### The forward-loop bug, concretely

```text
nums = [1, 3], total = 4, target = 2
```

Correct answer: `false` (`[1]` vs `[3]`). Loop `s` **upwards** for `num = 1`:

| s | `dp[s - 1]` | `dp[s]` new |
| -: | :---------- | :---------- |
| 1 | `dp[0]` = true | true |
| 2 | `dp[1]` = true - **written a moment ago by this same 1** | true |

`dp[2]` becomes true by using the `1` twice. Forwards returns `true`; backwards returns `false`. Same bug as yesterday, same fix.

### Early exit

`dp[target]` can only ever go from `false` to `true`. Once it is `true` you could return immediately. It does not change the worst case, so the implementation below keeps the loop plain; add `if (dp[target]) return true;` after each number if you want it.

=== complexity ===
### Time

`n` numbers, each sweeping at most `target + 1` sums.

```text
O(n * target)  =  O(n * sum)
```

With the constraints: at most `200 * 10000 = 2 * 10^6` steps.

### Space

One boolean array of `target + 1` entries.

```text
O(sum)
```

### Comparison

| Approach | Time | Space | Notes |
| :------- | ---: | ----: | :---- |
| Recursion over subsets | `O(2^n)` | `O(n)` stack | worst on `false` answers |
| Recursion + memo `(i, remaining)` | `O(n * sum)` | `O(n * sum)` | straight from the brute force |
| 2D boolean table | `O(n * sum)` | `O(n * sum)` | can reconstruct the subset |
| 1D boolean, backwards | **`O(n * sum)`** | **`O(sum)`** | the interview answer |

Like knapsack, this is pseudo-polynomial: it is fast because `nums[i] <= 100` keeps the sum small. With values up to `10^9`, the table is impossible and the problem goes back to being genuinely hard.

=== implementation ===
```java
class Solution {
    public boolean canPartition(int[] nums) {

        int total = 0;
        for (int num : nums) {
            total += num;
        }

        // Two equal integer halves need an even total.
        if (total % 2 != 0) {
            return false;
        }
        int target = total / 2;

        // dp[s] = can some subset of the numbers seen so far sum to exactly s?
        boolean[] dp = new boolean[target + 1];
        dp[0] = true;                       // the empty subset

        for (int num : nums) {
            // BACKWARDS, so each number is used at most once.
            for (int s = target; s >= num; s--) {
                dp[s] = dp[s] || dp[s - num];
            }
        }

        return dp[target];
    }
}
```

### The lines that matter

**1.**

```java
if (total % 2 != 0) {
    return false;
}
```

Not just an optimisation - it is a correctness filter. Without it, `total / 2` rounds down and the DP would happily report that `[1, 2]` (total `3`) has a subset summing to `1`, which says nothing about an equal split.

**2.**

```java
dp[0] = true;                       // the empty subset
```

The seed every other `true` grows from. Forget it and the array stays all-false forever, so the method returns `false` on every input.

**3.**

```java
for (int s = target; s >= num; s--) {
    dp[s] = dp[s] || dp[s - num];
}
```

Backwards is what keeps each number to one use. The lower bound `s >= num` keeps `s - num` non-negative and skips sums too small for this number to contribute to.

### Java notes

- `new boolean[n]` is filled with `false` by the JVM, which is the correct starting state for every `s > 0`.
- `dp[s] |= dp[s - num];` is equivalent and also valid Java - `|=` works on `boolean`. The `||` form is spelled out above because it reads as "skip or take".
- The faster-in-practice follow-up is a `java.util.BitSet` (or a `long[]` of bits): `bits = bits | (bits << num)` handles 64 sums per machine operation. Same complexity class, much smaller constant.

=== edgeCases ===
### Odd total

```text
[1, 2, 3, 5]  ->  false
```

Total `11`. Rejected before any DP runs.

### Single element

```text
[1]    ->  false
[2]    ->  false
```

`[1]`: total odd. `[2]`: total `2`, target `1`, and the only number is `2`, which is larger than `1` - the inner loop never runs, `dp[1]` stays `false`. One element can never be split into two non-empty halves of equal sum.

### Two equal elements

```text
[3, 3]  ->  true
```

Target `3`; the first `3` sets `dp[3] = dp[0] = true`.

### An element bigger than half

```text
[1, 2, 5]  ->  false
```

Total `8`, target `4`. The `5` can never sit in the half that must sum to `4`, and `1 + 2 = 3` is short. The DP needs no special case - `5` exceeds `target`, so its inner loop does nothing. (Some solutions return `false` early when `max(nums) > target`; it is a valid shortcut.)

### Even total, still impossible

```text
[2, 2, 3, 5]  ->  false
```

Total `12`, target `6`, but no subset sums to `6`. An even total is necessary, not sufficient. This is the case that forces the full DP.

### The forward-loop trap

```text
[1, 3]  ->  false   (a forward loop wrongly returns true)
```

Looping `s` upwards lets `1` be counted twice to reach `2`.

### All the same

```text
[1, 1, 1, 1]  ->  true
[1, 1, 1]     ->  false
```

Four ones split `2 / 2`. Three ones total `3`, odd.

### Largest input

`n = 200`, every `nums[i] = 100`: total `20000`, target `10000`, answer `true` (100 hundreds on each side). The table has `10001` entries and is swept 200 times - well within limits.

=== takeaway ===
> When you see **split into two groups with equal sum**, think **does one subset sum to `total / 2`?** - then run 0/1 knapsack with booleans, sum loop backwards.

### The core observation

Two equal halves of `S` means one half is exactly `S / 2`, and the other half is whatever is left over. So the two-sided problem is a one-sided reachability question. Reachability of each sum depends only on which numbers have been considered, so one boolean per sum, updated once per number, answers it.

### The pattern trigger

```text
      "split into two equal-sum groups"
                     |
                     v
      total odd?  ->  false, stop
                     |
                     v
      target = total / 2  (fix ONE group)
                     |
                     v
      dp[0] = true;  for each num:
          for s = target DOWN to num:
              dp[s] = dp[s] || dp[s - num]
                     |
                     v
                dp[target]
```

### The common mistakes

**Looping the sum forwards.** Each number gets reused, and inputs like `[1, 3]` flip from `false` to `true`.

**Forgetting `dp[0] = true`.** Every answer becomes `false`.

**Skipping the odd check and trusting `total / 2`.** Integer division hides the problem; `[1, 2]` would report success.

**Trying to build both subsets.** Tracking two running sums turns a 1D table into 2D for no gain. Fix one subset; the other is free.

### What to remember in six months

> "Two groups" problems usually collapse to "one subset hitting a number". Find the number, and it is yesterday's knapsack.

Target Sum (LC 494) is the same move with algebra: assigning `+` and `-` signs splits `nums` into `P` and `N` with `P - N = target` and `P + N = total`, so `P = (total + target) / 2` - count the subsets that reach it. Last Stone Weight II (LC 1049) asks for the reachable sum closest to `total / 2`. Same table every time.
