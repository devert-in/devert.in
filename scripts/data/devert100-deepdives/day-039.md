=== intro ===
Yesterday the stack was a building block - two of them made a queue. Today it stops being a container you implement and becomes the tool that solves the problem.

> When the next thing you must act on is always the **most recent** unfinished thing, you are looking at a stack. Postfix notation is the purest example: every operator acts on the two values produced most recently, and nothing else.

=== problem ===
You are given an arithmetic expression written in **Reverse Polish Notation** (postfix) as an array of string tokens. Evaluate it and return the integer result.

```text
tokens = ["2", "1", "+", "3", "*"]
answer = 9          because  (2 + 1) * 3 = 9
```

In postfix, the operator comes **after** its two operands. There are no brackets and no precedence rules - the order of the tokens already says what happens first.

### Reading postfix by hand

The rule is mechanical: walk left to right; whenever you hit an operator, it applies to the **two values immediately before it**, and the result replaces all three.

```text
2  1  +  3  *
\_____/
   3     3  *
   \________/
       9
```

### The example we will dry-run all day

This one is long enough to show every behaviour, including a subtraction where operand order matters:

```text
tokens = ["5", "1", "2", "+", "4", "*", "+", "3", "-"]
```

| Infix equivalent | Value |
| :--------------- | ----: |
| `5 + ((1 + 2) * 4) - 3` | 14 |

### The constraints that change the code

| Constraint | Why it matters |
| :--------- | :------------- |
| Tokens are `+`, `-`, `*`, `/` or an integer in `[-200, 200]` | A token like `"-11"` is a **number**, not an operator. Checking `token.charAt(0) == '-'` misreads it. |
| Division **truncates toward zero** | `-7 / 2` is `-3`, not `-4`. Java's `/` on `int` already does this; Python's `//` does not. |
| The expression is always valid | There is always a second operand to pop, and exactly one value is left at the end. No error handling needed. |
| Every intermediate fits in 32 bits | `int` is enough; no `long` required. |

### What makes it non-trivial

Two things. First, `a - b` and `a / b` are not symmetric, so you must know which value is the left operand. Second, an operator's operands may themselves be the results of earlier operators (`*` above multiplies `3`, which did not exist in the input - it came from `1 + 2`). You need somewhere to keep results until something consumes them.

=== pattern ===
**Stack - expression evaluation.**

Look at what an operator needs: the two values produced most recently that have not been consumed yet. "Most recent, not yet consumed" is precisely the definition of the top of a stack.

- A **number** is a value waiting to be used - push it.
- An **operator** consumes the top two values and produces one new value - pop two, push one.

Each operator's result goes back on the stack because it is itself a value waiting to be used by a later operator. That is the whole algorithm.

### Why the order of the pops matters

The stack is last-in, first-out. For `a b -`, `a` was pushed first and `b` second, so `b` is on top:

```text
push a  ->  [a]
push b  ->  [a, b]        top is b
pop     ->  b             the RIGHT operand comes off first
pop     ->  a             then the LEFT operand
result  =   a - b
```

Pop into `b` first, then `a`. Get this backwards and `5 3 -` returns `-2` instead of `2`. Addition and multiplication hide the bug because they are commutative.

### Recognising it

Reach for a stack when:

- the input is nested or bracketed, and the innermost thing must be finished first
- an item is "resolved" by the most recent unresolved item (matching brackets, undo, postfix operators)
- results of sub-computations have to wait until a later token consumes them

The mental question:

> When I hit something that needs earlier values, does it always want the **most recent** ones?

If yes, the earlier values belong on a stack.

=== bruteForce ===
Pretend we have never heard of a stack. The by-hand method above is already an algorithm: find an operator, combine it with the two tokens before it, replace the three with the result, and start again.

### Step logic

1. Copy the tokens into a mutable list.
2. Scan from the start until you hit the **first** operator, at index `i`.
3. Its operands are `list[i-2]` (left) and `list[i-1]` (right). Compute the result.
4. Replace those three entries with the single result.
5. Repeat until one entry is left.

The first operator always has two plain numbers right before it - nothing to its left is an operator, so nothing to its left is unevaluated.

### Dry run

```text
tokens = ["5", "1", "2", "+", "4", "*", "+", "3", "-"]
```

| round | list at start of round | tokens scanned | op found at `i` | a = list[i-2] | b = list[i-1] | result | list after |
| ----: | :--------------------- | -------------: | --------------: | ------------: | ------------: | -----: | :--------- |
| 1 | `[5, 1, 2, +, 4, *, +, 3, -]` | 4 | 3 (`+`) | 1 | 2 | 3 | `[5, 3, 4, *, +, 3, -]` |
| 2 | `[5, 3, 4, *, +, 3, -]` | 4 | 3 (`*`) | 3 | 4 | 12 | `[5, 12, +, 3, -]` |
| 3 | `[5, 12, +, 3, -]` | 3 | 2 (`+`) | 5 | 12 | 17 | `[17, 3, -]` |
| 4 | `[17, 3, -]` | 3 | 2 (`-`) | 17 | 3 | 14 | `[14]` |

One entry left: **14**. Correct. Round 4 is the one to stare at: `a` is the **earlier** token, so the result is `17 - 3`, not `3 - 17`.

### Java

```java
class Solution {
    public int evalRPN(String[] tokens) {

        List<String> list = new ArrayList<>(Arrays.asList(tokens));

        while (list.size() > 1) {

            // Find the first operator - its operands are the two tokens before it.
            int i = 0;
            while (!isOperator(list.get(i))) {
                i++;
            }

            int a = Integer.parseInt(list.get(i - 2));
            int b = Integer.parseInt(list.get(i - 1));
            int result = apply(a, b, list.get(i));

            // Replace "a b op" with the single result.
            list.set(i - 2, String.valueOf(result));
            list.remove(i);
            list.remove(i - 1);
        }

        return Integer.parseInt(list.get(0));
    }

    private boolean isOperator(String t) {
        return t.length() == 1 && "+-*/".indexOf(t.charAt(0)) >= 0;
    }

    private int apply(int a, int b, String op) {
        return switch (op) {
            case "+" -> a + b;
            case "-" -> a - b;
            case "*" -> a * b;
            default  -> a / b;
        };
    }
}
```

### Complexity

**Time:** `O(n^2)` - **Space:** `O(n)` for the list

### Where it hurts

Two kinds of waste, both visible in the table.

**Rescanning.** Every round starts at index 0. Round 2 walks past `5` and `3` again; round 3 walks past `5` again. Nothing to the left of the last change ever changes - it is all plain numbers - yet we re-read it every round. Make the operands pile up at the front and it gets bad:

```text
["1", "2", "3", "4", "5", "+", "+", "+", "+"]

round 1: scan 6 tokens   [1, 2, 3, 9, +, +, +]
round 2: scan 5 tokens   [1, 2, 12, +, +]
round 3: scan 4 tokens   [1, 14, +]
round 4: scan 3 tokens   [15]
```

With `n/2` numbers followed by `n/2` operators, the scans sum to about `n^2 / 8`.

**Shifting.** `list.remove(i)` on an `ArrayList` shifts every later element one slot left. Each round pays that again.

Now look at *what* each round actually touches: the operator and the two entries right before it - always the **end** of the already-scanned region. Everything else is untouched. We are treating a structure that only ever changes at one end as if it could change anywhere.

=== optimization ===
### The key observation

Split the list at the scan position. To the left is a run of fully evaluated numbers; to the right are tokens we have not looked at yet.

```text
[ evaluated numbers ... x  y ] [ op  rest of tokens ... ]
                        ^  ^
          the operator only ever touches these two
```

When the scan hits an operator, it combines the **last two** evaluated numbers and leaves a single number in their place - still at the end. Then it would restart from the left, but there is nothing new there. So do not restart: keep going from where you are.

A region that only grows and shrinks at its end, where you only ever look at the last element or two, is a **stack**. The brute force was already using one; it just was not admitting it.

### The algorithm

Walk the tokens once:

- number -> `push` it
- operator -> `b = pop()`, `a = pop()`, `push(a op b)`

At the end the stack holds exactly one value - the answer.

### Dry run on the same example

```text
tokens = ["5", "1", "2", "+", "4", "*", "+", "3", "-"]
```

Stack shown bottom to top.

| step | token | kind | b = pop() | a = pop() | pushed | stack after |
| ---: | :---- | :--- | --------: | --------: | -----: | :---------- |
| 1 | `5` | number | - | - | 5 | `[5]` |
| 2 | `1` | number | - | - | 1 | `[5, 1]` |
| 3 | `2` | number | - | - | 2 | `[5, 1, 2]` |
| 4 | `+` | operator | 2 | 1 | 1 + 2 = 3 | `[5, 3]` |
| 5 | `4` | number | - | - | 4 | `[5, 3, 4]` |
| 6 | `*` | operator | 4 | 3 | 3 * 4 = 12 | `[5, 12]` |
| 7 | `+` | operator | 12 | 5 | 5 + 12 = 17 | `[17]` |
| 8 | `3` | number | - | - | 3 | `[17, 3]` |
| 9 | `-` | operator | 3 | 17 | 17 - 3 = 14 | `[14]` |

Final stack `[14]`, so the answer is **14** - the same as the brute force, in 9 steps instead of 14 scanned tokens plus four rounds of shifting.

Compare the "stack after" column with the brute force's "list after" column. Row 4 here is `[5, 3]` and the brute force's round 1 left `[5, 3, 4, *, +, 3, -]` - the same evaluated prefix, minus the tokens not yet read. The stack is the brute force's list with the unread suffix cut off.

### The detail that decides correctness

Step 9: `b` is popped first and is `3`; `a` is popped second and is `17`. The result is `a - b = 14`. Writing `stack.pop() - stack.pop()` evaluates left to right in Java, giving `3 - 17 = -14`. Always name the two pops.

=== complexity ===
### Time

Each token is read once. A number costs one push; an operator costs two pops and one push. All `O(1)`.

```text
O(n)
```

### Space

The stack never holds more values than there are number tokens. For an input like `["1", "2", "3", ..., "+", "+", ...]` it holds about `n/2` at once.

```text
O(n)
```

### Comparison

| Approach | Time | Space | Rereads tokens? |
| :------- | ---: | ----: | :-------------- |
| Find first operator, splice, repeat | `O(n^2)` | `O(n)` | yes, every round |
| Recursive descent from the right end | `O(n)` | `O(n)` call stack | no |
| Explicit stack, one left-to-right pass | **`O(n)`** | **`O(n)`** | no |

The recursive version (evaluate from the last token backwards: an operator recursively evaluates its right operand, then its left) is worth knowing as an interview aside - it is the same stack, just the JVM's call stack instead of yours, and it can overflow on deep expressions.

=== implementation ===
```java
class Solution {
    public int evalRPN(String[] tokens) {

        Deque<Integer> stack = new ArrayDeque<>();

        for (String token : tokens) {
            if (isOperator(token)) {
                int b = stack.pop();   // right operand - pushed last, popped FIRST
                int a = stack.pop();   // left operand
                stack.push(apply(a, b, token));
            } else {
                stack.push(Integer.parseInt(token));
            }
        }

        return stack.pop();
    }

    // "-11" is a number: an operator is exactly one character long.
    private boolean isOperator(String t) {
        return t.length() == 1 && "+-*/".indexOf(t.charAt(0)) >= 0;
    }

    private int apply(int a, int b, String op) {
        return switch (op) {
            case "+" -> a + b;
            case "-" -> a - b;
            case "*" -> a * b;
            default  -> a / b;   // Java int division truncates toward zero
        };
    }
}
```

### The lines that matter

**1.**

```java
int b = stack.pop();   // right operand - pushed last, popped FIRST
int a = stack.pop();   // left operand
```

The whole problem's one trap. Two named variables make the order impossible to get wrong, and they make `apply(a, b, token)` read exactly like the infix `a op b`.

**2.**

```java
return t.length() == 1 && "+-*/".indexOf(t.charAt(0)) >= 0;
```

`"-"` is the minus operator; `"-3"` is the number negative three. Both start with `'-'`. Length is what tells them apart. A check like `t.equals("-")` also works, but `t.charAt(0) == '-'` does not.

**3.**

```java
default  -> a / b;   // Java int division truncates toward zero
```

The problem asks for truncation toward zero, and that is exactly what Java's `int` division does: `-7 / 2 == -3`. No `Math.floorDiv`, which would give `-4`.

### Java notes

- `Deque<Integer>` with `ArrayDeque` is the modern stack. `java.util.Stack` works but is synchronized and extends `Vector`; avoid it in new code. `push`/`pop` on an `ArrayDeque` operate on the head, so the head is the top.
- `stack.pop()` returns an `Integer`, auto-unboxed into `int b`. Unboxing a `null` would throw, but a valid expression never pops an empty stack - and `ArrayDeque.pop()` on an empty deque throws `NoSuchElementException` rather than returning `null` anyway.
- The arrow-form `switch` expression needs Java 14+. On older Java use `if`/`else if` chains or a classic `switch` with `return` in each case.
- `Integer.parseInt("-11")` handles the sign itself. No manual parsing.

=== edgeCases ===
### A single number

```text
["18"]  ->  18
```

No operators. The loop pushes `18` and the final `pop()` returns it. The brute force's `while (list.size() > 1)` never runs.

### Subtraction order

```text
["3", "5", "-"]  ->  -2
```

`b = 5`, `a = 3`, `3 - 5 = -2`. With the pops reversed you get `2` - wrong, and silently so.

### Division order

```text
["6", "3", "/"]  ->  2
["3", "6", "/"]  ->  0
```

Same two numbers, different answers. `3 / 6` truncates to `0`.

### Negative division truncates toward zero

```text
["-7", "2", "/"]  ->  -3
["7", "-2", "/"]  ->  -3
```

The true quotient is `-3.5`. Toward zero gives `-3`; flooring would give `-4`. Java's `/` is already correct - this is the case that breaks a Python port using `//`.

### Negative number tokens

```text
["2", "-3", "*"]   ->  -6
["-3", "-3", "-"]  ->  0
```

`"-3"` is parsed as a number, never mistaken for the operator. The second line is the sharpest test: three tokens start with `-` and only one is an operator.

### Zero on top

```text
["0", "5", "/"]  ->  0
```

`0 / 5 = 0`. Division by zero itself cannot happen - the problem guarantees a valid expression.

### Deep operand pile

```text
["1", "2", "3", "4", "5", "+", "+", "+", "+"]  ->  15
```

The stack grows to five values before the first operator fires. This is the brute force's worst shape and costs the stack version nothing extra.

### LeetCode's long example

```text
["10", "6", "9", "3", "+", "-11", "*", "/", "*", "17", "+", "5", "+"]  ->  22
```

`9 + 3 = 12`, `12 * -11 = -132`, `6 / -132 = 0` (truncation), `10 * 0 = 0`, `0 + 17 = 17`, `17 + 5 = 22`. It exercises a negative token and a truncation to zero in one go.

=== takeaway ===
> When you see **"each operator applies to the most recent values"** - postfix, nested brackets, undo - think **stack**. Push what is waiting, pop what gets consumed, push the result back because it is now waiting too.

### The core observation

The brute force only ever changed the last two evaluated values. A structure that only changes at one end is a stack, so scanning from the start every round was rereading data that could not have moved.

### The pattern trigger

```text
             read token
                 |
        +--------+--------+
        |                 |
     number            operator
        |                 |
      push         b = pop()   <- right operand FIRST
                   a = pop()
                   push(a op b)
                 |
                 v
      after the last token: stack holds exactly the answer
```

### The common mistakes

**Popping in the wrong order.** `stack.pop() - stack.pop()` computes `b - a`. It passes every test made of `+` and `*`.

**Detecting operators by first character.** `"-11".charAt(0) == '-'` is true. Check the whole token, or its length.

**Floor division.** In Java this is correct by default. In Python, `a // b` floors; use `int(a / b)`.

### What to remember in six months

> A stack holds values that have been produced but not yet consumed. Any problem where the consumer is always "the most recent producer" is a stack problem, whether or not the word appears.
