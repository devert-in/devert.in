=== intro ===
Yesterday's Find Peak Element showed that binary search does not need a sorted array - it needs a comparison that tells you which half to throw away. Today the data goes two-dimensional, and the same idea survives in a new shape: no midpoint at all, just one comparison per step that throws away a whole row or a whole column.

> Binary search is not "look at the middle". It is "every comparison discards a region the answer cannot be in". Pick the cell where one comparison can discard the most, and the search almost writes itself.

=== problem ===
You get an `m x n` integer matrix with two properties:

- every **row** is sorted ascending, left to right
- every **column** is sorted ascending, top to bottom

Return `true` if `target` appears anywhere in it, otherwise `false`.

```text
matrix =
  [ 1,  4,  7, 11, 15]
  [ 2,  5,  8, 12, 19]
  [ 3,  6,  9, 16, 22]
  [10, 13, 14, 17, 24]
  [18, 21, 23, 26, 30]

target = 13  ->  true     (row 3, column 1)
target = 20  ->  false
```

### What the two sortedness rules do NOT give you

It is tempting to read this as "the matrix is sorted", flatten it, and binary search. That fails. Read row 0 then row 1:

```text
row 0 ends with 15, row 1 starts with 2
```

The rows are not chained end to end. `2 < 15`, so the flattened sequence `1, 4, 7, 11, 15, 2, 5, ...` is not sorted, and a single binary search over it is wrong. That is the difference from **Search a 2D Matrix (LC 74)**, where each row starts after the previous row ends and one binary search over `m * n` cells is exactly right.

Here the order is only **partial**: you know a cell is smaller than everything to its right and everything below it, but you know nothing about how it compares to a cell that is up-and-to-the-right of it. `11` (row 0) and `10` (row 3) are an example - the larger one is in the earlier row.

### The constraints that matter

| constraint | value | what it means |
| :--------- | ----: | :------------ |
| `m`, `n` | 1 to 300 | never empty; up to 90,000 cells |
| values | -10^9 to 10^9 | fits in `int`; duplicates allowed |
| target | -10^9 to 10^9 | may be outside the matrix's range entirely |

90,000 cells is small enough that a full scan passes on LeetCode. The point of the problem is not that the scan is too slow - it is that the scan ignores two pieces of information the problem handed you.

=== pattern ===
**Staircase search** (also called *search space elimination* or the *saddleback* search).

It belongs to the binary search family for one reason: every comparison discards a block of cells that provably cannot hold the target. It is not halving, but it is the same contract.

### The one cell that makes a decision

Look at the four corners and ask: if I compare `target` against this cell, does the result tell me which way to go?

```text
top-left  (1):   right is bigger, down is bigger   -> target > 1 says "right OR down"  - no decision
bottom-right (30): left is smaller, up is smaller  -> target < 30 says "left OR up"    - no decision
top-right (15):  left is smaller, down is bigger   -> target < 15 says "left", target > 15 says "down"
bottom-left (18): up is smaller, right is bigger   -> target < 18 says "up",   target > 18 says "right"
```

From the **top-right** corner the two directions disagree: one only goes down in value, the other only goes up. So a single comparison picks exactly one direction - and, more importantly, it rules out an entire line of cells.

### Why a whole row or column disappears

Stand at `matrix[row][col]` where `col` is the rightmost column still in play and `row` is the topmost row still in play.

- If `matrix[row][col] > target`: everything **below** in this column is even larger (columns ascend). The whole column `col` is too big. Drop it: `col--`.
- If `matrix[row][col] < target`: everything **to the left** in this row is even smaller (rows ascend). The whole row `row` is too small. Drop it: `row++`.

Each step deletes one row or one column. There are only `m` rows and `n` columns, so after at most `m + n` steps there is nothing left.

### Recognising it

Reach for staircase search when:

- a 2D grid is sorted along **both** axes independently
- the question is membership, counting cells `<= x`, or finding pairs in two sorted lists
- a flat binary search does not apply because rows are not chained end to end

The mental question:

> Is there a starting point where "too big" and "too small" send me in two different directions, each of which discards a full line?

=== bruteForce ===
Ignore the sortedness entirely. Visit every cell, row by row, and stop the moment one equals the target.

### Step logic

1. For each `r` from `0` to `m - 1`
2. For each `c` from `0` to `n - 1`
3. If `matrix[r][c] == target`, return `true`
4. After the loops, return `false`

### Dry run

```text
target = 13
```

| step | r | c | matrix[r][c] | == 13? | action |
| ---: | -: | -: | -----------: | :----- | :----- |
| 1 | 0 | 0 | 1 | no | next |
| 2 | 0 | 1 | 4 | no | next |
| 3 | 0 | 2 | 7 | no | next |
| 4 | 0 | 3 | 11 | no | next |
| 5 | 0 | 4 | 15 | no | next row |
| 6 | 1 | 0 | 2 | no | next |
| 7 | 1 | 1 | 5 | no | next |
| 8 | 1 | 2 | 8 | no | next |
| 9 | 1 | 3 | 12 | no | next |
| 10 | 1 | 4 | 19 | no | next row |
| 11 | 2 | 0 | 3 | no | next |
| 12 | 2 | 1 | 6 | no | next |
| 13 | 2 | 2 | 9 | no | next |
| 14 | 2 | 3 | 16 | no | next |
| 15 | 2 | 4 | 22 | no | next row |
| 16 | 3 | 0 | 10 | no | next |
| 17 | 3 | 1 | 13 | **yes** | return `true` |

Correct after 17 comparisons. For `target = 20`, which is absent, the loop runs to the end: **25** comparisons, then `false`.

### Java

```java
class Solution {
    public boolean searchMatrix(int[][] matrix, int target) {

        for (int r = 0; r < matrix.length; r++) {
            for (int c = 0; c < matrix[r].length; c++) {
                if (matrix[r][c] == target) {
                    return true;
                }
            }
        }

        return false;
    }
}
```

### Complexity

**Time:** `O(m * n)` - **Space:** `O(1)`

### Where it hurts

Look at steps 5, 10 and 15. Each time we were at the end of a row holding a value **bigger** than 13 (`15`, `19`, `22`), and each time we kept going into the next row anyway. Worse, look at step 14: `16 > 13`, and column 3 ascends downward, so `17` and `26` below it are also bigger than 13. The scan does not care - if the target had been absent it would have checked them too.

The brute force throws away every comparison's information. "This cell is too big" means a whole column below it is too big; "this cell is too small" means a whole row to its left is too small. The scan learns that 25 times and uses it zero times.

### A better-but-not-best middle step

Rows are sorted, so you can binary search each row instead of scanning it: `O(m log n)`. On a 300 x 300 matrix that is about `300 * 9 = 2,700` comparisons instead of 90,000. It uses the row order but still ignores the column order completely - and that unused half is what the optimisation spends.

=== optimization ===
The waste is that a comparison tells us about a whole line of cells and we act on only one cell. So start where one comparison can retire a whole line: the **top-right** corner.

### Key observation

At the top-right cell of the region still in play, the row runs smaller to the left and the column runs larger downward. So:

```text
value > target  ->  this value and everything BELOW it is too big   ->  col--
value < target  ->  this value and everything LEFT of it is too small ->  row++
value == target ->  found
```

Each comparison permanently deletes one column or one row. The remaining region is always a rectangle whose top-right corner is the next cell to check.

### Step logic

1. `row = 0`, `col = n - 1`
2. While `row < m` and `col >= 0`:
   - equal: return `true`
   - too big: `col--`
   - too small: `row++`
3. Fell off the grid: return `false`

### Dry run - target = 13

| step | row | col | value | vs 13 | action | discarded |
| ---: | --: | --: | ----: | :---- | :----- | :-------- |
| 1 | 0 | 4 | 15 | bigger | `col--` | column 4 (15, 19, 22, 24, 30) |
| 2 | 0 | 3 | 11 | smaller | `row++` | row 0 (1, 4, 7, 11) |
| 3 | 1 | 3 | 12 | smaller | `row++` | row 1 (2, 5, 8, 12) |
| 4 | 2 | 3 | 16 | bigger | `col--` | column 3 (16, 17, 26) |
| 5 | 2 | 2 | 9 | smaller | `row++` | row 2 (3, 6, 9) |
| 6 | 3 | 2 | 14 | bigger | `col--` | column 2 (14, 23) |
| 7 | 3 | 1 | 13 | **equal** | return `true` | - |

7 comparisons instead of 17. The path is the "staircase":

```text
  [ 1,  4,  7, 11<-15]
  [ 2,  5,  8, 12, 19]
  [ 3,  6,  9<-16, 22]
  [10, 13<-14, 17, 24]
  [18, 21, 23, 26, 30]

  15 -> 11 -> 12 -> 16 -> 9 -> 14 -> 13
```

### Dry run - target = 20 (absent)

| step | row | col | value | vs 20 | action |
| ---: | --: | --: | ----: | :---- | :----- |
| 1 | 0 | 4 | 15 | smaller | `row++` |
| 2 | 1 | 4 | 19 | smaller | `row++` |
| 3 | 2 | 4 | 22 | bigger | `col--` |
| 4 | 2 | 3 | 16 | smaller | `row++` |
| 5 | 3 | 3 | 17 | smaller | `row++` |
| 6 | 4 | 3 | 26 | bigger | `col--` |
| 7 | 4 | 2 | 23 | bigger | `col--` |
| 8 | 4 | 1 | 21 | bigger | `col--` |
| 9 | 4 | 0 | 18 | smaller | `row++` -> `row = 5` |

`row = 5 == m`: the region is empty, return `false`. 9 comparisons instead of 25 - and the answer "absent" is now a proof, not a shrug, because every cell was either checked or discarded by a valid inequality.

### Why it never skips the target

Suppose the target is at `(tr, tc)`. While the search is still running, it is always true that `row <= tr` and `col >= tc`:

- we only `row++` when `matrix[row][col] < target`. If `row == tr`, then `matrix[tr][col] < matrix[tr][tc]` would need `col < tc` (row ascends), contradicting `col >= tc`. So we never step past row `tr`.
- symmetrically, we only `col--` when the value is bigger, which cannot happen at `col == tc` while `row <= tr`.

The pointers can only close in on `(tr, tc)`; they can never jump over it.

### Bottom-left works too

Start at `(m - 1, 0)`: bigger -> `row--`, smaller -> `col++`. Same proof, mirrored. Top-left and bottom-right do not work, because from there both neighbours move the value the same way.

=== complexity ===
### Time

Each iteration moves `row` down by one or `col` left by one. `row` can increase at most `m` times and `col` can decrease at most `n` times before the loop exits.

```text
O(m + n)
```

The source sheet lists this as `O(m + log n)`; that is a typo. The staircase never binary searches - it walks, and the walk is `O(m + n)`. If `m` is much smaller than `n`, binary searching each row (`O(m log n)`) can actually beat it.

### Space

Two integer indices.

```text
O(1)
```

### Comparison

| Approach | Time | Space | Uses row order | Uses column order |
| :------- | ---: | ----: | :------------- | :---------------- |
| Scan every cell | `O(m * n)` | `O(1)` | no | no |
| Binary search each row | `O(m log n)` | `O(1)` | yes | no |
| Staircase from top-right | **`O(m + n)`** | **`O(1)`** | yes | yes |

On the largest input (300 x 300):

| Approach | worst-case comparisons |
| :------- | ---------------------: |
| Scan every cell | 90,000 |
| Binary search each row | about 2,700 |
| Staircase | at most 599 |

=== implementation ===
```java
class Solution {
    public boolean searchMatrix(int[][] matrix, int target) {

        if (matrix.length == 0 || matrix[0].length == 0) {
            return false;
        }

        // Top-right corner: left is smaller, down is bigger.
        int row = 0;
        int col = matrix[0].length - 1;

        while (row < matrix.length && col >= 0) {
            int value = matrix[row][col];

            if (value == target) {
                return true;
            } else if (value > target) {
                col--;      // everything below in this column is even bigger
            } else {
                row++;      // everything left in this row is even smaller
            }
        }

        return false;
    }
}
```

### The lines that matter

**1.**

```java
int row = 0;
int col = matrix[0].length - 1;
```

The starting corner is the algorithm. Start at `(0, 0)` and both "right" and "down" increase the value, so a comparison that says "go bigger" cannot choose between them.

**2.**

```java
} else if (value > target) {
    col--;      // everything below in this column is even bigger
```

This is the elimination. It is not moving one cell left - it is deleting the entire remaining column, because the column ascends downward from here.

**3.**

```java
while (row < matrix.length && col >= 0) {
```

Two exits, one per direction of travel. `row` only grows and `col` only shrinks, so these are the only two walls the search can hit. Either one means the remaining rectangle is empty.

### Java notes

- `int[][]` in Java is an array of arrays. `matrix[0].length` is the column count, and LeetCode guarantees every row has the same length. The emptiness guard runs first so `matrix[0]` is never read on an empty array - LeetCode never sends one, but the guard costs nothing and makes the method safe to reuse.
- Reading `matrix[row][col]` into `value` once is not an optimisation the JIT needs, but it keeps the three branches readable and makes the dry run's "value" column map onto a real variable.
- No arithmetic on the values happens, only comparisons, so there is no overflow risk even with values at `-10^9` and `10^9`.

=== edgeCases ===
### 1 x 1, present and absent

```text
[[5]], target 5  ->  true
[[5]], target 3  ->  false
```

Start and end at `(0, 0)`. For `3`, `5 > 3` so `col--` makes `col = -1` and the loop exits.

### Single row

```text
[[1, 3, 5, 7]], target 3  ->  true
```

Starts at `7`, moves left `7 -> 5 -> 3`. With one row the staircase degrades to a linear scan from the right, `O(n)`. (A plain binary search would be `O(log n)` here - the staircase pays for its generality.)

### Single column

```text
[[1], [3], [5]], target 4  ->  false
```

`1 < 4` row++, `3 < 4` row++, `5 > 4` col-- to `-1`. Exit, `false`.

### Target smaller than every cell

```text
example matrix, target 0  ->  false
```

Every comparison is "bigger": `col` walks `4, 3, 2, 1, 0, -1` along row 0. Five steps.

### Target larger than every cell

```text
example matrix, target 31  ->  false
```

Every comparison is "smaller": `row` walks down column 4: `15, 19, 22, 24, 30`, then `row = 5`. Five steps.

### Target in the far corner from the start

```text
example matrix, target 18  ->  true
```

`18` is bottom-left - the farthest cell from top-right. The walk goes `15 < 18` down, `19 > 18` left, `12 < 18` down, `16 < 18` down, `17 < 18` down, `26 > 18` left, `23 > 18` left, `21 > 18` left, `18` found. Nine comparisons, still within `m + n - 1 = 9`.

### Duplicates

```text
[[1, 2, 2], [2, 2, 3]], target 2  ->  true
```

Sortedness is non-decreasing here. Equality is checked first, so duplicates never cause a wrong move: the first `2` reached returns `true`.

### Negative values

```text
[[-5, -2], [-3, 0]], target -3  ->  true
```

Start at `-2 > -3`, col-- to `-5 < -3`, row++ to `-3`. Only comparisons, so sign is irrelevant.

### Empty matrix

```text
[], target 1  ->  false
```

Outside LeetCode's constraints, but the guard returns `false` instead of throwing `ArrayIndexOutOfBoundsException` on `matrix[0]`.

=== takeaway ===
> When you see a grid **sorted along both rows and columns**, think **start at a corner where the two directions disagree** - top-right or bottom-left - and drop a whole row or column per comparison.

### The core observation

A comparison against a cell tells you about every cell that is ordered relative to it. From the top-right corner, "too big" condemns the whole column below and "too small" condemns the whole row to the left. Each step shrinks the problem by a full line, so the walk is `O(m + n)`.

### The pattern trigger

```text
     2D grid, rows ascend, columns ascend
                     |
                     v
       rows chained end to end? ---- yes ---> one binary search over m*n (LC 74)
                     |
                     no
                     v
       start at top-right (or bottom-left)
                     |
          +----------+----------+
          |          |          |
       bigger     equal      smaller
       col--     return      row++
     (drop col)   true     (drop row)
```

### The common mistakes

**Flattening and binary searching.** Only valid for LC 74. Here row 1 can start below row 0's end, so the flattened sequence is not sorted.

**Starting at top-left.** Both neighbours are bigger; when `target` is bigger too you have no rule for which way to go, and guessing can skip the answer.

**Calling it `O(log)`.** It is a walk, not a halving. `O(m + n)` is the honest bound, and an interviewer who asks will expect you to know the difference.

### What to remember in six months

> In a doubly sorted grid, the top-right corner is a binary search pivot for both dimensions at once: every comparison retires a row or a column.

The same walk counts how many cells are `<= x` in `O(m + n)`, which is the inner step of **Kth Smallest Element in a Sorted Matrix (LC 378)** - binary search on the value, staircase to count. It is also the two-pointer "pair with given sum" from two sorted arrays, drawn as a grid.
