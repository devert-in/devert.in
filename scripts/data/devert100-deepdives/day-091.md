=== intro ===
Day 87 left a promise unpaid. Greedy - "always take the largest coin that fits" - gives the fewest coins for Indian currency, but with coins `[1, 3, 4]` and amount `6` it picks `4 + 1 + 1` (three coins) when `3 + 3` (two coins) exists. Today we fix that properly.

> Greedy commits to one choice and never looks back. DP tries **every** choice for the last coin - but answers each smaller amount only once, so trying everything stays cheap.

The habit today: when a greedy has a counterexample, do not patch the greedy. Ask "what was the last coin?", try all of them, and let a table remember the sub-answers.

=== problem ===
Given coin denominations `coins` (unlimited supply of each) and a target `amount`, return the **fewest coins** that add up to exactly `amount`. If it cannot be made, return `-1`.

```text
coins = [1, 3, 4], amount = 6   ->   2      (3 + 3)
```

### Every way to make 6 from [1, 3, 4]

| combination | coins used |
| :---------- | ---------: |
| 1 + 1 + 1 + 1 + 1 + 1 | 6 |
| 3 + 1 + 1 + 1 | 4 |
| 4 + 1 + 1 | 3 |
| **3 + 3** | **2** |

The fewest is `2`. Greedy finds the `4 + 1 + 1` row, because it grabs `4` first and is then stuck with `2` left.

### LeetCode's examples

```text
coins = [1, 2, 5], amount = 11   ->   3      (5 + 5 + 1)
coins = [2],       amount = 3    ->  -1      (odd amount, only even coins)
coins = [1],       amount = 0    ->   0      (zero coins make zero)
```

### Constraints that matter

- `1 <= coins.length <= 12` - few denominations.
- `1 <= coins[i] <= 2^31 - 1` - a coin can be enormous. Any code that does `a - coin` and uses it as an index without checking is a crash waiting to happen.
- `0 <= amount <= 10^4` - small enough to make a table with one cell per amount.
- Unlimited supply: the same coin can be used any number of times. This is what makes it an **unbounded** knapsack.

### What makes it non-trivial

Two things. First, greedy is wrong for arbitrary coin systems, so the "obvious" fast answer is out. Second, the number of ways to combine coins grows explosively, so trying every combination is out too. The answer sits between them: try every last coin, but share the work.

=== pattern ===
**Unbounded Knapsack DP** - 1D DP over the amount, minimising.

### Why it is DP

Look at the **last coin** in an optimal answer for amount `a`. It is one of the denominations, say `c`. Remove it, and what remains is a way to make `a - c` - and it must be the *fewest* coins for `a - c`, or you could swap in a better one and beat the "optimal" answer. So:

```text
f(a) = 1 + min over every coin c <= a of f(a - c)
       ^              \______ best for the rest ______/
   the last coin
```

with `f(0) = 0` (nothing to pay, no coins).

That is Climbing Stairs again - "group by the last move" - except the moves are coin values, and we take a `min` instead of a sum.

### Why it is "unbounded"

After using coin `c` we recurse on `a - c` with the **same** full set of coins. Nothing is crossed off. That is the difference from 0/1 knapsack (day 93), where each item may be used once.

### The four steps

| Step | For Coin Change |
| :--- | :-------------- |
| State | `dp[a]` = fewest coins that make exactly `a` |
| Recurrence | `dp[a] = min(dp[a], dp[a - c] + 1)` for each coin `c <= a` |
| Base case | `dp[0] = 0`; every other cell starts at "impossible" |
| Order | `a` from `1` to `amount`, because `dp[a]` reads smaller amounts |

### Recognising it

Reach for unbounded knapsack when:

- you build a **target total** from **reusable** pieces
- the question is **min pieces**, **max value**, **can it be done**, or **how many ways**
- the target is a number small enough to index an array (here up to `10^4`)

The mental question:

> If I knew the best answer for every smaller total, could I get this total's answer by trying each possible last piece?

=== bruteForce ===
Pretend you do not know DP. The natural brute force: to make `a`, try each coin as the last coin, solve the rest recursively, and keep the best.

### Step logic

`f(a)` = fewest coins for `a`, or `-1` if impossible.

1. If `a == 0`, return `0`.
2. For each coin `c` with `c <= a`, compute `sub = f(a - c)`. If `sub` is not `-1`, `sub + 1` is a candidate.
3. Return the smallest candidate, or `-1` if there were none.

### Java

```java
class Solution {
    public int coinChange(int[] coins, int amount) {

        if (amount == 0) {
            return 0;                       // nothing left to pay
        }

        int best = -1;                      // -1 = no way found yet
        for (int coin : coins) {
            if (coin <= amount) {
                int sub = coinChange(coins, amount - coin);
                if (sub != -1 && (best == -1 || sub + 1 < best)) {
                    best = sub + 1;         // this coin last, plus the best for the rest
                }
            }
        }
        return best;
    }
}
```

### Why it is correct

Every valid combination has some last coin, and the recursion tries every coin in that role. For each, the rest is solved optimally by induction on the amount. The minimum over all last coins is therefore the true minimum. If no coin leads anywhere, every branch returned `-1`, and so does this call.

### Complexity

**Time:** `O(k^(amount / minCoin))` - exponential, with `k` coins branching at every level - **Space:** `O(amount)` call stack (with a coin of `1` the recursion goes `amount` deep)

### Where it hurts

Count each call in the table:

| call | times computed |
| :--- | -------------: |
| `f(6)` | 1 |
| `f(5)` | 1 |
| `f(4)` | 1 |
| `f(3)` | 2 |
| `f(2)` | 4 |
| `f(1)` | 6 |
| `f(0)` | 9 |

24 calls for 7 distinct amounts. `f(2) = 2` is rebuilt four times, `f(1)` six times. Fewest-coins-for-2 is a fixed fact about the coin set; it does not depend on which route reached it.

With `coins = [1, 2, 5]` and `amount = 11`, the recursion already makes 527 calls to answer 12 distinct questions. With `amount = 10^4` it would never finish - yet there are only `10^4 + 1` distinct questions.

=== optimization ===
**The repeated work:** `f(a)` for the same `a` is recomputed every time a different combination of earlier coins happens to leave `a` behind.

**The key observation:** `f(a)` depends only on `a`. So compute it once per amount, smallest first. When we reach `a`, every `f(a - c)` is already in the table.

### Deriving the table

1. `dp[0] = 0`.
2. Every other `dp[a]` starts as **"impossible"**. We use `amount + 1` for that: no real answer can need more than `amount` coins (even all `1`s use exactly `amount`), so `amount + 1` is safely bigger than anything real.
3. For `a = 1..amount`, try each coin `c <= a`: `dp[a] = min(dp[a], dp[a - c] + 1)`.
4. If `dp[amount]` is still `amount + 1`, nothing reached it: return `-1`.

### Why `amount + 1` and not `Integer.MAX_VALUE`

`dp[a - c] + 1` is computed for unreachable `a - c` too. With `Integer.MAX_VALUE`, that `+ 1` wraps to `Integer.MIN_VALUE` - a hugely *negative* number - and `min` would gladly pick it. `amount + 1` can be incremented without overflow and still means "impossible".

### Dry run - same example

`coins = [1, 3, 4]`, `amount = 6`. "Impossible" is `7`.

```text
start:  dp = [0, 7, 7, 7, 7, 7, 7]
```

| a | coin 1: dp[a-1] + 1 | coin 3: dp[a-3] + 1 | coin 4: dp[a-4] + 1 | dp[a] | dp after |
| -: | ------------------: | ------------------: | ------------------: | ----: | :------- |
| 1 | dp[0]+1 = 1 | too big | too big | **1** | `[0, 1, 7, 7, 7, 7, 7]` |
| 2 | dp[1]+1 = 2 | too big | too big | **2** | `[0, 1, 2, 7, 7, 7, 7]` |
| 3 | dp[2]+1 = 3 | dp[0]+1 = 1 | too big | **1** | `[0, 1, 2, 1, 7, 7, 7]` |
| 4 | dp[3]+1 = 2 | dp[1]+1 = 2 | dp[0]+1 = 1 | **1** | `[0, 1, 2, 1, 1, 7, 7]` |
| 5 | dp[4]+1 = 2 | dp[2]+1 = 3 | dp[1]+1 = 2 | **2** | `[0, 1, 2, 1, 1, 2, 7]` |
| 6 | dp[5]+1 = 3 | dp[3]+1 = 2 | dp[2]+1 = 3 | **2** | `[0, 1, 2, 1, 1, 2, 2]` |

`dp[6] = 2`, not `7`, so the answer is `2`. Eighteen coin checks instead of 24 recursive calls - and on `amount = 10^4` with 12 coins, at most 120,000 checks.

### Reading row 6 against greedy

Greedy picks coin `4` and is left with `dp[2] = 2` - total `3`. The table also tries coin `3`, which leaves `dp[3] = 1` - total `2`. Greedy's mistake was never trying the second option. The DP tries every option, and it can afford to because every `dp[a - c]` is a lookup.

### An unreachable amount

`coins = [2]`, `amount = 3`. "Impossible" is `4`.

| a | coin 2: dp[a-2] + 1 | dp[a] |
| -: | ------------------: | ----: |
| 1 | too big | 4 |
| 2 | dp[0]+1 = 1 | 1 |
| 3 | dp[1]+1 = 5 | min(4, 5) = 4 |

`dp[3] = 4 > 3`, so return `-1`. Note `dp[1] + 1 = 5` - the sentinel did get incremented, harmlessly. With `Integer.MAX_VALUE` as the sentinel, that is the step that would have wrapped negative.

=== complexity ===
### Time

`amount` cells, each trying all `k` coins once.

```text
O(k * amount)
```

### Space

One array of `amount + 1` integers.

```text
O(amount)
```

### Why

There are `amount + 1` distinct subproblems. Each one does `k` lookups into smaller, already-solved subproblems. The exponential tree of the brute force becomes a single left-to-right sweep.

### Comparison

| Approach | Time | Space | Correct for any coins? |
| :------- | ---: | ----: | :--------------------- |
| Greedy (largest first) | `O(k log k + amount / c)` | `O(1)` | no - only canonical systems |
| Plain recursion | exponential | `O(amount)` stack | yes, but times out |
| Memoised recursion | `O(k * amount)` | `O(amount)` + stack | yes |
| Bottom-up `dp[]` | **`O(k * amount)`** | **`O(amount)`** | yes |

The memoised version is fine in principle, but with a coin of `1` and `amount = 10^4` its recursion goes 10,000 calls deep, which is close to Java's default stack limit. Bottom-up has no recursion at all.

=== implementation ===
```java
class Solution {
    public int coinChange(int[] coins, int amount) {

        // dp[a] = fewest coins that make exactly a.
        int[] dp = new int[amount + 1];
        Arrays.fill(dp, amount + 1);   // "impossible": more coins than any real answer
        dp[0] = 0;                     // zero coins make zero

        for (int a = 1; a <= amount; a++) {
            for (int coin : coins) {
                if (coin <= a) {
                    dp[a] = Math.min(dp[a], dp[a - coin] + 1);   // coin as the last coin
                }
            }
        }

        return dp[amount] > amount ? -1 : dp[amount];
    }
}
```

### The lines that matter

**1.**

```java
dp[a] = Math.min(dp[a], dp[a - coin] + 1);   // coin as the last coin
```

The recurrence. `dp[a - coin]` is the best for what remains after paying `coin`; `+ 1` counts `coin` itself. `Math.min` with the current `dp[a]` keeps the best last coin seen so far.

**2.**

```java
Arrays.fill(dp, amount + 1);   // "impossible": more coins than any real answer
```

The sentinel. Large enough that no real answer reaches it, small enough that `+ 1` cannot overflow.

**3.**

```java
if (coin <= a) {
```

Guards the index. Coins can be up to `2^31 - 1`, so `a - coin` would be negative and `dp[a - coin]` would throw.

**4.**

```java
return dp[amount] > amount ? -1 : dp[amount];
```

Anything above `amount` can only be the untouched sentinel - `Math.min` never lets a cell climb past `amount + 1` - so it means unreachable.

### The memoised version (top-down)

```java
class Solution {
    public int coinChange(int[] coins, int amount) {
        int[] memo = new int[amount + 1];
        Arrays.fill(memo, -2);              // -2 = not computed; -1 = impossible
        return best(coins, amount, memo);
    }

    private int best(int[] coins, int a, int[] memo) {
        if (a == 0) {
            return 0;
        }
        if (memo[a] != -2) {
            return memo[a];
        }
        int result = -1;
        for (int coin : coins) {
            if (coin <= a) {
                int sub = best(coins, a - coin, memo);
                if (sub != -1 && (result == -1 || sub + 1 < result)) {
                    result = sub + 1;
                }
            }
        }
        memo[a] = result;
        return result;
    }
}
```

The brute force with a cache. Two sentinels are needed here, because `-1` ("impossible") is a legitimate, cacheable answer and must not be confused with "not computed yet".

### Java notes

- The loop order (amounts outer, coins inner) does not matter for this problem: we want a minimum, and every coin is tried for every amount either way. Tomorrow it will matter a lot.
- `int` is enough: answers are at most `10^4`.
- `Arrays.fill` lives in `java.util`, pre-imported on LeetCode.

=== edgeCases ===
### Amount zero

```text
coins = [1], amount = 0  ->  0
```

`dp = [0]`; the loop never runs; `dp[0] = 0` is not greater than `0`. Zero coins, not `-1`.

### Unreachable amount

```text
coins = [2], amount = 3  ->  -1
```

Only even totals are reachable. `dp[3]` keeps its sentinel `4`.

### Single coin that fits exactly

```text
coins = [1], amount = 1  ->  1
```

### A coin larger than the amount

```text
coins = [2147483647], amount = 2  ->  -1
```

The `coin <= a` guard skips it at every step, so nothing is ever subtracted. Without the guard, `dp[a - coin]` indexes a negative position.

### Greedy's counterexample

```text
coins = [1, 3, 4], amount = 6  ->  2
```

Greedy says `3` (`4 + 1 + 1`). The DP finds `3 + 3`.

### Amount not reachable with the small coins

```text
coins = [5, 10], amount = 3  ->  -1
```

Every coin is too big at every step. The table stays at the sentinel.

### Only the coin `1`

```text
coins = [1], amount = 10000  ->  10000
```

The largest possible answer - exactly `amount` coins. This is why `amount + 1` is a safe "impossible".

### Unsorted, awkward denominations

```text
coins = [186, 419, 83, 408], amount = 6249  ->  20
```

The coins do not need to be sorted, and no coin divides the others. The table does not care.

=== takeaway ===
> When you see **"fewest pieces to reach a total, pieces reusable"**, think **`dp[a] = min over pieces c of dp[a - c] + 1`, sentinel = impossible**. And distrust any greedy that has not been proven.

### The core observation

The optimal answer for `a` ends with some coin `c`, and what remains must be optimal for `a - c`. So try every coin as the last one. The answer for each amount depends only on the amount, so a table computes each once - in order of increasing amount, where every lookup is already done.

### The pattern trigger

```text
     build TARGET from REUSABLE pieces, optimise the count
                          |
                          v
            "what was the LAST piece?"  -> try every piece
                          |
                          v
        dp[a] = min( dp[a - c] + 1 )  over pieces c <= a
                          |
                          v
     dp[0] = 0, everything else = "impossible" (amount + 1)
                          |
                          v
          sweep a = 1..target; sentinel left -> return -1
```

### The common mistakes

**Using `Integer.MAX_VALUE` as infinity.** `MAX_VALUE + 1` wraps negative and wins every `min`. Use `amount + 1`, or check for the sentinel before adding.

**Trusting greedy.** It passes `[1, 2, 5]` and fails `[1, 3, 4]`. Greedy is correct only for "canonical" coin systems, and the problem never promises one.

**Returning `0` for impossible.** Zero is a real answer (for `amount = 0`). Impossible must be `-1`, and the final check must be against the sentinel, not against `0`.

**Missing the `coin <= a` guard.** With coins up to `2^31 - 1`, a negative index is guaranteed on some test.

### What to remember in six months

> Unbounded knapsack: one array indexed by the total, each cell tries every piece as the last piece. `min` for fewest, `max` for best value, `||` for possible, `+` for number of ways.

That last line is tomorrow: Coin Change II counts the ways instead of minimising - and the loop order, which did not matter today, decides whether you count combinations or permutations. The same shape solves Perfect Squares (LC 279 - the "coins" are `1, 4, 9, 16, ...`) and Minimum Cost For Tickets (LC 983).
