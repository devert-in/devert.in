=== intro ===
Yesterday two pointers moved at speeds 1 and 2 to find the middle. Today the exact same two pointers answer a completely different question: does this list ever end?

> When you cannot remember where you have been, run two walkers at different speeds. If the road loops, the faster one is guaranteed to catch the slower one from behind. If it does not loop, the faster one simply reaches the end.

=== problem ===
Given `head`, return `true` if the linked list contains a **cycle** - some node whose `next` points back to a node earlier in the list - and `false` otherwise.

```text
head = 3 -> 2 -> 0 -> -4
            ^          |
            +----------+          -4.next is node 2

answer = true
```

LeetCode describes the cycle with `pos`, the index the tail connects back to (`-1` for no cycle). Here `pos = 1`. **`pos` is not passed to your function** - it is only how the test data is built. You get `head` and nothing else.

### Three small examples

| list | pos | answer | why |
| :--- | --: | :----- | :-- |
| `3 -> 2 -> 0 -> -4` | 1 | `true` | `-4` points back to `2` |
| `1 -> 2` | 0 | `true` | `2` points back to `1` |
| `1` | -1 | `false` | `1.next` is `null` |

### Why this is not trivial

The usual way to walk a list is `while (node != null) node = node.next;`. On a list with a cycle that loop **never ends** - `null` never arrives. So "walk until the end" cannot be the test, because a cyclic list has no end to find.

And you cannot tell from one node whether you are in a loop. Every node looks the same: a value and a `next`. The only evidence of a cycle is **coming back to a node you have already visited**.

### Same node, not same value

"Visited" means the same **object**, not the same `val`. `1 -> 1 -> 1 -> null` has repeated values and no cycle. Every check in this problem compares references (`==` on nodes), never `val`.

### Constraints that matter

- `0` to `10^4` nodes. `head` can be `null`.
- The follow-up asks for `O(1)` memory - that is the real problem.

=== pattern ===
**Fast and slow pointers - Floyd's cycle detection.**

Same two pointers as Day 30: `slow` moves one node per round, `fast` moves two. The meaning is different.

- **No cycle:** `fast` runs ahead and hits `null`. Done - `false`.
- **Cycle:** neither pointer ever hits `null`. Both end up circling the loop, and because `fast` is faster, it eventually lands on the **same node** as `slow`. Done - `true`.

### Why they must meet (and cannot jump past each other)

Once both pointers are inside the loop, look at the gap from `fast` back to `slow` - how many steps `fast` still needs to catch up. Every round, `slow` moves 1 and `fast` moves 2, so the gap shrinks by **exactly 1**.

```text
gap:  4 -> 3 -> 2 -> 1 -> 0   meet
```

A gap that shrinks by exactly one per round cannot skip from `1` to `-1`. It must pass through `0`. That is why speed 2 against speed 1 is the standard choice: the relative speed is 1, so a meeting is guaranteed and happens within one lap of the cycle.

### Recognising it

Reach for Floyd when:

- a structure follows "next" pointers and might loop - linked lists, or **functions** like `x -> f(x)`
- you are asked to detect a loop with `O(1)` memory
- the sequence is generated by a rule (Happy Number LC 202: digit-square sums; Find the Duplicate Number LC 287: `i -> nums[i]`)

The mental question:

> If I keep following `next`, will I either stop or repeat? If I cannot afford to remember what I have seen, can a faster walker find the repeat for me?

=== bruteForce ===
The natural first idea: remember every node you have visited. If you ever reach one twice, there is a cycle. If you reach `null`, there is not.

### Step logic

1. Create an empty `HashSet<ListNode>` called `seen`.
2. Walk from `head`. For each node:
   - if `seen` already contains it, return `true`
   - otherwise add it and move to `next`
3. If you reach `null`, return `false`.

A hash set of **nodes** uses the object's identity (`ListNode` does not override `equals`/`hashCode`), so two different nodes with equal values are correctly treated as different.

### Dry run

```text
3 -> 2 -> 0 -> -4 -> (back to 2)
```

| step | node | already in `seen`? | action | `seen` after |
| ---: | ---: | :----------------- | :----- | :----------- |
| 1 | 3 | no | add, move to 2 | `{3}` |
| 2 | 2 | no | add, move to 0 | `{3, 2}` |
| 3 | 0 | no | add, move to -4 | `{3, 2, 0}` |
| 4 | -4 | no | add, move to `-4.next` = 2 | `{3, 2, 0, -4}` |
| 5 | 2 | **yes** | return `true` | `{3, 2, 0, -4}` |

Step 5 is the cycle: we are standing on node `2` for the second time.

On the acyclic list `1 -> 2 -> null`, the walk adds `1`, adds `2`, reaches `null` and returns `false`.

### Java

```java
public class Solution {
    public boolean hasCycle(ListNode head) {

        Set<ListNode> seen = new HashSet<>();

        for (ListNode node = head; node != null; node = node.next) {
            if (!seen.add(node)) {      // add returns false if already present
                return true;
            }
        }

        return false;   // reached null: the list ends, so no cycle
    }
}
```

### Complexity

**Time:** `O(n)` - **Space:** `O(n)`

### Where it hurts

The time is optimal - you have to reach the cycle before you can see it.

The cost is memory: up to `10^4` node references in a hash set, each with hashing and boxing overhead, to answer a yes/no question. The follow-up explicitly asks for `O(1)` space.

Now look at what the set is *for*. It remembers every node so that a revisit can be recognised. But we do not care **which** node repeats, or **when** it first repeated. We only need to know that **some** repeat happens. Storing `n` facts to extract one bit is the waste.

> Is there a way to prove "this walk repeats" without remembering where it has been?

=== optimization ===
Replace memory with motion.

### The key observation

If the list has a cycle, any walker that enters it stays in it forever. Put **two** walkers on the list at different speeds. In a loop, the faster one keeps gaining on the slower one, and since it gains exactly one node per round, it eventually lands on the slower one. In a list with an end, the faster one simply falls off.

So:

- `fast` reaches `null` -> **no cycle**
- `slow == fast` at some point -> **cycle**

Two references, no set.

### Dry run

Same list. Label nodes by value (all distinct here):

```text
3 -> 2 -> 0 -> -4 -> (back to 2)
```

| round | slow (start) | fast (start) | slow moves to | fast moves to | `slow == fast`? |
| ----: | -----------: | -----------: | ------------: | :------------ | :-------------- |
| - | 3 | 3 | - | - | not checked (both start at head) |
| 1 | 3 | 3 | 2 | 3 -> 2 -> **0** | no |
| 2 | 2 | 0 | 0 | 0 -> -4 -> **2** | no |
| 3 | 0 | 2 | -4 | 2 -> 0 -> **-4** | **yes** - return `true` |

Read the gap. After round 1 `fast` is on `0`, one node ahead of `slow` on `2`. Inside the loop `2 -> 0 -> -4 -> 2` (length 3), `fast` needs 2 more steps to reach `slow` from behind. After round 2 that gap is 1. After round 3 it is 0. One per round, exactly as promised.

### The no-cycle dry run

```text
1 -> 2 -> 3 -> null
```

| round | slow (start) | fast (start) | `fast != null && fast.next != null`? | slow (end) | fast (end) |
| ----: | -----------: | -----------: | :----------------------------------- | ---------: | ---------: |
| 1 | 1 | 1 | yes | 2 | 3 |
| 2 | 2 | 3 | no (`3.next` is `null`) | - | - |

The loop exits and the method returns `false`. `fast` found the end, which proves there is no cycle.

### Why compare after moving

Both pointers start on `head`, so they are equal before anyone moves. Checking `slow == fast` at the top of the loop would return `true` immediately on every list. Move first, then compare.

### How long it takes

Let `a` be the number of nodes before the cycle and `c` the cycle length. `slow` enters the cycle after `a` rounds. From then on the gap is less than `c` and shrinks by one per round, so they meet within `c` more rounds. Total under `a + c <= n` rounds - linear.

=== complexity ===
### Time

At most about `n` rounds, as above, with constant work each.

```text
O(n)
```

### Space

Two references.

```text
O(1)
```

### Comparison

| Approach | Time | Extra space | Tells you where the cycle starts? |
| :------- | ---: | ----------: | :-------------------------------- |
| HashSet of visited nodes | `O(n)` | `O(n)` | yes - the first repeated node |
| Floyd (slow +1, fast +2) | **`O(n)`** | **`O(1)`** | not directly - needs a second phase (LC 142) |

The set version gives you more information for free, which is why it is the right first answer to say out loud. Floyd gives you exactly the bit you asked for, in constant memory - and with one extra phase it recovers the start too.

=== implementation ===
```java
public class Solution {
    public boolean hasCycle(ListNode head) {

        ListNode slow = head;
        ListNode fast = head;

        // If fast can't take two steps, the list has an end -> no cycle.
        while (fast != null && fast.next != null) {
            slow = slow.next;          // 1 step
            fast = fast.next.next;     // 2 steps

            if (slow == fast) {        // same NODE, not same value
                return true;
            }
        }

        return false;
    }
}
```

### The lines that matter

**1.**

```java
while (fast != null && fast.next != null) {
```

The exact guard from Day 30. It does double duty here: it keeps `fast.next.next` from throwing, and it **is** the no-cycle answer - if this ever fails, `fast` found the end.

**2.**

```java
if (slow == fast) {        // same NODE, not same value
```

`==` on objects compares references. Writing `slow.val == fast.val` reports a cycle on `1 -> 1 -> null`, which has none.

**3.**

```java
slow = slow.next;          // 1 step
fast = fast.next.next;     // 2 steps
```

Move **before** comparing. Both start at `head`; comparing first would return `true` on every non-empty list.

### Follow-up: where does the cycle start? (LC 142)

After they meet, put one pointer back on `head` and leave the other on the meeting node. Move both **one** step at a time. They meet again exactly at the start of the cycle.

```java
public class Solution {
    public ListNode detectCycle(ListNode head) {

        ListNode slow = head;
        ListNode fast = head;

        while (fast != null && fast.next != null) {
            slow = slow.next;
            fast = fast.next.next;

            if (slow == fast) {
                // Phase 2: equal speeds from head and from the meeting point.
                ListNode finder = head;
                while (finder != slow) {
                    finder = finder.next;
                    slow = slow.next;
                }
                return finder;   // the first node of the cycle
            }
        }

        return null;   // no cycle
    }
}
```

**Why it works.** Let `a` = steps from `head` to the cycle start, `b` = steps from the cycle start to the meeting point, `c` = cycle length. At the meeting, `slow` has walked `a + b` and `fast` has walked twice that. `fast`'s extra distance is a whole number of laps:

```text
2(a + b) = a + b + k*c     ->     a + b = k*c     ->     a = k*c - b
```

`k*c - b` steps from the meeting point is: finish the lap (`c - b` steps) to the cycle start, then go round `k - 1` more full laps. So a walker from `head` and a walker from the meeting point, both taking `a` steps, arrive at the cycle start together.

On our example: `a = 1` (`3 -> 2`), `c = 3`, meeting at `-4` so `b = 2`. Check: `a + b = 3 = 1 * c`. From `-4`, one step reaches `2`; from `head`, one step reaches `2`. Cycle start: node `2`.

### Java notes

- LeetCode's template for these two problems is `public class Solution` - either `public class` or plain `class` is accepted.
- `HashSet.add` returns `false` when the element is already present, which lets the brute force check and insert in one call.
- `ListNode` does not override `equals` or `hashCode`, so both `HashSet<ListNode>` and `==` work on identity - exactly what "same node" means.

=== edgeCases ===
### Empty list

```text
head = null  ->  false
```

`fast != null` fails immediately. A list with no nodes cannot loop.

### Single node, no cycle

```text
1 -> null  ->  false
```

`fast.next` is `null`, the loop never runs.

### Single node pointing to itself

```text
1 -> (back to 1)   pos = 0  ->  true
```

Round 1: `slow = 1.next = 1`, `fast = 1.next.next = 1`. Equal - `true`. The smallest possible cycle.

### Two nodes, tail back to head

```text
1 -> 2 -> (back to 1)   pos = 0  ->  true
```

Round 1: `slow = 2`, `fast = 1`. Round 2: `slow = 1`, `fast = 1`. Equal.

### Two nodes, no cycle

```text
1 -> 2 -> null  ->  false
```

Round 1: `slow = 2`, `fast = null`. The loop exits.

### Tail points to itself

```text
1 -> 2 -> 3 -> 4 -> (back to 4)   pos = 3  ->  true
```

A cycle of length 1 at the far end. `fast` arrives first and spins in place on `4` until `slow` walks in.

### Repeated values, no cycle - the trap

```text
1 -> 1 -> 1 -> null  ->  false
```

Any approach that tracks seen **values** says `true` here. Comparing references gives the right answer.

### Longest acyclic list

```text
10^4 nodes, pos = -1  ->  false
```

`fast` reaches the end after about `5000` rounds. No memory grows with `n`.

=== takeaway ===
> When you see **"does this sequence loop?"** and you cannot afford to remember every step, think **slow +1, fast +2**. They meet if and only if there is a cycle.

### The core observation

Inside a cycle, `fast` gains exactly one node on `slow` per round, so the gap counts down to zero and a meeting is unavoidable. Outside a cycle, `fast` reaches `null`. Two pointers therefore answer "is there a repeat?" without storing a single visited node.

### The pattern trigger

```text
     follow next / f(x) repeatedly
                 |
                 v
     slow = slow.next          fast = fast.next.next
                 |
        +--------+---------+
        |                  |
  fast hits null      slow == fast
        |                  |
     no cycle            cycle
                           |
                           v
            (LC 142) reset one to head,
            both +1, meet at cycle start
```

### The common mistakes

**Comparing before moving.** Both start at `head`, so the first comparison is always `true`.

**Comparing values.** `slow.val == fast.val` fails on any list with duplicates.

**Guarding only `fast.next`.** On an even-length acyclic list `fast` becomes `null` and `fast.next` throws.

**Walking until `null` with no second pointer.** On a cyclic list that loop never ends - the test times out rather than failing.

### What to remember in six months

> Two speeds, one meeting. If they meet, it loops; if `fast` falls off, it ends. Then: reset one to `head`, both at speed 1, and they meet at the loop's entrance.

The same idea works on anything that maps a value to a "next" value: Happy Number (LC 202) runs it on digit-square sums, and Find the Duplicate Number (LC 287) runs both phases on `i -> nums[i]` to find the repeated value without modifying the array.
