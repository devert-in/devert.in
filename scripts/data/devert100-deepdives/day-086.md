=== intro ===
Day 85's greedy needed a heap to keep re-ranking. Today's greedy needs nothing but a running sum - the hard part is not the code, it is **proving** that a shortcut is safe.

> A failed attempt is information. When a simulation from start `s` dies at station `k`, it has not just ruled out `s` - it has ruled out every start between `s` and `k`. Learning to ask "what else did that failure just rule out?" is what turns `O(n^2)` into `O(n)`.

=== problem ===
There are `n` gas stations on a **circular** route. Station `i` gives you `gas[i]` fuel, and driving from station `i` to station `i + 1` costs `cost[i]` fuel. Your tank is unlimited and starts **empty**. Return the index of the station you can start from to drive all the way around once, or `-1` if no start works. If a solution exists, it is unique.

```text
gas  = [1, 2, 3, 4, 5]
cost = [3, 4, 5, 1, 2]
output = 3
```

### The net gain at each station

What matters at each station is not `gas` or `cost` alone, but the difference: how much fuel you are up (or down) after filling there and driving to the next one.

| station | gas | cost | `gas - cost` |
| ------: | --: | ---: | -----------: |
| 0 | 1 | 3 | -2 |
| 1 | 2 | 4 | -2 |
| 2 | 3 | 5 | -2 |
| 3 | 4 | 1 | +3 |
| 4 | 5 | 2 | +3 |

Starting at 3: tank goes `3 -> 6 -> 4 -> 2 -> 0`. It never dips below zero, and it arrives back at station 3 with exactly `0` - which is allowed.

### What makes it non-trivial

1. **Circular.** After station `n - 1` comes station `0`. Any simulation has to wrap around.
2. **The tank must never go negative at any point**, not just at the end. Enough total fuel is necessary but not sufficient on its own for a given start - starting at `0` here would fail immediately even if the totals were fine.
3. **Arriving with exactly `0` is fine.** The check is `tank < 0`, not `tank <= 0`.

Constraints: `1 <= n <= 10^5`, `0 <= gas[i], cost[i] <= 10^4`.

=== pattern ===
**Greedy - running sum with reset**, the same skeleton as Kadane's algorithm.

### Two facts carry the whole solution

**Fact 1 - the total decides whether any answer exists.** If `sum(gas) < sum(cost)`, you burn more than you collect over one lap, so every start fails: return `-1`. If `sum(gas) >= sum(cost)`, some start works (proved in the optimization section).

**Fact 2 - a failure rules out a whole range.** If you start at `s` and the tank first goes negative after station `k`, then no station from `s` to `k` can be the start. You can jump straight to `k + 1`.

Why fact 2 holds: when you reached any station `m` between `s` and `k`, your tank was `>= 0` - you had not failed yet. Starting at `m` instead means arriving there with `0`, which is **no better**. If you still failed at `k` carrying that extra fuel, you will certainly fail at or before `k` without it.

```text
start s ............ m ............ k   (tank < 0 here)
        tank >= 0 at m
        starting fresh at m = same trip minus a non-negative head start
        -> also fails by k
```

### Recognising it

- a circular or linear walk with a running balance that must never drop below zero
- "find the starting point" where trying every start is the brute force
- a running sum where a negative prefix is useless baggage (Kadane's reset)

The mental question:

> If my running sum goes negative at `k`, could starting anywhere in the stretch I just walked have done better? If not, reset and start after `k`.

=== bruteForce ===
Try every station as the start, and drive the full lap from it. The first start that never runs dry is the answer.

### Step logic

1. For each `start` from `0` to `n - 1`:
   - `tank = 0`
   - for `step = 0 .. n-1`: station `i = (start + step) % n`; `tank += gas[i] - cost[i]`; if `tank < 0`, this start fails - stop.
   - if all `n` steps succeed, return `start`.
2. If no start succeeds, return `-1`.

### Dry run

```text
gas  = [1, 2, 3, 4, 5]
cost = [3, 4, 5, 1, 2]
gain = [-2, -2, -2, +3, +3]
```

| start | step | station `i` | tank before | `gas[i] - cost[i]` | tank after | status |
| ----: | ---: | ----------: | ----------: | -----------------: | ---------: | :----- |
| 0 | 0 | 0 | 0 | -2 | -2 | fails at 0 |
| 1 | 0 | 1 | 0 | -2 | -2 | fails at 1 |
| 2 | 0 | 2 | 0 | -2 | -2 | fails at 2 |
| 3 | 0 | 3 | 0 | +3 | 3 | ok |
| 3 | 1 | 4 | 3 | +3 | 6 | ok |
| 3 | 2 | 0 | 6 | -2 | 4 | ok (wrapped) |
| 3 | 3 | 1 | 4 | -2 | 2 | ok |
| 3 | 4 | 2 | 2 | -2 | 0 | ok - full lap done |

```text
return 3
```

Correct. On this input the failures are quick, so it only took 8 steps.

### Java

```java
class Solution {
    public int canCompleteCircuit(int[] gas, int[] cost) {

        int n = gas.length;

        for (int start = 0; start < n; start++) {
            int tank = 0;
            boolean ok = true;

            for (int step = 0; step < n; step++) {
                int i = (start + step) % n;           // wrap around the circle
                tank += gas[i] - cost[i];
                if (tank < 0) {
                    ok = false;
                    break;
                }
            }

            if (ok) return start;
        }

        return -1;
    }
}
```

### Complexity

**Time:** `O(n^2)` - up to `n` starts, up to `n` steps each. **Space:** `O(1)`.

### Where it hurts

Make the failures happen late. Here every start runs almost a full lap before dying:

```text
gas  = [2, 2, 2, 2, 0]
cost = [1, 1, 1, 1, 5]
gain = [+1, +1, +1, +1, -5]
```

| start | stations driven | tanks after each | fails at |
| ----: | :-------------- | :--------------- | -------: |
| 0 | 0, 1, 2, 3, 4 | 1, 2, 3, 4, -1 | 4 |
| 1 | 1, 2, 3, 4 | 1, 2, 3, -2 | 4 |
| 2 | 2, 3, 4 | 1, 2, -3 | 4 |
| 3 | 3, 4 | 1, -4 | 4 |
| 4 | 4 | -5 | 4 |

Answer `-1`, after 15 steps. Every row re-drives stations it already drove in the row above, and dies at the **same** station `4`.

Two pieces of waste are visible in that table:

1. **Start 0 failing at 4 already told us starts 1-4 fail.** Each of them is the same trip with a non-negative head start removed. Rows 2-5 are pure repetition.
2. **The answer was decided before any simulation.** `sum(gain) = 4 - 5 = -1 < 0`. No start can survive a lap that loses fuel overall.

Use both facts and one pass is enough.

=== optimization ===
### The observation

From the pattern section: if a run starting at `s` first goes negative at station `k`, every start in `s..k` fails, so the next candidate is `k + 1`. And the candidate starts never move backwards, so one left-to-right pass visits each station once.

That pass leaves one question: the final candidate's run reaches station `n - 1` without failing - but it has not driven the wrap-around part (`0 .. start-1`) yet. That is where the total comes in: **if the total gain is `>= 0`, the final candidate survives the wrap-around too.** So:

1. `total` = running sum of every `gas[i] - cost[i]` (decides `-1`)
2. `tank` = running sum since the current candidate `start`
3. whenever `tank < 0`: `start = i + 1`, `tank = 0`
4. at the end: `total >= 0 ? start : -1`

### Dry run

```text
gain = [-2, -2, -2, +3, +3]
total = 0, tank = 0, start = 0
```

| i | gain | total after | tank after `+= gain` | `tank < 0`? | start | tank after reset |
| -: | ---: | ----------: | -------------------: | :---------- | ----: | ---------------: |
| 0 | -2 | -2 | -2 | yes | 1 | 0 |
| 1 | -2 | -4 | -2 | yes | 2 | 0 |
| 2 | -2 | -6 | -2 | yes | 3 | 0 |
| 3 | +3 | -3 | 3 | no | 3 | 3 |
| 4 | +3 | 0 | 6 | no | 3 | 6 |

```text
total = 0 >= 0  ->  return start = 3
```

Five steps instead of eight - and on the "where it hurts" input, five steps instead of fifteen:

| i | gain | total after | tank after `+= gain` | `tank < 0`? | start |
| -: | ---: | ----------: | -------------------: | :---------- | ----: |
| 0 | +1 | 1 | 1 | no | 0 |
| 1 | +1 | 2 | 2 | no | 0 |
| 2 | +1 | 3 | 3 | no | 0 |
| 3 | +1 | 4 | 4 | no | 0 |
| 4 | -5 | -1 | -1 | yes | 5 |

`total = -1 < 0`, so return `-1`. (The candidate `start = 5` is never returned - more on that in the implementation notes.)

### Proving the reset is safe (the follow-up interviewers ask)

Let `P(i) = gain[0] + ... + gain[i]`, with `P(-1) = 0`.

**What the reset really tracks.** `tank` at station `i` equals `P(i) - P(start - 1)`. A reset happens when that goes negative, i.e. when `P(i)` drops **strictly below** the prefix value at the last reset point. So each reset marks a new strict minimum of `P`, and the final `start - 1` is the (first) position where `P` is smallest.

**Every station after `start` is fine.** For `start <= j <= n-1`, the tank is `P(j) - P(start-1) >= 0`, because `P(start-1)` is the minimum.

**The wrap-around is fine.** For `j < start`, the tank after driving `start .. n-1` and then `0 .. j` is:

```text
(P(n-1) - P(start-1)) + P(j)  =  P(n-1) + (P(j) - P(start-1))
                                    >= 0         >= 0
```

`P(n-1)` is the total, assumed `>= 0`; and `P(j) >= P(start-1)` because `P(start-1)` is the minimum. So the tank never goes negative anywhere on the lap. That is the whole proof: **start right after the lowest point of the running sum.**

```text
P:   0   -2   -4   -6   -3    0
         i=0  i=1  i=2  i=3  i=4
                    ^
              minimum at i=2  ->  start = 3
```

=== complexity ===
### Time

One pass over `n` stations, constant work per station.

```text
O(n)
```

### Space

Three integers: `total`, `tank`, `start`.

```text
O(1)
```

### Comparison

| Approach | Time | Space | Key idea |
| :------- | ---: | ----: | :------- |
| Try every start, simulate a lap | `O(n^2)` | `O(1)` | none |
| Running sum with reset + total check | **`O(n)`** | **`O(1)`** | a failure at `k` rules out `s..k` |

An equivalent `O(n)` formulation: compute the prefix sums, find the index of the minimum, answer is that index `+ 1` (mod `n`) if the total is `>= 0`. Same proof, two passes instead of one.

=== implementation ===
```java
class Solution {
    public int canCompleteCircuit(int[] gas, int[] cost) {

        int total = 0;      // net fuel over the whole lap - decides -1
        int tank = 0;       // net fuel since the current candidate start
        int start = 0;      // current candidate

        for (int i = 0; i < gas.length; i++) {
            int gain = gas[i] - cost[i];
            total += gain;
            tank += gain;

            if (tank < 0) {         // cannot reach i + 1 from start, or from anything in between
                start = i + 1;
                tank = 0;
            }
        }

        return total >= 0 ? start : -1;
    }
}
```

### The lines that matter

**1.**

```java
if (tank < 0) {         // cannot reach i + 1 from start, or from anything in between
```

Strict `<`. Arriving with exactly `0` is allowed, so a tank of `0` must not trigger a reset - `gas = [1, 1]`, `cost = [1, 1]` has every tank at `0` and the answer is `0`.

**2.**

```java
start = i + 1;
tank = 0;
```

Jump past the whole failed stretch, not to `start + 1`. Moving to `start + 1` is correct but brings back the `O(n^2)`.

**3.**

```java
return total >= 0 ? start : -1;
```

The total is the existence check, and the proof shows it also covers the wrap-around - which is why the loop never has to drive past `n - 1`.

### Java notes

- `start` can end up as `n` (a reset on the last station). That only happens when `P(n-1)` is a new strict minimum below `0` - so `total < 0` and `-1` is returned. `n` is never returned.
- No overflow: `|total| <= 10^5 * 10^4 = 10^9`, inside `int`.
- `total` and `tank` are separate on purpose. `tank` is reset; `total` never is.

=== edgeCases ===
### Not enough fuel overall

```text
gas = [2, 3, 4], cost = [3, 4, 3]  ->  -1
```

LeetCode's second example. Total gain `9 - 10 = -1`.

### Single station, enough fuel

```text
gas = [5], cost = [4]  ->  0
```

### Single station, not enough

```text
gas = [4], cost = [5]  ->  -1
```

### Every tank exactly zero

```text
gas = [1, 1], cost = [1, 1]  ->  0
```

The tank is `0` everywhere. `0 < 0` is false, so no reset. Writing `tank <= 0` would move the start to `2` and the total check would still pass - returning an index that does not exist.

### Answer is station 0

```text
gas = [3, 1, 1], cost = [1, 2, 2]  ->  0
```

Gains `+2, -1, -1`. Tank `2, 1, 0` - no reset ever happens.

### Answer is the last station

```text
gas = [0, 0, 5], cost = [1, 1, 3]  ->  2
```

Gains `-1, -1, +2`. Resets at `0` and `1`, leaving `start = 2`, total `0`. Check: from `2` the tank goes `2 -> 1 -> 0`.

### Late failure everywhere

```text
gas = [2, 2, 2, 2, 0], cost = [1, 1, 1, 1, 5]  ->  -1
```

The brute force's worst case. The greedy reads it once and the total settles it.

### Zero-gain stations

```text
gas = [0, 0, 0], cost = [0, 0, 0]  ->  0
```

Nothing gained, nothing spent. Every start works; the greedy returns `0`.

=== takeaway ===
> When you see **"find the start of a circular trip where a running balance must never go negative"**, think **total decides existence; reset the start after every failure**.

### The core observation

If the run from `s` dies at `k`, every start in `s..k` dies by `k` too - they are the same trip with a non-negative head start removed. So skip to `k + 1`. And if the lap's total is non-negative, the start right after the running sum's lowest point survives the whole loop, wrap-around included.

### The pattern trigger

```text
       circular route, running balance must stay >= 0
                         |
                         v
          total gain < 0  ->  return -1  (no start can work)
                         |
                         v
       one pass:  tank += gain
                  tank < 0  ->  start = i + 1, tank = 0
                         |
                         v
          answer = start (just after the minimum prefix sum)
```

### The common mistakes

**`tank <= 0` instead of `< 0`.** Arriving empty is fine; resetting on zero can push `start` past the last index.

**Resetting `start` to `start + 1`.** Correct, but it is the brute force again.

**Forgetting the total check**, and trying to prove the candidate by simulating the wrap-around. The total already proves it.

**Mixing up `total` and `tank`.** Reset only `tank`. `total` covers the whole lap.

### What to remember in six months

> A failure at `k` disqualifies every start up to `k`. Start after the lowest point of the running sum.

The same reset-on-negative skeleton is Kadane's algorithm (Maximum Subarray, LC 53), and the "a failure rules out a range" argument reappears in Jump Game, in Best Time to Buy and Sell Stock (reset the buy day at a new low), and in any "minimum starting value" problem (LC 1413).
