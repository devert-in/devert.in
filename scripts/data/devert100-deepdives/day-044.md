=== intro ===
Week 7 opened with stacks, queues and the monotonic deque of Sliding Window Maximum - structures that remember what you have already seen. Today the topic changes to **Binary Search**, and the habit changes with it: instead of remembering more, you learn to **throw away half of what is left** with every single comparison.

> A sorted array is not just "data in order". It is a promise that one comparison against the middle tells you which half the answer cannot be in. Binary search is the discipline of cashing that promise in, every step, without an off-by-one.

=== problem ===
Given an array `nums` sorted in **ascending** order with **distinct** values, and an integer `target`, return the index of `target`, or `-1` if it is not there. The required time is `O(log n)`.

```text
nums   = [-1, 0, 3, 5, 9, 12]
target = 9
answer = 4
```

```text
nums   = [-1, 0, 3, 5, 9, 12]
target = 2
answer = -1
```

| index | 0 | 1 | 2 | 3 | 4 | 5 |
| :---- | -: | -: | -: | -: | -: | -: |
| value | -1 | 0 | 3 | 5 | **9** | 12 |

`nums[4] = 9`, so the first example returns `4`. There is no `2` anywhere, so the second returns `-1`.

### The constraints that matter

- `1 <= nums.length <= 10^4` - never empty on LeetCode, but the code we write will handle empty anyway.
- `-10^4 < nums[i], target < 10^4`.
- All values are **unique**. With duplicates "the index of target" would be ambiguous - that is tomorrow's problem (LC 34).
- `nums` is **sorted ascending**. This is the whole problem. Remove it and the best you can do is look at every element.
- **`O(log n)`** is stated outright. A linear scan is correct and will be accepted by the judge on these sizes, but it is not the answer being asked for.

### Why this is worth a full day

Every binary search you will ever write - lower bound, upper bound, search on the answer, rotated arrays, peak finding - is this loop with a different condition. The three things that go wrong (the loop condition, the update of `lo`/`hi`, and the midpoint) all show up here in their simplest form. Get them exactly right once and the next four days are variations, not new algorithms.

=== pattern ===
**Classic Binary Search.**

The idea: keep a window `[lo, hi]` of indices where the target **could still be**. Look at the middle element. Because the array is sorted, that one comparison rules out an entire half:

```text
if nums[mid] <  target:  everything at mid and LEFT of mid is even smaller  -> discard left
if nums[mid] >  target:  everything at mid and RIGHT of mid is even larger  -> discard right
if nums[mid] == target:  found it
```

### The invariant

> If `target` is anywhere in `nums`, it is at some index in `[lo, hi]`.

At the start `lo = 0`, `hi = n - 1` - the whole array, so the invariant holds trivially. Each step discards only indices that provably cannot hold `target`, so it keeps holding. When the window becomes empty (`lo > hi`), the invariant says the target is nowhere - return `-1`.

### The picture

```text
 lo                 mid                  hi
  |                  |                    |
[-1,   0,   3,   5,   9,   12]
           all < nums[mid]  |  all > nums[mid]
```

One comparison, half the window gone. Six elements become three, three become one, one becomes zero. That is `log2(n)` steps.

### Recognising it

Reach for binary search when:

- the input is **sorted** (or sorted after a rotation, or sorted along some axis)
- the problem demands **`O(log n)`** - nothing else on a plain array gives that
- you need "the first / last position where something becomes true"
- the answer is a number in a range and you can test "is `x` big enough?" (this is binary search on the answer - day 46)

The mental question:

> If I look at one element in the middle, can I say for certain that the answer is **not** on one side of it?

If yes, binary search applies, sorted array or not. That question is what makes Find Peak Element (day 48) a binary search problem even though its array is unsorted.

=== bruteForce ===
Forget the ordering for a moment. The obvious answer: look at every element, left to right, until one equals `target`.

### Step logic

1. For `i` from `0` to `n - 1`:
2. If `nums[i] == target`, return `i`.
3. If the loop finishes, the target is absent: return `-1`.

### Dry run - target present

```text
nums = [-1, 0, 3, 5, 9, 12], target = 9
```

| step | i | nums[i] | nums[i] == 9? | action | comparisons so far |
| ---: | -: | ------: | :------------ | :----- | -----------------: |
| 1 | 0 | -1 | no | next | 1 |
| 2 | 1 | 0 | no | next | 2 |
| 3 | 2 | 3 | no | next | 3 |
| 4 | 3 | 5 | no | next | 4 |
| 5 | 4 | 9 | **yes** | return `4` | 5 |

### Dry run - target absent

```text
nums = [-1, 0, 3, 5, 9, 12], target = 2
```

| step | i | nums[i] | nums[i] == 2? | action | comparisons so far |
| ---: | -: | ------: | :------------ | :----- | -----------------: |
| 1 | 0 | -1 | no | next | 1 |
| 2 | 1 | 0 | no | next | 2 |
| 3 | 2 | 3 | no | next | 3 |
| 4 | 3 | 5 | no | next | 4 |
| 5 | 4 | 9 | no | next | 5 |
| 6 | 5 | 12 | no | next | 6 |
| - | - | - | - | loop ends, return `-1` | 6 |

Both answers are correct. The scan works on any array, sorted or not - which is exactly the problem.

### Java

```java
class Solution {
    public int search(int[] nums, int target) {

        for (int i = 0; i < nums.length; i++) {
            if (nums[i] == target) {
                return i;
            }
        }

        return -1;
    }
}
```

### Complexity

**Time:** `O(n)` - **Space:** `O(1)`

### Where it hurts

Look at step 3 of the second table. We compared `nums[2] = 3` with `target = 2` and learned `3 > 2`. In a sorted array, that single fact proves that `5`, `9` and `12` are **also** greater than `2` - none of them can be the target. The scan ignores that and checks all three anyway.

Worse, at step 1 we learned `-1 < 2`. That tells us nothing useful about the right side, so the scan is spending each comparison to eliminate exactly **one** element.

```text
comparison       what the scan eliminates     what the sort order actually proves
nums[2]=3 > 2    index 2                      indices 2, 3, 4, 5
```

The information is already there, paid for, and thrown away. The fix is not to compare faster - it is to compare at the point where each answer eliminates the **most**: the middle.

=== optimization ===
### The key observation

Every comparison against `nums[k]` splits the remaining candidates into "left of `k`" and "right of `k`", and the sort order tells us one of those groups is impossible. To make the worst case as good as possible, pick `k` so the two groups are the same size. That is the middle. Each comparison then halves the window, whichever way it goes.

### Deriving the loop step by step

1. Candidates are the indices `[lo, hi]`. Start with `lo = 0`, `hi = n - 1`.
2. While there is at least one candidate - `lo <= hi` - pick `mid = lo + (hi - lo) / 2`.
3. If `nums[mid] == target`, return `mid`.
4. If `nums[mid] < target`, `mid` and everything left of it are too small: `lo = mid + 1`.
5. If `nums[mid] > target`, `mid` and everything right of it are too large: `hi = mid - 1`.
6. If the window empties, return `-1`.

Note the `+ 1` and `- 1`. We already know `nums[mid]` is not the target, so `mid` itself leaves the window. That is also what guarantees progress: the window shrinks by at least one every iteration, so the loop cannot spin forever.

### Dry run - target present

```text
nums = [-1, 0, 3, 5, 9, 12], target = 9
```

| step | lo | hi | mid | nums[mid] | compare to 9 | action | window after |
| ---: | -: | -: | --: | --------: | :----------- | :----- | :----------- |
| 1 | 0 | 5 | 2 | 3 | 3 < 9 | `lo = mid + 1 = 3` | `[3..5]` = `[5, 9, 12]` |
| 2 | 3 | 5 | 4 | 9 | **equal** | return `4` | - |

Two comparisons instead of five.

### Dry run - target absent

```text
nums = [-1, 0, 3, 5, 9, 12], target = 2
```

| step | lo | hi | mid | nums[mid] | compare to 2 | action | window after |
| ---: | -: | -: | --: | --------: | :----------- | :----- | :----------- |
| 1 | 0 | 5 | 2 | 3 | 3 > 2 | `hi = mid - 1 = 1` | `[0..1]` = `[-1, 0]` |
| 2 | 0 | 1 | 0 | -1 | -1 < 2 | `lo = mid + 1 = 1` | `[1..1]` = `[0]` |
| 3 | 1 | 1 | 1 | 0 | 0 < 2 | `lo = mid + 1 = 2` | `[2..1]` = empty |
| - | 2 | 1 | - | - | `lo > hi` | loop ends, return `-1` | - |

Three comparisons instead of six. Look at step 1: the comparison `3 > 2` that the brute force used to rule out one index here rules out four.

Look at step 3 too. The window is a single element (`lo == hi == 1`). If the loop condition were `lo < hi`, we would have exited **before** checking it. With these update rules, `lo <= hi` is what makes the last candidate get examined.

Notice also that when the search fails, `lo` ends at `2` - exactly the index where `2` would be inserted to keep the array sorted. That is not a coincidence, and it is the whole of the follow-up (LC 35).

### Why `mid = lo + (hi - lo) / 2`

The textbook `(lo + hi) / 2` is mathematically the same, but `lo + hi` can exceed `Integer.MAX_VALUE` when both are large:

```text
lo = 1,500,000,000   hi = 2,000,000,000
lo + hi          = 3,500,000,000  -> overflows int to -794,967,296
(lo + hi) / 2    = -397,483,648   -> negative index, crash
lo + (hi-lo)/2   = 1,750,000,000  -> correct
```

`hi - lo` is never larger than `hi`, so it cannot overflow. On LeetCode 704 `n <= 10^4` and it never matters - which is precisely why it is a habit to build now, before the day it does (binary search on an answer range up to `2^31 - 1`, day 46).

=== complexity ===
### Time

Each iteration halves the window. Starting from `n` candidates, after `k` iterations at most `n / 2^k` remain; the loop stops when that drops below one.

```text
O(log n)
```

### Space

Three integers: `lo`, `hi`, `mid`.

```text
O(1)
```

### What `log n` actually buys

| n | linear scan, worst case | binary search, worst case |
| -: | ----------------------: | ------------------------: |
| 6 | 6 | 3 |
| 1,000 | 1,000 | 10 |
| 10,000 | 10,000 | 14 |
| 1,000,000 | 1,000,000 | 20 |
| 1,000,000,000 | 1,000,000,000 | 30 |

### Comparison

| Approach | Time | Space | Uses sorting? |
| :------- | ---: | ----: | :------------ |
| Linear scan | `O(n)` | `O(1)` | no |
| Iterative binary search | **`O(log n)`** | **`O(1)`** | yes |
| Recursive binary search | `O(log n)` | `O(log n)` stack | yes |

The recursive version is a fine way to *explain* the halving, but the iterative loop is what you should write: same time, no stack frames.

=== implementation ===
```java
class Solution {
    public int search(int[] nums, int target) {

        // Invariant: if target is in nums, its index is in [lo, hi].
        int lo = 0;
        int hi = nums.length - 1;

        while (lo <= hi) {                       // window still has a candidate
            int mid = lo + (hi - lo) / 2;        // no int overflow

            if (nums[mid] == target) {
                return mid;
            } else if (nums[mid] < target) {
                lo = mid + 1;                    // mid and its left are too small
            } else {
                hi = mid - 1;                    // mid and its right are too large
            }
        }

        return -1;                               // window empty: not present
    }
}
```

### The lines that matter

**1.**

```java
int hi = nums.length - 1;
```

`hi` is an **inclusive** bound - it points at a real element. That choice decides the other two lines: an inclusive `hi` pairs with `lo <= hi` and `hi = mid - 1`.

**2.**

```java
while (lo <= hi) {                       // window still has a candidate
```

`lo == hi` is a one-element window, not an empty one. With `<`, the dry run's step 3 would never happen and `[5]` searched for `5` would return `-1`.

**3.**

```java
int mid = lo + (hi - lo) / 2;        // no int overflow
```

The distance `hi - lo` cannot overflow; the sum `lo + hi` can. Integer division rounds down, so in a two-element window `mid` is the left one.

**4.**

```java
lo = mid + 1;                    // mid and its left are too small
```

`mid` has been checked, so it leaves the window. Writing `lo = mid` here is the classic infinite loop: with `lo = 3, hi = 4`, `mid = 3`, and if `nums[3] < target` the window never changes.

### The other template - half-open `[lo, hi)`

The same search can be written with an **exclusive** `hi`. It never returns early; it narrows to the first index whose value is `>= target` and checks that one at the end:

```java
class Solution {
    public int search(int[] nums, int target) {

        int lo = 0;
        int hi = nums.length;                    // exclusive

        while (lo < hi) {                        // window [lo, hi) non-empty
            int mid = lo + (hi - lo) / 2;
            if (nums[mid] < target) {
                lo = mid + 1;
            } else {
                hi = mid;                        // mid might be the answer - keep it
            }
        }

        return (lo < nums.length && nums[lo] == target) ? lo : -1;
    }
}
```

Each template is self-consistent; mixing them is where bugs come from. `hi = n - 1` goes with `lo <= hi` and `hi = mid - 1`. `hi = n` goes with `lo < hi` and `hi = mid`. Pick one per problem and say out loud which one you picked. The half-open form is the one that becomes tomorrow's lower bound.

### Follow-up - Search Insert Position (LC 35)

"Return the index of `target`, or where it would be inserted." That is the half-open loop with the final check removed - the loop already computes the first index whose value is `>= target`:

```java
class Solution {
    public int searchInsert(int[] nums, int target) {

        int lo = 0;
        int hi = nums.length;

        while (lo < hi) {
            int mid = lo + (hi - lo) / 2;
            if (nums[mid] < target) {
                lo = mid + 1;
            } else {
                hi = mid;
            }
        }

        return lo;
    }
}
```

### Java notes

- `Arrays.binarySearch(nums, target)` exists and is `O(log n)`, but when the key is missing it returns `-(insertionPoint) - 1`, not `-1`. Fine in production after checking the sign; in an interview, write the loop - that is what is being tested.
- `/ 2` on non-negative `int`s rounds down. `(hi - lo) >>> 1` is an equivalent bit-shift some codebases prefer; it is not faster in any way that matters.
- The `else if` chain makes the three outcomes mutually exclusive and readable. Three separate `if`s would also work here but invite bugs once `lo`/`hi` change mid-iteration.

=== edgeCases ===
### Single element, present

```text
nums = [5], target = 5  ->  0
```

`lo = hi = 0`, `mid = 0`, match. This is the case `lo < hi` would get wrong in the inclusive template.

### Single element, absent

```text
nums = [5], target = -5  ->  -1
```

`nums[0] = 5 > -5`, so `hi = -1`. Window `[0..-1]` is empty, return `-1`.

### Target is the first element

```text
nums = [-1, 0, 3, 5, 9, 12], target = -1  ->  0
```

`mid = 2` (3 > -1, `hi = 1`), `mid = 0` (match). The left boundary is reached without any special case.

### Target is the last element

```text
nums = [-1, 0, 3, 5, 9, 12], target = 12  ->  5
```

`mid = 2` (`lo = 3`), `mid = 4` (`lo = 5`), `mid = 5` (match). Three steps, the last on a one-element window.

### Target smaller than everything

```text
nums = [-1, 0, 3, 5, 9, 12], target = -5  ->  -1
```

`hi` keeps moving left until it reaches `-1`. No index below `0` is ever read, because the loop exits before computing `mid` on an empty window.

### Target larger than everything

```text
nums = [-1, 0, 3, 5, 9, 12], target = 13  ->  -1
```

`lo` walks right until it is `6`, one past the end. Again the loop exits before `nums[6]` is touched.

### Target falls in a gap

```text
nums = [-1, 0, 3, 5, 9, 12], target = 4  ->  -1
```

The window closes between `3` and `5` (`lo = 3`, `hi = 2`). `lo = 3` is where `4` would be inserted.

### Two elements

```text
nums = [2, 5], target = 5  ->  1
nums = [2, 5], target = 2  ->  0
```

`mid = 0` first (rounding down). For `5`: `2 < 5`, `lo = 1`, then `mid = 1`, match. A two-element window is where `lo = mid` instead of `mid + 1` loops forever.

### Empty array (outside LeetCode's constraints)

```text
nums = [], target = 3  ->  -1
```

`hi = -1`, so `lo <= hi` is false immediately. No index is read.

### Search Insert Position, the follow-up

```text
[1, 3, 5, 6], target = 5  ->  2    (found)
[1, 3, 5, 6], target = 2  ->  1    (between 1 and 3)
[1, 3, 5, 6], target = 7  ->  4    (past the end - a valid insert index)
[1, 3, 5, 6], target = 0  ->  0    (before everything)
```

### Huge indices

With `lo = 1,500,000,000` and `hi = 2,000,000,000`, `(lo + hi) / 2` is `-397,483,648`; `lo + (hi - lo) / 2` is `1,750,000,000`. Unreachable on LC 704's sizes, reachable the moment you binary search over a value range instead of an array.

=== takeaway ===
> When you see **sorted** input and **`O(log n)`**, think **binary search**: keep a window where the answer must be, compare at the middle, and discard the half that cannot contain it.

### The core observation

In a sorted array, one comparison with `nums[mid]` proves something about **every** element on one side of `mid`. A linear scan pays for that information and uses it to eliminate one element; binary search uses it to eliminate half. Halving `n` repeatedly reaches one in `log2(n)` steps.

### The pattern trigger

```text
          sorted array / monotonic condition
                         |
                         v
           window [lo, hi] = "answer could be here"
                         |
                         v
          mid = lo + (hi - lo) / 2,  compare
          /              |               \
   too small          equal            too large
   lo = mid + 1     return mid        hi = mid - 1
                         |
                         v
         lo > hi  ->  window empty  ->  -1
         (and lo is the insert position)
```

### The common mistakes

**Mixing templates.** `hi = n` with `lo <= hi` reads `nums[n]` and throws. `hi = n - 1` with `lo < hi` skips the last one-element window and misses targets. Decide inclusive or exclusive `hi` first; the loop condition and updates follow.

**`lo = mid` or `hi = mid` in the inclusive template.** The window stops shrinking when it has two elements and the loop never ends.

**`(lo + hi) / 2`.** Harmless here, a negative index the day the range is large.

**Using binary search on unsorted data.** It runs, returns something, and is wrong. The sort order (or another monotonic property) is the precondition, not a detail.

### What to remember in six months

> Binary search is not "find the element". It is "maintain a window where the answer must be, and shrink it by half using one comparison".

Say the invariant before writing the loop. Then the next four days - first/last position (LC 34), integer square root (LC 69), rotated array (LC 33), peak element (LC 162) - are this same loop with a different answer to "which half can I discard?".
