=== intro ===
Day 9 compared characters by **position** - first with last, second with second-to-last. Today position stops mattering entirely. Two strings are anagrams if they use the same letters the same number of times, in any order.

> When the order of elements is irrelevant and only "how many of each" matters, stop sorting and start counting. A frequency table is the order-free fingerprint of a collection.

=== problem ===
Given two strings `s` and `t`, return `true` if `t` is an **anagram** of `s` - that is, `t` uses exactly the same characters as `s`, each exactly the same number of times, possibly rearranged.

| s | t | anagram? |
| :- | :- | :------- |
| `"anagram"` | `"nagaram"` | `true` |
| `"rat"` | `"car"` | `false` |

### What "same characters, same counts" means

Lay out the letter counts of the first example side by side:

| letter | count in `"anagram"` | count in `"nagaram"` |
| :----: | -------------------: | -------------------: |
| `a` | 3 | 3 |
| `g` | 1 | 1 |
| `m` | 1 | 1 |
| `n` | 1 | 1 |
| `r` | 1 | 1 |

Every row matches, so `true`. For `"rat"` vs `"car"`, `t` has a `c` that `s` lacks and `s` has a `t` that `t` lacks - two rows differ, so `false`.

### The condition that makes it non-trivial

Having the same **set** of letters is not enough. Counts matter:

```text
s = "aab",  t = "abb"
same letters {a, b}, same length 3 - but a:2 vs a:1  ->  false
```

Any approach that only checks "is every letter of `t` somewhere in `s`" passes this pair and is wrong.

### Constraints that matter

- `1 <= s.length, t.length <= 5 * 10^4`.
- `s` and `t` consist of **lowercase English letters** only. That is 26 possible characters - and that small fixed alphabet is what the optimal solution is built on.
- The follow-up asks: what if the inputs contain Unicode characters? Keep it in mind; the answer changes the data structure, not the idea.

=== pattern ===
**Hashing / Frequency Count.**

The reframe: an anagram check is not a string comparison at all. It is a **multiset** comparison - two bags of letters, are they the same bag?

A frequency table describes a bag exactly, with no order information:

```text
"anagram"  ->  a:3  g:1  m:1  n:1  r:1
"nagaram"  ->  a:3  g:1  m:1  n:1  r:1     same table  ->  anagram
```

For lowercase English letters the table is just an `int[26]`, where index `0` is `a`, index `1` is `b`, ..., index `25` is `z`. The character itself computes its slot: `c - 'a'`.

One more trick makes it a single table instead of two: **add** for every letter of `s`, **subtract** for every letter of `t`. If the bags are equal, every slot ends at exactly zero.

### Recognising it

Reach for a frequency count when:

- the problem says **anagram**, **permutation**, **rearrangement**, or "same characters"
- the order of elements does not affect the answer, but their multiplicities do
- the alphabet is small and fixed (letters, digits, a known set of values) - then a plain array beats a `HashMap`

The mental question:

> If I shuffled the input, would the answer change? If not, a count of each value is all the information I need.

=== bruteForce ===
If two strings are rearrangements of each other, putting both into a **canonical order** makes them identical. Sorting is a canonical order.

### Step logic

1. Convert both strings to `char[]`.
2. Sort both arrays.
3. They are anagrams if the sorted arrays are equal, position by position.

(A cheaper first check: if the lengths differ, they cannot be anagrams.)

### Dry run

```text
s = "anagram"
t = "nagaram"
```

**Length check.** `7 == 7`, continue.

**Sort both.**

| step | s chars | t chars |
| :--- | :------ | :------ |
| as given | `[a, n, a, g, r, a, m]` | `[n, a, g, a, r, a, m]` |
| after `Arrays.sort` | `[a, a, a, g, m, n, r]` | `[a, a, a, g, m, n, r]` |

**Compare position by position** (this is what `Arrays.equals` does):

| k | sortedS[k] | sortedT[k] | equal? |
| -: | :--------: | :--------: | :----- |
| 0 | `a` | `a` | yes |
| 1 | `a` | `a` | yes |
| 2 | `a` | `a` | yes |
| 3 | `g` | `g` | yes |
| 4 | `m` | `m` | yes |
| 5 | `n` | `n` | yes |
| 6 | `r` | `r` | yes |

All 7 equal, so `true`.

For `"rat"` vs `"car"`: sorted `[a, r, t]` vs `[a, c, r]`. Position 0 matches, position 1 is `r` vs `c` - `false`.

### Java

```java
class Solution {
    public boolean isAnagram(String s, String t) {

        if (s.length() != t.length()) {
            return false;
        }

        char[] a = s.toCharArray();
        char[] b = t.toCharArray();
        Arrays.sort(a);
        Arrays.sort(b);

        return Arrays.equals(a, b);
    }
}
```

### Complexity

**Time:** `O(n log n)` - **Space:** `O(n)` (the two `char[]` copies; Java strings are immutable, so sorting requires a copy)

### Where it hurts

Look at what the sort actually produced: `[a, a, a, g, m, n, r]`. Read it as runs and it is just the frequency table written out longhand - three `a`s, one `g`, one `m`, one `n`, one `r`.

Sorting computed a full **ordering** of every character - which `a` comes before which `g` - and then the comparison threw the ordering away and only used "how many of each". The `O(n log n)` buys information the question never asked for.

There are only 26 possible letters. Counting how many of each takes one look per character, `O(n)`, with no comparisons between characters at all.

> We do not need the letters in order. We only need to know how many of each there are.

=== optimization ===
### The observation

Two strings are anagrams exactly when their frequency tables are equal. With a 26-letter alphabet, a frequency table is an `int[26]`, and building one is a single pass.

Instead of building two tables and comparing them, build **one** table as a running balance:

- for every character of `s`, `count[c - 'a']++`
- for every character of `t`, `count[c - 'a']--`

Every letter that appears equally often in both is incremented and decremented the same number of times and lands back on `0`. Any slot that is not `0` at the end is a letter whose counts differ.

Because the lengths are equal (checked first), both strings can be walked in the **same loop**, one character of each per iteration.

### Dry run

```text
s = "anagram"
t = "nagaram"
```

Only non-zero slots are shown; every other slot is `0`.

| i | s[i] | t[i] | `count[s[i]]++` | `count[t[i]]--` | non-zero slots after |
| -: | :--: | :--: | :-------------- | :-------------- | :------------------- |
| - | - | - | - | - | `{}` |
| 0 | `a` | `n` | a: 0 -> 1 | n: 0 -> -1 | `{a:1, n:-1}` |
| 1 | `n` | `a` | n: -1 -> 0 | a: 1 -> 0 | `{}` |
| 2 | `a` | `g` | a: 0 -> 1 | g: 0 -> -1 | `{a:1, g:-1}` |
| 3 | `g` | `a` | g: -1 -> 0 | a: 1 -> 0 | `{}` |
| 4 | `r` | `r` | r: 0 -> 1 | r: 1 -> 0 | `{}` |
| 5 | `a` | `a` | a: 0 -> 1 | a: 1 -> 0 | `{}` |
| 6 | `m` | `m` | m: 0 -> 1 | m: 1 -> 0 | `{}` |

**Final scan.** All 26 slots are `0`, so `true`.

Notice the table goes empty and refills several times. It does not matter *when* a letter is balanced, only that it is balanced at the end - which is the order-independence of anagrams, visible in the data.

### The same procedure on a `false` input

```text
s = "rat"
t = "car"
```

| i | s[i] | t[i] | `count[s[i]]++` | `count[t[i]]--` | non-zero slots after |
| -: | :--: | :--: | :-------------- | :-------------- | :------------------- |
| 0 | `r` | `c` | r: 0 -> 1 | c: 0 -> -1 | `{c:-1, r:1}` |
| 1 | `a` | `a` | a: 0 -> 1 | a: 1 -> 0 | `{c:-1, r:1}` |
| 2 | `t` | `r` | t: 0 -> 1 | r: 1 -> 0 | `{c:-1, t:1}` |

**Final scan.** Slot `c` is `-1` (`t` has an extra `c`), slot `t` is `1` (`s` has an extra `t`). Not all zero, so `false`. The table even tells you *which* letters are off and by how much.

=== complexity ===
### Time

One pass over both strings together (`n` iterations, two array updates each), then one pass over 26 slots.

```text
O(n + 26) = O(n)
```

### Space

One `int[26]`, whatever the input length.

```text
O(1)   - 26 counters is a constant
```

If the alphabet were not fixed (Unicode), the table would grow with the number of distinct characters `k`, giving `O(k)` space with a `HashMap`.

### Comparison

| Approach | Time | Extra space | Works for Unicode as-is? |
| :------- | ---: | ----------: | :----------------------- |
| Sort both, compare | `O(n log n)` | `O(n)` | almost - compares UTF-16 units, not code points (see Java notes) |
| `int[26]` balance | **`O(n)`** | **`O(1)`** | no - indexes by `c - 'a'` |
| `HashMap` balance | `O(n)` | `O(k)` | yes, with code points |

=== implementation ===
```java
class Solution {
    public boolean isAnagram(String s, String t) {

        // Different lengths can never have equal letter counts.
        if (s.length() != t.length()) {
            return false;
        }

        // count[x] = (occurrences of letter x in s) - (occurrences in t)
        int[] count = new int[26];
        for (int i = 0; i < s.length(); i++) {
            count[s.charAt(i) - 'a']++;
            count[t.charAt(i) - 'a']--;
        }

        // Every letter must balance out exactly.
        for (int c : count) {
            if (c != 0) {
                return false;
            }
        }
        return true;
    }
}
```

### The lines that matter

**1.**

```java
if (s.length() != t.length()) {
    return false;
}
```

Not just an optimisation. The single loop below indexes `t.charAt(i)` for every `i` in `s` - without this check, a shorter `t` would throw `StringIndexOutOfBoundsException`, and a longer `t` would have its tail silently ignored.

**2.**

```java
count[s.charAt(i) - 'a']++;
count[t.charAt(i) - 'a']--;
```

`s.charAt(i) - 'a'` turns `'a'..'z'` into `0..25`. In Java, subtracting two `char`s produces an `int`, so this is a valid array index with no cast.

**3.**

```java
for (int c : count) {
    if (c != 0) {
        return false;
    }
}
```

Checking for `!= 0`, not `> 0`. With equal lengths, any surplus in one slot forces a deficit in another, so checking either sign would happen to work - but `!= 0` states the actual condition and stays correct if someone removes the length check.

### The Unicode follow-up

`c - 'a'` only works for 26 lowercase letters. For arbitrary characters, swap the array for a `HashMap` and keep everything else:

```java
class Solution {
    public boolean isAnagram(String s, String t) {

        if (s.length() != t.length()) {
            return false;
        }

        Map<Integer, Integer> count = new HashMap<>();
        for (int cp : s.codePoints().toArray()) {
            count.merge(cp, 1, Integer::sum);
        }
        for (int cp : t.codePoints().toArray()) {
            count.merge(cp, -1, Integer::sum);
        }

        for (int v : count.values()) {
            if (v != 0) {
                return false;
            }
        }
        return true;
    }
}
```

### Java notes

- `int[] count = new int[26]` is zero-initialised by the JVM, so no fill loop is needed.
- `count.merge(cp, 1, Integer::sum)` means "insert `1` if absent, otherwise add `1`" - the idiomatic one-line counter update.
- **Why `codePoints()` and not `charAt`.** A Java `char` is a 16-bit UTF-16 unit. Characters outside the Basic Multilingual Plane (many emoji, some CJK) take **two** `char`s. Counting `char`s would split them into halves; `codePoints()` yields each real character once.
- The length check is still valid in the Unicode version: two strings with the same multiset of code points always have the same UTF-16 length.

=== edgeCases ===
### Different lengths

```text
s = "a",  t = "ab"   ->  false
```

Rejected before any counting. Without the check, the shared loop would stop after `s` and never see `t`'s `b`.

### Same letters, different counts

```text
s = "aab",  t = "abb"   ->  false
```

Final table `{a:1, b:-1}`. This is the case that defeats a "same set of letters" check.

### Identical strings

```text
s = "abc",  t = "abc"   ->  true
```

Every slot goes `+1` then `-1` in the same iteration.

### Single characters

```text
s = "a",  t = "a"   ->  true
s = "a",  t = "b"   ->  false
```

### One repeated letter

```text
s = "aaaa",  t = "aaaa"   ->  true
s = "aaaa",  t = "aaab"   ->  false
```

### Completely disjoint letters, same length

```text
s = "abc",  t = "xyz"   ->  false
```

Six non-zero slots at the end.

### Reversed string

```text
s = "listen",  t = "silent"   ->  true
```

The classic. Order never enters the computation.

=== takeaway ===
> When you see **anagram, permutation, or "same characters"**, think **frequency count**. If the alphabet is small and fixed, the count is an `int[]` indexed by `c - 'a'`.

### The core observation

Anagrams are equal **multisets**. A frequency table is a multiset with the order removed - so sorting, which computes order, does strictly more work than the question needs. Incrementing for one string and decrementing for the other turns "are these two tables equal?" into "is this one table all zero?".

### The pattern trigger

```text
          does shuffling the input change the answer?
                           |
                          no
                           |
                           v
             only "how many of each" matters
                           |
            +--------------+---------------+
            |                              |
   small fixed alphabet            open-ended values
   (a-z, digits, 0..k)             (Unicode, any int)
            |                              |
   int[26], index c - 'a'        HashMap<value, count>
            |                              |
            +--------------+---------------+
                           |
              +1 for one side, -1 for the other
              answer: is every count zero?
```

### The common mistakes

**Checking membership instead of counts.** "Every letter of `t` appears in `s`" accepts `"aab"` / `"abb"`.

**Skipping the length check in the single-loop version.** Shorter `t` crashes; longer `t` has its extra characters ignored.

**Reaching for `HashMap` on lowercase input.** It works, but boxes every count into an `Integer` and hashes every character. `int[26]` is simpler and faster when the alphabet is known.
