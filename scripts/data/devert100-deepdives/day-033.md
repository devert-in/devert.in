=== intro ===
This day pulls the week together. Day 30's two pointers measured a *fraction* of the list by moving at different speeds. Today two pointers move at the **same** speed with a **fixed gap** between them, and that gap measures an *offset from the end*. Day 32's dummy node comes along to handle the one deletion that has nothing in front of it.

> To find "the k-th from the end" in one pass, do not count the end. Put a ruler of length `k` on the list and slide it until its front edge falls off. Its back edge is where you wanted to be.

=== problem ===
Given the `head` of a linked list and an integer `n`, remove the `n`-th node **from the end** and return the head.

```text
head = 1 -> 2 -> 3 -> 4 -> 5,   n = 2
answer = 1 -> 2 -> 3 -> 5
```

Counting from the end: `5` is 1st, `4` is 2nd. So node `4` goes.

### What "remove" requires

You cannot delete a node by standing on it. In a singly linked list the only way to remove node `4` is to change the `next` of the node **before** it:

```text
before:   3 -> 4 -> 5
after:    3 -------> 5          3.next = 3.next.next
```

So the real target is not the `n`-th node from the end - it is the node **just before it**. Every bug in this problem comes from landing one node too far or one too short.

### The case that needs care

```text
head = 1 -> 2,   n = 2   ->   answer = 2
```

The 2nd from the end of a 2-node list is the **head**. There is no node before it to re-point. The answer is `head.next`, and any solution has to handle that.

### Index arithmetic, once

For a list of length `L`, the `n`-th node from the end is at 0-based index `L - n` from the front. The node before it is at `L - n - 1`. When `n = L`, that is `-1` - which is exactly the "no node before the head" case.

### Constraints that matter

- `1` to `30` nodes. The list is never empty.
- `1 <= n <= L`. `n` is always valid - you never need to handle "n is too big".
- The follow-up: **could you do this in one pass?**

=== pattern ===
**Two pointers with a fixed gap**, plus a **dummy node**.

Put `fast` some fixed number of nodes ahead of `slow`, then move **both one step at a time**. The gap never changes. When `fast` reaches the end, `slow` is exactly that many nodes behind the end.

```text
gap of 3:   slow . . fast
                         \  slide both right until fast falls off
            1 -> 2 -> 3 -> 4 -> 5 -> null
                      ^              ^
                    slow            fast
```

We want `slow` to stop on the node **before** the target, so the gap must be **`n + 1`**. And since that node might not exist (when the head is the target), we start both pointers on a `dummy` that sits before the head. Now there is always a node before the target - at worst, the dummy itself.

### Fast/slow vs fixed gap

| Technique | How they move | What it measures | Example |
| :-------- | :------------ | :--------------- | :------ |
| Different speeds | `slow +1`, `fast +2` | a fraction of the length | middle (Day 30) |
| Fixed gap | both `+1`, `fast` starts ahead | an offset from the end | `n`-th from end (today) |

### Recognising it

Reach for a fixed gap when:

- the problem says "k-th / n-th **from the end**" on a singly linked list
- it asks for one pass, so counting the length first is ruled out
- it needs the last `k` nodes as a block (Rotate List LC 61, Swapping Nodes LC 1721)

And reach for a dummy whenever the operation might change the head.

The mental question:

> If I place a pointer `k` nodes ahead and move both together, where is the trailing pointer when the leading one falls off?

=== bruteForce ===
The direct idea: you cannot count from the end, so turn it into counting from the front. Learn `L`, then the target is at index `L - n`.

### Step logic

1. Walk the list once to get `length`.
2. `target = length - n` (0-based index of the node to delete).
3. If `target == 0`, the head is being removed - return `head.next`.
4. Otherwise walk from `head` to index `target - 1` (the node before the target) and re-point its `next`.

### Dry run

```text
head = 1 -> 2 -> 3 -> 4 -> 5,   n = 2
```

**Pass 1 - count.**

| step | node | length after |
| ---: | ---: | -----------: |
| 1 | 1 | 1 |
| 2 | 2 | 2 |
| 3 | 3 | 3 |
| 4 | 4 | 4 |
| 5 | 5 | 5 |
| 6 | null | stop, `length = 5` |

`target = 5 - 2 = 3`. Index 3 holds `4`. Not the head, so continue.

**Pass 2 - walk to index `target - 1 = 2`.**

| i | prev before | `prev = prev.next` | prev after |
| -: | ----------: | :----------------- | ---------: |
| - | - | start at head | 1 |
| 0 | 1 | 1 -> 2 | 2 |
| 1 | 2 | 2 -> 3 | 3 |
| 2 | - | `i < 2` false, stop | 3 |

**Unlink.** `prev` is `3`, `prev.next` is `4`, `prev.next.next` is `5`. Set `3.next = 5`.

```text
1 -> 2 -> 3 -> 5
```

### The head case, dry-run

```text
head = 1 -> 2,   n = 2
```

Pass 1: `length = 2`. `target = 2 - 2 = 0`. Return `head.next`, which is `2`. Pass 2 never runs - and it could not, because there is no index `-1` to walk to.

### Java

```java
class Solution {
    public ListNode removeNthFromEnd(ListNode head, int n) {

        // Pass 1: count the nodes.
        int length = 0;
        for (ListNode node = head; node != null; node = node.next) {
            length++;
        }

        int target = length - n;    // 0-based index of the node to delete

        // Deleting the head: there is no node before it to re-point.
        if (target == 0) {
            return head.next;
        }

        // Pass 2: stop on the node just BEFORE the target.
        ListNode prev = head;
        for (int i = 0; i < target - 1; i++) {
            prev = prev.next;
        }

        prev.next = prev.next.next;
        return head;
    }
}
```

### Complexity

**Time:** `O(L)` - **Space:** `O(1)`

### Where it hurts

The complexity is already optimal, so be precise about what is wrong.

**Two passes.** The tables show `5 + 2 = 7` pointer moves, about `L + (L - n)` in general. Pass 1 walks to the end only to learn one number, then pass 2 starts over from `head` and re-walks most of the same nodes. The follow-up asks for one pass precisely to see whether you can avoid that restart.

**A special case for the head.** Step 3 is a separate branch because "the node before the target" does not exist when the target is the head. Branches like that are where off-by-one bugs hide - drop it and `n = L` crashes or deletes the wrong node.

Two questions:

> Can I know "I am `n + 1` nodes before the end" without knowing where the end is?

> Can I make sure there is *always* a node before the target, so the head is not special?

=== optimization ===
Answer the second question first, because it makes the first one cleaner.

### Observation 1 - a dummy gives every node a predecessor

Put a `dummy` node in front: `dummy -> 1 -> 2 -> 3 -> 4 -> 5`. Now even the head has a node before it. Removing the head becomes `dummy.next = dummy.next.next`, the same line as removing anything else. Return `dummy.next` at the end.

### Observation 2 - a fixed gap finds the predecessor in one pass

We want `slow` to end on the node **before** the target, which is `n + 1` nodes before `null` (counting `null` as the position just past the tail). So:

1. Start `fast` and `slow` on `dummy`.
2. Move `fast` forward `n + 1` times. Now the gap is `n + 1`.
3. Move both one step at a time until `fast` is `null`.
4. `slow.next` is the target. Unlink it: `slow.next = slow.next.next`.

Because `n <= L`, the `n + 1` steps from `dummy` reach at most one past the tail - `null` - and never try to step past it.

### Dry run

Same example. Write `D` for the dummy.

```text
D -> 1 -> 2 -> 3 -> 4 -> 5 -> null,   n = 2,   so fast moves n + 1 = 3 steps
```

**Phase 1 - open the gap.**

| step | fast before | fast after | slow |
| ---: | ----------: | ---------: | ---: |
| - | - | D | D |
| 1 | D | 1 | D |
| 2 | 1 | 2 | D |
| 3 | 2 | 3 | D |

Gap is now 3: `D -> 1 -> 2 -> 3` (`slow` on `D`, `fast` on `3`).

**Phase 2 - slide both until `fast` falls off.**

| round | fast before | `fast != null`? | slow after | fast after |
| ----: | ----------: | :-------------- | ---------: | ---------: |
| 1 | 3 | yes | 1 | 4 |
| 2 | 4 | yes | 2 | 5 |
| 3 | 5 | yes | 3 | null |
| 4 | null | **no** - stop | 3 | null |

**Unlink.** `slow` is `3`; `slow.next` is `4`, the 2nd from the end. Set `3.next = 4.next = 5`.

```text
D -> 1 -> 2 -> 3 -> 5          return dummy.next = 1
```

Total pointer moves: 3 for `fast` in phase 1, then 3 rounds of both. One traversal - nothing restarts from `head`.

### The head case, dry-run

```text
D -> 1 -> 2 -> null,   n = 2,   fast moves 3 steps
```

| phase | fast | slow |
| :---- | ---: | ---: |
| start | D | D |
| after step 1 | 1 | D |
| after step 2 | 2 | D |
| after step 3 | null | D |
| phase 2 | `fast` already `null`, loop never runs | D |

Unlink: `D.next = D.next.next`, so `D.next` becomes `2`. Return `dummy.next` = `2`. The head was removed by the same line as any other node - no branch.

### Why the gap is exactly `n + 1`

Number the positions `D = 0`, first node `= 1`, ..., last node `= L`, `null = L + 1`. The target, `n`-th from the end, is at position `L - n + 1`, so its predecessor is at `L - n`. When `fast` stops at `L + 1`, `slow` is `n + 1` behind it: `L + 1 - (n + 1) = L - n`. Exactly the predecessor.

A gap of `n` would leave `slow` **on** the target, which you cannot delete from.

=== complexity ===
### Time

`fast` walks from `dummy` to `null` exactly once - `L + 1` steps - and `slow` trails it.

```text
O(L)
```

### Space

`dummy`, `fast`, `slow`.

```text
O(1)
```

### Comparison

| Approach | Time | Extra space | Traversals | Head special case? |
| :------- | ---: | ----------: | ---------: | :----------------- |
| Copy nodes into an array, index `L - n - 1` | `O(L)` | `O(L)` | 1 | yes |
| Count, then walk to `L - n - 1` | `O(L)` | `O(1)` | 2 | yes |
| Dummy + fixed gap `n + 1` | **`O(L)`** | **`O(1)`** | **1** | **no** |

All three are linear. The improvement is one traversal and one fewer branch - say exactly that, not "faster".

=== implementation ===
```java
class Solution {
    public ListNode removeNthFromEnd(ListNode head, int n) {

        ListNode dummy = new ListNode(0, head);   // gives the head a predecessor
        ListNode fast = dummy;
        ListNode slow = dummy;

        // Open a gap of n + 1 so slow stops BEFORE the target, not on it.
        for (int i = 0; i <= n; i++) {
            fast = fast.next;
        }

        // Slide the fixed-size window until fast falls off the end.
        while (fast != null) {
            fast = fast.next;
            slow = slow.next;
        }

        // slow.next is the n-th node from the end: skip over it.
        slow.next = slow.next.next;

        return dummy.next;   // not head - head itself may have been removed
    }
}
```

### The lines that matter

**1.**

```java
for (int i = 0; i <= n; i++) {
```

`<=`, so the loop runs `n + 1` times. Writing `i < n` gives a gap of `n`, and `slow` stops **on** the target - you then delete the node after it instead.

**2.**

```java
ListNode dummy = new ListNode(0, head);   // gives the head a predecessor
```

LeetCode's two-argument constructor links the dummy to `head` in one line. With it, `n = L` needs no special case.

**3.**

```java
return dummy.next;   // not head - head itself may have been removed
```

When the head is deleted, `head` still points at the removed node. Returning it gives back the very node you were asked to remove. `dummy.next` is always the true first node.

### Java notes

- `new ListNode(0, head)` and `new ListNode(0)` followed by `dummy.next = head` are equivalent; the first is shorter.
- The removed node is not explicitly freed - nothing references it any more, so the garbage collector reclaims it. In C or C++ you would `delete` it yourself.
- Without the dummy, the one-pass version still works if you move `fast` `n` steps from `head` and check `if (fast == null) return head.next;` before sliding. It is the same head special case as the brute force, moved to a different place - which is why the dummy is the cleaner answer.

=== edgeCases ===
### Single node

```text
[1],  n = 1  ->  []
```

`fast` moves 2 steps: `D -> 1 -> null`. Phase 2 does not run. `D.next = 1.next = null`. Return `null`.

### Remove the head of a longer list

```text
[1, 2, 3, 4, 5],  n = 5  ->  [2, 3, 4, 5]
```

`fast` moves 6 steps and lands on `null`; `slow` stays on `D`; `D.next` becomes `2`.

### Remove the head of two

```text
[1, 2],  n = 2  ->  [2]
```

The dry run above.

### Remove the tail

```text
[1, 2],  n = 1  ->  [1]
[1, 2, 3, 4, 5],  n = 1  ->  [1, 2, 3, 4]
```

`slow` ends on the second-to-last node; `slow.next.next` is `null`, so the new tail's `next` becomes `null`.

### Remove a middle node

```text
[1, 2, 3, 4, 5],  n = 3  ->  [1, 2, 4, 5]
```

### Duplicate values

```text
[7, 7, 7],  n = 2  ->  [7, 7]
```

The **middle** node object is removed. Nothing compares values, so duplicates cannot cause the wrong node to go.

### Maximum length

```text
30 nodes,  n = 30  ->  the head is removed, 29 nodes remain
30 nodes,  n = 1   ->  the tail is removed, 29 nodes remain
```

`fast` takes `n + 1 <= 31` steps, which lands at most on `null` - never past it, because `n <= L` is guaranteed.

=== takeaway ===
> When you see **"n-th from the end"** with **one pass**, think **fixed gap**: start `fast` ahead, move both together, and the trailing pointer lands where you need it. When the head might change, think **dummy**.

### The core observation

Two pointers moving at the same speed keep a constant distance. So if `fast` is `n + 1` ahead and reaches `null`, `slow` is `n + 1` before `null` - the predecessor of the `n`-th node from the end - without the length ever being computed. The dummy guarantees that predecessor exists even when the target is the head.

### The pattern trigger

```text
      dummy -> head -> ... -> tail -> null
        ^
   fast, slow
        |
        v
   fast moves n + 1 steps          (open the gap)
        |
        v
   while fast != null: both +1     (slide the gap)
        |
        v
   slow.next = slow.next.next      (slow is the predecessor)
        |
        v
   return dummy.next
```

### The common mistakes

**Gap of `n` instead of `n + 1`.** `slow` stops on the target, and you delete the node after it.

**No dummy.** Then `n = L` either crashes (`fast` steps past `null`) or needs a separate branch.

**Returning `head`.** When the head was removed, `head` is the deleted node.

**Trying to delete the node you are standing on.** In a singly linked list you can only remove a node from its predecessor. Aim for the node before.

### What to remember in six months

> Different speeds measure a fraction; the same speed with a head start measures an offset. Aim one node early when you need to delete.

Rotate List (LC 61) uses the same gap to find the new tail `k` from the end. Swapping Nodes in a Linked List (LC 1721) uses it to find the `k`-th from the end. And the dummy node is now a reflex for anything that might touch the head - insertion, deletion, partition, de-duplication.
