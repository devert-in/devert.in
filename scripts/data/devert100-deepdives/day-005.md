=== intro ===
Today is the first problem in this run where the optimal solution looks like a **magic trick** until you see why it works.

> When a guarantee is handed to you in the problem statement, it is not decoration. It is usually the thing the intended solution is built on.

=== problem ===
Return the element that appears **more than `n/2` times** in the array. The problem guarantees such an element always exists.

```text
nums = [3, 2, 3]           ->  3
nums = [2, 2, 1, 1, 1, 2, 2]  ->  2
```

### "More than n/2" is a strong promise

Not "the most common". **Strictly more than half.** For `n = 7` that means at least 4 occurrences. Two consequences follow immediately, and the optimal solution needs both:

1. **There can only ever be one.** Two different elements each appearing more than `n/2` times would need more than `n` elements total.
2. **It survives cancellation.** If you paired off every majority element with a different, non-majority element, you would run out of non-majority elements first - because there are fewer than half of them. Some majority elements would be left unpaired.

That second point is the entire algorithm. Hold on to it.

### Verify the count

```text
nums = [2, 2, 1, 1, 1, 2, 2]
n = 7,  n/2 = 3.5
2 appears 4 times  ->  4 > 3.5  ->  majority
1 appears 3 times  ->  3 < 3.5  ->  not
```

=== pattern ===
**Boyer-Moore Voting.**

The reframe: stop counting occurrences and start tracking a **running balance**.

Imagine every element is a voter. Two voters who disagree cancel each other out and both leave. Keep doing that and ask: who is still standing at the end?

Because the majority element occupies more than half the seats, no matter how the cancellations are arranged, it **cannot be fully cancelled**. Every cancellation removes one majority vote and one non-majority vote, and there simply are not enough non-majority votes to go around.

So the algorithm carries two variables:

- `candidate` - who is currently holding the floor
- `count` - by how many votes

When `count` hits zero, the current candidate has been fully cancelled out, and we adopt the next element as the new candidate.

### Recognising it

Reach for vote-cancelling when:

- the problem guarantees something appears more than `n/k` times
- you need `O(1)` space and a counting structure is banned
- the question is about *dominance*, not exact frequencies

The mental question:

> Can I replace "count everything" with "track a single running balance"?

=== bruteForce ===
Two obvious approaches. Both are reasonable; both spend something the optimal does not.

### Approach A - count with a HashMap

Walk the array, tally each value, return the one whose tally exceeds `n/2`.

```text
nums = [2, 2, 1, 1, 1, 2, 2]
```

| i | num | map after | exceeds 3.5? |
| -: | --: | :-------- | :----------- |
| 0 | 2 | `{2:1}` | no |
| 1 | 2 | `{2:2}` | no |
| 2 | 1 | `{2:2, 1:1}` | no |
| 3 | 1 | `{2:2, 1:2}` | no |
| 4 | 1 | `{2:2, 1:3}` | no |
| 5 | 2 | `{2:3, 1:3}` | no |
| 6 | 2 | `{2:4, 1:3}` | **yes, 2** |

**Time:** `O(n)` — **Space:** `O(n)`

```java
import java.util.HashMap;
import java.util.Map;

class Solution {
    public int majorityElement(int[] nums) {

        Map<Integer, Integer> counts = new HashMap<>();

        for (int num : nums) {
            counts.put(num, counts.getOrDefault(num, 0) + 1);
            if (counts.get(num) > nums.length / 2) {
                return num;
            }
        }

        return -1;
    }
}
```

### Approach B - sort and take the middle

If one value occupies more than half the array, then after sorting it must cover the midpoint - there is no way to place more than `n/2` copies of something without straddling index `n/2`.

```text
[2, 2, 1, 1, 1, 2, 2]  ->  sort  ->  [1, 1, 1, 2, 2, 2, 2]
                                            index 3 = 2
```

**Time:** `O(n log n)` — **Space:** `O(1)` or `O(n)` depending on the sort

```java
import java.util.Arrays;

class Solution {
    public int majorityElement(int[] nums) {
        Arrays.sort(nums);
        return nums[nums.length / 2];
    }
}
```

### Where they hurt

Approach A is already `O(n)` in time, so there is no speed to win. What it spends is **memory**: a map that can grow to `n` entries for an answer that is a single integer.

Approach B spends a `log n` factor to learn an ordering the question never asked about, and mutates the caller's array as a side effect.

The real question for today:

> Do I need to know how many times **every** value appears, in order to find the one that appears most?

=== optimization ===
No. You need one candidate and one counter.

### The algorithm

```text
count = 0, candidate = undefined

for each num:
    if count == 0:  candidate = num
    count += (num == candidate) ? +1 : -1
```

### Why it cannot fail

Think of `count` as "how many unmatched copies of `candidate` we are currently holding". Each disagreeing element cancels one of them. When the balance reaches zero, everything seen so far has paired off perfectly, and the remainder of the array still contains a majority element - so we can safely restart from the next element.

Because the majority element appears more than `n/2` times, it can never be cancelled to zero across the whole array. Whoever is holding the floor at the end is it.

### Dry run

```text
nums = [2, 2, 1, 1, 1, 2, 2]
```

| i | num | count before | count == 0? | candidate | count after |
| -: | --: | -----------: | :---------- | --------: | ----------: |
| 0 | 2 | 0 | yes -> adopt 2 | 2 | 1 |
| 1 | 2 | 1 | no | 2 | 2 |
| 2 | 1 | 2 | no | 2 | 1 |
| 3 | 1 | 1 | no | 2 | **0** |
| 4 | 1 | 0 | yes -> adopt 1 | **1** | 1 |
| 5 | 2 | 1 | no | 1 | **0** |
| 6 | 2 | 0 | yes -> adopt 2 | **2** | 1 |

Answer: `2`. Correct.

### Read row 3 and row 4 carefully

At `i = 3` the count hits zero. That means the prefix `[2, 2, 1, 1]` has cancelled itself out perfectly - two `2`s against two `1`s. Whatever the majority of the whole array is, it must also be the majority of what remains, `[1, 2, 2]`, because we just discarded a balanced chunk.

That is the invariant: **discarding a balanced prefix never changes the answer.** The algorithm is repeatedly throwing away balanced chunks until only the winner is left standing.

### Note what the candidate is NOT

At `i = 4` the candidate becomes `1`, which is not the answer. Mid-run the candidate is meaningless - it is only the **final** candidate that is guaranteed correct. Do not return early.

=== complexity ===
### Time

One pass, constant work per element.

```text
O(n)
```

### Space

Two variables.

```text
O(1)
```

### Comparison

| Approach | Time | Space | Mutates input? |
| :------- | ---: | ----: | :------------- |
| HashMap count | `O(n)` | `O(n)` | no |
| Sort + middle | `O(n log n)` | `O(1)`-`O(n)` | **yes** |
| Boyer-Moore | **`O(n)`** | **`O(1)`** | no |

Boyer-Moore is the only one that is optimal in both columns, and the only one that leaves the caller's array alone.

### The catch worth stating out loud

Boyer-Moore's correctness depends **entirely** on the guarantee that a majority exists. Given `[1, 2, 3]` it returns `3` - confidently, and wrongly, because there is no majority to find.

If the guarantee is not given, add a **second pass** that counts the candidate's actual occurrences and checks it exceeds `n/2`. That is still `O(n)` time and `O(1)` space. Mentioning this unprompted in an interview is a strong signal.

=== implementation ===
```java
class Solution {
    public int majorityElement(int[] nums) {

        int candidate = nums[0];
        int count = 0;

        for (int num : nums) {

            // Everything before this point has cancelled out perfectly, so
            // start fresh from here.
            if (count == 0) {
                candidate = num;
            }

            count += (num == candidate) ? 1 : -1;
        }

        return candidate;
    }
}
```

### The lines that matter

**1.**

```java
if (count == 0) {
    candidate = num;
}
```

A zero balance means the prefix cancelled itself out. Discarding a balanced prefix cannot change which element is in the majority of the rest, so restarting here is safe.

**2.**

```java
count += (num == candidate) ? 1 : -1;
```

One line covering three cases: adopt (count was just set to 0, `num == candidate`, so it goes to 1), agree (+1), disagree (-1).

**3.**

```java
return candidate;
```

No verification pass, because the problem guarantees a majority exists. Remove that guarantee and this line becomes a bug.

### Why `candidate = nums[0]` in the initialiser

Purely to satisfy the compiler - `count` starts at `0`, so the first iteration overwrites it immediately. Initialising to `nums[0]` rather than, say, `0` avoids the misleading impression that `0` is a meaningful starting candidate.

### The verification variant, for when there is no guarantee

```java
class Solution {
    public int majorityElement(int[] nums) {

        int candidate = nums[0];
        int count = 0;

        for (int num : nums) {
            if (count == 0) candidate = num;
            count += (num == candidate) ? 1 : -1;
        }

        // Second pass: confirm the candidate really is a majority.
        int occurrences = 0;
        for (int num : nums) {
            if (num == candidate) occurrences++;
        }

        return occurrences > nums.length / 2 ? candidate : -1;
    }
}
```

=== edgeCases ===
### Single element

```text
[1]  ->  1
```

`count` starts 0, adopts `1`, goes to 1. Returns `1`. Trivially a majority of itself.

### Two identical elements

```text
[5, 5]  ->  5
```

Adopt `5`, then agree. `count = 2`.

### The majority is all at the start

```text
[7, 7, 7, 1, 2]  ->  7
```

| i | num | count before | candidate | count after |
| -: | --: | -----------: | --------: | ----------: |
| 0 | 7 | 0 | 7 | 1 |
| 1 | 7 | 1 | 7 | 2 |
| 2 | 7 | 2 | 7 | 3 |
| 3 | 1 | 3 | 7 | 2 |
| 4 | 2 | 2 | 7 | 1 |

Never drops to zero. The lead built early absorbs both dissenters.

### The majority is all at the end

```text
[1, 2, 7, 7, 7]  ->  7
```

| i | num | count before | candidate | count after |
| -: | --: | -----------: | --------: | ----------: |
| 0 | 1 | 0 | 1 | 1 |
| 1 | 2 | 1 | 1 | **0** |
| 2 | 7 | 0 | **7** | 1 |
| 3 | 7 | 1 | 7 | 2 |
| 4 | 7 | 2 | 7 | 3 |

The balanced prefix `[1, 2]` is discarded at `i = 1`, exactly as the invariant promises.

### The majority alternates with others

```text
[1, 2, 1, 3, 1]  ->  1
```

| i | num | count before | candidate | count after |
| -: | --: | -----------: | --------: | ----------: |
| 0 | 1 | 0 | 1 | 1 |
| 1 | 2 | 1 | 1 | 0 |
| 2 | 1 | 0 | 1 | 1 |
| 3 | 3 | 1 | 1 | 0 |
| 4 | 1 | 0 | 1 | 1 |

The count keeps returning to zero, but `1` keeps being re-adopted because it is the one always arriving next. Worst case for intuition, correct anyway.

### Negative numbers and zero

```text
[-1, -1, 2]  ->  -1
[0, 0, 1]    ->  0
```

The algorithm only ever tests equality, never magnitude or sign. Both work.

### No majority - the case it gets WRONG

```text
[1, 2, 3]  ->  returns 3
```

There is no majority element, and the algorithm returns a confident wrong answer. This is not a bug; it is the stated precondition being violated. Use the verification variant when the guarantee is absent.

=== takeaway ===
> When you see **"appears more than n/2 times"** with a guarantee it exists, think **vote cancelling** - one candidate, one counter, `O(1)` space.

### The core observation

Discarding a balanced prefix - equal numbers of "for" and "against" - cannot change which element holds the majority of what remains. The algorithm is nothing more than that fact applied repeatedly until only the winner is left holding the floor.

### The pattern trigger

```text
        count == 0?
        /          \
      yes           no
       |             |
  adopt current   does it agree
   as candidate   with candidate?
                    /        \
                  yes         no
                   |           |
                count++     count--
```

### The common mistake

Believing the candidate is meaningful before the loop ends. In the main dry run the candidate is `1` at step 4 and `2` at step 6 - only the final value carries the guarantee. Returning early on a high count is wrong.

The second mistake: using Boyer-Moore where no majority is promised. It always returns *something*, and with no verification pass you cannot tell a real answer from a confident guess.

### What to remember in six months

> A guarantee in the problem statement is load-bearing. "More than n/2" is not flavour text - it is the precondition that makes an `O(1)`-space answer possible at all.

The same idea scales: for "more than `n/3` times" (LC 229) you track **two** candidates and two counters, because at most two such elements can exist. The pattern generalises to `n/k` with `k-1` candidates.
