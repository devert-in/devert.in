=== intro ===
Yesterday, Longest Common Subsequence taught you to fill a table where `dp[i][j]` describes two prefixes. Today keeps that exact table and changes the question it answers: not "how much do these strings share", but "how much does it **cost** to turn one into the other".

> When two strings have to be compared and the answer is built from their prefixes, draw the `(m+1) x (n+1)` grid first. Row 0 and column 0 are the empty string, and getting them right is half the problem.

=== problem ===
Given two strings `word1` and `word2`, return the **minimum number of operations** needed to turn `word1` into `word2`. Three operations are allowed, each costing `1`:

- **Insert** a character
- **Delete** a character
- **Replace** a character with another

LeetCode's first example:

```text
word1 = "horse"
word2 = "ros"
answer = 3
```

One way to do it in 3:

```text
horse  ->  rorse     replace 'h' with 'r'
rorse  ->  rose      delete 'r'
rose   ->  ros       delete 'e'
```

There is no way to do it in 2, and proving that is what the algorithm is for. Listing *a* sequence of edits is easy; knowing it is the *shortest* is the problem.

### The example we will trace

The `horse` table is worth seeing (it appears at the end of the optimization section), but its brute-force recursion makes 77 calls - too many to trace honestly. So both dry runs below use a smaller pair that still needs every kind of reasoning:

```text
word1 = "abd"
word2 = "bcd"
answer = 2
```

| step | operation | string |
| ---: | :-------- | :----- |
| 0 | start | `abd` |
| 1 | delete `a` | `bd` |
| 2 | insert `c` after `b` | `bcd` |

Replacing `a -> b` then `b -> c` also takes 2. Different paths, same minimum - which is why the problem asks only for the number.

### The constraints that matter

- `0 <= word1.length, word2.length <= 500`. Either string may be **empty**.
- Lowercase English letters only.

`500 x 500` is 250,000 cell pairs. Anything polynomial in `m * n` is fine; anything exponential is not.

=== pattern ===
**2D Dynamic Programming on two strings.**

### Why it belongs here

Look only at the **last character** of each string. There are exactly two situations:

```text
word1 = "ab d"      word2 = "bc d"
            ^                   ^
       last chars equal: they can be left alone.
       The cost is whatever it takes to turn "ab" into "bc".
```

```text
word1 = "a b"       word2 = "b c"
           ^                   ^
       last chars differ: SOMETHING must happen to fix the end.
```

When they differ, the edit that fixes the end is one of three, and each one leaves a **smaller version of the same problem**:

| last edit | what it does | what is left to solve |
| :-------- | :----------- | :-------------------- |
| delete | remove `word1`'s last char | `word1[0..i-1)` -> `word2[0..j)` |
| insert | append `word2`'s last char | `word1[0..i)` -> `word2[0..j-1)` |
| replace | overwrite `word1`'s last char with `word2`'s | `word1[0..i-1)` -> `word2[0..j-1)` |

So the answer for prefixes `(i, j)` depends only on answers for `(i-1, j)`, `(i, j-1)` and `(i-1, j-1)`. That is **optimal substructure**. And as the brute force will show, the same `(i, j)` pairs are reached over and over by different edit orders - **overlapping subproblems**. Both together mean DP.

### The state

```text
dp[i][j] = fewest operations to turn the first i chars of word1
           into the first j chars of word2
```

### Recognising it

Reach for this grid when:

- there are **two sequences** and the answer compares or aligns them
- each step consumes a character from one string, the other, or both
- the question is a min, max, count, or yes/no

LCS, Edit Distance, Delete Operation for Two Strings (LC 583), Distinct Subsequences (LC 115), Interleaving String (LC 97), Wildcard and Regex Matching - all the same grid.

The mental question:

> If I only look at the last character of each string, what are my choices - and does every choice leave a shorter pair of prefixes?

=== bruteForce ===
Pretend we do not know about tables yet. Just follow the case analysis from the pattern section literally, as a recursive function `solve(i, j)`:

1. If `i == 0`, `word1` is used up: insert the remaining `j` characters. Return `j`.
2. If `j == 0`, `word2` is used up: delete the remaining `i` characters. Return `i`.
3. If the last characters match, they cost nothing: return `solve(i-1, j-1)`.
4. Otherwise try all three edits and keep the cheapest: `1 + min(delete, insert, replace)`.

### Dry run

```text
word1 = "abd", word2 = "bcd"
call solve(3, 3)
```

Every call, in the order Java makes them. Indentation in the `call` column is recursion depth. Calls 12-15 repeat calls 5-8 exactly, and `solve(0,1)` is asked three separate times.

| # | call | prefixes | last chars | action | returns |
| -: | :--- | :------- | :--------- | :----- | ------: |
| 1 | `solve(3,3)` | `abd` vs `bcd` | `d` = `d` | match, go to `(2,2)` | 2 |
| 2 | `. solve(2,2)` | `ab` vs `bc` | `b` != `c` | try del, ins, rep | 1 + min(2, 1, 1) = 2 |
| 3 | `. . solve(1,2)` | `a` vs `bc` | `a` != `c` | try del, ins, rep | 1 + min(2, 1, 1) = 2 |
| 4 | `. . . solve(0,2)` | `""` vs `bc` | - | base: `i == 0` | 2 |
| 5 | `. . . solve(1,1)` | `a` vs `b` | `a` != `b` | try del, ins, rep | 1 + min(1, 1, 0) = 1 |
| 6 | `. . . . solve(0,1)` | `""` vs `b` | - | base: `i == 0` | 1 |
| 7 | `. . . . solve(1,0)` | `a` vs `""` | - | base: `j == 0` | 1 |
| 8 | `. . . . solve(0,0)` | `""` vs `""` | - | base | 0 |
| 9 | `. . . solve(0,1)` | `""` vs `b` | - | base: `i == 0` | 1 |
| 10 | `. . solve(2,1)` | `ab` vs `b` | `b` = `b` | match, go to `(1,0)` | 1 |
| 11 | `. . . solve(1,0)` | `a` vs `""` | - | base: `j == 0` | 1 |
| 12 | `. . solve(1,1)` | `a` vs `b` | `a` != `b` | try del, ins, rep | 1 + min(1, 1, 0) = 1 |
| 13 | `. . . solve(0,1)` | `""` vs `b` | - | base: `i == 0` | 1 |
| 14 | `. . . solve(1,0)` | `a` vs `""` | - | base: `j == 0` | 1 |
| 15 | `. . . solve(0,0)` | `""` vs `""` | - | base | 0 |

Read call 2's three children in order: delete leads to call 3 (returns 2), insert leads to call 10 (returns 1), replace leads to call 12 (returns 1). The min is 1, plus the edit itself, so `solve(2,2) = 2`. Call 1 passes that up unchanged because `d` matched. Answer: **2**.

### Java

```java
class Solution {
    public int minDistance(String word1, String word2) {
        return solve(word1, word2, word1.length(), word2.length());
    }

    // Fewest operations to turn word1's first i chars into word2's first j chars.
    private int solve(String word1, String word2, int i, int j) {
        if (i == 0) return j;          // insert the j chars still missing
        if (j == 0) return i;          // delete the i chars still left over

        if (word1.charAt(i - 1) == word2.charAt(j - 1)) {
            return solve(word1, word2, i - 1, j - 1);   // last chars agree - free
        }

        int delete  = solve(word1, word2, i - 1, j);
        int insert  = solve(word1, word2, i, j - 1);
        int replace = solve(word1, word2, i - 1, j - 1);
        return 1 + Math.min(delete, Math.min(insert, replace));
    }
}
```

### Complexity

**Time:** `O(3^(m+n))` - **Space:** `O(m + n)` recursion depth

### Where it hurts

Count how often each question was asked in that 15-call trace:

| subproblem | prefixes | times computed |
| :--------- | :------- | -------------: |
| `(1,1)` | `a` vs `b` | 2 |
| `(0,1)` | `""` vs `b` | 3 |
| `(1,0)` | `a` vs `""` | 3 |
| `(0,0)` | `""` vs `""` | 2 |

15 calls, but only **9 distinct** `(i, j)` pairs. On a toy input a third of the work is repeated. It gets much worse as the strings grow, because every mismatch branches three ways and the branches keep landing on the same cells:

| input | calls | distinct `(i, j)` |
| :---- | ----: | ----------------: |
| `abd` / `bcd` | 15 | 9 |
| `horse` / `ros` | 77 | 18 |
| `sea` / `eat` | 50 | 13 |

`solve(2, 0)` alone is recomputed 12 times on `horse` / `ros`. On two 500-character strings the call count is astronomical while the number of distinct questions is only `501 * 501`.

The answer to `solve(i, j)` never changes - it depends only on `i` and `j`. So compute each one **once** and look it up after that.

=== optimization ===
The repeated work has a fixed shape: the result of `solve(i, j)` is a pure function of two integers in the ranges `0..m` and `0..n`. That is a grid with `(m+1) * (n+1)` cells.

### Step 1 - remember answers (top-down)

The smallest change to the brute force: keep a `memo[i][j]`, check it before recursing, store into it before returning.

```java
class Solution {
    private int[][] memo;

    public int minDistance(String word1, String word2) {
        memo = new int[word1.length() + 1][word2.length() + 1];
        for (int[] row : memo) Arrays.fill(row, -1);    // -1 = not computed yet
        return solve(word1, word2, word1.length(), word2.length());
    }

    private int solve(String word1, String word2, int i, int j) {
        if (i == 0) return j;
        if (j == 0) return i;
        if (memo[i][j] != -1) return memo[i][j];

        int result;
        if (word1.charAt(i - 1) == word2.charAt(j - 1)) {
            result = solve(word1, word2, i - 1, j - 1);
        } else {
            int delete  = solve(word1, word2, i - 1, j);
            int insert  = solve(word1, word2, i, j - 1);
            int replace = solve(word1, word2, i - 1, j - 1);
            result = 1 + Math.min(delete, Math.min(insert, replace));
        }
        memo[i][j] = result;
        return result;
    }
}
```

On `abd` / `bcd`, calls 12-15 collapse into a single lookup of `memo[1][1]`. This is already `O(m * n)`. But the recursion depth is `m + n` (up to 1,000 frames), and the order of filling is hidden inside the call stack.

### Step 2 - fill the grid in order (bottom-up)

Every cell needs only its **up**, **left** and **up-left** neighbours. So if we fill row by row, left to right, those three are always ready.

```text
            j-1        j
         +--------+--------+
   i-1   |  diag  |   up   |     up   = dp[i-1][j]   -> delete word1[i-1]
         +--------+--------+     left = dp[i][j-1]   -> insert word2[j-1]
   i     |  left  |  ????  |     diag = dp[i-1][j-1] -> replace (or free on a match)
         +--------+--------+
```

The base cases become the first row and column:

- `dp[0][j] = j` - from the empty string, insert `j` characters
- `dp[i][0] = i` - to the empty string, delete `i` characters

### Dry run - same example

```text
word1 = "abd"  (rows, i)
word2 = "bcd"  (columns, j)
```

Start with only the base cases:

```text
          ""   b    c    d
    ""     0   1    2    3
    a      1   .    .    .
    b      2   .    .    .
    d      3   .    .    .
```

Now fill all nine inner cells, row by row:

| cell | `word1[i-1]` | `word2[j-1]` | match? | up | left | diag | `dp[i][j]` |
| :--- | :----------: | :----------: | :----- | -: | ---: | ---: | ---------: |
| `(1,1)` | `a` | `b` | no | 1 | 1 | 0 | 1 + 0 = **1** |
| `(1,2)` | `a` | `c` | no | 2 | 1 | 1 | 1 + 1 = **2** |
| `(1,3)` | `a` | `d` | no | 3 | 2 | 2 | 1 + 2 = **3** |
| `(2,1)` | `b` | `b` | yes | - | - | 1 | diag = **1** |
| `(2,2)` | `b` | `c` | no | 2 | 1 | 1 | 1 + 1 = **2** |
| `(2,3)` | `b` | `d` | no | 3 | 2 | 2 | 1 + 2 = **3** |
| `(3,1)` | `d` | `b` | no | 1 | 3 | 2 | 1 + 1 = **2** |
| `(3,2)` | `d` | `c` | no | 2 | 2 | 1 | 1 + 1 = **2** |
| `(3,3)` | `d` | `d` | yes | - | - | 2 | diag = **2** |

The finished table:

```text
          ""   b    c    d
    ""     0   1    2    3
    a      1   1    2    3
    b      2   1    2    3
    d      3   2    2   [2]
```

`dp[3][3] = 2`. Same answer as the recursion, with exactly 9 computed cells and no repeats. Notice `dp[2][2] = 2` and `dp[2][1] = 1` - those are the values calls 2 and 10 returned in the brute-force trace. The table is the recursion's answers, written down.

### Reading the edits back out

Start at the bottom-right and ask "which neighbour did this come from?":

```text
(3,3)  d = d, came from diag        -> keep 'd'
(2,2)  b != c, left = 1 is a min    -> INSERT 'c'
(2,1)  b = b, came from diag        -> keep 'b'
(1,0)  base, 1                      -> DELETE 'a'
```

Delete `a`, insert `c`: exactly the 2-step plan from the problem section.

### Why a match takes the diagonal for free

On a match we copy `dp[i-1][j-1]` without considering up or left. That is safe because neighbouring cells differ by at most 1, so `dp[i-1][j-1] <= dp[i-1][j] + 1` and `dp[i-1][j-1] <= dp[i][j-1] + 1`. The diagonal is never beaten.

### The LeetCode example, for reference

```text
          ""   r    o    s
    ""     0   1    2    3
    h      1   1    2    3
    o      2   2    1    2
    r      3   2    2    2
    s      4   3    3    2
    e      5   4    4   [3]
```

Tracing back from `(5,3)`: up (delete `e`), diag on `s = s`, up (delete `r`), diag on `o = o`, diag from `(1,1)` with cost (replace `h -> r`). Three edits - the `horse -> rorse -> rose -> ros` sequence.

=== complexity ===
### Time

`(m+1) * (n+1)` cells, each filled with one comparison and at most three lookups.

```text
O(m * n)
```

### Space

The full table is `(m+1) * (n+1)` integers.

```text
O(m * n)
```

Each row only reads the row directly above it, so two rows - or one row plus a saved diagonal - is enough. That brings it to `O(n)`, shown in the implementation section.

### Comparison

| Approach | Time | Space | Notes |
| :------- | ---: | ----: | :---- |
| Plain recursion | `O(3^(m+n))` | `O(m + n)` | 77 calls for `horse`/`ros` |
| Memoised recursion | `O(m * n)` | `O(m * n)` | plus `O(m + n)` stack |
| Bottom-up table | **`O(m * n)`** | `O(m * n)` | can trace the edits back |
| Single rolling row | **`O(m * n)`** | **`O(n)`** | count only, no traceback |

For `500 x 500` the table version does 250,000 cell updates - a few milliseconds.

=== implementation ===
```java
class Solution {
    public int minDistance(String word1, String word2) {

        int m = word1.length();
        int n = word2.length();

        // dp[i][j] = fewest operations to turn word1[0..i) into word2[0..j).
        int[][] dp = new int[m + 1][n + 1];

        for (int i = 0; i <= m; i++) dp[i][0] = i;   // delete everything
        for (int j = 0; j <= n; j++) dp[0][j] = j;   // insert everything

        for (int i = 1; i <= m; i++) {
            for (int j = 1; j <= n; j++) {
                if (word1.charAt(i - 1) == word2.charAt(j - 1)) {
                    dp[i][j] = dp[i - 1][j - 1];   // nothing to fix here
                } else {
                    int replace = dp[i - 1][j - 1];
                    int delete  = dp[i - 1][j];
                    int insert  = dp[i][j - 1];
                    dp[i][j] = 1 + Math.min(replace, Math.min(delete, insert));
                }
            }
        }

        return dp[m][n];
    }
}
```

### The lines that matter

**1.**

```java
for (int i = 0; i <= m; i++) dp[i][0] = i;   // delete everything
for (int j = 0; j <= n; j++) dp[0][j] = j;   // insert everything
```

The base cases are not zeros. Turning `"abc"` into `""` costs 3 deletions; turning `""` into `"bc"` costs 2 insertions. Leave them at Java's default `0` and every answer comes out too small.

**2.**

```java
if (word1.charAt(i - 1) == word2.charAt(j - 1)) {
```

`dp` is indexed by **length**, the strings by **position**. Cell `(i, j)` talks about the characters at `i - 1` and `j - 1`. That off-by-one is the price of having row 0 and column 0 mean "empty string".

**3.**

```java
dp[i][j] = 1 + Math.min(replace, Math.min(delete, insert));
```

`Math.min` takes two arguments, so three-way minimum is two nested calls. The `1 +` is the edit being made at this cell; each neighbour already includes the cost of everything before it.

### The `O(n)` space version

Row `i` reads only row `i - 1`. Keep one array, and save the one value that gets overwritten before it is needed - the diagonal.

```java
class Solution {
    public int minDistance(String word1, String word2) {

        int m = word1.length();
        int n = word2.length();

        int[] dp = new int[n + 1];
        for (int j = 0; j <= n; j++) dp[j] = j;        // row 0

        for (int i = 1; i <= m; i++) {
            int diag = dp[0];                         // old dp[i-1][0]
            dp[0] = i;                                // new dp[i][0]
            for (int j = 1; j <= n; j++) {
                int up = dp[j];                       // still row i-1
                if (word1.charAt(i - 1) == word2.charAt(j - 1)) {
                    dp[j] = diag;
                } else {
                    dp[j] = 1 + Math.min(diag, Math.min(up, dp[j - 1]));
                }
                diag = up;                            // becomes next cell's diagonal
            }
        }

        return dp[n];
    }
}
```

Before `dp[j]` is overwritten it still holds row `i - 1`'s value (that is `up`). `dp[j - 1]` was already overwritten, so it holds row `i`'s value (that is `left`). The diagonal - row `i - 1`, column `j - 1` - was overwritten one step ago, which is why `diag = up` saves it just before it is lost.

### Java notes

- `charAt` on a `String` is `O(1)`. Calling `toCharArray()` once first is marginally faster and some people find it more readable; it does not change the complexity.
- `new int[m + 1][n + 1]` allocates `m + 1` separate row arrays. For `501 x 501` that is about 1 MB - fine, but it is why the rolling-row version is the follow-up.
- The table version is the one to write first in an interview: it is easier to dry-run on a whiteboard, and you can trace the actual edits back out of it.

=== edgeCases ===
### Both strings empty

```text
"", ""  ->  0
```

Neither loop body runs; `dp[0][0] = 0` is returned.

### One string empty

```text
"", "abc"  ->  3
"abc", ""  ->  3
```

The answer is read straight off a base row or column. These are exactly the cases the base cases exist for.

### Identical strings

```text
"abc", "abc"  ->  0
```

Every diagonal cell is a match, so the zero in `dp[0][0]` is copied down the diagonal to `dp[3][3]`.

### Nothing in common, same length

```text
"abc", "xyz"  ->  3
```

Three replacements. Never more than `max(m, n)` in general: replace the overlap, then insert or delete the rest.

### One is a prefix of the other

```text
"ab", "abcd"  ->  2
```

Two inserts at the end. The first two diagonal cells match for free, then the row walks right paying `1` per column.

### Same letters, different order

```text
"ab", "ba"  ->  2
```

Not 1. There is no "swap" operation, so you either replace both characters, or delete one end and insert at the other.

### Single characters

```text
"a", "b"  ->  1
"a", "a"  ->  0
```

### The second LeetCode example

```text
"intention", "execution"  ->  5
```

`intention -> inention` (delete `t`) `-> enention` (replace `i -> e`) `-> exention` (replace `n -> x`) `-> exection` (replace `n -> c`) `-> execution` (insert `u`).

### Maximum size

Two 500-character strings: 251,001 cells, well within limits. The plain recursion would never finish on this input - which is the practical reason the table matters.

=== takeaway ===
> When you see **two strings** and a question about **converting, aligning or comparing** them, think **`dp[i][j]` over prefixes**, decided by the last character of each.

### The core observation

Only the last characters need a decision. If they match, they are free and the problem shrinks diagonally. If not, one of three edits fixes the end, and each leaves a smaller pair of prefixes: delete moves **up**, insert moves **left**, replace moves **diagonally**. The answer to every prefix pair is reused by many longer ones, so a table computes each exactly once.

### The pattern trigger

```text
       two sequences, compare / transform / align
                        |
                        v
       state: dp[i][j] over prefixes of length i and j
       row 0 and col 0 = the empty string (base cases)
                        |
                        v
       look at word1[i-1] and word2[j-1]
              /                    \
          equal                   differ
            |                        |
      dp[i-1][j-1]       1 + min(up, left, diag)
                        |
                        v
       fill row by row; answer in dp[m][n]
```

### The common mistakes

**Zero base cases.** Leaving `dp[i][0]` and `dp[0][j]` at `0` says "converting to or from the empty string is free". Every answer is then too small.

**Indexing the strings with `i` instead of `i - 1`.** The table has one extra row and column; the strings do not. `charAt(i)` reads the wrong character and throws at `i = m`.

**Rolling row without saving the diagonal.** In the `O(n)` version, `dp[j - 1]` has already been overwritten with the current row by the time you need the previous row's value. Forgetting `diag` silently computes something else.

**Treating "ab" -> "ba" as one edit.** Swap is not an allowed operation. If the problem ever adds it, that is a different recurrence (Damerau-Levenshtein).

### What to remember in six months

> Edit Distance is LCS with costs. Same grid, same last-character question - matches go diagonal for free, and a mismatch pays `1` to step up, left, or diagonally.

Delete Operation for Two Strings (LC 583) is this with replace removed. One Edit Distance (LC 161) asks whether the answer is exactly 1, which you can check in a single linear pass without the table. Spell checkers, `diff` tools and DNA alignment all run some version of this grid.
