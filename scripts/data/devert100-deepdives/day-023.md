=== intro ===
Day 22 closed out two pointers and sliding windows with Trapping Rain Water. Today opens the hashing and prefix sum block - and it opens with the problem that shows exactly where a sliding window stops working.

> When a subarray sum has to hit an exact value and the array can contain negatives, stop moving windows. Turn "sum of a range" into "difference of two running totals", and the question becomes Day 1's: have I already seen the number I need?

=== problem ===
Given an integer array `nums` and an integer `k`, return the **number** of contiguous, non-empty subarrays whose elements sum to exactly `k`.

```text
nums = [1, 2, 3, -3, 3]
k    = 3
```

| Subarray | Indices | Sum |
| :------- | :------ | --: |
| `[1, 2]` | 0..1 | 3 |
| `[1, 2, 3, -3]` | 0..3 | 3 |
| `[3]` | 2..2 | 3 |
| `[3, -3, 3]` | 2..4 | 3 |
| `[3]` | 4..4 | 3 |

```text
answer = 5
```

Two `[3]`s appear in that list, and both count. Subarrays are identified by **position**, not by content - the `3` at index 2 and the `3` at index 4 are different subarrays.

### The constraints that shape the solution

```text
1 <= nums.length <= 2 * 10^4
-1000 <= nums[i] <= 1000
-10^7 <= k <= 10^7
```

1. **Values can be negative.** This is the line that matters most. It means adding an element can make a sum go *down*, so a running sum is not monotonic - and that is exactly the property a sliding window depends on.
2. **`n` up to 20,000.** An `O(n^2)` solution does about 200 million additions. That is borderline; the intended answer is `O(n)`.
3. **The answer is a count, not a list.** We never have to say *which* subarrays - only how many. That is what lets a hash map of counts do the job.

### Why a sliding window fails here

On Day 22's sliding windows, the rule was: if the window sum is too big, shrink from the left. That only works when shrinking always makes the sum smaller - when every element is positive.

```text
nums = [3, -3, 3], k = 3
window [3]        sum 3  -> match
grow  [3, -3]     sum 0  -> too small, grow
grow  [3, -3, 3]  sum 3  -> match
```

With a window, "too small" and "too big" stop meaning "grow" and "shrink". A negative element can bring an oversized window back down to `k` later, so you can never safely throw the left edge away. We need a different tool.

=== pattern ===
**Prefix Sum + HashMap** (counting form).

Define `prefix[j]` as the sum of the first `j` elements. Then the sum of any subarray is the difference of two prefix sums:

```text
sum(nums[i..j]) = prefix[j + 1] - prefix[i]
```

So "this subarray sums to `k`" is the same statement as:

```text
prefix[j + 1] - prefix[i] = k
                prefix[i] = prefix[j + 1] - k
```

Read that last line as a question asked while standing at index `j` with the running sum in hand:

> How many earlier running sums were equal to `currentSum - k`?

Each one of those earlier positions is the start of a subarray that ends here and sums to `k`. "How many times have I seen value X?" is a `HashMap<Integer, Integer>` lookup. This is Day 1's complement lookup, applied to running totals instead of to elements.

### The picture

```text
index:        0    1    2    3    4
nums:         1    2    3   -3    3
prefix:  0    1    3    6    3    6
         ^                   ^
         the empty prefix    at index 3, sum = 3, need 3 - 3 = 0 -> seen once
                             so [1, 2, 3, -3] sums to 3
```

The leading `0` is the sum of the empty prefix - nothing taken yet. It is the reason the map starts as `{0: 1}`, and it is what lets a subarray starting at index 0 be counted.

### Recognising it

Reach for prefix sum + hash map when:

- the problem asks about **contiguous subarrays** and a **sum** (or anything that becomes a sum)
- the target is **exact** ("equals k", "divisible by k", "equal number of X and Y")
- the values can be **negative or zero**, which rules out a sliding window

The mental question:

> Can I rewrite "this range satisfies the condition" as "two running totals differ by a fixed amount"?

If yes, one pass with a map of running totals answers it.

=== bruteForce ===
Pretend the trick is unknown. The direct reading of the problem is: try every subarray, add it up, count the ones that hit `k`.

The naive version recomputes each subarray's sum from scratch, which is `O(n^3)`. One improvement is free: fix the start, then extend the end one element at a time, carrying a running `sum`. Each extension costs one addition.

### Step logic

1. For every `start` from `0` to `n - 1`:
2. Reset `sum = 0`.
3. For every `end` from `start` to `n - 1`: add `nums[end]` to `sum`; if `sum == k`, increment `count`.

### Dry run

```text
nums = [1, 2, 3, -3, 3], k = 3
```

| start | end | nums[end] | sum | sum == 3? | count |
| ----: | --: | --------: | --: | :-------- | ----: |
| 0 | 0 | 1 | 1 | no | 0 |
| 0 | 1 | 2 | 3 | **yes** | 1 |
| 0 | 2 | 3 | 6 | no | 1 |
| 0 | 3 | -3 | 3 | **yes** | 2 |
| 0 | 4 | 3 | 6 | no | 2 |
| 1 | 1 | 2 | 2 | no | 2 |
| 1 | 2 | 3 | 5 | no | 2 |
| 1 | 3 | -3 | 2 | no | 2 |
| 1 | 4 | 3 | 5 | no | 2 |
| 2 | 2 | 3 | 3 | **yes** | 3 |
| 2 | 3 | -3 | 0 | no | 3 |
| 2 | 4 | 3 | 3 | **yes** | 4 |
| 3 | 3 | -3 | -3 | no | 4 |
| 3 | 4 | 3 | 0 | no | 4 |
| 4 | 4 | 3 | 3 | **yes** | 5 |

`count = 5`. Correct.

Look at rows `(0, 1)` and `(0, 3)`: the sum hit `3`, went up to `6`, then came back down to `3`. Under a sliding window we would have stopped extending at `6`. The brute force does not care about direction, which is why it is correct with negatives.

### Java

```java
class Solution {
    public int subarraySum(int[] nums, int k) {

        int count = 0;

        for (int start = 0; start < nums.length; start++) {

            int sum = 0;

            for (int end = start; end < nums.length; end++) {
                sum += nums[end];
                if (sum == k) {
                    count++;
                }
            }
        }

        return count;
    }
}
```

### Complexity

**Time:** `O(n^2)` - **Space:** `O(1)`

### Where it hurts

The table has 15 rows for 5 elements: `n(n + 1) / 2` subarrays, one row each. At `n = 20,000` that is 200 million rows.

Now look at what each row's `sum` actually is. Row `(2, 4)` computes `3 + (-3) + 3 = 3`. But the row `(0, 4)` already computed the sum of everything up to index 4 (`6`), and row `(0, 1)` already computed the sum of everything before index 2 (`3`). Their difference is `6 - 3 = 3` - the same answer, with no new additions.

```text
sum(2..4) = (sum of 0..4) - (sum of 0..1) = 6 - 3 = 3
```

Every row with `start > 0` is re-adding elements that the `start = 0` rows already added. The only sums we really need are the `n` running totals from index 0. Every subarray sum is a difference of two of them.

And once we see that, the inner loop is not "try every start" any more. It is "count how many earlier running totals equal `current - k`" - a question a hash map answers in one step.

=== optimization ===
### The key observation

Let `prefix` be the running sum up to and including the current index. A subarray ending here sums to `k` exactly when some earlier running total equals `prefix - k`. So:

- keep a map from **running total -> how many times it has occurred so far**
- at each index, add `map[prefix - k]` to the answer
- then record the current `prefix` in the map

### Why the map starts as `{0: 1}`

Before reading any element, the running total is `0`, and that empty prefix genuinely exists - it is the left edge of every subarray that starts at index 0. Without it, `[1, 2]` (indices 0..1) would never be counted, because at index 1 we need an earlier total of `3 - 3 = 0`, and no element-ending prefix is `0`.

### Step logic

1. `map = {0: 1}`, `prefix = 0`, `count = 0`.
2. For each `num`: `prefix += num`.
3. `count += map.getOrDefault(prefix - k, 0)`.
4. `map[prefix]++` - **after** the lookup.

### Dry run - same example

```text
nums = [1, 2, 3, -3, 3], k = 3
```

| i | nums[i] | prefix | need `prefix - 3` | map[need] | count | map after recording prefix |
| -: | ------: | -----: | ----------------: | --------: | ----: | :------------------------- |
| - | - | 0 | - | - | 0 | `{0:1}` |
| 0 | 1 | 1 | -2 | 0 | 0 | `{0:1, 1:1}` |
| 1 | 2 | 3 | 0 | 1 | **1** | `{0:1, 1:1, 3:1}` |
| 2 | 3 | 6 | 3 | 1 | **2** | `{0:1, 1:1, 3:1, 6:1}` |
| 3 | -3 | 3 | 0 | 1 | **3** | `{0:1, 1:1, 3:2, 6:1}` |
| 4 | 3 | 6 | 3 | **2** | **5** | `{0:1, 1:1, 3:2, 6:2}` |

`count = 5`. Same answer, five rows instead of fifteen.

### Reading the rows back as subarrays

Each lookup hit is a set of subarrays ending at `i`:

| i | earlier total that matched | at prefix position | subarray found |
| -: | :------------------------- | :----------------- | :------------- |
| 1 | `0` | the empty prefix | `[1, 2]` = indices 0..1 |
| 2 | `3` | after index 1 | `[3]` = index 2 |
| 3 | `0` | the empty prefix | `[1, 2, 3, -3]` = indices 0..3 |
| 4 | `3` (first time) | after index 1 | `[3, -3, 3]` = indices 2..4 |
| 4 | `3` (second time) | after index 3 | `[3]` = index 4 |

Row `i = 4` is the reason the map stores **counts** rather than a yes/no. The total `3` occurred twice before index 4, so two different subarrays end at index 4 with sum `3`. A `HashSet` would have counted one.

### Why the order of the last two steps matters

The lookup must happen **before** the current prefix is recorded. If you record first, then with `k = 0` the lookup `map[prefix - 0]` finds the entry you just added - which corresponds to the *empty* subarray from here to here. Empty subarrays are not allowed, so that would over-count by one at every index.

=== complexity ===
### Time

One pass. Each index does one addition, one `getOrDefault` and one `merge`, each `O(1)` on average for a `HashMap`.

```text
O(n)
```

### Space

The map holds at most one entry per distinct running total, and there are at most `n + 1` running totals (including the empty prefix).

```text
O(n)
```

### Why

The brute force spends its time *re-deriving* sums. The optimal version derives each running total once and stores it, so every later question about it is a lookup. That is the trade: `O(n)` memory buys back a factor of `n` in time.

### Comparison

| Approach | Time | Space | Works with negatives? |
| :------- | ---: | ----: | :-------------------- |
| Recompute each subarray | `O(n^3)` | `O(1)` | yes |
| Fixed start, running sum | `O(n^2)` | `O(1)` | yes |
| Sliding window | `O(n)` | `O(1)` | **no** |
| Prefix sum + HashMap | **`O(n)`** | `O(n)` | yes |

The sliding window row is there on purpose. It is the wrong answer that looks right, and saying out loud why it fails ("negatives break monotonicity") is worth more in an interview than jumping straight to the map.

=== implementation ===
```java
class Solution {
    public int subarraySum(int[] nums, int k) {

        // running total -> how many times it has appeared so far
        Map<Integer, Integer> seen = new HashMap<>();
        seen.put(0, 1);     // the empty prefix, before any element

        int prefix = 0;
        int count = 0;

        for (int num : nums) {
            prefix += num;

            // every earlier total equal to prefix - k starts a subarray
            // that ends here and sums to k
            count += seen.getOrDefault(prefix - k, 0);

            // record AFTER the lookup, so a subarray is never empty
            seen.merge(prefix, 1, Integer::sum);
        }

        return count;
    }
}
```

### The lines that matter

**1.**

```java
seen.put(0, 1);     // the empty prefix, before any element
```

Without this, every subarray that starts at index 0 is invisible. `[3]` with `k = 3` would return `0`. It is the single most common bug on this problem.

**2.**

```java
count += seen.getOrDefault(prefix - k, 0);
```

`+=` the **count**, not `+= 1`. One lookup can stand for several subarrays at once, as index 4 of the dry run showed.

**3.**

```java
seen.merge(prefix, 1, Integer::sum);
```

`merge` inserts `1` if the key is absent, otherwise adds `1` to the existing value. It is the one-line form of `seen.put(prefix, seen.getOrDefault(prefix, 0) + 1)`. It comes after the lookup for the reason the optimization section gave: the other order counts empty subarrays when `k = 0`.

### Java notes

- `Map<Integer, Integer>` boxes every key. That is fine at `n = 20,000`. In a tight loop on huge inputs an `int[]` offset array can replace it, but only when the range of running totals is small and known.
- Overflow is not a concern here: `|prefix| <= 2 * 10^4 * 1000 = 2 * 10^7`, well inside `int`. Without that bound, use `long prefix` and a `Map<Long, Integer>`.
- `getOrDefault` avoids the `NullPointerException` you would get from unboxing `seen.get(x)` when `x` is missing.

=== edgeCases ===
### Single element equal to k

```text
nums = [3], k = 3  ->  1
```

Only works because of the `{0: 1}` seed: at index 0, `prefix = 3`, need `0`, found once.

### Single element not equal to k

```text
nums = [5], k = 3  ->  0
```

### Duplicates - the LeetCode example

```text
nums = [1, 1, 1], k = 2  ->  2
```

`[1, 1]` at indices 0..1 and again at 1..2. Two different subarrays with identical content, both counted.

### k = 0 with zeros

```text
nums = [0, 0, 0], k = 0  ->  6
```

Every one of the six subarrays sums to `0`. The running total is `0` four times (including the seed), and the map counts `1 + 2 + 3 = 6`. This is the case that catches recording before looking up - that order returns `9`.

### Negatives cancelling out

```text
nums = [1, -1, 0], k = 0  ->  3
```

`[1, -1]`, `[0]`, and `[1, -1, 0]`. A sliding window would miss the first one: after `[1]` its sum is too big, so it would shrink away the `1` before the `-1` arrives.

### Negative k

```text
nums = [-1, -1, 1], k = -1  ->  3
```

`[-1]` at index 0, `[-1]` at index 1, and `[-1, -1, 1]`. Nothing in the algorithm assumes `k > 0`.

### No subarray hits k

```text
nums = [1, 2, 3], k = 7  ->  0
```

The full array sums to `6`. Every lookup misses.

### Whole array is the only answer

```text
nums = [2, -1, 2], k = 3  ->  1
```

Running totals `0, 2, 1, 3`. Only the final one has a partner (`3 - 3 = 0`, the seed), so only the whole array counts.

=== takeaway ===
> When you see **"count subarrays whose sum equals k"** - especially with negatives allowed - think **running total plus a hash map of how often each total has appeared**, seeded with `{0: 1}`.

### The core observation

A subarray sum is the difference of two running totals. So "a subarray ending here sums to `k`" means "some earlier running total was `prefix - k`", and counting those is a hash map lookup. The nested loop disappears because the start index is never chosen - it is looked up.

### The pattern trigger

```text
   contiguous subarray + exact sum target
                  |
                  v
        negatives possible?  -- no -->  sliding window may work
                  |
                 yes
                  v
   sum(i..j) = prefix[j+1] - prefix[i]
                  |
                  v
   at each j: count += map[prefix - k]
              map[prefix]++        (after the lookup)
                  |
                  v
   seed map with {0: 1}  =  the empty prefix
```

### The common mistakes

**Forgetting the seed.** Every subarray that starts at index 0 is lost. The bug passes many random tests and fails the obvious one.

**Recording before looking up.** Counts empty subarrays when `k = 0`.

**Using a set instead of a map of counts.** Correct on inputs with distinct running totals, wrong whenever a total repeats.

**Reaching for a sliding window.** It passes all-positive tests and silently fails the first negative.

### What to remember in six months

> Range sum = difference of two prefix sums. Turn the range condition into "an earlier prefix equals X" and the map does the rest.
