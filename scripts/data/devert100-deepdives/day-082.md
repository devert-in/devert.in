=== intro ===
Yesterday's greedy sorted intervals by end time and proved it with an exchange argument. Today the items have no time at all - just a value and a weight - and the greedy key becomes a **ratio**.

> Before trusting a greedy, ask what the problem lets you do with the leftovers. Here you may cut an item into pieces, and that single permission is the whole reason greedy works. Take it away (Day 93's 0/1 knapsack) and the same greedy gives wrong answers.

=== problem ===
There are `n` items. Item `i` has value `val[i]` and weight `wt[i]`. A knapsack holds at most `capacity` weight. You may take **any fraction** of an item: taking a fraction `f` of item `i` (with `0 <= f <= 1`) adds `f * wt[i]` weight and `f * val[i]` value. Return the **maximum total value** that fits.

```text
val      = [60, 100, 120]
wt       = [10,  20,  30]
capacity = 50
answer   = 240.0
```

How `240` is reached:

| item | value | weight | taken | weight used | value gained |
| ---: | ----: | -----: | :---- | ----------: | -----------: |
| 0 | 60 | 10 | all | 10 | 60 |
| 1 | 100 | 20 | all | 20 | 100 |
| 2 | 120 | 30 | 20 of 30 = two thirds | 20 | 80 |
| | | | **total** | **50** | **240** |

### "Fractional" is the word that matters

Think of the items as sacks of spice, not laptops. Half a sack of saffron is worth half the price. That changes everything:

- The knapsack never has to be left partly empty if there is still anything outside it - you can always pour in a bit more.
- An item is never "too big to fit" - you take as much as fits.

The non-fractional version (each item all-or-nothing) is a different problem with a different solution, and mixing them up is the most common mistake on this topic.

### What the constraints tell you

- `n` up to `10^5`, values and weights up to `10^5`. Anything exponential is out; the expected solution is a **sort**, `O(n log n)`.
- The answer is a `double`. GFG accepts it to about six decimal places, because a fraction like `100 * 1/3` has no exact decimal form.
- `val[i] * wt[j]` can reach `10^10`, which does not fit in an `int`. That matters for the comparator.

=== pattern ===
**Greedy - sort by value per unit weight.**

The reframe: stop thinking about items and think about **units of weight**. Each unit of capacity is a slot, and you are deciding what to pour into it. Item `i` puts `val[i] / wt[i]` of value into every unit it occupies - its **ratio**, or value density.

```text
item 0:  60 / 10  = 6.0  per unit
item 1: 100 / 20  = 5.0  per unit
item 2: 120 / 30  = 4.0  per unit
```

If every unit can be filled with whatever you like, fill each one with the **densest** material still available. Item 0 first until it runs out, then item 1, then item 2 until the bag is full.

### Recognising it

Reach for ratio-greedy when:

- there is a **budget** (capacity, time, money) and items consume it
- items are **divisible**: fractions, liquids, hours, "you may take part of"
- every unit of an item is worth the same as every other unit of it

The mental question:

> Can I split items freely? If so, what is each unit of budget worth under each item?

If items cannot be split, stop - that is 0/1 knapsack, and it needs dynamic programming.

=== bruteForce ===
Think as if the ratio idea has not occurred to us yet.

Any sensible way of packing looks like this: pick an **order** for the items, then walk that order putting each item in whole while it fits, and when one does not fit, take as much of it as the remaining space allows and stop. So the brute force tries **every order** - all `n!` permutations - packs each one that way, and keeps the best total.

(Why is "pack in some order" enough to find the optimum? Because the optimum itself has that shape - several whole items, then at most one partial one. The optimisation section proves it.)

### Dry run

```text
val = [60, 100, 120],  wt = [10, 20, 30],  capacity = 50
```

Three items, `3! = 6` orders. Each cell shows what the item contributes and the space left after it.

| order | 1st item | 2nd item | 3rd item | total | best after |
| :---- | :------- | :------- | :------- | ----: | ---------: |
| 0, 1, 2 | item 0 whole: +60, left 40 | item 1 whole: +100, left 20 | item 2, 20 of 30: +80, left 0 | 240 | 240 |
| 0, 2, 1 | item 0 whole: +60, left 40 | item 2 whole: +120, left 10 | item 1, 10 of 20: +50, left 0 | 230 | 240 |
| 1, 0, 2 | item 1 whole: +100, left 30 | item 0 whole: +60, left 20 | item 2, 20 of 30: +80, left 0 | 240 | 240 |
| 1, 2, 0 | item 1 whole: +100, left 30 | item 2 whole: +120, left 0 | bag full: +0 | 220 | 240 |
| 2, 0, 1 | item 2 whole: +120, left 20 | item 0 whole: +60, left 10 | item 1, 10 of 20: +50, left 0 | 230 | 240 |
| 2, 1, 0 | item 2 whole: +120, left 20 | item 1 whole: +100, left 0 | bag full: +0 | 220 | 240 |

Answer `240.0`. Correct.

Notice the two winning rows: `0, 1, 2` and `1, 0, 2`. Both put item 2 **last**, so it is the one that gets cut. The two worst rows (`220`) are the ones that put item 2 in **whole** and let it crowd out item 0.

### Java

```java
class Solution {

    private double best;

    public double fractionalKnapsack(int[] val, int[] wt, int capacity) {
        best = 0;
        int n = val.length;
        permute(val, wt, capacity, new int[n], new boolean[n], 0);
        return best;
    }

    // Build every order of the items, one position at a time.
    private void permute(int[] val, int[] wt, int capacity,
                         int[] order, boolean[] used, int depth) {
        int n = val.length;
        if (depth == n) {
            best = Math.max(best, fillInOrder(val, wt, capacity, order));
            return;
        }
        for (int i = 0; i < n; i++) {
            if (used[i]) continue;
            used[i] = true;
            order[depth] = i;
            permute(val, wt, capacity, order, used, depth + 1);
            used[i] = false;
        }
    }

    // Whole items while they fit, then a fraction of the next one.
    private double fillInOrder(int[] val, int[] wt, int capacity, int[] order) {
        double total = 0;
        int remaining = capacity;
        for (int i : order) {
            if (remaining == 0) break;
            if (wt[i] <= remaining) {
                total += val[i];
                remaining -= wt[i];
            } else {
                total += (double) val[i] * remaining / wt[i];
                remaining = 0;
            }
        }
        return total;
    }
}
```

### Complexity

**Time:** `O(n! * n)` - **Space:** `O(n)` for the order and recursion

### Where it hurts

Six orders for three items is fine. Ten items is 3.6 million orders; twenty is `2.4 * 10^18`. Hopeless at `n = 10^5`.

And the table shows that almost all of that work is pointless. Every losing row puts item 2 - the **least dense** item, 4 per unit - ahead of a denser one, so it occupies space that item 0 (6 per unit) or item 1 (5 per unit) would have filled better. Both winning rows put item 2 last, where it is the one that gets cut. The order between items 0 and 1 does not matter here only because both fit whole either way.

So the search is really asking "which order is best?", and the table already hints at the answer: **densest first**. If that can be proved, there is only one order to try.

=== optimization ===
### The key observation

Measure each item by its density `val[i] / wt[i]`. Then:

> In an optimal packing, no unit of a less dense item is in the bag while some of a denser item is left outside.

**Proof by exchange.** Suppose a packing has some weight `e` of item `j` inside, while some weight `e` of a denser item `i` is outside (`density[i] > density[j]`). Take out `e` of item `j` and pour in `e` of item `i`. The total weight is unchanged, and the value changes by

```text
e * density[i]  -  e * density[j]   =   e * (density[i] - density[j])   >   0
```

The packing got strictly better, so it was not optimal. Therefore an optimal packing takes the densest item fully before touching the next one, and so on. Exactly one item at most is cut - the one in progress when the bag fills.

The swap only works because `e` can be **any** amount. That is where "fractional" is used, and why the argument collapses when items are all-or-nothing.

### The algorithm

1. Sort the items by density, highest first.
2. Walk them. If an item fits whole, take it all. Otherwise take the fraction that fills the bag, and stop.

### Dry run

Densities: item 0 = 6.0, item 1 = 5.0, item 2 = 4.0. Sorted order: `0, 1, 2`.

| item | value | weight | density | `remaining` before | fits whole? | taken | value added | total | `remaining` after |
| ---: | ----: | -----: | ------: | -----------------: | :---------- | :---- | ----------: | ----: | ----------------: |
| - | - | - | - | - | - | start | - | 0 | 50 |
| 0 | 60 | 10 | 6.0 | 50 | yes, `10 <= 50` | all | 60 | 60 | 40 |
| 1 | 100 | 20 | 5.0 | 40 | yes, `20 <= 40` | all | 100 | 160 | 20 |
| 2 | 120 | 30 | 4.0 | 20 | no, `30 > 20` | 20 of 30 | `120 * 20 / 30 = 80` | 240 | 0 |

Answer `240.0` - the brute force's best row, found directly, in one pass after one sort.

### Why greedy fails for 0/1 knapsack

Same items, but now each must be taken whole or not at all.

```text
ratio-greedy, whole items only:
  item 0 (10)  -> take, value 60,  left 40
  item 1 (20)  -> take, value 160, left 20
  item 2 (30)  -> does not fit, skip
  total = 160

best 0/1 choice:
  item 1 + item 2 = weight 50, value 220
```

The greedy fills the bag with dense items and leaves 20 units of space it cannot use, because the last item cannot be cut. The exchange argument needed to swap "a little" of one item for "a little" of another, and that move does not exist when items are indivisible. 0/1 knapsack has to compare whole combinations - that is dynamic programming, on Day 93.

=== complexity ===
### Time

Sorting `n` items by density is `O(n log n)`. The fill is one pass, `O(n)`, often stopping early.

```text
O(n log n)
```

### Space

An `Integer[]` of indices, so `val[i]` and `wt[i]` stay paired while sorting.

```text
O(n) for the index array, O(1) beyond it
```

The `O(1)` sometimes quoted assumes items arrive as objects that can be sorted in place (GFG's older `Item[]` signature). With two parallel arrays, some paired structure is unavoidable.

### Comparison

| Approach | Time | Space | Correct for fractional? | Correct for 0/1? |
| :------- | ---: | ----: | :---------------------- | :--------------- |
| All `n!` orders | `O(n! * n)` | `O(n)` | yes | - |
| **Sort by density, fill** | **`O(n log n)`** | **`O(n)`** | **yes** | no |
| Sort by value, or by weight | `O(n log n)` | `O(n)` | no | no |
| DP over capacity (Day 93) | `O(n * W)` | `O(W)` | - | yes |

Sorting by value takes item 2 (120) first and loses; sorting by lightest weight happens to work on this example but not in general. Only density is backed by the exchange argument.

=== implementation ===
```java
class Solution {
    public double fractionalKnapsack(int[] val, int[] wt, int capacity) {

        int n = val.length;

        // Sort indices so val[i] and wt[i] stay paired.
        Integer[] order = new Integer[n];
        for (int i = 0; i < n; i++) {
            order[i] = i;
        }

        // Highest value-per-weight first. a/b > c/d  <=>  a*d > c*b (all positive),
        // so compare cross-products as long: exact, and no int overflow.
        Arrays.sort(order, (a, b) -> Long.compare((long) val[b] * wt[a], (long) val[a] * wt[b]));

        double total = 0;
        int remaining = capacity;

        for (int i : order) {
            if (remaining == 0) break;

            if (wt[i] <= remaining) {          // fits whole: take all of it
                total += val[i];
                remaining -= wt[i];
            } else {                           // take the fraction that fills the bag
                total += (double) val[i] * remaining / wt[i];
                remaining = 0;
            }
        }

        return total;
    }
}
```

### The lines that matter

**1.**

```java
Arrays.sort(order, (a, b) -> Long.compare((long) val[b] * wt[a], (long) val[a] * wt[b]));
```

Item `a` should come before `b` when `val[a] / wt[a] > val[b] / wt[b]`, which (weights are positive) is the same as `val[a] * wt[b] > val[b] * wt[a]`. Putting the `b` product first in `Long.compare` makes the sort **descending**. The cast to `long` happens **before** the multiplication; `(long) (val[b] * wt[a])` would overflow first and cast the garbage.

**2.**

```java
total += (double) val[i] * remaining / wt[i];
```

The fractional step. The cast makes the whole expression floating-point; without it, `val[i] * remaining / wt[i]` is integer division and `100 * 1 / 3` becomes `33` instead of `33.333...`.

**3.**

```java
if (remaining == 0) break;
```

Once the bag is full, nothing else can add value. Not required for correctness - the fractional branch would add `0` - but it stops the loop early.

### Java notes

- Comparing cross-products instead of `(double) val[i] / wt[i]` avoids floating-point rounding in the sort. Two different ratios that are extremely close can round to the same `double`; integer cross-products never do.
- `Integer[]`, not `int[]`: `Arrays.sort` only accepts a comparator for object arrays.
- GFG's older signature is `double fractionalKnapsack(int W, Item arr[], int n)` with an `Item` class holding `value` and `weight`. The body is the same - sort `arr` with the same comparator using `x.value` and `x.weight`.
- GFG compares the returned `double` to about six decimal places. Return the full `double`; do not round it yourself.

=== edgeCases ===
### Everything fits

```text
val = [10, 20], wt = [1, 2], capacity = 100  ->  30.0
```

Both items are taken whole and `remaining` ends at `97`. No fraction is ever needed.

### Capacity smaller than every item

```text
val = [60], wt = [10], capacity = 5  ->  30.0
```

The very first item goes straight to the fractional branch: half of it, half its value.

### Exact fill, no fraction

```text
val = [60, 100, 120], wt = [10, 20, 30], capacity = 30  ->  160.0
```

Items 0 and 1 fill the bag exactly, `remaining` hits `0`, and the loop breaks before item 2.

### Equal densities

```text
val = [10, 20, 30], wt = [1, 2, 3], capacity = 3  ->  30.0
```

Every item has density 10, so the order among them does not matter. Any 3 units of weight are worth 30.

### A non-terminating decimal

```text
val = [100], wt = [3], capacity = 1  ->  33.333333...
```

The fractional branch must be floating-point. Integer arithmetic here returns `33`.

### Capacity zero

```text
val = [60, 100], wt = [10, 20], capacity = 0  ->  0.0
```

The `remaining == 0` check fires on the first iteration.

### Sorting by value instead of density

```text
val = [60, 100, 120], wt = [10, 20, 30], capacity = 50
by value:   item 2 (30) +120, item 1 (20) +100, bag full  ->  220.0   (wrong)
by density:                                                ->  240.0
```

The most valuable item is not the best use of space.

### The 0/1 trap

```text
same items, whole items only:  ratio-greedy gives 160, true best is 220
```

Not a bug in this solution - a reminder that it solves a different problem from 0/1 knapsack.

=== takeaway ===
> When you see **"items with value and weight, you may take fractions, maximise value under a capacity"**, think **sort by value / weight descending, take whole items until one does not fit, then take a fraction of it**.

### The core observation

With divisible items, every unit of capacity is filled independently, and the best thing to put in it is the densest material left. Any packing that holds a less dense unit while a denser one is outside can be improved by swapping a little of one for the other. So the optimum takes items in density order and cuts at most one.

### The pattern trigger

```text
     budget + items with (value, cost)
                    |
           can items be split?
             /            \
           yes             no
            |               |
  sort by value/cost     0/1 knapsack:
  descending, fill        DP (Day 93)
  whole, then fraction
```

### The common mistakes

**Using this greedy on 0/1 knapsack.** It returns 160 where 220 is possible. The exchange argument needs fractions.

**Sorting by value, or by weight.** Only density is proven.

**Integer division in the fractional step.** `val * remaining / wt` without a `double` loses the fraction.

**`int` cross-products in the comparator.** `10^5 * 10^5` overflows `int`; cast to `long` before multiplying.

### What to remember in six months

> Divisible items: greedy by ratio. Indivisible items: DP. The ability to take "a little more" of something is exactly what the greedy proof uses.

The same density idea appears in Maximum Units on a Truck (LC 1710, where every box has weight 1 so density is just units per box), in job sequencing by profit per hour, and as the upper-bound estimate inside branch-and-bound solvers for 0/1 knapsack.
