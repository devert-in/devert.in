=== intro ===
The last two days used a queue to process courses in waves: everything free now, then everything that freed up. Today the same wave idea moves onto a grid, and the waves are literally minutes on a clock.

The new twist is that the spreading does not start from one place. It starts from every rotten orange at once.

> When several sources spread at the same speed, do not run one search per source. Put every source in the queue at time zero and run one search. The queue keeps them in step for you.

=== problem ===
You get an `m x n` grid where each cell is:

- `0` - empty
- `1` - a fresh orange
- `2` - a rotten orange

Every minute, every fresh orange that is **4-directionally adjacent** (up, down, left, right) to a rotten orange becomes rotten. Return the **minimum number of minutes** until no fresh orange is left, or `-1` if that never happens.

```java
public int orangesRotting(int[][] grid)
```

### The example used all day

```text
grid = [[2, 1, 1],
        [1, 1, 0],
        [0, 1, 1]]
```

Label every cell `(row, col)`. Watch it spread:

```text
minute 0        minute 1        minute 2        minute 3        minute 4
2 1 1           2 2 1           2 2 2           2 2 2           2 2 2
1 1 0           2 1 0           2 2 0           2 2 0           2 2 0
0 1 1           0 1 1           0 1 1           0 2 1           0 2 2
```

Answer: `4`.

| minute | newly rotten | fresh left |
| -----: | :----------- | ---------: |
| 0 | - (start: `(0,0)` is rotten) | 6 |
| 1 | `(0,1)`, `(1,0)` | 4 |
| 2 | `(0,2)`, `(1,1)` | 2 |
| 3 | `(2,1)` | 1 |
| 4 | `(2,2)` | 0 |

### Three details that change the answer

1. **Rot spreads one step per minute.** An orange that turns rotten at minute 1 does not also rot its own neighbours at minute 1. In the picture, `(0,2)` sits next to `(0,1)`, which rots at minute 1 - but `(0,2)` waits until minute 2.
2. **Only 4 directions.** Diagonal neighbours do not count.
3. **Two different "nothing happens" outcomes.** No fresh oranges at the start means `0` minutes. A fresh orange that no rot can ever reach (walled off by empty cells) means `-1`.

### Constraints that matter

`1 <= m, n <= 10`. Small - which is why a slow simulation also passes on LeetCode. But the same problem on a `1000 x 1000` warehouse map is where the difference matters, and interviews ask for the version that scales.

=== pattern ===
**Multi-source BFS** - breadth-first search that starts from many cells at once.

### Why BFS at all

BFS explores a graph in **rings of equal distance**: first the start, then everything 1 step away, then everything 2 steps away. Rot spreading is exactly that: minute `k` rots the oranges that are `k` steps from the rot. So "how many minutes?" is "how many BFS rings until nothing fresh is left?"

### Why many sources

With one rotten orange, the minute at which a fresh orange rots is its distance from that orange. With several, it rots when the **nearest** rot reaches it - the minimum over all sources. You could BFS from each rotten orange separately and take minimums, but that repeats the whole search per source.

The trick: put **every** rotten orange into the queue before starting. They all form ring `0` together. BFS then expands all of them in lockstep, and each fresh orange is first reached by whichever source is nearest - automatically.

```text
  think of an invisible "super source" S, one step before every rotten orange:

              S
           /  |  \
         2    2    2      <- ring 0 (all rotten oranges)
        / \   |   / \
       1   1  1  1   1    <- ring 1
              ...
```

### Counting minutes with BFS levels

Process the queue **one level at a time**: read `size = queue.size()`, pop exactly that many, and push their fresh neighbours. Everything pushed during a level is the next minute's rot. One level = one minute.

### Recognising it

Reach for multi-source BFS when:

- something spreads, floods, infects, or propagates from **several starting points** at the same speed
- the question is "how long until everything is reached?" or "distance from each cell to the nearest X"
- moves are unweighted (every step costs the same)

The mental question:

> Is this "distance to the nearest of many sources"? Then all sources go in the queue at distance zero.

=== bruteForce ===
Simulate the clock directly. Each minute, look at the whole grid, find every fresh orange that touches a rotten one, rot them all, and advance the clock. Stop when a minute changes nothing.

### Step logic

1. Scan every cell. For each fresh cell, check its 4 neighbours; if any is rotten, add it to `toRot`.
2. If `toRot` is empty, stop.
3. Rot everything in `toRot` **after** the scan - not during it - and add one minute.
4. At the end, if any fresh orange remains, return `-1`; otherwise return the minutes.

Step 3's timing is the whole correctness question. Rotting `(0,1)` mid-scan would let `(0,2)`, scanned right after it, rot in the same minute - which detail 1 forbids.

### Dry run on the example

The fresh cells are scanned in row order. "Rotten neighbour?" looks at the grid as it was at the start of the minute.

| 1 | `(1,0)` | `(0,0)` | yes |
| 1 | `(1,1)` | none | no |
| 1 | `(2,1)` | none | no |
| 1 | `(2,2)` | none | no |
| 2 | `(0,2)` | `(0,1)` | yes |
| 2 | `(1,1)` | `(1,0)`, `(0,1)` | yes |
| 2 | `(2,1)` | none (`(1,1)` still fresh) | no |
| 2 | `(2,2)` | none | no |

Minute-level summary:

No fresh orange remains, so the answer is `4`.

### Java

```java
class Solution {
    public int orangesRotting(int[][] grid) {

        int m = grid.length, n = grid[0].length;
        int[][] dirs = { {1, 0}, {-1, 0}, {0, 1}, {0, -1} };
        int minutes = 0;

        while (true) {
            List<int[]> toRot = new ArrayList<>();

            for (int r = 0; r < m; r++) {
                for (int c = 0; c < n; c++) {
                    if (grid[r][c] != 1) continue;
                    for (int[] d : dirs) {
                        int nr = r + d[0], nc = c + d[1];
                        if (nr >= 0 && nr < m && nc >= 0 && nc < n && grid[nr][nc] == 2) {
                            toRot.add(new int[] { r, c });
                            break;
                        }
                    }
                }
            }

            if (toRot.isEmpty()) break;
            for (int[] cell : toRot) grid[cell[0]][cell[1]] = 2;   // apply after the scan
            minutes++;
        }

        for (int[] row : grid) {
            for (int v : row) {
                if (v == 1) return -1;
            }
        }
        return minutes;
    }
}
```

### Complexity

**Time:** `O((m * n)^2)` - **Space:** `O(m * n)` for `toRot`

Each minute scans all `m * n` cells. In the worst case - a long snake of fresh oranges with rot at one end - only one orange rots per minute, so there can be about `m * n` minutes.

### Where it hurts

Look at minute 4 in the table. To rot one orange, `(2,2)`, the scan visited all nine cells. Minute 3: nine cells to rot one. Across the run, 45 cell visits to rot six oranges.

Most of those visits are hopeless. A fresh orange can only rot this minute if a neighbour **rotted last minute** - an orange that has been rotten for a while has already rotted every neighbour it ever will. So the only cells worth looking at are the neighbours of the **newest** rot.

The brute force has no memory of which oranges are new. It rediscovers the frontier every minute by scanning everything.

> Keep the frontier. Each minute, expand only the oranges that rotted in the previous minute. That frontier is exactly a BFS queue level.

=== optimization ===
### The plan

1. One scan of the grid: push every rotten cell into the queue, count the fresh ones.
2. If `fresh == 0`, return `0` immediately.
3. While the queue is not empty **and** `fresh > 0`:
   - `size = queue.size()` - the oranges that rotted last minute
   - pop exactly `size` cells; for each fresh 4-neighbour: mark it rotten **now**, `fresh--`, push it
   - `minutes++`
4. Return `minutes` if `fresh == 0`, else `-1`.

### Dry run on the same example

Neighbours are tried in the order down, up, right, left. `q` lists cells front-first.

| minute | popped | neighbour checks | newly rotten | `fresh` after | `q` after level |
| -----: | :----- | :--------------- | :----------- | ------------: | :-------------- |
| start | - | initial scan | - | 6 | `[(0,0)]` |
| 1 | `(0,0)` | down `(1,0)` fresh, up out, right `(0,1)` fresh, left out | `(1,0)`, `(0,1)` | 4 | `[(1,0), (0,1)]` |
| 2 | `(1,0)` | down `(2,0)` empty, up `(0,0)` rotten, right `(1,1)` fresh, left out | `(1,1)` | 3 | - |
| 2 | `(0,1)` | down `(1,1)` rotten now, up out, right `(0,2)` fresh, left `(0,0)` rotten | `(0,2)` | 2 | `[(1,1), (0,2)]` |
| 3 | `(1,1)` | down `(2,1)` fresh, up `(0,1)` rotten, right `(1,2)` empty, left `(1,0)` rotten | `(2,1)` | 1 | - |
| 3 | `(0,2)` | down `(1,2)` empty, up out, right out, left `(0,1)` rotten | - | 1 | `[(2,1)]` |
| 4 | `(2,1)` | down out, up `(1,1)` rotten, right `(2,2)` fresh, left `(2,0)` empty | `(2,2)` | 0 | `[(2,2)]` |

After minute 4, `fresh == 0`, so the loop stops without popping `(2,2)`. Return `4`.

Count the work: six pops (one per orange that ever had a chance to spread), four neighbour checks each. Every cell is pushed at most once.

### Row 2's second line is the important one

When `(0,1)` looks down at `(1,1)`, it is already rotten - `(1,0)` marked it a moment earlier in the same level. Because the cell was set to `2` **at push time**, it is not pushed twice. If we only marked cells when popping them, `(1,1)` would enter the queue twice and `fresh` would be decremented twice, going wrong.

### Why the loop also checks `fresh > 0`

Without it, the loop would pop `(2,2)` in a fifth level, find nothing to rot, and still do `minutes++`, returning `5`. The last level of any BFS spreads nothing; the `fresh > 0` condition stops before that empty minute is counted.

### Multi-source in action

```text
grid = [[2, 1, 1, 1, 2]]
```

Both ends start in the queue together:

| minute | popped | newly rotten | `fresh` after |
| -----: | :----- | :----------- | ------------: |
| 1 | `(0,0)`, `(0,4)` | `(0,1)`, `(0,3)` | 1 |
| 2 | `(0,1)`, `(0,3)` | `(0,2)` | 0 |

Answer `2`. A BFS from only the first rotten orange would answer `3` (the farthest fresh orange, `(0,3)`, is three steps from `(0,0)`) - and would have to be repeated per source and merged to get it right.

=== complexity ===
### Time

The initial scan is `O(m * n)`. Every cell is pushed at most once (it is marked rotten when pushed, so it is never fresh again), and each pop checks 4 neighbours.

```text
O(m * n)
```

### Space

In the worst case the queue holds a large share of the grid - for example a grid that starts almost entirely rotten.

```text
O(m * n)
```

### Comparison

| Approach | Time | Space | Notes |
| :------- | ---: | ----: | :---- |
| Minute-by-minute full scan | `O((m * n)^2)` | `O(m * n)` | rescans the whole grid every minute |
| Separate BFS from each rotten orange | `O(k * m * n)` | `O(m * n)` | `k` = number of rotten oranges at the start |
| Multi-source BFS | **`O(m * n)`** | **`O(m * n)`** | one search, all sources in lockstep |

On a `1000 x 1000` grid the full-scan simulation can reach `10^12` steps; multi-source BFS does about `4 * 10^6`.

=== implementation ===
```java
class Solution {
    public int orangesRotting(int[][] grid) {

        int m = grid.length, n = grid[0].length;
        Deque<int[]> queue = new ArrayDeque<>();
        int fresh = 0;

        // Every rotten orange is a source at minute 0.
        for (int r = 0; r < m; r++) {
            for (int c = 0; c < n; c++) {
                if (grid[r][c] == 2) queue.offer(new int[] { r, c });
                else if (grid[r][c] == 1) fresh++;
            }
        }
        if (fresh == 0) return 0;

        int[][] dirs = { {1, 0}, {-1, 0}, {0, 1}, {0, -1} };
        int minutes = 0;

        while (!queue.isEmpty() && fresh > 0) {
            int size = queue.size();            // exactly the oranges that rotted last minute
            for (int i = 0; i < size; i++) {
                int[] cell = queue.poll();
                for (int[] d : dirs) {
                    int nr = cell[0] + d[0], nc = cell[1] + d[1];
                    if (nr < 0 || nr >= m || nc < 0 || nc >= n || grid[nr][nc] != 1) continue;
                    grid[nr][nc] = 2;           // rot it now, so nobody pushes it twice
                    fresh--;
                    queue.offer(new int[] { nr, nc });
                }
            }
            minutes++;
        }

        return fresh == 0 ? minutes : -1;
    }
}
```

### The lines that matter

**1.**

```java
if (grid[r][c] == 2) queue.offer(new int[] { r, c });
```

All sources enter before the BFS starts. This one line is what makes it multi-source.

**2.**

```java
int size = queue.size();            // exactly the oranges that rotted last minute
```

The level boundary. Reading the size **once** before the inner loop matters: the queue grows during the loop, and `i < queue.size()` would keep consuming next minute's oranges in this minute.

**3.**

```java
grid[nr][nc] = 2;           // rot it now, so nobody pushes it twice
fresh--;
```

Marking at push time is the BFS "visited" rule, and the grid itself is the visited array - no extra `boolean[][]`. `fresh` lets the final answer be one comparison instead of another full scan.

**4.**

```java
return fresh == 0 ? minutes : -1;
```

The queue can run dry while fresh oranges remain - they were never adjacent to any rot. That is the `-1` case.

### Java notes

- `int[] { r, c }` is the usual way to queue a coordinate pair. An alternative is encoding it as one int, `r * n + c`, and decoding with `/ n` and `% n` - fewer allocations, same complexity.
- The `dirs` array keeps the four neighbour checks in one loop instead of four copies of the bounds check.
- This version modifies `grid`. If the caller needs it intact, copy it first; LeetCode does not care.

=== edgeCases ===
### A fresh orange nothing can reach

```text
[[2, 1, 1],
 [0, 1, 1],
 [1, 0, 1]]   ->  -1
```

The bottom-left orange `(2,0)` has an empty cell above it and to its right. The queue empties with `fresh = 1`.

### No fresh oranges at all

```text
[[0, 2]]  ->  0
```

Returned by the early `fresh == 0` check, before any BFS.

### Only empty cells

```text
[[0]]  ->  0
```

Nothing fresh, so zero minutes - even though there is nothing rotten either.

### A fresh orange and no rot anywhere

```text
[[1]]  ->  -1
```

The queue starts empty, the loop never runs, `fresh = 1`.

### A single rotten orange

```text
[[2]]  ->  0
```

### One step

```text
[[2, 1]]  ->  1
```

The smallest case where the `fresh > 0` loop condition matters: without it the answer would come out as `2`.

### Two sources meeting in the middle

```text
[[2, 1, 1, 1, 2]]  ->  2
```

Both ends spread toward the centre at once. Spreading from the left source alone would take `3`.

### Diagonals do not count

```text
[[2, 0],
 [0, 1]]  ->  -1
```

`(1,1)` touches `(0,0)` only at a corner.

### Everything already rotten

```text
[[2, 2],
 [2, 2]]  ->  0
```

=== takeaway ===
> When you see **something spreading from several places at once, one step per tick**, and the question is **"how long until it reaches everything?"**, think **multi-source BFS**: every source in the queue at time zero, one level per tick.

### The core observation

A fresh orange can only rot this minute if a neighbour rotted last minute. So the only cells worth expanding are the newest rot - which is exactly one level of a BFS queue. Putting every initially rotten orange into the queue together makes all sources spread in lockstep, so each orange is reached first by its nearest source, with one search instead of one per source.

### The pattern trigger

```text
     grid, several sources, spreads 1 cell per tick
                     |
                     v
     scan once: queue all sources, count targets
                     |
                     v
     while queue not empty AND targets remain:
         size = queue.size()       <- one tick
         pop size cells, mark + push their neighbours
         ticks++
                     |
                     v
     targets left ?  -1  :  ticks
```

### The common mistakes

**Rotting during the scan in a simulation.** Lets rot travel several cells in one minute. Collect, then apply.

**Marking visited at pop time.** The same cell gets pushed by two neighbours in one level, and `fresh` is decremented twice.

**Counting the empty last level.** Returns one minute too many unless the loop also stops when `fresh` hits `0`.

**Forgetting the `0` case.** No fresh oranges at the start is `0`, not `-1`.

### What to remember in six months

> Nearest-of-many-sources distance = one BFS with every source at distance zero.

The same shape solves 01 Matrix (LC 542: distance from every cell to the nearest `0`), Walls and Gates (LC 286: distance to the nearest gate), As Far from Land as Possible (LC 1162), and Map of Highest Peak (LC 1765). Swap "rotten orange" for the source and "fresh" for the target; the loop does not change.
