=== intro ===
Day 23 used a hash map to remember running totals. Today strips hashing down to its simplest form - a set that only answers "is this number here?" - and shows that the hard part is not the lookup but deciding **where to start**.

> An `O(n)` bound with nested loops is not a contradiction. It just means the inner loop must be guaranteed to run only a few times in total, not per iteration. Learn to argue about total work, not loop depth.

=== problem ===
Given an **unsorted** array of integers, return the length of the longest run of consecutive integers that can be formed from its values. The run does not have to be contiguous in the array, and the algorithm must run in `O(n)` time.

```text
nums = [100, 4, 200, 1, 3, 2]
```

The values `1, 2, 3, 4` are all present, so they form a run of length 4. `100` and `200` are each a run of length 1 on their own.

```text
answer = 4
```

### What "consecutive" means here

| Values present | Runs | Longest |
| :------------- | :--- | ------: |
| `100, 4, 200, 1, 3, 2` | `{1,2,3,4}`, `{100}`, `{200}` | 4 |
| `0, 3, 7, 2, 5, 8, 4, 6, 0, 1` | `{0..8}` | 9 |
| `1, 2, 0, 1` | `{0,1,2}` | 3 |

Three things to notice:

1. **Position in the array is irrelevant.** `1` is at index 3 and `2` is at index 5. Only the *set of values* matters.
2. **Duplicates add nothing.** In the third row, the second `1` does not make the run longer. A run is a set of distinct integers.
3. **Consecutive means differ by exactly 1.** `1, 3, 5` is not a run, even though it is evenly spaced.

### The constraint that makes it a medium

```text
0 <= nums.length <= 10^5
-10^9 <= nums[i] <= 10^9
must run in O(n)
```

Without the `O(n)` requirement, this is an easy problem: sort and scan. The requirement forbids sorting, which costs `O(n log n)`. So we need to know whether `x + 1` exists **without** having the values in order.

=== pattern ===
**Hash Set** - membership lookup, plus a rule for where to start counting.

"Is `x + 1` in the input?" is the question a `HashSet` answers in `O(1)`. With that, from any value `x` we can walk upward - `x + 1`, `x + 2`, ... - until a value is missing, and the number of steps is the length of the run.

The problem is that walking from **every** value repeats work. Walking from `2` re-walks `3, 4` that walking from `1` already covered. The fix is one question asked before walking:

> Is `x - 1` in the set?

If it is, `x` is in the **middle** of a run that started somewhere lower, and some other value will count this run. Skip it. If it is not, `x` is the **start** of a run, and only then do we walk.

### The picture

```text
values present:   1   2   3   4         100         200
                  ^                      ^           ^
               start of run           start        start
             (0 not present)        (99 absent)  (199 absent)

walk from 1:  1 -> 2 -> 3 -> 4 -> (5 missing)   length 4
2, 3, 4:  each has its predecessor present -> skip, never walk
```

Every run is walked exactly once, from its smallest value.

### Recognising it

Reach for a hash set with a "start only at the beginning" rule when:

- the question is about values forming a **chain** (`x`, `x + 1`, `x + 2`, or more generally `x` and some `f(x)`)
- the order of elements in the input does not matter
- sorting would solve it but the bound says `O(n)`

The mental question:

> If I walk a chain from every element, how do I make sure I only walk each chain once?

The answer is almost always: only start from an element that has no predecessor.

=== bruteForce ===
Ignore the `O(n)` requirement for a moment. If the values were sorted, every run would sit in a contiguous block, and one left-to-right scan would find them all.

### Step logic

1. Copy and sort the array.
2. Walk it with a counter `current` (length of the run ending here) and `best`.
3. If `sorted[i] == sorted[i - 1]`, it is a duplicate - skip it without resetting.
4. If `sorted[i] == sorted[i - 1] + 1`, the run continues: `current++`.
5. Otherwise the run is broken: `current = 1`.
6. After each step, `best = max(best, current)`.

### Dry run

```text
nums   = [100, 4, 200, 1, 3, 2]
sorted = [1, 2, 3, 4, 100, 200]
```

| i | sorted[i] | sorted[i-1] | relation | current | best |
| -: | --------: | ----------: | :------- | ------: | ---: |
| 0 | 1 | - | first element | 1 | 1 |
| 1 | 2 | 1 | `+1`, continue | 2 | 2 |
| 2 | 3 | 2 | `+1`, continue | 3 | 3 |
| 3 | 4 | 3 | `+1`, continue | 4 | 4 |
| 4 | 100 | 4 | gap, reset | 1 | 4 |
| 5 | 200 | 100 | gap, reset | 1 | 4 |

`best = 4`. Correct.

With a duplicate, step 3 matters:

```text
sorted = [0, 1, 1, 2]
```

| i | sorted[i] | sorted[i-1] | relation | current | best |
| -: | --------: | ----------: | :------- | ------: | ---: |
| 0 | 0 | - | first element | 1 | 1 |
| 1 | 1 | 0 | `+1`, continue | 2 | 2 |
| 2 | 1 | 1 | duplicate, skip | 2 | 2 |
| 3 | 2 | 1 | `+1`, continue | 3 | 3 |

Without the duplicate rule, row 2 would reset `current` to 1 and the answer would come out as 2.

### Java

```java
class Solution {
    public int longestConsecutive(int[] nums) {

        if (nums.length == 0) {
            return 0;
        }

        int[] sorted = nums.clone();
        Arrays.sort(sorted);

        int best = 1;
        int current = 1;

        for (int i = 1; i < sorted.length; i++) {

            if (sorted[i] == sorted[i - 1]) {
                continue;                       // duplicate: neither extends nor breaks
            }

            if (sorted[i] == sorted[i - 1] + 1) {
                current++;
            } else {
                current = 1;
            }

            best = Math.max(best, current);
        }

        return best;
    }
}
```

### Complexity

**Time:** `O(n log n)` - **Space:** `O(n)` for the sorted copy (or `O(log n)` if you sort the input in place)

### Where it hurts

The scan is `O(n)`. All of the cost is the sort, and the sort is doing far more than we need.

Sorting establishes the **full order** of every value: that `4 < 100 < 200`, that `100` comes before `200`. We never use any of that. The only facts the scan ever consults are of the form "is `x + 1` present?". Sorting answers that as a side effect of answering a much harder question.

So the question becomes:

> Can I check "is `x + 1` present?" directly, without ordering anything?

A `HashSet` does exactly that in `O(1)`.

=== optimization ===
### First attempt - walk from every value

Put every value in a set. For each value `x`, walk `x + 1`, `x + 2`, ... while present, and track the longest walk.

That is correct, but count the lookups on `nums = [1, 2, 3, 4]`:

| start x | walk | lookups |
| ------: | :--- | ------: |
| 1 | 2, 3, 4, (5 missing) | 4 |
| 2 | 3, 4, (5 missing) | 3 |
| 3 | 4, (5 missing) | 2 |
| 4 | (5 missing) | 1 |

`4 + 3 + 2 + 1 = 10` lookups - `n(n + 1) / 2`. On an input like `[1, 2, 3, ..., 100000]` this is `O(n^2)`, worse than sorting. The walks from `2`, `3` and `4` re-walk a suffix of the walk from `1`.

### The key observation

Every walk that starts in the middle of a run is a strict sub-walk of the one that starts at the bottom. It can never find a longer run. So only walk from `x` when `x - 1` is **absent** - when `x` is the smallest value of its run.

### Step logic

1. Add every value to a `HashSet`. This also removes duplicates.
2. For each `x` in the **set**:
3. If `x - 1` is in the set, skip - `x` is not a run start.
4. Otherwise walk `x + 1`, `x + 2`, ... while present, counting `length`.
5. `best = max(best, length)`.

### Dry run - same example

```text
nums = [100, 4, 200, 1, 3, 2]
set  = {100, 4, 200, 1, 3, 2}
```

A `HashSet` iterates in its own internal order. The order does not affect the answer, so the table uses input order to make it easy to follow.

| x | x - 1 in set? | run start? | values walked | length | best |
| --: | :------------ | :--------- | :------------ | -----: | ---: |
| 100 | 99: no | **yes** | 101 missing | 1 | 1 |
| 4 | 3: yes | no, skip | - | - | 1 |
| 200 | 199: no | **yes** | 201 missing | 1 | 1 |
| 1 | 0: no | **yes** | 2, 3, 4, then 5 missing | 4 | **4** |
| 3 | 2: yes | no, skip | - | - | 4 |
| 2 | 1: yes | no, skip | - | - | 4 |

`best = 4`.

### Counting the work

Total `contains` calls:

- one `x - 1` check per value: 6
- walk steps: `100 -> 101` (1), `200 -> 201` (1), `1 -> 2, 3, 4, 5` (4): 6 in total

12 lookups for 6 values. Every value is reached by **at most one** walk - the one from the start of its run - so the walk steps across the whole loop add up to at most `n` plus one miss per run. The nested `while` does not make this `O(n^2)`; it makes it `O(2n)`.

That is the argument to give in an interview. "There is a loop inside a loop, but each element is visited by the inner loop at most once in total."

=== complexity ===
### Time

Building the set: `n` insertions. The main loop: one predecessor check per distinct value, plus walk steps that total at most `n` plus one failed check per run.

```text
O(n) on average
```

"On average" because `HashSet` operations are `O(1)` expected, not worst-case.

### Space

The set holds every distinct value.

```text
O(n)
```

### Why

The sort spent `O(n log n)` establishing an order we never used. The set answers only the question the scan actually asks, and the run-start rule guarantees that question is asked a linear number of times.

### Comparison

| Approach | Time | Space | Notes |
| :------- | ---: | ----: | :---- |
| For each x, linear-search for x+1, x+2, ... | `O(n^3)` | `O(1)` | no extra structure at all |
| Sort, then scan | `O(n log n)` | `O(n)` or `O(log n)` | simplest correct answer |
| Set, walk from every value | `O(n^2)` worst | `O(n)` | correct, but the set alone does not help |
| Set, walk only from run starts | **`O(n)`** | `O(n)` | the intended answer |

The third row is the important one to say out loud. A set is not enough on its own - the `x - 1` check is what makes the bound linear.

=== implementation ===
```java
class Solution {
    public int longestConsecutive(int[] nums) {

        Set<Integer> set = new HashSet<>();
        for (int num : nums) {
            set.add(num);
        }

        int best = 0;

        for (int x : set) {

            if (set.contains(x - 1)) {
                continue;               // x is inside a run, not its start
            }

            int length = 1;
            int next = x + 1;
            while (set.contains(next)) {
                length++;
                next++;
            }

            best = Math.max(best, length);
        }

        return best;
    }
}
```

### The lines that matter

**1.**

```java
if (set.contains(x - 1)) {
    continue;               // x is inside a run, not its start
}
```

This is the whole optimisation. Delete it and the code still returns correct answers - it just becomes `O(n^2)` on a long run. That is what makes it easy to forget and hard to notice.

**2.**

```java
for (int x : set) {
```

Iterate the **set**, not `nums`. With `nums = [1, 1, 1, ..., 1, 2, 3, ..., 50000]`, iterating the array would treat every copy of `1` as a run start and re-walk the whole run each time. The set has one `1`.

**3.**

```java
int best = 0;
```

`0`, not `1`. An empty array has no run at all; the loop body never executes and `0` is returned without a special case.

### Java notes

- `Set<Integer>` boxes each `int`. For `10^5` values that is fine. Calls like `set.contains(x - 1)` auto-box the argument; no cast is needed.
- `x - 1` and `x + 1` can overflow `int` at `Integer.MIN_VALUE` and `Integer.MAX_VALUE`. LeetCode limits values to `+-10^9`, so it cannot happen here. Outside that guarantee, see the last edge case.
- `HashSet` iteration order is unspecified. The algorithm does not depend on it, which is worth noting if an interviewer asks why the table above looks "out of order".

=== edgeCases ===
### Empty array

```text
[]  ->  0
```

The loop has nothing to iterate. `best` stays `0`.

### Single element

```text
[7]  ->  1
```

### All duplicates

```text
[5, 5, 5]  ->  1
```

The set is `{5}`. One run start, length 1.

### Duplicates inside a run

```text
[1, 2, 0, 1]  ->  3
```

The set is `{0, 1, 2}`. The duplicate `1` disappears on insertion, which is why the set version needs no duplicate rule while the sorted version does.

### No two values consecutive

```text
[10, 30, 20]  ->  1
```

Every value is a run start, every walk stops after one miss.

### Negative values

```text
[-1, -2, 0, 2]  ->  3
```

The run is `-2, -1, 0`. Nothing assumes positives; `-2 - 1 = -3` is simply absent.

### The LeetCode long example

```text
[0, 3, 7, 2, 5, 8, 4, 6, 0, 1]  ->  9
```

Only `0` is a run start (`-1` is absent). One walk covers `0` through `8`.

### Many duplicates of the run start

```text
[1, 1, 1, 1, 2, 3]  ->  3
```

Correct either way, but this is the input shape that turns "iterate `nums`" into `O(n^2)`: each copy of `1` would walk `2, 3` again.

### Integer overflow at the extremes

```text
[Integer.MIN_VALUE, Integer.MAX_VALUE]  ->  this code returns 2, the true answer is 1
```

Two wraps conspire. `Integer.MIN_VALUE - 1` wraps to `Integer.MAX_VALUE`, which is in the set, so `MIN_VALUE` is wrongly treated as "not a run start" and skipped. Then `Integer.MAX_VALUE + 1` wraps to `Integer.MIN_VALUE`, which is in the set, so the walk from `MAX_VALUE` "continues" into it. LeetCode's `+-10^9` bound rules this out. If you ever lift the bound, store the values in a `Set<Long>` and do the `x - 1` / `x + 1` arithmetic in `long`.

=== takeaway ===
> When you see **"longest chain of values, in `O(n)`, input unsorted"**, think **hash set + start only where the predecessor is missing**.

### The core observation

Sorting answers "what is the full order?" when we only ever ask "is `x + 1` present?". A hash set answers the second question directly. And because a walk from the middle of a run is a sub-walk of the walk from its start, walking only from starts makes the total inner-loop work linear.

### The pattern trigger

```text
       values form chains (x, x+1, x+2, ...)
                       |
                       v
          put every value in a HashSet
                       |
                       v
          for x in SET:  is x-1 present?
                 /                \
               yes                 no
                |                   |
              skip            walk x+1, x+2, ...
                                    |
                                    v
                       each value walked at most once
                            -> O(n) total
```

### The common mistakes

**Dropping the `x - 1` check.** Still correct, now quadratic. A test suite with one long run catches it as a timeout.

**Iterating the array instead of the set.** Duplicated run starts repeat the walk.

**Forgetting duplicates in the sorted version.** Resetting the counter on an equal value splits one run into two.

**Saying "nested loops, so `O(n^2)`".** The right analysis counts total inner iterations across the whole run, not per outer iteration.

### What to remember in six months

> Nested loops can still be `O(n)`. Count how many times each element is touched in total - if it is a constant, the algorithm is linear.

The same "only start at the beginning" rule shows up again in graph problems (only start a traversal from an unvisited node), and the Union-Find follow-up solves this problem by unioning `x` with `x + 1` and returning the largest component size.
