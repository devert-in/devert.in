=== intro ===
Week 6 starts, and with it a new data structure. The linked-list week was about rewiring pointers; this week is about **what to remember, and in what order to forget it**.

> When the thing you need to deal with next is always the most recent thing you have not dealt with yet, you are looking at a stack.

=== problem ===
Given a string `s` made only of the characters `( ) [ ] { }`, return `true` if every bracket is closed correctly.

"Correctly" means three things at once:

1. Every opener is closed by a closer of the **same type**.
2. Brackets close in the **right order** - the most recently opened one must close first.
3. Every closer has a matching opener **before** it.

```text
s = "([]{})"   ->  true
s = "([)]"     ->  false
```

### Reading the two examples

```text
( [ ] { } )
| |_| |_| |
|_________|      every pair is properly nested
```

```text
( [ ) ]
| |_|_|          ")" tries to close "(" while "[" is still open
|___|            the pairs cross - not allowed
```

`"([)]"` has the right **counts** - one of each opener, one of each closer, all matched by type. It is still invalid, because of order. That single example rules out every solution that only counts.

### What the constraints tell you

- `1 <= s.length <= 10^4`.
- `s` contains only the six bracket characters - no letters, no spaces.
- An odd-length string can never be valid: every valid string is made of pairs.

=== pattern ===
**Stack.**

Read the string left to right. When you see a closer, which opener must it match? Not the first one, not any one - **the most recent opener that has not been closed yet**. In `"([]{})"`, the `]` at index 2 must match the `[` at index 1, because that is the innermost open bracket at that moment.

"Most recent unfinished thing" is the definition of the top of a stack:

- an opener is something we have started and not finished: **push** it
- a closer finishes the most recent unfinished thing: it must match the **top**, then **pop** it
- at the end, nothing may be left unfinished: the stack must be **empty**

### The picture

```text
s = ( [ ] { } )

read (   stack: (          opened
read [   stack: ( [        opened, nested inside (
read ]   stack: (          closes [ - the top
read {   stack: ( {
read }   stack: (          closes { - the top
read )   stack:            closes ( - the top
end      stack empty  ->  valid
```

### Recognising it

Reach for a stack when:

- items must be **matched**, and the match for the newest item comes first (brackets, HTML tags, nested function calls)
- you are **undoing** in reverse order (backspace strings, simplifying paths, undo history)
- the input is **nested** and you need to know what encloses the current position

The mental question:

> When I meet the next "closing" event, is it always about the most recent "opening" event I have not resolved? If yes, push openings and pop on closings.

=== bruteForce ===
Forget data structures. What can you see by just looking at the string?

A valid string always has at least one **adjacent** matching pair - `()`, `[]` or `{}` - somewhere inside it: the innermost pair. Remove it, and what is left must still be valid. So keep deleting adjacent pairs until nothing changes. If the string empties, it was valid.

### Step logic

1. Replace every `"()"`, then every `"[]"`, then every `"{}"` with `""`.
2. If the string got shorter, repeat from step 1.
3. If nothing changed, stop. Valid exactly when the string is now empty.

### Dry run

```text
s = "([]{})"
```

| pass | before | after removing `()` | after removing `[]` | after removing `{}` | length | changed? |
| ---: | :----- | :------------------ | :------------------ | :------------------ | -----: | :------- |
| 1 | `([]{})` | `([]{})` | `({})` | `()` | 6 -> 2 | yes |
| 2 | `()` | (empty) | (empty) | (empty) | 2 -> 0 | yes |
| 3 | (empty) | (empty) | (empty) | (empty) | 0 -> 0 | no, stop |

The string is empty: `true`.

Notice pass 1: there was no `()` to remove at first. The `(` and `)` only became adjacent **after** the inner pairs were deleted. That is why one pass is not enough.

And the invalid example:

```text
s = "([)]"
```

| pass | before | after `()` | after `[]` | after `{}` | length | changed? |
| ---: | :----- | :--------- | :--------- | :--------- | -----: | :------- |
| 1 | `([)]` | `([)]` | `([)]` | `([)]` | 4 -> 4 | no, stop |

No adjacent matching pair anywhere. Not empty: `false`. Correct - the crossing pairs never become adjacent.

### Java

```java
class Solution {
    public boolean isValid(String s) {

        while (true) {
            String next = s.replace("()", "")
                           .replace("[]", "")
                           .replace("{}", "");

            if (next.length() == s.length()) {
                break;          // nothing removable left
            }
            s = next;
        }

        return s.isEmpty();
    }
}
```

### Complexity

**Time:** `O(n^2)` - **Space:** `O(n)`

### Where it hurts

Each pass scans the whole string and builds new strings: `O(n)`. How many passes? Try the worst input, deep nesting:

```text
"(((())))"
pass 1:  "((()))"      only the innermost "()" is adjacent
pass 2:  "(())"
pass 3:  "()"
pass 4:  ""
pass 5:  no change
```

Each pass removes only **one** pair, so `n/2` passes of `O(n)` work each: `O(n^2)`. With `10^4` characters, that is tens of millions of character copies.

Now look at **where** the new pair appears after each removal. In pass 1 above, deleting the innermost `()` makes the `(` just before it adjacent to the `)` just after it. The next match always forms **right at the spot we just removed**, between the opener immediately to its left and the next character.

So every pass rescans the whole string to find a pair whose location we already knew.

> The brute force forgets everything between passes. What it should remember is "the openers to the left of where I am, that are still waiting" - and only the last of them is ever the next candidate.

=== optimization ===
Keep the waiting openers in a stack as you read left to right. The top of the stack is "the opener immediately to the left" from the brute force - the only one a closer could legally match.

### The key observation

At any point in a left-to-right scan, the unmatched openers so far form a list, and **only the last one can be closed next**. Closing anything earlier would make pairs cross, like `"([)]"`. A list where you only ever touch the last element is a stack.

### Step by step

1. If the length is odd, return `false` immediately.
2. For each character `c`:
   - opener: push it
   - closer: if the stack is empty, there is nothing to close - return `false`. Otherwise pop the top; if it is not the matching opener, return `false`.
3. After the loop, return `true` only if the stack is empty (no opener left unclosed).

### Dry run - same string

```text
s = "([]{})"     stack shown bottom -> top
```

| i | c | kind | stack before | check | stack after |
| -: | :- | :--- | :----------- | :---- | :---------- |
| 0 | `(` | opener | `[]` | - | `[ ( ]` |
| 1 | `[` | opener | `[ ( ]` | - | `[ (, [ ]` |
| 2 | `]` | closer | `[ (, [ ]` | top `[` matches `]` - pop | `[ ( ]` |
| 3 | `{` | opener | `[ ( ]` | - | `[ (, { ]` |
| 4 | `}` | closer | `[ (, { ]` | top `{` matches `}` - pop | `[ ( ]` |
| 5 | `)` | closer | `[ ( ]` | top `(` matches `)` - pop | `[]` |
| end | - | - | `[]` | stack empty | return `true` |

Six characters, six constant-time steps. Row 5 is the moment the brute force needed a whole second pass to discover: after `{}` closed, `(` was back on top, ready to meet `)`.

### Dry run - the crossing example

```text
s = "([)]"
```

| i | c | kind | stack before | check | result |
| -: | :- | :--- | :----------- | :---- | :----- |
| 0 | `(` | opener | `[]` | - | `[ ( ]` |
| 1 | `[` | opener | `[ ( ]` | - | `[ (, [ ]` |
| 2 | `)` | closer | `[ (, [ ]` | top is `[`, but `)` needs `(` | return `false` |

The stack catches the crossing at the first closer that tries to skip over an open bracket. Index 3 is never read.

### The three ways to fail

Each `return false` in the algorithm corresponds to one of the three rules in the problem:

| failure | example | where it is caught |
| :------ | :------ | :----------------- |
| wrong type or wrong order | `"(]"`, `"([)]"` | top does not match the closer |
| closer with nothing open | `")("`, `"]"` | stack empty when a closer arrives |
| opener never closed | `"(("`, `"(()"` | stack not empty at the end |

Forget any one of the three checks and some input slips through.

=== complexity ===
### Time

One pass. Each character is pushed at most once and popped at most once, both `O(1)`.

```text
O(n)
```

### Space

In the worst case every character is an opener - `"(((((("` has even length, passes the early check, and pushes all six before the final `isEmpty()` rejects it.

```text
O(n)
```

### Comparison

| Approach | Time | Space | Notes |
| :------- | ---: | ----: | :---- |
| Repeatedly delete adjacent pairs | `O(n^2)` | `O(n)` | simple, slow on deep nesting |
| Counter per bracket type | `O(n)` | `O(1)` | **wrong** - accepts `"([)]"` |
| Stack | **`O(n)`** | **`O(n)`** | correct and optimal |

### Why a counter is not enough (but almost is)

With **one** bracket type, a single integer works: `+1` on `(`, `-1` on `)`, fail if it ever goes negative, and it must end at `0`. The counter is a stack that only ever holds `(`, so storing the count is enough.

With three types, the stack must remember **which** type is on top, and a count cannot. That is why this problem needs `O(n)` space and its one-type cousin does not.

=== implementation ===
```java
class Solution {
    public boolean isValid(String s) {

        // Every valid string is made of pairs.
        if (s.length() % 2 == 1) {
            return false;
        }

        Deque<Character> stack = new ArrayDeque<>();

        for (char c : s.toCharArray()) {

            if (c == '(' || c == '[' || c == '{') {
                stack.push(c);              // opened, waiting to be closed
            } else {
                if (stack.isEmpty()) {
                    return false;           // closer with nothing open
                }
                char open = stack.pop();
                if ((c == ')' && open != '(')
                        || (c == ']' && open != '[')
                        || (c == '}' && open != '{')) {
                    return false;           // wrong type, or pairs cross
                }
            }
        }

        // Anything still on the stack was opened and never closed.
        return stack.isEmpty();
    }
}
```

### The lines that matter

**1.**

```java
if (stack.isEmpty()) {
    return false;           // closer with nothing open
}
```

This check must come **before** `pop()`. `ArrayDeque.pop()` on an empty deque throws `NoSuchElementException`, so skipping it does not return `false` - it crashes on input like `"]"`.

**2.**

```java
char open = stack.pop();
```

Pop first, then compare. Whether it matches or not, this opener is resolved for this character: if it matches, it is closed; if not, we return `false` on the next line anyway.

**3.**

```java
return stack.isEmpty();
```

Not `return true`. `"(("` has even length, never fails a match, and leaves two openers on the stack. Returning `true` here is the most common bug in this problem.

### The "push the expected closer" variant

Instead of pushing the opener and translating later, push the closer you will need:

```java
class Solution {
    public boolean isValid(String s) {

        Deque<Character> stack = new ArrayDeque<>();

        for (char c : s.toCharArray()) {
            if (c == '(') {
                stack.push(')');
            } else if (c == '[') {
                stack.push(']');
            } else if (c == '{') {
                stack.push('}');
            } else if (stack.isEmpty() || stack.pop() != c) {
                return false;
            }
        }

        return stack.isEmpty();
    }
}
```

The match test collapses to `stack.pop() != c`. Same algorithm, same complexity, fewer places to get a pair wrong. Note the `||` short-circuit: `pop()` only runs when the stack is not empty.

### Java notes

- Use `ArrayDeque` as the stack, not `java.util.Stack`. `Stack` extends `Vector`, so every call is synchronized for no benefit. `ArrayDeque`'s `push`, `pop` and `peek` work on the head of the deque, which is exactly stack behaviour.
- `Deque<Character>` stores boxed `Character` objects. `char open = stack.pop()` unboxes; in the variant, `stack.pop() != c` compares a `Character` with a `char`, which also unboxes, so it compares values, not references.
- `s.toCharArray()` copies the string (`O(n)` space). `for (int i = 0; i < s.length(); i++) { char c = s.charAt(i); ... }` avoids the copy; the stack already makes space `O(n)`, so it does not change the complexity.

=== edgeCases ===
### Odd length

```text
"("     ->  false
"(()"   ->  false
```

Rejected before the loop starts. A string of pairs always has even length.

### Closer first

```text
")("  ->  false
"]"   ->  false
```

`")("` has even length and one of each bracket, so it passes the length check. The first character is a closer and the stack is empty - `false`. `"]"` is caught by the odd-length check before that.

### Only openers

```text
"(("    ->  false
"([{{"  ->  false
```

Even length, no mismatches, nothing ever closes. Only the final `stack.isEmpty()` check catches it.

### Wrong type

```text
"(]"  ->  false
```

### Crossing pairs

```text
"([)]"  ->  false
```

Right counts, right types, wrong order. Caught at index 2.

### Deep nesting

```text
"{[()]}"     ->  true
"((((()))))" ->  true
```

The brute force's worst case is the stack's ordinary case: push five, pop five.

### Side by side

```text
"()[]{}"  ->  true
```

The stack empties between groups; that is fine, it just has to be empty at the very end.

### Single pair

```text
"()"  ->  true
```

### Empty string

```text
""  ->  true
```

LeetCode guarantees at least one character, but the code is correct anyway: length `0` is even, the loop does not run, the stack is empty.

=== takeaway ===
> When you see **matching pairs that must nest** - brackets, tags, begin/end markers - think **stack**: push the opener, and every closer must match the top.

### The core observation

At any moment, only the **most recently opened, still-open** bracket can be closed next. Closing anything older would make pairs cross. Keeping open brackets in a stack puts that one bracket on top, so each closer is checked in `O(1)` instead of being found by rescanning the string.

### The pattern trigger

```text
         read left to right
                |
       opener?--+--closer?
          |          |
        push      stack empty?  -- yes -->  false
                     |
                     no
                     |
                pop; matches?   -- no  -->  false
                     |
                    yes, continue
                |
         end: stack empty?  -->  that is the answer
```

### The common mistakes

**Returning `true` at the end instead of `stack.isEmpty()`.** Lets `"(("` through.

**Popping without checking for empty.** Crashes on `")"` instead of returning `false`.

**Counting instead of stacking.** Counts are correct for one bracket type and wrong for three - `"([)]"` has perfect counts.

**Using `java.util.Stack`.** Works, but it is a legacy synchronized class. `ArrayDeque` is the modern answer and interviewers notice.

> A stack answers one question in `O(1)`: "what is the most recent thing I have not finished yet?"
