=== intro ===
Days 44 to 46 all had one thing in common: the whole search space was sorted, so one comparison at `mid` told you which side to keep. Today the array is **broken in one place** - sorted, then rotated - and the whole-array ordering is gone.

> You do not need the whole array to be sorted. You need to know, at every `mid`, **which half is sorted** - because a sorted half is the one place where "is the target in here?" can be answered with two comparisons. Check that half; if the target is not in it, it is in the other.

=== problem ===
An array of **distinct** integers was sorted ascending and then **rotated** at an unknown pivot: some prefix was cut off and moved to the end. Given the rotated array and a `target`, return the index of `target`, or `-1`. The required time is `O(log n)`.

```text
original sorted : [0, 1, 2, 4, 5, 6, 7]
rotated         : [4, 5, 6, 7, 0, 1, 2]     ([0, 1, 2] moved to the back)

target = 0  ->  4
target = 3  ->  -1
```

| index | 0 | 1 | 2 | 3 | 4 | 5 | 6 |
| :---- | -: | -: | -: | -: | -: | -: | -: |
| value | 4 | 5 | 6 | 7 | **0** | 1 | 2 |

The array is two sorted runs glued together: `[4, 5, 6, 7]` and `[0, 1, 2]`. The "drop" between `7` and `0` is the only place where order breaks.

### The constraints that matter

- `1 <= nums.length <= 5000`, values in `[-10^4, 10^4]`.
- All values are **distinct**. This is what makes the core comparison `nums[lo] <= nums[mid]` trustworthy. With duplicates it can lie - that is LC 81, discussed at the end.
- The array may be rotated by `0` positions - i.e. **not rotated at all**. The solution must not assume a drop exists.
- **`O(log n)`** - a scan is correct but is not the answer.

### Why day 44's search fails here

Run plain binary search for `0`:

```text
lo = 0, hi = 6, mid = 3, nums[3] = 7 > 0  ->  hi = 2   (discard the right half)
```

But `0` is in the right half. Plain binary search assumes "`7 > 0`, so everything right of `7` is bigger too", and the rotation makes that false. Every later step searches `[4, 5, 6]` and returns `-1`. The fix is not to give up on halving; it is to decide which half to discard with a test the rotation cannot fool.

=== pattern ===
**Binary Search on the sorted half.**

Cut a rotated array anywhere and look at the two pieces `[lo..mid]` and `[mid..hi]`. The drop is in at most one of them, so **at least one piece is fully sorted**:

```text
[4, 5, 6, 7, 0, 1, 2]
 lo       mid      hi

[lo..mid] = [4, 5, 6, 7]   sorted  (nums[lo] = 4 <= nums[mid] = 7)
[mid..hi] = [7, 0, 1, 2]   contains the drop
```

How to tell which one, with one comparison:

- `nums[lo] <= nums[mid]` -> no drop between `lo` and `mid` -> **left half sorted**.
- otherwise -> the drop is between `lo` and `mid` -> **right half sorted**.

And for a sorted piece, membership is a range check: the target is in `[4, 5, 6, 7]` exactly when `4 <= target <= 7` (we use `< nums[mid]` since `mid` itself was already checked). If it is in the sorted half, search there. If not, it can only be in the other half - whether or not that half is sorted.

### Recognising it

Reach for this when:

- the input is "sorted, then rotated" or "sorted except for one break"
- the problem asks for `O(log n)` on an array that is not globally sorted
- some local test at `mid` (here "is the left half sorted?") still tells you which side to throw away

The mental question - the same one as day 44, asked more carefully:

> At `mid`, is there **some** half I can fully reason about? If the target provably is not in it, discard it; if it provably is, discard the other.

Binary search only ever needed a reliable way to discard half. Sortedness of the whole array was one way to get it; sortedness of one half is another.

=== bruteForce ===
Ignore the structure entirely and scan.

### Step logic

1. For `i` from `0` to `n - 1`: if `nums[i] == target`, return `i`.
2. If nothing matched, return `-1`.

### Dry run - target present

```text
nums = [4, 5, 6, 7, 0, 1, 2], target = 0
```

| step | i | nums[i] | nums[i] == 0? | action | comparisons so far |
| ---: | -: | ------: | :------------ | :----- | -----------------: |
| 1 | 0 | 4 | no | next | 1 |
| 2 | 1 | 5 | no | next | 2 |
| 3 | 2 | 6 | no | next | 3 |
| 4 | 3 | 7 | no | next | 4 |
| 5 | 4 | 0 | **yes** | return `4` | 5 |

### Dry run - target absent

```text
nums = [4, 5, 6, 7, 0, 1, 2], target = 3
```

| step | i | nums[i] | nums[i] == 3? | action | comparisons so far |
| ---: | -: | ------: | :------------ | :----- | -----------------: |
| 1 | 0 | 4 | no | next | 1 |
| 2 | 1 | 5 | no | next | 2 |
| 3 | 2 | 6 | no | next | 3 |
| 4 | 3 | 7 | no | next | 4 |
| 5 | 4 | 0 | no | next | 5 |
| 6 | 5 | 1 | no | next | 6 |
| 7 | 6 | 2 | no | next | 7 |
| - | - | - | - | loop ends, return `-1` | 7 |

### Java

```java
class Solution {
    public int search(int[] nums, int target) {

        for (int i = 0; i < nums.length; i++) {
            if (nums[i] == target) {
                return i;
            }
        }

        return -1;
    }
}
```

### Complexity

**Time:** `O(n)` - **Space:** `O(1)`

### Where it hurts

Rows 1 to 4 of the second table check `4, 5, 6, 7` one by one. But those four values are a **sorted run**: knowing `nums[0] = 4` and `nums[3] = 7`, the target `3` is below the run's smallest value, so none of the four can match. Two comparisons settle four elements; the scan spent four.

The same holds for `[0, 1, 2]`: `3 > 2`, the run's largest value, so none of those three can match either.

```text
run          range        target 3 inside?   elements the scan checked anyway
[4, 5, 6, 7]  4..7         no                 4
[0, 1, 2]     0..2         no                 3
```

The array is not unstructured - it is two sorted runs. The scan treats it as noise. The question is how to find a sorted run without first scanning for the drop. Answer: you do not need to find it. Whatever `mid` you pick, one side of it is already a sorted run.

=== optimization ===
### The key observation

Split `[lo..hi]` at `mid`. The single drop in the array lies in at most one of `[lo..mid]` and `[mid..hi]`, so the other is sorted. `nums[lo] <= nums[mid]` identifies which. In the sorted half, "could the target be here?" is a range test on its two endpoints. That is enough to discard a half every step.

### Deriving it step by step

1. `lo = 0`, `hi = n - 1`.
2. While `lo <= hi`: `mid = lo + (hi - lo) / 2`. If `nums[mid] == target`, return `mid`.
3. If `nums[lo] <= nums[mid]` (**left half sorted**):
   - if `nums[lo] <= target < nums[mid]`, the target can only be on the left: `hi = mid - 1`;
   - otherwise it can only be on the right: `lo = mid + 1`.
4. Else (**right half sorted**):
   - if `nums[mid] < target <= nums[hi]`, it can only be on the right: `lo = mid + 1`;
   - otherwise: `hi = mid - 1`.
5. Window empty: return `-1`.

### Dry run - target present

```text
nums = [4, 5, 6, 7, 0, 1, 2], target = 0
```

| step | lo | hi | mid | nums[lo] | nums[mid] | nums[hi] | sorted half | target in it? | action |
| ---: | -: | -: | --: | -------: | --------: | -------: | :---------- | :------------ | :----- |
| 1 | 0 | 6 | 3 | 4 | 7 | 2 | left `[4..7]` | `4 <= 0`? no | `lo = 4` |
| 2 | 4 | 6 | 5 | 0 | 1 | 2 | left `[0..1]` | `0 <= 0 < 1`? yes | `hi = 4` |
| 3 | 4 | 4 | 4 | 0 | 0 | 0 | - | - | `nums[4] == 0`, return **4** |

Step 1 is exactly where plain binary search went wrong. It saw `7 > 0` and went left. Here, the left half `[4, 5, 6, 7]` is recognised as sorted, `0` is outside its range `4..7`, so the left half is discarded instead.

### Dry run - target absent

```text
nums = [4, 5, 6, 7, 0, 1, 2], target = 3
```

| step | lo | hi | mid | nums[lo] | nums[mid] | nums[hi] | sorted half | target in it? | action |
| ---: | -: | -: | --: | -------: | --------: | -------: | :---------- | :------------ | :----- |
| 1 | 0 | 6 | 3 | 4 | 7 | 2 | left `[4..7]` | `4 <= 3`? no | `lo = 4` |
| 2 | 4 | 6 | 5 | 0 | 1 | 2 | left `[0..1]` | `3 < 1`? no | `lo = 6` |
| 3 | 6 | 6 | 6 | 2 | 2 | 2 | left `[2]` | `3 < 2`? no | `lo = 7` |
| - | 7 | 6 | - | - | - | - | - | `lo > hi` | return **-1** |

Three steps against the scan's seven. Step 1 is the table from "Where it hurts" in action: two comparisons (`4 <= 3`, implicitly against `7`) dispose of the whole run `[4, 5, 6, 7]`.

### Dry run - when the RIGHT half is the sorted one

The example above only exercised the left branch. A different rotation:

```text
nums = [6, 7, 0, 1, 2, 4, 5], target = 5
```

| step | lo | hi | mid | nums[lo] | nums[mid] | nums[hi] | sorted half | target in it? | action |
| ---: | -: | -: | --: | -------: | --------: | -------: | :---------- | :------------ | :----- |
| 1 | 0 | 6 | 3 | 6 | 1 | 5 | right `[1..5]` (`6 <= 1` false) | `1 < 5 <= 5`? yes | `lo = 4` |
| 2 | 4 | 6 | 5 | 2 | 4 | 5 | left `[2..4]` | `5 < 4`? no | `lo = 6` |
| 3 | 6 | 6 | 6 | 5 | 5 | 5 | - | - | `nums[6] == 5`, return **6** |

Step 1: `nums[lo] = 6 > nums[mid] = 1`, so the drop is on the left and `[1, 2, 4, 5]` is the sorted half. `5` is inside its range, so search there.

### Why `<=` in `nums[lo] <= nums[mid]`

When the window has two elements, `mid` rounds down to `lo`, and `nums[lo] == nums[mid]` because they are the same element. A one-element half `[lo..mid]` is sorted, so the test must say "left sorted" - hence `<=`.

```text
nums = [3, 1], target = 1
lo = 0, hi = 1, mid = 0, nums[mid] = 3 != 1

with <= : 3 <= 3, left [3] sorted, 1 not in 3..3  ->  lo = 1  ->  finds 1 at index 1
with <  : 3 <  3 false, "right [3, 1] sorted" (it is not), 3 < 1 false  ->  hi = -1  ->  returns -1
```

With `<`, the code concludes the right half `[3, 1]` is sorted - it is not - and throws away the target.

=== complexity ===
### Time

Each iteration does a constant number of comparisons and discards half the window.

```text
O(log n)
```

### Space

`lo`, `hi`, `mid`.

```text
O(1)
```

### Comparison

| Approach | Time | Space | Passes |
| :------- | ---: | ----: | -----: |
| Linear scan | `O(n)` | `O(1)` | 1 |
| Find the pivot (min index), then binary search the right run | `O(log n)` | `O(1)` | 2 |
| Sorted-half binary search | **`O(log n)`** | **`O(1)`** | **1** |

The two-pass version is a perfectly good answer and easier to get right under pressure: find the minimum's index with LC 153's search (shown below), then run day 44's search on whichever run could contain the target. The one-pass version is the one interviewers usually expect, because it shows you understood *why* binary search works rather than reducing the problem back to it.

=== implementation ===
```java
class Solution {
    public int search(int[] nums, int target) {

        int lo = 0;
        int hi = nums.length - 1;

        while (lo <= hi) {
            int mid = lo + (hi - lo) / 2;

            if (nums[mid] == target) {
                return mid;
            }

            if (nums[lo] <= nums[mid]) {
                // Left half [lo..mid] is sorted.
                if (nums[lo] <= target && target < nums[mid]) {
                    hi = mid - 1;               // target is inside the sorted left
                } else {
                    lo = mid + 1;               // so it can only be on the right
                }
            } else {
                // Right half [mid..hi] is sorted.
                if (nums[mid] < target && target <= nums[hi]) {
                    lo = mid + 1;               // target is inside the sorted right
                } else {
                    hi = mid - 1;               // so it can only be on the left
                }
            }
        }

        return -1;
    }
}
```

### The lines that matter

**1.**

```java
if (nums[lo] <= nums[mid]) {
```

The one comparison that tells you where the drop is not. `<=` covers the case `lo == mid`, where the left half is a single element and therefore sorted.

**2.**

```java
if (nums[lo] <= target && target < nums[mid]) {
```

A range check only means something on a sorted run - which is why it is only ever applied to the half just proven sorted. `< nums[mid]` is strict because `nums[mid] == target` was handled above.

**3.**

```java
if (nums[mid] < target && target <= nums[hi]) {
```

The mirror image for the right half: strict at `mid`, inclusive at `hi`.

### The rule underneath

Notice that the code never asks "is the target in the **unsorted** half?". It cannot answer that with endpoints - `[7, 0, 1, 2]` has endpoints `7` and `2`, and the range `2..7` says nothing about `0`. It only ever asks about the sorted half, and sends the target to the other half by elimination.

### Bonus - Find Minimum in Rotated Sorted Array (LC 153)

The minimum is the element right after the drop. Compare `mid` with `hi`: if `nums[mid] > nums[hi]`, the drop is to the right of `mid`; otherwise `mid` itself may be the minimum.

```java
class Solution {
    public int findMin(int[] nums) {

        int lo = 0;
        int hi = nums.length - 1;

        while (lo < hi) {
            int mid = lo + (hi - lo) / 2;
            if (nums[mid] > nums[hi]) {
                lo = mid + 1;               // drop is right of mid
            } else {
                hi = mid;                   // mid could be the minimum - keep it
            }
        }

        return nums[lo];
    }
}
```

Its index `lo` is also the number of positions the array was rotated by. Compare with `nums[hi]`, not `nums[lo]`: on an unrotated array `nums[mid] >= nums[lo]` is true everywhere and tells you nothing.

### Follow-up - with duplicates (LC 81)

With duplicates, `nums[lo] == nums[mid] == nums[hi]` can happen on both sides of a drop (`[1, 0, 1, 1, 1]`), and then neither half can be proven sorted. The only safe move is to shrink both ends by one:

```java
class Solution {
    public boolean search(int[] nums, int target) {

        int lo = 0, hi = nums.length - 1;

        while (lo <= hi) {
            int mid = lo + (hi - lo) / 2;
            if (nums[mid] == target) return true;

            if (nums[lo] == nums[mid] && nums[mid] == nums[hi]) {
                lo++;                       // cannot tell which half is sorted
                hi--;
            } else if (nums[lo] <= nums[mid]) {
                if (nums[lo] <= target && target < nums[mid]) hi = mid - 1;
                else lo = mid + 1;
            } else {
                if (nums[mid] < target && target <= nums[hi]) lo = mid + 1;
                else hi = mid - 1;
            }
        }

        return false;
    }
}
```

That shrink-by-one step makes the worst case `O(n)` - on an array of all `1`s with one `0` hidden somewhere, no comparison can tell you where it is.

### Java notes

- `target < nums[mid]` combined with `nums[lo] <= target` is written as two comparisons; Java has no chained `a <= b < c`.
- No `long` needed: values are within `[-10^4, 10^4]` and only compared, never added.

### Not rotated at all

```text
nums = [1, 2, 3, 4, 5], target = 4  ->  3
```

`nums[lo] <= nums[mid]` is always true, so every step takes the left-sorted branch and the code behaves exactly like day 44's search.

### Single element

```text
nums = [1], target = 1  ->  0
nums = [1], target = 0  ->  -1
```

### Two elements, rotated

```text
nums = [3, 1], target = 1  ->  1
nums = [3, 1], target = 3  ->  0
```

The case that makes `<=` mandatory (see the optimization section).

### Target is the minimum (just after the drop)

```text
nums = [4, 5, 6, 7, 0, 1, 2], target = 0  ->  4
```

### Target at either end


```text
[2, 5, 6, 0, 0, 1, 2], target = 0  ->  true

```

=== takeaway ===
> When you see a **sorted array that has been rotated** (or broken once), think **binary search on the sorted half**: at every `mid`, one half is sorted - range-check the target against that half, and discard whichever half cannot contain it.

### The core observation

A single drop can be on only one side of `mid`. So one half is always sorted, `nums[lo] <= nums[mid]` tells you which, and a sorted half answers "is the target in here?" with two comparisons. Binary search never needed global order - it needed a reliable way to discard half.

### The pattern trigger

```text
                  rotated sorted array
                           |
                           v
            nums[mid] == target ?  -> return mid
                           |
                           v
              nums[lo] <= nums[mid] ?
               /                    \
        LEFT sorted              RIGHT sorted
  target in [nums[lo], nums[mid])?   target in (nums[mid], nums[hi]]?
      yes: hi = mid-1                 yes: lo = mid+1
      no : lo = mid+1                 no : hi = mid-1
```

### The common mistakes

**Range-checking the unsorted half.** Its endpoints say nothing about what is inside. Always test the sorted half and reach the other by elimination.

**`<` instead of `<=` in `nums[lo] <= nums[mid]`.** Breaks on two-element windows like `[3, 1]`.

**Getting the inclusive/strict ends wrong.** `nums[lo] <= target < nums[mid]` and `nums[mid] < target <= nums[hi]`. `mid` is already checked; the far endpoint is still a candidate.

**Assuming there is a rotation.** An unrotated array is valid input; the code above handles it without a special case.

**Carrying this to duplicates unchanged.** With duplicates, `nums[lo] == nums[mid]` no longer proves the left is sorted. LC 81 needs the shrink step and is `O(n)` worst case.

### What to remember in six months

> Binary search needs a way to discard half, not a sorted array. In a rotated array, one half is always sorted - use that half to decide.

The same "which side is still well-behaved?" question drives LC 153 (minimum - compare with `nums[hi]`), LC 81 (duplicates) and tomorrow's Find Peak Element, where nothing is sorted at all and the slope at `mid` is what decides.
