=== intro ===
Week 3 opens: **Two Pointers and Sliding Window**. Week 2 ended with pointers growing outward from a center; today they go back to walking the same direction - a **slow** pointer that marks the finished output and a **fast** pointer that scans ahead.

You have already met this shape twice: Move Zeroes (Day 3) and String Compression (Day 13). Today is the purest version of it, and the new ingredient is the word **sorted**.

> When an array is sorted, every copy of a value sits next to the others. "Have I seen this before?" stops being a lookup in a set and becomes one comparison with the last thing you kept.

=== problem ===
Given an integer array `nums` sorted in **non-decreasing** order, remove the duplicates **in-place** so each unique value appears once, keeping their relative order. Return `k`, the number of unique values. The first `k` slots of `nums` must hold them; anything after index `k - 1` is ignored.

```text
nums = [0, 0, 1, 1, 1, 2, 2, 3, 3, 4]
return 5,  nums = [0, 1, 2, 3, 4, _, _, _, _, _]
```

The `_` slots can hold anything - the judge only reads the first `k`.

### The example as groups

| value | indices | copies | kept |
| ----: | :------ | -----: | ---: |
| 0 | 0-1 | 2 | 1 |
| 1 | 2-4 | 3 | 1 |
| 2 | 5-6 | 2 | 1 |
| 3 | 7-8 | 2 | 1 |
| 4 | 9 | 1 | 1 |

Five groups, five unique values, `k = 5`.

### A smaller example

```text
nums = [1, 1, 2]   ->   return 2,  nums = [1, 2, _]
```

### The constraints that matter

- **Sorted, non-decreasing.** Equal values are adjacent. This is the whole problem - without it, you would need a set.
- **In-place, `O(1)` extra memory.** You may not allocate a second array or a set.
- `1 <= nums.length <= 3 * 10^4`, values between `-100` and `100`. Negatives are allowed, so do not use `0` or `-1` as a "nothing yet" marker.

=== pattern ===
**Two Pointers - slow / fast**, both moving left to right.

- `fast` visits every element. It is the loop variable.
- `slow` is the index of the **last unique value written** so far.

The invariant:

> `nums[0..slow]` holds every distinct value seen so far, in order, each exactly once.

For each `fast`, ask one question: is `nums[fast]` different from `nums[slow]`? If yes, it is a new value - advance `slow` and copy it there. If no, it is another copy of a value already kept - skip it.

### Why one comparison is enough

Because the array is sorted, a value's copies form one contiguous block. When `fast` reaches a value, the only kept value it could possibly duplicate is the **most recent** one, `nums[slow]`. Any earlier kept value is strictly smaller and can never appear again.

```text
kept so far:  [0, 1, 2]         slow -> 2
fast sees:    2   -> equals nums[slow], duplicate
fast sees:    3   -> differs, new: slow = 3, nums[3] = 3
```

No set, no search - just a neighbour check.

### How it relates to Days 3 and 13

All three are the same read/write skeleton. Only the "keep" rule changes:

| day | problem | keep `nums[fast]` when... |
| --: | :------ | :------------------------ |
| 3 | Move Zeroes | it is non-zero |
| 13 | String Compression | it starts a new run (then also write the count) |
| 15 | Remove Duplicates | it differs from the last kept value |

Today is literally Day 13 where every run compresses to just its character.

### Recognising it

Reach for slow/fast pointers when:

- the input is **sorted** (or the problem is about adjacent groups)
- you must **remove / compact / dedupe in-place**
- you return a **length**, and the tail is declared irrelevant

The mental question:

> Does deciding whether to keep this element only require looking at the last element I kept?

=== bruteForce ===
Ignore the sorted order and the space limit for a moment. "Remove duplicates" is the textbook job of a **set**: insert every element, the set throws the repeats away, then write the set back into `nums`.

A `LinkedHashSet` keeps insertion order, so the values come back out in the same order they went in.

### Step logic

1. Walk `nums`, adding each value to a `LinkedHashSet`. Duplicates are silently rejected.
2. Walk the set, writing each value to `nums[0], nums[1], ...`.
3. Return the set's size.

### Dry run

```text
nums = [0, 0, 1, 1, 1, 2, 2, 3, 3, 4]
```

**Phase 1 - fill the set.**

| i | nums[i] | already in set? | set after |
| -: | ------: | :-------------- | :-------- |
| 0 | 0 | no - add | `{0}` |
| 1 | 0 | yes - ignored | `{0}` |
| 2 | 1 | no - add | `{0, 1}` |
| 3 | 1 | yes - ignored | `{0, 1}` |
| 4 | 1 | yes - ignored | `{0, 1}` |
| 5 | 2 | no - add | `{0, 1, 2}` |
| 6 | 2 | yes - ignored | `{0, 1, 2}` |
| 7 | 3 | no - add | `{0, 1, 2, 3}` |
| 8 | 3 | yes - ignored | `{0, 1, 2, 3}` |
| 9 | 4 | no - add | `{0, 1, 2, 3, 4}` |

**Phase 2 - write back.**

| k | value from set | nums after |
| -: | -------------: | :--------- |
| 0 | 0 | `[0, 0, 1, 1, 1, 2, 2, 3, 3, 4]` |
| 1 | 1 | `[0, 1, 1, 1, 1, 2, 2, 3, 3, 4]` |
| 2 | 2 | `[0, 1, 2, 1, 1, 2, 2, 3, 3, 4]` |
| 3 | 3 | `[0, 1, 2, 3, 1, 2, 2, 3, 3, 4]` |
| 4 | 4 | `[0, 1, 2, 3, 4, 2, 2, 3, 3, 4]` |

Return `set.size() = 5`. The first five slots are `0 1 2 3 4`.

### Java

```java
class Solution {
    public int removeDuplicates(int[] nums) {

        Set<Integer> seen = new LinkedHashSet<>();
        for (int num : nums) {
            seen.add(num);              // duplicates are ignored by the set
        }

        int k = 0;
        for (int num : seen) {
            nums[k] = num;
            k++;
        }
        return k;
    }
}
```

### Why it works

A set holds each value once by definition, and `LinkedHashSet` remembers first-insertion order. Since the input is sorted, first-insertion order is sorted order, so the write-back is correct.

### Complexity

**Time:** `O(n)` average (hash insertions) - **Space:** `O(n)` extra for the set

### Where it hurts

Two problems, one of which disqualifies it outright.

1. **It breaks the rules.** The problem demands `O(1)` extra memory. The set holds up to `n` boxed `Integer`s - with an all-unique array, a full copy of the input plus object overhead.
2. **It ignores the one fact we were given.** Look at Phase 1's "already in set?" column. Every `yes` happened when `nums[i]` equalled `nums[i - 1]` - the previous element. A hash set can answer "have I seen this anywhere?", but the sorted input only ever asks "is this the same as the last one?". We paid for a general-purpose membership structure to answer a question one comparison can answer.

> In a sorted array, "seen before" means "equal to the last kept value". The set is doing a job one integer can do.

=== optimization ===
Replace the set with a single index: the position of the last value we kept.

### The observation

In sorted input, duplicates are adjacent. So the only kept value that `nums[fast]` could equal is the latest one, `nums[slow]`. Keep `slow` pointing at it and compare against it.

And the writes are safe for the same reason as Days 3 and 13: `slow` advances at most once per step of `fast`, so `slow < fast` whenever we write. The slot `slow` lands on has already been read.

### The algorithm

1. If the array is empty, return `0`.
2. `slow = 0` - the first element is always unique.
3. For `fast` from `1` to `n - 1`:
   - if `nums[fast] != nums[slow]`: `slow++`, then `nums[slow] = nums[fast]`.
4. Return `slow + 1` (a count, and `slow` is an index).

### Dry run on the same example

```text
nums = [0, 0, 1, 1, 1, 2, 2, 3, 3, 4]
```

| fast | nums[fast] | nums[slow] | different? | action | slow | nums after |
| ---: | ---------: | ---------: | :--------- | :----- | ---: | :--------- |
| - | - | - | - | start | 0 | `[0, 0, 1, 1, 1, 2, 2, 3, 3, 4]` |
| 1 | 0 | 0 | no | skip | 0 | `[0, 0, 1, 1, 1, 2, 2, 3, 3, 4]` |
| 2 | 1 | 0 | yes | `slow=1`, `nums[1]=1` | 1 | `[0, 1, 1, 1, 1, 2, 2, 3, 3, 4]` |
| 3 | 1 | 1 | no | skip | 1 | `[0, 1, 1, 1, 1, 2, 2, 3, 3, 4]` |
| 4 | 1 | 1 | no | skip | 1 | `[0, 1, 1, 1, 1, 2, 2, 3, 3, 4]` |
| 5 | 2 | 1 | yes | `slow=2`, `nums[2]=2` | 2 | `[0, 1, 2, 1, 1, 2, 2, 3, 3, 4]` |
| 6 | 2 | 2 | no | skip | 2 | `[0, 1, 2, 1, 1, 2, 2, 3, 3, 4]` |
| 7 | 3 | 2 | yes | `slow=3`, `nums[3]=3` | 3 | `[0, 1, 2, 3, 1, 2, 2, 3, 3, 4]` |
| 8 | 3 | 3 | no | skip | 3 | `[0, 1, 2, 3, 1, 2, 2, 3, 3, 4]` |
| 9 | 4 | 3 | yes | `slow=4`, `nums[4]=4` | 4 | `[0, 1, 2, 3, 4, 2, 2, 3, 3, 4]` |

Return `slow + 1 = 5`. Same final array as the brute force, with no set.

### Reading the table

- The `nums[slow]` column only ever increases - it is always the largest value kept so far, which is the only one a new element can equal.
- Look at `fast = 2`: we overwrote `nums[1]` (a `0`) with `1`. That `0` was read at `fast = 1` and judged a duplicate, so nothing was lost.
- The gap `fast - slow` at any moment is exactly the number of duplicates skipped so far.

### Why "sorted" is load-bearing

```text
nums = [1, 2, 1]
fast=1: 2 != 1 -> slow=1, nums[1]=2
fast=2: 1 != 2 -> slow=2, nums[2]=1
return 3   ->   [1, 2, 1]
```

The second `1` is not adjacent to the first, so the neighbour check cannot see it. On unsorted input you need a set (or sort first). The algorithm is not wrong - it is answering a question that only has this answer on sorted input.

=== complexity ===
### Time

`fast` visits each of the `n` elements once; each visit is one comparison and at most one write.

```text
O(n)
```

### Space

Two integers, `slow` and `fast`.

```text
O(1) extra
```

### Comparison

| Approach | Time | Extra space | Uses sortedness? |
| :------- | ---: | ----------: | :--------------- |
| `LinkedHashSet` + write back | `O(n)` average | `O(n)` | no |
| New array, copy uniques | `O(n)` | `O(n)` | yes |
| Slow / fast in place | **`O(n)`** | **`O(1)`** | yes |

The time does not improve - you must look at every element. The whole gain is the space, and it comes entirely from trusting the sorted order.

=== implementation ===
```java
class Solution {
    public int removeDuplicates(int[] nums) {

        if (nums.length == 0) {
            return 0;
        }

        int slow = 0;   // index of the last unique value kept

        for (int fast = 1; fast < nums.length; fast++) {
            if (nums[fast] != nums[slow]) {
                slow++;
                nums[slow] = nums[fast];
            }
        }

        return slow + 1;
    }
}
```

### The lines that matter

**1.**

```java
int slow = 0;   // index of the last unique value kept
```

`slow` starts on index `0`, not before it, because the first element is unique by definition - there is nothing before it to duplicate. That is also why `fast` starts at `1`.

**2.**

```java
if (nums[fast] != nums[slow]) {
    slow++;
    nums[slow] = nums[fast];
}
```

Increment **first**, then write. `slow` points at the last kept value; writing before incrementing would overwrite that kept value instead of placing the new one after it.

**3.**

```java
return slow + 1;
```

`slow` is an index; the problem wants a count. Returning `slow` is an off-by-one that drops the last unique value - `[1, 1, 2]` would report `1` instead of `2`.

### Java notes

- The empty-array guard is not needed under LeetCode's constraints (`n >= 1`), but it is free, and without it an empty input would return `1`.
- `nums[slow] = nums[fast]` when `slow == fast` (no duplicates seen yet) writes a value onto itself. Harmless; adding `if (slow != fast)` saves the write but not any time worth measuring.
- The method mutates the caller's array, since Java passes the array reference.

### The follow-up: at most two copies (LC 80)

Rewrite it with a **write** cursor that counts kept elements, and compare against the element `2` slots back in the output:

```java
class Solution {
    public int removeDuplicates(int[] nums) {

        int k = 0;   // number of elements kept so far

        for (int num : nums) {
            // keep it if fewer than 2 are kept, or it differs from
            // the element two slots back in the output
            if (k < 2 || num != nums[k - 2]) {
                nums[k] = num;
                k++;
            }
        }

        return k;
    }
}
```

Replace both `2`s with `1` and it solves today's problem; with any `m`, it allows at most `m` copies. In sorted output, if `num` equals the value `m` slots back, then all `m` slots in between hold that same value too - so keeping it would make `m + 1`.

=== edgeCases ===
### Single element

```text
[1]  ->  return 1,  [1]
```

The loop never runs; `slow = 0`, return `1`.

### Empty array

```text
[]  ->  return 0
```

Outside LeetCode's constraints, handled by the guard.

### All the same

```text
[2, 2, 2, 2]  ->  return 1,  [2, _, _, _]
```

Every comparison says "equal". `slow` never moves.

### All unique

```text
[1, 2, 3]  ->  return 3,  [1, 2, 3]
```

Every comparison says "different". `slow` and `fast` move together and each element is written onto itself.

### Smallest example with a duplicate

```text
[1, 1, 2]  ->  return 2,  [1, 2, _]
```

The `2` moves from index 2 to index 1.

### Negative values

```text
[-3, -3, -1, 0, 0]  ->  return 3,  [-3, -1, 0, _, _]
```

The comparison is with real values, so there is no sentinel to collide with. A solution that initialises "last seen" to `0` or `-1` would wrongly skip a leading `0` or `-1`.

### Duplicates only at the end

```text
[1, 2, 3, 3, 3]  ->  return 3,  [1, 2, 3, _, _]
```

### Unsorted input (not a valid input - shows why sorted matters)

```text
[1, 2, 1]  ->  return 3,  [1, 2, 1]
```

The two `1`s are not adjacent, so the neighbour check never compares them. Not a bug in the algorithm; a reminder of the precondition it relies on.

=== takeaway ===
> When you see **"sorted" + "remove duplicates in-place"**, think **slow/fast pointers**: compare each element with the **last kept** one, not with everything kept.

### The core observation

Sorting puts every copy of a value next to the others. So "have I already kept this value?" can only be true for the most recently kept value, and one comparison with `nums[slow]` replaces an entire hash set. The writes are safe because `slow` never passes `fast`.

### The pattern trigger

```text
     fast ----> visits every element
                       |
                       v
          nums[fast] == nums[slow] ?
                /                \
              yes                 no
               |                   |
         duplicate - skip     slow++
                              nums[slow] = nums[fast]
                       |
                       v
      nums[0..slow] = every distinct value so far
                       |
                       v
               return slow + 1
```

### The common mistakes

**Returning `slow` instead of `slow + 1`.** Index versus count. It silently drops the last unique value.

**Writing before incrementing.** `nums[slow] = nums[fast]; slow++;` overwrites the last kept value instead of placing the new one after it.

**Comparing with `nums[fast - 1]` and writing at `slow`.** This one actually works for LC 26, because `nums[fast - 1]` in the original order is the previous input value. But it does **not** generalise to LC 80 - there you must compare against the **output** (`nums[k - 2]`), not the input. Comparing with what you kept is the habit that scales.

**Reaching for a set.** Correct, `O(n)` space, and a sign the word "sorted" was not read.

### What to remember in six months

> Sorted means duplicates are neighbours. Neighbour checks replace hash sets.

The same skeleton, with a different keep condition, solves Remove Element (LC 27), Move Zeroes (LC 283), Remove Duplicates II (LC 80) and String Compression (LC 443). If you can write the LC 80 version from memory, you can write all of them.
