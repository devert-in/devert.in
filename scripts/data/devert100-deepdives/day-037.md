=== intro ===
Yesterday the stack held exactly what the problem gave us - brackets. Today it has to answer a question about **all** of its contents (what is the smallest?) while still only being allowed to touch the top.

> When a data structure needs to answer a question about everything it holds, and it only ever changes at one end, store the answer **at that end**, next to each element, at the moment the element arrives.

=== problem ===
Design a class `MinStack` with four operations, **each in `O(1)` time**:

| method | does |
| :----- | :--- |
| `push(val)` | put `val` on top |
| `pop()` | remove the top element |
| `top()` | return the top element |
| `getMin()` | return the smallest element currently in the stack |

### The example

```text
MinStack s = new MinStack();
s.push(-2);
s.push(0);
s.push(-3);
s.getMin();   // -3
s.pop();
s.top();      //  0
s.getMin();   // -2
```

LeetCode writes this as the call list `["MinStack","push","push","push","getMin","pop","top","getMin"]` with expected output `[null,null,null,null,-3,null,0,-2]` - `null` for every method that returns nothing.

### What makes it non-trivial

`push`, `pop` and `top` are an ordinary stack - `ArrayDeque` already does them in `O(1)`. The whole problem is `getMin`, and specifically this moment:

```text
stack (bottom -> top):  [-2, 0, -3]     min = -3
pop()
stack (bottom -> top):  [-2, 0]         min = ?
```

When `-3` leaves, the minimum has to go **back** to `-2`. Keeping a single `min` variable cannot do that: after the pop, the variable still says `-3`, and nothing remembers what the minimum was before `-3` arrived.

### What the constraints tell you

- Values span the full `int` range, `-2^31` to `2^31 - 1`. That matters for one of the follow-up tricks.
- `pop`, `top` and `getMin` are only called on a non-empty stack.
- Up to `3 * 10^4` calls in total.

=== pattern ===
**Stack with an auxiliary minimum** - augmenting each entry with a summary of everything beneath it.

The observation that drives it is about what a stack can and cannot do. A stack only changes **at the top**. So while an element sits in the stack, everything **below** it is frozen - nothing underneath can be added, removed or changed until this element is popped.

That means: the minimum of "this element and everything below it" is fixed for as long as this element is in the stack. Compute it once, at push time, and store it **with** the element.

```text
push -2    entry (-2, min -2)
push  0    entry ( 0, min -2)     min(0, -2)
push -3    entry (-3, min -3)     min(-3, -2)

stack:  (-2,-2)  (0,-2)  (-3,-3)  <- top
                                     getMin = -3

pop     (-2,-2)  (0,-2)           <- top
                                     getMin = -2   (already stored, nothing recomputed)
```

Popping does not need to "restore" the old minimum. The old minimum was never lost - it is sitting in the entry that is now on top.

### Recognising it

Reach for an augmented stack when:

- you need a **running aggregate** (min, max, sum, count of something) of a stack's contents
- elements only enter and leave at one end
- the question must be answered in `O(1)` after any number of pops

The mental question:

> While this element is on the stack, can anything below it change? If not, whatever I compute about "it and everything below" stays true until it is popped.

The same trick works for any combine step that only looks at the new value and the summary below it - max, sum, GCD - and two of these stacks glued into a queue (tomorrow's construction) give a queue with an `O(1)` minimum.

=== bruteForce ===
Forget `O(1)` for `getMin`. Keep a normal stack, and when someone asks for the minimum, look at every element.

### Step logic

- `push`, `pop`, `top`: ordinary stack operations.
- `getMin`: walk the whole stack, keeping the smallest value seen.

### Dry run

The LeetCode example, step by step. The stack is shown bottom to top.

| # | call | stack after | elements read by getMin | running min while scanning | returns |
| -: | :--- | :---------- | :---------------------- | :------------------------- | :------ |
| 1 | `push(-2)` | `[-2]` | - | - | - |
| 2 | `push(0)` | `[-2, 0]` | - | - | - |
| 3 | `push(-3)` | `[-2, 0, -3]` | - | - | - |
| 4 | `getMin()` | `[-2, 0, -3]` | -3, 0, -2 | -3 -> -3 -> -3 | **-3** |
| 5 | `pop()` | `[-2, 0]` | - | - | - |
| 6 | `top()` | `[-2, 0]` | - | - | **0** |
| 7 | `getMin()` | `[-2, 0]` | 0, -2 | 0 -> -2 | **-2** |

(`ArrayDeque` iterates from the top down, which is why the scan reads `-3` first.)

Output: `-3`, `0`, `-2`. Correct.

### Java

```java
class MinStack {

    private final Deque<Integer> stack = new ArrayDeque<>();

    public MinStack() {
    }

    public void push(int val) {
        stack.push(val);
    }

    public void pop() {
        stack.pop();
    }

    public int top() {
        return stack.peek();
    }

    public int getMin() {
        int min = Integer.MAX_VALUE;
        for (int v : stack) {           // reads every element
            min = Math.min(min, v);
        }
        return min;
    }
}
```

### Complexity

**Time:** `push`, `pop`, `top` `O(1)`; `getMin` `O(n)` - **Space:** `O(n)`

### Where it hurts

Look at rows 4 and 7. Row 7 reads `0` and `-2` and concludes the minimum is `-2`. But row 4 **already read** `0` and `-2` - it walked straight past them on its way through the stack. The fact "the minimum of `[-2, 0]` is `-2`" was computed in row 4 and thrown away.

And nothing about `[-2, 0]` changed between rows 4 and 7. Only the element **above** them was removed. In a stack, the elements below the top never change - only the top does. So every `getMin` re-derives facts about a region of the stack that has been frozen since those elements were pushed.

With `3 * 10^4` calls, alternating `push` and `getMin` makes the scans total about `n^2 / 2` reads - roughly `10^8` for nothing.

> The minimum of "an element and everything below it" cannot change while that element is in the stack. Compute it once, at push time, and keep it.

=== optimization ===
Store the answer to `getMin` inside each entry.

### The key observation

Let `minBelow(e)` be the minimum of entry `e` and everything beneath it. Then:

```text
minBelow(new entry) = min(new value, minBelow(entry currently on top))
```

One comparison, at push time. And because nothing below an entry changes while it is in the stack, `minBelow` stays correct until that entry is popped. `getMin()` is then just `minBelow(top)`.

### Step by step

Each stack entry is a pair `{value, minSoFar}`.

- `push(val)`: `minSoFar = stack empty ? val : min(val, top.minSoFar)`. Push `{val, minSoFar}`.
- `pop()`: pop the pair. Nothing to recompute.
- `top()`: `top.value`.
- `getMin()`: `top.minSoFar`.

### Dry run - same calls

| # | call | computation | stack after (`{value, minSoFar}`, bottom -> top) | returns |
| -: | :--- | :---------- | :------------------------------------------------ | :------ |
| 1 | `push(-2)` | stack empty, so `minSoFar = -2` | `{-2,-2}` | - |
| 2 | `push(0)` | `min(0, -2) = -2` | `{-2,-2} {0,-2}` | - |
| 3 | `push(-3)` | `min(-3, -2) = -3` | `{-2,-2} {0,-2} {-3,-3}` | - |
| 4 | `getMin()` | read top's `minSoFar` | unchanged | **-3** |
| 5 | `pop()` | remove `{-3,-3}` | `{-2,-2} {0,-2}` | - |
| 6 | `top()` | read top's `value` | unchanged | **0** |
| 7 | `getMin()` | read top's `minSoFar` | unchanged | **-2** |

Row 7 is the moment the brute force rescanned. Here it is one read: the `-2` was stored in `{0,-2}` back at row 2, when `0` was pushed on top of `-2`.

### The two-stack version - and the duplicate trap

Storing a `minSoFar` with **every** entry repeats the same minimum many times. The other classic layout keeps a second stack, `mins`, that only grows when a new minimum (or a tie) arrives:

- `push(val)`: push onto `stack`; also push onto `mins` if `mins` is empty or `val <= mins.top`.
- `pop()`: pop from `stack`; if the popped value equals `mins.top`, pop `mins` too.
- `getMin()`: `mins.top`.

The `<=` is not a style choice. Watch what `<` does with a repeated minimum:

| call | stack | mins with `<=` | mins with `<` |
| :--- | :---- | :------------- | :------------ |
| `push(0)` | `[0]` | `[0]` | `[0]` |
| `push(1)` | `[0, 1]` | `[0]` | `[0]` |
| `push(0)` | `[0, 1, 0]` | `[0, 0]` | `[0]` (tie not pushed) |
| `pop()` | `[0, 1]` | `[0]` | `[]` (popped value `0` equals top) |
| `getMin()` | `[0, 1]` | **0** | crash - `mins` is empty |

With `<`, the second `0` was never recorded, so popping it removed the record of the **first** `0`. With `<=`, every copy of the minimum has its own entry in `mins`.

### The `O(1)` extra space follow-up

It is possible to keep a single `long min` and no second structure, by storing an **encoded** value whenever a new minimum arrives:

- `push(val)` with `val < min`: push `2*val - min` (which is less than `val`, so it is recognisable as encoded), then `min = val`.
- `pop()` of a value `top < min`: that entry was encoded; the previous minimum was `2*min - top`. Restore it.
- `top()`: if the stored value is `< min`, the real value is `min` itself.

With `push(-2), push(0), push(-3)`: stored `-2` (min `-2`), stored `0`, then `-3 < -2` so store `2*(-3) - (-2) = -4` and set min `-3`. Popping `-4`: since `-4 < -3`, restore min to `2*(-3) - (-4) = -2`. It works, but it needs `long` (with `int`, `2*val - min` overflows at the extremes of the range) and it is easy to get wrong under pressure. Mention it; implement the pair version unless asked.

=== complexity ===
### Time

Every operation does a constant number of stack operations and at most one comparison.

```text
push, pop, top, getMin:  O(1) each
```

### Space

One pair per element.

```text
O(n)
```

### Comparison

| Approach | push | pop | top | getMin | Extra space |
| :------- | ---: | --: | --: | -----: | ----------: |
| Plain stack, scan for min | `O(1)` | `O(1)` | `O(1)` | `O(n)` | none |
| Single `min` variable | `O(1)` | **wrong** after popping the min | `O(1)` | `O(1)` | `O(1)` |
| Pairs `{value, minSoFar}` | `O(1)` | `O(1)` | `O(1)` | **`O(1)`** | `O(n)` |
| Two stacks, `<=` | `O(1)` | `O(1)` | `O(1)` | **`O(1)`** | `O(n)` worst, often less |
| Encoded `2*val - min` | `O(1)` | `O(1)` | `O(1)` | **`O(1)`** | `O(1)` beyond the stack |

The two-stack version saves memory when minimums are rare (pushing `1, 2, 3, ..., n` keeps `mins` at size 1), but in the worst case (strictly decreasing pushes) both stacks hold `n` entries. All versions are `O(n)` space overall, because the stack itself is.

=== implementation ===
```java
class MinStack {

    // Each entry is {value, minimum of this value and everything below it}.
    private final Deque<int[]> stack = new ArrayDeque<>();

    public MinStack() {
    }

    public void push(int val) {
        int minSoFar = stack.isEmpty() ? val : Math.min(val, stack.peek()[1]);
        stack.push(new int[] { val, minSoFar });
    }

    public void pop() {
        stack.pop();                    // the entry below already knows its own min
    }

    public int top() {
        return stack.peek()[0];
    }

    public int getMin() {
        return stack.peek()[1];
    }
}
```

### The lines that matter

**1.**

```java
int minSoFar = stack.isEmpty() ? val : Math.min(val, stack.peek()[1]);
```

The whole idea in one line. The new entry's minimum is its own value compared against the **previous top's stored minimum** - not against every element, because the previous top already summarises everything below it. The empty check handles the first push, where there is nothing to compare against.

**2.**

```java
stack.pop();                    // the entry below already knows its own min
```

No restoring, no recomputation. This is the line that a single `min` variable cannot write correctly.

**3.**

```java
return stack.peek()[1];
```

`getMin` is a field read.

### The two-stack version

```java
class MinStack {

    private final Deque<Integer> stack = new ArrayDeque<>();
    private final Deque<Integer> mins = new ArrayDeque<>();

    public MinStack() {
    }

    public void push(int val) {
        stack.push(val);
        if (mins.isEmpty() || val <= mins.peek()) {     // <= keeps every copy of a tied minimum
            mins.push(val);
        }
    }

    public void pop() {
        int val = stack.pop();
        if (val == mins.peek()) {                       // int vs Integer: compares values
            mins.pop();
        }
    }

    public int top() {
        return stack.peek();
    }

    public int getMin() {
        return mins.peek();
    }
}
```

### The encoded version, for the follow-up

```java
class MinStack {

    private final Deque<Long> stack = new ArrayDeque<>();
    private long min;

    public MinStack() {
    }

    public void push(int val) {
        if (stack.isEmpty()) {
            stack.push((long) val);
            min = val;
        } else if (val >= min) {
            stack.push((long) val);
        } else {
            stack.push(2L * val - min);     // encoded: always < val, so always < the new min
            min = val;
        }
    }

    public void pop() {
        long top = stack.pop();
        if (top < min) {
            min = 2 * min - top;            // undo the encoding: recover the previous min
        }
    }

    public int top() {
        long top = stack.peek();
        return (int) (top < min ? min : top);
    }

    public int getMin() {
        return (int) min;
    }
}
```

### Java notes

- `int val = stack.pop();` unboxes the `Integer` into an `int`, so `val == mins.peek()` compares numbers. Writing `stack.pop() == mins.peek()` would compare two `Integer` **references** - correct for values in `-128..127` (Java caches those) and wrong for anything else. It passes small tests and fails on `push(512)`.
- `Deque<int[]>` stores two ints per entry with no boxing; it is faster than a `Deque` of a custom pair class and needs no extra declaration.
- In the encoded version, `2L * val` forces `long` arithmetic **before** the multiplication. `2 * val` would overflow as an `int` first and then widen the wrong answer.
- `ArrayDeque.peek()` returns `null` on an empty deque, so `stack.peek()[1]` would throw `NullPointerException`. LeetCode promises `top`/`getMin`/`pop` are never called when empty; in production code you would check and throw a clearer exception.

=== edgeCases ===
### The LeetCode example

```text
push(-2), push(0), push(-3), getMin(), pop(), top(), getMin()
->  -3, 0, -2
```

### Duplicate minimums

```text
push(0), push(1), push(0), getMin(), pop(), getMin()
->  0, 0
```

The case that breaks the two-stack version when it uses `<` instead of `<=`. The pair version is immune - each `0` carries its own `minSoFar`.

### Popping the minimum restores the previous one

```text
push(5), push(3), push(7), push(2)
getMin() -> 2
pop(), getMin() -> 3
pop(), getMin() -> 3       (7 was not the min; removing it changes nothing)
pop(), getMin() -> 5
```

### Increasing pushes

```text
push(1), push(2), push(3), getMin() -> 1, top() -> 3
```

The minimum is the bottom element and never changes. In the two-stack version `mins` stays at size 1.

### Decreasing pushes

```text
push(3), push(2), push(1), getMin() -> 1
pop(), getMin() -> 2
```

Every push is a new minimum. In the two-stack version `mins` grows as large as `stack` - the worst case for its memory.

### Extreme values

```text
push(-2147483648), push(2147483647)
getMin() -> -2147483648, top() -> 2147483647
pop(), push(-2147483648), getMin() -> -2147483648
```

The pair and two-stack versions only compare, so they cannot overflow. The encoded version computes `2*val - min`, which is why it stores `long`.

### Single element

```text
push(42), top() -> 42, getMin() -> 42
```

### Push after emptying

```text
push(1), pop(), push(9), getMin() -> 9
```

After the stack empties, the next push must not compare against a stale minimum. The `stack.isEmpty()` check in `push` handles it - a version with a separate `min` field that is never reset would wrongly return `1`.

=== takeaway ===
> When a stack must answer **"what is the min (or max) of everything in it?"** in `O(1)`, store that answer **with each entry** at push time. Nothing below an entry can change while it is there.

### The core observation

A stack only changes at the top, so the region below any element is frozen until that element leaves. The minimum of "this element and everything below" is therefore permanent for the element's lifetime - compute it once, from the previous top's stored minimum, and popping restores the old answer automatically.

### The pattern trigger

```text
     need aggregate of the whole stack in O(1)
                       |
                       v
     on push:  agg = combine(val, top.agg)      (min, max, sum, gcd ...)
               push {val, agg}
                       |
                       v
     on pop:   just pop - the entry below already holds its own agg
                       |
                       v
     query:    top.agg
```

### The common mistakes

**A single `min` variable.** Correct until the minimum is popped, then permanently wrong - nothing remembers the previous minimum.

**`<` instead of `<=` in the two-stack version.** Breaks on duplicate minimums: popping one copy erases the record of the other.

**Comparing `Integer` objects with `==`.** Passes on small values thanks to the cache, fails on `512`.

**`int` arithmetic in the encoded trick.** `2 * val - min` overflows at the edges of the `int` range.

### What to remember in six months

> Augment each entry with a summary of everything beneath it. A stack never invalidates what is below the top.

The same move gives a Max Stack, a stack with `O(1)` sum, and - with two of these stacks glued into a queue (tomorrow's construction) - a queue that reports its min or max in `O(1)`, which is one way to solve Sliding Window Maximum (LC 239).
