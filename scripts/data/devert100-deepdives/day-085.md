=== intro ===
Week 13 opens where week 12 left off: greedy. Days 81-84 each sorted once and swept. Today a single sort is not enough, because every step creates a **new** item that has to be slotted back into the order - so the sorted list becomes a **min-heap**.

> If the greedy choice is "take the smallest", and taking it produces something new that competes for "smallest" next time, you need a structure that keeps answering "what is smallest now?" after every insert. That is a heap, and that is the whole upgrade.

=== problem ===
You have `n` ropes of given lengths. Joining two ropes of lengths `a` and `b` costs `a + b` and produces one rope of length `a + b`. Keep joining until one rope is left. Return the **minimum total cost**.

This is GFG's "Minimum Cost of Ropes", and the same problem as LeetCode 1167 "Minimum Cost to Connect Sticks" (Premium, so the GFG version is the free one to practise on).

```text
ropes  = [4, 3, 2, 6]
output = 29
```

One optimal order:

| join | ropes before | pick | new rope | cost of this join | running total |
| ---: | :----------- | :--- | -------: | ----------------: | ------------: |
| 1 | `[4, 3, 2, 6]` | 2 + 3 | 5 | 5 | 5 |
| 2 | `[4, 5, 6]` | 4 + 5 | 9 | 9 | 14 |
| 3 | `[6, 9]` | 6 + 9 | 15 | 15 | 29 |

### What makes it non-trivial

**The cost of a join is paid again later.** The rope `5` made in join 1 is not done - it is an input to join 2, so its length is paid a second time. The `9` from join 2 is paid again in join 3. A short rope that gets joined early ends up being paid for in *every* later join it is part of.

Look at what each original rope ends up costing in the order above:

```text
rope 2:  inside join 1, join 2, join 3   ->  paid 3 times  ->  6
rope 3:  inside join 1, join 2, join 3   ->  paid 3 times  ->  9
rope 4:  inside          join 2, join 3   ->  paid 2 times  ->  8
rope 6:  inside                  join 3   ->  paid 1 time   ->  6
                                                    total  =  29
```

So the question is really: **which ropes should be paid for the most times?** Clearly the shortest ones.

### The last join is fixed

Whatever order you choose, the final join always produces one rope of length `4 + 3 + 2 + 6 = 15`, and always costs `15`. Only the earlier joins are up for negotiation.

Constraints (GFG): `1 <= n <= 10^5`, `1 <= arr[i] <= 10^4`. The total can exceed an `int` on large inputs, so the answer is a `long`.

=== pattern ===
**Greedy with a min-heap** - the same idea as Huffman coding.

### Why it is greedy

At every step there is one obviously-safe move: **join the two shortest ropes currently on the table.** The reason comes from the "paid how many times" view:

```text
total cost = sum over every original rope of (length * number of joins it takes part in)
```

The number of joins a rope takes part in is its **depth** in the tree of joins. Long ropes should be shallow (paid rarely), short ropes deep (paid often). The deepest pair in any join tree are joined *first* - so the two shortest ropes should be joined first.

And after that first join, the problem is the same problem again, one rope smaller. The same argument applies to the new set of ropes, including the freshly-made one.

### Why it needs a heap, not a sort

After joining `2 + 3 = 5`, the new rope `5` has to compete again. Is it now the shortest? Second shortest? Longer than everything? It depends on the input. A list sorted once at the start cannot answer that; re-sorting after every join costs `O(n log n)` each time.

A min-heap answers "give me the smallest" in `O(log n)` and "add this new item" in `O(log n)`, which is exactly the loop: poll, poll, add.

### Recognising it

- "combine items pairwise until one is left", with a cost that depends on the sizes being combined
- the combined result goes back into the pool
- minimise total cost (or total time, or total weighted length)

The mental question:

> Does each item's contribution get multiplied by how early it is combined? If so, combine the smallest first - and keep a heap, because the results re-enter the pool.

Other places it appears: Huffman coding, optimal merging of sorted files, Last Stone Weight (with a max-heap), and "minimum cost to merge" problems where any two piles may be merged.

=== bruteForce ===
Do not assume we know which pair to join. Try **every** pair, recurse on what is left, and keep the cheapest total.

### Step logic

1. If one rope (or none) is left, the remaining cost is `0`.
2. Otherwise, for every pair `(i, j)`:
   - join them: `joined = ropes[i] + ropes[j]`
   - build the new set of ropes: everything except `i` and `j`, plus `joined`
   - candidate cost = `joined + best(new set)`
3. Return the minimum candidate.

### Java

```java
class Solution {
    public long minCost(int[] arr) {
        List<Long> ropes = new ArrayList<>();
        for (int len : arr) ropes.add((long) len);
        return best(ropes);
    }

    // Cheapest way to finish joining the ropes in this list.
    private long best(List<Long> ropes) {
        if (ropes.size() <= 1) return 0;

        long answer = Long.MAX_VALUE;

        for (int i = 0; i < ropes.size(); i++) {
            for (int j = i + 1; j < ropes.size(); j++) {
                long joined = ropes.get(i) + ropes.get(j);

                List<Long> next = new ArrayList<>();
                for (int k = 0; k < ropes.size(); k++) {
                    if (k != i && k != j) next.add(ropes.get(k));
                }
                next.add(joined);

                answer = Math.min(answer, joined + best(next));
            }
        }

        return answer;
    }
}
```

### Complexity

**Time:** the number of orders is `C(n,2) * C(n-1,2) * ... * C(2,2)`, which is `n! * (n-1)! / 2^(n-1)`. For `n = 4` that is 18; for `n = 8` it is 1,587,600; for `n = 10` it is about 2.6 billion. Super-exponential. **Space:** `O(n^2)` - the recursion is `n - 1` levels deep and each level holds a list of up to `n` ropes.

### Where it hurts

Read the table's "cost" columns and look for the pattern in the cheap rows. Every total of `29` or `30` starts by joining two ropes from `{2, 3, 4}`. Every total of `35` or more joins a `6` early - or builds a big rope early and then pays for it again.

The brute force explores 18 orders to discover a rule it could have known in advance: **a rope joined early is paid for again in every later join**. So the rope you join first should be as short as possible - and the other rope in that join, too.

It also recomputes the same state many times: rows 1 and 4 both reach `[9, 6]` and finish identically; rows 9 and 11 both reach `[10, 5]`. But even memoising those states leaves an exponential number of multisets. The real fix is not to search at all.

=== optimization ===
### The observation

Write the total cost the "paid how many times" way:

```text
total = sum of (length of rope r) * (number of joins r takes part in)
```

Picture the joins as a tree: the original ropes are leaves, each join is an internal node, the final rope is the root. "Number of joins r takes part in" is the **depth** of leaf `r`. So:

```text
total = sum of length(r) * depth(r)
```

To minimise that, the **shortest** ropes should be the **deepest** leaves. The deepest two leaves of any such tree are siblings that get joined together - and that join happens before anything above them. So in some optimal order, **the two shortest ropes are joined first**.

After that join, you have a new problem of the same shape: `n - 1` ropes, including the new one. Apply the same rule again. That is the whole algorithm:

1. Put every rope in a min-heap.
2. While more than one rope remains: poll the two smallest `a` and `b`, add `a + b` to the cost, push `a + b` back.
3. Return the cost.

### Dry run

```text
ropes = [4, 3, 2, 6]
heap  = {2, 3, 4, 6}
```

| step | heap before | poll a | poll b | `a + b` | cost after | push | heap after |
| ---: | :---------- | -----: | -----: | ------: | ---------: | ---: | :--------- |
| 1 | `{2, 3, 4, 6}` | 2 | 3 | 5 | 5 | 5 | `{4, 5, 6}` |
| 2 | `{4, 5, 6}` | 4 | 5 | 9 | 14 | 9 | `{6, 9}` |
| 3 | `{6, 9}` | 6 | 9 | 15 | 29 | 15 | `{15}` |

```text
heap has one rope left  ->  cost = 29
```

That is exactly row 10 of the brute-force table - found directly, without looking at the other 17.

### Why the new rope must go back into the heap

Step 2 is where the heap earns its place. After step 1 the new rope `5` is not the smallest (`4` is) but it is the second smallest, so it is joined next. Change the input to `[1, 1, 1, 1]`:

| step | heap before | poll a | poll b | `a + b` | cost after | heap after |
| ---: | :---------- | -----: | -----: | ------: | ---------: | :--------- |
| 1 | `{1, 1, 1, 1}` | 1 | 1 | 2 | 2 | `{1, 1, 2}` |
| 2 | `{1, 1, 2}` | 1 | 1 | 2 | 4 | `{2, 2}` |
| 3 | `{2, 2}` | 2 | 2 | 4 | 8 | `{4}` |

Total `8`. Now the new rope from step 1 was **not** used in step 2 - two original ropes were shorter. A "sort once and keep adding the next rope onto the growing one" approach does `1+1 = 2`, `2+1 = 3`, `3+1 = 4`, total `9`, which is wrong. Only a structure that re-ranks the new rope among the old ones gets `8`.

=== complexity ===
### Time

Building the heap: `n` inserts, `O(n log n)` (or `O(n)` with a bulk heapify). The loop runs `n - 1` times, each doing two polls and one add, each `O(log n)`.

```text
O(n log n)
```

### Space

The heap holds at most `n` ropes.

```text
O(n)
```

### Comparison

| Approach | Time | Space | Correct? |
| :------- | ---: | ----: | :------- |
| Try every join order | `n! (n-1)! / 2^(n-1)` | `O(n^2)` | yes |
| Sort once, chain onto the running rope | `O(n log n)` | `O(1)` | no - `[1,1,1,1]` gives 9 |
| Re-sort after every join | `O(n^2 log n)` | `O(n)` | yes |
| Min-heap | **`O(n log n)`** | `O(n)` | yes |

### A linear-time variant

If the ropes are already sorted, two plain queues do it in `O(n)`: one holds the sorted originals, the other holds the joined ropes - which come out in non-decreasing order on their own. Each step takes the smaller front of the two queues, twice. Worth mentioning as a follow-up; the heap is the expected interview answer.

=== implementation ===
```java
class Solution {
    public long minCost(int[] arr) {

        // Min-heap of current rope lengths. long: the total can exceed int.
        PriorityQueue<Long> heap = new PriorityQueue<>();
        for (int len : arr) {
            heap.add((long) len);
        }

        long cost = 0;

        while (heap.size() > 1) {
            long a = heap.poll();       // shortest
            long b = heap.poll();       // second shortest
            cost += a + b;              // pay for this join
            heap.add(a + b);            // the new rope competes again
        }

        return cost;
    }
}
```

### The lines that matter

**1.**

```java
while (heap.size() > 1) {
```

`> 1`, not `> 0`. With one rope left there is nothing to join. With `>= 1` the second `poll()` would return `null` and unboxing it throws a `NullPointerException`.

**2.**

```java
cost += a + b;              // pay for this join
heap.add(a + b);            // the new rope competes again
```

Both halves matter. The cost is paid now; the new rope is pushed back so its length can be paid again in later joins - which is exactly the "depth" the greedy argument is about.

**3.**

```java
PriorityQueue<Long> heap = new PriorityQueue<>();
```

Java's `PriorityQueue` is a **min**-heap by default - `poll()` returns the smallest. No comparator needed. `Long`, not `Integer`, because joined ropes grow and the running cost can pass `2^31 - 1`.

### Java notes

- **Signatures.** GFG's stub has changed over time (older: `long minCost(long arr[], int n)`; newer: one `int[]` parameter). The body is the same - adjust the parameter list to whatever the editor shows. On LeetCode 1167 the method is `public int connectSticks(int[] sticks)`; the same body works with `int` there, since LeetCode's constraints keep the total inside an `int`.
- `heap.add((long) len)` boxes each length into a `Long`. Boxing costs a little time; for `n = 10^5` it is not a concern.
- `new PriorityQueue<>(list)` heapifies a collection in `O(n)`, a constant-factor improvement over `n` separate adds. The overall bound is still `O(n log n)` because of the loop.

=== edgeCases ===
### Single rope

```text
[5]  ->  0
```

Nothing to join. The `while` loop never runs.

### Two ropes

```text
[4, 7]  ->  11
```

Exactly one join, and it is the fixed final join: the total length.

### All equal

```text
[1, 1, 1, 1]  ->  8
```

Two original ropes are joined before the new `2` is touched. The "sort once and chain" shortcut gives `9` here.

### Already sorted

```text
[1, 2, 3, 4, 5]  ->  33
```

`1+2 = 3` (3), `3+3 = 6` (9), `4+5 = 9` (18), `6+9 = 15` (33). Note step 3: the heap picks the two originals `4` and `5` over the new `6`.

### GFG's second example

```text
[4, 2, 7, 6, 9]  ->  62
```

`2+4 = 6` (6), `6+6 = 12` (18), `7+9 = 16` (34), `12+16 = 28` (62).

### LeetCode 1167's examples

```text
[2, 4, 3]     ->  14
[1, 8, 3, 5]  ->  30
```

### Large totals

```text
100000 ropes of length 10000  ->  16,689,280,000
```

Far beyond `Integer.MAX_VALUE` (about `2.1 * 10^9`). With `int` the total silently wraps to a wrong value. This is why both the heap elements and `cost` are `long`.

=== takeaway ===
> When you see **"combine two at a time until one is left"**, where each combine costs the **sum of the sizes** and the result **goes back into the pool**, think **min-heap: poll two, push their sum**.

### The core observation

Each rope is paid for once per join it takes part in, so the total is `sum(length * depth)` in the tree of joins. Short ropes should be deep - joined first. After each join the problem repeats with one fewer rope, so "join the two shortest" applies again, and a heap keeps track of which two are shortest now.

### The pattern trigger

```text
     pool of sizes, combine any two, result rejoins the pool
                            |
                            v
          cost of a combine = sum of the two sizes
                            |
                            v
       total = sum(size * times combined)  ->  smallest first
                            |
                            v
           min-heap:  while size > 1:
                         a = poll, b = poll
                         cost += a + b, push a + b
```

### The common mistakes

**Sorting once instead of using a heap.** The joined rope has to be re-ranked against the remaining originals. Chaining onto one growing rope is wrong on `[1, 1, 1, 1]`.

**Using `int`.** Fine on every small example, wrong on large inputs.

**Joining the longest first** - the instinct "get the big ones out of the way" is exactly backwards: big ropes joined early are paid for again and again.

### What to remember in six months

> Combine-two-until-one with additive cost is Huffman coding. Smallest two first, and a heap because the result goes back in.

Same skeleton: Huffman encoding, optimal merge of sorted files, Last Stone Weight (LC 1046, max-heap, smash the two largest), and Minimum Cost to Connect Sticks (LC 1167, this exact problem).
