=== intro ===
Yesterday was about one pointer and the arrow it must not lose. Today adds a second pointer that walks the **same** list at a **different speed** - and the gap between them measures something you would otherwise need a full pass to learn.

> If you need a position defined *relative to the length* (the middle, a third of the way, `k` from the end), you usually do not need the length. Let one pointer run ahead at a known rate, and the other one lands on the answer by itself.

=== problem ===
Given the `head` of a singly linked list, return the **middle node**. If there are two middle nodes, return the **second** one.

```text
head   = 1 -> 2 -> 3 -> 4 -> 5 -> null
answer = node 3        (LeetCode prints it as [3, 4, 5])
```

```text
head   = 1 -> 2 -> 3 -> 4 -> 5 -> 6 -> null
answer = node 4        (two middles: 3 and 4, take the second)
```

### What is being returned

A **node**, not a value. LeetCode serialises the returned node and everything after it, which is why the expected output for the first example is shown as `[3, 4, 5]`. You do not build anything new - you return a reference to a node that already exists in the list.

### "Middle" in index terms

Number the nodes from `0`. For a list of length `n`, the answer is the node at index `n / 2` (integer division).

| n | indices | middle(s) | answer index `n / 2` |
| -: | :------ | :-------- | -------------------: |
| 1 | 0 | 0 | 0 |
| 2 | 0 1 | 0, 1 | 1 |
| 5 | 0 1 2 3 4 | 2 | 2 |
| 6 | 0 1 2 3 4 5 | 2, 3 | 3 |

"Second middle" and "index `n / 2`" are the same rule. Keep that in mind - it is exactly what the fast pointer's stopping condition will produce.

### Why this is not trivial

With an array, `a[n / 2]` is one line. A linked list gives you neither `n` nor random access. To reach index `n / 2` you must walk there, and to know where "there" is you seem to need `n` first.

### Constraints that matter

- `1` to `100` nodes. The list is **never empty**, so `head` is never `null`.

=== pattern ===
**Fast and slow pointers** (also called the tortoise and the hare).

Two pointers start at `head`. Each round, `slow` moves **one** node and `fast` moves **two**. After `k` rounds:

```text
slow is at index k
fast is at index 2k
```

So `slow` is always exactly halfway to wherever `fast` is. When `fast` reaches the end of the list, `slow` is halfway to the end - which is the middle. You never counted anything.

### The picture

```text
round 0:   [1]  2   3   4   5          slow = 1, fast = 1
            sf

round 1:    1  [2] [3]  4   5          slow = 2, fast = 3
                s   f

round 2:    1   2  [3]  4  [5]         slow = 3, fast = 5
                    s       f          fast has no next -> stop, answer 3
```

### Recognising it

Reach for fast/slow when:

- the answer is a position that is a **fixed fraction** of the length (middle, first third)
- you need to detect whether a list **loops** (Day 31 - fast laps slow)
- you need to split a list into halves (Sort List, Palindrome List, Reorder List)
- the problem asks for "one pass" on a linked list and mentions the length

The mental question:

> Is the position I want defined relative to the end? Then can a pointer moving at a different speed reach the end for me?

A close cousin is the **fixed-gap** pair (Day 33): same speed, but one starts `k` nodes ahead. Speed difference measures *fractions*; a fixed gap measures *offsets*.

=== bruteForce ===
The direct approach: we need `n`, so get `n`.

### Step logic

1. Walk the whole list, counting nodes. Call it `length`.
2. Start again at `head` and take `length / 2` steps.
3. Return the node you are standing on.

### Dry run - odd length

```text
head = 1 -> 2 -> 3 -> 4 -> 5 -> null
```

**Pass 1 - count.**

| step | node | length after |
| ---: | ---: | -----------: |
| - | - | 0 |
| 1 | 1 | 1 |
| 2 | 2 | 2 |
| 3 | 3 | 3 |
| 4 | 4 | 4 |
| 5 | 5 | 5 |
| 6 | null | stop, `length = 5` |

**Pass 2 - walk `5 / 2 = 2` steps.**

| i | node before | `node = node.next` | node after |
| -: | ----------: | :----------------- | ---------: |
| - | - | start at head | 1 |
| 0 | 1 | 1 -> 2 | 2 |
| 1 | 2 | 2 -> 3 | 3 |
| 2 | - | `i < 2` false, stop | 3 |

Return node `3`. Correct.

### Dry run - even length

```text
head = 1 -> 2 -> 3 -> 4 -> 5 -> 6 -> null
```

Pass 1 counts `length = 6`. Pass 2 walks `6 / 2 = 3` steps:

| i | node before | node after |
| -: | ----------: | ---------: |
| 0 | 1 | 2 |
| 1 | 2 | 3 |
| 2 | 3 | 4 |

Return node `4` - the second middle, because integer division `6 / 2 = 3` is the index of the second one.

### Java

```java
class Solution {
    public ListNode middleNode(ListNode head) {

        // Pass 1: learn the length.
        int length = 0;
        for (ListNode node = head; node != null; node = node.next) {
            length++;
        }

        // Pass 2: walk to index length / 2.
        ListNode middle = head;
        for (int i = 0; i < length / 2; i++) {
            middle = middle.next;
        }

        return middle;
    }
}
```

### Complexity

**Time:** `O(n)` - **Space:** `O(1)`

### Where it hurts

Be honest here: the complexity is already `O(n)` time and `O(1)` space, which is optimal. This is not a case where the brute force is hopeless.

The waste is in **how the walking is organised**. Count the steps from the tables: `5 + 2 = 7` for the odd list, `6 + 3 = 9` for the even one. In general `n + n / 2`, about `1.5n`.

And look at *what* pass 1 visits. It walks all the way to the end, learns one number, and throws every node away. Then pass 2 starts over from `head` and re-walks the first half of those same nodes. The first half of the list is traversed **twice, one after the other**, and nothing about the middle is known until the second traversal is done.

The second cost is structural. The algorithm cannot produce any answer until it has seen the end of the list. That matters when the list is a stream or when this is one step inside a bigger algorithm (Sort List splits the list at its middle on every recursive call; Palindrome List finds the middle and then reverses from it).

The question:

> Pass 1 only exists to know where the end is. Can I find the middle at the same moment I find the end?

=== optimization ===
Let a second pointer find the end, and make it move twice as fast as the first.

### The key observation

If `fast` moves two nodes per round and `slow` moves one, then after every round:

```text
index(fast) = 2 * index(slow)
```

So the moment `fast` cannot move any further, `slow` is at half of `fast`'s position. The end-finding pass and the walk-to-the-middle pass happen **at the same time**.

### When exactly to stop

`fast` jumps two nodes: `fast = fast.next.next`. That is only safe if both `fast` and `fast.next` exist. So the loop runs while:

```text
fast != null && fast.next != null
```

- **Odd length:** `fast` lands exactly on the last node. `fast.next` is `null` - stop.
- **Even length:** `fast` jumps past the last node to `null` - stop.

### Dry run - odd length

```text
head = 1 -> 2 -> 3 -> 4 -> 5 -> null
```

| round | slow (start) | fast (start) | fast.next | continue? | slow (end) | fast (end) |
| ----: | -----------: | -----------: | --------: | :-------- | ---------: | ---------: |
| - | - | - | - | init | 1 | 1 |
| 1 | 1 | 1 | 2 | yes | 2 | 3 |
| 2 | 2 | 3 | 4 | yes | 3 | 5 |
| 3 | 3 | 5 | null | **no** | 3 | 5 |

Return `slow` = node `3`. `fast` landed on `1, 3, 5` and `slow` walked the first half exactly once, alongside it - no restart from `head`.

### Dry run - even length

```text
head = 1 -> 2 -> 3 -> 4 -> 5 -> 6 -> null
```

| round | slow (start) | fast (start) | fast.next | continue? | slow (end) | fast (end) |
| ----: | -----------: | -----------: | --------: | :-------- | ---------: | ---------: |
| - | - | - | - | init | 1 | 1 |
| 1 | 1 | 1 | 2 | yes | 2 | 3 |
| 2 | 2 | 3 | 4 | yes | 3 | 5 |
| 3 | 3 | 5 | 6 | yes | 4 | null |
| 4 | 4 | null | - | **no** | 4 | null |

Return `slow` = node `4` - the second middle, with no special case for even lengths. The stopping condition produces index `n / 2` on its own.

### Why it is always `n / 2`

After `k` rounds `slow` is at index `k` and `fast` at `2k`.

- If `n` is odd, the loop stops when `fast` is on the last node, index `n - 1`. So `2k = n - 1`, `k = (n - 1) / 2 = n / 2` in integer division.
- If `n` is even, it stops when `fast` is `null`, one past the end, index `n`. So `2k = n`, `k = n / 2`.

Both cases give `slow` at index `n / 2`. That is the proof, and it is worth being able to say out loud.

### Getting the FIRST middle instead

Some problems (Sort List, Palindrome List) want the **first** middle on even lengths, so the left half is never longer than the right. Start `fast` one node ahead:

```text
slow = head, fast = head.next
```

Now `fast` is at `2k + 1`, and on `1 -> 2 -> 3 -> 4 -> 5 -> 6` the loop stops with `slow` on `3`. On odd lengths the answer does not change. The implementation section shows it.

=== complexity ===
### Time

`fast` reaches the end in about `n / 2` rounds, each doing constant work.

```text
O(n)
```

### Space

Two references.

```text
O(1)
```

### Comparison

| Approach | Time | Extra space | Traversals |
| :------- | ---: | ----------: | ---------: |
| Copy nodes into an array, return `arr[n/2]` | `O(n)` | `O(n)` | 1 |
| Count, then walk `n/2` | `O(n)` | `O(1)` | 2 |
| Fast and slow | **`O(n)`** | **`O(1)`** | **1** |

All three are `O(n)`. "One pass" and "better complexity" are different claims - only make the one that is true.

Be precise about pointer hops too. On `n = 6`, count-then-walk makes `6 + 3 = 9` hops. Fast/slow makes `3` hops with `slow` and `6` node-steps with `fast` - also `9`. The total work is the same. What changes is that both walks happen **together**, so the middle is known **at the moment the end is reached**, with no array and no restart from `head`. That is why it is the version every bigger linked list algorithm reuses.

=== implementation ===
```java
class Solution {
    public ListNode middleNode(ListNode head) {

        ListNode slow = head;   // moves 1 node per round
        ListNode fast = head;   // moves 2 nodes per round

        // fast needs two nodes ahead of it to make a full jump.
        while (fast != null && fast.next != null) {
            slow = slow.next;
            fast = fast.next.next;
        }

        // index(slow) = n / 2 -> the second middle on even lengths.
        return slow;
    }
}
```

### The lines that matter

**1.**

```java
while (fast != null && fast.next != null) {
```

Both checks are required, and the **order** is required. `fast != null` catches the even-length end; `fast.next != null` catches the odd-length end. Java's `&&` short-circuits, so `fast.next` is never read when `fast` is `null`. Write them the other way round and an even-length list throws `NullPointerException`.

**2.**

```java
fast = fast.next.next;
```

Safe only because the loop condition just proved `fast.next` exists. `fast.next.next` itself may be `null` - that is fine, it is how the even case ends.

**3.**

```java
ListNode fast = head;   // moves 2 nodes per round
```

Starting `fast` at `head` is what selects the **second** middle. This is the one line to change for the first-middle variant.

### The first-middle variant

```java
class Solution {
    public ListNode middleNode(ListNode head) {

        if (head == null) {
            return null;
        }

        ListNode slow = head;
        ListNode fast = head.next;   // one ahead -> first middle on even n

        while (fast != null && fast.next != null) {
            slow = slow.next;
            fast = fast.next.next;
        }

        return slow;   // index (n - 1) / 2
    }
}
```

The `null` guard is there because `head.next` would throw on an empty list. LC 876 never passes one, but the helpers you write for Sort List and Palindrome List often do.

### Java notes

- `slow` never needs a null check. It moves only when `fast` could move twice, so it is always strictly behind a node that exists.
- The method returns a reference into the existing list. Nothing is copied; the caller's list is unchanged.

=== edgeCases ===
### Single node

```text
1  ->  node 1
```

`fast.next` is `null` immediately, the loop never runs, `slow` is `head`.

### Two nodes

```text
1 -> 2  ->  node 2
```

One round: `slow = 2`, `fast = null`. Second middle, as asked. (The first-middle variant returns node `1`.)

### Three nodes

```text
1 -> 2 -> 3  ->  node 2
```

One round: `slow = 2`, `fast = 3`. `fast.next` is `null`, stop.

### Four nodes

```text
1 -> 2 -> 3 -> 4  ->  node 3
```

Two rounds: `(2, 3)` then `(3, null)`. The first-middle variant returns node `2`.

### All values equal

```text
7 -> 7 -> 7 -> 7  ->  the THIRD node (index 2)
```

Every node has value `7`, so "return 7" would look right and be wrong. The question asks for a specific node. Fast/slow never reads `val`, so it returns the correct object.

### Maximum length

```text
1 -> 2 -> ... -> 100  ->  node 51 (index 50)
```

`fast` takes `50` rounds to fall off the end.

### Empty list

LC 876 guarantees at least one node. If you reuse the second-middle code elsewhere it returns `null` safely - `fast != null` is false at once. The first-middle variant needs its explicit guard.

=== takeaway ===
> When you see **"middle"**, **"halfway"** or **"split into halves"** on a linked list, think **fast moves two, slow moves one**. When `fast` hits the end, `slow` is the answer.

### The core observation

`index(fast) = 2 * index(slow)` after every round. So whatever moment `fast` reaches the end, `slow` is at half of it. The length you thought you needed is measured implicitly by the distance between two pointers.

### The pattern trigger

```text
     position defined relative to the END of a list
                         |
            +------------+-------------+
            |                          |
     a FRACTION of n              an OFFSET from the end
     (middle, 1/3)                (k-th from end)
            |                          |
   different SPEEDS            same speed, fixed GAP
   slow +1, fast +2            fast starts k ahead
            |                          |
            +------------+-------------+
                         |
                         v
          fast hits null  ->  slow is the answer
```

### The common mistakes

**`fast.next != null && fast != null`.** Wrong order. On an even-length list `fast` becomes `null` and `fast.next` throws.

**Checking only `fast.next != null`.** Same crash, from the other side.

**Returning the wrong middle.** Starting `fast` at `head` gives the second middle; starting it at `head.next` gives the first. Decide which one the problem wants before you write the first line.

**Returning `slow.val`.** The question returns a node.

### What to remember in six months

> Two pointers at speeds 1 and 2 turn "where is the end?" into "where is the middle?" for free.

The same two lines are the first half of Palindrome Linked List (Day 35), Reorder List (LC 143) and Sort List (LC 148), and the same speed difference is what tomorrow's cycle detection runs on. Only the stopping condition changes.
