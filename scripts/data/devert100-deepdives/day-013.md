=== intro ===
Day 12 grouped strings by a **canonical key** - a hashing problem about what two strings have in common. Today goes back to the shape from Day 3: one array, two cursors, and output written over input that has already been read.

> When a problem asks you to rewrite an array in-place into something **no longer than** the original, the first question is not "how do I build the output" but "can the output fit behind the part I have already read?" If it can, a write pointer is all the extra memory you need.

=== problem ===
You are given a `char[]`. Compress it **in-place** using run-length encoding:

- every maximal run of the same character becomes that character, followed by the run's length
- if the run's length is `1`, write only the character - no `1`
- if the length has several digits, each digit is its own `char` (`12` becomes `'1', '2'`)

Return the new length `k`. Only the first `k` slots of `chars` are checked; whatever sits after them does not matter.

```text
chars  = ['a','a','b','b','c','c','c']
result = ['a','2','b','2','c','3']      return 6
```

### Reading the example as runs

| run | character | length | written as | chars used |
| --: | :-------- | -----: | :--------- | ---------: |
| 1 | `a` | 2 | `a 2` | 2 |
| 2 | `b` | 2 | `b 2` | 2 |
| 3 | `c` | 3 | `c 3` | 2 |

Seven characters in, six out. The function returns `6`, and `chars[0..5]` must hold `a 2 b 2 c 3`.

### Two more examples that each test one rule

```text
['a']                                   ->  ['a']                 return 1
['a','b','b','b','b','b','b','b','b','b','b','b','b']
                                        ->  ['a','b','1','2']     return 4
```

The first is the "length 1 writes no count" rule. The second has a run of twelve `b`s, so the count `12` is written as **two** characters, `'1'` then `'2'` - not as the single `char` with value 12.

### The constraints that matter

- `1 <= chars.length <= 2000`, so a count has at most four digits.
- Characters can be letters, digits or symbols. That makes the output ambiguous to decode (`['1','1','1']` compresses to `['1','3']`), but decoding is not asked for - just encode faithfully.
- **Constant extra space** is the follow-up the interviewer is waiting for. A `StringBuilder` solves the problem; it does not solve the follow-up.

### Runs are maximal and local

A run ends the moment the character changes. `['a','a','b','a','a']` is **three** runs - `a2`, `b`, `a2` - not "four a's and a b". This is not counting frequencies; it is walking the array left to right.

=== pattern ===
**Two Pointers - read / write**, the same shape as Day 3's Move Zeroes, with a run-scanning loop inside it.

- `read` scans forward and **finds the end of the current run**. It moves through every character exactly once.
- `write` marks the next free slot of the **compressed output**, which lives at the front of the same array.

What changes from Day 3 is the unit of work. Move Zeroes decided "keep or skip" one element at a time. Here `read` consumes a whole run, and `write` then emits one character plus zero or more digit characters for it.

### Why the output can share the input's storage

The invariant is the same as Day 3's:

> `write` never overtakes `read`. Every slot we write to has already been read.

It holds because a run can only shrink or stay the same size when compressed:

| run length `L` | compressed size `1 + digits` | shrinks by |
| -------------: | ---------------------------: | ---------: |
| 1 | 1 | 0 |
| 2 | 2 | 0 |
| 3 | 2 | 1 |
| 9 | 2 | 7 |
| 10 | 3 | 7 |
| 12 | 3 | 9 |
| 100 | 4 | 96 |

The compressed form of a run never takes more room than the run itself. So after writing run after run, `write` is always at or behind the start of the next unread run.

### Recognising it

Reach for read/write pointers with an inner run-scan when:

- the task is "in-place" and the output is **never longer** than the input
- the output is built from **consecutive groups** of equal elements (compression, dedupe, collapse spaces)
- you are asked to return the new length, with the tail of the array declared irrelevant

The mental question:

> Can I read one whole group, decide what it turns into, and write that at the front - knowing the front is already-read territory?

=== bruteForce ===
Forget in-place for a moment. The obvious approach: build the compressed string in a `StringBuilder`, then copy it back into `chars`.

### Step logic

1. Start `i` at `0`.
2. Remember `ch = chars[i]`. Move `j` forward from `i` while `chars[j] == ch`. The run is `chars[i..j-1]`, its length is `count = j - i`.
3. Append `ch`. If `count > 1`, append `count` (the `StringBuilder` turns `12` into the two characters `"12"` for us).
4. Set `i = j` and repeat until `i` reaches the end.
5. Copy every character of the builder back into `chars[0..]`, and return the builder's length.

### Dry run

```text
chars = ['a','a','b','b','c','c','c']     n = 7
```

**Phase 1 - build the string.**

| step | i | ch | j stops at | count | appended | sb after |
| ---: | -: | :- | ---------: | ----: | :------- | :------- |
| 1 | 0 | `a` | 2 | 2 | `"a" + "2"` | `"a2"` |
| 2 | 2 | `b` | 4 | 2 | `"b" + "2"` | `"a2b2"` |
| 3 | 4 | `c` | 7 | 3 | `"c" + "3"` | `"a2b2c3"` |
| 4 | 7 | - | - | - | loop ends (`i == n`) | `"a2b2c3"` |

**Phase 2 - copy back.**

| k | sb.charAt(k) | chars after |
| -: | :---------- | :---------- |
| 0 | `a` | `[a, a, b, b, c, c, c]` |
| 1 | `2` | `[a, 2, b, b, c, c, c]` |
| 2 | `b` | `[a, 2, b, b, c, c, c]` |
| 3 | `2` | `[a, 2, b, 2, c, c, c]` |
| 4 | `c` | `[a, 2, b, 2, c, c, c]` |
| 5 | `3` | `[a, 2, b, 2, c, 3, c]` |

Return `sb.length() = 6`. The first six slots are `a 2 b 2 c 3`; the trailing `c` at index 6 is outside the answer and ignored.

### Java

```java
class Solution {
    public int compress(char[] chars) {

        StringBuilder sb = new StringBuilder();
        int n = chars.length;
        int i = 0;

        while (i < n) {
            char ch = chars[i];
            int j = i;
            while (j < n && chars[j] == ch) {
                j++;
            }
            int count = j - i;

            sb.append(ch);
            if (count > 1) {
                sb.append(count);       // appends the digits, e.g. "12"
            }
            i = j;
        }

        for (int k = 0; k < sb.length(); k++) {
            chars[k] = sb.charAt(k);
        }
        return sb.length();
    }
}
```

### Why it is correct

Each pass of the outer loop consumes exactly one maximal run (`j` stops at the first different character or the end), and appends exactly that run's encoding. Runs are processed in order, so the builder holds the full compressed string in order.

### Complexity

**Time:** `O(n)` - **Space:** `O(n)` extra

### Where it hurts

Time is already optimal - every character has to be looked at once, so `O(n)` is the floor.

The cost is the **second buffer**. The builder grows to as many as `n` characters (every run of length 1, e.g. `['a','b','c']`), so the extra space is `O(n)` - which is exactly what the follow-up forbids.

And look at Phase 2. It copies characters into slots that, by the time we copy, we have **already finished reading**. Six writes to move data from one buffer to another, when the target slots were free the moment Phase 1 had read past them.

> The builder exists only to hold output until it is safe to write it into `chars`. If it is always already safe, the builder is pure overhead.

=== optimization ===
Point the builder's job at the front of `chars` itself.

### The observation

When we finish scanning a run of length `L` that started at index `start`, we write `1 + digits(L)` characters at `write`. Two facts:

1. `write <= start`, because everything before this run compressed into at most the space it occupied.
2. `1 + digits(L) <= L` for every `L >= 2`, and equals `L` when `L = 1`.

So after writing, `write <= start + L`, which is where the next unread run begins. **The writes never touch a character we still need.** The array can hold the finished output at the front and the unread input behind it, exactly like Day 3:

```text
[  compressed output  |  stale  |  not yet read  ]
                      ^         ^
                    write      read
```

### The algorithm

1. `read = 0`, `write = 0`.
2. While `read < n`:
   - `ch = chars[read]`, `start = read`.
   - Advance `read` while `chars[read] == ch`. Now `count = read - start`.
   - `chars[write++] = ch`.
   - If `count > 1`, write each digit of `count` at `write++`.
3. Return `write`.

### Dry run on the same example

```text
chars = ['a','a','b','b','c','c','c']     n = 7
```

| run | ch | start | read after scan | count | writes | chars after | write |
| --: | :- | ----: | --------------: | ----: | :----- | :---------- | ----: |
| - | - | - | 0 | - | start | `[a, a, b, b, c, c, c]` | 0 |
| 1 | `a` | 0 | 2 | 2 | `chars[0]='a'`, `chars[1]='2'` | `[a, 2, b, b, c, c, c]` | 2 |
| 2 | `b` | 2 | 4 | 2 | `chars[2]='b'`, `chars[3]='2'` | `[a, 2, b, 2, c, c, c]` | 4 |
| 3 | `c` | 4 | 7 | 3 | `chars[4]='c'`, `chars[5]='3'` | `[a, 2, b, 2, c, 3, c]` | 6 |

`read == 7 == n`, the loop ends, return `write = 6`. Same answer as the brute force, no builder.

In this example `write` and `start` happen to be equal at the start of runs 1, 2 and 3, because the first two runs had length 2 and compressed to exactly 2 characters. The next example shows the gap opening up.

### Dry run where `write` falls behind

```text
chars = ['a','b','b','b','b','b','b','b','b','b','b','b','b']     n = 13
```

| run | ch | start | read after scan | count | writes | write |
| --: | :- | ----: | --------------: | ----: | :----- | ----: |
| 1 | `a` | 0 | 1 | 1 | `chars[0]='a'` (no count - length 1) | 1 |
| 2 | `b` | 1 | 13 | 12 | `chars[1]='b'`, `chars[2]='1'`, `chars[3]='2'` | 4 |

Return `4`; `chars[0..3] = a b 1 2`. Run 2 occupied indices `1..12` and its encoding needed only `1..3`. By the time we write index `2` and `3` (overwriting two `b`s), `read` is already at `13` - those `b`s were counted long ago.

### The order that keeps it safe

Scan the **whole** run first, write second. If you wrote `ch` and started emitting digits while still counting, you would not know the count yet - and you would not be able to prove the writes stay behind `read`. Counting first is what makes `count` final and the invariant provable.

### Writing the digits

`count` is at most `2000`, so it has at most four digits. The simplest correct way:

```text
count = 12  ->  Integer.toString(12) = "12"  ->  write '1', then '2'
```

That allocates a tiny string per run, which is constant-bounded (four characters), so the extra space stays `O(1)`. If an interviewer wants zero allocation, write the digits with `% 10` and then reverse that slice in place - shown in the Java notes.

=== complexity ===
### Time

`read` only moves forward and visits each index once across all runs. Writes total at most `n`. Converting a count to digits costs at most four steps per run.

```text
O(n)
```

### Space

Three integers (`read`, `write`, `start`) plus the count's digit string, which is at most four characters.

```text
O(1) extra
```

### Comparison

| Approach | Time | Extra space | Writes into `chars` |
| :------- | ---: | ----------: | :------------------ |
| `StringBuilder` + copy back | `O(n)` | `O(n)` | `k`, after building everything |
| Read / write in place | `O(n)` | **`O(1)`** | `k`, directly |

Both are linear. The difference is entirely the buffer, which is exactly what the follow-up asks you to remove.

=== implementation ===
```java
class Solution {
    public int compress(char[] chars) {

        int n = chars.length;
        int read = 0;   // scans runs
        int write = 0;  // next free slot of the compressed output

        while (read < n) {
            char ch = chars[read];
            int start = read;

            // Consume the whole run before writing anything.
            while (read < n && chars[read] == ch) {
                read++;
            }
            int count = read - start;

            chars[write++] = ch;
            if (count > 1) {
                for (char d : Integer.toString(count).toCharArray()) {
                    chars[write++] = d;
                }
            }
        }

        return write;
    }
}
```

### The lines that matter

**1.**

```java
while (read < n && chars[read] == ch) {
    read++;
}
int count = read - start;
```

The run is fully measured before a single character is written. The bounds check comes first so `chars[read]` is never evaluated at `read == n`.

**2.**

```java
chars[write++] = ch;
if (count > 1) {
```

The character is always written; the count only when it is greater than one. Writing `'1'` for single characters is the most common wrong answer - it turns `['a','b','c']` into `a1b1c1`, length 6 instead of 3.

**3.**

```java
for (char d : Integer.toString(count).toCharArray()) {
    chars[write++] = d;
}
```

A count of `12` becomes the two characters `'1'` and `'2'`. Writing `(char) count` would store the single character with code 12, a control character - it compiles and is wrong.

**4.**

```java
return write;
```

`write` is the number of characters produced - the new length. Returning `read` (always `n`) is a quiet bug that passes no test with any compression in it.

### Java notes

- `chars[write++] = ch` writes at `write`, then increments. The post-increment is what lets one line both place a character and advance the cursor.
- `(char) ('0' + 5)` is `'5'`, but only for a single digit. For multi-digit counts you need every digit, which is why `Integer.toString` is used.
- A zero-allocation digit writer, if asked: write digits least-significant first, then reverse that slice.

```java
class Solution {
    public int compress(char[] chars) {

        int n = chars.length;
        int read = 0;
        int write = 0;

        while (read < n) {
            char ch = chars[read];
            int start = read;
            while (read < n && chars[read] == ch) {
                read++;
            }
            int count = read - start;

            chars[write++] = ch;
            if (count > 1) {
                int from = write;
                while (count > 0) {
                    chars[write++] = (char) ('0' + count % 10);
                    count /= 10;
                }
                // digits came out reversed - flip chars[from..write-1]
                for (int l = from, r = write - 1; l < r; l++, r--) {
                    char t = chars[l];
                    chars[l] = chars[r];
                    chars[r] = t;
                }
            }
        }

        return write;
    }
}
```

The invariant still holds: the reversed digits occupy the same slots as before, all behind `read`.

=== edgeCases ===
### Single character

```text
['a']  ->  ['a']    return 1
```

One run of length 1. Write `a`, no count. `write = 1`.

### No repeats at all

```text
['a','b','c']  ->  ['a','b','c']    return 3
```

Three runs of length 1. Nothing compresses, every character is written onto itself. This is the case that catches solutions writing `'1'`.

### Run of exactly ten

```text
['a' x 10]  ->  ['a','1','0']    return 3
```

The first count with two digits. A solution that writes `'0' + count` stores `':'` (character code 58) instead of `'1','0'`.

### Long run after a single

```text
['a','b' x 12]  ->  ['a','b','1','2']    return 4
```

The LeetCode example. `write` falls nine slots behind `read`.

### Three-digit count

```text
['a' x 100]  ->  ['a','1','0','0']    return 4
```

The digit writer has to handle a zero in the middle and at the end.

### Singles between runs

```text
['a','a','b','c','c']  ->  ['a','2','b','c','2']    return 5
```

The run of length 1 in the middle writes only `b`. Getting this right means the count condition is evaluated per run, not once.

### The same character in separate runs

```text
['a','a','b','a','a']  ->  ['a','2','b','a','2']    return 5
```

Runs are local. `a` appears twice in the output because it appears in two separate runs. A frequency-map solution would wrongly produce `a4b`.

### Digit characters in the input

```text
['1','1','1']  ->  ['1','3']    return 2
```

The input characters are just characters. The output is ambiguous to decode, but that is not this problem's concern.

### Two of the same

```text
['a','a']  ->  ['a','2']    return 2
```

A run of length 2 compresses to 2 characters - no saving, but the rule says write the count, so write it.

=== takeaway ===
> When you see **"in-place" + "consecutive groups" + "return the new length"**, think **read/write pointers with an inner run-scan**. `read` measures a group; `write` emits its encoding at the front.

### The core observation

A run of length `L` compresses to `1 + digits(L)` characters, which is never more than `L`. So the output written so far always fits inside the input already read, and `write` can never overtake `read`. That one inequality is what makes the second buffer unnecessary.

### The pattern trigger

```text
        read at the start of a run
                    |
                    v
      advance read while chars[read] == ch
                    |
                    v
          count = read - start   (final, never changes again)
                    |
                    v
     write ch  ->  if count > 1, write its digits
                    |
                    v
          everything before write is finished output
```

### The common mistakes

**Writing a `'1'` for single characters.** The problem explicitly omits it. `['a','b','c']` must return 3, not 6.

**Writing the count as one `char`.** `(char) count` and `(char) ('0' + count)` both break at `count >= 10`. Each digit is a separate character.

**Counting frequencies instead of runs.** A `HashMap<Character, Integer>` merges separate runs of the same letter. This problem is positional.

**Returning the wrong length.** The answer is `write`, the size of what you produced - not `n`, and not the number of runs.

### What to remember in six months

> A read/write pointer works whenever the output of every group is no bigger than the group itself. Check that inequality first; if it holds, the array is its own buffer.

The same skeleton covers Remove Duplicates from Sorted Array (LC 26 - Day 15, where each run compresses to one element), Remove Duplicates II (LC 80, at most two), and the decode follow-up - which **cannot** be done in place in general, because decoding makes the output longer. That asymmetry is the inequality at work.
