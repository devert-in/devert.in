=== intro ===
Day 17 used two pointers that **close in** from opposite ends of a sorted array. Today both pointers move in the **same direction**, a fixed distance apart - and the gap between them becomes a window.

> When you slide a window one step, almost nothing changes: one element walks in, one walks out. Pay for those two, not for everything in between.

=== problem ===
Given an integer array `nums` and an integer `k`, find the contiguous subarray of length **exactly `k`** with the largest average, and return that average.

```text
nums = [1, 12, -5, -6, 50, 3],  k = 4
```

There are only three windows of length 4:

| start | window | sum | average |
| ----: | :----- | --: | ------: |
| 0 | `[1, 12, -5, -6]` | 2 | 0.5 |
| 1 | `[12, -5, -6, 50]` | 51 | 12.75 |
| 2 | `[-5, -6, 50, 3]` | 42 | 10.5 |

The answer is `12.75`.

### Average is a disguise

Every window has the same length `k`, so dividing by `k` never changes which window wins. The window with the largest **average** is the window with the largest **sum**.

```text
maximise  sum / k   <=>   maximise  sum      (k is a fixed positive number)
```

So work entirely in integers, find the best sum, and divide exactly **once**, at the very end. That removes floating-point from the loop altogether.

### How many windows are there?

With `n` elements and window size `k`, the first window starts at `0` and the last starts at `n - k`. That is `n - k + 1` windows. For the example: `6 - 4 + 1 = 3`.

### Constraints that matter

- `1 <= k <= n <= 10^5` - at least one full window always exists.
- `-10^4 <= nums[i] <= 10^4` - values can be **negative**, so the best sum can be negative. That single fact decides how the running maximum must be initialised.
- The largest possible sum is `10^5 * 10^4 = 10^9`, which fits in an `int` (max about `2.1 * 10^9`).

=== pattern ===
**Fixed-size Sliding Window.**

A window is a contiguous range `[left, right]` that you move across the array. When the size is fixed at `k`, the window is completely described by its start, and moving it one step to the right does exactly two things:

```text
before:   [ 1 | 12  -5  -6 ]  50   3        sum = 2
after:      1  [ 12  -5  -6 | 50 ]  3        sum = 2 - 1 + 50 = 51
            ^                  ^
         leaves             enters
```

The three middle elements `12, -5, -6` are in both windows. Their sum did not change, so there is no reason to add them up again.

```text
newSum = oldSum + entering - leaving
```

That is the whole pattern. Everything else is bookkeeping.

### Why it belongs to "sliding window"

Three properties together make this a sliding window problem:

1. The answer is about a **contiguous** range.
2. Consecutive candidate ranges **overlap** heavily.
3. The quantity being tracked (a sum) can be **updated incrementally** - you can add an element and remove an element in `O(1)`.

If any one of those fails, the window does not help. Non-contiguous picks have no window. Non-overlapping chunks share nothing to reuse. A quantity like "median of the window" cannot be updated by one add and one remove in `O(1)` (it needs a heap or a balanced tree).

### Recognising it

Reach for a fixed window when the problem says:

- "subarray / substring of size `k`" or "every `k` consecutive elements"
- "maximum / minimum / average of each window"
- "count windows of length `k` that satisfy ..."

The mental question:

> When the window moves one step, what changes? If the answer is "one element in, one element out", carry the state forward instead of rebuilding it.

=== bruteForce ===
Pretend we have not noticed the overlap. The obvious plan:

1. For every legal start `i` from `0` to `n - k`:
2. Add up `nums[i]` through `nums[i + k - 1]` into `sum`.
3. If `sum` beats `best`, remember it.
4. At the end, return `best / k` as a `double`.

### Dry run

```text
nums = [1, 12, -5, -6, 50, 3],  k = 4
best starts at Integer.MIN_VALUE (written -inf below)
```

Every addition, every variable:

| i | j | nums[j] | sum after `sum += nums[j]` | window done? | best |
| -: | -: | ------: | -------------------------: | :----------- | ---: |
| 0 | 0 | 1 | 1 | no | -inf |
| 0 | 1 | 12 | 13 | no | -inf |
| 0 | 2 | -5 | 8 | no | -inf |
| 0 | 3 | -6 | 2 | yes, `2 > -inf` | 2 |
| 1 | 1 | 12 | 12 | no | 2 |
| 1 | 2 | -5 | 7 | no | 2 |
| 1 | 3 | -6 | 1 | no | 2 |
| 1 | 4 | 50 | 51 | yes, `51 > 2` | 51 |
| 2 | 2 | -5 | -5 | no | 51 |
| 2 | 3 | -6 | -11 | no | 51 |
| 2 | 4 | 50 | 39 | no | 51 |
| 2 | 5 | 3 | 42 | yes, `42 < 51` | 51 |

```text
best = 51   ->   51 / 4.0 = 12.75
```

Correct. Note that `sum` is reset to `0` at the start of every new `i` - that reset is exactly the work we are about to stop doing.

### Java

```java
class Solution {
    public double findMaxAverage(int[] nums, int k) {

        int n = nums.length;
        int best = Integer.MIN_VALUE;

        for (int i = 0; i + k <= n; i++) {

            int sum = 0;
            for (int j = i; j < i + k; j++) {
                sum += nums[j];
            }

            best = Math.max(best, sum);
        }

        return (double) best / k;
    }
}
```

### Complexity

**Time:** `O((n - k + 1) * k)`, which is `O(n * k)` - **Space:** `O(1)`

The worst case is `k` around `n / 2`: about `n/2` windows of `n/2` additions each, so `O(n^2)` in the worst case. With `n = 10^5` that is 2.5 billion additions - far too slow.

### Where it hurts

Line up the additions the table performed, one row per window:

```text
i = 0:   1 + 12 + (-5) + (-6)
i = 1:       12 + (-5) + (-6) + 50
i = 2:            (-5) + (-6) + 50 + 3
```

The pair `(-5) + (-6)` is added **three** times. `12` is added twice. Of the 12 additions in the table, only 6 distinct elements exist - half the work is repetition.

In general consecutive windows share `k - 1` elements. The brute force throws the shared part away and rebuilds it, so it does `k` additions per window when only **two** values actually changed.

> The window moved one step. Why am I touching all `k` elements?

=== optimization ===
### The key observation

Window `i` and window `i + 1` differ by exactly two elements:

```text
window i      =  nums[i]  nums[i+1] ... nums[i+k-1]
window i + 1  =           nums[i+1] ... nums[i+k-1]  nums[i+k]
```

So:

```text
sum(i + 1) = sum(i) - nums[i] + nums[i + k]
```

If we index by the **entering** element `r` instead, the element leaving is `r - k`:

```text
sum += nums[r] - nums[r - k]
```

### Building the algorithm

1. Add up the first window, `nums[0..k-1]`, the ordinary way. That is `sum`, and also the first value of `best`.
2. For `r` from `k` to `n - 1`: slide - add `nums[r]`, subtract `nums[r - k]` - then update `best`.
3. Return `best / k` as a `double`.

Step 1 costs `k` additions once. Step 2 costs two operations per window. Total about `n`.

### Dry run on the same example

```text
nums = [1, 12, -5, -6, 50, 3],  k = 4
```

**Step 1 - build the first window:**

| i | nums[i] | sum |
| -: | ------: | --: |
| 0 | 1 | 1 |
| 1 | 12 | 13 |
| 2 | -5 | 8 |
| 3 | -6 | 2 |

```text
sum = 2,  best = 2      (window [1, 12, -5, -6])
```

**Step 2 - slide:**

| r | entering `nums[r]` | leaving `nums[r-k]` | sum before | sum after | window | best |
| -: | -----------------: | ------------------: | ---------: | --------: | :----- | ---: |
| 4 | 50 | 1 | 2 | 2 + 50 - 1 = **51** | `[12, -5, -6, 50]` | 51 |
| 5 | 3 | 12 | 51 | 51 + 3 - 12 = **42** | `[-5, -6, 50, 3]` | 51 |

```text
best = 51   ->   51 / 4.0 = 12.75
```

Same answer as the brute force. The brute force did 12 additions; this did 4 to build plus 2 slides of 2 operations each, 8 in total - and the gap widens with `k`. For `n = 10^5, k = 5 * 10^4` it is about `10^5` operations instead of `2.5 * 10^9`.

### Why `best` starts at the first window, not at 0

Try `best = 0` on an all-negative input:

```text
nums = [-1, -2, -3],  k = 2
windows: [-1, -2] = -3,  [-2, -3] = -5
```

| step | sum | best (init 0) | best (init first window) |
| :--- | --: | ------------: | -----------------------: |
| first window | -3 | 0 | -3 |
| slide r = 2 | -5 | 0 | -3 |

With `best = 0` the answer comes out as `0.0` - the average of a window that does not exist. The correct answer is `-3 / 2 = -1.5`. Initialising from a real window (or from `Integer.MIN_VALUE`) is the fix; the first window is cleaner because it is a value we actually observed.

=== complexity ===
### Time

Building the first window touches `k` elements. Each of the remaining `n - k` slides does one add, one subtract and one comparison.

```text
k + (n - k) = n   ->   O(n)
```

### Space

Three integers: `sum`, `best`, and the loop index. No array proportional to the input.

```text
O(1)
```

### Comparison

| Approach | Time | Space | Work per window |
| :------- | ---: | ----: | --------------: |
| Re-sum every window | `O(n * k)` | `O(1)` | `k` |
| Prefix sums array | `O(n)` | `O(n)` | 1 subtraction |
| Sliding window | **`O(n)`** | **`O(1)`** | 2 |

The prefix-sum route (`sum(i..i+k-1) = prefix[i+k] - prefix[i]`) is also `O(n)` and is worth naming in an interview - but it spends an `O(n)` array to answer arbitrary range queries, and here the windows are only ever visited left to right. The window carries just the one range it needs.

=== implementation ===
```java
class Solution {
    public double findMaxAverage(int[] nums, int k) {

        // 1. Sum of the first window, nums[0..k-1].
        int sum = 0;
        for (int i = 0; i < k; i++) {
            sum += nums[i];
        }

        // 2. Best starts as a REAL window, never as 0 - sums can be negative.
        int best = sum;

        // 3. Slide: nums[r] enters on the right, nums[r - k] leaves on the left.
        for (int r = k; r < nums.length; r++) {
            sum += nums[r] - nums[r - k];
            best = Math.max(best, sum);
        }

        // 4. Divide once, as a double.
        return (double) best / k;
    }
}
```

### The lines that matter

**1.**

```java
int best = sum;
```

The running maximum is seeded with a window that exists. Seeding with `0` silently returns `0.0` whenever every window is negative.

**2.**

```java
sum += nums[r] - nums[r - k];
```

The entire optimisation is this one line. `r` is the index **entering**; the window is `[r - k + 1, r]`, so the index that just fell off the left is `r - k`.

**3.**

```java
return (double) best / k;
```

The cast applies to `best` before the division, so Java does floating-point division. Write `(double) (best / k)` instead and the integer division happens first: `51 / 4` is `12`, and you return `12.0`.

### The general fixed-window template

The same three moves - build, slide, record - solve every fixed-size window problem. Only what you add, remove, and record changes:

```text
build window of size k
record(window)
for r = k .. n-1:
    add    nums[r]
    remove nums[r - k]
    record(window)
```

### The follow-up: when the size is not fixed

LeetCode 209 asks for the **shortest** subarray whose sum is at least `target` (all values positive). Now the window has no fixed size - it grows on the right until valid, then shrinks from the left while it stays valid. This is the variable window that the next four days are built on:

```java
class Solution {
    public int minSubArrayLen(int target, int[] nums) {

        int left = 0, sum = 0, best = Integer.MAX_VALUE;

        for (int right = 0; right < nums.length; right++) {
            sum += nums[right];                 // grow

            while (sum >= target) {             // valid: try to shrink
                best = Math.min(best, right - left + 1);
                sum -= nums[left];
                left++;
            }
        }

        return best == Integer.MAX_VALUE ? 0 : best;
    }
}
```

The difference is when the left edge moves. The fixed window removes exactly one element on every step, unconditionally; the variable window removes inside a `while`, only for as long as a condition holds. Because every value is positive, shrinking can only lower `sum`, which is what makes "shrink while valid" safe.

### Java notes

- `int` is safe for `sum` here: `|sum| <= 10^5 * 10^4 = 10^9 < 2^31 - 1`. If the constraints were larger, use `long`.
- `Math.max(int, int)` returns an `int` - no hidden widening.
- LeetCode accepts answers within `10^-5` of the expected value, so the final `double` division is precise enough. Dividing inside the loop would also work, but it adds `n` floating-point divisions for nothing.

=== edgeCases ===
### Every window is negative

```text
nums = [-1, -2, -3],  k = 2  ->  -1.5
```

The windows sum to `-3` and `-5`. With `best` seeded from the first window the answer is `-3 / 2 = -1.5`. Seeding with `0` would return `0.0`.

### k equals n - one window only

```text
nums = [1, 2, 3, 4],  k = 4  ->  2.5
```

The build loop sums everything (`10`), the slide loop runs zero times (`r = 4` is not `< 4`). Answer `10 / 4 = 2.5`.

### Single element

```text
nums = [5],  k = 1  ->  5.0
```

The smallest legal input. Build gives `sum = 5`, no slides.

### k = 1 - the window is just the maximum element

```text
nums = [3, -1, 7, 2],  k = 1  ->  7.0
```

Each slide adds `nums[r]` and subtracts `nums[r - 1]`, so `sum` is always exactly the current element. The answer is the largest element.

### The best window is the last one

```text
nums = [1, 1, 1, 9],  k = 2  ->  5.0
```

Windows: `2, 2, 10`. The best is only found on the final slide - a loop bound of `r < nums.length - 1` would miss it.

### All equal values

```text
nums = [2, 2, 2],  k = 2  ->  2.0
```

Every window ties. `Math.max` keeps the same value; no special handling for ties.

### Integer division trap

```text
nums = [1, 2],  k = 2  ->  1.5
```

`(double) best / k` gives `3 / 2.0 = 1.5`. The mis-parenthesised `(double) (best / k)` gives `1.0`.

### Largest possible sum

```text
nums = [10000, 10000, ..., 10000]  (n = 100000),  k = 100000  ->  10000.0
```

`sum = 10^9`, which still fits in an `int`. This is the boundary the constraint was chosen around.

=== takeaway ===
> When you see **"contiguous subarray of size k"**, think **fixed sliding window**: build the first window, then each step add what enters and subtract what leaves.

### The core observation

Consecutive windows of size `k` share `k - 1` elements. Recomputing them is pure waste; the only new information per step is one element in and one element out. And since every window has the same length, maximising the average is the same as maximising the sum - so stay in integers and divide once.

### The pattern trigger

```text
        "subarray of length k" / "every k consecutive"
                          |
                          v
          can the quantity be updated by
          +1 element in, -1 element out, in O(1)?
                 /                    \
               yes                     no (median, mode...)
                |                       |
                v                       v
   build first window,          window + heap / tree /
   then slide:                  monotonic deque
   sum += nums[r] - nums[r-k]
```

### The common mistakes

**Seeding `best` with `0`.** Works on every positive test and fails the first all-negative one. Seed from the first window.

**Off-by-one on the leaving index.** With `r` as the entering index, the leaving index is `r - k`, not `r - k + 1` (that one is still in the window).

**Dividing before casting.** `(double) (best / k)` truncates first. Cast the operand, not the result.

**Dividing inside the loop.** Not wrong, just pointless - and comparing doubles invites precision questions you never needed to answer.

### What to remember in six months

> A fixed window is a running sum with a tail. Every step: `+ new`, `- old`, record.

It is the warm-up for the variable window, where the size is decided by a condition instead of `k`.
