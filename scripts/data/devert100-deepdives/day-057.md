=== intro ===
Week 9 opens the **search tree** half of the trees block. Days 54-56 treated a tree as pure shape; from today the *values* carry an ordering rule, and that rule is something you can exploit - or, today, verify.

Yesterday information flowed **up**: children reported heights to their parent. Today it flows **down**: every ancestor imposes a limit, and a node has to respect all of them at once.

> When a node's validity depends on its ancestors, not just its parent, pass the constraint down as an argument. A window `(low, high)` that narrows at each step carries everything the ancestors require.

=== problem ===
Given the `root` of a binary tree, decide whether it is a **valid binary search tree**:

- every value in a node's **left subtree** is **strictly less** than the node's value
- every value in a node's **right subtree** is **strictly greater** than the node's value
- both subtrees are themselves valid BSTs

```text
      2
     / \
    1   3

root   = [2, 1, 3]
output = true
```

```text
      5
     / \
    1   4
       / \
      3   6

root   = [5, 1, 4, null, null, 3, 6]
output = false      (4 is in 5's right subtree but 4 < 5)
```

### The word that makes it non-trivial: subtree

The rule is about **all descendants**, not just the immediate children. This tree passes every parent-child check and is still invalid:

```text
      5
     / \
    4   6
       / \
      3   7

root = [5, 4, 6, null, null, 3, 7]
```

| node | left child < node? | right child > node? |
| ---: | :----------------- | :------------------ |
| 5 | 4 < 5, yes | 6 > 5, yes |
| 6 | 3 < 6, yes | 7 > 6, yes |

Every local check passes. But `3` sits in the **right subtree of 5**, so it must be greater than 5 - and it is not. Answer: `false`.

That is the bug in the most common wrong solution.

### Constraints that matter

| fact | consequence |
| :--- | :---------- |
| `1 <= n <= 10^4` | quadratic is uncomfortable |
| values span the **full** `int` range, `-2^31` to `2^31 - 1` | `Integer.MIN_VALUE` / `MAX_VALUE` cannot be used as "no limit" sentinels |
| **strictly** less / greater | duplicates anywhere in an ancestor chain make the tree invalid |

=== pattern ===
**DFS with bounds** (top-down constraint passing). The equivalent alternative is **inorder traversal must be strictly increasing**.

### Why bounds

Walk down from the root and watch what each step promises:

```text
      5                        5 allows anything:        (-inf, +inf)
       \
        6                      right of 5:   > 5         (5, +inf)
       /
      3                        left of 6:    < 6         (5, 6)
```

Every time you go **left**, the parent's value becomes a new **upper** limit. Every time you go **right**, it becomes a new **lower** limit. The window only ever narrows, and the current window is exactly the set of values allowed by *every* ancestor at once - because the tightest limit on each side is the one that matters, and the window always holds the tightest.

So instead of looking up and down the tree, each node needs only two numbers handed to it by its parent.

### Why inorder also works

Inorder visits left subtree, node, right subtree. For a BST that means every value is visited after everything smaller and before everything larger - so a valid BST produces a **strictly increasing** sequence, and any tree that produces one is a valid BST. Checking "each value is greater than the previous one" is a single pass.

### Recognising it

Reach for constraint passing when:

- a node must satisfy a condition imposed by **all** its ancestors, not just its parent
- the condition is a range, a parity, a path sum, a depth - something an ancestor can compute and hand down
- a bottom-up approach would need to return several summary values (min, max, valid) from each subtree

The mental question:

> What does this node need to know about its ancestors? Can that be summarised in one or two values I pass down as arguments?

=== bruteForce ===
Translate the definition word for word. "Every value in the left subtree is less than the node" means "the **largest** value in the left subtree is less than the node". So compute that maximum, and the minimum of the right subtree, at every node.

### Step logic

1. `isValidBST(node)`: if `node` is `null`, return `true`.
2. If there is a left subtree, compute `maxOf(node.left)` by walking all of it. If it is `>= node.val`, return `false`.
3. If there is a right subtree, compute `minOf(node.right)` the same way. If it is `<= node.val`, return `false`.
4. Return `isValidBST(node.left) && isValidBST(node.right)`.

### Dry run

A valid tree, so the brute force cannot stop early and every visit shows:

```text
          8
        /   \
       4     12
      / \   /  \
     2   6 10   14

root = [8, 4, 12, 2, 6, 10, 14]
```

Preorder over nodes; "scan visits" counts nodes touched by that row's `maxOf` and `minOf` calls.

| step | node | `maxOf(left)` | `< node`? | `minOf(right)` | `> node`? | scan visits |
| ---: | ---: | ------------: | :-------- | -------------: | :-------- | ----------: |
| 1 | 8 | max(4, 2, 6) = 6 | yes | min(12, 10, 14) = 10 | yes | 3 + 3 = 6 |
| 2 | 4 | 2 | yes | 6 | yes | 1 + 1 = 2 |
| 3 | 2 | - | - | - | - | 0 |
| 4 | 6 | - | - | - | - | 0 |
| 5 | 12 | 10 | yes | 14 | yes | 1 + 1 = 2 |
| 6 | 10 | - | - | - | - | 0 |
| 7 | 14 | - | - | - | - | 0 |

All checks pass:

```text
answer = true
```

Seven nodes, ten scan visits on top of the seven checks. Nodes `2` and `6` were scanned in step 1 and again in step 2.

### Java

```java
class Solution {
    public boolean isValidBST(TreeNode root) {

        if (root == null) return true;

        if (root.left != null && maxOf(root.left) >= root.val) return false;
        if (root.right != null && minOf(root.right) <= root.val) return false;

        return isValidBST(root.left) && isValidBST(root.right);
    }

    private int maxOf(TreeNode node) {
        if (node == null) return Integer.MIN_VALUE;
        return Math.max(node.val, Math.max(maxOf(node.left), maxOf(node.right)));
    }

    private int minOf(TreeNode node) {
        if (node == null) return Integer.MAX_VALUE;
        return Math.min(node.val, Math.min(minOf(node.left), minOf(node.right)));
    }
}
```

The `!= null` guards matter: without them a `null` left child would report `Integer.MIN_VALUE` as its maximum, and a node whose value *is* `Integer.MIN_VALUE` would fail `MIN_VALUE >= MIN_VALUE`.

### Complexity

**Time:** `O(n^2)` worst case (skewed), `O(n log n)` balanced - **Space:** `O(h)` recursion stack

### Where it hurts

Every node is scanned once by each of its ancestors' `maxOf` / `minOf` calls. On a chain that is `n(n-1)/2` scans:

```text
1
 \
  2
   \
    3
     \
      4

at 1: minOf scans 2, 3, 4      3
at 2: minOf scans 3, 4         2
at 3: minOf scans 4            1
                              ----
                               6
```

The deeper problem is the **direction** of the work. Each node looks *down* at its entire subtree to learn its extremes, and every ancestor repeats that look. But the information actually needed is about the *path above* the node: which ancestors it sits left of, which it sits right of. That path is already being walked by the recursion - it just is not being remembered.

What if each call carried the ancestors' limits down with it, so a node could be checked in `O(1)`?

=== optimization ===
### The observation

A node at the end of a root-to-node path must be:

- **less than** every ancestor it lies to the **left** of
- **greater than** every ancestor it lies to the **right** of

Only the tightest of each matters - the smallest "must be less than" and the largest "must be greater than". Call them `high` and `low`. They are updated in `O(1)` per step:

```text
go left from node:   high = node.val   (low unchanged)
go right from node:  low  = node.val   (high unchanged)
```

Why is it always safe to just *replace* the bound rather than take a min/max? Because the child's value already passed `low < val < high` at the parent, so the parent's value is automatically tighter than the bound it replaces.

### Deriving the function

```text
valid(node, low, high):
    if node is null:                       true
    if not (low < node.val < high):        false
    return valid(node.left,  low,      node.val)
       and valid(node.right, node.val, high)

answer = valid(root, -infinity, +infinity)
```

### Dry run - same tree

```text
          8
        /   \
       4     12
      / \   /  \
     2   6 10   14
```

Preorder, each node checked against the window it was handed:

| step | node | low | high | `low < val < high`? | passes to left | passes to right |
| ---: | ---: | --: | ---: | :------------------ | :------------- | :-------------- |
| 1 | 8 | -inf | +inf | yes | (-inf, 8) | (8, +inf) |
| 2 | 4 | -inf | 8 | yes | (-inf, 4) | (4, 8) |
| 3 | 2 | -inf | 4 | yes | (-inf, 2) | (2, 4) |
| 4 | 6 | 4 | 8 | yes | (4, 6) | (6, 8) |
| 5 | 12 | 8 | +inf | yes | (8, 12) | (12, +inf) |
| 6 | 10 | 8 | 12 | yes | (8, 10) | (10, 12) |
| 7 | 14 | 12 | +inf | yes | (12, 14) | (14, +inf) |

```text
answer = true
```

Seven checks, each `O(1)`. No scans at all.

Look at step 4: node `6` has window `(4, 8)`. The `4` came from its parent; the `8` came from its **grandparent** - a limit the local parent-child check would never see.

### Dry run - the trap tree

```text
      5
     / \
    4   6
       / \
      3   7
```

| step | node | low | high | `low < val < high`? | result |
| ---: | ---: | --: | ---: | :------------------ | :----- |
| 1 | 5 | -inf | +inf | yes | recurse |
| 2 | 4 | -inf | 5 | yes | recurse (children null) |
| 3 | 6 | 5 | +inf | yes | recurse |
| 4 | 3 | 5 | 6 | **no**, 3 is not > 5 | **false** |

```text
answer = false
```

The lower bound `5` travelled two steps down - through `6` - to reach `3`. That inherited bound is exactly what the parent-only check lacks.

### What stands in for infinity

Node values can be `Integer.MIN_VALUE` or `Integer.MAX_VALUE`. Starting with `int` bounds of those values would reject a legal single-node tree `[2147483647]`, since `2147483647 < 2147483647` is false. Use `long` bounds starting at `Long.MIN_VALUE` / `Long.MAX_VALUE`: every `int` lies strictly inside them.

=== complexity ===
### Time

Each node is checked once, in `O(1)`.

```text
O(n)
```

### Space

Recursion depth equals the height, with two `long`s per frame.

```text
O(h)
```

`O(log n)` balanced, `O(n)` on a chain.

### Comparison

| Approach | Time | Space | Notes |
| :------- | ---: | ----: | :---- |
| Parent-child check only | `O(n)` | `O(h)` | **wrong** - misses grandparent limits |
| Subtree max / min at every node | `O(n^2)` worst | `O(h)` | correct, repeated scans |
| Bounds passed down | **`O(n)`** | `O(h)` | one `O(1)` check per node |
| Inorder, strictly increasing | **`O(n)`** | `O(h)` | same cost, different idea |

A third `O(n)` route exists: post-order that **returns** `(min, max, valid)` from each subtree - yesterday's bottom-up shape. It works, but each call returns three values; passing two bounds down is simpler.

=== implementation ===
```java
class Solution {
    public boolean isValidBST(TreeNode root) {
        return valid(root, Long.MIN_VALUE, Long.MAX_VALUE);
    }

    // Every value in this subtree must lie strictly inside (low, high).
    private boolean valid(TreeNode node, long low, long high) {
        if (node == null) return true;

        if (node.val <= low || node.val >= high) return false;

        return valid(node.left, low, node.val)      // going left: node.val is the new ceiling
            && valid(node.right, node.val, high);   // going right: node.val is the new floor
    }
}
```

### The lines that matter

**1.**

```java
return valid(root, Long.MIN_VALUE, Long.MAX_VALUE);
```

`long`, not `int`. With `Integer.MIN_VALUE` as the starting floor, a node holding `Integer.MIN_VALUE` would fail `val <= low`. Widening to `long` makes the sentinels unreachable by any real value.

**2.**

```java
if (node.val <= low || node.val >= high) return false;
```

`<=` and `>=`: equality fails. A BST here has no duplicates, so `[2, 2]` and `[2, null, 2]` are both invalid.

**3.**

```java
return valid(node.left, low, node.val)      // going left: node.val is the new ceiling
    && valid(node.right, node.val, high);   // going right: node.val is the new floor
```

Each child keeps one inherited bound and replaces the other with its parent's value. That inherited bound is what the parent-child check misses. `&&` short-circuits, so once the left subtree fails, the right is never explored.

### The inorder version

The other standard answer: an iterative inorder traversal that remembers the previous value.

```java
class Solution {
    public boolean isValidBST(TreeNode root) {

        Deque<TreeNode> stack = new ArrayDeque<>();
        TreeNode cur = root;
        Integer prev = null;                       // null = nothing visited yet

        while (cur != null || !stack.isEmpty()) {
            while (cur != null) {                  // slide to the leftmost unvisited node
                stack.push(cur);
                cur = cur.left;
            }
            cur = stack.pop();

            if (prev != null && cur.val <= prev) return false;
            prev = cur.val;

            cur = cur.right;
        }

        return true;
    }
}
```

On the trap tree the inorder sequence is `4, 5, 3, 6, 7` - and `3 <= 5` fails at the third value. Using `Integer prev = null` instead of `int prev = Integer.MIN_VALUE` dodges the same overflow trap the `long` bounds dodge.

### Java notes

- `node.val <= low` compares an `int` with a `long`; Java widens the `int` automatically. No cast needed.
- In the inorder version, `cur.val <= prev` unboxes `prev`. That is safe only because `prev != null` is checked first on the same line - `&&` evaluates left to right.
- Recursion depth is up to `10^4` on a chain. LeetCode's stack handles it; in production code on untrusted input, prefer the iterative inorder version.

### Single node

```text
root = [1]  ->  true
```

### Simple valid tree

```text
root = [2, 1, 3]  ->  true
```

### LeetCode's invalid example

```text
root = [5, 1, 4, null, null, 3, 6]  ->  false
```

Fails at `4`: window `(5, +inf)`, and `4` is not greater than 5.

### Grandparent violation (the parent-child trap)

```text
root = [5, 4, 6, null, null, 3, 7]  ->  false
```

Every parent-child pair is ordered correctly. `3` breaks the lower bound inherited from `5`.

### Duplicate as a left child

```text
root = [1, 1]  ->  false
```

`1` is not strictly less than `1`.

### Duplicate as a right child

```text
root = [1, null, 1]  ->  false
```

### All values equal

```text
root = [2, 2, 2]  ->  false
```

### Extreme values

```text
root = [2147483647]                        ->  true
root = [-2147483648]                       ->  true
root = [-2147483648, null, 2147483647]     ->  true
```

All three break a solution that uses `Integer.MIN_VALUE` / `Integer.MAX_VALUE` as its "no limit" values. With `long` bounds they pass.

### A chain that is valid

```text
root = [1, null, 2, null, 3, null, 4]  ->  true
```

Every step goes right, so the floor rises `1, 2, 3` and the ceiling stays `+inf`. Valid, if badly unbalanced - and the brute force's `O(n^2)` shape.

=== takeaway ===
> When you see **"every node in the subtree must be less / greater than ..."**, think **pass a `(low, high)` window down the recursion**: left child gets `(low, val)`, right child gets `(val, high)`.

### The core observation

A node's legal range is set by its whole ancestor path, but only the tightest bound on each side matters, and both can be updated in `O(1)` per step. So the ancestors' constraints fit in two arguments, and each node is checked once. Equivalently: a tree is a valid BST exactly when its inorder sequence is strictly increasing.

### The pattern trigger

```text
     validity depends on ALL ancestors, not just the parent
                         |
                         v
          valid(node, low, high):
              null                    -> true
              val outside (low, high) -> false
                         |
          left child:   (low,  val)     <- val becomes the ceiling
          right child:  (val,  high)    <- val becomes the floor
                         |
          start: (-inf, +inf) using long, not int
```

### The common mistakes

**Checking only `left.val < node.val < right.val`.** Passes on every tree where the violation is a grandparent's - and that is the whole point of the problem.

**Using `Integer.MIN_VALUE` / `MAX_VALUE` as infinity.** LeetCode's tests include those exact values. Use `long`, or nullable `Integer` bounds.

**Allowing equality.** `<` vs `<=` decides whether `[1, 1]` is valid. Here it is not.

**Using a static `prev` in the inorder version** and forgetting to reset it between test cases. Keep it local, or reset it in the public method.

### What to remember in six months

> Information can flow **up** a tree (return values) or **down** it (arguments). Heights and diameters flow up. Constraints from ancestors flow down.

Pick the direction before writing a line. Top-down constraint passing also solves Path Sum (LC 112: pass the remaining sum), Sum Root to Leaf Numbers (LC 129: pass the number so far), Count Good Nodes (LC 1448: pass the max so far), and Recover Binary Search Tree (LC 99), which uses the inorder view to find the two out-of-order values.
