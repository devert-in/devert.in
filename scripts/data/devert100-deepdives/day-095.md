=== intro ===
Days 93 and 94 were knapsack: a budget, items in or out, a table indexed by capacity. Today the table is indexed by **position**, and the question at each position is not "in or out?" but "what is the best chain that **ends here**?".

> The habit for today: when a subsequence problem feels slippery, pin one end down. "The longest increasing subsequence" is hard to grab; "the longest one that ends at index `i`" is one loop. And then, once the DP works, look at what it stores and ask whether it is storing too much - that question is how `O(n^2)` becomes `O(n log n)`.

=== problem ===
Given an integer array `nums`, return the length of the **longest strictly increasing subsequence**.

A *subsequence* keeps the original order but may skip elements. It does not have to be contiguous.

```text
nums = [10, 9, 2, 5, 3, 7, 101, 18]   ->  4
```

| a longest increasing subsequence | indices | length |
| :------------------------------- | :------ | -----: |
| [2, 5, 7, 101] | 2, 3, 5, 6 | 4 |
| [2, 3, 7, 18] | 2, 4, 5, 7 | 4 |
| [2, 3, 7, 101] | 2, 4, 5, 6 | 4 |

Several subsequences tie; the problem only asks for the **length**.

### Two words that change the answer

**Subsequence, not subarray.** `[2, 5, 7, 101]` skips `3` between `5` and `7`. If you only looked at contiguous runs, the longest increasing one is `[2, 5]` or `[3, 7, 101]` - length 3, the wrong answer.

**Strictly** increasing. `[7, 7, 7, 7]` has answer `1`, not `4`. Equal neighbours do not extend a chain. This one word decides a `<` versus `<=` in the brute force and a lower-bound versus upper-bound in the fast version.

### Constraints that matter

`1 <= nums.length <= 2500`, values in `[-10^4, 10^4]`. An `O(n^2)` solution (about `6 * 10^6` steps) passes. The follow-up asks for `O(n log n)`, and that is the version interviewers probe.

=== pattern ===
**1D DP on "ends at `i`"**, then **patience sorting** (a sorted `tails` array with binary search).

### Why "ends at `i`"

The overall LIS ends *somewhere*. If, for every index `i`, you knew the length of the longest increasing subsequence that **ends exactly at `nums[i]`**, the answer is just the largest of those.

And "ends at `i`" has clean structure. Such a chain is either `nums[i]` alone, or some chain ending at an earlier `j` with `nums[j] < nums[i]`, with `nums[i]` stuck on the end:

```text
dp[i] = 1 + max( dp[j]  for j < i with nums[j] < nums[i] )     (or 1 if no such j)
answer = max over all i of dp[i]
```

That is optimal substructure: the best chain ending at `i` is built from the best chain ending at some valid `j`.

### Why patience sorting then works

The `O(n^2)` DP asks, for each new element, "which earlier chain can I extend?". But among all chains of the same length, only the one with the **smallest last element** matters - it is the easiest to extend. Keep just that one number per length, and the lookup becomes a binary search.

### Recognising it

Reach for this family when:

- the answer is a **subsequence** (order kept, gaps allowed) under some **ordering rule** between consecutive picks
- "longest chain", "maximum nesting", "most boxes stacked", "longest sequence where each next one is bigger"
- the structure can be **sorted on one dimension** to leave an LIS on the other (Russian Doll Envelopes)

The mental question:

> If I knew the best answer ending at every earlier position, could I compute the best answer ending here?

=== bruteForce ===
Start from the definition, with no caching. To find the longest increasing chain ending at `i`, try **every** earlier `j` that could precede it, and recursively find the longest chain ending at that `j`.

### Step logic

1. `endAt(i)`: start with `len = 1` (`nums[i]` alone).
2. For every `j < i` with `nums[j] < nums[i]`, `len = max(len, 1 + endAt(j))` - a **recursive** call.
3. The answer is the maximum of `endAt(i)` over every `i`.

This enumerates every increasing chain explicitly. In the worst case that is every subset of the array.

### Dry run

```text
nums = [10, 9, 2, 5, 3, 7, 101, 18]
index    0  1  2  3  4  5    6   7
```

For each top-level `i`: which earlier `j` qualify (`nums[j] < nums[i]`), what `endAt(j)` each returns, the result, and the **number of calls** the recursion makes to get it (its own call plus everything beneath it).

| i | nums[i] | qualifying j (endAt j) | `endAt(i)` | calls made | best so far |
| -: | ------: | :--------------------- | ---------: | ---------: | ----------: |
| 0 | 10 | none | 1 | 1 | 1 |
| 1 | 9 | none (10 > 9) | 1 | 1 | 1 |
| 2 | 2 | none | 1 | 1 | 1 |
| 3 | 5 | j=2 (1) | 2 | 2 | 2 |
| 4 | 3 | j=2 (1) | 2 | 2 | 2 |
| 5 | 7 | j=2 (1), j=3 (2), j=4 (2) | 3 | 6 | 3 |
| 6 | 101 | j=0 (1), j=1 (1), j=2 (1), j=3 (2), j=4 (2), j=5 (3) | 4 | 14 | 4 |
| 7 | 18 | j=0 (1), j=1 (1), j=2 (1), j=3 (2), j=4 (2), j=5 (3) | 4 | 14 | **4** |

Answer `4`. Row `i = 6` is `1 + endAt(5) = 1 + 3`: the chain `[2, 5, 7, 101]` (or `[2, 3, 7, 101]`).

Where did `14` calls come from? `endAt(6)` makes its own call (1), then calls `endAt(0..5)`, which make `1 + 1 + 1 + 2 + 2 + 6 = 13` between them. And `endAt(5)`'s 6 calls themselves re-ran `endAt(2)`, `endAt(3)` (which re-ran `endAt(2)`), and `endAt(4)` (which re-ran `endAt(2)` again).

### Java

```java
class Solution {
    public int lengthOfLIS(int[] nums) {

        int best = 0;
        for (int i = 0; i < nums.length; i++) {
            best = Math.max(best, endAt(nums, i));
        }
        return best;
    }

    // Length of the longest strictly increasing subsequence ending at nums[i].
    private int endAt(int[] nums, int i) {
        int len = 1;
        for (int j = 0; j < i; j++) {
            if (nums[j] < nums[i]) {
                len = Math.max(len, 1 + endAt(nums, j));
            }
        }
        return len;
    }
}
```

### Complexity

**Time:** `O(2^n)` worst case - **Space:** `O(n)` recursion stack

### Where it hurts

Count the calls in the table: `1 + 1 + 1 + 2 + 2 + 6 + 14 + 14 = 41` calls to compute **8** distinct values. `endAt(2)` alone is evaluated 18 times.

On a strictly increasing array every `j` qualifies for every `i`, and the call count doubles with each index:

```text
calls(i) = 1 + calls(0) + calls(1) + ... + calls(i-1) = 2^i
```

At `n = 2500` that is not a number a computer will reach. Yet `endAt(i)` depends on nothing but `i` - there are only `n` distinct answers. Every repeated call is pure waste. Store each `endAt(i)` once and the exponential becomes `O(n^2)`.

=== optimization ===
### Step 1 - store `endAt(i)` once: the `O(n^2)` DP

Compute `dp[i]` left to right. By the time we reach `i`, every `dp[j]` for `j < i` is already final, so the inner loop reads them instead of recursing.

```java
class Solution {
    public int lengthOfLIS(int[] nums) {

        int n = nums.length;
        int[] dp = new int[n];      // dp[i] = LIS length ending exactly at i
        int best = 0;

        for (int i = 0; i < n; i++) {
            dp[i] = 1;              // nums[i] on its own
            for (int j = 0; j < i; j++) {
                if (nums[j] < nums[i]) {
                    dp[i] = Math.max(dp[i], dp[j] + 1);
                }
            }
            best = Math.max(best, dp[i]);
        }

        return best;
    }
}
```

| i | nums[i] | j with nums[j] < nums[i] | their dp | `dp[i]` | dp array after |
| -: | ------: | :----------------------- | :------- | ------: | :------------- |
| 0 | 10 | - | - | 1 | `[1, -, -, -, -, -, -, -]` |
| 1 | 9 | - | - | 1 | `[1, 1, -, -, -, -, -, -]` |
| 2 | 2 | - | - | 1 | `[1, 1, 1, -, -, -, -, -]` |
| 3 | 5 | 2 | 1 | 2 | `[1, 1, 1, 2, -, -, -, -]` |
| 4 | 3 | 2 | 1 | 2 | `[1, 1, 1, 2, 2, -, -, -]` |
| 5 | 7 | 2, 3, 4 | 1, 2, 2 | 3 | `[1, 1, 1, 2, 2, 3, -, -]` |
| 6 | 101 | 0, 1, 2, 3, 4, 5 | 1, 1, 1, 2, 2, 3 | 4 | `[1, 1, 1, 2, 2, 3, 4, -]` |
| 7 | 18 | 0, 1, 2, 3, 4, 5 | 1, 1, 1, 2, 2, 3 | 4 | `[1, 1, 1, 2, 2, 3, 4, 4]` |

`max(dp) = 4`. Exactly the brute force's `endAt` column, computed once each. `O(n^2)` time, `O(n)` space - and it passes LeetCode.

### Where `O(n^2)` still wastes work

At `i = 7` the inner loop scanned all seven earlier entries to discover one fact: the best chain `18` can extend has length `3`. Look at what that scan was really comparing:

```text
length 1 chains end at: 10, 9, 2       -> only the smallest, 2, matters
length 2 chains end at: 5, 3           -> only the smallest, 3, matters
length 3 chains end at: 7              -> 7
```

If two chains have the same length, the one ending in the **smaller** number is at least as good: anything that can extend the bigger tail can also extend the smaller one. So for each length we need only **one** number - the smallest tail seen so far.

### Step 2 - the key observation: keep only the best tail per length

```text
tails[k] = the smallest last element of any increasing subsequence of length k + 1 seen so far
```

Two facts make this fast:

1. **`tails` is strictly increasing.** A length-`k+1` chain contains a length-`k` chain ending in a smaller number, so the best length-`k` tail is smaller than the best length-`k+1` tail.
2. **Each new `x` changes exactly one slot.** Find the first `tails[k] >= x`:
   - if none exists, `x` is bigger than every tail - it extends the longest chain, so **append** it.
   - otherwise `x` can follow the chain of length `k` (whose tail is `< x`), giving a length-`k+1` chain ending in `x <= tails[k]` - a better tail, so **replace** `tails[k]` with `x`.

Because `tails` is sorted, "first `tails[k] >= x`" is a **binary search** (a lower bound). The answer is `tails`' size.

### Dry run - patience sorting

| x | tails before | lower bound of x | action | tails after | size |
| --: | :----------- | :--------------- | :----- | :---------- | ---: |
| 10 | `[]` | index 0 (end) | append | `[10]` | 1 |
| 9 | `[10]` | index 0 (10 >= 9) | replace 10 with 9 | `[9]` | 1 |
| 2 | `[9]` | index 0 (9 >= 2) | replace 9 with 2 | `[2]` | 1 |
| 5 | `[2]` | index 1 (end) | append | `[2, 5]` | 2 |
| 3 | `[2, 5]` | index 1 (5 >= 3) | replace 5 with 3 | `[2, 3]` | 2 |
| 7 | `[2, 3]` | index 2 (end) | append | `[2, 3, 7]` | 3 |
| 101 | `[2, 3, 7]` | index 3 (end) | append | `[2, 3, 7, 101]` | 4 |
| 18 | `[2, 3, 7, 101]` | index 3 (101 >= 18) | replace 101 with 18 | `[2, 3, 7, 18]` | 4 |

Answer: size `4`.

Compare to the `O(n^2)` table at `i = 7`: there we scanned seven entries to find "longest extendable chain has length 3". Here a binary search over four tails found the same thing - `18` lands at index 3, meaning it extends a length-3 chain.

### `tails` is not the LIS

In this example `tails` ended as `[2, 3, 7, 18]`, which happens to be a real subsequence. That is luck. Try:

```text
nums = [3, 4, 5, 1]
```

| x | tails after |
| --: | :---------- |
| 3 | `[3]` |
| 4 | `[3, 4]` |
| 5 | `[3, 4, 5]` |
| 1 | `[1, 4, 5]` |

`[1, 4, 5]` is **not** a subsequence - `1` comes after `5` in the input. But the size, `3`, is correct (`[3, 4, 5]`). Replacing `3` with `1` did not change any existing length; it only recorded that a length-1 chain can now end in something smaller, in case later elements need it. Only `tails.length` is meaningful. To print an actual LIS you need extra bookkeeping (see the takeaway).

=== complexity ===
### Time

Each of the `n` elements does one binary search over at most `n` tails.

```text
O(n log n)
```

### Space

The `tails` array holds at most `n` entries.

```text
O(n)
```

### Comparison

| Approach | Time | Space | Notes |
| :------- | ---: | ----: | :---- |
| Recursion over every chain | `O(2^n)` | `O(n)` stack | 41 calls for 8 values on the example |
| `dp[i]` = LIS ending at `i` | `O(n^2)` | `O(n)` | easiest to explain; can reconstruct the LIS |
| `tails` + binary search | **`O(n log n)`** | **`O(n)`** | the follow-up answer; length only |

For `n = 2500`, `n^2` is `6.25 * 10^6` and `n log n` is about `2.8 * 10^4`. Both pass. Lead with the `O(n^2)` DP in an interview - it shows the recurrence - then improve it.

=== implementation ===
```java
class Solution {
    public int lengthOfLIS(int[] nums) {

        // tails[k] = smallest tail of any increasing subsequence of length k + 1.
        int[] tails = new int[nums.length];
        int size = 0;

        for (int x : nums) {
            // Lower bound: first index in tails[0..size) with tails[idx] >= x.
            int lo = 0, hi = size;
            while (lo < hi) {
                int mid = (lo + hi) >>> 1;
                if (tails[mid] < x) {
                    lo = mid + 1;
                } else {
                    hi = mid;
                }
            }

            tails[lo] = x;          // replace a tail, or append when lo == size
            if (lo == size) {
                size++;
            }
        }

        return size;
    }
}
```

### The lines that matter

**1.**

```java
if (tails[mid] < x) {
    lo = mid + 1;
```

`<`, not `<=`. This finds the first tail **`>=` x**, so an equal element *replaces* rather than extends - which is what "strictly increasing" demands. Change it to `<=` and the search finds the first tail `> x`; `[7, 7, 7, 7]` would then return `4`, the answer to *longest non-decreasing* subsequence.

**2.**

```java
tails[lo] = x;          // replace a tail, or append when lo == size
```

One line does both cases. If `lo == size`, every tail was smaller than `x`, so this writes one past the current end - an append. Otherwise it overwrites a tail with a smaller-or-equal value, which can only make future extensions easier.

**3.**

```java
int lo = 0, hi = size;
```

The search range is `[0, size)`, half-open, so `lo` can land on `size` itself. That is how "no tail is `>= x`" is reported without a special case.

### Java notes

- `(lo + hi) >>> 1` is the overflow-safe midpoint. With `n <= 2500` overflow is impossible, but the habit costs nothing.
- `Arrays.binarySearch(tails, 0, size, x)` also works: it returns the index if found, else `-(insertionPoint) - 1`. Convert a negative result with `-(r + 1)`. Values are distinct within `tails`, so a found index is exactly the lower bound. The hand-written loop is clearer to explain.
- `tails` is sized `nums.length` up front so no `ArrayList` boxing is needed; `size` tracks how much of it is live.

=== edgeCases ===
### Single element

```text
[5]  ->  1
```

### All equal

```text
[7, 7, 7, 7]  ->  1
```

Every `7` finds `tails[0] = 7 >= 7` and replaces it. Strictness handled by the lower bound.

### Strictly decreasing

```text
[5, 4, 3, 2, 1]  ->  1
```

Every element replaces `tails[0]`. In the `O(n^2)` DP, no `j` ever qualifies, so every `dp[i] = 1`.

### Strictly increasing

```text
[1, 2, 3, 4]  ->  4
```

Every element appends. This is the brute force's worst case (`2^n` calls) and the fast version's simplest case.

### Repeated value in the middle

```text
[1, 3, 3, 4]  ->  3
```

`[1, 3, 4]`. The second `3` replaces the first rather than extending - `[1, 3, 3, 4]` is not strictly increasing.

### LeetCode's second example

```text
[0, 1, 0, 3, 2, 3]  ->  4
```

`[0, 1, 2, 3]`. `tails` goes `[0]`, `[0, 1]`, `[0, 1]`, `[0, 1, 3]`, `[0, 1, 2]`, `[0, 1, 2, 3]`.

### Negative numbers

```text
[-2, -1]  ->  2
```

Nothing assumes non-negative values; comparisons work the same.

### The "tails is the LIS" trap

```text
[3, 4, 5, 1]  ->  3      (final tails = [1, 4, 5], not a valid subsequence)
```

The length is right; the contents are not an answer. Never return `tails` as "the LIS".

=== takeaway ===
> When you see **longest subsequence with an ordering rule**, think **`dp[i]` = best chain ending at `i`**. When asked for faster, keep **only the smallest tail per length** and binary-search it.

### The core observation

Pinning the end of the chain to index `i` turns a slippery global question into a local one with `n` answers. Then: among equal-length chains, only the smallest tail matters, and those best tails form a sorted array - so "which chain can I extend?" is a binary search, not a scan.

### The pattern trigger

```text
        longest subsequence, order kept, each next > previous
                          |
                          v
        dp[i] = 1 + max dp[j]  (j < i, nums[j] < nums[i])    O(n^2)
                          |
                 "can you do better?"
                          |
                          v
        tails[k] = smallest tail of length k+1  (sorted)
        each x: lower_bound -> replace, or append        O(n log n)
                          |
                          v
                 answer = size of tails
```

### The common mistakes

**`<=` instead of `<` in the binary search.** Computes non-decreasing instead of strictly increasing. `[7, 7, 7, 7]` is the test that catches it.

**Returning `tails` as the subsequence.** Only its length is correct. `[3, 4, 5, 1]` gives `[1, 4, 5]`.

**Confusing subsequence with subarray.** A sliding window or "count the current run" approach answers a different question.

**Returning `dp[n - 1]` instead of `max(dp)`.** The LIS does not have to end at the last element - in `[1, 2, 0]`, `dp[2] = 1` but the answer is `2`.

### What to remember in six months

> `O(n^2)`: best chain ending here. `O(n log n)`: best tail per length, sorted, lower bound.

To **print** an LIS, use the `O(n^2)` DP with a `parent[i]` array recording which `j` gave the max, then walk back from the index with the largest `dp`. (The `O(n log n)` version can do it too, by storing the index of each tail and each element's predecessor.) Russian Doll Envelopes (LC 354) is LIS after sorting by width ascending and height **descending** - the descending tie-break stops two same-width envelopes from nesting. Number of LIS (LC 673), Largest Divisible Subset (LC 368) and Maximum Length of Pair Chain (LC 646) are the same `dp[i]` skeleton with a different "can `j` precede `i`?" test.
