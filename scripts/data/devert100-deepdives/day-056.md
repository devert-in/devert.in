=== intro ===
Yesterday's diameter taught the shape: a post-order function returns a height to its parent while checking something at the node. Today keeps that exact skeleton and changes only what is checked - and adds one new trick: when the check fails, the return value itself carries the bad news upward.

> When a recursive function must return a number *and* report failure, and the number can never be negative, let `-1` mean "failed". The parent checks for it and passes it straight up, and the whole tree stops working the moment the answer is known.

=== problem ===
Given the `root` of a binary tree, return `true` if it is **height-balanced**:

> for **every** node, the heights of its left and right subtrees differ by at most 1.

```text
        3
       / \
      9   20
         /  \
        15   7

root   = [3, 9, 20, null, null, 15, 7]
output = true
```

```text
            1
           / \
          2   2
         / \
        3   3
       / \
      4   4

root   = [1, 2, 2, 3, 3, null, null, 4, 4]
output = false      (at the root: left height 3, right height 1)
```

### What "height" means here

Height is the number of nodes on the longest downward path. `height(null) = 0`, `height(leaf) = 1`. The *difference* is what matters, so counting edges instead would give the same answer - but pick one and stay consistent.

### The word that makes it non-trivial: every

Checking the root alone is not enough. Here the root is perfectly balanced and the tree is not:

```text
            1
          /   \
         2     3
        /     / \
       4     6   7
      /     /
     5     8

root = [1, 2, 3, 4, null, 6, 7, 5, null, 8]

at node 1:  left height 3, right height 3   -> fine
at node 2:  left height 2, right height 0   -> differs by 2
output = false
```

The condition must hold at all `n` nodes, and each node's check needs two heights. That is where the cost comes from.

### Constraints

- `0 <= n <= 5000`. An **empty tree is balanced** (`true`): there is no node at which the condition can fail.
- Values are irrelevant - only the shape matters.

=== pattern ===
**DFS, post-order, bottom-up with a sentinel.**

### Why bottom-up

To check node `x` you need `height(x.left)` and `height(x.right)`. To compute `height(x)` you need... the same two numbers. So the check and the height want the same inputs, and both inputs come from the children. Children first, then the node: **post-order**.

### The template from yesterday

```text
f(node):
    L = f(left)
    R = f(right)
    <do something with L and R at this node>
    return 1 + max(L, R)
```

Diameter's "something" was `best = max(best, L + R)`. Today's is `if |L - R| > 1: fail`.

### The new idea: a sentinel in the return value

A height is always `>= 0`. So `-1` is free to mean "this subtree is not balanced". Once any node returns `-1`:

- its parent sees `-1` and returns `-1` too, without checking anything else
- that repeats all the way to the root
- the root returning `-1` means `false`; anything else means `true`

One return value now carries **two** facts - the height when things are fine, and the failure when they are not - with no extra field or wrapper object.

### Recognising it

Reach for the bottom-up sentinel when:

- a property must hold at **every** node, and checking it needs a value computed from the subtree (height, size, min/max, sum)
- the brute force calls a helper like `height()` inside another recursion
- once the property fails anywhere, the overall answer is fixed

The mental question:

> Can the value I compute for my parent also tell my parent "stop, it is already broken"? If the value has an impossible range, use it.

=== bruteForce ===
Read the definition top-down: at each node, compute both subtree heights with a helper, compare them, then recurse into both children.

### Step logic

1. `isBalanced(node)`: if `node` is `null`, return `true`.
2. Compute `height(node.left)` and `height(node.right)` - each is a full walk of that subtree.
3. If they differ by more than 1, return `false`.
4. Otherwise return `isBalanced(node.left) && isBalanced(node.right)`.

### Dry run

A balanced tree, so the brute force runs to completion and every bit of its work shows up:

```text
            1
          /   \
         2     3
        / \     \
       4   5     6
      /
     7

root = [1, 2, 3, 4, 5, null, 6, 7]
```

`isBalanced` visits in preorder: `1, 2, 4, 7, 5, 3, 6`. "Height visits" counts nodes touched by that row's two `height` calls.

| step | node | `height(left)` | `height(right)` | diff | ok? | height visits |
| ---: | ---: | -------------: | --------------: | ---: | :-- | ------------: |
| 1 | 1 | `height(2)` = 3 | `height(3)` = 2 | 1 | yes | 4 + 2 = 6 |
| 2 | 2 | `height(4)` = 2 | `height(5)` = 1 | 1 | yes | 2 + 1 = 3 |
| 3 | 4 | `height(7)` = 1 | `height(null)` = 0 | 1 | yes | 1 |
| 4 | 7 | 0 | 0 | 0 | yes | 0 |
| 5 | 5 | 0 | 0 | 0 | yes | 0 |
| 6 | 3 | `height(null)` = 0 | `height(6)` = 1 | 1 | yes | 1 |
| 7 | 6 | 0 | 0 | 0 | yes | 0 |

Every node passes, so:

```text
answer = true
```

Seven `isBalanced` calls and **eleven** height visits for a seven-node tree. Node `7` was visited by `height` three times (steps 1, 2, 3) - once for each ancestor.

### Java

```java
class Solution {
    public boolean isBalanced(TreeNode root) {

        if (root == null) return true;

        int diff = Math.abs(height(root.left) - height(root.right));
        if (diff > 1) return false;

        return isBalanced(root.left) && isBalanced(root.right);
    }

    private int height(TreeNode node) {
        if (node == null) return 0;
        return 1 + Math.max(height(node.left), height(node.right));
    }
}
```

### Complexity

**Time:** `O(n^2)` worst case, `O(n log n)` on a balanced tree - **Space:** `O(h)` recursion stack

### Where it hurts

Each node's height is recomputed by every ancestor's check. A node at depth `d` is walked `d` times by `height` alone.

The worst case is a tall tree that stays balanced long enough for the brute force to keep descending - or a chain whose imbalance only shows near the bottom. Either way the sum of depths reaches `O(n^2)`. With `n = 5000` that is millions of redundant visits.

There is a second, quieter waste. The brute force goes **top-down**: it does all of its expensive height work at the root *before* it discovers that some subtree is broken. The deep-imbalance tree from the problem section shows it - the root check walks all seven nodes below it, passes, and only then does the recursion find the failure at node `2`.

Both wastes have one fix. Heights are built from children's heights. If the recursion computed heights **bottom-up**, each would be computed once, and a failure low in the tree would be known before anything above it is touched.

=== optimization ===
### The observation

`height(x) = 1 + max(height(x.left), height(x.right))`. The two numbers needed to compute a node's height are exactly the two numbers needed to check its balance. So compute them once, check, and return the height - post-order, one walk.

When the check fails, there is no meaningful height to return, and no need for one: the answer is already `false`. Return `-1` instead, and make every caller pass `-1` through.

### Deriving the function

```text
check(node):
    if node is null:              return 0
    L = check(node.left);         if L == -1: return -1
    R = check(node.right);        if R == -1: return -1
    if |L - R| > 1:               return -1
    return 1 + max(L, R)

isBalanced(root) = check(root) != -1
```

Note where the `-1` test on `L` sits: **before** the right subtree is explored. A broken left subtree means the right one never gets visited.

### Dry run - same tree

```text
            1
          /   \
         2     3
        / \     \
       4   5     6
      /
     7
```

Post-order finishes nodes in the order `7, 4, 5, 2, 6, 3, 1`:

| step | node | L | R | `abs(L - R)` | returns |
| ---: | ---: | -: | -: | -----------: | ------: |
| 1 | 7 | 0 | 0 | 0 | 1 |
| 2 | 4 | 1 | 0 | 1 | 2 |
| 3 | 5 | 0 | 0 | 0 | 1 |
| 4 | 2 | 2 | 1 | 1 | 3 |
| 5 | 6 | 0 | 0 | 0 | 1 |
| 6 | 3 | 0 | 1 | 1 | 2 |
| 7 | 1 | 3 | 2 | 1 | 4 |

`check(root) = 4`, which is not `-1`:

```text
answer = true
```

Seven rows, seven nodes, each visited once. The brute force needed seven calls plus eleven height visits.

### Dry run - the sentinel at work

The tree whose root is fine but whose node `2` is not:

```text
            1
          /   \
         2     3
        /     / \
       4     6   7
      /     /
     5     8
```

| step | node | L | R | `abs(L - R)` | returns | note |
| ---: | ---: | -: | -: | -----------: | ------: | :--- |
| 1 | 5 | 0 | 0 | 0 | 1 | |
| 2 | 4 | 1 | 0 | 1 | 2 | |
| 3 | 2 | 2 | 0 | 2 | **-1** | fails here |
| 4 | 1 | -1 | - | - | **-1** | `L == -1`, return at once |

```text
check(root) = -1  ->  answer = false
```

Nodes `3`, `6`, `7` and `8` - half the tree - are **never visited**. The brute force on the same tree would walk all of them at the root before discovering anything.

=== complexity ===
### Time

Every node is visited at most once, with `O(1)` work besides the recursive calls. An early `-1` only ever skips work.

```text
O(n)
```

### Space

Only the recursion stack, as deep as the tree is tall.

```text
O(h)
```

`h` is `O(log n)` when the tree *is* balanced - by definition. When it is not, the stack can still reach `O(n)`: on a long chain, post-order has to descend all the way to the bottom before the first `-1` can be created near it. The early exit saves time on the way back up, not depth on the way down.

### Comparison

| Approach | Time | Space | Stops early on failure? |
| :------- | ---: | ----: | :---------------------- |
| Top-down, height helper per node | `O(n^2)` worst, `O(n log n)` balanced | `O(h)` | only after the expensive checks above it |
| Bottom-up with `-1` sentinel | **`O(n)`** | `O(h)` | yes - unwinds from the first failure |

=== implementation ===
```java
class Solution {
    public boolean isBalanced(TreeNode root) {
        return check(root) != -1;
    }

    // Height of `node` (null = 0, leaf = 1) if its subtree is balanced,
    // otherwise -1. A real height is never negative, so -1 is unambiguous.
    private int check(TreeNode node) {
        if (node == null) return 0;

        int left = check(node.left);
        if (left == -1) return -1;                 // left subtree already failed

        int right = check(node.right);
        if (right == -1) return -1;                // right subtree already failed

        if (Math.abs(left - right) > 1) return -1; // this node fails

        return 1 + Math.max(left, right);
    }
}
```

### The lines that matter

**1.**

```java
int left = check(node.left);
if (left == -1) return -1;                 // left subtree already failed
```

The check sits between the two recursive calls, not after both. If the left subtree is broken, the right subtree is never explored. Moving both `-1` tests to the end would still be correct - and would throw away the early exit.

**2.**

```java
if (Math.abs(left - right) > 1) return -1; // this node fails
```

The only place a `-1` is ever *created*. Every other `-1` is just being passed upward. `> 1`, not `>= 1`: a difference of exactly 1 is allowed.

**3.**

```java
return check(root) != -1;
```

The public method only has to translate the sentinel back into a boolean. `0` (the empty tree) is not `-1`, so an empty tree is correctly `true`.

### The global-flag version, for comparison

Yesterday's diameter used a field for its answer. The same works here and some people find it more readable:

```java
class Solution {

    private boolean balanced;

    public boolean isBalanced(TreeNode root) {
        balanced = true;
        height(root);
        return balanced;
    }

    private int height(TreeNode node) {
        if (node == null || !balanced) return 0;   // stop work once it has failed

        int left = height(node.left);
        int right = height(node.right);

        if (Math.abs(left - right) > 1) balanced = false;

        return 1 + Math.max(left, right);
    }
}
```

Same `O(n)`. The sentinel version needs no shared state, which is why it is the more common interview answer.

### Java notes

- `Math.abs(int)` is fine here: heights are at most 5000, so `left - right` never overflows.
- `-1` works as a sentinel only because heights are non-negative. If a function's real range included `-1`, you would return `Integer.MIN_VALUE`, an `Integer` (with `null`), or a small record instead.
- `&&` in the brute force short-circuits: if the left subtree is unbalanced, the right is never checked. That helps, but not with the repeated height work.

=== edgeCases ===
### Empty tree

```text
root = []  ->  true
```

`check(null)` returns `0`, which is not `-1`.

### Single node

```text
root = [1]  ->  true
```

Both subtrees have height `0`.

### Two nodes

```text
root = [1, 2]  ->  true
```

Heights `1` and `0` - a difference of exactly 1 is allowed.

### Three-node chain

```text
root = [1, 2, null, 3]  ->  false
```

The smallest unbalanced tree. At the root, left height `2`, right height `0`.

### LeetCode's first example

```text
root = [3, 9, 20, null, null, 15, 7]  ->  true
```

### LeetCode's second example

```text
root = [1, 2, 2, 3, 3, null, null, 4, 4]  ->  false
```

Here the failure is at the root itself (`3` vs `1`), so the sentinel is created on the very last check.

### Balanced at the root, broken below

```text
root = [1, 2, 3, 4, null, 6, 7, 5, null, 8]  ->  false
```

The trap tree from the problem section. A solution that only compares heights at the root returns `true` here.

### Lopsided but still balanced

```text
root = [1, 2, 3, 4, 5, null, 6, 7]  ->  true
```

Every node's subtrees differ by exactly 0 or 1, even though the tree visibly leans left. Balanced does not mean symmetric.

=== takeaway ===
> When you see **"for every node, compare something about its two subtrees"**, think **post-order, return the subtree value, and use an impossible value (`-1`) to report failure upward**.

### The core observation

The two heights a node needs for its balance check are exactly the two heights it needs to compute its own height. Computing them bottom-up means each is computed once - and a failure discovered low in the tree can short-circuit everything above it, because a height is never negative and `-1` is free to mean "broken".

### The pattern trigger

```text
     property must hold at EVERY node,
     and needs a value built from children
                     |
                     v
       f(node):  L = f(left)   if L == -1 -> return -1
                 R = f(right)  if R == -1 -> return -1
                     |
             property fails here?  -> return -1
                     |
             return the value the parent needs
                     |
                     v
         answer = (f(root) != -1)
```

### The common mistakes

**Checking only the root.** "Left height and right height differ by at most 1" is necessary and not sufficient. The condition is on every node.

**Computing heights top-down.** It is correct and it is `O(n^2)`. If a check calls `height()` inside another recursion, the two walks can almost always be merged.

**Forgetting to propagate the sentinel.** If a parent computes `1 + max(-1, 2)` it gets `3`, and the failure disappears. Every caller must test for `-1` before using the value.

**Using `>= 1` instead of `> 1`.** A difference of exactly 1 is balanced. `[1, 2]` must be `true`.

### What to remember in six months

> If the brute force calls a helper on a subtree from inside a traversal of that subtree, make the traversal **return** what the helper computed. One post-order pass replaces both.

That sentence covers Diameter (yesterday), this problem, Maximum Path Sum (LC 124), Count Univalue Subtrees, Largest BST Subtree, and "is this a valid heap". The value returned changes; the shape of the function never does.
