=== intro ===
Day 1 starts with the single most asked interview question there is - and with the idea that the rest of this run keeps returning to:

> A lookup you have already paid for is free. If you find yourself searching a list you have already walked past, a hash map can usually turn that search into a single step.

=== problem ===
You are given an array of integers and a target:

```text
nums   = [2, 7, 11, 15]
target = 9
```

Return the **indices** of the two numbers that add up to the target.

```text
nums[0] + nums[1] = 2 + 7 = 9
answer = [0, 1]
```

### What the guarantees actually give you

The problem promises two things, and both change the solution:

1. **Exactly one solution exists.** You never have to decide between two valid answers, and you never have to handle "no answer" - so the moment you find a pair, you can return immediately.
2. **You cannot use the same element twice.** `nums = [3, 5], target = 6` is **not** solvable by using `3` twice. This one line is the source of most wrong submissions, and section 7 shows exactly how it bites.

### Return indices, not values

```text
nums = [3, 2, 4], target = 6
```

The answer is `[1, 2]` - the positions of `2` and `4`. Returning `[2, 4]` is a different (wrong) answer. Keep that straight from the start, because the optimal solution stores positions for exactly this reason.

=== pattern ===
**Hashing**, specifically *complement lookup*.

Here is the reframe that turns this from a search problem into a lookup problem.

The naive reading is: "find two numbers `a` and `b` such that `a + b == target`." That sounds like it needs two things at once, which is why people reach for two loops.

But rewrite it. Standing on a single number `a`, the partner you need is completely determined:

```text
b = target - a
```

There is no searching for `b`. You already know its exact value. The only question left is:

> Have I already seen the number `target - a`?

"Have I seen X?" is the question a hash set answers in `O(1)`. And because we must return indices, we use a hash **map** from value to index instead of a set.

### Recognising it

Reach for complement lookup whenever you see:

- "two numbers that sum to X"
- "does a pair exist with difference K"
- "have I seen this value before"
- any pairing condition where fixing one element **determines** the other

The mental question:

> If I fix one element, can I compute exactly what its partner must be?

If yes, you almost never need the second loop.

=== bruteForce ===
Pretend you have never heard of a hash map. What is the obvious approach?

Check every pair.

For each index `i`, walk every later index `j`, and test whether `nums[i] + nums[j] == target`.

### Walkthrough

```text
nums = [2, 7, 11, 15], target = 9
```

```text
i=0 (2):  j=1 (7)  -> 2 + 7  = 9   MATCH, return [0, 1]
```

We got lucky on the first comparison. Take a less lucky input:

```text
nums = [3, 2, 4], target = 6
```

Now trace it properly, one comparison per row:

| step | i | j | nums[i] | nums[j] | sum | == 6? | action |
| ---: | -: | -: | ------: | ------: | --: | :---- | :----- |
| 1 | 0 | 1 | 3 | 2 | 5 | no | advance j |
| 2 | 0 | 2 | 3 | 4 | 7 | no | j exhausted, advance i |
| 3 | 1 | 2 | 2 | 4 | **6** | **yes** | return `[1, 2]` |

Three comparisons for three elements. Read the `i` column: it only advances
once the inner loop has run to the end. That is the shape of the waste - for
every single `i`, we walk the entire remaining array again.

### Watch it get worse

The same trace on a six-element array where the answer is last:

```text
nums = [1, 2, 3, 4, 5, 9], target = 14
```

| i | j values tried | comparisons | found? |
| -: | :------------- | ----------: | :----- |
| 0 | 1,2,3,4,5 | 5 | no |
| 1 | 2,3,4,5 | 4 | no |
| 2 | 3,4,5 | 3 | no |
| 3 | 4,5 | 2 | no |
| 4 | 5 | 1 | **yes** (5 + 9 = 14) |

15 comparisons for 6 elements. Add one element and it becomes 21, then 28. The
column of shrinking counts - 5, 4, 3, 2, 1 - is the `n(n-1)/2` that makes this
quadratic.

### Why `j` starts at `i + 1`

Two reasons, and they are different:

- Starting at `i` would let an element pair with **itself**, which the problem forbids.
- Starting at `0` would re-check every pair in the opposite order - pure waste.

### Java

```java
class Solution {
    public int[] twoSum(int[] nums, int target) {

        for (int i = 0; i < nums.length; i++) {

            for (int j = i + 1; j < nums.length; j++) {

                if (nums[i] + nums[j] == target) {
                    return new int[] { i, j };
                }
            }
        }

        return new int[] {};
    }
}
```

### Complexity

The inner loop runs `n-1` times, then `n-2`, then `n-3`... which totals about `n^2 / 2` comparisons.

**Time:** `O(n^2)` — **Space:** `O(1)`

### Where it hurts

For `n = 10,000` that is around 50 million comparisons.

Now name the waste precisely, because the fix comes straight out of it. Look at
the trace above: when `i = 4`, we compare `nums[4]` against `nums[5]`. But we
have **already read `nums[5]`** - four times, once for each earlier `i`. Every
element gets re-read once per element before it.

We keep re-reading values we have already seen, because we never wrote down
anything about them.

That is the opening for the optimisation.

=== optimization ===
The brute force throws away knowledge. Every time we move `i` forward, everything learned about the elements behind it is forgotten and has to be rescanned.

So: remember them.

As we walk the array, store each number we pass in a hash map:

```text
value -> the index it appeared at
```

Then at each new number `a`, instead of scanning backwards, compute the complement and ask the map one question.

### The key observation

> If `a + b == target` and `b` comes before `a`, then when we reach `a`, `b` is already in the map.

So we never need to look forward, and we never need to look backward manually. Every pair gets found exactly once - at the moment its **second** element is reached.

### Dry run

```text
nums = [2, 7, 11, 15], target = 9
```

**i = 0, num = 2**

```text
complement = 9 - 2 = 7
is 7 in the map?  map is empty -> no
store: map = {2 -> 0}
```

**i = 1, num = 7**

```text
complement = 9 - 7 = 2
is 2 in the map?  YES, at index 0
return [0, 1]
```

Two array reads. The brute force needed the same number here only by luck; on a longer array the gap is enormous.

### A longer trace

```text
nums = [3, 2, 4], target = 6
```

| i | num | complement | in map? | action | map after |
| -: | --: | ---------: | :------ | :----- | :-------- |
| 0 | 3 | 3 | no (empty) | store 3 | `{3:0}` |
| 1 | 2 | 4 | no | store 2 | `{3:0, 2:1}` |
| 2 | 4 | 2 | **yes, index 1** | return `[1, 2]` | - |

Look closely at row 0. The complement of `3` is `3`, and the map is empty **because we check before we store**. That single ordering decision is what stops `3` pairing with itself - and it is the whole reason section 7 exists.

=== complexity ===
### Time

One pass over `n` elements. For each element we do a constant amount of work: one subtraction, one map lookup, one map insert. Hash map operations are `O(1)` on average.

```text
O(n)
```

### Space

In the worst case - no pair found until the very last element - the map holds `n - 1` entries.

```text
O(n)
```

### Comparison

| Approach | Time | Space | Passes |
| :------- | ---: | ----: | -----: |
| Brute force | `O(n^2)` | `O(1)` | many |
| Hash map | **`O(n)`** | `O(n)` | 1 |

This is the classic **space-for-time trade**. We spend `O(n)` memory to remove an entire nested loop. When an interviewer asks "can you do better than `O(n^2)`", they are almost always asking whether you are willing to make that trade.

### A word on "average"

Hash lookups are `O(1)` *average*, not guaranteed. With adversarial keys designed to collide, a hash map degrades toward `O(n)` per operation. It is worth saying out loud in an interview - it shows you know the difference between the average and the worst case.

=== implementation ===
```java
import java.util.HashMap;
import java.util.Map;

class Solution {
    public int[] twoSum(int[] nums, int target) {

        // value -> index it was seen at
        Map<Integer, Integer> seen = new HashMap<>();

        for (int i = 0; i < nums.length; i++) {

            int complement = target - nums[i];

            // CHECK before INSERT - this is what stops an element
            // pairing with itself.
            if (seen.containsKey(complement)) {
                return new int[] { seen.get(complement), i };
            }

            seen.put(nums[i], i);
        }

        // Unreachable given the problem's "exactly one solution" guarantee.
        return new int[] {};
    }
}
```

### The three lines that matter

**1.**

```java
int complement = target - nums[i];
```

We are not searching. We are computing the exact value we need, then asking one question about it.

**2.**

```java
if (seen.containsKey(complement)) {
    return new int[] { seen.get(complement), i };
}
```

The map holds only elements **before** `i`, because we have not inserted `nums[i]` yet. So a hit is guaranteed to be a different element at a smaller index.

**3.**

```java
seen.put(nums[i], i);
```

Runs *after* the check. Reverse these two lines and the solution breaks - see the edge cases.

### Why the returned order is `[seen.get(complement), i]`

The map entry is the earlier index and `i` is the current one, so this returns them in ascending order. LeetCode accepts either order here, but ascending is what a reader expects.

### Java notes

- `Map<Integer, Integer>` autoboxes. For very large inputs an `int[]`-backed open-addressing map is faster, but no interviewer expects that here.
- `containsKey` then `get` is two lookups. `Integer idx = seen.get(complement); if (idx != null)` does it in one - a reasonable micro-optimisation to mention, though not one that changes the complexity.
- Duplicate values overwrite each other in the map (`put` replaces). That is harmless here, because we return on the first match and only ever need *one* valid partner.

=== edgeCases ===
### The duplicate trap - the one that matters

```text
nums = [3, 3], target = 6
```

The answer is `[0, 1]`. Trace it:

```text
i=0: complement = 3, map empty -> no match. store {3 -> 0}
i=1: complement = 3, map has 3 at index 0 -> return [0, 1]
```

Correct. Now flip the two lines so we insert *before* checking:

```text
i=0: store {3 -> 0}. complement = 3, map has 3 at index 0 -> return [0, 0]
```

`[0, 0]` - the same element used twice, which the problem forbids. **Check before insert** is not a style preference; it is the correctness condition.

### An element whose complement is itself, but with no partner

```text
nums = [3, 2, 4], target = 6
```

At `i = 0`, the complement of `3` is `3`. Because the map is empty, nothing matches and we move on correctly. The same ordering that solves `[3, 3]` also avoids a false positive here.

### Negative numbers

```text
nums = [-3, 4, 3, 90], target = 0
```

```text
i=0: complement = 3,  not seen. store -3
i=1: complement = -4, not seen. store 4
i=2: complement = -3, SEEN at 0 -> return [0, 2]
```

Nothing special is needed. Subtraction handles negatives, and hash maps do not care about sign.

### Two elements only

```text
nums = [1, 2], target = 3  ->  [0, 1]
```

The minimum valid input. Works without a special case.

### Zeros

```text
nums = [0, 4, 3, 0], target = 0  ->  [0, 3]
```

`0` is a perfectly ordinary key. The second `0` finds the first.

### Integer overflow

`target - nums[i]` can overflow if `target` is near `Integer.MIN_VALUE` and `nums[i]` is large and positive. LeetCode's constraints keep this in range, but on a whiteboard it is worth a sentence - `long complement = (long) target - nums[i];` removes the risk.

=== takeaway ===
> When you see **"find a pair that satisfies a condition"**, ask whether fixing one element **determines** the other. If it does, one hash map replaces the inner loop.

### The core observation

`a + b == target` is not a statement about two unknowns. Fix `a` and `b` is fully determined: `b = target - a`. The problem was never a search - it was a lookup wearing a search's clothing.

### The pattern trigger

```text
                For each element a
                        |
                        v
          What exactly must its partner be?
                        |
                        v
              b = target - a   (computed, not searched)
                        |
                        v
             Have I already seen b?  -> hash map, O(1)
                        |
                        v
                Yes -> answer.  No -> remember a.
```

### The common mistake

Inserting before checking. It passes `[2, 7, 11, 15]` and fails `[3, 3]`, so it is the kind of bug that survives casual testing and dies in the interview. **Check, then insert.**

### What to remember in six months

Not the code. This:

> A nested loop that re-scans elements you have already walked past is almost always a hash map in disguise.

That single sentence is the seed of Two Sum, Contains Duplicate, Subarray Sum Equals K, Longest Consecutive Sequence, group-anagrams, and a dozen others in this run. You are not learning one problem today - you are learning the reflex.

### One more thing worth knowing

If the array were **sorted**, you would not need the map at all: two pointers from both ends gives `O(n)` time and `O(1)` space (that is LC 167). The hash map is the price of the array being unsorted. Knowing both, and knowing *why* you would pick each, is the answer that distinguishes a good candidate.
