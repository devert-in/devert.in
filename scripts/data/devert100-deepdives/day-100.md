Day 100. The run started with Two Sum and one idea - a lookup you have already paid for is free. Since then it has moved through arrays, two pointers, hashing, linked lists, stacks, binary search, trees, heaps, graphs, greedy and DP. Yesterday added backtracking. Today's problem needs two of those at once: the **grid DFS** from Number of Islands, and the **choose / explore / un-choose** from Subsets.

That is the point of finishing here. Day 100 is not a new pattern - it is two old ones recognised in an unseen problem, which is what the whole run was for.

> When a search must not reuse what it is standing on, mark it on the way in and **restore it on the way out**. Number of Islands never restores, because a flooded cell stays flooded. Word Search must, because a cell that failed one path may be exactly what another path needs.

=== problem ===
Given an `m x n` grid of characters `board` and a string `word`, return `true` if `word` can be spelled by a path of **adjacent** cells, where:

- adjacent means **up, down, left or right** - not diagonal
- each cell may be used **at most once** in the path

LeetCode's board:

```text
     0   1   2   3
0    A   B   C   E
1    S   F   C   S
2    A   D   E   E
```

| word | answer | why |
| :--- | :----- | :-- |
| `ABCCED` | true | `(0,0) A -> (0,1) B -> (0,2) C -> (1,2) C -> (2,2) E -> (2,1) D` |
| `SEE` | true | `(1,3) S -> (2,3) E -> (2,2) E` |
| `ABCB` | false | after `A B C` the only `B` adjacent is the one already used |

`ABCB` is the case that defines the problem. The letters are all there, and `B` is even next to `C` - but it is the *same* `B`. "Each cell at most once" is the constraint the algorithm has to enforce.

### The example we will trace

Tracing the 3x4 board by hand is long (the brute force builds 138 full paths for `ABCB`). Both dry runs below use a small board that still exercises every rule - a wrong start, a dead end, and a cell that is blocked because it is already on the path:

```text
     0   1   2
0    A   C   C
1    T   A   C

word = "CAT"   ->   true:  (0,1) C -> (1,1) A -> (1,0) T
```

The optimised `ABCCED` trace is shown at the end of the optimization section.

### The constraints that matter

- `1 <= m, n <= 6`
- `1 <= word.length <= 15`
- Upper- and lower-case English letters. `'a'` and `'A'` are different.

At most 36 cells and 15 letters. Tiny - which is the signal that an exponential search is expected, and the job is to cut it down.

=== pattern ===
**DFS + Backtracking on a grid.**

### Why it belongs here

There are two ideas, and each comes from a problem you have already solved.

**Grid DFS** (Number of Islands, day 66): from a cell, try the four neighbours, skip anything out of bounds, recurse. The grid *is* the graph - each cell is a node, each adjacency an edge.

**Backtracking** (Subsets, day 99): build one candidate along a path, and undo the last choice when you return so the next branch starts clean.

Word Search needs both because the path has state. Where you can go next depends on *which cells the current path already used*. That state must be added on the way down and removed on the way back up:

```text
             Number of Islands            Word Search
visit      mark cell '0' (sunk)          mark cell '#'
leave      leave it sunk                 RESTORE the letter
why        a cell belongs to one island  a cell can be on many different paths
```

### The state

```text
dfs(r, c, k) = can word[k..] be spelled starting at cell (r, c),
               without touching any cell currently marked '#'?
```

### Recognising it

Reach for grid DFS + backtracking when:

- the input is a grid and the answer is a **path** through it
- the path must not revisit cells
- you need to know whether a path *exists* (or list them all), not the shortest one - shortest would mean BFS

The mental question:

> Is the "visited" state about the whole search, or only about the current path? If it is about the current path, it has to be undone when the path backs up.

=== bruteForce ===
Pretend we have not thought about pruning. The most direct idea is: **every path of length `word.length()` is a candidate spelling. Build each one, and compare it to the word.**

1. From every cell, walk paths through unvisited neighbours, appending letters to a `StringBuilder`.
2. When the path has `word.length()` letters, compare the whole string to `word`.
3. Undo on the way back (unmark the cell, delete the last letter) so other paths can use it.
4. Stop at the first match.

Neighbours are tried in the order **down, up, right, left**.

### Dry run

```text
     0   1   2
0    A   C   C
1    T   A   C          word = "CAT"
```

Each row is one complete 3-cell path, in the order the search builds them:

| # | start | path | letters | `equals("CAT")`? |
| -: | :---- | :--- | :------ | :--------------- |
| 1 | `(0,0)` | `(0,0) -> (1,0) -> (1,1)` | `ATA` | no |
| 2 | `(0,0)` | `(0,0) -> (0,1) -> (1,1)` | `ACA` | no |
| 3 | `(0,0)` | `(0,0) -> (0,1) -> (0,2)` | `ACC` | no |
| 4 | `(0,1)` | `(0,1) -> (1,1) -> (1,2)` | `CAC` | no |
| 5 | `(0,1)` | `(0,1) -> (1,1) -> (1,0)` | `CAT` | **yes - return true** |

Some detail on the rows:

- Rows 1-3 all start at `A`. The word starts with `C`, so all three were dead from their first cell - but the search did not know until it had built three letters and compared.
- Row 4 had the right first two letters, `CA`, then went to `C`. Wrong at letter 3.
- Row 4 -> 5: `(1,2)` was unvisited and its letter removed when row 4 finished, so `(1,1)` could try its next neighbour. That undo step is already backtracking.
- From `(1,1)` in row 4/5, the "up" neighbour `(0,1)` was skipped because it is `visited` - it is the `C` this path started from. That is the "each cell once" rule.

### Java

```java
class Solution {
    public boolean exist(char[][] board, String word) {
        boolean[][] visited = new boolean[board.length][board[0].length];
        for (int r = 0; r < board.length; r++) {
            for (int c = 0; c < board[0].length; c++) {
                if (walk(board, word, r, c, visited, new StringBuilder())) return true;
            }
        }
        return false;
    }

    // Extend the path through (r, c); compare only once it is word.length() long.
    private boolean walk(char[][] board, String word, int r, int c,
                         boolean[][] visited, StringBuilder path) {
        visited[r][c] = true;
        path.append(board[r][c]);

        boolean found = false;
        if (path.length() == word.length()) {
            found = path.toString().equals(word);
        } else {
            int[][] dirs = { { 1, 0 }, { -1, 0 }, { 0, 1 }, { 0, -1 } };
            for (int[] d : dirs) {
                int nr = r + d[0], nc = c + d[1];
                if (nr < 0 || nc < 0 || nr >= board.length || nc >= board[0].length) continue;
                if (visited[nr][nc]) continue;
                if (walk(board, word, nr, nc, visited, path)) {
                    found = true;
                    break;
                }
            }
        }

        path.deleteCharAt(path.length() - 1);     // undo, so other paths can use this cell
        visited[r][c] = false;
        return found;
    }
}
```

### Complexity

**Time:** `O(m * n * 4 * 3^(L-1) * L)` - **Space:** `O(m * n)` for `visited`, plus `O(L)` stack

From each start there are up to 4 first moves and then at most 3 (you cannot step back onto the cell you came from), and each finished path costs `O(L)` to compare.

### Where it hurts

The word is checked **once, at the end**. Every path is built to full length before anything is compared, so a path that was wrong at its first letter costs exactly as much as one wrong at its last.

Five paths on the toy board does not look bad. On LeetCode's board it does:

| word | full paths built by brute force | answer |
| :--- | ------------------------------: | :----- |
| `ABCCED` | 25 | true |
| `SEE` | 44 | true |
| `ABCB` | 138 | false |

And it grows by roughly a factor of 3 per extra letter. With `L = 15` on a 6x6 board, the number of complete paths is in the hundreds of millions, almost all of them wrong from their first or second letter.

The fix is in the brute force's own rows 1-3: the moment a path's letter disagrees with the word at that position, **no extension of it can ever match**. Compare letter by letter as you go, and those subtrees are never entered.

=== optimization ===
### The key observation

A path can only spell `word` if its `k`-th cell holds `word[k]`, for every `k`. So check each cell **when you step onto it**, against the one letter it has to be. A mismatch ends that branch immediately, with nothing built below it.

That makes the `StringBuilder` unnecessary - the recursion depth `k` already says which letter we are matching.

### The second observation - the board can hold `visited`

A separate `boolean[][]` is not needed either. Overwrite the cell with a character that matches no letter (`'#'`) while it is on the path, and put the letter back when you leave. The letter check then rejects visited cells for free, because `'#'` never equals `word.charAt(k)`.

### The algorithm

`dfs(r, c, k)`:

1. If `k == word.length()`, every letter has matched: return `true`.
2. If `(r, c)` is out of bounds, or `board[r][c] != word[k]`, return `false`. (This also rejects `'#'`.)
3. Save the letter, write `'#'`.
4. Try `dfs` on the four neighbours with `k + 1`; stop at the first `true`.
5. **Restore the letter.** Return the result.

Call `dfs(r, c, 0)` from every cell.

### Dry run - same example

```text
     0   1   2
0    A   C   C
1    T   A   C          word = "CAT"
```

Every call, in order. Indentation is depth; `k` is the index of the letter this call must match.

| # | call | cell holds | must match `word[k]` | result | board after |
| -: | :--- | :--------- | :------------------- | :----- | :---------- |
| 1 | `(0,0) k=0` start | `A` | `C` | mismatch, return false | unchanged |
| 2 | `(0,1) k=0` start | `C` | `C` | match, mark | `A # C / T A C` |
| 3 | `. (1,1) k=1` down | `A` | `A` | match, mark | `A # C / T # C` |
| 4 | `. . (2,1) k=2` down | - | - | out of bounds, false | same |
| 5 | `. . (0,1) k=2` up | `#` | `T` | mismatch (on path), false | same |
| 6 | `. . (1,2) k=2` right | `C` | `T` | mismatch, false | same |
| 7 | `. . (1,0) k=2` left | `T` | `T` | match, mark | `A # C / # # C` |
| 8 | `. . . (2,0) k=3` down | - | - | `k == 3`: **true** | same |
| - | back in call 7 | | | restore `T`, return true | `A # C / T # C` |
| - | back in call 3 | | | restore `A`, return true | `A # C / T A C` |
| - | back in call 2 | | | restore `C`, return true | `A C C / T A C` |

Compare with the brute force:

- Brute rows 1-3 (three full paths from `A`) became **call 1**: one comparison.
- Brute row 4 (`CAC`, built in full) became **call 6**: one comparison, at the letter where it went wrong.
- Call 5 is the reuse rule. `(0,1)` holds `'#'` because it is the `C` this path started on, so it cannot be the `T`.
- The board is back to its original letters when `exist` returns. Callers never see the `'#'`.

Notice call 8: `k == word.length()` is checked **before** bounds. The last letter matched at `(1,0)`, and its first neighbour `(2,0)` is off the board - but we no longer need any cell, so that is a success, not a failure.

=== complexity ===
### Time

Up to `m * n` starting cells. From each, the first step has 4 directions and every later step at most 3 (the cell you came from is marked). The path is at most `L` long.

```text
O(m * n * 3^L)
```

That is the worst case - a board of all `A`s and a word like `AAAA...AB` that matches almost to the end everywhere. On ordinary boards pruning cuts nearly every branch at its first or second letter.

### Space

No `visited` array, no `StringBuilder`. The recursion is at most `L + 1` deep.

```text
O(L)
```

### Comparison

| Approach | Compares | Worst-case time | Extra space |
| :------- | :------- | --------------: | ----------: |
| Build full paths, compare at the end | once per full path | `O(m * n * 3^L * L)` | `O(m * n + L)` |
| DFS, compare letter by letter, mark in place | once per step | **`O(m * n * 3^L)`** | **`O(L)`** |

| word on the 3x4 board | brute-force full paths | optimised calls |
| :-------------------- | ---------------------: | --------------: |
| `ABCCED` | 25 | 14 |
| `SEE` | 44 | 18 |
| `ABCB` | 138 | 28 |

Be honest in an interview: the worst-case bound barely changes. The gain is that pruning makes the *typical* search tiny. That is the nature of backtracking - its value is measured in branches not explored.

=== implementation ===
```java
class Solution {
    public boolean exist(char[][] board, String word) {
        for (int r = 0; r < board.length; r++) {
            for (int c = 0; c < board[0].length; c++) {
                if (dfs(board, word, r, c, 0)) return true;
            }
        }
        return false;
    }

    // Can word[k..] be spelled starting at (r, c)?
    private boolean dfs(char[][] board, String word, int r, int c, int k) {
        if (k == word.length()) return true;                     // every letter matched
        if (r < 0 || c < 0 || r >= board.length || c >= board[0].length) return false;
        if (board[r][c] != word.charAt(k)) return false;         // prune - also rejects '#'

        char saved = board[r][c];
        board[r][c] = '#';                                       // on the path: no reuse

        boolean found = dfs(board, word, r + 1, c, k + 1)
                     || dfs(board, word, r - 1, c, k + 1)
                     || dfs(board, word, r, c + 1, k + 1)
                     || dfs(board, word, r, c - 1, k + 1);

        board[r][c] = saved;                                     // backtrack: restore
        return found;
    }
}
```

### The lines that matter

**1.**

```java
if (k == word.length()) return true;                     // every letter matched
```

First, before the bounds check. After the last letter matches, the next call may well be off the board - and that must count as success. Put the bounds check first and a word ending on an edge cell is never found.

**2.**

```java
if (board[r][c] != word.charAt(k)) return false;         // prune - also rejects '#'
```

The whole optimisation in one line. It cuts every branch at the first wrong letter, and because `'#'` is not a letter, it is also the "already on this path" check.

**3.**

```java
board[r][c] = saved;                                     // backtrack: restore
```

The line that makes it backtracking rather than flood fill. Without it, a cell used by a failed path stays `'#'` forever, and a later path that needs it fails. The edge cases show a one-row board where that turns a `true` into a `false`.

### Why `||` and not four `if`s

`||` short-circuits: once one direction returns `true`, the remaining calls are never made. That is the "stop at the first match" rule for free. Note that the restore line still runs, because the assignment to `found` completes first.

### Pruning before the search (follow-up)

Two cheap checks that interviewers like:

```java
class Solution {
    public boolean exist(char[][] board, String word) {
        int cells = board.length * board[0].length;
        if (word.length() > cells) return false;             // cannot fit without reuse

        int[] have = new int[128];
        for (char[] row : board) for (char ch : row) have[ch]++;
        int[] need = new int[128];
        for (char ch : word.toCharArray()) {
            if (++need[ch] > have[ch]) return false;          // a letter the board lacks
        }

        // Start from the rarer end: fewer starting cells, earlier pruning.
        if (have[word.charAt(0)] > have[word.charAt(word.length() - 1)]) {
            word = new StringBuilder(word).reverse().toString();
        }

        for (int r = 0; r < board.length; r++) {
            for (int c = 0; c < board[0].length; c++) {
                if (dfs(board, word, r, c, 0)) return true;
            }
        }
        return false;
    }

    private boolean dfs(char[][] board, String word, int r, int c, int k) {
        if (k == word.length()) return true;
        if (r < 0 || c < 0 || r >= board.length || c >= board[0].length) return false;
        if (board[r][c] != word.charAt(k)) return false;

        char saved = board[r][c];
        board[r][c] = '#';
        boolean found = dfs(board, word, r + 1, c, k + 1)
                     || dfs(board, word, r - 1, c, k + 1)
                     || dfs(board, word, r, c + 1, k + 1)
                     || dfs(board, word, r, c - 1, k + 1);
        board[r][c] = saved;
        return found;
    }
}
```

Reversing is safe because a path read backwards is still a path. On an adversarial board like all `A`s with word `BAAAA...`, it is the difference between an instant answer and exponential work.

### Java notes

- `char[][]` cells are mutated in place, and the caller's board is modified during the search. Every path restores what it changed, so the board is identical when `exist` returns - worth saying out loud, since mutating input is otherwise a code-review flag.
- `'#'` is safe because the board only contains letters. If it could contain any character, use a `boolean[][] visited` instead (the brute force's approach) - same algorithm, `O(m * n)` extra space.
- `int[128]` covers all ASCII, so upper and lower case are counted separately - matching the problem's case-sensitive rule.

=== edgeCases ===
### Single cell

```text
[[A]], "A"  ->  true
[[A]], "B"  ->  false
```

Call `(0,0) k=0` matches, marks, then the first neighbour call has `k == 1 == length`: true.

### Word longer than the board

```text
[[A, B]], "ABA"  ->  false
```

The path would need to reuse `A`. The DFS finds `A -> B`, then the only neighbour of `B` is `'#'`.

### The reuse trap (LeetCode example 3)

```text
LeetCode board, "ABCB"  ->  false
```

### LeetCode example 2

```text
LeetCode board, "SEE"  ->  true
```

`(1,0) S` fails immediately (no `E` neighbour). `(1,3) S -> (2,3) E`; `(2,3)`'s "up" neighbour is the `S`, now `'#'`; "left" is `(2,2) E`. Found.

### Forgetting to restore

```text
[[B, A, A]], "AAB"  ->  true
```

The correct path is `(0,2) A -> (0,1) A -> (0,0) B`. But the search starts at `(0,1)` first: it matches `A`, goes right to `(0,2) A`, finds no `B` there, and fails. Without the restore, `(0,1)` and `(0,2)` stay `'#'`, so the later start at `(0,2)` is rejected at once and the answer comes out **false**. With the restore it is **true**.

### Case matters

```text
[[a]], "A"  ->  false
```

### All the same letter

```text
[[A, A], [A, A]], "AAAA"   ->  true
[[A, A], [A, A]], "AAAAA"  ->  false
```

Four cells form a loop, so 4 letters fit; a fifth would need a reuse.

### Letter missing from the board

```text
LeetCode board, "ABZ"  ->  false
```

The plain DFS discovers this by searching. The frequency pre-check rejects it before any DFS starts.

### Word ends on an edge

```text
[[C, A, T]], "CAT"  ->  true
```

The `T` is in the last column, so the call after it is out of bounds. It works only because `k == word.length()` is checked before bounds.

=== takeaway ===
> When you see **a grid** and **a path that cannot reuse cells**, think **DFS with mark-on-entry and restore-on-exit**, pruned by checking one letter per step.

### The core observation

A path can only succeed if each cell matches the letter at its depth, so compare as you step, not at the end - a wrong letter kills its whole subtree. And "visited" belongs to the current path only, so it is marked going in and undone coming out. Overwriting the cell with `'#'` does both jobs at once: the letter check rejects it, and restoring the letter releases it for the next path.

### The pattern trigger

```text
       grid + "find a path" + "each cell once"
                        |
                        v
       for every cell: dfs(r, c, k = 0)
                        |
                        v
       dfs(r, c, k):
           k == L                 -> true     (check FIRST)
           out of bounds          -> false
           board[r][c] != word[k] -> false    (prune; also rejects '#')
           mark '#'
           try 4 neighbours with k+1
           RESTORE                            (backtrack)
```

### The common mistakes

**Not restoring the cell.** That is flood fill, not backtracking. It passes many tests and fails on any board where a failed path used a cell a later path needs.

**Checking bounds before `k == L`.** Misses every word whose last letter sits on the edge.

**Comparing at the end instead of per step.** Correct, and exponentially slower on real inputs.

**Allowing diagonals.** The problem says horizontally or vertically adjacent. Four directions, not eight.

**Starting only from cells that match `word[0]` and then forgetting to check `word[0]` in `dfs`.** Fine if consistent - but the clean version lets `dfs` do every check itself.

### What to remember in six months

> Mark on the way in, restore on the way out. If the visited state belongs to the path, not the whole search, it must be undone.
