=== intro ===
Week 6 ended with a stack that held bars still waiting for a wall. Week 7 opens with the same "throw away what can never matter" idea - but now elements also **leave from the old end**, because the window slides past them. A stack can only drop things from one end. Today needs both.

> A monotonic stack forgets elements that are beaten. A monotonic **deque** also forgets elements that are too old. Whenever "beaten" and "expired" are both reasons to stop caring about something, you want a deque.

=== problem ===
Given an array `nums` and a window size `k`, slide the window from the left edge to the right edge one step at a time. Return the **maximum** inside each window.

```text
nums = [1, 3, -1, -3, 5, 3, 6, 7],  k = 3
```

| window start | window | max |
| -----------: | :----- | --: |
| 0 | `[1, 3, -1]` | 3 |
| 1 | `[3, -1, -3]` | 3 |
| 2 | `[-1, -3, 5]` | 5 |
| 3 | `[-3, 5, 3]` | 5 |
| 4 | `[5, 3, 6]` | 6 |
| 5 | `[3, 6, 7]` | 7 |

```text
answer = [3, 3, 5, 5, 6, 7]
```

There are `n - k + 1` windows, so the output has `n - k + 1` entries - here `8 - 3 + 1 = 6`.

### Why this is harder than a sliding-window sum

For a sum you add the new element and subtract the old one: `O(1)` per slide. Max has no "subtract". If the element leaving the window **was** the maximum, you have no idea what the new maximum is without looking at the rest of the window again.

```text
nums = [9, 1, 2, 3], k = 2

window [9, 1]  max 9
window [1, 2]  9 has left - the max is now 2, and nothing about "9" tells you that
```

That one fact is the whole difficulty.

### The constraints that matter

| Constraint | Why it matters |
| :--------- | :------------- |
| `1 <= n <= 10^5` | Combined with large `k`, `O(n * k)` reaches `~2.5 * 10^9`. Needs `O(n)` or `O(n log n)`. |
| `1 <= k <= n` | `k = 1` means every element is its own window; `k = n` means one window. No empty-window case. |
| `-10^4 <= nums[i] <= 10^4` | Negatives exist, so never initialise a max to `0`. |

=== pattern ===
**Monotonic deque (of indices).**

The reframe: instead of asking "what is the max of this window?" every time, keep a short list of **candidates** - elements that could still become the max of some future window - and keep it in an order where the answer is always at the front.

Which elements can be thrown away for good? Two kinds:

1. **Beaten.** If an element has a **larger-or-equal element to its right** inside the window, it can never be the max again. The right-hand one is at least as big and will stay in the window at least as long. Same reasoning as days 40-42: the newcomer dismisses everyone smaller.
2. **Expired.** An element whose index is left of the window can never be the max again either, however big it is.

Remove both kinds and the candidates are in **strictly decreasing order of value** (any smaller-or-equal-before-larger pair would have been "beaten"), and **increasing order of index**. So:

- the **front** is the largest - that is the window's max
- beaten elements are always at the **back** (the newcomer pops them, stack-style)
- expired elements are always at the **front** (they are the oldest)

Removing from both ends means a double-ended queue.

### Why indices, again

To know whether the front has expired you need its position: `front <= i - k`. The value is `nums[front]`. Same lesson as day 41.

### Recognising it

- "max / min of every window of size `k`"
- a sliding window where the aggregate has **no inverse** (max, min - unlike sum or XOR)
- a DP whose transition is "best of the last `k` states" (Jump Game VI, Constrained Subsequence Sum)

The mental question:

> Inside the window, which elements can I prove will never be the answer again - and do they always sit at one of the two ends?

=== bruteForce ===
Compute each window's max from scratch.

### Step logic

1. For each window start `i` from `0` to `n - k`:
2. Set `max = nums[i]`, then compare with `nums[i + 1] .. nums[i + k - 1]`.
3. Store `max` as `result[i]`.

### Dry run

```text
nums = [1, 3, -1, -3, 5, 3, 6, 7],  k = 3
index   0  1   2   3  4  5  6  7
```

| i | window | start `max` | compare 2nd | compare 3rd | `result[i]` | comparisons |
| -: | :----- | ----------: | :---------- | :---------- | ----------: | ----------: |
| 0 | `[1, 3, -1]` | 1 | 3 > 1 -> 3 | -1 < 3 -> 3 | **3** | 2 |
| 1 | `[3, -1, -3]` | 3 | -1 < 3 -> 3 | -3 < 3 -> 3 | **3** | 2 |
| 2 | `[-1, -3, 5]` | -1 | -3 < -1 -> -1 | 5 > -1 -> 5 | **5** | 2 |
| 3 | `[-3, 5, 3]` | -3 | 5 > -3 -> 5 | 3 < 5 -> 5 | **5** | 2 |
| 4 | `[5, 3, 6]` | 5 | 3 < 5 -> 5 | 6 > 5 -> 6 | **6** | 2 |
| 5 | `[3, 6, 7]` | 3 | 6 > 3 -> 6 | 7 > 6 -> 7 | **7** | 2 |

```text
result = [3, 3, 5, 5, 6, 7]
```

Correct, in `6 * 2 = 12` comparisons.

### Java

```java
class Solution {
    public int[] maxSlidingWindow(int[] nums, int k) {

        int n = nums.length;
        int[] result = new int[n - k + 1];

        for (int i = 0; i + k <= n; i++) {
            int max = nums[i];                 // not 0 - values can be negative
            for (int j = i + 1; j < i + k; j++) {
                max = Math.max(max, nums[j]);
            }
            result[i] = max;
        }

        return result;
    }
}
```

### Complexity

**Time:** `O((n - k + 1) * k)`, which is `O(n * k)` - **Space:** `O(1)` extra

### Where it hurts

Consecutive windows share `k - 1` elements. Window 1 is `[3, -1, -3]` and window 2 is `[-1, -3, 5]` - we compared `-1` and `-3` in both. Every element is looked at up to `k` times.

At `n = 10^5` and `k = 5 * 10^4`, that is about `(n - k) * k = 2.5 * 10^9` comparisons.

The natural fix - keep one running max and update it as the window slides - fails exactly when the max leaves:

```text
nums = [9, 1, 2, 3], k = 2

running max after [9, 1]:  9
slide: 9 leaves, 2 enters  ->  running max still says 9   WRONG (should be 2)
```

One number is not enough memory. When the max leaves, we need to know the **runner-up**, and when that leaves, the one after it. We need a ranked list of candidates - but only the ones that can actually still win.

=== optimization ===
### The key observation

Look at window 2, `[-1, -3, 5]`. Once `5` has arrived, `-1` and `-3` are **dead**: `5` is bigger and arrived later, so `5` will outlast them in every future window. No window that contains them and not `5` will ever exist again. Throw them away now.

After throwing away every element that has a larger-or-equal element after it, what is left is decreasing. The front is the max. When the front expires, the next one in line is the new max - the runner-up we needed, already ranked.

### The algorithm

Keep a deque of indices. For each `i`:

1. **Expire.** If the front index is `<= i - k`, it has left the window `[i - k + 1, i]`. Remove it from the front.
2. **Dismiss.** While the back's value is `<= nums[i]`, remove it from the back - `nums[i]` beats it and outlives it.
3. **Join.** Add `i` at the back.
4. **Answer.** Once `i >= k - 1` (the first full window is complete), `nums[front]` is this window's max.

### Dry run on the same example

```text
nums = [1, 3, -1, -3, 5, 3, 6, 7],  k = 3
```

Deque shows indices with values in brackets, front on the left.

| i | nums[i] | window | expire front? (`front <= i - 3`) | dismiss from back | deque after join | output |
| -: | ------: | :----- | :------------------------------- | :---------------- | :--------------- | :----- |
| 0 | 1 | `[0..0]` partial | empty | none | `[0(1)]` | - |
| 1 | 3 | `[0..1]` partial | 0 <= -2? no | 1 <= 3: drop 0 | `[1(3)]` | - |
| 2 | -1 | `[0..2]` | 1 <= -1? no | 3 <= -1? no | `[1(3), 2(-1)]` | `result[0] = 3` |
| 3 | -3 | `[1..3]` | 1 <= 0? no | -1 <= -3? no | `[1(3), 2(-1), 3(-3)]` | `result[1] = 3` |
| 4 | 5 | `[2..4]` | 1 <= 1? **yes: drop 1** | -3 <= 5: drop 3; -1 <= 5: drop 2 | `[4(5)]` | `result[2] = 5` |
| 5 | 3 | `[3..5]` | 4 <= 2? no | 5 <= 3? no | `[4(5), 5(3)]` | `result[3] = 5` |
| 6 | 6 | `[4..6]` | 4 <= 3? no | 3 <= 6: drop 5; 5 <= 6: drop 4 | `[6(6)]` | `result[4] = 6` |
| 7 | 7 | `[5..7]` | 6 <= 4? no | 6 <= 7: drop 6 | `[7(7)]` | `result[5] = 7` |

```text
result = [3, 3, 5, 5, 6, 7]
```

Same as the brute force. Three rows are worth rereading:

- **Row 3.** The deque holds three candidates `3, -1, -3` - all still alive, in decreasing order. If `3` expires before anything bigger arrives, `-1` takes over without any rescanning.
- **Row 4.** Both removal kinds in one step. Index `1` (value `3`) **expires** off the front - it is out of window `[2..4]`. Then `5` **dismisses** `-3` and `-1` off the back.
- **Row 1.** `1` is dismissed before any window is even complete. Dead candidates are dropped as early as possible.

Total: 8 joins and 7 removals (1 expiry + 6 dismissals). Every index enters once and leaves at most once.

=== complexity ===
### Time

Each index is added to the deque once and removed at most once (from either end). The output step is `O(1)`.

```text
O(n)
```

### Space

The deque only holds indices inside the current window, so at most `k` of them. The `result` array is the required output.

```text
O(k) extra
```

### Comparison

| Approach | Time | Extra space | Note |
| :------- | ---: | ----------: | :--- |
| Rescan every window | `O(n * k)` | `O(1)` | `~2.5 * 10^9` at the limits |
| Max-heap with lazy deletion | `O(n log n)` | `O(n)` | expired tops discarded when seen |
| `TreeMap` as a multiset | `O(n log k)` | `O(k)` | remove the leaving value explicitly |
| Block prefix / suffix max | `O(n)` | `O(n)` | day 7's idea, per block of `k` |
| Monotonic deque | **`O(n)`** | **`O(k)`** | each index in and out once |

The heap is the natural first improvement and worth describing in an interview before the deque: push `(value, index)`; before reading the top, pop it while its index has left the window. Old elements are not removed when they leave - only when they surface at the top - so the heap can hold up to `n` entries.

```java
class Solution {
    public int[] maxSlidingWindow(int[] nums, int k) {

        int n = nums.length;
        int[] result = new int[n - k + 1];

        // max-heap of {value, index}
        PriorityQueue<int[]> heap = new PriorityQueue<>((a, b) -> Integer.compare(b[0], a[0]));

        for (int i = 0; i < n; i++) {
            heap.offer(new int[] { nums[i], i });
            if (i >= k - 1) {
                while (heap.peek()[1] <= i - k) {
                    heap.poll();               // lazy delete: the top has left the window
                }
                result[i - k + 1] = heap.peek()[0];
            }
        }

        return result;
    }
}
```

=== implementation ===
```java
class Solution {
    public int[] maxSlidingWindow(int[] nums, int k) {

        int n = nums.length;
        int[] result = new int[n - k + 1];
        Deque<Integer> dq = new ArrayDeque<>();   // indices; values strictly decreasing front to back

        for (int i = 0; i < n; i++) {

            // 1. Expire: the front slid out of the window [i - k + 1, i].
            if (!dq.isEmpty() && dq.peekFirst() <= i - k) {
                dq.pollFirst();
            }

            // 2. Dismiss: anything not bigger than nums[i] can never be a max again.
            while (!dq.isEmpty() && nums[dq.peekLast()] <= nums[i]) {
                dq.pollLast();
            }

            // 3. Join.
            dq.offerLast(i);

            // 4. Answer, once the first full window exists.
            if (i >= k - 1) {
                result[i - k + 1] = nums[dq.peekFirst()];
            }
        }

        return result;
    }
}
```

### The lines that matter

**1.**

```java
if (!dq.isEmpty() && dq.peekFirst() <= i - k) {
    dq.pollFirst();
}
```

`if`, not `while`, and that is not an accident. The window moves one step at a time and the deque's indices are distinct and increasing, so at most one index - exactly `i - k` - can fall out per step. A `while` is also correct, just never loops twice.

**2.**

```java
while (!dq.isEmpty() && nums[dq.peekLast()] <= nums[i]) {
```

`while`, because one large newcomer can dismiss many (row 4 dismissed two). `<=` drops equal values too: the newer copy outlives the older one, so the older one is redundant. `<` also gives correct output - it just keeps duplicate candidates around longer.

**3.**

```java
result[i - k + 1] = nums[dq.peekFirst()];
```

The deque holds an index; the answer is the value at it. `i - k + 1` is the start of the current window, which is also its position in `result`.

### The order of the steps

Expire before reading the answer - otherwise a dead front is reported as the max. Dismiss before joining - otherwise `nums[i]` would compare against itself. Expire and dismiss can run in either order relative to each other: an index that is both expired and smaller than `nums[i]` gets removed either way.

### Java notes

- `ArrayDeque` gives `offerLast`/`pollLast`/`peekLast` for the back and `pollFirst`/`peekFirst` for the front, all `O(1)`. `LinkedList` also implements `Deque` but is slower; `java.util.Stack` cannot remove from the bottom at all.
- `peekFirst()` returns `null` on an empty deque, and unboxing `null` throws. Every access above is guarded by `!dq.isEmpty()`, and step 4 always runs after a join, so the deque is never empty there.
- The comparator `Integer.compare(b[0], a[0])` in the heap version avoids the `b[0] - a[0]` habit, which overflows for values near `Integer.MIN_VALUE`.

=== edgeCases ===
### Window of size 1

```text
nums = [4, -2, 7], k = 1  ->  [4, -2, 7]
```

Every element is its own window. The new index dismisses or expires the previous one each step; the deque never holds more than one.

### Window covers the whole array

```text
nums = [1, 3, 2], k = 3  ->  [3]
```

One window, one output, written at `i = 2`.

### Single element

```text
nums = [1], k = 1  ->  [1]
```

LeetCode's example 2.

### Strictly increasing

```text
nums = [1, 2, 3, 4, 5], k = 2  ->  [2, 3, 4, 5]
```

Every newcomer dismisses everything; the deque is always a single index and expiry never fires.

### Strictly decreasing

```text
nums = [5, 4, 3, 2, 1], k = 3  ->  [5, 4, 3]
```

Nothing is ever dismissed - every element is a candidate. The answer changes only because the front **expires**. This is the case that breaks a stack-only solution.

### The max leaves the window

```text
nums = [9, 1, 2, 3], k = 2  ->  [9, 2, 3]
```

The running-max shortcut returns `[9, 9, 9]`. The deque drops index `0` by expiry at `i = 2`, and `2` (which dismissed `1`) is already at the front.

### Duplicates

```text
nums = [7, 7, 7, 7], k = 2  ->  [7, 7, 7]
```

With `<=`, each new `7` dismisses the old one, so the deque always holds exactly one index and nothing ever needs to expire.

### All negative

```text
nums = [-4, -2, -9, -1], k = 2  ->  [-2, -2, -1]
```

Initialising any max to `0` would print `[0, 0, 0]`. The deque never invents a value - it only ever reports an element that exists.

=== takeaway ===
> When you see **"max (or min) of every window of size k"**, think **monotonic deque of indices**. Dismiss from the back what the newcomer beats; expire from the front what the window has left; read the answer at the front.

### The core observation

An element with a bigger-or-equal element after it in the window can never be the max again. Discard every such element and the survivors are sorted - so the max is at one end, the newcomer acts at the other, and expiry only ever touches the oldest end.

### The pattern trigger

```text
   for each i
        |
        v
   front index <= i - k ?  -> pollFirst()        (expired)
        |
        v
   while nums[back] <= nums[i]:  pollLast()      (beaten)
        |
        v
   offerLast(i)
        |
        v
   i >= k - 1 ?  -> answer = nums[peekFirst()]
```

### The common mistakes

**Storing values instead of indices.** You cannot tell whether the front has left the window.

**Reading the answer before expiring.** The front may be an index that left one step ago.

**Writing output from `i = 0`.** The first `k - 1` steps build a partial window; output starts at `i = k - 1`, into `result[i - k + 1]`.

**Keeping a single running max.** Correct until the max leaves the window, then stuck on a value that is no longer there.

### What to remember in six months

> A monotonic stack drops elements that are beaten. A monotonic deque also drops elements that are too old. Same invariant, one more exit.

For window **minimum**, flip the comparison (dismiss while `nums[back] >= nums[i]`). The same deque powers Shortest Subarray with Sum at Least K (LC 862) over prefix sums, and any DP of the form `dp[i] = nums[i] + max(dp[i-k..i-1])` such as Jump Game VI (LC 1696).

A sliding-window sum is easy: add the new element, subtract the old one. Max has no subtract. When the maximum leaves the window, one stored number tells you nothing about what the new maximum is - so the naive approach rescans every window: `O(n * k)`.

The observation: inside the window, any element with a bigger-or-equal element after it can never be the max again. The bigger one is at least as large and will stay at least as long. Throw it away.

What survives is a decreasing list of candidates, which needs exits at both ends:
- the back, where a newcomer dismisses everything it beats
- the front, where the oldest candidate expires when the window slides past it

The front is always the window's maximum.

Pattern: Monotonic Deque
Time: `O(n)`
Space: `O(k)`

Store indices, not values - otherwise you can't tell when the front has expired. Each index enters once and leaves once, which is what makes it linear.
