=== intro ===
Yesterday every step cost the same, and a FIFO queue was enough: BFS reached cells in order of distance for free. Today the edges carry **different** weights, and that guarantee is gone. The fix is one swap - the FIFO queue becomes a min-heap - and that swap is Dijkstra's algorithm.

> When edges have different non-negative costs, always expand the closest unfinished node next. Its distance can no longer improve, so you never have to come back to it.

=== problem ===
There are `n` network nodes labelled `1` to `n`. You are given `times[i] = [u, v, w]`: a signal sent from `u` reaches `v` after `w` time units. Edges are **directed** - `u -> v` does not imply `v -> u`.

A signal is sent from node `k`. Return the time it takes for **all** `n` nodes to receive it, or `-1` if some node never does.

### The worked example used all day

```text
n = 4, k = 1
times = [[2,4,2], [3,4,5], [3,2,2], [1,2,4], [1,3,1]]
```

| edge | from | to | time |
| :--- | ---: | -: | ---: |
| e0 | 2 | 4 | 2 |
| e1 | 3 | 4 | 5 |
| e2 | 3 | 2 | 2 |
| e3 | 1 | 2 | 4 |
| e4 | 1 | 3 | 1 |

```text
        4
   1 -------> 2
   |        ^ |
 1 |     2 /  | 2
   v      /   v
   3 --------> 4
        5
```

The fastest arrival at each node:

| node | fastest route | time |
| ---: | :------------ | ---: |
| 1 | start | 0 |
| 3 | 1 -> 3 | 1 |
| 2 | 1 -> 3 -> 2 | 1 + 2 = 3 |
| 4 | 1 -> 3 -> 2 -> 4 | 1 + 2 + 2 = 5 |

```text
answer = 5
```

### Read the question twice

"The time for **all** nodes to receive it" is the **maximum** of the shortest arrival times, not their sum. Every node receives the signal at its own shortest time, in parallel; the network is done when the slowest of them is done.

So the problem is really two steps:

1. compute the **shortest distance** from `k` to every node (single-source shortest path)
2. return the **largest** of them - or `-1` if any is infinite

### What makes it non-trivial

Look at node 2. The direct edge `1 -> 2` costs `4`. The two-edge route `1 -> 3 -> 2` costs `3`. **More edges, less time.** BFS from yesterday would reach node 2 in one hop and call it done at `4` - wrong. Fewest edges and cheapest path are no longer the same thing.

### Constraints that matter

- `1 <= n <= 100`, up to `6000` edges
- `0 <= w <= 100` - **weights are never negative**. This is the condition that makes today's algorithm valid. Day 76 removes it.

=== pattern ===
**Dijkstra's algorithm** - single-source shortest path with non-negative weights.

### The two ideas it is built from

**Relaxation.** Keep a best-known distance `dist[v]` for every node, starting at infinity (and `0` for the source). Looking at an edge `u -> v` with weight `w`:

```text
if dist[u] + w < dist[v]:
    dist[v] = dist[u] + w      "I found a cheaper way into v, through u"
```

That single step is all any shortest-path algorithm does. The algorithms differ only in **which edge they relax next**.

**Greedy order.** Among all nodes whose distance is not final yet, the one with the **smallest** tentative distance is already final. Any other route to it would have to leave through some other unfinished node, which is already at least as far away - and with non-negative weights, walking further can only add cost.

So Dijkstra: repeatedly take the closest unfinished node, declare it final, and relax its outgoing edges. A min-heap hands you "the closest" in `O(log)` time.

### BFS and Dijkstra are the same loop

```text
BFS:       queue (FIFO)      -> pops nodes in order of EDGE COUNT
Dijkstra:  min-heap by dist  -> pops nodes in order of TOTAL COST
```

When every weight is `1`, total cost equals edge count and the two do exactly the same thing. That is the cleanest way to remember Dijkstra: BFS with a priority queue.

### Recognising it

Reach for Dijkstra when:

- you need the cheapest / fastest / shortest route from **one** source
- edges have **different** costs
- every cost is **non-negative**
- the "graph" may be implicit - a grid with per-cell costs, states with transition costs

The mental question:

> Are the step costs different but never negative? Then pop the cheapest frontier node first.

If all costs are equal, BFS is simpler. If any cost is negative, Dijkstra's greedy argument breaks - that is tomorrow.

=== bruteForce ===
Forget about order. We know relaxation is the basic step, so do the most obvious thing with it: **relax every edge, and keep doing it until a full pass changes nothing.**

### Step logic

1. `dist[k] = 0`, every other `dist` is infinity.
2. Loop over **all** edges in the given order. For each `u -> v` with weight `w`: if `dist[u]` is known and `dist[u] + w < dist[v]`, update `dist[v]` and remember that something changed.
3. If the pass changed anything, do another full pass. If it changed nothing, every distance is final - stop.
4. Answer = the maximum `dist`, or `-1` if any node is still infinity.

It terminates because each update strictly lowers some distance, and with non-negative weights distances cannot go down forever.

### Java

```java
class Solution {
    public int networkDelayTime(int[][] times, int n, int k) {

        int[] dist = new int[n + 1];
        Arrays.fill(dist, Integer.MAX_VALUE);
        dist[k] = 0;

        boolean changed = true;
        while (changed) {
            changed = false;
            for (int[] t : times) {
                int u = t[0], v = t[1], w = t[2];
                if (dist[u] == Integer.MAX_VALUE) continue;   // u not reached yet
                if (dist[u] + w < dist[v]) {
                    dist[v] = dist[u] + w;
                    changed = true;
                }
            }
        }

        int answer = 0;
        for (int i = 1; i <= n; i++) {
            if (dist[i] == Integer.MAX_VALUE) return -1;
            answer = Math.max(answer, dist[i]);
        }
        return answer;
    }
}
```

### Complexity

**Time:** `O(V * E)` - **Space:** `O(V)`

A shortest path uses at most `V - 1` edges, and each pass extends every known shortest path by at least one more edge, so there are at most `V - 1` improving passes plus one confirming pass, each scanning all `E` edges.

### Where it hurts

Count the work in the table: **20 edge checks** for a graph with 5 edges. Only 5 of them updated anything, and 2 of those updates were **thrown away later**:

```text
pass 1: dist[2] = 4     -> overwritten in pass 2 with 3
pass 2: dist[4] = 6     -> overwritten in pass 3 with 5
```

Both wasted updates have the same cause. In pass 2 we relaxed `2 -> 4` using `dist[2] = 4`, **before** `dist[2]` was final. We pushed a wrong value forward, then had to come back and push the corrected one.

The rest of the waste is re-checking: edges `e3` and `e4` start at node 1, whose distance was final from the very beginning, yet they were checked in every pass.

At LeetCode's size (`V = 100`, `E = 6000`) this still passes - `600,000` checks. On a road network with `10^5` nodes and `10^6` edges it is `10^11`. The waste is structural:

> We relax edges out of nodes whose distance might still change. What if we only ever relaxed out of a node once its distance is final - and did it exactly once?

=== optimization ===
### The key observation

Take every node whose distance is not final yet, and look at the one with the **smallest tentative distance**. Call it `u`.

Its distance is already final. Any other route into `u` has to leave the finished region through some other unfinished node `x` first - and `dist[x] >= dist[u]` because `u` was the smallest. The remaining edges from `x` to `u` cost `>= 0`. So that route costs at least `dist[u]`. Nothing can beat it.

That gives an order in which every node's distance is final **before** we relax out of it:

1. pick the unfinished node with the smallest distance
2. it is now final - relax each of its outgoing edges once
3. repeat

No node's edges are ever relaxed with a wrong distance, so nothing is ever overwritten by a later pass and nothing needs re-checking.

### Getting the minimum fast: a min-heap with lazy deletion

Scanning all nodes for the minimum costs `O(V)` per step. A min-heap of `(distance, node)` pairs gives it in `O(log)`.

Java's `PriorityQueue` cannot lower the priority of an entry already inside it. So when `dist[v]` improves, we simply **push a new pair** and leave the old one in the heap. Later, when the old pair surfaces, we notice that its distance is larger than `dist[v]` and **skip it**. That is called a **stale entry**, and this trick is lazy deletion.

### Step logic

1. Build an adjacency list: for each node, its outgoing `(to, weight)` pairs.
2. `dist[k] = 0`, others infinity. Push `(0, k)`.
3. Pop the smallest pair `(d, u)`. If `d > dist[u]`, it is stale - skip it.
4. Otherwise `u` is final. For each edge `u -> v` with weight `w`: if `d + w < dist[v]`, set `dist[v] = d + w` and push `(dist[v], v)`.
5. Repeat until the heap is empty. Answer = max `dist`, or `-1` if any is infinite.

### Dry run - same graph

Adjacency list built from `times` (in input order):

```text
1: (2, 4), (3, 1)
2: (4, 2)
3: (4, 5), (2, 2)
4: -
```

| step | pop `(d, u)` | stale? | relax | dist[1..4] after | heap after |
| ---: | :----------- | :----- | :---- | :--------------- | :--------- |
| 0 | - | - | start | 0, inf, inf, inf | (0,1) |
| 1 | (0, 1) | no, `0 = dist[1]` | 1->2: 0+4=4 < inf, push (4,2). 1->3: 0+1=1 < inf, push (1,3) | 0, 4, 1, inf | (1,3) (4,2) |
| 2 | (1, 3) | no, `1 = dist[3]` | 3->4: 1+5=6 < inf, push (6,4). 3->2: 1+2=3 < 4, push (3,2) | 0, 3, 1, 6 | (3,2) (4,2) (6,4) |
| 3 | (3, 2) | no, `3 = dist[2]` | 2->4: 3+2=5 < 6, push (5,4) | 0, 3, 1, 5 | (4,2) (5,4) (6,4) |
| 4 | (4, 2) | **yes**, `4 > dist[2] = 3` | skip | 0, 3, 1, 5 | (5,4) (6,4) |
| 5 | (5, 4) | no, `5 = dist[4]` | node 4 has no edges | 0, 3, 1, 5 | (6,4) |
| 6 | (6, 4) | **yes**, `6 > dist[4] = 5` | skip | 0, 3, 1, 5 | empty |

```text
dist[1..4] = [0, 3, 1, 5]   ->   max = 5
```

Same answer. Now compare the work:

- Nodes were finalised in order `1 (0), 3 (1), 2 (3), 4 (5)` - strictly increasing distance, exactly as the observation promised.
- Each node's outgoing edges were relaxed **once**: 5 edge relaxations in total, against 20 edge checks for the brute force.
- The two stale entries, `(4,2)` and `(6,4)`, are the brute force's two wasted updates. Dijkstra still produces them, but it **never relaxes out of them** - step 4 and step 6 discard them in `O(log)` without touching any edge.

### Why non-negative weights are required

The observation said "the remaining edges cost `>= 0`, so walking further cannot help". A negative edge breaks exactly that sentence:

```text
1 -> 2  weight 2
1 -> 3  weight 5
3 -> 2  weight -4
```

Dijkstra pops node 2 at distance `2` and treats it as final. Later it pops node 3 at `5` and discovers `5 + (-4) = 1 < 2`. Node 2 was not final after all.

What happens next depends on the version:

- The **textbook** version keeps a `finalised[]` set and never touches a finalised node again. It ignores the improvement and returns `dist[2] = 2` - **wrong**, with no error.
- The **lazy** version written below has no such set. It pushes `(1, 2)` and processes node 2 a second time, so here it self-corrects. But "each node is processed once" no longer holds, and on adversarial graphs the re-processing grows exponentially. With a negative **cycle** it never terminates at all.

Either way, the guarantee is gone. Day 76 handles negative weights properly with Bellman-Ford - which is today's brute force, given a fixed bound on the number of passes.

=== complexity ===
### Time

Every edge can push at most one heap entry (only when it improves a distance), so the heap holds at most `E + 1` entries. Each push and pop costs `O(log E)`.

```text
O(E log E)  =  O(E log V)      since E <= V^2, log E <= 2 log V
```

Including building the adjacency list and the final scan over `dist`, it is usually written `O((V + E) log V)`.

### Space

The adjacency list stores every edge once, `dist` is `V + 1` ints, and the heap holds up to `E` pairs.

```text
O(V + E)
```

### Comparison

| Approach | Time | Space | Negative weights? |
| :------- | ---: | ----: | :---------------- |
| Relax all edges until stable | `O(V * E)` | `O(V)` | yes, if no negative cycle |
| Dijkstra, array scan for the minimum | `O(V^2 + E)` | `O(V + E)` | no |
| Dijkstra, binary heap with lazy deletion | **`O((V + E) log V)`** | **`O(V + E)`** | no |

The array-scan version is worth knowing: on a **dense** graph where `E` is close to `V^2`, `O(V^2)` beats `O(V^2 log V)`. Day 77 uses exactly that trade-off for Prim's algorithm.

=== implementation ===
```java
class Solution {
    public int networkDelayTime(int[][] times, int n, int k) {

        // Adjacency list: graph.get(u) = list of {v, w} for edges u -> v.
        List<List<int[]>> graph = new ArrayList<>();
        for (int i = 0; i <= n; i++) graph.add(new ArrayList<>());
        for (int[] t : times) graph.get(t[0]).add(new int[] {t[1], t[2]});

        int[] dist = new int[n + 1];
        Arrays.fill(dist, Integer.MAX_VALUE);
        dist[k] = 0;

        // Min-heap of {distance, node}, smallest distance first.
        PriorityQueue<int[]> heap = new PriorityQueue<>((a, b) -> Integer.compare(a[0], b[0]));
        heap.offer(new int[] {0, k});

        while (!heap.isEmpty()) {

            int[] top = heap.poll();
            int d = top[0], u = top[1];

            if (d > dist[u]) continue;            // stale entry - u already finalised cheaper

            for (int[] edge : graph.get(u)) {
                int v = edge[0], w = edge[1];
                if (d + w < dist[v]) {
                    dist[v] = d + w;
                    heap.offer(new int[] {dist[v], v});
                }
            }
        }

        int answer = 0;
        for (int i = 1; i <= n; i++) {
            if (dist[i] == Integer.MAX_VALUE) return -1;   // never received the signal
            answer = Math.max(answer, dist[i]);
        }
        return answer;
    }
}
```

### The lines that matter

**1.**

```java
if (d > dist[u]) continue;            // stale entry - u already finalised cheaper
```

The lazy-deletion check. Without it the code is still correct, but every stale entry would re-relax all of `u`'s edges with a worse distance - wasted work that, on adversarial graphs, undoes the complexity bound. Note `>` and not `>=`: the live entry has `d == dist[u]` and must be processed.

**2.**

```java
PriorityQueue<int[]> heap = new PriorityQueue<>((a, b) -> Integer.compare(a[0], b[0]));
```

Order by distance, index `0` of the pair. `Integer.compare` rather than `a[0] - b[0]`: subtraction can overflow for large values, which silently inverts the ordering. Here distances are at most `100 * 99`, so both work, but the habit is worth having.

**3.**

```java
if (d + w < dist[v]) {
```

`d` is `dist[u]` at this point (the stale check guarantees it), and it is never `Integer.MAX_VALUE`, because only reached nodes are ever pushed. So `d + w` cannot overflow - unlike in the brute force, which needs an explicit `dist[u] == Integer.MAX_VALUE` guard.

**4.**

```java
answer = Math.max(answer, dist[i]);
```

The **max**, not the sum. All nodes receive the signal in parallel; the slowest one decides.

### Java notes

- Nodes are labelled `1..n`, so `graph` and `dist` have `n + 1` slots and index `0` is simply unused. That is cleaner than subtracting 1 everywhere.
- `List<List<int[]>>` is the standard adjacency list for weighted edges. A `Map<Integer, List<int[]>>` works too but is slower and adds nothing when nodes are dense integers.
- `Arrays.fill(dist, Integer.MAX_VALUE)` stands for infinity. Never add to it without checking - `Integer.MAX_VALUE + 1` wraps to a large negative number.
- The heap may hold several entries for the same node. That is by design; do not try to remove old entries (`PriorityQueue.remove(Object)` is `O(n)`).

=== edgeCases ===
### A node the signal cannot reach

```text
n = 2, k = 2, times = [[1,2,1]]  ->  -1
```

The edge is directed `1 -> 2`. Starting at 2, node 1 stays at infinity, and the final scan returns `-1`.

### Same edge, reachable direction

```text
n = 2, k = 1, times = [[1,2,1]]  ->  1
```

### A single node

```text
n = 1, k = 1, times = []  ->  0
```

The source has the signal at time `0`. The heap pops `(0,1)`, there are no edges, and the max over one distance is `0`.

### LeetCode's first example

```text
n = 4, k = 2, times = [[2,1,1],[2,3,1],[3,4,1]]  ->  2
```

`dist = [1, 0, 1, 2]` for nodes 1..4; the slowest is node 4 at `2`.

### Parallel edges

```text
n = 2, k = 1, times = [[1,2,5],[1,2,1]]  ->  1
```

Two edges between the same pair. Both are relaxed; the cheaper one wins. No deduplication needed.

### Zero-weight edges

```text
n = 3, k = 1, times = [[1,2,0],[2,3,0]]  ->  0
```

Weights may be `0` (the constraint is `0 <= w`). Dijkstra is still valid - zero is non-negative.

### A cycle

```text
n = 3, k = 1, times = [[1,2,1],[2,3,1],[3,1,1]]  ->  2
```

When node 1 is reached again through `3 -> 1`, `2 + 1 = 3` is not less than `dist[1] = 0`, so nothing is pushed. Cycles with non-negative weight can never improve a distance.

### The cheap route has more edges

```text
n = 3, k = 1, times = [[1,3,10],[1,2,1],[2,3,1]]  ->  2
```

BFS-by-hops would answer `10`. This is the case that rules BFS out.

### Max, not sum

```text
n = 4, k = 1, times = [[1,2,3],[1,3,3],[1,4,3]]  ->  3
```

Three nodes at time `3` each, reached in parallel. Summing would answer `9`.

=== takeaway ===
> When you see **"cheapest / fastest route from one source"** with **different non-negative costs**, think **Dijkstra**: a min-heap of `(dist, node)`, pop the closest, skip stale entries, relax its edges.

### The core observation

The closest unfinished node is already final, because any detour leaves through a node that is no closer and then adds a non-negative cost. Processing nodes in that order means each node's edges are relaxed once, with a distance that will never change.

### The pattern trigger

```text
        shortest path from ONE source
                    |
                    v
          what do the edges cost?
         /          |             \
   all equal   different, >= 0   some negative
       |            |                 |
      BFS       Dijkstra         Bellman-Ford
                    |
                    v
   heap.offer({0, src})
   pop {d, u}:  d > dist[u]?  skip (stale)
   each u -> v (w):  d + w < dist[v]?  update, offer
```

### The common mistakes

**Forgetting the stale check.** Still correct, but stale entries re-relax whole adjacency lists for nothing.

**Using BFS because "it's a shortest path".** BFS counts edges. Different weights need Dijkstra.

**Using Dijkstra with negative edges.** The textbook version returns a wrong answer with no error; the lazy version may self-correct but loses its complexity bound and hangs on a negative cycle.

**Summing the distances.** The question asks when the **last** node hears the signal - the max.

**Adding to `Integer.MAX_VALUE`.** In any relax loop that can see an unreached node, guard it first.

### What to remember in six months

> Dijkstra is BFS with a min-heap. It needs non-negative weights, because the proof is "walking further cannot make it cheaper".

The same loop solves Path With Minimum Effort (LC 1631 - relax with `max(d, |height diff|)` instead of `d + w`), Swim in Rising Water, Cheapest path in a weighted grid, and Network Delay Time's many disguises. Only the relaxation formula changes.
