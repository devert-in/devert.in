=== intro ===
Yesterday was about **visiting** every node: pre, in and post order, and the stack that remembers where to come back to. Today the visit has to **produce something** - a number - and the number for a node depends on the numbers for its children.

> The single most reused idea in tree problems: ask each child for its answer, then combine. If you can phrase the answer for a node in terms of the answers for its two subtrees, the whole solution is a base case plus one line.

=== problem ===
Given the `root` of a binary tree, return its **maximum depth**: the number of nodes on the longest path from the root down to a leaf.

```text
        3
       / \
      9   20
         /  \
        15   7

root = [3, 9, 20, null, null, 15, 7]   ->   3
```

The three root-to-leaf paths:

| path | nodes on it |
| :--- | ----------: |
| 3 -> 9 | 2 |
| 3 -> 20 -> 15 | 3 |
| 3 -> 20 -> 7 | 3 |

The longest has 3 nodes, so the answer is `3`.

### Two words worth pinning down

**Depth counts nodes, not edges.** A single node has depth `1`. An empty tree has depth `0`. Some textbooks define height in edges (a single node is `0`); LeetCode 104 does not - and an off-by-one here fails every test.

**A leaf has no children at all.** The path must end at a leaf. That detail does not change this problem's answer (the deepest node is always a leaf), but it is exactly what breaks the "minimum depth" follow-up, so read it now.

### The constraints that matter

| constraint | value | what it means |
| :--------- | ----: | :------------ |
| nodes | 0 to 10^4 | empty tree is a real input |
| values | -100 to 100 | irrelevant - depth never looks at values |

10^4 nodes in a straight line is a recursion 10^4 calls deep. Java handles that on LeetCode, but it is close enough to the edge to be worth knowing.

=== pattern ===
**DFS, postorder - "ask the children, then combine".**

Stand at any node and suppose someone tells you the maximum depth of its left subtree (`L`) and of its right subtree (`R`). The longest path from this node goes through this node and then down into whichever subtree is deeper:

```text
depth(node) = 1 + max(L, R)
depth(null) = 0
```

That is the whole algorithm. It is postorder because the node's own answer can only be computed **after** both children have returned theirs.

### Why the definition is the code

The problem says "longest root-to-leaf path". The recurrence says the same thing one level at a time: a node's longest downward path is itself plus its children's longest downward path. Nothing is searched; it falls out of the structure.

### Recognising it

Reach for "1 + combine(children)" when:

- the answer for a tree is built from the answers for its subtrees (height, size, sum, balanced?, diameter)
- an empty tree has an obvious answer (`0`, `true`, empty)
- you do not need anything from the parent

The mental question:

> If both of my subtrees already handed me their answers, what is mine?

If you can answer that in one line, write the base case for `null` and you are done.

=== bruteForce ===
Take the problem statement literally. "Longest root-to-leaf path": so list every root-to-leaf path, then measure the longest.

### Step logic

1. DFS from the root, carrying the **current path** as a list.
2. On entering a node, append it to the path.
3. If it is a leaf, save a **copy** of the path.
4. Recurse into the children, then remove the node from the path on the way back (backtrack).
5. At the end, return the size of the longest saved path (or `0` if there are none).

### Dry run

| step | node | path after append | leaf? | saved paths | on return |
| ---: | ---: | :---------------- | :---- | :---------- | :-------- |
| 1 | 3 | `[3]` | no | none | - |
| 2 | 9 | `[3, 9]` | **yes** | `[3, 9]` | remove 9 -> `[3]` |
| 3 | 20 | `[3, 20]` | no | `[3, 9]` | - |
| 4 | 15 | `[3, 20, 15]` | **yes** | `[3, 9]`, `[3, 20, 15]` | remove 15 -> `[3, 20]` |
| 5 | 7 | `[3, 20, 7]` | **yes** | `[3, 9]`, `[3, 20, 15]`, `[3, 20, 7]` | remove 7 -> `[3, 20]` |
| 6 | 20 | - | - | - | remove 20 -> `[3]` |
| 7 | 3 | - | - | - | remove 3 -> `[]` |

Saved path sizes: `2, 3, 3`. Maximum: **3**. Correct.

### Java

```java
class Solution {
    public int maxDepth(TreeNode root) {

        List<List<Integer>> paths = new ArrayList<>();
        collect(root, new ArrayList<>(), paths);

        int best = 0;
        for (List<Integer> p : paths) {
            best = Math.max(best, p.size());
        }
        return best;
    }

    private void collect(TreeNode node, List<Integer> path, List<List<Integer>> paths) {
        if (node == null) return;

        path.add(node.val);
        if (node.left == null && node.right == null) {
            paths.add(new ArrayList<>(path));     // copy: path keeps changing
        } else {
            collect(node.left, path, paths);
            collect(node.right, path, paths);
        }
        path.remove(path.size() - 1);             // backtrack
    }
}
```

### Complexity

**Time:** `O(n * h)` worst case - **Space:** `O(n * h)` for the saved paths

Every leaf copies a path of up to `h` nodes, and there can be up to about `n / 2` leaves.

### Where it hurts

Look at the "saved paths" column. We stored `3, 20, 15` and `3, 20, 7` in full - every value on every path - and then used only one number from each: its **length**. The values were never needed.

There is a second, subtler waste. The prefix `3, 20` is shared by two paths and was copied twice. In a tree shaped like a broom - a long handle of `n / 2` nodes ending in a fan of `n / 2` leaves - every leaf copies the whole handle, and the copying alone is `O(n^2)`.

Strip out what was never used:

- do not store paths, store only a length
- do not even carry the length down - let each subtree **report** its own deepest length up

That second step is the observation that makes the problem one line.

=== optimization ===
### Step 1 - carry a number, not a list

Pass the depth down instead of the path, and keep one running maximum. This is preorder: each node knows its depth from its parent before looking at children.

```text
visit(node, depth):
    if node is null: return
    best = max(best, depth)
    visit(node.left,  depth + 1)
    visit(node.right, depth + 1)
```

Already `O(n)` time and `O(h)` space. It works, but it needs a field (`best`) living outside the recursion.

### Step 2 - let the children report up

Flip the direction. Instead of telling each child "you are at depth `d`", ask each child "how deep does your subtree go?" and add one for yourself.

### Key observation

```text
maxDepth(node) = 1 + max(maxDepth(node.left), maxDepth(node.right))
maxDepth(null) = 0
```

No path, no running maximum, no shared state. Each call returns its subtree's answer and the root's call returns the tree's.

### Dry run - same tree, postorder

| order | call | left returns | right returns | computes | returns |
| ----: | :--- | -----------: | ------------: | :------- | ------: |
| 1 | `maxDepth(9)` | 0 (null) | 0 (null) | 1 + max(0, 0) | 1 |
| 2 | `maxDepth(15)` | 0 (null) | 0 (null) | 1 + max(0, 0) | 1 |
| 3 | `maxDepth(7)` | 0 (null) | 0 (null) | 1 + max(0, 0) | 1 |
| 4 | `maxDepth(20)` | 1 (from 15) | 1 (from 7) | 1 + max(1, 1) | 2 |
| 5 | `maxDepth(3)` | 1 (from 9) | 2 (from 20) | 1 + max(1, 2) | **3** |

The rows are in the order the calls **finish**, which is postorder: `9, 15, 7, 20, 3`. A node's row cannot be filled until the rows of both its children are.

The same values written on the tree:

```text
            3  -> 3
           / \
   1 <-  9    20  -> 2
             /  \
     1 <-  15    7  -> 1
```

### Step 3 (alternative) - count the levels with BFS

Depth is also "how many levels does the tree have". Process the tree level by level with a queue and count the levels:

| level | queue at start of level | nodes processed | children queued | levels counted |
| ----: | :---------------------- | :-------------- | :-------------- | -------------: |
| 1 | `[3]` | 3 | 9, 20 | 1 |
| 2 | `[9, 20]` | 9, 20 | 15, 7 | 2 |
| 3 | `[15, 7]` | 15, 7 | none | 3 |
| - | `[]` | - | - | stop: **3** |

Same answer, no recursion at all. That matters for a very deep tree, and it is the template for Level Order Traversal on day 54.

=== complexity ===
### Time

Each node is visited once and does constant work.

```text
O(n)
```

### Space

Recursive: one call frame per level of the current path.

```text
O(h)    balanced: log n     skewed (a chain): n
```

BFS: the queue holds one level at a time, so `O(w)` where `w` is the widest level - up to about `n / 2` for the last level of a perfect tree.

### Comparison

| Approach | Time | Extra space | Shared state |
| :------- | ---: | ----------: | :----------- |
| Collect all paths | `O(n * h)` | `O(n * h)` | list of paths |
| Top-down depth + running max | `O(n)` | `O(h)` | one `best` field |
| Bottom-up `1 + max(L, R)` | **`O(n)`** | **`O(h)`** | none |
| BFS level count | `O(n)` | `O(w)` | none |

Recursive DFS is cheaper on wide, shallow trees; BFS is safer on narrow, deep ones. Both are accepted; the bottom-up recursion is the one interviewers expect first.

=== implementation ===
```java
class Solution {
    public int maxDepth(TreeNode root) {
        if (root == null) {
            return 0;                               // empty tree has no levels
        }
        int left = maxDepth(root.left);             // ask the left subtree
        int right = maxDepth(root.right);           // ask the right subtree
        return 1 + Math.max(left, right);           // this node + the deeper side
    }
}
```

### The lines that matter

**1.**

```java
if (root == null) {
    return 0;                               // empty tree has no levels
}
```

The base case carries the definition. Returning `0` for `null` is what makes a leaf come out as `1 + max(0, 0) = 1` - one node, depth one. Return `1` here and every answer is one too large; forget the check and the first leaf throws `NullPointerException`.

**2.**

```java
return 1 + Math.max(left, right);           // this node + the deeper side
```

`1` counts the current node, `max` picks the deeper subtree. This line is the entire algorithm; everything else is plumbing.

**3.**

```java
int left = maxDepth(root.left);             // ask the left subtree
```

The method calls itself with a smaller tree. No helper, no extra parameters - `maxDepth` of a subtree is exactly the question we want answered for it. When the public method already has the right signature for the subproblem, use it directly.

### The BFS version, for very deep trees

```java
class Solution {
    public int maxDepth(TreeNode root) {
        if (root == null) return 0;

        Queue<TreeNode> queue = new ArrayDeque<>();
        queue.offer(root);
        int depth = 0;

        while (!queue.isEmpty()) {
            int levelSize = queue.size();           // freeze this level's size
            for (int i = 0; i < levelSize; i++) {
                TreeNode node = queue.poll();
                if (node.left != null) queue.offer(node.left);
                if (node.right != null) queue.offer(node.right);
            }
            depth++;                                // one full level done
        }
        return depth;
    }
}
```

`levelSize` must be read **before** the inner loop. Inside the loop the queue grows with the next level's nodes, and `queue.size()` would keep changing.

### Java notes

- `Math.max(int, int)` returns `int`; no casting needed.
- `Queue<TreeNode> queue = new ArrayDeque<>()` - `offer` adds to the back, `poll` removes from the front. `ArrayDeque` does not accept `null`, which is why children are checked before `offer`.
- The recursive version uses the JVM call stack. LeetCode's limit of 10^4 nodes fits; on an unbounded chain of hundreds of thousands of nodes it can throw `StackOverflowError`, and the BFS version is the safe choice.

=== edgeCases ===
### Empty tree

```text
root = null  ->  0
```

The base case fires immediately.

### Single node

```text
[1]  ->  1
```

`1 + max(0, 0)`. Depth counts nodes, so one node is depth one, not zero.

### LeetCode's second example: one child only

```text
[1, null, 2]  ->  2

    1
     \
      2
```

`maxDepth(1) = 1 + max(0, 1) = 2`. The missing left child contributes `0`, and `max` correctly ignores it.

### A chain (fully skewed)

```text
1 -> 2 -> 3 -> 4 -> 5, all left children  ->  5
```

`h = n`. The recursion goes 5 calls deep before the first one returns. This is the worst case for space.

### A perfect tree

```text
[1, 2, 3, 4, 5, 6, 7]  ->  3
```

`h = log2(n + 1) = 3`. The best case for space: only 3 frames at once, for 7 nodes.

### The deep side is the left side

```text
[1, 2, 3, 4, null, null, null, 5]  ->  4

        1
       / \
      2   3
     /
    4
   /
  5
```

`max` does not care which side wins. Left returns `3`, right returns `1`, answer `4`.

### A 100,000-node chain

```text
100,000 nodes, each the left child of the previous  ->  100000
```

Ten times LeetCode's limit. The BFS version returns `100000` with a queue that never holds more than one node. The recursive version needs 100,000 nested calls, which can exhaust a default JVM thread stack.

=== takeaway ===
> When you see **"height / depth / size / sum of a tree"**, think **`f(node) = combine(f(left), f(right))` with a base case for `null`** - postorder, one line of logic.

### The core observation

The answer for a tree is built from the answers for its two subtrees: `1 + max(L, R)`. Collecting paths stores everything and uses only lengths; passing the depth down needs a global; asking the children to report up needs nothing but the return value.

### The pattern trigger

```text
       answer for a node depends on its subtrees?
                       |
                      yes
                       v
       f(null) = <identity>      0 for depth/size/sum
       f(node) = combine( f(left), f(right) ) + this node's part
                       |
                       v
       depth:  1 + max(L, R)
       size:   1 + L + R
       sum:    node.val + L + R
```

### The common mistakes

**Counting edges instead of nodes.** Returning `-1` or `0` for a leaf; LeetCode wants `1`.

**Base case `return 1` for null.** Every depth comes out one too large.

**Copying `maxDepth` into Minimum Depth (LC 111) with `min`.** For `[1, null, 2]` the naive `1 + min(L, R)` returns `1`, because the missing left child reports `0`. But a missing child is not a leaf - the only leaf is `2`, so the minimum depth is `2`. When exactly one child is `null`, minimum depth must take the other side.

**Reading `queue.size()` inside the BFS loop** instead of freezing it in `levelSize` first.

### What to remember in six months

> A tree problem is usually one sentence: "my answer, given my children's answers". Write that sentence, write what `null` returns, and you are done.

The same shape solves Balanced Binary Tree (LC 110), Diameter of Binary Tree (LC 543), Count Complete Tree Nodes, and Path Sum variants. Diameter is the step up: the recursion still returns height, but at each node you also update a separate best with `L + R`.
