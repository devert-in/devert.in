=== intro ===
Yesterday the stack held **values waiting to be consumed** by an operator. Today it holds **elements waiting for an answer** - and that small shift in what the stack means is the single most reused idea of this whole week.

> When every element is asking "who is the first one after me that beats me?", do not send each one searching to the right. Let each new element arrive and answer everyone who was waiting for it.

=== problem ===
You get two arrays of **distinct** integers. `nums1` is a subset of `nums2`. For each value in `nums1`, find where it sits in `nums2` and return the **first element to its right in `nums2` that is greater** than it, or `-1` if there is none.

```text
nums1  = [4, 1, 2]
nums2  = [1, 3, 4, 2]
answer = [-1, 3, -1]
```

- `4` sits at index 2 of `nums2`. To its right is only `2`. Nothing greater: `-1`.
- `1` sits at index 0. The first thing to its right is `3`, which is greater: `3`.
- `2` is the last element of `nums2`. Nothing to its right at all: `-1`.

### "Next greater" means first, not largest

```text
nums2 = [1, 5, 3, 10]
next greater of 1 is 5, not 10
```

You stop at the **first** greater element. The biggest one further right is irrelevant.

### The example we will dry-run all day

```text
nums1 = [3, 4, 7, 2]
nums2 = [2, 7, 3, 5, 4, 6, 1]
```

| value in nums2 | 2 | 7 | 3 | 5 | 4 | 6 | 1 |
| :------------- | -: | -: | -: | -: | -: | -: | -: |
| next greater   | 7 | -1 | 5 | 6 | 6 | -1 | -1 |

So the answer for `nums1 = [3, 4, 7, 2]` is:

```text
answer = [5, 6, -1, 7]
```

Look at `5` and `4` - both get `6`, even though `4` is between them. One later element can answer several earlier ones at once. That is the fact today's solution is built on.

### The constraints that matter

| Constraint | Why it matters |
| :--------- | :------------- |
| All values in `nums2` are **distinct** | A value identifies its position, so a `value -> next greater` map is unambiguous. |
| `nums1` is a subset of `nums2` | Every query has a position in `nums2`; no "not found" case. |
| `0 <= values <= 10^4`, lengths `<= 1000` | The brute force passes here - the follow-up asks for `O(n + m)`, which is the real exercise. |

=== pattern ===
**Monotonic decreasing stack.**

Here is the reframe. Instead of each element **looking right** for its answer, walk left to right and let each new element **look back** at everyone still waiting.

Who is "still waiting" at any moment? Every earlier element that has not yet seen anything bigger than itself. And those waiting elements are always in **decreasing order**:

```text
waiting list after reading 2, 7, 3, 5, 4:   [7, 5, 4]
```

Why must it decrease? If a waiting element were smaller than a later waiting element, that later element would have been its next greater - so it would not be waiting any more. Contradiction.

Because the waiting list is sorted, a newcomer `x` resolves exactly the waiting elements smaller than `x` - and those are all at the **most recent** end. Pop them, record `x` as their answer, stop at the first one that is bigger than `x`, then join the list yourself. Most recent end only means a stack.

### Recognising it

Reach for a monotonic stack when:

- each element needs the **nearest** element to its left or right that is greater / smaller
- the brute force is "for each `i`, scan outward until the condition holds"
- one element can be the answer for a run of earlier elements

The mental question:

> When a new element arrives, which earlier elements does it settle - and are those always the most recent unsettled ones?

| You want | Stack order (bottom to top) | Pop while |
| :------- | :-------------------------- | :-------- |
| next **greater** | decreasing | `x > top` |
| next **smaller** | increasing | `x < top` |

=== bruteForce ===
Do exactly what the problem says, for each query separately.

### Step logic

For each value `q` in `nums1`:

1. Walk `nums2` from the start until you find `q` at index `j`.
2. From `j + 1`, walk right until you see something greater than `q`.
3. That element is the answer; if you run off the end, the answer is `-1`.

### Dry run

```text
nums1 = [3, 4, 7, 2]
nums2 = [2, 7, 3, 5, 4, 6, 1]
         0  1  2  3  4  5  6
```

| query | find: indices checked | found at `j` | scan `k` | `nums2[k]` | `> query`? | answer so far |
| ----: | :-------------------- | -----------: | -------: | ---------: | :--------- | ------------: |
| 3 | 0, 1, 2 | 2 | 3 | 5 | yes - stop | **5** |
| 4 | 0, 1, 2, 3, 4 | 4 | 5 | 6 | yes - stop | **6** |
| 7 | 0, 1 | 1 | 2 | 3 | no | -1 |
| 7 | | | 3 | 5 | no | -1 |
| 7 | | | 4 | 4 | no | -1 |
| 7 | | | 5 | 6 | no | -1 |
| 7 | | | 6 | 1 | no - end of array | **-1** |
| 2 | 0 | 0 | 1 | 7 | yes - stop | **7** |

```text
answer = [5, 6, -1, 7]
```

Correct. Total work: 11 comparisons to find positions, 8 comparisons scanning - 19 for 4 queries over 7 elements.

### Java

```java
class Solution {
    public int[] nextGreaterElement(int[] nums1, int[] nums2) {

        int[] ans = new int[nums1.length];

        for (int i = 0; i < nums1.length; i++) {

            // 1. find where nums1[i] sits in nums2
            int j = 0;
            while (nums2[j] != nums1[i]) {
                j++;
            }

            // 2. scan right for the first greater element
            int next = -1;
            for (int k = j + 1; k < nums2.length; k++) {
                if (nums2[k] > nums1[i]) {
                    next = nums2[k];
                    break;
                }
            }

            ans[i] = next;
        }

        return ans;
    }
}
```

### Complexity

**Time:** `O(n * m)` where `n = nums1.length`, `m = nums2.length` - **Space:** `O(1)` extra

### Where it hurts

The find step is the cheap waste - a `value -> index` map removes it. The scan is the real one.

Look at the `7` rows. The scan walks over `3, 5, 4, 6, 1` comparing each one with `7` and learns only "smaller than 7". But in passing it walked straight past the answers for `3` (which is `5`), for `5` and `4` (which are both `6`). If `nums1` asked about those too, each would launch its own scan over the same stretch.

The worst case makes it obvious. `nums2 = [7, 6, 5, 4, 3, 2, 1]` with every value queried: every scan runs to the end and finds nothing.

```text
scan from 7: 6 5 4 3 2 1   (6 comparisons)
scan from 6:   5 4 3 2 1   (5)
scan from 5:     4 3 2 1   (4)
...                        total  m(m-1)/2
```

The same elements are compared again and again, and every comparison against a smaller element is thrown away. What we want is for each element to be **looked at a constant number of times**, no matter how many queries pass over it.

=== optimization ===
### The key observation

Flip the direction of the question. An element does not need to find its answer - its answer will **arrive**. When we reach `6` while walking left to right, `6` is the next greater element of every still-unanswered element before it that is smaller than `6`.

And, as the pattern section showed, the unanswered elements are always in decreasing order, so the ones `6` settles are a contiguous run at the most recent end. Pop them; stop at the first one bigger than the newcomer; push the newcomer.

### The algorithm

1. Walk `nums2` once with a stack of unanswered values.
2. For each `x`: while the stack is non-empty and `x > top`, pop `top` and record `nextGreater[top] = x`.
3. Push `x` - it is now waiting too.
4. Anything left on the stack at the end never saw a greater element: answer `-1`.
5. Answer each query in `nums1` with one map lookup.

### Dry run on the same example

```text
nums2 = [2, 7, 3, 5, 4, 6, 1]
```

Stack shown bottom to top.

| i | x | stack before | pops (`top -> x`) | stack after push | map after |
| -: | -: | :----------- | :---------------- | :--------------- | :-------- |
| 0 | 2 | `[]` | none | `[2]` | `{}` |
| 1 | 7 | `[2]` | `2 -> 7` | `[7]` | `{2:7}` |
| 2 | 3 | `[7]` | none (3 < 7) | `[7, 3]` | `{2:7}` |
| 3 | 5 | `[7, 3]` | `3 -> 5`, then 5 < 7 stops | `[7, 5]` | `{2:7, 3:5}` |
| 4 | 4 | `[7, 5]` | none (4 < 5) | `[7, 5, 4]` | `{2:7, 3:5}` |
| 5 | 6 | `[7, 5, 4]` | `4 -> 6`, `5 -> 6`, then 6 < 7 stops | `[7, 6]` | `{2:7, 3:5, 4:6, 5:6}` |
| 6 | 1 | `[7, 6]` | none (1 < 6) | `[7, 6, 1]` | `{2:7, 3:5, 4:6, 5:6}` |

End of array. `7`, `6` and `1` are still waiting - they have no next greater element.

Now the queries:

| query | `getOrDefault(query, -1)` |
| ----: | ------------------------: |
| 3 | 5 |
| 4 | 6 |
| 7 | -1 |
| 2 | 7 |

```text
answer = [5, 6, -1, 7]
```

Same as the brute force. Read the "stack before" column top to bottom and check it is **decreasing in every row** - that invariant is what made every pop correct.

### Why it is linear

Row 5 popped two elements at once, so one step is not `O(1)`. But count across the whole run: 7 pushes and 4 pops. Every element is pushed exactly once and popped **at most once**, so the total number of stack operations is at most `2m`, whatever the input. That is amortised `O(1)` per element.

=== complexity ===
### Time

Each of the `m` elements of `nums2` is pushed once and popped at most once. Each of the `n` queries is one hash lookup.

```text
O(m + n)
```

### Space

The map holds at most `m` entries, and the stack at most `m` values (a strictly decreasing `nums2` keeps them all).

```text
O(m)
```

### Comparison

| Approach | Time | Extra space | Worst input |
| :------- | ---: | ----------: | :---------- |
| Find + scan right per query | `O(n * m)` | `O(1)` | decreasing `nums2` |
| `value -> index` map + scan right | `O(n * m)` | `O(m)` | decreasing `nums2` |
| Monotonic stack over `nums2` + map | **`O(n + m)`** | **`O(m)`** | none |

The middle row is the tempting half-fix: it removes the find step but keeps the scan, which is where the quadratic cost actually lives.

=== implementation ===
```java
class Solution {
    public int[] nextGreaterElement(int[] nums1, int[] nums2) {

        Map<Integer, Integer> nextGreater = new HashMap<>();
        Deque<Integer> stack = new ArrayDeque<>();   // values still waiting; decreasing bottom to top

        for (int x : nums2) {
            // x is the answer for every waiting value smaller than it.
            while (!stack.isEmpty() && x > stack.peek()) {
                nextGreater.put(stack.pop(), x);
            }
            stack.push(x);
        }
        // Whatever is still on the stack has no greater element: left out of the map.

        int[] ans = new int[nums1.length];
        for (int i = 0; i < nums1.length; i++) {
            ans[i] = nextGreater.getOrDefault(nums1[i], -1);
        }

        return ans;
    }
}
```

### The lines that matter

**1.**

```java
while (!stack.isEmpty() && x > stack.peek()) {
    nextGreater.put(stack.pop(), x);
}
```

`while`, not `if`. One newcomer can settle a whole run of waiting values - row 5 of the dry run settled `4` and `5` together. The `isEmpty()` check comes first so `peek()` is never called on an empty stack.

**2.**

```java
stack.push(x);
```

Unconditional, and **after** the loop. Every element waits for its own answer. Pushing it before the loop would compare `x` with itself.

**3.**

```java
ans[i] = nextGreater.getOrDefault(nums1[i], -1);
```

The leftover stack is never emptied explicitly. Anything never popped is simply absent from the map, and `getOrDefault` turns absence into `-1`.

### Java notes

- `x > stack.peek()` compares `int` with an auto-unboxed `Integer`, which is fine. Comparing two `Integer` objects with `==` would not be - it compares references and fails for values outside `-128..127`.
- Keying the map by **value** is only safe because `nums2` has distinct values. With duplicates you would store **indices** on the stack and write into an `int[]` by position - which is exactly tomorrow's problem.
- `ArrayDeque` is the stack: `push`, `pop`, `peek` all work on the head.

=== edgeCases ===
### LeetCode example 1

```text
nums1 = [4, 1, 2], nums2 = [1, 3, 4, 2]  ->  [-1, 3, -1]
```

Stack run: `1` popped by `3`, `3` popped by `4`, then `[4, 2]` left waiting.

### LeetCode example 2

```text
nums1 = [2, 4], nums2 = [1, 2, 3, 4]  ->  [3, -1]
```

### Single element

```text
nums1 = [1], nums2 = [1]  ->  [-1]
```

Pushed, never popped, absent from the map.

### Strictly increasing nums2

```text
nums1 = [1, 2, 3, 4], nums2 = [1, 2, 3, 4]  ->  [2, 3, 4, -1]
```

Every element is popped by the very next one. The stack never holds more than one value.

### Strictly decreasing nums2

```text
nums1 = [4, 3, 2, 1], nums2 = [4, 3, 2, 1]  ->  [-1, -1, -1, -1]
```

Nothing is ever popped; the stack ends holding all four. This is the brute force's worst case and the stack's largest memory use - and it is still one pass.

### First, not largest

```text
nums1 = [1], nums2 = [1, 5, 3, 10]  ->  [5]
```

`5` pops `1` the moment it arrives. `10` never gets the chance.

### Query order differs from nums2 order

```text
nums1 = [2, 1], nums2 = [1, 2]  ->  [-1, 2]
```

The answer follows `nums1`'s order. The map decouples the two orders - which is why we build it first and answer queries afterwards.

### One element settles many

```text
nums1 = [5, 4, 3, 9], nums2 = [5, 4, 3, 9]  ->  [9, 9, 9, -1]
```

`9` arrives to a stack `[5, 4, 3]` and pops all three in one step.

=== takeaway ===
> When you see **"first element to the right that is greater (or smaller)"**, think **monotonic stack**. Walk once; each newcomer pops and answers everyone smaller that is still waiting, then waits itself.

### The core observation

The unanswered elements are always sorted (decreasing for "next greater"), so a newcomer settles exactly a run at the most recent end. That turns "everyone scans right" into "everyone is pushed once and popped once".

### The pattern trigger

```text
      for each x, left to right
                |
                v
   while stack not empty AND x beats top:
          pop top          <- top's answer is x
                |
                v
           push x          <- x now waits
                |
                v
   left on the stack at the end = no answer (-1)
```

### The common mistakes

**`if` instead of `while`.** Settles only one waiting element per newcomer; in the example `5` would never get `6`.

**Wrong comparison direction.** `x < top` builds next **smaller**. Pick the direction from the question, then the stack order follows from it.

**Forgetting the leftovers.** If you write answers into an array without a default, the elements still on the stack keep whatever the array was initialised to. Default to `-1`.

### What to remember in six months

> A monotonic stack is a waiting room. Elements enter in order, and each new arrival dismisses everyone it beats. Each element enters once and leaves once, so the whole thing is linear.

The follow-up, Next Greater Element II (LC 503), makes the array circular: walk `2n` indices using `i % n`, and only push during the first lap. Tomorrow's Daily Temperatures is this same loop with **indices** on the stack instead of values, because the answer becomes a distance.
