=== intro ===
Seven days of binary search ended yesterday with Koko, where the "array" being searched was a range of speeds you never even built. Today the data stops being a line. A tree branches, so there is no single "next element" - and before you can solve any tree problem you need a reliable way to visit every node exactly once.

> A traversal is one recursive skeleton: handle the left subtree, handle the right subtree, and visit the node somewhere around them. Where you put the visit - before, between, or after - is the only thing that changes, and choosing it is the first decision in almost every tree problem.

=== problem ===
Given the `root` of a binary tree, return its node values in three orders:

| order | rule | LeetCode |
| :---- | :--- | :------- |
| Preorder | Root, then Left subtree, then Right subtree | LC 144 |
| Inorder | Left subtree, then Root, then Right subtree | LC 94 |
| Postorder | Left subtree, then Right subtree, then Root | LC 145 |

The rule applies **recursively**: "Left subtree" means "traverse the whole left subtree in the same order", not "the left child".

### The sample tree

```text
            1
          /   \
         2     3
        / \   / \
       4   5 6   7
```

```text
Preorder   1, 2, 4, 5, 3, 6, 7
Inorder    4, 2, 5, 1, 6, 3, 7
Postorder  4, 5, 2, 6, 7, 3, 1
```

Check inorder by hand. The root is `1`, so the answer is "inorder of the left subtree, then 1, then inorder of the right subtree":

```text
inorder(2-subtree) = inorder(4), 2, inorder(5) = 4, 2, 5
inorder(3-subtree) = inorder(6), 3, inorder(7) = 6, 3, 7
inorder(whole)     = 4, 2, 5,  1,  6, 3, 7
```

### The LeetCode node

LeetCode supplies the node type; you never declare it:

```text
TreeNode { int val; TreeNode left; TreeNode right; }
```

An absent child is `null`. An empty tree is `root == null`, and the expected answer for it is an empty list, not an exception.

### The constraints that matter

| constraint | value | what it means |
| :--------- | ----: | :------------ |
| nodes | 0 to 100 | empty tree is a real input |
| values | -100 to 100 | duplicates and negatives allowed - never identify a node by its value |

The follow-up on LC 94 asks: *recursive solution is trivial, could you do it iteratively?* That follow-up is what this day is really about.

=== pattern ===
**Depth-First Search** - go as deep as possible down one branch before backing up to try the next.

### One skeleton, three visit positions

```text
dfs(node):
    if node is null: return
    [PRE]   visit here  ->  preorder
    dfs(node.left)
    [IN]    visit here  ->  inorder
    dfs(node.right)
    [POST]  visit here  ->  postorder
```

The DFS itself is identical in all three. Every node is entered once, its left subtree is fully explored, then its right subtree. Only the moment you write the value down moves.

### Which order a problem wants

| visit position | the node sees... | typical use |
| :------------- | :--------------- | :---------- |
| Pre | nothing from its children yet | copying or serialising a tree, passing information **down** (depth, path so far) |
| In | its whole left subtree done | BSTs: inorder of a BST is **sorted** |
| Post | both subtrees done | computing something **from** the children: height, size, sums, deleting a tree |

### Recognising it

The mental question for any tree problem:

> Does a node need information from its parent (go preorder), from its children (go postorder), or does the left-node-right order itself mean something (go inorder)?

Tomorrow's problem, Maximum Depth, is a postorder problem: a node's depth is only known after both children report theirs.

=== bruteForce ===
The first solution anyone writes is the definition, transcribed: recursion. It is not "brute force" in the wasteful sense - it already visits each node once - but it is the naive version, and it hides the most important part of the algorithm inside the JVM.

### Step logic (inorder)

1. If the node is `null`, return.
2. Recurse into the left child.
3. Append the node's value.
4. Recurse into the right child.

### Dry run - recursive inorder on the sample tree

The "call stack" column is what the JVM is holding: every call that has started but not finished, bottom to top.

| step | executing | what happens | call stack (bottom -> top) | output |
| ---: | :-------- | :----------- | :------------------------- | :----- |
| 1 | `dfs(1)` | go left | `1` | `[]` |
| 2 | `dfs(2)` | go left | `1, 2` | `[]` |
| 3 | `dfs(4)` | go left: `dfs(null)` returns at once | `1, 2, 4` | `[]` |
| 4 | `dfs(4)` | visit 4 | `1, 2, 4` | `[4]` |
| 5 | `dfs(4)` | go right: `dfs(null)` returns; `dfs(4)` finishes | `1, 2` | `[4]` |
| 6 | `dfs(2)` | visit 2 | `1, 2` | `[4, 2]` |
| 7 | `dfs(5)` | go left: null | `1, 2, 5` | `[4, 2]` |
| 8 | `dfs(5)` | visit 5; go right: null; finishes | `1, 2` | `[4, 2, 5]` |
| 9 | `dfs(2)` | both sides done; finishes | `1` | `[4, 2, 5]` |
| 10 | `dfs(1)` | visit 1 | `1` | `[4, 2, 5, 1]` |
| 11 | `dfs(3)` | go left | `1, 3` | `[4, 2, 5, 1]` |
| 12 | `dfs(6)` | left null; visit 6; right null; finishes | `1, 3` | `[4, 2, 5, 1, 6]` |
| 13 | `dfs(3)` | visit 3 | `1, 3` | `[4, 2, 5, 1, 6, 3]` |
| 14 | `dfs(7)` | left null; visit 7; right null; finishes | `1, 3` | `[4, 2, 5, 1, 6, 3, 7]` |
| 15 | `dfs(3)`, `dfs(1)` | both finish | empty | `[4, 2, 5, 1, 6, 3, 7]` |

Notice the call stack never holds more than 3 frames. That is the tree's height, not its size.

### Java

All three orders, sharing nothing but the shape:

```java
class Solution {

    public List<Integer> inorderTraversal(TreeNode root) {
        List<Integer> result = new ArrayList<>();
        inorder(root, result);
        return result;
    }

    private void inorder(TreeNode node, List<Integer> result) {
        if (node == null) return;
        inorder(node.left, result);
        result.add(node.val);           // visit BETWEEN the two calls
        inorder(node.right, result);
    }

    public List<Integer> preorderTraversal(TreeNode root) {
        List<Integer> result = new ArrayList<>();
        preorder(root, result);
        return result;
    }

    private void preorder(TreeNode node, List<Integer> result) {
        if (node == null) return;
        result.add(node.val);           // visit BEFORE the two calls
        preorder(node.left, result);
        preorder(node.right, result);
    }

    public List<Integer> postorderTraversal(TreeNode root) {
        List<Integer> result = new ArrayList<>();
        postorder(root, result);
        return result;
    }

    private void postorder(TreeNode node, List<Integer> result) {
        if (node == null) return;
        postorder(node.left, result);
        postorder(node.right, result);
        result.add(node.val);           // visit AFTER the two calls
    }
}
```

### Complexity

**Time:** `O(n)` - **Space:** `O(h)` call stack, where `h` is the tree's height

### Where it hurts

Nothing is computed twice, so the time cannot improve: you have to output `n` values. The weaknesses are elsewhere.

**The stack is invisible.** The table's "call stack" column is doing all the bookkeeping - remembering that after finishing node `4` we must come back to `2` and visit it. The code never shows that. If an interviewer asks "do it without recursion", you cannot answer unless you know what that column was holding.

**The stack is the JVM's, and it is small.** A tree with 100,000 nodes in a straight line (each node only has a left child) needs 100,000 nested calls. The default thread stack can run out long before that and throw `StackOverflowError`. LeetCode's 100-node limit hides this; production data does not.

The fix for both: take the call stack out of the JVM and hold it yourself.

=== optimization ===
The recursive call stack stores exactly one thing per frame: **a node whose left subtree we are still exploring, and which we must come back to.** Replace it with an explicit `Deque<TreeNode>` and you get the same traversal with the bookkeeping in plain sight.

### Key observation (inorder)

In the dry run, a node was visited at the moment its frame resumed after the left call returned. So:

1. From the current node, keep going left, **pushing** every node you pass. These are the frames waiting for their left subtree to finish.
2. When you cannot go left any more, the top of the stack is the leftmost unvisited node. **Pop and visit** it - its left side is done.
3. Move to its **right** child and repeat from step 1. (Its frame does not need to come back after the right subtree, so it is not pushed again.)

Stop when there is no current node **and** the stack is empty.

### Dry run - iterative inorder on the same tree

| step | curr before | action | stack after (bottom -> top) | curr after | output |
| ---: | ----------: | :----- | :-------------------------- | ---------: | :----- |
| 1 | 1 | push 1, go left | `1` | 2 | `[]` |
| 2 | 2 | push 2, go left | `1, 2` | 4 | `[]` |
| 3 | 4 | push 4, go left | `1, 2, 4` | null | `[]` |
| 4 | null | pop 4, visit, go right | `1, 2` | null | `[4]` |
| 5 | null | pop 2, visit, go right | `1` | 5 | `[4, 2]` |
| 6 | 5 | push 5, go left | `1, 5` | null | `[4, 2]` |
| 7 | null | pop 5, visit, go right | `1` | null | `[4, 2, 5]` |
| 8 | null | pop 1, visit, go right | empty | 3 | `[4, 2, 5, 1]` |
| 9 | 3 | push 3, go left | `3` | 6 | `[4, 2, 5, 1]` |
| 10 | 6 | push 6, go left | `3, 6` | null | `[4, 2, 5, 1]` |
| 11 | null | pop 6, visit, go right | `3` | null | `[4, 2, 5, 1, 6]` |
| 12 | null | pop 3, visit, go right | empty | 7 | `[4, 2, 5, 1, 6, 3]` |
| 13 | 7 | push 7, go left | `7` | null | `[4, 2, 5, 1, 6, 3]` |
| 14 | null | pop 7, visit, go right | empty | null | `[4, 2, 5, 1, 6, 3, 7]` |
| 15 | null | `curr == null` and stack empty: stop | empty | null | `[4, 2, 5, 1, 6, 3, 7]` |

Compare row 8 here with row 10 of the recursive table: popping `1` is the moment `dfs(1)` resumed. The explicit stack is the call stack, minus the frames that had nothing left to do.

### Preorder - simpler, because the visit comes first

Preorder visits a node the moment it is reached, so nothing needs to wait. Pop, visit, then push the children - **right first**, so that left is on top and comes out first.

| step | pop | visit | push | stack after (bottom -> top) | output |
| ---: | --: | ----: | :--- | :-------------------------- | :----- |
| 0 | - | - | root 1 | `1` | `[]` |
| 1 | 1 | 1 | 3, then 2 | `3, 2` | `[1]` |
| 2 | 2 | 2 | 5, then 4 | `3, 5, 4` | `[1, 2]` |
| 3 | 4 | 4 | - | `3, 5` | `[1, 2, 4]` |
| 4 | 5 | 5 | - | `3` | `[1, 2, 4, 5]` |
| 5 | 3 | 3 | 7, then 6 | `7, 6` | `[1, 2, 4, 5, 3]` |
| 6 | 6 | 6 | - | `7` | `[1, 2, 4, 5, 3, 6]` |
| 7 | 7 | 7 | - | empty | `[1, 2, 4, 5, 3, 6, 7]` |

### Postorder - preorder's mirror, reversed

Postorder is Left, Right, Root. Read it backwards and you get Root, Right, Left - which is preorder with the children swapped. So run that easy traversal (push left first, then right) and **prepend** each value instead of appending:

```text
Root-Right-Left order:  1, 3, 7, 6, 2, 5, 4
reversed:               4, 5, 2, 6, 7, 3, 1   = postorder
```

The implementation section also shows a one-stack postorder that visits nodes in true postorder, for when the order of visiting matters and not only the output list.

=== complexity ===
### Time

Every node is pushed once and popped once (iterative) or entered once (recursive).

```text
O(n)
```

### Space

The stack holds at most one node per level of the current path, so it is bounded by the height `h`.

```text
O(h)    balanced tree: h = log n     skewed tree: h = n
```

The output list is `O(n)` but it is the required answer, not extra space.

### Comparison

| Approach | Time | Extra space | Stack lives in | Deep-tree risk |
| :------- | ---: | ----------: | :------------- | :------------- |
| Recursive | `O(n)` | `O(h)` | JVM call stack | `StackOverflowError` |
| Iterative, explicit stack | `O(n)` | `O(h)` | heap (`ArrayDeque`) | none |
| Morris (follow-up) | `O(n)` | **`O(1)`** | nowhere - borrows null pointers | none |

On the sample tree, `h = 3`. A 100-node tree shaped like a linked list has `h = 100`.

=== implementation ===
```java
class Solution {

    // LC 94 - Left, Root, Right
    public List<Integer> inorderTraversal(TreeNode root) {
        List<Integer> result = new ArrayList<>();
        Deque<TreeNode> stack = new ArrayDeque<>();
        TreeNode curr = root;

        while (curr != null || !stack.isEmpty()) {
            while (curr != null) {          // dive left, remembering the path
                stack.push(curr);
                curr = curr.left;
            }
            curr = stack.pop();             // leftmost node not yet visited
            result.add(curr.val);           // its left side is done: visit
            curr = curr.right;              // now handle its right subtree
        }
        return result;
    }

    // LC 144 - Root, Left, Right
    public List<Integer> preorderTraversal(TreeNode root) {
        List<Integer> result = new ArrayList<>();
        if (root == null) return result;

        Deque<TreeNode> stack = new ArrayDeque<>();
        stack.push(root);
        while (!stack.isEmpty()) {
            TreeNode node = stack.pop();
            result.add(node.val);
            if (node.right != null) stack.push(node.right);   // pushed first, popped last
            if (node.left != null) stack.push(node.left);
        }
        return result;
    }

    // LC 145 - Left, Right, Root
    public List<Integer> postorderTraversal(TreeNode root) {
        LinkedList<Integer> result = new LinkedList<>();
        if (root == null) return result;

        Deque<TreeNode> stack = new ArrayDeque<>();
        stack.push(root);
        while (!stack.isEmpty()) {
            TreeNode node = stack.pop();
            result.addFirst(node.val);      // Root-Right-Left, written backwards
            if (node.left != null) stack.push(node.left);
            if (node.right != null) stack.push(node.right);
        }
        return result;
    }
}
```

### The lines that matter

**1.**

```java
while (curr != null || !stack.isEmpty()) {
```

Two reasons to keep going: there is a subtree still to dive into (`curr`), or there are ancestors waiting to be visited (`stack`). Checking only the stack fails twice: the loop would never start (the stack begins empty), and even if forced to start it would stop after step 8 of the dry run, when the stack is momentarily empty but `curr` is `3` and the whole right subtree is still unvisited.

**2.**

```java
curr = stack.pop();             // leftmost node not yet visited
result.add(curr.val);           // its left side is done: visit
curr = curr.right;              // now handle its right subtree
```

These three lines are the recursive frame resuming: visit, then make the right call. Setting `curr` to the right child - even when it is `null` - is what makes the next iteration either dive into that subtree or fall through to the next pop.

**3.**

```java
if (node.right != null) stack.push(node.right);   // pushed first, popped last
if (node.left != null) stack.push(node.left);
```

A stack reverses order. To get left before right out, push right before left in. Swapping these two lines silently produces Root-Right-Left.

### Postorder with one stack, in true visit order

The reversal trick produces the right list, but it touches nodes in Root-Right-Left order. When each node must be **processed** only after both children (for example freeing memory, or combining child results), use one stack and remember the last node you visited:

```java
class Solution {
    public List<Integer> postorderTraversal(TreeNode root) {
        List<Integer> result = new ArrayList<>();
        Deque<TreeNode> stack = new ArrayDeque<>();
        TreeNode curr = root;
        TreeNode lastVisited = null;

        while (curr != null || !stack.isEmpty()) {
            while (curr != null) {
                stack.push(curr);
                curr = curr.left;
            }
            TreeNode top = stack.peek();
            if (top.right != null && top.right != lastVisited) {
                curr = top.right;           // right subtree not done yet: go do it
            } else {
                result.add(top.val);        // both sides done: visit
                lastVisited = stack.pop();
            }
        }
        return result;
    }
}
```

`top.right != lastVisited` is how a node tells "I am back from my left subtree" (right not done yet) apart from "I am back from my right subtree" (time to visit).

### Morris inorder - the O(1) space follow-up

Morris traversal needs no stack. Before descending left, it makes the rightmost node of the left subtree (the in-order predecessor) point back to the current node - a temporary "thread" that replaces the stack entry. On the second arrival it removes the thread, so the tree is left exactly as it was found.

```java
class Solution {
    public List<Integer> inorderTraversal(TreeNode root) {
        List<Integer> result = new ArrayList<>();
        TreeNode curr = root;

        while (curr != null) {
            if (curr.left == null) {
                result.add(curr.val);
                curr = curr.right;
            } else {
                TreeNode pred = curr.left;
                while (pred.right != null && pred.right != curr) {
                    pred = pred.right;
                }
                if (pred.right == null) {
                    pred.right = curr;          // thread: come back here later
                    curr = curr.left;
                } else {
                    pred.right = null;          // second arrival: undo the thread
                    result.add(curr.val);
                    curr = curr.right;
                }
            }
        }
        return result;
    }
}
```

Still `O(n)` time - each edge is walked at most a constant number of times - with `O(1)` extra space. Mention it if asked about space; write the stack version first.

### Java notes

- `Deque<TreeNode> stack = new ArrayDeque<>()` is the modern Java stack. `push`, `pop` and `peek` all work on the front. The old `java.util.Stack` class is synchronised and extends `Vector`; avoid it in new code.
- `ArrayDeque` rejects `null` elements, which is why the preorder and postorder versions check children before pushing.
- `LinkedList.addFirst` is `O(1)`. Prepending to an `ArrayList` with `add(0, x)` is `O(n)` per call and turns postorder into `O(n^2)`; the alternative is append and then `Collections.reverse` once at the end.
- Returning a `LinkedList<Integer>` from a method declared to return `List<Integer>` is fine - it implements `List`.

=== edgeCases ===
### Empty tree

```text
root = null  ->  inorder [], preorder [], postorder []
```

Inorder: the `while` condition is false immediately. Preorder and postorder: the explicit `root == null` check returns the empty list before anything is pushed onto an `ArrayDeque` that would reject `null`.

### Single node

```text
[1]  ->  inorder [1], preorder [1], postorder [1]
```

### LeetCode's example: `[1, null, 2, 3]`

```text
    1
     \
      2
     /
    3

inorder [1, 3, 2]    preorder [1, 2, 3]    postorder [3, 2, 1]
```

The root has no left child, so it is visited first in inorder, then its right subtree `(3, 2)` in inorder.

### Left-skewed tree

```text
      1
     /
    2
   /
  3

inorder [3, 2, 1]    preorder [1, 2, 3]    postorder [3, 2, 1]
```

The stack grows to the full height (3) before the first pop. This is the shape where `h = n`.

### Right-skewed tree

```text
  1
   \
    2
     \
      3

inorder [1, 2, 3]    preorder [1, 2, 3]    postorder [3, 2, 1]
```

Inorder's stack never holds more than one node here - each node is pushed, popped, and replaced by its right child.

### A BST - inorder comes out sorted

```text
        4
      /   \
     2     6
    / \   / \
   1   3 5   7

inorder [1, 2, 3, 4, 5, 6, 7]
```

Every node is greater than its left subtree and smaller than its right, so Left-Root-Right lists them in ascending order. This is the property behind Validate BST and Kth Smallest in a BST.

### Duplicate and negative values

```text
     0
    / \
  -1   0

inorder [-1, 0, 0]    preorder [0, -1, 0]    postorder [-1, 0, 0]
```

The traversals follow pointers, never values, so duplicates and negatives need no care at all.

### A very deep tree

A left-skewed chain of 100,000 nodes: the iterative versions return all 100,000 values; the recursive version needs 100,000 nested calls and can throw `StackOverflowError` on a default JVM stack. Not reachable within LeetCode's 100-node limit, but it is the reason the iterative form exists.

=== takeaway ===
> When you see **"visit every node of a tree"**, think **DFS with the visit before, between, or after the two recursive calls** - and when recursion is not allowed, **an explicit stack holding the nodes you still have to come back to**.

### The core observation

The three traversals are one algorithm. The DFS always goes left subtree, then right subtree; only the moment of writing the value moves. The recursive call stack holds "nodes waiting for their left subtree to finish", and an explicit `Deque` can hold exactly the same thing.

### The pattern trigger

```text
             tree problem
                  |
                  v
   what does a node need, and from where?
        |               |                 |
   from parent      left-node-right    from children
   (depth, path)    order matters      (height, size, sum)
        |               |                 |
     PREorder        INorder          POSTorder
                        |
                  BST -> sorted
```

### The common mistakes

**Checking only the stack in iterative inorder.** The stack starts empty, and it empties again for a moment after the root is popped, while the whole right subtree is still waiting in `curr`. The loop needs `curr != null || !stack.isEmpty()`.

**Pushing left before right in iterative preorder.** The stack reverses it, and you get Root-Right-Left.

**Prepending to an `ArrayList`.** `add(0, x)` shifts every element; the postorder becomes quadratic.

**Treating "left subtree" as "left child".** Inorder of the sample tree is not `2, 1, 3, ...`; the whole left subtree `4, 2, 5` comes before `1`.

### What to remember in six months

> Pre, in, post is a question of **when** you visit, not **how** you move. The movement is always the same depth-first walk, and its memory is a stack of the nodes you still owe a visit.

From here, almost every tree problem is one of these three walks with a small piece of work at the visit point: Maximum Depth (post), Invert Tree (pre or post), Validate BST (in), Path Sum (pre), Diameter (post).
