=== intro ===
Yesterday the interesting edge was the one that sat **on** a cycle - it was redundant, so removing it cost nothing. Today flips that around: the interesting edges are the ones that sit on **no** cycle at all, because removing one of them splits the network in two.

> A single DFS records far more than "visited or not". If you also write down **when** each node was discovered and **how far back** its subtree can reach, one traversal answers questions that otherwise need a traversal per edge.

=== problem ===
There are `n` servers numbered `0..n-1`, joined by undirected `connections`. A connection is **critical** if removing it leaves some server unable to reach some other server. Return every critical connection, in any order.

Graph theory calls these edges **bridges**.

```text
n = 5
connections = [[0,1], [1,2], [2,0], [1,3], [3,4]]
answer      = [[1,3], [3,4]]
```

Draw it:

```text
    0 ----- 1 ----- 3 ----- 4
     \     /
      \   /
        2
```

Check each edge by hand:

| edge | if removed, can everyone still reach everyone? | critical? |
| :--- | :--------------------------------------------- | :-------- |
| `[0,1]` | yes - `0` still reaches `1` through `2` | no |
| `[1,2]` | yes - `1` still reaches `2` through `0` | no |
| `[2,0]` | yes - `2` still reaches `0` through `1` | no |
| `[1,3]` | no - `{3, 4}` is cut off from `{0, 1, 2}` | **yes** |
| `[3,4]` | no - `4` is cut off | **yes** |

The three triangle edges each have a detour. The two tail edges have none.

### The one-sentence definition worth remembering

> An edge is a bridge **exactly when it lies on no cycle**.

If an edge `(u, v)` is on a cycle, the rest of the cycle is a detour from `u` to `v`, so removing the edge disconnects nothing. If it is on no cycle, there is no other route, and removing it separates `u` from `v`.

### What the constraints tell you

- `2 <= n <= 10^5`, `n - 1 <= connections.length <= 10^5`. The graph is connected, and there are no repeated connections.
- With `10^5` edges, anything that does a full traversal **per edge** is about `10^10` operations. The constraint is telling you the answer must come out of **one** traversal: `O(V + E)`.

=== pattern ===
**Tarjan's bridge-finding algorithm** - a DFS that records discovery time and low-link.

Run a DFS and label each node with:

- `disc[u]` - the **time** `u` was first discovered (0, 1, 2, ... in visiting order).
- `low[u]` - the **earliest discovery time** reachable from `u`'s DFS subtree, using tree edges downward and **at most one** non-tree edge back up.

Then a tree edge from parent `u` to child `v` is a bridge exactly when

```text
low[v] > disc[u]
```

In words: nothing in `v`'s subtree can climb back to `u` or anything discovered before `u` without using the edge `(u, v)` itself. So that edge is the subtree's only lifeline.

### Why a DFS can see cycles this way

In an **undirected** DFS, every edge is one of two kinds:

- a **tree edge** - the DFS used it to discover a new node, or
- a **back edge** - it connects a node to one of its own **ancestors** in the DFS tree.

There are no "cross" edges between unrelated branches: if `u` had an edge to an unvisited node in another branch, the DFS would have walked down it from `u` first, making it `u`'s descendant.

So every cycle in the graph is a path of tree edges closed by one back edge. A back edge from deep in `v`'s subtree to above `u` means there is a cycle passing through `(u, v)`. `low[v]` is the measurement of whether such a back edge exists.

### Recognising it

Reach for disc/low DFS when:

- the question is about **single points of failure** - an edge or a node whose removal disconnects the graph
- the words are "critical connection", "bridge", "cut edge", "articulation point", "cut vertex", "biconnected", "2-edge-connected"
- removing each element and re-checking connectivity would be correct but too slow

The mental question:

> Can this subtree get back above its parent without using the edge that connects them?

=== bruteForce ===
Take the definition literally. For each edge, remove it, and check if the graph is still connected. If it is not, the edge is critical.

"Still connected" is one DFS from node `0`: count how many nodes it reaches. If the count is less than `n`, something got cut off.

### Dry run

```text
n = 5
connections = [[0,1], [1,2], [2,0], [1,3], [3,4]]
```

The DFS column lists nodes in the order a recursive DFS from `0` first reaches them, trying neighbours in the order their edges appear.

| skip | removed edge | edges left | DFS from 0 reaches | count | `< 5`? | bridges after |
| ---: | :----------- | :--------- | :----------------- | ----: | :----- | :------------ |
| 0 | `[0,1]` | `[1,2] [2,0] [1,3] [3,4]` | 0, 2, 1, 3, 4 | 5 | no | `[]` |
| 1 | `[1,2]` | `[0,1] [2,0] [1,3] [3,4]` | 0, 1, 3, 4, 2 | 5 | no | `[]` |
| 2 | `[2,0]` | `[0,1] [1,2] [1,3] [3,4]` | 0, 1, 2, 3, 4 | 5 | no | `[]` |
| 3 | `[1,3]` | `[0,1] [1,2] [2,0] [3,4]` | 0, 1, 2 | 3 | **yes** | `[[1,3]]` |
| 4 | `[3,4]` | `[0,1] [1,2] [2,0] [1,3]` | 0, 1, 2, 3 | 4 | **yes** | `[[1,3], [3,4]]` |

Row 0 is worth a second look: without `[0,1]`, the DFS reaches `1` the long way, `0 -> 2 -> 1`. That detour is the cycle doing its job.

### Java

```java
class Solution {
    public List<List<Integer>> criticalConnections(int n, List<List<Integer>> connections) {

        List<List<Integer>> bridges = new ArrayList<>();

        // Remove each edge in turn; if node 0 can no longer reach everyone, it was critical.
        for (int skip = 0; skip < connections.size(); skip++) {
            if (countReachable(n, connections, skip) < n) {
                bridges.add(connections.get(skip));
            }
        }

        return bridges;
    }

    private int countReachable(int n, List<List<Integer>> connections, int skip) {

        List<List<Integer>> adj = new ArrayList<>();
        for (int i = 0; i < n; i++) {
            adj.add(new ArrayList<>());
        }
        for (int i = 0; i < connections.size(); i++) {
            if (i == skip) continue;
            int a = connections.get(i).get(0);
            int b = connections.get(i).get(1);
            adj.get(a).add(b);
            adj.get(b).add(a);
        }

        boolean[] seen = new boolean[n];
        Deque<Integer> stack = new ArrayDeque<>();
        stack.push(0);
        seen[0] = true;
        int count = 1;

        while (!stack.isEmpty()) {
            int u = stack.pop();
            for (int v : adj.get(u)) {
                if (!seen[v]) {
                    seen[v] = true;
                    count++;
                    stack.push(v);
                }
            }
        }

        return count;
    }
}
```

(The stack-based DFS here may reach nodes in a different order from the table. The **count** is what decides the answer, and it is the same.)

### Complexity

**Time:** `O(E * (V + E))` - **Space:** `O(V + E)`

### Where it hurts

Every row rebuilds the graph and walks **all of it**, just to learn about **one** edge. At the constraint limit that is `10^5` traversals of a `10^5`-edge graph.

And the traversals are almost identical. Look at rows 0, 1 and 2: each one walks the triangle, discovers the triangle has a detour, and forgets it. Row 3 and row 4 both walk the triangle again before reaching the part that matters.

The question each row is really asking is local:

> Does the edge `(u, v)` have a detour?

A detour exists exactly when the edge is on a cycle. A single DFS already **sees** every cycle - each one shows up as a back edge to an ancestor. If we record, during that one DFS, how far back each subtree can reach, we can answer the local question for every edge at once.

=== optimization ===
### The key observation

Run one DFS. Look at a tree edge from parent `u` down to child `v`. The nodes below it form `v`'s subtree.

```text
        (earlier nodes)
              |
              u          disc[u]
              |
              v   <-- the tree edge in question
            / | \
        (v's subtree)
```

If **any** node in `v`'s subtree has a back edge to `u` or to something discovered **before** `u`, then there is a loop through `(u, v)`, and the edge has a detour. If none does, `(u, v)` is the only connection between the subtree and the rest of the graph.

So for each node compute:

```text
low[v] = min( disc[v],
              disc[w]  for every back edge v -> w,
              low[c]   for every DFS child c of v )
```

and the test becomes

```text
low[v] >  disc[u]   ->   (u, v) is a bridge
low[v] <= disc[u]   ->   some back edge reaches u or above: not a bridge
```

### Why the comparison is strict

If `low[v] == disc[u]`, the subtree has a back edge landing **on `u` itself**. Then `u -> v -> ... -> u` is a cycle containing the edge `(u, v)`, so it is not a bridge. Only `low[v] > disc[u]` - the subtree cannot get even as high as `u` - means the edge is the sole link. (Tomorrow's articulation points use `>=` for exactly this reason: a back edge landing on `u` saves the **edge** but not the **vertex**.)

### Why the parent must be skipped

The edge `(u, v)` appears in `v`'s adjacency list as `v -> u`. If we treated that as a back edge, every child would claim `low[v] <= disc[u]` using the very edge we are testing, and **no bridge would ever be found**. So when exploring `v`, the edge back to its parent is ignored.

### Reading the final arrays

```text
node    0  1  2  3  4
disc    0  1  2  3  4
low     0  0  0  3  4
```

The triangle nodes all have `low = 0`: each can reach node `0`'s discovery time. Node `3`'s subtree (`{3, 4}`) can only reach time `3` - itself - so it cannot get above `1`, and the edge `(1,3)` is its only lifeline. Node `4` can only reach itself, so `(3,4)` is a bridge too.

Step 8 is the moment the cycle is "noticed": the back edge `2 -> 0` pulls `low[2]` down to `0`, and step 9 passes that up to `1`. Step 19 shows the same edge seen from the other side - harmless, because `disc[2]` is larger than `low[0]` already.

=== complexity ===
### Time

One DFS. Every node is entered once, and every edge is looked at twice (once from each end).

```text
O(V + E)
```

Building the adjacency list is also `O(V + E)`.

### Space

The adjacency list holds every edge twice: `O(V + E)`. `disc` and `low` are `O(V)`. The recursion stack can be as deep as `V` on a path-shaped graph.

```text
O(V + E)
```

### Comparison

| Approach | Time | Space | At `V = E = 10^5` |
| :------- | ---: | ----: | :---------------- |
| Remove each edge, DFS for connectivity | `O(E * (V + E))` | `O(V + E)` | about `2 * 10^10` steps - too slow |
| **Tarjan disc/low DFS** | **`O(V + E)`** | **`O(V + E)`** | about `3 * 10^5` steps |

Same graph, same DFS machinery. The only change is that the DFS **writes down** two numbers per node instead of throwing that information away.

=== implementation ===
```java
class Solution {

    private List<List<Integer>> adj;
    private int[] disc;    // discovery time of each node, -1 if unvisited
    private int[] low;     // earliest discovery time reachable from the node's subtree
    private int timer = 0;
    private List<List<Integer>> bridges;

    public List<List<Integer>> criticalConnections(int n, List<List<Integer>> connections) {

        adj = new ArrayList<>();
        for (int i = 0; i < n; i++) {
            adj.add(new ArrayList<>());
        }
        for (List<Integer> c : connections) {
            adj.get(c.get(0)).add(c.get(1));
            adj.get(c.get(1)).add(c.get(0));
        }

        disc = new int[n];
        low = new int[n];
        Arrays.fill(disc, -1);
        bridges = new ArrayList<>();

        for (int i = 0; i < n; i++) {
            if (disc[i] == -1) {
                dfs(i, -1);
            }
        }

        return bridges;
    }

    private void dfs(int u, int parent) {

        disc[u] = low[u] = timer++;

        for (int v : adj.get(u)) {
            if (v == parent) continue;              // never use the edge we came down

            if (disc[v] == -1) {                    // tree edge
                dfs(v, u);
                low[u] = Math.min(low[u], low[v]);
                if (low[v] > disc[u]) {             // subtree cannot climb to u or above
                    bridges.add(Arrays.asList(u, v));
                }
            } else {                                // back edge to an ancestor
                low[u] = Math.min(low[u], disc[v]);
            }
        }
    }
}
```

### The lines that matter

**1.**

```java
if (v == parent) continue;              // never use the edge we came down
```

Without this, the edge back to the parent counts as a back edge, `low[v]` drops to `disc[u]`, and the strict test below never fires. The result is an empty answer on every graph.

**2.**

```java
low[u] = Math.min(low[u], low[v]);
if (low[v] > disc[u]) {             // subtree cannot climb to u or above
```

The first line passes a child's reach up to its parent - a back edge found deep in the tree lowers `low` all the way up the chain. The second line is the bridge test, with the strict `>` the optimisation section justified.

**3.**

```java
low[u] = Math.min(low[u], disc[v]);
```

For a back edge, take `disc[v]`, **not** `low[v]`. `low` is defined as "reachable using at most one back edge"; taking `low[v]` here would chain a second one. For bridges both versions happen to give the same answer, but `disc[v]` is the textbook definition and the one that stays correct when you reuse this code for articulation points tomorrow.

### Java notes

- `disc[u] = low[u] = timer++;` assigns right to left: `timer++` yields the old value, which goes into `low[u]`, then into `disc[u]`. Both start equal - a node can always reach itself.
- `Arrays.fill(disc, -1)` makes `-1` the "unvisited" marker. Using `0` would not work, because the first node is discovered at time `0`.
- Skipping by **parent vertex** is safe because LeetCode guarantees no repeated connections. With parallel edges (two separate cables between `u` and `v`), neither is a bridge, and you must skip by **edge index** instead so the second cable still counts as a back edge.
- The recursion can reach depth `n` on a path-shaped graph. LeetCode's Java stack handles `10^5` here; on a default local JVM it may throw `StackOverflowError`, in which case run it in a `new Thread(null, runnable, "dfs", 1 << 26)` or convert the DFS to an explicit stack.
- The outer `for` loop calls `dfs` on every unvisited node. LeetCode's graph is connected, so it only fires once, but the loop makes the method correct for disconnected graphs too.

=== edgeCases ===
### Two nodes, one edge

```text
n = 2, [[0,1]]  ->  [[0,1]]
```

`disc = [0, 1]`, `low = [0, 1]`. `low[1] = 1 > disc[0] = 0`, so the only edge is a bridge.

### A single cycle

```text
n = 3, [[0,1], [1,2], [2,0]]  ->  []
```

Every edge has a detour. The back edge `2 -> 0` drives `low` to `0` for every node, so no `low[v] > disc[u]` ever holds.

### A tree - every edge is a bridge

```text
n = 4, [[0,1], [1,2], [2,3]]  ->  [[2,3], [1,2], [0,1]]
```

No cycles at all, so no back edges, so every `low[v] = disc[v] > disc[u]`. Bridges are reported deepest first, because the test runs as the recursion unwinds.

### A star

```text
n = 4, [[0,1], [0,2], [0,3]]  ->  [[0,1], [0,2], [0,3]]
```

Every leaf hangs on one edge.

### Two cycles joined by one edge

```text
n = 6, [[0,1], [1,2], [2,0], [2,3], [3,4], [4,5], [5,3]]  ->  [[2,3]]
```

Each triangle has internal detours; the edge between them has none. `low[3] = 3` (its triangle only reaches back to itself) and `disc[2] = 2`, so `3 > 2`.

### The parent-edge trap

```text
n = 2, [[0,1]]   with the "skip parent" line deleted  ->  []   (wrong)
```

At node `1`, the edge back to `0` is mistaken for a back edge, `low[1]` becomes `0`, and `0 > 0` is false. The most common bug in this algorithm, and it fails on the smallest possible input.

### A very long path

```text
n = 100000, [[0,1], [1,2], ..., [99998,99999]]  ->  all 99999 edges
```

Correct, but the recursion is 100000 frames deep. Fine on LeetCode; locally, give the thread a larger stack or use an iterative DFS.

=== takeaway ===
> When you see **"which edge, if removed, disconnects the graph"**, think **one DFS with `disc` and `low`**, and test each tree edge with `low[child] > disc[parent]`.

### The core observation

An edge is a bridge exactly when it is on no cycle. In an undirected DFS every cycle closes with a back edge to an ancestor, so "is `(u, v)` on a cycle?" becomes "can `v`'s subtree reach `u` or above with one back edge?" - and `low[v]` is precisely that measurement.

### The pattern trigger

```text
        DFS enters u:  disc[u] = low[u] = timer++
                         |
            for each neighbour v of u
          /              |                 \
   v == parent      v unvisited           v visited
     skip           dfs(v, u)            back edge:
                    low[u] = min(        low[u] = min(
                      low[u], low[v])      low[u], disc[v])
                    low[v] > disc[u] ?
                      -> bridge (u, v)
```

### The common mistakes

**Not skipping the parent edge.** Every child then "reaches" its parent, and no bridge is ever found.

**Using `>=` instead of `>`.** That is the articulation-point test. With `>=`, a triangle reports bridges that are not there.

**Using `low[v]` instead of `disc[v]` for a back edge.** Harmless for bridges, wrong for articulation points - learn the version that works for both.

**Starting `disc` at `0` as the unvisited marker.** Node `0`'s real discovery time is `0`, so it looks unvisited forever.

### What to remember in six months

> `disc` is when you arrived. `low` is how far back your subtree can reach. A bridge is a tree edge whose child subtree cannot reach above its parent: `low[v] > disc[u]`.

The same DFS, with one comparison changed to `>=` and a special rule for the root, finds articulation points (tomorrow). Extended with a stack, it finds strongly connected components (Tarjan's SCC) and biconnected components.
