=== intro ===
Day 3 taught the forward-moving write pointer. Today the same idea runs **backwards** - and the direction is the entire trick.

> When writing into an array would destroy data you still need to read, try filling it from the end instead.

=== problem ===
`nums1` has length `m + n`. Its first `m` slots hold sorted values; the last `n` are padding zeros. `nums2` holds `n` sorted values. Merge `nums2` into `nums1` so `nums1` ends up fully sorted, **in-place**.

```text
nums1 = [1, 2, 3, 0, 0, 0],  m = 3
nums2 = [2, 5, 6],           n = 3

result: [1, 2, 2, 3, 5, 6]
```

### Read the setup carefully

The padding is the whole point. `nums1` is **already big enough** to hold the answer - the problem has handed you the output buffer disguised as the input. There is no allocation to do and no array to return; you mutate `nums1`.

The zeros are **not data**. They are empty space. Treating them as values to be sorted is the most common wrong start.

### Second example

```text
nums1 = [1], m = 1
nums2 = [],  n = 0   ->  [1]

nums1 = [0], m = 0
nums2 = [1], n = 1   ->  [1]
```

The `m = 0` case matters: `nums1` contributes nothing and the answer is entirely `nums2`.

=== pattern ===
**Two pointers, merging from the end.**

This is the merge step of merge sort, with one twist. The classic merge walks both inputs left to right and appends the smaller value to a fresh output array. Here there is no fresh array - the output has to live inside `nums1`.

Go left to right and you immediately destroy data:

```text
nums1 = [1, 2, 3, 0, 0, 0]
nums2 = [2, 5, 6]

write 1 at index 0  ok
write 2 at index 1  ok  (from nums2)
                        but nums1[1] was 2, still unread - now gone
```

The fix is to notice **where the free space is**. The empty slots are at the **end**. So write there, largest first, and the write pointer starts beyond everything still unread.

### Recognising it

Reach for back-to-front filling when:

- the output must go into one of the inputs
- the spare capacity is at the end
- forward writing would overwrite unread input

The mental question:

> Is there a direction in which the slot I am writing to is guaranteed to be one I no longer need?

=== bruteForce ===
Forget the structure. The obvious move: dump `nums2` into the tail of `nums1`, then sort the whole thing.

### Dry run

```text
nums1 = [1, 2, 3, 0, 0, 0], m = 3
nums2 = [2, 5, 6],          n = 3
```

**Phase 1 - copy `nums2` into the padding:**

| j | nums2[j] | writes to nums1[m + j] | nums1 after |
| -: | -------: | ---------------------: | :---------- |
| 0 | 2 | index 3 | `[1, 2, 3, 2, 0, 0]` |
| 1 | 5 | index 4 | `[1, 2, 3, 2, 5, 0]` |
| 2 | 6 | index 5 | `[1, 2, 3, 2, 5, 6]` |

**Phase 2 - sort the whole array:**

```text
[1, 2, 3, 2, 5, 6]  ->  Arrays.sort  ->  [1, 2, 2, 3, 5, 6]
```

Correct.

### Java

```java
import java.util.Arrays;

class Solution {
    public void merge(int[] nums1, int m, int[] nums2, int n) {

        for (int j = 0; j < n; j++) {
            nums1[m + j] = nums2[j];
        }

        Arrays.sort(nums1);
    }
}
```

### Complexity

**Time:** `O((m + n) log(m + n))` — **Space:** `O(1)` extra (sorting in place)

### Where it hurts

The sort is doing work that has already been done. Both inputs arrived **sorted**, and phase 2 throws that away and rediscovers the ordering from scratch.

Look at the array after phase 1: `[1, 2, 3, 2, 5, 6]`. It is not random - it is two sorted runs stuck together. A general-purpose sort has no idea; it will compare `1` against `3` and `5` against `6` as if it knew nothing.

That is the waste: **we paid `log` for information we were given for free.**

=== optimization ===
Two sorted lists can be merged in linear time by repeatedly taking the smaller head. The only obstacle is where to put the result.

### The key observation

The free space is at the **end** of `nums1`. So build the answer from the **largest value down**:

- `i` - last real element of `nums1`, starts at `m - 1`
- `j` - last element of `nums2`, starts at `n - 1`
- `k` - where the next value goes, starts at `m + n - 1`

At each step, compare `nums1[i]` and `nums2[j]`, write the **larger** at `k`, then step that pointer and `k` back one.

### Why this can never clobber unread data

`k` starts at `m + n - 1` and `i` starts at `m - 1`. Since `n >= 0`, we have `k >= i` at the start, and `k` decreases at least as fast as `i` (it moves every step; `i` only moves when `nums1` wins). So `k` is always at or ahead of `i` - the slot we write to is never one we still need to read.

### Dry run

```text
nums1 = [1, 2, 3, 0, 0, 0], m = 3
nums2 = [2, 5, 6],          n = 3
```

| step | i | j | k | nums1[i] | nums2[j] | larger | write | nums1 after |
| ---: | -: | -: | -: | -------: | -------: | :----- | :---- | :---------- |
| start | 2 | 2 | 5 | 3 | 6 | - | - | `[1, 2, 3, 0, 0, 0]` |
| 1 | 2 | 2 | 5 | 3 | 6 | nums2 | `nums1[5] = 6` | `[1, 2, 3, 0, 0, 6]` |
| 2 | 2 | 1 | 4 | 3 | 5 | nums2 | `nums1[4] = 5` | `[1, 2, 3, 0, 5, 6]` |
| 3 | 2 | 0 | 3 | 3 | 2 | nums1 | `nums1[3] = 3` | `[1, 2, 3, 3, 5, 6]` |
| 4 | 1 | 0 | 2 | 2 | 2 | tie -> nums2 | `nums1[2] = 2` | `[1, 2, 2, 3, 5, 6]` |
| 5 | 1 | -1 | 1 | 2 | - | nums2 empty | stop | `[1, 2, 2, 3, 5, 6]` |

Step 3 is the one to stare at: we write `3` into index 3, a padding slot. Step 4 writes `2` into index 2 - overwriting the `3` we just read at `i = 2`. Already consumed, so it costs nothing.

### Why the loop can stop when `nums2` is empty

At step 5, `j` has run out but `i = 1` still points at real data - `[1, 2]`. Those values are **already sitting in indices 0 and 1**, exactly where they belong. Nothing to move.

The reverse is not true: if `nums1` runs out first, the remaining `nums2` values must still be copied down, because they are in the wrong array.

=== complexity ===
### Time

Every step writes exactly one value into its final position, and there are `m + n` positions.

```text
O(m + n)
```

### Space

Three integers.

```text
O(1)
```

### Comparison

| Approach | Time | Space | Uses the sortedness? |
| :------- | ---: | ----: | :------------------- |
| Copy + sort | `O((m+n) log(m+n))` | `O(1)` | no |
| Merge from the end | **`O(m + n)`** | `O(1)` | yes |

Dropping the `log` is the whole gain, and it comes from exploiting a property the input already had.

### The forward-merge trap

You could merge left to right into a **temporary** array and copy back: also `O(m + n)` time, but `O(m + n)` space. Same complexity class in time, strictly worse in space, and it ignores the buffer the problem handed you. Filling backwards is what makes `O(1)` possible.

=== implementation ===
```java
class Solution {
    public void merge(int[] nums1, int m, int[] nums2, int n) {

        int i = m - 1;          // last real value in nums1
        int j = n - 1;          // last value in nums2
        int k = m + n - 1;      // next slot to fill, from the back

        // Only nums2 needs draining. Anything left in nums1 is already home.
        while (j >= 0) {
            if (i >= 0 && nums1[i] > nums2[j]) {
                nums1[k] = nums1[i];
                i--;
            } else {
                nums1[k] = nums2[j];
                j--;
            }
            k--;
        }
    }
}
```

### The lines that matter

**1.**

```java
int k = m + n - 1;
```

The write cursor starts at the very last slot, not at `m`. This is what guarantees `k >= i` for the whole run.

**2.**

```java
while (j >= 0) {
```

The loop condition is on `j` alone, not `i >= 0 || j >= 0`. Once `nums2` is drained we are finished, because leftover `nums1` values are already in place. Looping on both would work but performs pointless self-assignments.

**3.**

```java
if (i >= 0 && nums1[i] > nums2[j])
```

The `i >= 0` guard comes **first** and short-circuits. Without it, an exhausted `nums1` (`i == -1`) would index out of bounds. Java's `&&` guarantees `nums1[i]` is never evaluated when `i < 0`.

### Why `>` and not `>=`

With `>`, a tie sends `nums2`'s value first. Either is correct for equal values, but `>` keeps the code taking from `nums2` on ties, which drains `j` faster and ends the loop sooner.

### Java notes

- `void` return: `nums1` is mutated in place. Reassigning `nums1 = something` inside the method would change only the local reference and the caller would see nothing.
- No `Arrays.copyOf`, no `System.arraycopy` needed. The whole merge is three index variables.

=== edgeCases ===
### nums2 is empty

```text
nums1 = [1], m = 1, nums2 = [], n = 0  ->  [1]
```

`j` starts at `-1`, the loop never runs, `nums1` is untouched. Correct.

### nums1 has no real elements

```text
nums1 = [0], m = 0, nums2 = [1], n = 1  ->  [1]
```

`i = -1` from the start, so the guard always fails and every value comes from `nums2`. This is exactly the case the `i >= 0` check exists for - without it, the first iteration reads `nums1[-1]` and throws.

### All of nums2 is smaller

```text
nums1 = [4, 5, 6, 0, 0, 0], m = 3
nums2 = [1, 2, 3],          n = 3
```

Steps 1-3 drain `nums1` into the back half; steps 4-6 copy `nums2` into the front. Result `[1, 2, 3, 4, 5, 6]`. The `i >= 0` guard carries the last three iterations.

### All of nums2 is larger

```text
nums1 = [1, 2, 3, 0, 0, 0], nums2 = [4, 5, 6]
```

`nums2` drains first into indices 5, 4, 3; the loop exits with `i = 2` and `nums1`'s values already correct at 0, 1, 2. Zero wasted writes.

### Duplicates across both arrays

```text
nums1 = [1, 2, 2, 0, 0], m = 3
nums2 = [2, 2],          n = 2   ->  [1, 2, 2, 2, 2]
```

Ties are handled by the `else` branch. Stability is not required here (the values are indistinguishable), but the merge is stable anyway.

### Both empty

```text
m = 0, n = 0  ->  []
```

`j = -1`, loop body never executes. No index touched.

=== takeaway ===
> When the output has to go into one of the inputs, ask **which end has the free space** - and fill from there.

### The core observation

Forward writing fails only because the write cursor lands on unread data. Reversing direction puts the cursor in the padding, where `k >= i` holds permanently. Same merge, same comparisons, one direction flipped.

### The pattern trigger

```text
      Output must live inside an input?
                   |
                   v
      Where is the spare capacity?
             /            \
        at the front     at the end
             |                |
      merge forwards    merge BACKWARDS
                        largest value first
```

### The common mistake

Looping on `i >= 0 || j >= 0` and forgetting the `i >= 0` short-circuit inside the comparison. Both produce the same output on the happy path; the second throws `ArrayIndexOutOfBoundsException` the moment `nums1` drains first, which the `m = 0` test hits immediately.

### What to remember in six months

> Sorted input is information. If your solution calls a general sort on data that arrived sorted, you are paying `log n` for something you were given.

That is the same instinct behind binary search on a sorted array, the two-pointer scan in Valid Palindrome, and every merge in merge sort. Today it is worth exactly one `log` factor.
