=== intro ===
Days 1 and 2 were about **remembering** the right thing. Today is about **writing** to the right place.

> When a problem says "in-place", stop thinking about where elements are and start thinking about where the next one should *go*. One pointer that only ever moves forward is often the whole answer.

=== problem ===
Given an array, move every `0` to the end while keeping the **relative order** of the non-zero elements. Do it **in-place**.

```text
nums = [0, 1, 0, 3, 12]
```

becomes

```text
[1, 3, 12, 0, 0]
```

### Read the three constraints carefully - each one kills a different easy solution

1. **In-place.** You may not return a new array. This rules out the obvious "build a filtered copy" answer.
2. **Relative order preserved.** `1`, `3`, `12` must stay in that sequence. This rules out the tempting trick of swapping each zero with the last element, which is `O(n)` but scrambles the order.
3. **All zeros at the end.** Not "somewhere"; the tail must be entirely zeros.

### A second example

```text
nums = [0]      ->  [0]
nums = [1, 0]   ->  [1, 0]
nums = [0, 1]   ->  [1, 0]
```

Small ones matter here, because the pointer logic is easy to get subtly wrong at the boundaries.

=== pattern ===
**Two Pointers**, in its *fast / slow* (also called *read / write*) form.

This is a different shape from the two pointers you use on a sorted array, where the pair starts at opposite ends and closes inward. Here **both pointers move left to right**, at different speeds:

- The **read** pointer visits every element, one by one. It is just the loop variable.
- The **write** pointer marks the next slot where a kept element belongs.

The invariant that makes it work:

> Everything before `write` is already the correct answer-so-far, in the correct order.

The read pointer scans ahead and decides what to keep; the write pointer only advances when something is kept. Because both only move forward and the write pointer never outruns the read pointer, no element is ever overwritten before it has been read.

### Recognising it

Reach for read/write pointers whenever the task is:

- "remove all X in-place"
- "move all X to the end"
- "deduplicate a sorted array in-place"
- "compact / filter this array without extra space"

The mental question:

> Can I walk this array once, deciding for each element whether it belongs in the output - and if so, writing it to the next free slot?

If yes, you need one extra integer, not an extra array.

=== bruteForce ===
Forget in-place for a moment. What would you obviously do?

Build a new array. Walk the input; copy every non-zero into it; then pad the rest with zeros. Finally, copy it back over the original.

### Walkthrough

```text
nums = [0, 1, 0, 3, 12]
```

```text
collect non-zeros:  [1, 3, 12]
pad to length 5:    [1, 3, 12, 0, 0]
copy back into nums
```

Correct, and easy to reason about.

### Java

```java
class Solution {
    public void moveZeroes(int[] nums) {

        int[] result = new int[nums.length];
        int pos = 0;

        for (int num : nums) {
            if (num != 0) {
                result[pos] = num;
                pos++;
            }
        }
        // remaining slots are already 0 - Java zero-fills new int arrays

        for (int i = 0; i < nums.length; i++) {
            nums[i] = result[i];
        }
    }
}
```

### Complexity

**Time:** `O(n)` — **Space:** `O(n)`

### Where it hurts

The time is already optimal - you cannot solve this without looking at every element. The problem is the **space**, and more importantly, it **violates the stated constraint**. The interviewer said in-place; this allocates a second array the same size as the first.

So the question is not "how do I make this faster". It is:

> Do I actually need that second array, or can the original hold both the input I have not read yet and the output I have already produced?

=== optimization ===
Here is the observation that makes the extra array unnecessary.

The write pointer **can never get ahead of the read pointer**. `write` only advances when we keep an element, and we keep at most one element per read. So `write <= read`, always.

That means the slot we are about to write to has **already been read**. Overwriting it destroys nothing we still need.

The original array can therefore hold both things at once:

```text
[  finished output  |  not yet read  ]
                    ^
                  write/read frontier
```

### The two-phase version

**Phase 1** - walk the array; every time you see a non-zero, write it at `write` and advance.

**Phase 2** - everything from `write` to the end is leftover; fill it with `0`.

### Dry run

```text
nums = [0, 1, 0, 3, 12]
```

| read | nums[read] | zero? | action | array after | write |
| ---: | ---------: | :---- | :----- | :---------- | ----: |
| - | - | - | start | `[0, 1, 0, 3, 12]` | 0 |
| 0 | 0 | yes | skip | `[0, 1, 0, 3, 12]` | 0 |
| 1 | 1 | no | `nums[0] = 1` | `[1, 1, 0, 3, 12]` | 1 |
| 2 | 0 | yes | skip | `[1, 1, 0, 3, 12]` | 1 |
| 3 | 3 | no | `nums[1] = 3` | `[1, 3, 0, 3, 12]` | 2 |
| 4 | 12 | no | `nums[2] = 12` | `[1, 3, 12, 3, 12]` | 3 |

Phase 1 leaves `[1, 3, 12, 3, 12]`. The first three slots are the answer; the tail is stale garbage - old values we already copied forward.

**Phase 2** - zero-fill from index `write = 3`:

```text
[1, 3, 12, 0, 0]
```

Notice row `read = 1`: we wrote `1` into index `0`, over a value we had already read and decided to discard. That is the invariant doing its job.

### The swap variant

Instead of two phases, swap `nums[read]` and `nums[write]` whenever `nums[read]` is non-zero:

```text
[0, 1, 0, 3, 12]
read=0: 0 -> skip
read=1: swap idx1,idx0 -> [1, 0, 0, 3, 12]   write=1
read=2: 0 -> skip
read=3: swap idx3,idx1 -> [1, 3, 0, 0, 12]   write=2
read=4: swap idx4,idx2 -> [1, 3, 12, 0, 0]   write=3
```

Done in a single pass, no zero-fill needed - the zeros get pushed backwards for free. This is the version that answers the follow-up about minimising writes, because it never writes to a slot where the correct value already sits.

=== complexity ===
### Time

One pass for phase 1, one for phase 2. Two passes over `n` elements is `2n` operations, which is `O(n)` - constants drop.

```text
O(n)
```

The swap version does it in a single pass, but it is the same `O(n)`. "Fewer passes" and "better complexity" are different claims; only say the one that is true.

### Space

Two integers: `write`, and the loop counter.

```text
O(1)
```

### Comparison

| Approach | Time | Space | In-place? |
| :------- | ---: | ----: | :-------- |
| Copy to new array | `O(n)` | `O(n)` | no |
| Read/write, two phases | `O(n)` | **`O(1)`** | yes |
| Read/write, swapping | `O(n)` | **`O(1)`** | yes, fewest writes |

### On write count

For `[1, 2, 3, 4, 5]` (no zeros at all):

- Two-phase writes `nums[i] = nums[i]` five times - five pointless writes.
- Swapping checks `read == write` and can skip, doing **zero** writes.

Same complexity, genuinely different behaviour. If an interviewer asks "can you reduce the number of writes", this is the answer they want.

=== implementation ===
```java
class Solution {
    public void moveZeroes(int[] nums) {

        // Next slot where a kept (non-zero) element belongs.
        int write = 0;

        // Phase 1: compact the non-zeros to the front, order preserved.
        for (int read = 0; read < nums.length; read++) {
            if (nums[read] != 0) {
                nums[write] = nums[read];
                write++;
            }
        }

        // Phase 2: everything from `write` onward is stale - zero it out.
        while (write < nums.length) {
            nums[write] = 0;
            write++;
        }
    }
}
```

### The lines that matter

**1.**

```java
int write = 0;
```

Not an index into the input - a cursor into the **output**, which happens to live in the same array. Naming it `write` (rather than `j` or `slow`) is worth doing out loud in an interview; it tells the reader what the invariant is.

**2.**

```java
if (nums[read] != 0) { nums[write] = nums[read]; write++; }
```

`read` advances unconditionally; `write` advances only on a keep. That gap between them is exactly the number of zeros seen so far.

**3.**

```java
while (write < nums.length) { nums[write] = 0; write++; }
```

`write` is reused as the start of the tail. After phase 1 it holds the count of non-zeros, which is precisely where the zeros begin.

### The swap version, for the follow-up

```java
class Solution {
    public void moveZeroes(int[] nums) {

        int write = 0;

        for (int read = 0; read < nums.length; read++) {
            if (nums[read] != 0) {
                // Skip the self-swap when nothing needs to move.
                if (read != write) {
                    int temp = nums[write];
                    nums[write] = nums[read];
                    nums[read] = temp;
                }
                write++;
            }
        }
    }
}
```

### Java notes

- The method returns `void`. Java arrays are objects, so mutating `nums` is visible to the caller - returning a new array would *not* satisfy "in-place".
- `new int[n]` in the brute force is zero-filled by the JVM, which is why that version needs no explicit padding. Do not rely on that if you ever port this to C.

=== edgeCases ===
### All zeros

```text
[0, 0, 0]  ->  [0, 0, 0]
```

Phase 1 keeps nothing, so `write` stays `0`. Phase 2 fills all three slots with `0`. Correct, no special case.

### No zeros

```text
[1, 2, 3]  ->  [1, 2, 3]
```

Phase 1 writes each element onto itself; `write` ends at `3`, so phase 2 does nothing. Correct, though as noted it performs three redundant writes - the swap version avoids them.

### Single element

```text
[0]  ->  [0]
[7]  ->  [7]
```

Both work. The loop runs once and the phases handle the rest.

### Empty array

```text
[]  ->  []
```

Both loops have zero iterations. No index is ever touched, so there is no out-of-bounds risk.

### Zeros already at the end

```text
[1, 2, 0, 0]  ->  [1, 2, 0, 0]
```

Phase 1 writes `1` and `2` onto themselves and stops at `write = 2`; phase 2 rewrites the two zeros. Correct, just not minimal in writes.

### Leading zeros - the case that breaks naive attempts

```text
[0, 0, 1]  ->  [1, 0, 0]
```

The `1` has to travel from index 2 to index 0, jumping **two** slots. Any solution that only ever swaps adjacent elements would need multiple passes here. The write pointer handles the jump in one step, because it tracks the destination rather than a neighbour.

### The order-destroying trap

A tempting wrong answer: when you see a zero, swap it with the last unprocessed element and shrink the range. That is `O(n)` and it moves zeros to the end - but:

```text
[0, 1, 3, 12]  ->  swap idx0 with idx3  ->  [12, 1, 3, 0]
```

`12` is now first. Relative order destroyed. This passes a "are all zeros at the end" check and fails the actual problem, which is why constraint 2 is worth reading twice.

=== takeaway ===
> When you see **"in-place"** plus **"remove / move / filter these elements"**, reach for a **write pointer**. The read pointer decides; the write pointer places.

### The core observation

The write pointer can never overtake the read pointer, so every slot you write to has already been read. That single fact is what lets one array hold the finished output and the unread input at the same time - and it is why no second array is needed.

### The pattern trigger

```text
     read ----> visits every element
                        |
                        v
              Does this element belong in the output?
                   /              \
                 no                yes
                  |                 |
              do nothing     nums[write] = nums[read]
                                    write++
                        |
                        v
        everything before `write` is the finished answer
```

### The common mistake

Preserving *presence* but destroying *order*. Swapping with the far end, or sorting, or partitioning like quicksort, all get the zeros to the back and all fail. Whenever a problem says "relative order", a solution that reorders the kept elements is wrong no matter how fast it is.

### What to remember in six months

> `write` is not an index into the input. It is a cursor into the output that happens to share storage with the input.

Once that clicks, a whole family of problems collapses into the same six lines: Remove Element (LC 27), Remove Duplicates from Sorted Array (LC 26), Remove Duplicates II (LC 80), Sort Colors (LC 75), and this one. They differ only in the `if` condition that decides what to keep.
