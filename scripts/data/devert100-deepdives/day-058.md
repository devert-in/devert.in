=== intro ===
Yesterday you **verified** the BST ordering rule, and found the second way to see it: a valid BST's inorder traversal is strictly increasing. Today you **use** that fact. If walking the tree in inorder produces the values in sorted order, then the k-th smallest value is simply the k-th node that walk reaches - and you can stop there.

> When a structure already stores data in order, never sort it again. Find the traversal that reads the order out, and stop the moment you have what you need.

=== problem ===
Given the `root` of a binary search tree and an integer `k`, return the **k-th smallest** value in the tree (1-indexed).

```text
          5
         / \
        3   6
       / \
      2   4
     /
    1

root   = [5, 3, 6, 2, 4, null, null, 1],  k = 3
output = 3
```

All values in sorted order:

| rank | 1 | 2 | 3 | 4 | 5 | 6 |
| :--- | -: | -: | -: | -: | -: | -: |
| value | 1 | 2 | **3** | 4 | 5 | 6 |

The 3rd smallest is `3`.

### What the BST gives you

The tree is not arbitrary. For every node, everything in its left subtree is smaller and everything in its right subtree is larger. That is a lot of free information about rank:

```text
node 3:  left subtree {2, 1}   ->  2 values are smaller than 3 in its own subtree
node 5:  left subtree {3, 2, 4, 1}  ->  4 values are smaller than 5 overall
```

A solution that ignores this ordering is doing work the tree has already done.

### Constraints that matter

| fact | consequence |
| :--- | :---------- |
| `1 <= k <= n <= 10^4` | `k` is always valid - no "not found" case to handle |
| values are distinct (it is a BST) | "k-th smallest" is unambiguous |
| follow-up: the tree is modified often and queried often | a per-query `O(n)` walk is too slow; see the implementation section |

### What makes it non-trivial

Finding *a* correct answer is easy: dump every value, sort, index. The point of the problem is to notice that **sorting is redundant** for a BST, and then to notice that even a full traversal is more than you need when `k` is small.

=== pattern ===
**Inorder traversal**, iterative, with early exit.

### Why inorder

Inorder visits **left subtree, node, right subtree**. In a BST that is "everything smaller, then me, then everything larger" - recursively, at every node. So the order nodes are visited **is** sorted order:

```text
          5
         / \
        3   6            inorder:  1, 2, 3, 4, 5, 6
       / \
      2   4
     /
    1
```

Then "k-th smallest" becomes "k-th node visited in inorder". Count visits; stop at `k`.

### Why iterative

A recursive inorder can be stopped early, but it takes a global counter and a flag checked after every call. An explicit stack makes the stop a plain `return`. It also makes the cost visible: the stack holds the path from the root to the current node, so its size is at most `h`.

### The stack's job

The tricky part of iterative inorder is knowing what to visit next. The rule:

```text
1. Slide left as far as possible, pushing every node on the way.
   (The top of the stack is now the smallest unvisited node.)
2. Pop it. That is the next value in sorted order.
3. Move to its right child and repeat from step 1.
   (Its right subtree holds the values just above it.)
```

### Recognising it

Reach for an early-exit inorder walk when:

- the input is a **BST** and the question is about **rank** or **order** - k-th smallest, k-th largest (reverse inorder), the successor of a value, two values summing to a target
- you would otherwise "collect into a list and sort"
- the answer might be found long before the whole tree is read

The mental question:

> Does this structure already hold my data in sorted order? If yes, which traversal reads that order out - and how early can I stop?

=== bruteForce ===
Ignore that it is a BST. Collect every value with any traversal, sort the list, and return the element at index `k - 1`.

### Step logic

1. Traverse the whole tree (preorder here), appending each value to a list.
2. Sort the list.
3. Return `list.get(k - 1)`.

### Dry run

```text
          5
         / \
        3   6
       / \
      2   4
     /
    1

k = 3
```

**Phase 1 - collect** (preorder: node, left, right):

| step | visit | list after |
| ---: | ----: | :--------- |
| 1 | 5 | `[5]` |
| 2 | 3 | `[5, 3]` |
| 3 | 2 | `[5, 3, 2]` |
| 4 | 1 | `[5, 3, 2, 1]` |
| 5 | 4 | `[5, 3, 2, 1, 4]` |
| 6 | 6 | `[5, 3, 2, 1, 4, 6]` |

**Phase 2 - sort:**

```text
[5, 3, 2, 1, 4, 6]  ->  [1, 2, 3, 4, 5, 6]
```

**Phase 3 - index:**

```text
k - 1 = 2   ->   list.get(2) = 3
```

```text
answer = 3
```

Correct. Six nodes visited, six values stored, one `O(n log n)` sort - to read off the third element.

### Java

```java
class Solution {
    public int kthSmallest(TreeNode root, int k) {

        List<Integer> values = new ArrayList<>();
        collect(root, values);

        Collections.sort(values);

        return values.get(k - 1);
    }

    private void collect(TreeNode node, List<Integer> values) {
        if (node == null) return;
        values.add(node.val);
        collect(node.left, values);
        collect(node.right, values);
    }
}
```

### Complexity

**Time:** `O(n log n)` - **Space:** `O(n)` for the list (plus `O(h)` recursion)

### Where it hurts

Two separate wastes, and they are fixed by two separate observations.

**Waste 1: the sort.** The BST already holds the values in order. Preorder scrambled that order (`5, 3, 2, 1, 4, 6`), and then we paid `O(n log n)` to unscramble it. Had we collected in **inorder**, the list would have come out `[1, 2, 3, 4, 5, 6]` with no sort at all.

**Waste 2: reading everything.** Even with an inorder collection, we store all `n` values to use one. With `k = 3`, nodes `4`, `5` and `6` contribute nothing. With `n = 10^4` and `k = 1`, the brute force reads ten thousand nodes to return the leftmost one.

The question becomes:

> Can I walk the tree in sorted order and stop at the k-th node, without storing anything I have already passed?

=== optimization ===
### Observation 1 - inorder is sorted

Visiting left, node, right in a BST produces values in increasing order. So the k-th node *visited* in inorder is the k-th smallest. No list, no sort - just a counter.

### Observation 2 - stop at k

Nothing after the k-th visit can change the answer. If the traversal is iterative, stopping is a `return` from inside the loop. Nodes beyond the k-th are never visited, and their subtrees are never even pushed.

### Deriving the loop

```text
cur = root
loop:
    while cur is not null:  push cur;  cur = cur.left     # slide left
    cur = pop()                                           # next in sorted order
    k = k - 1
    if k == 0: return cur.val
    cur = cur.right                                       # successors are on the right
```

`k` counts down rather than a separate counter counting up - one fewer variable.

### Dry run - same tree, k = 3

```text
          5
         / \
        3   6
       / \
      2   4
     /
    1
```

Stack is written bottom to top (top on the right).

| step | action | stack after | cur after | k after | popped value |
| ---: | :----- | :---------- | :-------- | ------: | -----------: |
| start | - | `[]` | 5 | 3 | - |
| 1 | slide left: push 5, 3, 2, 1 | `[5, 3, 2, 1]` | null | 3 | - |
| 2 | pop 1, `k--` | `[5, 3, 2]` | 1 | 2 | 1 |
| 3 | `k != 0`, move right | `[5, 3, 2]` | null (1 has no right) | 2 | - |
| 4 | slide left: nothing to push | `[5, 3, 2]` | null | 2 | - |
| 5 | pop 2, `k--` | `[5, 3]` | 2 | 1 | 2 |
| 6 | `k != 0`, move right | `[5, 3]` | null (2 has no right) | 1 | - |
| 7 | slide left: nothing to push | `[5, 3]` | null | 1 | - |
| 8 | pop 3, `k--` | `[5]` | 3 | **0** | 3 |
| 9 | `k == 0` -> **return 3** | | | | |

```text
answer = 3
```

Count the work: 4 pushes (the left spine, length `h = 4`) and 3 pops (`k = 3`). Node `4` was never pushed, nor was `6`. Node `5` was pushed but never popped. Compare the brute force: 6 visits, 6 stored values, one sort.

### Where `O(h + k)` comes from

Before the first pop, the walk must reach the smallest value, which sits at the bottom of the left spine - up to `h` pushes. After that, each of the `k` pops is followed by at most a short slide into a right subtree, and every node pushed during those slides is one that will be popped soon after or lies on a path of length at most `h`. Total: `O(h + k)`.

### Dry run - k = 6 (the largest)

The worst case for early exit: every node is popped.

```text
pops in order:  1, 2, 3, 4, 5, 6        k: 5, 4, 3, 2, 1, 0   -> return 6
```

Here `O(h + k)` is `O(n)` - the same as a full traversal, but still no sort and no list.

=== complexity ===
### Time

```text
O(h + k)
```

`h` to reach the minimum, `k` pops to reach the answer. On a balanced tree that is `O(log n + k)`; when `k` is near `n`, or the tree is a chain, it is `O(n)`.

### Space

The stack holds at most one root-to-node path.

```text
O(h)
```

No list of values is ever built.

### Comparison

| Approach | Time | Extra space | Uses BST order? |
| :------- | ---: | ----------: | :-------------- |
| Collect all + sort | `O(n log n)` | `O(n)` | no |
| Recursive inorder into a list | `O(n)` | `O(n)` | yes, but reads everything |
| Iterative inorder, stop at k | **`O(h + k)`** | **`O(h)`** | yes, and stops early |
| Subtree sizes (follow-up) | `O(h)` per query | `O(n)` once, stored in nodes | yes, skips whole subtrees |

=== implementation ===
```java
class Solution {
    public int kthSmallest(TreeNode root, int k) {

        Deque<TreeNode> stack = new ArrayDeque<>();
        TreeNode cur = root;

        while (true) {
            while (cur != null) {          // slide to the smallest unvisited node
                stack.push(cur);
                cur = cur.left;
            }

            cur = stack.pop();             // next value in sorted order
            k--;
            if (k == 0) return cur.val;    // the k-th pop is the answer

            cur = cur.right;               // the values just above it live here
        }
    }
}
```

### The lines that matter

**1.**

```java
while (cur != null) {          // slide to the smallest unvisited node
    stack.push(cur);
    cur = cur.left;
}
```

The left slide. Every node on the way down is larger than the one below it, so it is pushed to be visited *later*, after its left subtree is done. When the slide ends, the top of the stack is the smallest value not yet visited.

**2.**

```java
k--;
if (k == 0) return cur.val;    // the k-th pop is the answer
```

Decrement first, then test: the first pop takes `k` from `k` to `k - 1`, so with `k = 1` the first pop returns immediately - the minimum. Counting down means no separate counter variable.

**3.**

```java
cur = cur.right;               // the values just above it live here
```

After visiting a node, its in-order successor is either the leftmost node of its right subtree, or (if there is no right subtree) the next node waiting on the stack. Setting `cur` to the right child and looping covers both: if it is `null`, the slide pushes nothing and the next pop takes from the stack.

### Why `while (true)` is safe

The constraints guarantee `1 <= k <= n`, so the k-th pop always happens before the stack runs dry. The compiler accepts the method without a trailing `return` because the loop never completes normally.

### The follow-up: modified often, queried often

If inserts and deletes interleave with many k-th-smallest queries, an `O(h + k)` walk per query is wasteful. Store in every node the **size of its subtree**. Then at each node, the left subtree's size says exactly how many values are smaller:

```text
leftSize = size(node.left)
k <= leftSize          ->  answer is in the left subtree
k == leftSize + 1      ->  answer is this node
k >  leftSize + 1      ->  answer is in the right subtree, as rank k - leftSize - 1
```

LeetCode's `TreeNode` has no size field, so this needs its own node type:

```java
class OrderStatisticBST {

    private static class SizedNode {
        int val;
        int size = 1;                 // nodes in this subtree, including itself
        SizedNode left, right;
        SizedNode(int val) { this.val = val; }
    }

    private SizedNode root;

    public void insert(int val) {
        root = insert(root, val);
    }

    private SizedNode insert(SizedNode node, int val) {
        if (node == null) return new SizedNode(val);
        if (val < node.val) node.left = insert(node.left, val);
        else node.right = insert(node.right, val);
        node.size++;                  // one more node somewhere below
        return node;
    }

    private static int size(SizedNode node) {
        return node == null ? 0 : node.size;
    }

    // 1-based k, assumes 1 <= k <= number of inserted values.
    public int kthSmallest(int k) {
        SizedNode node = root;
        while (true) {
            int leftSize = size(node.left);
            if (k <= leftSize) {
                node = node.left;
            } else if (k == leftSize + 1) {
                return node.val;
            } else {
                k -= leftSize + 1;    // skip the left subtree and this node
                node = node.right;
            }
        }
    }
}
```

Each query walks one root-to-node path: `O(h)`, independent of `k`. Inserts pay `O(h)` to update sizes on the way down. (Deletes must decrement sizes the same way.) With a self-balancing tree underneath, `h` stays `O(log n)`.

### Java notes

- `Deque<TreeNode> stack = new ArrayDeque<>()` with `push` / `pop` is the modern replacement for the legacy `java.util.Stack` class, which is synchronised and slower.
- `k` is a parameter, so decrementing it changes only the local copy - the caller's value is untouched.
- For **k-th largest**, run the mirror image: slide **right**, pop, move **left**. That is reverse inorder, which yields values in decreasing order.

=== edgeCases ===
### k = 1 (the minimum)

```text
root = [3, 1, 4, null, 2],  k = 1  ->  1
```

The left slide pushes `3, 1`; the first pop is `1`. Only the left spine is touched.

### k = n (the maximum)

```text
root = [5, 3, 6, 2, 4, null, null, 1],  k = 6  ->  6
```

Every node is popped. Early exit buys nothing here, which is why the bound is `O(h + k)` and not `O(h)`.

### Single node

```text
root = [1],  k = 1  ->  1
```

### Right-skewed chain

```text
root = [1, null, 2, null, 3],  k = 3  ->  3
```

Each slide pushes one node; each pop is followed by moving right. The stack never holds more than one node.

### Left-skewed chain

```text
root = [3, 2, null, 1],  k = 1  ->  1
```

The opposite shape: the first slide pushes the whole tree (`h = n = 3`) before the first pop. This is the `h` term of `O(h + k)` at its largest.

### Negative values

```text
root = [0, -5, 5],  k = 2  ->  0
```

Inorder is `-5, 0, 5`. Sign is irrelevant; only the ordering matters.

### The middle of a larger tree

```text
root = [5, 3, 6, 2, 4, null, null, 1],  k = 4  ->  4
```

The 4th pop is `4`, which is reached by moving right from `3` - the step that exercises `cur = cur.right` landing on a real node.

=== takeaway ===
> When you see **"k-th smallest / largest" in a BST**, think **inorder (or reverse inorder) with a counter, stopping at k**. Never collect and sort.

### The core observation

In a BST, inorder **is** sorted order. So rank questions reduce to counting visits in an inorder walk - and since nothing after the k-th visit matters, an iterative walk can stop there, having touched only the left spine and `k` nodes.

### The pattern trigger

```text
         BST  +  question about rank / order
                       |
                       v
        stack, cur = root
        loop:
            slide left, pushing          <- reach the smallest unvisited
            pop                          <- next in sorted order
            count it; at k -> return
            cur = right child            <- successors live there
                       |
         need it fast under many updates?
                       |
                       v
         store subtree sizes, walk one path: O(h)
```

### The common mistakes

**Sorting.** Correct and `O(n log n)`. It throws away the one property the input was given to you for.

**Collecting the full inorder list.** Better - `O(n)` - but it reads every node and stores every value to return one.

**Off-by-one on k.** `k` is 1-based. Returning on the pop where a 0-based counter equals `k` (instead of `k - 1`) returns the (k+1)-th value. Decrementing `k` before testing `k == 0` avoids the question entirely.

**Not moving to the right child.** Write `cur = null` after the pop instead of `cur = cur.right` and the walk only ever pops ancestors waiting on the stack - every right subtree is skipped, and `k = 4` on the example returns `5` instead of `4`. Drop the line entirely and it is worse: `cur` is still the popped node, the next slide pushes it straight back, and the walk pops the same node over and over.

### What to remember in six months

> A BST is a sorted array that has been folded into a tree. Inorder unfolds it, one value at a time, and you can stop unfolding whenever you like.

The same early-exit inorder walk solves Inorder Successor in BST (LC 285), Two Sum IV on a BST (LC 653, with a second, reverse-inorder stack), Minimum Absolute Difference in BST (LC 530: compare each pop with the previous one) and the BST Iterator (LC 173), which is literally this loop split into `next()` calls. Yesterday's validation used the same loop to check the order; today's uses it to read the order.

The easy answer: collect every value, sort, return index `k - 1`. `O(n log n)`. It works, and it ignores the only reason the input is a BST.

The fact that matters: an inorder traversal (left, node, right) of a BST visits values in sorted order. So the k-th smallest is just the k-th node visited. No list. No sort.

```
slide left, pushing each node
pop -> next value in sorted order
k--; if k == 0, that's the answer
move to the right child, repeat
```

Pattern: Inorder Traversal (iterative, early exit)
Time: `O(h + k)`
Space: `O(h)`

On the example, with k = 3, the walk does four pushes and three pops - and never touches the right half of the tree.

Follow-up worth knowing: if the tree changes often and is queried often, store subtree sizes in each node. Then the left subtree's size tells you which way to go, and each query is `O(h)` regardless of k.
