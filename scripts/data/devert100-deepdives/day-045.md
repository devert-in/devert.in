=== intro ===
Yesterday binary search had one job: find the target and stop. Today the array has **duplicates**, and "found it" is no longer the answer - you need the **first** copy and the **last** copy, still in `O(log n)`.

> A match at `mid` is not the end of the search. It is a fact about the answer - "the first occurrence is at `mid` or to its left" - and binary search keeps going on that fact. Recording a candidate and continuing to shrink is the move that turns "find" into "find the boundary".

=== problem ===
Given an array `nums` sorted in **non-decreasing** order (duplicates allowed) and an integer `target`, return `[first, last]` - the index of the first and last occurrence of `target`. If it is not present, return `[-1, -1]`. The required time is `O(log n)`.

```text
nums   = [5, 7, 7, 8, 8, 10]
target = 8
answer = [3, 4]
```

| index | 0 | 1 | 2 | 3 | 4 | 5 |
| :---- | -: | -: | -: | -: | -: | -: |
| value | 5 | 7 | 7 | **8** | **8** | 10 |

The `8`s occupy indices `3` and `4`, so the answer is `[3, 4]`.

```text
nums = [5, 7, 7, 8, 8, 10], target = 6   ->  [-1, -1]
nums = [],                  target = 0   ->  [-1, -1]
```

### The constraints that matter

- `0 <= nums.length <= 10^5` - the array **can be empty** here, unlike yesterday.
- `-10^9 <= nums[i], target <= 10^9`.
- **Non-decreasing**, not strictly increasing: equal values sit next to each other in one contiguous block. That is why "first" and "last" fully describe every occurrence.
- **`O(log n)`**. This is the constraint that makes the problem medium: a run of duplicates can be as long as the whole array, so anything that walks the run is `O(n)`.

### Why yesterday's code is not enough

Day 44's search returns `mid` the moment `nums[mid] == target`. On this example it lands on index `4` - a correct `8`, but it happens to be the last one; on `[8, 8, 8, 8, 8]` it would land on index `2`, which is neither first nor last. Which copy you hit depends on where the midpoints fall, so it tells you nothing about the boundaries.

=== pattern ===
**Lower Bound / Upper Bound** - binary search for a **boundary**, not a value.

Look at the array through a yes/no question instead of through its values:

```text
nums                 =  [ 5,  7,  7,  8,  8, 10]
nums[i] >= 8 ?       =  [ F,  F,  F,  T,  T,  T]    first T = 3  -> first occurrence
nums[i] >  8 ?       =  [ F,  F,  F,  F,  F,  T]    first T = 5  -> last occurrence + 1
```

Because the array is sorted, each question's answers are **monotonic**: a run of `F` followed by a run of `T`, never mixed. Finding where `F` turns into `T` is a binary search - compare at `mid`, and the answer tells you which side the switch is on.

- **Lower bound**: first index with `nums[i] >= target`. If that element equals `target`, it is the first occurrence.
- **Upper bound**: first index with `nums[i] > target`. One before it is the last occurrence.

### The equivalent "keep searching" form

The version most people write in interviews says the same thing in day 44's loop:

> On a match, **record** `mid` as the best answer so far, then keep searching **left** (for first) or **right** (for last).

The record is the safety net: if nothing better exists on that side, the recorded `mid` was the boundary.

### Recognising it

Reach for lower/upper bound when the problem says:

- "first" or "last" position of something in sorted data
- "how many times does `x` occur" in a sorted array (`last - first + 1`)
- "smallest element `>= x`" / "largest element `<= x`" (ceiling / floor)
- "insert position" (day 44's follow-up was a lower bound)

The mental question:

> Can I turn this into a yes/no question whose answers go `F F F ... T T T` across the array? Then I am looking for the first `T`.

That reframe is the bridge to everything harder in this topic. Day 46 asks it about numbers instead of indices.

=== bruteForce ===
Use what you already have. Day 44's binary search finds **some** occurrence in `O(log n)`. Duplicates are contiguous, so from that occurrence walk left while the value is still `target`, and walk right likewise.

### Step logic

1. Binary search for any index `k` with `nums[k] == target`. If none, return `[-1, -1]`.
2. `first = k`; while `first - 1 >= 0` and `nums[first - 1] == target`, decrement `first`.
3. `last = k`; while `last + 1 < n` and `nums[last + 1] == target`, increment `last`.
4. Return `[first, last]`.

### Dry run

```text
nums = [5, 7, 7, 8, 8, 10], target = 8
```

**Phase 1 - find any 8 (day 44's loop):**

| step | lo | hi | mid | nums[mid] | compare to 8 | action |
| ---: | -: | -: | --: | --------: | :----------- | :----- |
| 1 | 0 | 5 | 2 | 7 | 7 < 8 | `lo = 3` |
| 2 | 3 | 5 | 4 | 8 | **equal** | `k = 4` |

**Phase 2 - expand left from `k = 4`:**

| step | first | check index | nums[check] | still 8? | action |
| ---: | ----: | ----------: | ----------: | :------- | :----- |
| 1 | 4 | 3 | 8 | yes | `first = 3` |
| 2 | 3 | 2 | 7 | no | stop |

**Phase 3 - expand right from `k = 4`:**

| step | last | check index | nums[check] | still 8? | action |
| ---: | ---: | ----------: | ----------: | :------- | :----- |
| 1 | 4 | 5 | 10 | no | stop |

Result `[3, 4]`. Correct, and on this input it is quick: two binary-search steps and three expansion checks.

### Java

```java
class Solution {
    public int[] searchRange(int[] nums, int target) {

        // Phase 1: find any occurrence with a plain binary search.
        int lo = 0, hi = nums.length - 1, k = -1;
        while (lo <= hi) {
            int mid = lo + (hi - lo) / 2;
            if (nums[mid] == target) { k = mid; break; }
            else if (nums[mid] < target) lo = mid + 1;
            else hi = mid - 1;
        }
        if (k == -1) return new int[] { -1, -1 };

        // Phase 2 and 3: walk outward while the value is still target.
        int first = k, last = k;
        while (first - 1 >= 0 && nums[first - 1] == target) first--;
        while (last + 1 < nums.length && nums[last + 1] == target) last++;

        return new int[] { first, last };
    }
}
```

### Complexity

**Time:** `O(log n + r)` where `r` is the number of copies of `target` - which is `O(n)` worst case. **Space:** `O(1)`

### Where it hurts

Run it on an array that is nothing but the target:

```text
nums = [8, 8, 8, 8, 8, 8, 8], target = 8
```

| phase | work | steps |
| :---- | :--- | ----: |
| binary search | `mid = 3`, equal on the first comparison | 1 |
| expand left | indices 2, 1, 0 are 8, then index -1 is out of range | 3 |
| expand right | indices 4, 5, 6 are 8, then index 7 is out of range | 3 |

Seven elements, seven steps - every copy visited once. With `n = 10^5` copies, that is `10^5` steps after a binary search that took one. The `O(log n)` part is real; the walk throws it away.

The waste is specific. Every expansion step asks "is the element next to me still `target`?" and learns that the boundary is **at least one step further**. That is linear search for the boundary, one index at a time - the same mistake day 44 fixed, just aimed at a boundary instead of a value. The boundary is itself something a sorted array lets you binary search for.

=== optimization ===
### The key observation

When `nums[mid] == target` during a search for the **first** occurrence, we know two things:

1. `mid` is a valid candidate - the first occurrence is at `mid` or earlier.
2. Nothing to the right of `mid` can be the first occurrence.

So: **record `mid`, then discard the right half** (`hi = mid - 1`) exactly as if `nums[mid]` were too big. The search keeps halving, and either finds an earlier `8` (which overwrites the record) or runs out of window, in which case the record was the first.

For the **last** occurrence, mirror it: record `mid`, discard the left half (`lo = mid + 1`).

The only change from day 44 is what happens on equality. `<` and `>` are untouched.

### Deriving it step by step

1. `ans = -1`, `lo = 0`, `hi = n - 1`.
2. While `lo <= hi`: `mid = lo + (hi - lo) / 2`.
3. If `nums[mid] == target`: `ans = mid`; then `hi = mid - 1` (searching first) or `lo = mid + 1` (searching last).
4. Else if `nums[mid] < target`: `lo = mid + 1`.
5. Else: `hi = mid - 1`.
6. Return `ans`. Run once for first, once for last.

### Dry run - first occurrence

```text
nums = [5, 7, 7, 8, 8, 10], target = 8
```

| step | lo | hi | mid | nums[mid] | compare to 8 | ans after | action |
| ---: | -: | -: | --: | --------: | :----------- | --------: | :----- |
| 1 | 0 | 5 | 2 | 7 | 7 < 8 | -1 | `lo = 3` |
| 2 | 3 | 5 | 4 | 8 | equal | 4 | record, go left: `hi = 3` |
| 3 | 3 | 3 | 3 | 8 | equal | 3 | record, go left: `hi = 2` |
| - | 3 | 2 | - | - | `lo > hi` | **3** | stop |

Step 2 is exactly where day 44 would have returned `4`. Instead it records `4` and asks "is there an `8` further left?". Step 3 finds one and overwrites the record with `3`.

### Dry run - last occurrence

| step | lo | hi | mid | nums[mid] | compare to 8 | ans after | action |
| ---: | -: | -: | --: | --------: | :----------- | --------: | :----- |
| 1 | 0 | 5 | 2 | 7 | 7 < 8 | -1 | `lo = 3` |
| 2 | 3 | 5 | 4 | 8 | equal | 4 | record, go right: `lo = 5` |
| 3 | 5 | 5 | 5 | 10 | 10 > 8 | 4 | `hi = 4` |
| - | 5 | 4 | - | - | `lo > hi` | **4** | stop |

Step 3 is the safety net at work: the search went right looking for a later `8`, found `10`, and the record `4` stands.

Result: `[3, 4]`. Six comparisons in total, and that number does **not** grow with the length of the run of `8`s.

### The all-duplicates case, again

```text
nums = [8, 8, 8, 8, 8, 8, 8], target = 8   (first occurrence)
```

| step | lo | hi | mid | ans after | action |
| ---: | -: | -: | --: | --------: | :----- |
| 1 | 0 | 6 | 3 | 3 | `hi = 2` |
| 2 | 0 | 2 | 1 | 1 | `hi = 0` |
| 3 | 0 | 0 | 0 | 0 | `hi = -1` |
| - | 0 | -1 | - | **0** | stop |

Three steps where the brute force's left walk took three as well - but at `n = 10^5` this is 16 steps, not 50,000.

### Absent target - one search is enough

```text
nums = [5, 7, 7, 8, 8, 10], target = 6   (first occurrence)
```

| step | lo | hi | mid | nums[mid] | compare to 6 | ans after | action |
| ---: | -: | -: | --: | --------: | :----------- | --------: | :----- |
| 1 | 0 | 5 | 2 | 7 | 7 > 6 | -1 | `hi = 1` |
| 2 | 0 | 1 | 0 | 5 | 5 < 6 | -1 | `lo = 1` |
| 3 | 1 | 1 | 1 | 7 | 7 > 6 | -1 | `hi = 0` |
| - | 1 | 0 | - | - | `lo > hi` | **-1** | stop |

If there is no first occurrence there is no last one either, so the implementation returns `[-1, -1]` without running the second search.

=== complexity ===
### Time

Two binary searches, each halving the window per step, and neither ever stops early or walks.

```text
O(log n)
```

More precisely about `2 * log2(n)` comparisons - still `O(log n)`. For `n = 10^5` that is at most 34, regardless of how many duplicates there are.

### Space

`lo`, `hi`, `mid`, `ans`, plus the two-element result.

```text
O(1)
```

### Comparison

| Approach | Time (typical) | Time (all duplicates) | Space |
| :------- | -------------: | --------------------: | ----: |
| Linear scan for first and last | `O(n)` | `O(n)` | `O(1)` |
| Binary search + expand outward | `O(log n + r)` | `O(n)` | `O(1)` |
| Two boundary binary searches | **`O(log n)`** | **`O(log n)`** | **`O(1)`** |

The middle row is the honest stepping stone to mention in an interview: it is often fast, and the all-duplicates input is exactly the case the interviewer will ask about.

=== implementation ===
```java
class Solution {
    public int[] searchRange(int[] nums, int target) {

        int first = findBound(nums, target, true);
        if (first == -1) {
            return new int[] { -1, -1 };          // absent: skip the second search
        }
        int last = findBound(nums, target, false);

        return new int[] { first, last };
    }

    // Finds the first (findFirst = true) or last index of target, or -1.
    private int findBound(int[] nums, int target, boolean findFirst) {

        int lo = 0;
        int hi = nums.length - 1;
        int ans = -1;

        while (lo <= hi) {
            int mid = lo + (hi - lo) / 2;

            if (nums[mid] == target) {
                ans = mid;                        // a candidate - record it
                if (findFirst) {
                    hi = mid - 1;                 // an earlier copy may exist
                } else {
                    lo = mid + 1;                 // a later copy may exist
                }
            } else if (nums[mid] < target) {
                lo = mid + 1;
            } else {
                hi = mid - 1;
            }
        }

        return ans;
    }
}
```

### The lines that matter

**1.**

```java
ans = mid;                        // a candidate - record it
```

This is the line day 44 did not have. Day 44 returned here. Recording instead of returning keeps the loop alive while guaranteeing the answer is never lost.

**2.**

```java
if (findFirst) {
    hi = mid - 1;                 // an earlier copy may exist
} else {
    lo = mid + 1;                 // a later copy may exist
}
```

On a match, the loop treats `mid` as if it were "too big" (for first) or "too small" (for last). That is the entire difference between the two searches, which is why one method with a flag covers both.

**3.**

```java
int ans = -1;
```

The default doubles as the "not found" answer. If no comparison ever hits equality, `ans` is never written and `-1` comes back with no extra check.

### The lower-bound form

The same answer with two half-open lower-bound searches. `lowerBound(x)` is the first index whose value is `>= x`:

```java
class Solution {
    public int[] searchRange(int[] nums, int target) {

        int first = lowerBound(nums, target);
        if (first == nums.length || nums[first] != target) {
            return new int[] { -1, -1 };
        }
        // First index > target is the first index >= target + 1.
        int last = lowerBound(nums, target + 1) - 1;

        return new int[] { first, last };
    }

    private int lowerBound(int[] nums, int x) {
        int lo = 0, hi = nums.length;
        while (lo < hi) {
            int mid = lo + (hi - lo) / 2;
            if (nums[mid] < x) lo = mid + 1;
            else hi = mid;
        }
        return lo;
    }
}
```

`target + 1` is safe here because `target <= 10^9`. If `target` could be `Integer.MAX_VALUE`, it would overflow to `Integer.MIN_VALUE` - write a separate upper bound (`nums[mid] <= x`) instead.

### Java notes

- `new int[] { -1, -1 }` is an array literal; `new int[2]` would give `{0, 0}`, which is a plausible-looking wrong answer.
- `private` helper methods inside `Solution` are fine on LeetCode - only the public method's signature is fixed.
- The `boolean findFirst` flag keeps one loop instead of two copies that can drift apart. Two copy-pasted methods are equally correct; just make sure the only difference is the equality branch.

=== edgeCases ===
### Empty array

```text
nums = [], target = 0  ->  [-1, -1]
```

`hi = -1`, the loop never runs, `ans` stays `-1`. Allowed by this problem's constraints, unlike LC 704's.

### Single element, present

```text
nums = [1], target = 1  ->  [0, 0]
```

First and last are the same index. Both searches record `0` on their only step.

### Single element, absent

```text
nums = [1], target = 0  ->  [-1, -1]
```

### Target occurs exactly once

```text
nums = [1, 2, 3], target = 2  ->  [1, 1]
```

The first search records `1` and goes left into `[1]`, which is too small; the last search records `1` and goes right into `[3]`, too large. Both records stand.

### Every element is the target

```text
nums = [2, 2, 2, 2], target = 2  ->  [0, 3]
```

The case that turns the expand-outward approach linear. Here each search keeps moving toward its edge and ends there.

### Run at the very start

```text
nums = [1, 1, 2, 3], target = 1  ->  [0, 1]
```

### Run at the very end

```text
nums = [1, 2, 3, 3], target = 3  ->  [2, 3]
```

The last search keeps setting `lo = mid + 1` until `lo = 4 = n`, and the loop ends without ever reading `nums[4]`.

### Target in a gap

```text
nums = [5, 7, 7, 8, 8, 10], target = 6  ->  [-1, -1]
```

### Target outside the range

```text
nums = [5, 7, 7, 8, 8, 10], target = 4   ->  [-1, -1]
nums = [5, 7, 7, 8, 8, 10], target = 11  ->  [-1, -1]
```

### Negative values

```text
nums = [-3, -3, -1, 0], target = -3  ->  [0, 1]
```

Nothing about the comparisons depends on sign.

### Follow-up - count occurrences

```text
nums = [5, 7, 7, 8, 8, 10], target = 8  ->  count = 4 - 3 + 1 = 2
nums = [5, 7, 7, 8, 8, 10], target = 6  ->  count = 0
```

`last - first + 1` when present, `0` when `first == -1`. `O(log n)` counting, no matter how many copies.

=== takeaway ===
> When you see **"first" / "last" / "how many"** in **sorted data with duplicates**, think **boundary binary search**: on a match, record it and keep searching toward the side you care about.

### The core observation

In a sorted array, "is `nums[i] >= target`?" is false, false, ..., then true, true. The first occurrence is where that flips. A match at `mid` does not end the search - it proves the flip is at `mid` or to its left, which is just another way of discarding half the window.

### The pattern trigger

```text
             sorted, duplicates, need a boundary
                           |
                           v
              same loop as classic binary search
                           |
                           v
             nums[mid] == target ?
                /                    \
          searching FIRST         searching LAST
          ans = mid               ans = mid
          hi = mid - 1            lo = mid + 1
                \                    /
                           v
          window empties  ->  ans is the boundary (or -1)
```

### The common mistakes

**Returning on the first match.** The match you land on depends on where midpoints fall, not on where the run starts. It passes inputs without duplicates and fails the ones the problem is about.

**Expanding outward and calling it `O(log n)`.** It is `O(log n + r)`, and `r` can be `n`.

**Forgetting to record before moving.** `hi = mid - 1` on a match without `ans = mid` throws away the only copy you have proven exists; if it was the only one, you return `-1`.

**`target + 1` near `Integer.MAX_VALUE`.** Fine under LC 34's constraints, an overflow in general.

### What to remember in six months

> Binary search does not find values. It finds the point where a yes/no question flips from no to yes.

Classic search, lower bound, upper bound, insert position and occurrence count are all that one idea. Tomorrow the "array" disappears entirely: Sqrt(x) asks "is `m * m <= x`?" over the numbers `0..x`, and the same flip-finding loop answers it.

Yesterday's binary search stops at the first match. With duplicates, that match could be any copy of the target - the first, the last, or one in the middle - depending on where the midpoints happen to fall.

The tempting fix is to find one copy and walk outward. It works, and on an array that is all one value it walks the entire array: `O(n)`, not `O(log n)`.

The real fix is one changed line. On a match, don't return - record the index, then keep searching:

```
nums[mid] == target  ->  ans = mid; hi = mid - 1   (first occurrence)
nums[mid] == target  ->  ans = mid; lo = mid + 1   (last occurrence)
```

Pattern: Lower / Upper Bound
Time: `O(log n)`
Space: `O(1)`

The reframe that made it click: binary search doesn't find values, it finds where a yes/no question flips. "Is `nums[i] >= target`?" reads F F F T T T across a sorted array - the first occurrence is the first T.

Bonus: the count of any value in a sorted array is `last - first + 1`, in `O(log n)`.
